# 1. 背景意图 (Background)

发票备注模板（`InvoiceRemarkTem`）的 `OrgId` 存的是**公司id**（公司层级，不是部门），前端下拉选的也是公司（`GetMyPermissionCompaniesAsync`）。

此前实现把它当成「任意组织」处理，导致两个问题：

- **新增/修改校验过严**：使用 `EnsureUserOwnsOrgAsync`（要求 `orgId` 与本人 `UserOrganizationUnit` 直属组织**完全相等**）。用户通常挂在部门下（例如：青岛分公司 → 业务部），选择所属公司「青岛分公司」时会被判为「所选组织不在数据所属人(本人)所属组织范围内」，正常录入被卡死。
- **搜索过宽**：使用 `GetOrgAndDescendantIdsAsync` 把搜索公司连同其所有下属组织一起带上。既然数据只会存公司id，带下属组织没有意义，还会把下级公司的模板一起搜出来。

本次把「校验」和「搜索」都对齐到公司层级：**校验向上找公司，搜索直接相等**。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 基类新增公司层级校验方法

`CsprojBuilderAppServiceBase.EnsureUserOwnsCompanyOrgAsync(long? orgId, List<long> ownerUserIds)`

| 校验步骤 | 说明 | 报错文案 |
| :-- | :-- | :-- |
| 非空校验 | `orgId` 必填且 > 0 | 所属公司不能为空。 |
| 所属人校验 | `ownerUserIds` 必填且不能为空 | 数据所属人不能为空，无法校验所属公司。 |
| 存在校验 | `orgId` 必须是已存在的组织节点 | 所选公司不存在。 |
| 公司校验 | `orgId` 节点必须 `IsCompany = true`（不能传部门） | 所选组织不是公司，请选择公司。 |
| 归属校验 | 取数据所属人全部直属组织，逐条**向上**找到所属公司（自身是公司则取自身），`orgId` 命中任一即通过 | 所选公司不在数据所属人(本人)所属公司范围内。 |

- 「向上找公司」的口径复用基类 `GetCompanyOrgIdAsync`：取组织串（`Parents`，顶→底，含本组织）中**最接近本组织**的 `IsCompany = true` 节点，与 `OrganizationUnitAppService.GetUserCompanyIdsAsync`（每条组织链取最靠近叶子的公司）完全一致。
- 与 `EnsureUserOwnsOrgAsync` 并存、互不影响：**OrgId 存部门级组织的表继续用 `EnsureUserOwnsOrgAsync`，OrgId 存公司id 的表用 `EnsureUserOwnsCompanyOrgAsync`**。

## 2.2 发票备注模板新增/修改

`InvoiceRemarkTemAdminAppService.ValidateAsync` 中 `EnsureUserOwnsOrgAsync` → `EnsureUserOwnsCompanyOrgAsync`。

- 新增：所属人 = 当前登录人（`AbpSession.GetUserId()`）。
- 修改：所属人 = 该条数据的 `UserId`（数据所属人，非当前登录人），与原逻辑一致。
- 默认唯一校验仍按 `OrgId + CurrencyId` 精确相等（本身就是公司层级，无需调整），报错文案由「该组织该币别已存在默认发票备注模板」改为「该公司该币别已存在默认发票备注模板」。

## 2.3 发票备注模板列表搜索

`GetPagedListAsync` 中按组织搜索改为公司精确相等，移除 `GetOrgAndDescendantIdsAsync` 调用：

```csharp
// 变更前：搜公司 + 其所有下属组织
var orgSearchIds = await GetOrgAndDescendantIdsAsync(input.OrgId.Value);
.WhereIf(input.OrgId.HasValue, m => m.OrgId.HasValue && orgSearchIds.Contains(m.OrgId.Value));

// 变更后：公司层级直接相等
.WhereIf(input.OrgId.HasValue, m => m.OrgId == input.OrgId.Value);
```

`m.OrgId == input.OrgId.Value` 生成 `OrgId = @p`，`OrgId IS NULL` 的数据不会被搜出，与原 `m.OrgId.HasValue &&` 的效果一致。

# 3. 避坑指南 (Pitfalls)

- **公司层级字段不要复用 `EnsureUserOwnsOrgAsync`**：该方法是「直属组织完全相等，不判父子」，只适用于 OrgId 存部门/任意组织的表（海运出口等）。公司层级字段用它必然把「人在部门、数据挂公司」的正常场景拦掉。
- **搜索不要再套 `GetOrgAndDescendantIdsAsync`**：该方法用于「按组织搜索、数据可能挂在任意层级」的单据。公司层级数据只会存公司id，套下属组织除了多余 `IN` 子句，还会在多级公司结构下把下级公司的数据串进来。
- **多级公司只认最近的一级**：用户在「集团 → 山东分公司 → 青岛分公司 → 业务部」下时，向上找到的是**青岛分公司**（最接近的公司），录入「山东分公司」「集团」仍会被拦。这是与 `GetMyPermissionCompaniesAsync`/`GetUserCompanyIdsAsync` 一致的既有口径，如需放开到所有上级公司，需要同时调整这几处，不能只改校验。
- **修改接口的「本人」是数据所属人**：`EditAsync` 传的是 `data.UserId` 而不是当前登录人。A 建的模板由 B 修改时，校验的是 A 所属公司；这是既有口径，本次未改。
- **`DataPermissionFilterAsync` 与公司层级 OrgId**：数据权限的组织维度是「本组织及所有**下属**组织」，只有「我的公司/指定公司」权限才会覆盖到公司节点；仅有「我的部门」权限的用户，公司层级数据只能靠 `UserId` 命中可见。当前列表中该过滤被临时注释，恢复时需注意这一点。
