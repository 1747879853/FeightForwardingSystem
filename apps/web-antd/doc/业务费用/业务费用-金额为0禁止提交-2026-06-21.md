# 1. 背景意图 (Background)

费用录入阶段允许临时存在 `Amount=0` 的费用（例如先占位、待补价），因此**新建、编辑**环节不限制金额为 0。但金额为 0 的费用不应进入审核/已审核的正式状态，故在**提交审核**与**申请修改**两个会把费用推向正式状态的入口处，禁止金额为 0 的费用通过。

# 2. 核心逻辑变更 (Core Logic)

涉及文件：`src/CsprojBuilder.Application/App/OrderFee/OrderFeeAdminAppService.cs`

| 接口 | 业务动作 | 是否限制 Amount=0 |
| :-- | :-- | :-- |
| `AddAsync` / `BatchAddAsync` | 新建费用（录入状态） | 不限制（允许 0） |
| `EditAsync` / `BatchEditAsync` | 编辑费用（录入/驳回状态） | 不限制（允许 0） |
| `SubmitOrderFeeAsync` | 费用提交审核 | **限制**：`Amount==0` 抛出“金额为0的费用不可提交” |
| `ModifyOrderFeeAsync` | 已审核费用申请修改 | **限制**：`Amount==0` 抛出“金额为0的费用不可提交” |

校验逐条费用判断 `item.Amount == 0`：

- `SubmitOrderFeeAsync` 中直接使用入参 `item.Amount`（该接口持久化的就是入参金额），在数值范围校验后追加判断。
- `ModifyOrderFeeAsync` 中金额由 `item.Amount = ToFinancialRound(item.UnitPrice * item.Quantity)` 重算，判断放在重算之后，保证校验的是真实落库金额。

# 3. 避坑指南 (Pitfalls)

- **只拦 0，不拦负数**：判断使用 `== 0`，不影响负数（红冲/冲销）费用的提交。
- **重算时机**：`ModifyOrderFeeAsync` 的金额是后端按单价×数量重算的，校验必须放在重算之后，否则会校验到前端传来的旧值。
- **新建/编辑不拦**：`AddAsync`/`BatchAddAsync`/`EditAsync`/`BatchEditAsync` 本就无金额下限校验，保持原样即可允许 0。
- **批量审核未涉及**：本次只在“提交”和“申请修改”入口拦截，审核（`...AuditAsync`）环节不重复校验。
