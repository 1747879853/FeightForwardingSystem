# 费用任务按更改单拆行 — 前端对接文档

**变更日期**：2026-08-02

**变更概述**：业务上**每个更改单都是一条独立的费用任务**。此前费用任务相关接口一律按业务（`TransportOrder`）汇总，一票只返回一行，更改单的费用任务被混在主单行里，而行内的费用列表又把更改单费用整个排除掉，导致出现「费用列表是空的、但待办数量不为 0」的行。

本次把费用任务的归属维度下沉到 **(业务 + 更改单)**：任务主表 `TaskBase` 新增 `SecondId`（费用任务里就是更改单 id），费用任务列表按 `(业务, 更改单)` 拆行 —— 同一票下主单一行、每个有费用任务的更改单各一行；更改单行只返回该更改单的费用，且**会计期间返回该更改单的会计期间**。

---

## 一、前端必读的 3 个关键变化

| # | 变化 | 前端要做什么 |
| :-- | :-- | :-- |
| 1 | 行的唯一键从 `entityId` 变成 **`entityId` + `changeOrderId`** | 行 key、选中态、去重逻辑都要带上 `changeOrderId`（为 `null` 表示主单行） |
| 2 | 更改单行的 `transportOrder.accountDate` **已被替换成该更改单的会计期间** | 会计期间列**不用改取值逻辑**，继续读 `transportOrder.accountDate` 即可 |
| 3 | 详情、批量审核都要按行定位 | 点行进详情 / 勾行批量审核时，必须把该行的 `changeOrderId` **原样回传**，否则会串到同一票的其它更改单 |

> **同一票会出现多行**，`totalCount` 也随之变大（原来一票算 1 条，现在一票算「主单 + 各更改单」共 N 条）。分组统计接口的 `count` 已同步改成同一口径，两者仍然对得上。

### 3.5 changeOrder 字段（ChangeOrderSimpleDto）

| 字段名 | JSON Key | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| Id | `id` | Guid | 更改单 id，与本行 `changeOrderId` 相同 |
| AccountDate | `accountDate` | DateTime | 更改单会计期间，只取月的部分 |
| Reason | `reason` | string | 更改原因 |
| SortId | `sortId` | int | 排序 id |
| FeeLocked | `feeLocked` | bool | 该更改单是否已费用锁定 |

### 3.6 拆行与排序规则

1. **行的来源：** 只有存在费用任务（`SubmitOrderFee` / `ModifyOrderFee` / `DeleteOrderFee`）的 `(业务, 更改单)` 组合才会出现。某个更改单没有任何费用任务时**不会**产生行。
2. **行的粒度：** 同一 `(业务, 更改单)` 下的提交 / 申请修改 / 申请删除三类任务合并为一行，三个 `*ItemCount` 分别给出各类的待处理数量。
3. **`processed` 过滤：** 按本行判定。以前一票里任意一个更改单有待审核，主单行也会被 `processed=false` 捞出来，现在不会了。
4. **排序：** 固定按本行最新任务创建时间（`creationTime`）倒序，`sorting` 参数无效。
5. **`totalCount`：** 行数，不是业务票数。

## 五、接口 3 — OrderFeeTaskDetailAsync

**Summary：** 费用所有任务详情，与列表的行一一对应。

**路径：** `GET /api/services/app/OrderFeeAdmin/OrderFeeTaskDetailAsync`

**权限：** `Admin.OrderFee.Audit`

### 5.1 请求参数（OrderFeeTaskDetailInputDto）

| 字段名 | JSON Key | 类型 | 必填 | 变化 | 说明 |

| ChangeOrderId | `changeOrderId` | Guid? | 否 | **新增** | 更改单 id。不传代表查**主单**的费用任务，传了代表查该更改单的费用任务。把列表行的 `changeOrderId` 原样回传即可 |

### 5.2 请求示例

```

```

### 5.3 响应

结构同 `OrderFeeTaskListDto`（见 3.3），差异：

- 新增回显 `entityId`、`changeOrderId`（原来详情不返回 `entityId`）。
- 新增 `changeOrder` 对象，主单行为 `null`；传了 `changeOrderId` 时会替换 `transportOrder.accountDate`。
- `orderFeeTasks[]` 的每条费用带 `task` 字段（对应的任务信息），且包含「已删除但有通过的删除任务」的费用。
- **行为变化：** 不传 `changeOrderId` 时，**只返回主单费用**（以前返回整票所有费用，含更改单费用）。

### 5.4 报错

| 报错文案       | 触发条件                                               |
| :------------- | :----------------------------------------------------- |
| `业务id错误`   | `id` 对应的业务不存在                                  |
| `更改单id错误` | `changeOrderId` 不存在，或该更改单不属于 `id` 这票业务 |

## 六、接口 4 — OrderFeeTaskBatchAuditAsync

**Summary：** 费用所有任务批量审核，只审核待审核的，不能做审核后驳回。

**路径：** `POST /api/services/app/OrderFeeAdmin/OrderFeeTaskBatchAuditAsync`

## 八、费用锁定 FeeLockAsync 行为变化

**路径：** `PUT /api/services/app/TransportOrderAdmin/FeeLockAsync`（入参未变）

- 原行为：只要该票**任意一条**费用任务未处理完，锁主单和锁任何更改单都会被 `存在待审核的费用任务,不能进行费用锁定操作` 拦住。
- **新行为：** 锁主单只看主单的费用任务，锁某个更改单只看该更改单的费用任务，互不影响。

## 九、按费用操作的接口新增「同属一个更改单」校验

以下 6 个接口新增同一条校验：

| 接口                                    | 方法 |
| :-------------------------------------- | :--- |
| SubmitOrderFeeAsync（费用提交）         | POST |
| ModifyOrderFeeAsync（申请修改）         | POST |
| DeleteOrderFeeAsync（申请删除）         | POST |
| OrderFeeTaskAuditAsync（费用任务审核）  | POST |
| OrderFeeTaskWithdrawAsync（撤销提交）   | POST |
| OrderFeeTaskRejectedAsync（审核后驳回） | POST |

| 报错文案 | 触发条件 |
| :-- | :-- |
| `主单费用与更改单费用不可一起操作,不同更改单的费用也不可一起操作,请分开处理` | 一次请求的 `orderFeeIds` / `orderFees` 里出现了两种以上的更改单归属（含「主单 + 更改单」混选） |

原因：每个更改单是一条独立任务，一次操作的费用必须能落到唯一一条任务上。前端本来就是在某一行（某个更改单）的费用面板里操作，正常不会触发；跨行批量勾选的场景需要拆成多次请求。

**新增费用的归属改为后端接管：** `SubmitOrderFeeAsync` 支持顺带新增费用（`orderFees[].id` 传 `null`），这类费用的 `changeOrderId` 与会计期间原来完全依赖前端传值，前端不传就会落到主单上、会计期间还是空的。现在后端强制让新增费用跟随本次提交解析出的更改单，会计期间同步取该更改单的（主单取业务的），**前端不需要在新增费用上传 `changeOrderId`**；若显式传了且与本次提交的其它费用不一致，会命中上面那条校验。

**新增费用的归属改为后端接管：** `SubmitOrderFeeAsync` 支持顺带新增费用（`orderFees[].id` 传 `null`），这类费用的 `changeOrderId` 与会计期间原来完全依赖前端传值，前端不传就会落到主单上、会计期间还是空的。现在后端强制让新增费用跟随本次提交解析出的更改单，会计期间同步取该更改单的（主单取业务的），**前端不需要在新增费用上传 `changeOrderId`**；若显式传了且与本次提交的其它费用不一致，会命中上面那条校验。

## 十一、避坑指南

> [!IMPORTANT] **1. 不要再用 `entityId` 单独当行 key。** 同一票会返回多行，只用 `entityId` 会导致选中态串行、详情打开错行、批量审核审到别的更改单。

> [!IMPORTANT] **2. 更改单行的 `transportOrder.accountDate` 不是业务本身的会计期间。** 它已被替换成该更改单的会计期间。若某处确实需要业务本身的会计期间，请另外从业务详情接口取。

> [!IMPORTANT] **3. `OrderFeeTaskDetailAsync` 不传 `changeOrderId` 的语义变了。** 以前不传返回整票所有费用，现在不传只返回主单费用。老调用点如果依赖「一次拿到整票费用」，需要改成按行分别请求。

> [!IMPORTANT] **4. 存量数据一律算主单任务。** 本次不回填历史数据，升级前已存在的 `TaskBase.SecondId` 全为 `NULL`，所以历史（尤其是已处理完的）更改单费用任务会显示在主单行上。升级后新产生的任务才会正确归到更改单。

> [!IMPORTANT] **5. 某个更改单没有费用任务时不会出现行。** 费用任务列表是任务列表，不是更改单列表；要看全部更改单请用更改单自己的列表接口。
