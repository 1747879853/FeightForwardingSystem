# 背景意图

费用批量引入的查询接口原名 `GetSeaExportFeesAsync`，是按海运出口单一业务写的：

1. **基础查询直接打在 `_seaExportRepository` 上**，海运进口与空运出口的业务根本查不出来，无法把这两类业务的费用引入到别处。
2. **出参把海运出口字段平铺在根级**（`pol` / `pod` / `carrier` / `bookingAgent` / `vessel` / `innerVoyno`），`transportOrder` 只是个装 `commissionNum` / `mblNum` / `client` 的小对象，与其他模块「业务对象里按 `bizType` 挂三种业务类型对象」的口径不一致。
3. **`transportOrder.totalCtn` 是死字段**：DTO 里声明了、代码里也查了 `allOrderCtns` 并算出了 `thisOrderCtns`，但从未赋值给 DTO，前端拿到的恒为 `null`。

# 核心逻辑变更

## 1. 接口改名

| 项 | 原 | 新 |
| :-- | :-- | :-- |
| 方法名 | `GetSeaExportFeesAsync` | `GetTransportOrderFeesAsync` |
| 路由 | `GET /api/services/app/OrderFeeAdmin/GetSeaExportFeesAsync` | `GET /api/services/app/OrderFeeAdmin/GetTransportOrderFeesAsync` |
| 入参 | `SeaExportFeeQueryInputDto` | `TransportOrderFeeQueryInputDto` |
| 出参 | `List<SeaExportFeeListDto>` | `List<TransportOrderFeeListDto>` |

权限不变（`Admin.OrderFee.Get`）。DTO 文件同步由 `SeaExportFeeImportDto.cs` 改名为 `TransportOrderFeeImportDto.cs`（`git mv` 保留历史），文件内 `ImportOrderFeesToTransportOrderInputDto` 与 `GenerateOppositeOrderFeesInputDto` 未改动。

## 2. 出参结构：TransportOrder 内挂三种业务类型对象

新建了本接口专用的 DTO（未复用 `TransportOrderSimpleDto`，因为共享的 `SeaExportSimpleDto` 里没有 `BookingAgent`，复用会丢字段）：

```
TransportOrderFeeListDto
├── id                                  业务id
├── transportOrder : TransportOrderFeeOrderDto
│   ├── id / bizType / commissionNum / mblNum / client / totalCtn
│   ├── seaExport  : TransportOrderFeeSeaExportDto   仅 bizType=0
│   ├── seaImport  : TransportOrderFeeSeaImportDto   仅 bizType=1
│   └── airExport  : TransportOrderFeeAirExportDto   仅 bizType=2
└── orderFees[] : TransportOrderFeeItemDto           字段与原 SeaExportFeeItemDto 完全一致
```

**字段零丢失**，原有字段全部有新落点：

| 原字段 | 新位置 |
| :-- | :-- | --- | --- |
| `id` | `id`（保留）+ `transportOrder.id` |
| `pol` / `pod` | `transportOrder.seaExport | seaImport | airExport.pol`/`.pod` |
| `carrier` | `transportOrder.seaExport.carrier` / `seaImport.carrier` |
| `bookingAgent` | `transportOrder.seaExport.bookingAgent` / `airExport.bookingAgent` |
| `vessel` / `innerVoyno` | `transportOrder.seaExport` / `seaImport` 下同名字段 |
| `transportOrder.commissionNum` / `mblNum` / `client` | 位置不变 |
| `transportOrder.totalCtn` | 位置不变，且**本次才真正赋值** |
| `orderFees[]` 全部字段 | 完全不变 |

新增字段：`transportOrder.bizType`、`transportOrder.id`，以及空运出口特有的 `flightNo` 与 `pot`（中转地）。

三个业务类型对象的字段按各表实际拥有的列裁剪：海运进口没有 `bookingAgent`；空运出口没有 `carrier` / `vessel` / `innerVoyno`，改为 `flightNo`，且港口是空港。

## 3. 基础查询改打在 TransportOrder 上，港口按业务类型分表定位

查询主体由 `_seaExportRepository` 换成 `_transportOrderRepository`，数据权限相应从 `DataPermissionFilterAsync` + `FrightModule.SeaExport` 换成 `DataPermissionFilterTransportOrderAsync` + `FrightModule.TransportOrder`。

筛选字段长在三张扩展表上且各表列不一致。**`BizType` 设为必填**，因此每个条件只需挂到对应那张扩展表上，不必写三表 OR：

```csharp
var bizType = input.BizType;
var query = _transportOrderRepository.GetAll()
    .Where(m => m.BizType == bizType)
    .WhereIf(input.POLId.HasValue && bizType == BizType.SeaExport, m => m.SeaExport.POLId == input.POLId.Value)
    .WhereIf(input.POLId.HasValue && bizType == BizType.SeaImport, m => m.SeaImport.POLId == input.POLId.Value)
    .WhereIf(input.POLId.HasValue && bizType == BizType.AirExport, m => m.AirExport.POLId == input.POLId.Value)
    // ...
```

`BizType` 声明为**非空枚举 `public BizType BizType { get; set; }`，后端不做非空校验**。

| 筛选 | 海运出口 | 海运进口 | 空运出口 | 口径 |
| :-- | :-- | :-- | :-- | :-- |
| `bizType` | ✓ | ✓ | ✓ | **新增且必填**，一次只查一种。**它决定 `polId`/`podId` 属于哪张港口表** |
| `polId` / `podId` | 海港表 | 海港表 | 空港表 | 只挂到 `bizType` 对应那张扩展表，避免两张表 id 重号串数据 |
| `carrierId` | ✓ | ✓ | 无此字段 | `bizType=空运出口` 时传了不生效，空运出口照常返回 |
| `bookingAgentId` | ✓ | 无此字段 | ✓ | `bizType=海运进口` 时传了不生效，海运进口照常返回 |
| `clientId` / `keyword` | ✓ | ✓ | ✓ | 都在主单 `TransportOrder` 上，无需分类型 |

## 4. 关联数据查询

- 扩展表按业务id批量捞，**只捞「有符合条件费用的业务」**（原实现是先捞全部业务的港口再丢弃），且用私有投影行类（`SeaExportBizRow` / `SeaImportBizRow` / `AirExportBizRow`）只取需要的列，不物化整实体。
- 因 `BizType` 必填，**只查当前业务类型那一张扩展表**，另外两张直接给空列表（3 次查询降为 1 次）。港口查询随之只走海港表或只走空港表。
- 海港（海运出口+海运进口）走 `_portCodeRepository`，空港（空运出口）走新注入的 `_airPortRepository`。
- 箱信息同样收窄到有费用的业务，并改为投影行 `OrderCtnRow` 只取 `TransportOrderId` + `CtnCodeId`。
- 新注入 `IRepository<Entites.SeaImport, Guid>`、`IRepository<Entites.AirExport, Guid>`、`IRepository<Entites.AirPort, long>`。
- 顺带把同文件内 `OrderFeeTaskGroupedListAsync` 取空港名称那处的 `_transportOrderRepository.GetDbContext().Set<Entites.AirPort>()` 换成新注入的 `_airPortRepository`，本文件不再有 `GetDbContext` 取空港表的写法。

# 避坑指南

- **`BizType` 是非空枚举且后端不校验，漏传会静默变成 `0`（海运出口）。** 这是本项目最容易踩的一类坑：`BizType.SeaExport = 0` 恰好是枚举默认值，前端漏传不会报错、也不会返回空，而是安静地返回海运出口的数据。前端必须每次显式传值；联调时若发现「选了空运出口却出来海运出口的票」，第一时间查是不是漏传了 `bizType`。
- **港口 id 跨表重号，这正是 `BizType` 必填的原因。** 海港在 `App_PortCodes`、空港在 `App_AirPorts`，两张表 id 各自编号。不先定业务类型就无法判断 `polId` 该查哪张表。
- **`carrierId` / `bookingAgentId` 的语义是「对没有该字段的业务类型不生效」，不是「排除」。** `bizType=空运出口` 时传 `carrierId`，空运出口不会被过滤掉，会照常全部返回。前端筛选面板建议按 `bizType` 隐藏不适用的控件，避免用户误以为筛选生效了。
- **空运出口的 `flightNo` 不要当航次用。** 实体注释已写明航班与海运的 `innerVoyno` 语义无关，两者不可合并展示。
- **空运出口的中转地是单个 `pot`**，与海运出口的 `pot1`/`pot2` 不是同一概念（本接口原本也没返回 `pot1`/`pot2`）。
- **`totalCtn` 从本次开始才有值。** 之前是声明了没赋值的死字段，前端若曾按「恒为空」做过兜底逻辑，需要复查。
- **未复用 `TransportOrderSimpleDto` 是有意的。** 共享的 `SeaExportSimpleDto` 没有 `BookingAgent` 字段，复用会丢掉原接口的 `bookingAgent`；给共享 DTO 加字段又会波及另外 7 个已上线接口的出参体积。本接口字段诉求特殊，用专用 DTO 更合适。
