# 1. 背景意图 (Background)

业务费用（`OrderFee`）的结算对象 `SettlementId` 此前为**必填**（`Guid`）。实际业务中，费用在**录入阶段**往往还未确定结算对象，需要允许留空；但当费用**提交审核 / 申请修改**时，结算对象必须已确定。因此将 `SettlementId` 改为**可空**，并把必填校验从"录入"后移到"提交/申请修改"环节。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 实体与 DTO

| 位置 | 变更 |
| :-- | :-- |
| `Entites/OrderFee.cs` | `SettlementId` 由 `Guid` 改为 `Guid?` |
| `OrderFee/Dto/OrderFeeDto.cs` → `OrderFeeAddDto` / `OrderFeeEditDto` / `OrderFeeDto` | `SettlementId` 均改为 `Guid?` |
| `InvoiceApplication/Dto/InvoiceApplicationDto.cs` → `InvoiceApplicationFeeDto` | `SettlementId` 改为 `Guid?`（拉取可开票费用输出） |

> 数据库列改为可空由人工生成迁移（本次不生成 migration）。

## 2.2 校验规则（按费用状态区分）

| 接口 | 场景 | 结算对象校验 |
| :-- | :-- | :-- |
| `AddAsync` / `BatchAddAsync` / `BatchEditAsync`（录入/编辑） | 录入状态 | **可空**；仅当有值时校验客户是否存在 |
| `EditAsync`（录入） | 录入状态 | **可空**；仅当有值时校验存在性 |
| `SubmitOrderFeeAsync`（提交审核） | 提交 | **必填**；为空报"提交时结算对象不能为空" |
| `ModifyOrderFeeAsync`（申请修改） | 申请修改 | **必填**；为空报"结算对象不能为空" |
| 更改单 `ChangeOrderAdminAppService` 费用保存 | 录入 | **可空**（提交仍走 `SubmitOrderFeeAsync` 必填校验） |

## 2.3 跨服务编译适配（`Guid?` 影响）

以下接口在按结算对象聚合/关联客户时做了空值适配（`HasValue` 过滤或 `Guid?` 类型化），逻辑行为不变：

- 开票申请 `InvoiceApplicationAdminAppService`：拉取费用/详情组装客户ID集合时过滤空结算对象。
- 收费结算 `ReceiveSettlementAdminAppService`：客户ID `Concat` 链过滤空结算对象。
- 付费申请 `PaymentApplicationAdminAppService`：`(业务, 结算对象)` 分组键类型改为 `(Guid, Guid?)`；付费申请仅拉取已审核费用，结算对象必有值。
- 业务费用 `OrderFeeAdminAppService`：批量引入/任务审核快照等处的客户ID集合、结算对象名映射做空值过滤。

# 3. 避坑指南 (Blockers)

> [!IMPORTANT]
>
> - **提交/申请修改必须带结算对象**：录入可留空，但 `SubmitOrderFeeAsync`、`ModifyOrderFeeAsync` 会强校验，前端提交前需确保已选择结算对象。
> - **输出可能为 null**：`OrderFeeDto.SettlementId`、`InvoiceApplicationFeeDto.SettlementId` 现在可能为 `null`（录入状态费用），前端展示需容错。
> - **付费申请分组**：付费申请只拉取"审核通过"的费用，这些费用结算对象一定有值，分组键 `SettlementId` 取 `GetValueOrDefault()`。
