# 1. 业务背景说明 (Background)

**白话解释：**

业务费用（`OrderFee`）现在的审核是「一步到位」——谁有 `Admin.OrderFee.Audit` 权限，谁就能直接把费用审通过或驳回。中间没有任何审批链路，也没有分级审批、会签、按金额升级审批这些能力。

付费申请（`PaymentApplication`）已经接入了工作流引擎（`WorkFlow` 定义 + `WorkFlowInstance` 实例），支持按业务条件匹配出一条多级审批路径。本次要把同一套引擎接到业务费用上。

但费用的粒度比付费申请复杂得多：付费申请是「一单一个流程」，费用是「一票业务（可能还挂着更改单）下的 N 条费用」，而且每条费用都能被**单独提交、单独撤回、单独审核**。所以费用采用**主子工作流**结构：

- 一个 `(业务 + 更改单 + 任务类型)` 组合生成**一个主工作流**；
- 该组合下每条费用各生成**一个子工作流**；
- 所有子工作流的审批路径与主工作流**完全一致**，匹配条件只在组合级算一次。

**工作流定义只需要配两条**：费用提交一条（`TaskType = SubmitOrderFee`），费用变更一条（`TaskType = ModifyOrderFee`，申请修改与申请删除共用）。因为这三类申请可比较的费用字段完全相同，没必要配三遍。`TaskBase` 仍按任务类型分，所以申请修改与申请删除各有自己的主工作流实例，只是路径定义同源。

主工作流负责回答「这一行整体走到哪一步了、当前该谁审」，子工作流负责承载「每条费用各自审到哪一步了」。

# 2. 功能与操作说明 (Features & Operations)

- **费用提交审核：** 在费用面板勾选费用提交，生成 `SubmitOrderFee` 类型的主子工作流，费用进入 `Submitted`。
- **申请修改 / 申请删除：** 对已审核通过的费用发起，分别生成 `ModifyOrderFee` / `DeleteOrderFee` 类型的主子工作流。能否发起的校验：已对账 / 已付费申请 / 已开票 / **已收费结算（按费用）** 的不可发起；同一条费用已有在审的修改或删除申请时不可重复发起。
- **批量改结算对象：** `BatchModifyOrderFeeSettlementAsync` 把一批已审核费用的结算对象改成**同一个** `SettlementId`。一次只能一种收付类型。**应收直接改库、不走工作流**；**应付备注必填**，组装成只改了结算对象的申请修改入参后走 `ModifyOrderFeeAsync`（费用变更工作流）。卡点与申请修改相同。
- **撤回：** 提交人可随时撤回自己提交的、尚未出最终结论的费用，流程进行到第几级都能撤。已通过、已驳回的不可撤回。
- **审核：** 当前审核人可一次勾选任意多条费用通过或驳回，各条费用的子工作流独立推进。
- **审核后驳回：** 只有在该条费用的子工作流里审过且投了通过票的人，才能对它发起审核后驳回。
- **审核列表：** 按 `(业务 + 更改单)` 一个组合一行，只返回与当前登录人有关的行，新增「我的审核状态」筛选。

# 3. 状态流转说明 (Status Transitions)

## 3.1 费用状态（FeeStatus）

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 录入(0) / 驳回(3) | 提交人提交审核 | 提交审核(1) | 生成主子工作流，进入第 1 级 |
| 提交审核(1) | 提交人撤回 | 录入(0) | 该条子工作流与 `TaskItem` 一并删除 |
| 提交审核(1) | 工作流走完最后一级且全部通过 | 审核通过(2) | 中间级通过只推进工作流，不改费用状态 |
| 提交审核(1) | 任意一级审核人驳回 | 驳回(3) | 子工作流实例置 `Reject` |
| 审核通过(2) | 审核人发起审核后驳回 | 驳回(3) | 仅限该子工作流里投过通过票的人 |
| 提交审核(1) | 工作流所有节点均为「直接通过」 | 审核通过(2) | 不生成实例，直接置终态 |

## 3.2 子工作流实例状态（WorkFlowInstanceStatus）

| 当前状态 | 触发人/动作              | 目标状态       | 状态说明             |
| :------- | :----------------------- | :------------- | :------------------- |
| 活动(0)  | 最后一级通过             | 通过(1)        | 同时执行对应业务动作 |
| 活动(0)  | 任意一级驳回             | 拒绝(2)        | 流程立即终止         |
| 活动(0)  | 撤回该条费用             | 实例被删除     | 不保留记录           |
| 活动(0)  | 组合内发生重建且路径有变 | 实例被删除重建 | 退回第 1 级          |

## 3.3 主工作流推进

| 当前状态 | 触发条件 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 第 N 级 | 该组合下**所有未终结**的子工作流都已越过第 N 级 | 第 N+1 级 | 每次子工作流推进后回头判定一次 |
| 最后一级 | 同上 | 通过(1) | 主工作流实例置 `Pass` |
| 任意级 | 组合内发生撤回 / 新提交，且重新匹配出的路径**有变** | 删除重建 | 主工作流与所有在审子工作流一并退回第 1 级 |
| 第 N 级 | 组合内发生**撤回**，但路径**没变** | 仍是第 N 级或更靠后 | **主工作流实例保留、进度保留**，不重建；撤走费用后重算当前级，只会前进或不变 |
| 第 N 级 | 组合内发生**新提交**，但路径**没变** | 被拉回新费用所在的级 | **主工作流实例保留、不重建**，但当前级按 7.4 重算后会回退（新费用从第 1 级起步） |

主任务（`TaskBase`）的终态沿用现有 `TaskMainChangeAsync`：子任务全通过为 `Passed`，全驳回为 `Rejected`，有通过有驳回为 `PartialPassed`。

## 4.1 新增的工作流条件字段

这些条件由费用提交与费用变更两类工作流共用，不按任务类型拆开。

| 枚举 | 条件 | 取值来源 | 支持的比较符 |
| :-- | :-- | :-- | :-- |
| `OrderFeeUserId` | 业务所属人 | `TransportOrder.UserId`（**不是实际点提交的人**） | 等于 / 不等于 |
| `OrderFeeOrgID` | 业务所属组织 | `TransportOrder.OrgId` 及其下级组织 | 属于 / 不属于 |
| `OrderFeePaySide` | 收付类型 | `OrderFee.PaySide`，**组合内收付混合时该条件一律判为不满足** | 等于 / 不等于 |
| `OrderFeeBizType` | 业务类型 | `TransportOrder.BizType` | 等于 / 不等于 |
| `OrderFeeProfit` | 利润 | 应收合计 − 应付合计，均按 `Amount × ExchangeRate` 折算 | 大于 / 大于等于 / 小于 / 小于等于 |
| `OrderFeeProfitRate` | 利润率 % | 利润 ÷ 应付合计 × 100，填百分比数值（15 代表 15%）。**应付合计为 0 时该条件一律判为不满足** | 大于 / 大于等于 / 小于 / 小于等于 |
| `OrderFeeHasReceiveLessThanPay` | 存在某个费用名应收 < 应付 | 按 `FeeCodeId` 分别汇总收付后比较 | 是 / 不是（**不填值**） |
| `OrderFeeHasPayWithoutReceive` | 存在应付费用名但应收没有对应费用名的费用 | 同上 | 是 / 不是（**不填值**） |
| `OrderFeeHasReceiveWithoutPay` | 存在应收费用名但应付没有对应费用名的费用 | 同上 | 是 / 不是（**不填值**） |

### 利润与费用名比对的计算范围

这五个条件参与计算的费用是：**本行（业务 + 更改单）下，除录入状态和已驳回外的全部费用**（即 `FeeStatus` 为提交审核或审核通过）。

不能只算本次在审的费用——费用是按收付分批提交的，只提了应付时利润会等于负的应付合计，条件必然误判。

三个费用名比对条件**互不重叠**：`HasReceiveLessThanPay` 只比对应收应付**都存在**的费用名；只有一边有的分别归到后两个条件。费用名按 `FeeCodeId` 配对。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：没有配置工作流就完全不能提交]** 需要两份启用中的 `WorkFlow` 配置：**费用提交**（`SubmitOrderFee`）和**费用变更**（`ModifyOrderFee`，申请修改与申请删除共用）。缺哪一份，对应的申请就会被 `未配置或未启用XX工作流，无法提交审核` 拦下。配置端**禁止创建 `DeleteOrderFee` 类型的工作流**，会直接报 `费用申请删除与费用申请修改共用同一条工作流,请配置在费用申请修改下`——否则配了却永远不会生效，是个隐蔽的坑。

> [!IMPORTANT] **[卡点 2：上线前必须清空在审任务，不做旧数据兼容]** 存量的 `TaskStatus = Auditing` 且没有工作流实例的 `TaskItem`，上线后既走不了新流程也走不了老逻辑。**上线前要求业务把所有在审的费用任务处理完**，代码不写迁移和降级分支。

> [!IMPORTANT] **[卡点 3：路径变了才倒退，路径没变必须保留进度]** 组合内任何一次撤回或新提交，都会触发主工作流重新匹配，**撤回与新提交这两种触发的处理方式完全一致**。只有新路径与旧路径**存在差异**时，该组合下所有在审费用的子工作流才会被删除重建、退回第 1 级，已经审过的人需要重审；**路径完全一致时必须保留已有审批进度，主工作流与子工作流都不得重建**。已通过、已驳回的费用在两种情况下都不受影响。

> [!IMPORTANT] **[卡点 4：重建期间审核人会暂时从自己的列表里消失]** 列表沿用付费申请口径，只返回当前登录人在子工作流里 `TaskStatus` 有值的行。子工作流被重建后，第 2 级及以后的审核人状态会回到 `null`，这一行会从他的列表里消失，直到第 1 级重新审完才回来。或签场景下别人先审掉时同理。

> [!IMPORTANT] **[卡点 5：金额条件是简单求和，应收应付会互相抵消]** 组合内所有在审费用的金额直接相加，不区分收付方向、不做币别折算。一条 +10000 的应收和一条 -10000 的应付会汇总成 0，可能绕过金额审批阈值。配置工作流条件时要意识到这一点。

> [!IMPORTANT] **[卡点 6：算不出审核人时会直接执行业务动作]** 工作流所有节点都配成「直接通过」时不生成实例，直接落终态：提交的费用置为审核通过、**申请删除的直接删除费用**、申请修改的直接把修改应用到费用上。配置时务必确认这是预期行为。

> [!IMPORTANT] **[卡点 7：批量改结算对象按收付类型分叉]** 应收（`PaySide=收`）不建任务、不走工作流，工作单元结束时直接把 `SettlementId` 写成入参那一个。应付（`PaySide=付`）备注必填，其余卡点与 `ModifyOrderFeeAsync` 相同，会进入费用变更工作流；工作流未配置时应付会被拦住，应收不会。

# 7. 技术实现摘要

## 7.1 主子工作流模型

| 层级 | 载体 | 挂载字段 | 数量 |
| :-- | :-- | :-- | :-- |
| 主工作流 | `WorkFlowInstance` | `TaskBaseId` = 主任务 id，`ParentInstanceId` 为 `null` | 每个 `(业务, 更改单, 任务类型)` 一个，一个组合下最多 3 个 |
| 子工作流 | `WorkFlowInstance` | `TaskItemId` = 子任务 id，`ParentInstanceId` = 主工作流实例 id | 每条费用一个 |

三种任务类型各自匹配各自的 `WorkFlow` 定义（`TaskType` 为 `SubmitOrderFee` / `ModifyOrderFee` / `DeleteOrderFee`），互不干扰，各自独立推进。

## 7.2 工作流匹配

- **匹配时机：** 组合内发生提交或撤回时，对该任务类型重新匹配一次。
- **匹配口径：** 组合级。比较数据取该组合下本任务类型的**全部在审费用**汇总，只算一次，所有子工作流复用同一条路径。
- **条件数据来源：** 见 4.1。其中利润类与费用名比对类条件的计算范围是本行除录入和已驳回外的全部费用，与「在审费用」不是一个集合。
- **条件判断不做跨模块共用：** 每个模块可比较的业务字段不一样，`MatchTransition` 与条件判断都各自实现在自己的服务里，不上提到基类。
- **路径生成：** 复用付费申请 `CreateWorkFlowInstanceWithPaths` 的结构——先用 `MatchTransition` 匹配起始线，再沿节点逐级展开生成 `WorkFlowInstanceItem`，第 1 级置 `Auditing`、其余置 `null`。
- **审核人解析：** 在付费申请「用户 + 角色」两种来源之外，**新增 `UserAttribute` 分支**，从该票 `TransportOrder.OrderUsers` 里按属性取人。该属性在本票没有对应人员时，沿用现有报错方式抛 `未找到符合条件的用户`。
- **无审核人：** 所有节点都是「直接通过」导致 `WorkFlowInstanceItems` 为空时，不插入实例，直接执行业务动作（见卡点 6）。

## 7.3 重建规则（核心）

撤回和提交共用同一套重建流程：

1. 对该组合该任务类型**重新匹配**主工作流路径。
2. 把新路径与现有在审子工作流的路径**逐级比对**：层级数、每一级的审核人集合、每一级的 `PassMethod` 全部相同才算「没变」。
3. **路径有差异**时：主工作流实例删除重建，该组合下所有在审费用的子工作流一并删除重建、退回第 1 级；已通过、已驳回的子工作流保留不动，只把 `ParentInstanceId` 改挂到新的主工作流实例上。
4. **路径完全一致**时：**主工作流实例和所有子工作流都不重建，两者的审批进度全部原样保留**，`ParentInstanceId` 也无需变动。**撤回触发和新提交触发都适用这一条**，两者没有任何区别——撤回时主工作流同样不能被重置回第 1 级。
5. 本次新提交的费用，无论路径是否有变，都新建自己的子工作流并从第 1 级开始，`ParentInstanceId` 指向当前有效的主工作流实例。
6. 被撤回的那几条费用，其子工作流连同 `TaskItem` 一并删除，费用回到 `Entering`。
7. 组合内一条在审费用都不剩时，删除主工作流实例；`TaskBase` 沿用现有 `TaskMainChangeAsync` 里「没有子任务就删主任务」的逻辑。

> 「还存在正在审核中的费用」按**包含**申请修改、申请删除在审的费用计算——那些费用的 `FeeStatus` 是 `Passed`，但 `TaskItem` 尚未终结。

> [!WARNING] **「保留进度」与「重算当前级」不冲突，别理解成两套规则。** 保留进度指的是路径一致时主子工作流实例一律不删除重建、绝不重置回第 1 级；重算当前级指的是主工作流的级本来就派生自子工作流（见 7.4），实例保留的前提下按最新的子工作流状态算出它现在应该停在第几级。
>
> 两种触发的重算结果方向不同：
>
> - **撤回**：只会移除子工作流，不会引入新的落后子工作流，所以重算后主工作流的当前级**只会前进或不变，永远不会回退**。若被撤走的正是拖后腿的那条费用，主工作流反而会往前跳一级或几级。
> - **新提交**：新费用的子工作流从第 1 级起步，会把主工作流的当前级**拉回到新费用所在的级**。这是预期行为，主工作流反映的是该组合里走得最慢的那条费用。此时已在更高级别审过的人**不需要重审**（他们的子工作流进度还在），只是这一行会重新出现在第 1 级审核人的待办里。

## 7.4 推进规则

- 审核人一次可勾选任意多条费用。每条费用的子工作流独立按现有 `AuditWorkFlowInstanceAsync` 的逻辑推进（含或签置 `null`、会签等全部通过才流转）。
- 每条子工作流推进一级后，回头判定主工作流：该组合下**所有未终结**的子工作流都已越过主工作流当前级时，主工作流推进一级。
- 主工作流的当前级等价于「所有未终结子工作流里走得最慢的那一级」。它既会随审核往前推，也会在有新费用加入时**往回退**，所以实现上应在子工作流状态每次变化后按这个口径**统一重算**，而不是只做单向 `+1`。
- 子工作流走完最后一级才执行业务动作：提交类置费用为 `Passed`，删除类删除费用，修改类把 `TaskItem.Info` 的内容应用到费用并回填 `OriginalInfo`。中间级通过只推进工作流，不碰费用。
- 任意一级驳回，该条子工作流立即置 `Reject`，费用置 `Rejected`。

## 7.5 列表口径

- 行的粒度不变，仍按 `(业务 + 更改单)` 分组，一个组合一行（现有 `OrderFeeTaskListAsync` 已经是这个口径，无需改动分组逻辑）。
- **可见范围收窄：** 只返回当前登录人在子工作流 `WorkFlowInstanceItem` 里 `TaskStatus` 有值的行，与付费申请 `PayAppTaskListAsync` 口径一致。
- **新增「我的审核状态」筛选：**

| 筛选值 | 判定条件 |
| :-- | :-- |
| `0` 待我审核 | 该组合下**任意一条**费用的子工作流中，存在 `UserId` = 我且 `TaskStatus = Auditing` 的 item |
| `2` 我已审核 | 存在 `UserId` = 我且 `TaskStatus` 为 `Passed` 或 `Rejected` 的 item |
| 不传 | 上述两者的并集，即 `TaskStatus` 有值的全部 |

枚举取值刻意与 `TaskStatus` 对齐（`0` 对应 `Auditing`、`2` 对应 `Passed`），前端可与行状态 `MyTaskStatus` 共用一套字典。筛选项没有 `1`，因为「我已审核」把通过和驳回合并了。

- 分组统计接口 `OrderFeeTaskGroupedListAsync` 的筛选条件需同步跟进，保证 `count` 与列表 `totalCount` 仍然对得上。

## 7.6 接口改造清单

| 接口 | 改造点 |
| :-- | :-- |
| `SubmitOrderFeeAsync` | 建任务后生成主子工作流；触发组合级重建；无审核人时直接执行业务动作 |

| `BatchModifyOrderFeeSettlementAsync` | **新增**。一批费用改成同一个结算对象。应收直接改 `SettlementId`；应付组装申请修改入参后走 `ModifyOrderFeeAsync` |

| `OrderFeeTaskAuditAsync` | 逐条推进子工作流，末级才落业务；结束后重算主工作流当前级 |
| `OrderFeeTaskBatchAuditAsync` | 同上；批量一次覆盖多行，**只处理当前登录人是当前审核人的费用**，轮不到自己的跳过而不是整批抛错；一条都轮不到时报 `没有待您审核的费用任务` |
