# 背景意图

费用审核工作台的任务来源已经覆盖海运出口、海运进口、空运出口三种业务，但分组统计接口 `OrderFeeTaskGroupedListAsync` 是按海运出口单一业务写的，只读 `SeaExport` 扩展表。空运出口上线后暴露出两个问题：

1. **接口整体崩溃。** 投影里平铺了 `x.SeaExport.BLType` / `x.SeaExport.BillType`，而 `TransportOrder.SeaExport` 是可选一对一导航，海运进口和空运出口没有对应记录。EF 走 LEFT JOIN 拿到 NULL，往非空枚举里塞就抛 `Nullable object must have a value`。异常发生在 `ToListAsync()`、位置在 `switch (input.GroupField)` 之前，所以 **groupField 传 1 到 10 全部 500**。
2. **维度覆盖不全。** 海运进口本身有船公司、起运港、目的港、船名，空运出口有起运地、目的地，这些数据全被漏掉。

# 核心逻辑变更

## 1. 投影改为可空对象，修复崩溃

三种扩展表各自作为可空对象投影，一票只命中其中一张，另外两张为 `null`：

```csharp
SeaExport = x.SeaExport == null ? null : new { x.SeaExport.BLType, ... },
SeaImport = x.SeaImport == null ? null : new { x.SeaImport.CarrierId, ... },
AirExport = x.AirExport == null ? null : new { x.AirExport.POLId, x.AirExport.PODId },
```

后续分组一律走 `x.SeaExport?.BLType` 这种空传播，非空枚举的 key 变成可空枚举，空值分支返回 `null`。

## 2. 分组维度按字段归属重新划分

| 分组维度 | 海运出口 | 海运进口 | 空运出口 | 取值来源 |
| :-- | :-- | :-- | :-- | :-- |
| 装运方式 / 订单类型 / 签单方式 / 场站 | 有 | 无 | 无 | `SeaExport` 独有 |
| 船公司 | 有 | 有 | 无 | 两边同指船公司表，合并成一组 |
| 船名 | 有 | 有 | 无 | 两边同为自由文本，合并成一组 |
| 起运港 / 目的港 | 有 | 有 | 有 | 海运查港口代码表，空运查空运港口表 |
| 委托单位 / 付费方式 | 有 | 有 | 有 | 在主单 `TransportOrder` 上 |

不参与某维度的业务类型落到该维度下 key 为 `null` 的空分组，不做排除，保证各分组 `count` 之和仍等于列表 `totalCount`。

空运出口的航班号 `FlightNo` **不并入船名分组**，实体注释已写明「航班 自由文本 与海运的航次(InnerVoyno)无关」，两者语义不同。

## 3. 港口分组键改为「港口类型(IsSea) + 港口id」

海运港口在 `App_PortCodes`，空运港口在 `App_AirPorts`，两张表 id 各自编号会重号。若只用港口 id 做分组键，同号的海港与空港会被合成一组，且取名会串表。

分组键选的是 `(IsSea, PortId)` 而**不是** `(BizType, PortId)`：海运出口与海运进口共用港口代码表，同一个港口应当合并成一组，否则用户没法「只搜这个海港的全部海运业务」，只能按海出、海进分别点两次。只有海运与空运之间才需要区分，因为它们的港口分属两张表。

`OrderFeeTaskGroupDto` 相应新增 `IsSea` 字段。取名时 `IsSea == true` 走港口代码表，`false` 走空运港口表。

无港口的行，`IsSea` 一并置空，让三种业务类型的空港口并到同一个空分组，避免 UI 上出现三条空白行。

## 4. 筛选口径同步扩展（否则下钻查不到数据）

分组与下钻列表共用同一套 `WhereIf`，原先只匹配 `m.SeaExport.*`。只改分组不改筛选的话，点开海运进口或空运出口的分组会返回 0 条。

改动后：

- `Vessel` / `VesselEmpty` / `InnerVoyno` / `CarrierId` / `CarrierIdEmpty`：海运出口与海运进口两边匹配
- 入参新增 `IsSea`，与 `POLId` / `PODId` 配套：`true` 匹配海运出口+海运进口，`false` 匹配空运出口，不传则三张扩展表都匹配（会带出同号的另一类港口，仅为向后兼容保留）
- `POLIdEmpty` / `PODIdEmpty`：三种业务类型都为空才命中
- `BLType` / `BillType` / `CodeIssueTypeId` / `YardId` 及其 `*Empty`：仍只认海运出口，因为这些字段本就是海运出口独有

这套 `WhereIf` 在 `OrderFeeTaskGroupedListAsync` 和 `OrderFeeTaskListAsync` 里各有一份，两处逐字同步修改。

## 5. 列表与详情的 `transportOrder` 补齐业务类型简要

`OrderFeeTaskListAsync` / `OrderFeeTaskDetailAsync` 返回的 `TransportOrderSimpleDto` 上早就有 `SeaExport` / `SeaImport` / `AirExport` 三个字段（2026-08-10 外键对象化时加的），但这两个接口一直没赋值，前端拿到的恒为 `null`。

新增私有方法 `SetTransportOrderBizSimpleAsync`：按业务 Id 批量捞三张扩展表（扩展表与业务表共用同一个 Id），再一次性补齐港口、船公司、空运港口等外键对象，最后按 `BizType` 赋值，非当前类型置 `null`。全程按 Id 集合批量查，没有逐条查库。

调用点有一处顺序要求：必须在 `CloneTransportOrderSimple` **之前**赋值。列表会把同一业务按更改单拆成多行、给更改单行做 JSON 深拷贝，先赋值才能让拷贝出的行也带上简要对象。

# 避坑指南

- **不要在 EF 投影里平铺可选导航的非空值类型字段。** `x.OptionalNav.NonNullableEnum` 会在导航为空时抛 `Nullable object must have a value`。要么整体投影成可空对象（本次做法），要么显式转可空。这条同样适用于 `x.SeaImport.*`、`x.AirExport.*` 以及任何一对一可选扩展表。
- **`Where` 谓词里的 `m.SeaExport.BLType` 是安全的**，它会翻译成 SQL 不做 CLR materialization，只要前面有 `m.SeaExport != null` 兜底即可，本次没有改动这类写法的必要。
- **改了分组就必须同步改筛选。** 这两者是同一个功能的两半，本次崩溃之外最容易漏的就是下钻查不到数据。
- **港口 id 跨表重号是长期隐患。** 任何同时展示海运和空运港口的地方，都必须带港口类型一起定位，不能只凭 id。
- **区分维度要选在「数据来源」而不是「业务类型」上。** 港口用 `IsSea` 而非 `BizType` 做键，是因为重号的根源是两张基础资料表，与业务类型无关；按 `BizType` 拆会把共用同一张表的海出与海进也拆开，反而丢掉「按港口看全部海运业务」的能力。
