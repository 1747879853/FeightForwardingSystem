# 业务费用-费用任务分组支持全业务类型-前端对接文档-2026-08-11

## 1. 背景意图

费用审核工作台的任务列表里已经同时存在**海运出口、海运进口、空运出口**三种业务，但分组统计接口原先只读海运出口扩展表：

- 海运进口/空运出口没有 `App_SeaExports` 记录，读非空枚举时直接抛 `Nullable object must have a value`，导致 `OrderFeeTaskGroupedListAsync` **传任意 groupField 都 500**。
- 海运进口本来就有船公司、起运港、目的港、船名，却被漏掉；空运出口有起运地、目的地。

本次修复崩溃，并把分组维度按字段归属重新划分到三种业务类型。

## 2. 接口

| 项   | 值                                                             |
| :--- | :------------------------------------------------------------- |
| 方法 | `GET`                                                          |
| 地址 | `/api/services/app/OrderFeeAdmin/OrderFeeTaskGroupedListAsync` |
| 权限 | `Admin.OrderFee.Audit`                                         |
| 返回 | `List<OrderFeeTaskGroupDto>`（不分页，直接返回全部分组）       |

配套的下钻列表接口：`GET /api/services/app/OrderFeeAdmin/OrderFeeTaskListAsync`，入参与本接口除 `groupField` 外完全一致。

## 3. 入参（OrderFeeTaskGroupQueryDto）

继承 `OrderFeeTaskListInputDto` 与 `PagingAndSorting`。本接口不分页，`pageIndex`/`pageSize` 传了也不生效。

### 3.1 分组字段（本接口独有，必填）

| JSON Key     | 类型 | 说明                 |
| :----------- | :--- | :------------------- |
| `groupField` | int  | 分组维度，取值见下表 |

| 值  | 分组维度 | 参与的业务类型       |
| :-- | :------- | :------------------- |
| 1   | 装运方式 | 仅海运出口           |
| 2   | 订单类型 | 仅海运出口           |
| 3   | 委托单位 | 三种全部（取自主单） |
| 4   | 船公司   | 海运出口 + 海运进口  |
| 5   | 起运港   | 三种全部             |
| 6   | 目的港   | 三种全部             |
| 7   | 船名     | 海运出口 + 海运进口  |
| 8   | 付费方式 | 三种全部（取自主单） |
| 9   | 签单方式 | 仅海运出口           |
| 10  | 场站     | 仅海运出口           |

不参与某维度的业务类型会落到该维度下 `id` 为 `null` 的空分组，不会被丢弃，所以各分组 `count` 之和仍等于列表的 `totalCount`。

## 4. 破坏性变更：港口分组新增 `isSea`

`OrderFeeTaskGroupDto` **新增 `isSea` 字段**，入参也**新增同名的 `isSea`**。

海运的港口来自港口代码表，空运的起运地/目的地来自空运港口表，**两张表 id 各自编号、会重号**。所以按起运港/目的港分组时，分组键是 `isSea + id` 两个字段，只看 `id` 会把海港和同号的空港混成一组，港口名也会取错。

海运出口与海运进口共用港口代码表，同一个港口**合并为一组**，不再按业务类型细分，这样才能一次性筛出该港口下的全部海运业务。

| 场景                                     | `isSea`     | `id`          |
| :--------------------------------------- | :---------- | :------------ |
| 起运港/目的港分组，海港（海出+海进合并） | `true`      | 港口代码表 id |
| 起运港/目的港分组，空港（空运出口）      | `false`     | 空运港口表 id |
| 起运港/目的港分组，无港口                | `null`      | `null`        |
| 其余 8 个分组维度                        | 恒为 `null` | 按原规则      |

**下钻时必须把 `isSea` 和 `id` 一起回传**：

```
GET /OrderFeeTaskListAsync?isSea=true&polId=123    ← 正确，只查海运（海出+海进）
GET /OrderFeeTaskListAsync?isSea=false&polId=123   ← 正确，只查空运
GET /OrderFeeTaskListAsync?polId=123               ← 不传 isSea 会同时带出同id的海港与空港数据
```

无港口的空分组下钻时改用 `polIdEmpty=true` / `podIdEmpty=true`，不要传 `isSea` 和 `polId`。

`isSea` 与 `bizType` 可以叠加使用：`isSea=true&bizType=1&polId=123` 表示只看该海港下的海运进口业务。

## 5. 出参（OrderFeeTaskGroupDto）

| JSON Key | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | string | 分组值id。枚举为枚举值，委托单位为 Guid，船名为名称本身，其余为 long 型 id；无值时为 `null` |
| `isSea` | bool? | **新增**。港口类型，`true` 海港、`false` 空港。仅按起运港/目的港分组时有值，无港口的分组为 `null`；其余分组维度恒为 `null` |
| `name` | string | 分组显示名称，无值时为 `null` |
| `count` | int | 该分组下的数据条数（按「业务+更改单」拆行后的行数，与列表 `totalCount` 口径一致） |
| `logo` | AttachmentItemDto | 船公司logo，仅按船公司分组（`groupField=4`）时有值 |

各分组按 `count` 倒序返回。

### 5.1 `id` 在各分组维度下的格式

`id` 统一是 string，但含义随 `groupField` 变化，**不带任何类型前缀**：

| groupField | `id` 示例 | 实际含义 |
| :-- | :-- | :-- |
| 1 装运方式 / 2 订单类型 | `"0"` | 枚举值 |
| 3 委托单位 / 10 场站 | `"8a1f2c33-9b47-4d21-8f30-6b5c9e7a1122"` | Guid |
| 4 船公司 / 8 付费方式 / 9 签单方式 | `"12"` | long 型主键 |
| 5 起运港 / 6 目的港 | `"1001"` | long 型主键，**需配合 `isSea` 才能唯一定位** |
| 7 船名 | `"COSCO SHIPPING UNIVERSE"` | 船名字符串本身，不是 id |

任何维度下 `id` 为 `null` 都代表该维度无值（未填写 / 该业务类型没有此字段）。

## 6. 响应示例

按起运港分组（`groupField=5`）：

```json
{
  "result": [
    {
      "id": "1001",
      "isSea": true,
      "name": "SHANGHAI",
      "count": 17,
      "logo": null
    },
    {
      "id": "1001",
      "isSea": false,
      "name": "浦东国际机场",
      "count": 3,
      "logo": null
    },
    {
      "id": null,
      "isSea": null,
      "name": null,
      "count": 2,
      "logo": null
    }
  ],
  "success": true
}
```

前两条 `id` 同为 `1001` 但分属两张基础资料表：`isSea=true` 的是港口代码表的上海港（海运出口与海运进口合并计数），`isSea=false` 的是空运港口表里恰好也叫 1001 的浦东机场。**这正是必须带 `isSea` 的原因。**

按装运方式分组（`groupField=1`），海运进口和空运出口落到空分组：

```json
{
  "result": [
    { "id": "0", "isSea": null, "name": "整箱", "count": 20, "logo": null },
    { "id": null, "isSea": null, "name": null, "count": 8, "logo": null }
  ],
  "success": true
}
```

## 7. 列表与详情的 `transportOrder` 新增业务类型简要

`OrderFeeTaskListAsync` 与 `OrderFeeTaskDetailAsync` 返回的 `transportOrder`（`TransportOrderSimpleDto`）此前未填充业务类型子表，现按 `bizType` 挂上对应简要对象，三者互斥、非当前类型为 `null`。

| 项 | 值 |
| :-- | :-- |
| 列表 | `GET /api/services/app/OrderFeeAdmin/OrderFeeTaskListAsync` → `items[].transportOrder` |
| 详情 | `GET /api/services/app/OrderFeeAdmin/OrderFeeTaskDetailAsync` → `transportOrder` |

| JSON Key    | 类型                 | 何时有值             |
| :---------- | :------------------- | :------------------- |
| `seaExport` | `SeaExportSimpleDto` | `bizType=0` 海运出口 |
| `seaImport` | `SeaImportSimpleDto` | `bizType=1` 海运进口 |
| `airExport` | `AirExportSimpleDto` | `bizType=2` 空运出口 |

`SeaExportSimpleDto` / `SeaImportSimpleDto` 结构相同：

| JSON | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | Guid | 与业务 Id 相同 |
| `vessel` | string | 船名 |
| `innerVoyno` | string | 航次 |
| `pol` | `PortCodeSimpleDto` | 起运港对象（`id` / `portName` / `cnName`） |
| `polRemark` | string | 起运港备注 |
| `pod` | `PortCodeSimpleDto` | 目的港对象 |
| `podRemark` | string | 目的港备注 |
| `carrier` | `CarrierSimpleDto` | 船公司对象（`id` / `code` / `cnName` / `cnShortName` / `enName` / `ediCode`） |

`AirExportSimpleDto`：

| JSON | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | Guid | 与业务 Id 相同 |
| `flightNo` | string | 航班号 |
| `pol` | `AirPortSimpleDto` | 起运地（`id` / `iataCode` / `enName` / `cnName`） |
| `polRemark` | string | 起运地备注 |
| `pot` | `AirPortSimpleDto` | 中转地 |
| `potRemark` | string | 中转地备注 |
| `pod` | `AirPortSimpleDto` | 目的地 |
| `podRemark` | string | 目的地备注 |

同一业务按更改单拆成多行时，每行的 `transportOrder` 都会带上相同的业务类型简要。

```json
{
  "result": {
    "items": [
      {
        "entityId": "0f9c...",
        "changeOrderId": null,
        "transportOrder": {
          "id": "0f9c...",
          "bizType": 1,
          "mblNum": "SHA2026001",
          "seaExport": null,
          "seaImport": {
            "id": "0f9c...",
            "vessel": "COSCO SHIPPING UNIVERSE",
            "innerVoyno": "025E",
            "pol": { "id": 1001, "portName": "SHANGHAI", "cnName": "上海" },
            "polRemark": null,
            "pod": { "id": 1043, "portName": "NINGBO", "cnName": "宁波" },
            "podRemark": null,
            "carrier": {
              "id": 7,
              "code": "COSCO",
              "cnName": "中远海运",
              "cnShortName": "中远",
              "enName": "COSCO SHIPPING",
              "ediCode": "COS"
            }
          },
          "airExport": null
        }
      }
    ],
    "totalCount": 1
  },
  "success": true

```

需要完整业务详情时，仍分别调 `SeaExportAdmin` / `SeaImportAdmin` / `AirExportAdmin` 的 `DetailAsync`，不要依赖这里的简要对象。

## 8. 前端适配清单

- [ ] `OrderFeeTaskGroupDto` 增加 `isSea` 字段解析
- [ ] 起运港/目的港分组下钻时，`isSea` 与 `polId`/`podId` 一起传
- [ ] 起运港/目的港分组的列表 key 改用 `isSea + id` 组合，不要只用 `id`，否则同 id 的海港与空港会被 React/Vue 判为同一行
- [ ] 空分组（`id` 为 `null`）要能正常渲染，建议显示为「未设置」；下钻改传对应的 `*Empty=true`
- [ ] 港口筛选器（非分组下钻场景）也要带上 `isSea`，否则会串出另一类港口的数据
- [ ] 船公司、船名分组现在包含海运进口数据，分组数量和条数会比改造前多，属正常
- [ ] 列表/详情的 `transportOrder` 按 `bizType` 读 `seaExport`/`seaImport`/`airExport`，不要固定只读 `seaExport`
- [ ] 港口、船公司一律读对象字段（如 `seaImport.pol.cnName`），不要期望扁平的 `*Id`/`*Name`
