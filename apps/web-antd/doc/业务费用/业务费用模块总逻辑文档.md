# 1. 业务背景说明 (Background)

**白话解释：**

已审核通过的业务费用不能直接改、也不能直接删。要改走「申请修改」，要删走「申请删除」，都生成费用变更任务，审批通过后才真正写回或删除。

申请时提交人必须写明原因。这条原因是**任务级备注**（两个接口入参上的 `remark`），给审核人看，不是费用行自己的那条备注。

**件杂货（业务类型 3）上线后**，费用模块把它当成「海运类」业务看待：港口用海运港口表，船名、航次、签单方式和海运出口一样参与费用任务的筛选与分组；但它没有船公司、装运方式、订单类型、场站、集装箱。它多了一个**地面代理**，费用的结算对象类别选「地面代理」时，自动带出的就是件杂货上的地面代理。件杂货本身见 `文档/件杂货/件杂货模块总逻辑文档.md`。

# 2. 功能与操作说明 (Features & Operations)

- **申请修改：** 对已审核通过的费用提交「改成什么样」的快照，走费用变更工作流。一次只能操作同属一个更改单（或同为主单）的费用。
- **申请删除：** 对已审核通过的费用提交删除申请，走同一套费用变更工作流。
- **任务级备注：** 两个接口的 `remark` 都必填。空白也算没填。创建任务时写到每条子任务 `TaskItem.Remark`；新建主任务时还会经 AutoMap 落到 `TaskBase.Remark`。已有主任务再追加子任务时，只写子任务备注，不改主任务上已有的备注。
- **费用排序：** 每条费用有 `sortId`（int，越小越靠前，允许相同）。录入、编辑、提交、申请修改都按入参写入。也可以单独调「按入参改排序」把指定费用的 `sortId` 写成前端给的值，或调「恢复顺序」把某一票、某一更改单、某一种收付下的费用按录入时间从 0 重排。这两个接口不做锁定、状态、对账等任何判断，找不到的费用直接跳过。带 `sorting` 入参的费用列表仍按前端排序（基类默认 `CreationTime DESC`，不传也是这个）。没有排序入参的嵌套费用清单，以及费用打印，一律按 `sortId` 升序、相同再按创建时间升序。
- **费用预警：** 打开某一行费用面板时，用业务 id + 更改单 id（主单不传更改单）查出这一行的全部费用，按类型分组返回。按费用名拆开的组（汇率/税率不一致、费用名利润为负、应付费用名在应收中没有、费用名重复）每条明细带费用名 SimpleDto；单一币别利润每条带币别 SimpleDto；负数金额、汇率不是本月、结算对象不一致、海运费非美元、禁开，组内只有一条并把费用 id 合并。合计利润、币别 ≥ 3 种的 `items` 为空。只读，不改数据。收付用费用的 `PaySide`（`0` 收 / `1` 付），不分收付为 `null`。
- **费用工作流「业务所属组织」：** 连线条件 `OrderFeeOrgID`（属于 / 不属于）看的是业务单 `TransportOrder.OrgId`。配的是大组织时，下属部门的票也算属于：例如配「属于青岛分公司」，所属组织是青岛业务部的票也会走这条线。「不属于」方向同样按这棵组织树理解，青岛业务部不算「不属于青岛分公司」。
- **费用任务分组统计与任务列表：** 业务类型可筛件杂货（`bizType=3`）。船名、船名未填写、航次、起运港/目的港（海运港口）及其未填写、签单方式及其未填写这几个条件都覆盖件杂货；按起运港、目的港、船名、签单方式分组时，件杂货的票取件杂货上的值参与分组。船公司、装运方式、订单类型、场站件杂货没有，按它们分组时件杂货落到「未填写」组。各维度的覆盖范围见 4.7。
- **费用任务列表、详情与费用打印的业务简要：** 行上的业务 `transportOrder` 按业务类型挂简要对象，件杂货挂 `breakBulk`（船名、航次、码头航次、起运港、目的港及备注），由统一填充器给值，与业务详情、业务联系单等接口同一口径。
- **批量引入候选查询：** 挑选来源费用时 `bizType` 可选件杂货。起运港、目的港（海运港口）、订舱代理筛选对件杂货生效；船公司筛选对件杂货不生效（照常返回）。返回的业务对象挂 `breakBulk`，含船名、航次、起运港、目的港、订舱代理、地面代理。字段见 4.8。
- **引入费用、收付互生时自动带结算对象：** 引入费用选「不引入原结算对象」、以及收转付/付转收时，按结算对象类别去目标业务上找对应往来单位。订舱代理、目的港代理取海运出口或件杂货上的值，**新增地面代理 → 件杂货的地面代理**。完整映射见 4.9。

# 3. 状态流转说明 (Status Transitions)

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 已审核通过 | 有编辑权限的人调 `ModifyOrderFeeAsync` | 费用本身不变；生成/追加审核中的修改子任务 | 审批通过后才把快照写回费用 |
| 已审核通过 | 有编辑权限的人调 `DeleteOrderFeeAsync` | 费用本身不变；生成/追加审核中的删除子任务 | 审批通过后才真正删除费用 |
| 审核中 | 工作流全部节点都配成直接通过 | 申请修改：费用被改成快照；申请删除：费用被删 | `AutoPassOrderFeeTasksAsync` |
| 审核中 | 同一条费用再次申请修改或删除 | 拦截，不建新任务 | 报「费用已申请修改/删除,请等待审批」 |

## 4.5 费用预警

预警只读，按「这一行」的费用现场算：业务 id + 更改单 id（空 = 主单）。录入/驳回/已审核都算进去。没有机密查看权限时，机密费用不参与任何一条预警。

利润口径：2.1、3 用 `金额 × 汇率` 折本位币后再相减；2.2 明确不乘汇率，按原币金额相减。负数判断都是小于 0，等于 0 不预警。

| :-- | :-- | :-- | :-- |
| 1.1 / 1.2 | 同一 `FeeCodeId` 下汇率不都一样 | 收 / 付 | 每个费用名一条，带 `feeCode` |
| 1.3 / 1.4 | 同一 `FeeCodeId` 下税率不都一样 | 收 / 付 | 每个费用名一条，带 `feeCode` |
| 2.1 | 应收合计 − 应付合计（金额×汇率）小于 0 | `null` | 空数组 |
| 2.2 | 按 `CurrencyId` 分组，原币应收 − 原币应付小于 0 | `null` | 每个亏损币别一条，带 `currency` |

## 4.9 按结算对象类别自动带结算对象

两处会按结算对象类别（`IndustryCategory`）去目标业务上找往来单位当结算对象：

- **引入费用** `ImportOrderFeesToTransportOrderAsync`，入参 `importOriginalSettlement=false` 时，按**源费用的**结算对象类别找。
- **收付互生**（收转付 / 付转收）`GenerateOppositeOrderFeesAsync`，按费用代码上配置的默认客户类型字母换算成类别（字母第 n 个对应枚举值 n：`a`=船公司=1 … `w`=地面代理=23）。生成应收取 `DefaultDebitName`，生成应付取 `DefaultCreditName`。

| 结算对象类别（枚举值 / 字母） | 取目标业务上的哪一列 | 说明 |
| :-- | :-- | :-- |
| 发货人（2 / b） | `TransportOrder.ShipperId` | 四种业务都有 |
| 场站（3 / c） | `SeaExport.YardId` | 只有海运出口有；其它业务取不到 |
| 收货人（5 / e） | `TransportOrder.ConsigneeId` | — |
| 报关行（6 / f） | `TransportOrder.CustBrokerId` | — |
| 通知人（8 / h） | `TransportOrder.NotifierId` | — |
| 车队（9 / i） | `TransportOrder.TeamId` | — |
| 订舱代理（15 / o） | `SeaExport.BookingAgentId`，件杂货取 `BreakBulk.BookingAgentId` | 海运进口、空运出口取不到 |
| 委托单位（16 / p） | `TransportOrder.ClientId` | — |
| 仓库（17 / q） | `TransportOrder.WarehouseId` | — |
| 保险公司（18 / r） | `TransportOrder.InsuranceId` | — |
| 目的港代理（19 / s） | `SeaExport.PodAgentId`，件杂货取 `BreakBulk.PodAgentId` | 国外代理。海运进口、空运出口取不到 |
| **地面代理（23 / w）** | `BreakBulk.GroundAgentId` | **2026-09-27 新增**。只有件杂货有，其它业务取不到 |
| 其余类别（船公司、航空公司、快递公司、贸易商、代理、其他、供应商、船代、码头、工厂、个人） | — | 不支持：类别与结算对象一并置空 |

**取不到时的口径**：类别支持、但目标业务上这一列为空（或这种业务根本没有这一列）时，**保留类别、结算对象置空**；类别为空或不支持时，类别与结算对象一并置空。两种情况都不报错，费用照常生成为录入状态，由用户补结算对象后再提交。

同一套映射也用在账单识别生成费用（`GeminiAdminAppService`，件杂货的票会带上件杂货扩展表）与完成服务项按模板生成费用（只有海运出口有服务项）。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：任务级备注必填]** `ModifyOrderFeeAsync`、`DeleteOrderFeeAsync` 的 `remark` 为空或纯空白时分别报「申请修改原因不能为空」「申请删除原因不能为空」，任务不会创建。前端提交前必须让用户填。不要和费用行 `orderFees[].remark`、也不要和提交审核的负利润备注搞混。

> [!IMPORTANT] **[卡点 2：非审核通过不能申请]** 申请修改报「非审核通过状态费用不可提交」；申请删除报「非审核通过状态费用不可申请删除」。

> [!IMPORTANT] **[卡点 3：已进入下游单据的不能动]** 已对账、已付费申请、已关联开票申请、已收费结算，分别报「已参与对账的费用不可申请修改/删除」「已进行付费申请的费用不可申请修改/删除」「已关联开票申请的费用不可申请修改/删除」「已进行收费结算的费用不可申请修改/删除」。

> [!IMPORTANT] **[卡点 4：一次只能操作同一个更改单]** 主单费用与更改单费用、不同更改单的费用不能混在一次请求里。报「主单费用与更改单费用不可一起操作,不同更改单的费用也不可一起操作,请分开处理」。

> [!IMPORTANT] **[卡点 5：费用锁定后不能提交]** 主单或该更改单已做费用锁定时，申请修改/申请删除都会被 `FeeLockedCheckAsync` 拦住。

> [!IMPORTANT] **[卡点 6：工作流没配好先拦]** 费用变更工作流未配置或未启用时，报「未配置或未启用费用变更工作流，无法提交审核」，此时还没有建任务。

> [!IMPORTANT] **[卡点 7：有 sorting 入参的列表不要改成 sortId]** `PagingAndSorting.Sorting` 基类默认就是 `CreationTime DESC`，前端不传也会带上这个值。因此 `OrderFeeAdmin/GetPagedListAsync` 以及付费申请、对账、开票申请、收费结算等外层列表，一律仍走入参 `sorting`。只有费用打印会覆盖成 `SortId ASC, CreationTime ASC`；没有费用级排序入参的嵌套费用清单才按 `sortId` 再 `creationTime`。

> [!IMPORTANT] **[卡点 8：单独改排序、恢复顺序不做任何业务判断]** `SortOrderFeesAsync`、`RestoreOrderFeeSortAsync` 只改 `sortId`，不查费用锁定、状态、对账、付费申请、开票，也不调字段屏蔽回填。列表为空或费用 id 不存在就跳过，不报错。恢复顺序按 `creationTime` 升序从 `0` 递增，`changeOrderId` 为空只动主单费用。

> [!IMPORTANT] **[卡点 9：费用预警按「这一行」全部费用算，主单和更改单不能混]** `changeOrderId` 为空只看主单费用；有值只看该更改单。不要拿主单预警去解释更改单面板，也不要指望接口把主单+更改单费用加在一起。

> [!IMPORTANT] **[卡点 10：预警 6 的「本月汇率」跟录入带出汇率同一套口径]** 会计期间：主单用业务 `AccountDate`，更改单用更改单 `AccountDate`。本位币（业务所属公司配的）费用必须汇率 = 1，不查表。其它币别按「币别 + 本位币 + 会计期间」取汇率表，区间重叠取起始日期最晚的一条；应收对 `DRValue`，应付对 `CRValue`；匹配不到或对应收付值为空按 0。公司没配本位币时 6.1/6.2 整段跳过，不报错。

> [!IMPORTANT] **[卡点 11：合计利润和单币别利润不是同一套数]** 2.1 用金额×汇率再相减，和提交审核时的负利润备注同一折算方式（但提交审核会排除录入状态，预警把录入状态也算进去）。2.2 按币别分组、**不乘汇率**，原币应收 − 原币应付。一个币别只有应付没有应收，只要应付金额 &gt; 0 就会命中 2.2。

> [!IMPORTANT] **[卡点 12：海运费只看费用名中文名是否包含「海运费」]** 不看英文名，也不把「海运附加费」这种不含「海运费」三字的算进去。「国际海运费」会命中。币别代码去空格后忽略大小写等于 `USD` 才算美元。

> [!IMPORTANT] **[卡点 13：组织条件是「配大组织覆盖下属」，不是「配小组织覆盖上级」]** 工作流配「属于青岛分公司」时，青岛分公司自己以及青岛业务部等下属部门的票都会走这条线。反过来，票的所属组织是青岛分公司、条件却配成青岛业务部，**匹配不上**，会落到其它线或默认线；对不上任何起始线时提交会报「业务数据不满足任何起始审批条件」。不要指望配部门能覆盖分公司。

> [!IMPORTANT] **[卡点 14：件杂货的港口是海港，按港口下钻要带 `isSea=true`]** 件杂货的起运港、目的港和海运出口、海运进口共用海运港口表。费用任务按起运港/目的港分组时，件杂货和同一港口的海运票**并成一组**（`isSea=true`）；下钻列表要把 `isSea=true` 和港口 id 一起传，只传 id 会把空运港口表里同号的机场也带出来。批量引入候选查询 `bizType=3` 时 `polId`/`podId` 也传海港 id。

> [!IMPORTANT] **[卡点 15：件杂货没有船公司、装运方式、订单类型、场站]** 费用任务按这几项筛选时件杂货的票不会出现；按「未填写」筛（`carrierIdEmpty`、`blTypeEmpty`、`billTypeEmpty`、`yardIdEmpty`）或按它们分组时，件杂货的票全部算未填写。批量引入候选查询传 `carrierId` 时，对 `bizType=3` 不生效，照常返回。这是预期，不是漏数。

> [!IMPORTANT] **[卡点 16：地面代理只有件杂货能带出来]** 结算对象类别为「地面代理」时，只有目标业务是件杂货才带得出结算对象（取件杂货的地面代理）。目标业务是海运出口等其它类型时，**保留类别「地面代理」、结算对象为空**；在件杂货上线之前，地面代理属于不支持的类别，类别和结算对象会一起被清空，现在类别会留下来。两种情况都不报错，费用生成为录入状态，要补结算对象才能提交。另外订舱代理只从海运出口、件杂货上取，目的港代理同理；空运出口的票选订舱代理类别时结算对象为空，这是既有口径，本次未改。
