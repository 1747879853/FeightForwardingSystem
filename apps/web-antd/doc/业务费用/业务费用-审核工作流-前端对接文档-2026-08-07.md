# 业务费用审核工作流 — 前端对接文档

**变更日期**：2026-08-07

**变更概述**：业务费用审核此前是「一步到位」——谁有 `Admin.OrderFee.Audit` 权限，谁就能直接把费用审通过或驳回，没有任何审批链路。本次接入工作流引擎，采用**主子工作流**结构：一个 `(业务 + 更改单 + 任务类型)` 组合生成一个主工作流，该组合下每条费用各生成一个子工作流，路径完全一致。

**本次没有新增任何接口地址**，全部是既有接口的入参、出参或行为变更，另有 3 个旧接口下线。

---

## 一、前端必读的 5 个关键变化

| # | 变化 | 前端要做什么 |
| :--- | :--- | :--- |
| 1 | 费用任务列表**只返回与当前登录人有关的行** | 有审核权限不代表能看到全部待办，只有工作流路径上轮到过你的行才会出现。原来「审核列表看到全部」的预期要改 |
| 2 | 列表新增筛选 `myAuditStatus`（`0` 待我审核 / `2` 我已审核） | 加筛选控件，取值与 `TaskStatus` 对齐 |
| 3 | 列表行新增 `myTaskStatus` 与 `workFlows` | 前者是我在本行的状态，后者是主工作流审批路径，可直接渲染审批流图 |
| 4 | 审核不再是一步到位 | 调 `OrderFeeTaskAuditAsync` 通过后，费用**可能仍是待审核状态**（流程还没走完），不能假设审完就变已通过 |
| 5 | 3 个旧的分开审核接口**已下线** | `SubmitOrderFeeAuditAsync` / `ModifyOrderFeeAuditAsync` / `DeleteOrderFeeAuditAsync` 已整体注释，调用会 404，统一改用 `OrderFeeTaskAuditAsync` |

> [!NOTE]
> **入参 `myAuditStatus` 与出参 `myTaskStatus` 取值已对齐，可共用一套字典。**
> 入参 `myAuditStatus`（筛选）：`0` 待我审核、`2` 我已审核（通过和驳回都算）。
> 出参 `myTaskStatus`（行状态，`TaskStatus` 枚举）：`0` 待我审核、`1` 我已驳回、`2` 我已通过。
> 出参多一个 `1`（驳回）的细分，筛选项没有；筛选传 `2` 会把我通过的和我驳回的都查出来。

### 2.6 可见范围规则（行为变化，重点）

判定依据是**子工作流**里当前登录人的状态：

| 场景 | 是否出现在我的列表 |
| :--- | :--- |
| 我在第 1 级，正在等我审 | 出现，`myTaskStatus = 0` |
| 我在第 1 级且已审完，流程走到第 2 级 | 出现，`myTaskStatus = 1` 或 `2` |
| 我在第 2 级，流程还在第 1 级（还没轮到我） | **不出现** |
| 或签场景，同级别的别人先审掉了 | **不出现**（我的状态被置回 `null`） |
| 组合内发生撤回或新提交导致工作流重建 | **暂时不出现**，直到重新轮到我 |

> 最后两行是常见困惑来源：审核人会看到自己的待办「凭空消失」，这是设计如此，不是 bug。

**权限：** `Admin.OrderFee.Audit`

### 4.1 请求参数（OrderFeeTaskDetailInputDto，未变）

## 五、接口 4 — OrderFeeTaskAuditAsync（行为变）

**Summary：** 费用所有任务审核，逐条推进子工作流。

**路径：** `POST /api/services/app/OrderFeeAdmin/OrderFeeTaskAuditAsync`

**权限：** `Admin.OrderFee.Audit`

### 5.1 请求参数（OrderFeeTaskAuditDto，未变）

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| Success | `success` | bool | 是 | 审核意见，`true` 通过 / `false` 驳回 |
| Remark | `remark` | string | 否 | 审批意见 |
| OrderFeeIds | `orderFeeIds` | Guid[] | 是 | 要审核的费用 id 列表，必须同属一个业务且同属一个更改单（或同为主单） |

### 5.2 响应

无返回值（`result` 为 `null`）。

### 5.3 行为变化（重点）

- **通过不等于审完。** 通过后若还有下一级审核人，费用状态**不变**（提交类仍是「提交审核」），只是工作流推进一级。只有走完最后一级才会真正落业务：提交类置为审核通过、申请删除类真正删除费用、申请修改类把修改应用到费用上。
- **驳回立即生效。** 任意一级驳回，该条费用的子工作流立即终止，费用置为驳回。
- 前端审核后应**重新拉取列表**，不要在本地直接把行改成已通过。

### 5.4 新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |
| `未找到该费用的审核流程` | 该费用没有对应的子工作流实例（通常是存量数据或工作流被清理） |
| `非当前审核人不可审核` | 当前登录人不是该费用子工作流的当前审核人 |

## 六、接口 5 — OrderFeeTaskBatchAuditAsync（行为变）

**Summary：** 费用所有任务批量审核。

**路径：** `POST /api/services/app/OrderFeeAdmin/OrderFeeTaskBatchAuditAsync`

**权限：** `Admin.OrderFee.Audit`

### 6.1 请求参数（OrderFeeTaskBatchAuditDto，未变）

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| Success | `success` | bool | 是 | 审核意见，`true` 通过 / `false` 驳回 |
| Remark | `remark` | string | 否 | 备注 |
| TransportOrderIds | `transportOrderIds` | Guid[] | 否 | 兼容字段，审核该业务下全部（主单 + 所有更改单）。`items` 有值时忽略 |
| Items | `items` | array | 否 | 要审核的行列表，与列表行一一对应，**推荐使用** |

`items[]`（OrderFeeTaskBatchAuditItemDto）：

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| TransportOrderId | `transportOrderId` | Guid | 是 | 业务 id，就是列表行的 `entityId` |
| ChangeOrderId | `changeOrderId` | Guid? | 否 | 更改单 id，就是列表行的 `changeOrderId` |

### 6.2 行为变化（重点）

批量审核一次覆盖多行，而当前登录人**未必是每一条费用的当前审核人**。现在的行为是：

- **只处理轮到当前登录人审的那些费用**，轮不到的**静默跳过**，不会整批失败。
- 一条都轮不到时报 `没有待您审核的费用任务`。

所以批量审核后，被处理的费用条数**可能少于**前端勾选的条数，必须重新拉列表核对，不能按勾选数量做本地更新。

### 6.3 新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |
| `没有待您审核的费用任务` | 勾选范围内没有任何一条费用轮到当前登录人审 |

## 七、接口 6 — OrderFeeTaskWithdrawAsync（行为变）

**Summary：** 费用所有任务撤销提交。

**路径：** `POST /api/services/app/OrderFeeAdmin/OrderFeeTaskWithdrawAsync`

**权限：** `Admin.OrderFee.Edit`

### 7.1 请求参数（OrderFeeTaskWithdrawDto，未变）

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| OrderFeeIds | `orderFeeIds` | Guid[] | 是 | 要撤回的费用 id 列表，必须同属一个业务且同属一个更改单（或同为主单） |

### 7.2 行为变化

- **流程进行到第几级都能撤回**，只要该条费用还没出最终结论。已通过、已驳回的撤不了。
- 撤回后会重建该组合剩余在审费用的主子工作流：路径没变则保留已有审批进度，路径有变则全部退回第 1 级。
- **费用创建人与任务提交人都能撤回**：当前登录人是 `orderFee.creatorUserId`（费用创建人）或该费用待审任务的提交人，任一命中即可撤回，两者不必是同一个人。典型场景是业务联系单审核通过自动生成并提交的费用，创建人与提交人都记当票销售。

### 7.3 新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |

## 九、接口 8~10 — 三个提交入口（行为变）

`SubmitOrderFeeAsync` / `ModifyOrderFeeAsync` / `DeleteOrderFeeAsync` 的**入参、出参完全未变**，仍返回主任务 id（Guid）。

**路径：**

| 接口 | 方法 | 路径 |
| :--- | :--- | :--- |
| SubmitOrderFeeAsync | POST | `/api/services/app/OrderFeeAdmin/SubmitOrderFeeAsync` |
| ModifyOrderFeeAsync | POST | `/api/services/app/OrderFeeAdmin/ModifyOrderFeeAsync` |
| DeleteOrderFeeAsync | POST | `/api/services/app/OrderFeeAdmin/DeleteOrderFeeAsync` |

### 9.1 行为变化

- 提交后会生成或重建该组合的主子工作流。
- **本次提交会连带影响该组合下已在审的其它费用**：若重新匹配出的路径与原路径不同，所有在审费用的子工作流会被删除重建、退回第 1 级；路径相同则保留已有进度。
- 若工作流所有节点都配成「直接通过」（算不出任何审核人），**直接执行业务动作**：提交的费用直接置为审核通过、申请删除的**直接删除费用**、申请修改的直接应用修改。

### 9.2 新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |
| `未配置或未启用费用提交工作流，无法提交审核` | 没有启用中的费用提交工作流 |
| `未配置或未启用费用变更工作流，无法提交审核` | 没有启用中的费用变更工作流（申请修改与申请删除共用） |
| `已进行收费结算的费用不可申请修改` | 申请修改时费用已存在按费用收费结算明细 |
| `已进行收费结算的费用不可申请删除` | 申请删除时费用已存在按费用收费结算明细 |
| `业务数据不满足任何起始审批条件` | 工作流起始线的条件都没匹配上，且没有配默认线 |
| `未找到符合条件的用户,请检查工作流节点{节点id}` | 节点算不出任何审核人 |
| `本票业务未指定工作流节点所需的关联人员,请检查工作流节点{节点id}` | 节点配了按用户属性审核，但本票业务没有该属性的关联人员 |

### 9.3 新增接口 BatchModifyOrderFeeSettlementAsync

**Summary：** 批量把已审核费用的结算对象改成**同一个**。一次请求只能一种收付类型。应收直接改库、不走工作流；应付备注必填，走申请修改工作流（与 `ModifyOrderFeeAsync` 相同）。

**路径：** `POST /api/services/app/OrderFeeAdmin/BatchModifyOrderFeeSettlementAsync`

**权限：** `Admin.OrderFee.Edit`

#### 9.3.1 入参（`BatchModifyOrderFeeSettlementDto`）

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| TransportOrderId | `transportOrderId` | Guid | 是 | 业务 id。费用必须属于这一票 |
| PaySide | `paySide` | int | 是 | 收付类型。`0` 收、`1` 付。一次只能一种，且必须与这批费用一致 |
| SettlementId | `settlementId` | Guid | 是 | **要改成的结算对象 id，只有一个**，本批费用全部改成它 |
| Remark | `remark` | string | 应付必填 | 最长 4096。应付写入每条 `TaskItem.Remark`；应收不使用 |
| OrderFeeIds | `orderFeeIds` | Guid[] | 是 | 费用 id 列表，必须已审核通过 |

#### 9.3.2 出参（`BatchModifyOrderFeeSettlementResultDto`）

| 字段名 | JSON Key | 类型 | 何时有值 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| TaskBaseId | `taskBaseId` | Guid? | **仅应付** | 申请修改主任务 id。应收直接改库，此字段为 `null` |

#### 9.3.3 行为

- 卡点与 `ModifyOrderFeeAsync` 相同：非审核通过、已对账、已付费申请、已开票、已收费结算、已有在审修改/删除、主单与更改单混选、费用锁定，一律拦截。
- **应收（`paySide=0`）：** 不建任务、不走工作流，直接把各条费用的 `SettlementId` 写成入参这一个。
- **应付（`paySide=1`）：** `remark` 必填；其余字段保持库里原值，只把结算对象改成入参这一个，然后走 `ModifyOrderFeeAsync`（生成/重建费用变更工作流）。

#### 9.3.4 本接口新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |
| `收付类型错误` | `paySide` 不是 `0`/`1` |
| `一次只能修改一种收付类型的费用` | `orderFeeIds` 里同时有应收和应付 |
| `费用收付类型与输入不一致` | 费用的收付类型与入参 `paySide` 不同 |
| `申请修改原因不能为空` | 应付未传 `remark` 或全是空白 |
| `费用不存在` | 有费用 id 在库里找不到 |

其余报错与 `ModifyOrderFeeAsync` 相同（含应付工作流未配置）。

## 十一、工作流配置端（WorkFlowAdminAppService）

**路径：** `POST /api/services/app/WorkFlowAdmin/EditAsync`（入参结构未变）

### 11.1 新增的费用条件类型（TaskTypeCondition）

配置费用工作流的连线条件时可用，费用提交与费用变更两类工作流**共用同一套**：

| 枚举值 | 条件 | 可用比较符（ShouldBe） | Value 填什么 |
| :--- | :--- | :--- | :--- |
| `1` | 业务所属人 | `8` 等于、`9` 不等于 | 用户 id（long） |
| `2` | 业务所属组织 | `10` 属于、`11` 不属于 | 组织 id（long），会自动展开下级组织 |
| `4` | 收付类型 | `8` 等于、`9` 不等于 | PaySide 枚举值 |
| `5` | 业务类型 | `8` 等于、`9` 不等于 | BizType 枚举值 |
| `6` | 利润 | `4` 小于、`5` 小于等于、`6` 大于、`7` 大于等于 | 金额（decimal） |
| `7` | 利润率 % | 同上 | 百分比数值，`15` 代表 15% |
| `8` | 存在某个费用名应收 < 应付 | `0` 是、`1` 不是 | **不用填** |
| `9` | 存在应付费用名但应收没有 | `0` 是、`1` 不是 | **不用填** |
| `10` | 存在应收费用名但应付没有 | `0` 是、`1` 不是 | **不用填** |

> 枚举值 `3` 已废弃（原「费用金额」条件），不要使用。

### 11.2 计算口径

- **利润** = 应收合计 − 应付合计，均按 `金额 × 汇率` 折算。
- **利润率%** = 利润 ÷ 应付合计 × 100。**应付合计为 0 时该条件一律判为不满足。**
- 参与计算的费用是**本行（业务 + 更改单）下除录入状态和已驳回外的全部费用**，不是只算本次在审的。
- 三个费用名比对条件按 `FeeCodeId` 配对，且**互不重叠**：`8` 只比对应收应付都存在的费用名，只有一边有的分别归入 `9` 和 `10`。
- **收付类型**条件取本次在审费用的收付方向，**组合内收付混合时该条件一律判为不满足**。

### 11.3 新增报错

| 报错文案 | 触发条件 |
| :--- | :--- |
| `费用申请删除与费用申请修改共用同一条工作流,请配置在费用申请修改下` | 试图创建 `TaskType = 2`（费用申请删除）的工作流 |
| `非费用任务不可输入费用条件` | 在非费用工作流上配置了费用条件 |
| `利润条件比较符输入错误` / `利润率条件比较符输入错误` / `费用名比对条件比较符输入错误` | 比较符不在允许范围 |

> 费用工作流**支持按用户属性配置审核人**（如「本单销售」「本单操作」），审核人从该票业务的关联人员（`OrderUser`）里解析。付费申请工作流不支持这个能力。

## 十三、避坑指南

> [!IMPORTANT]
> **1. 筛选「我已审核」传 `2`，不是 `1`。** 取值与 `TaskStatus` 对齐（`0` 审核中 / `1` 驳回 / `2` 通过），所以筛选项跳过了 `1`。筛选传 `2` 会把我通过的和我驳回的都查出来。

> [!IMPORTANT]
> **2. 审核通过后费用状态可能不变。** 多级审批下，中间级通过只推进工作流。前端不能在本地把行标成已通过。

> [!IMPORTANT]
> **3. 待办会「消失」。** 或签被别人先审掉、组合内发生撤回或新提交导致工作流重建，都会让这一行暂时从当前审核人的列表里消失。这是设计如此。

> [!IMPORTANT]
> **4. 提交一条费用会影响同组合其它在审费用。** 若路径重新匹配后有变化，已经审到第 3 级的费用会被退回第 1 级重审。

> [!IMPORTANT]
> **5. 上线前必须清空存量在审任务。** 存量的待审核任务没有工作流实例，上线后既走不了新流程也走不了老逻辑，审核时会报 `未找到该费用的审核流程`。

> [!IMPORTANT]
> **6. 上线前必须配好两份工作流。** 费用提交、费用变更各一份且启用，否则所有提交类操作全部被拦。
