> 本文档汇总组织机构模块的接口说明与变更记录，供前端对接使用。服务名：`OrganizationUnitAppService` 基础路径：`/api/services/app/OrganizationUnit/` 关联文档：`文档/用户/用户api.md`

## 一、数据模型

### 1.1 OrganizationUnitDto（组织返回模型）

| 字段名 | 类型 | 说明 |
| :-- | :-- | :-- |
| id | long | 组织id |
| parentId | long? | 父级组织id |
| code | string | 层级编码（如 "00001.00002"） |
| displayName | string | 组织名称 |
| memberCount | int | 直接成员数（只算**未删除**的用户，同一用户重复关联只算一次） |
| memberCountTotal | int | 总成员数（含下级，口径同上） |
| isCompany | bool | 是否是公司（false=部门） |
| localCurrencyId | long? | 本位币id |
| localCurrencyCode | string | 本位币代码（如 "CNY"、"USD"）【只读】 |
| shortName | string | 组织简称 |
| enName | string | 英文名 |
| chargeUserId | long? | 负责人用户id |
| chargeUserNickName | string | 负责人名称【只读】 |
| contactPhone | string | 联系电话 |
| email | string | 邮箱 |
| address | string | 办公地址 |
| webUrl | string | 官方网址 |
| enable | bool | 是否启用 |
| unifiedSocialCreditCode | string | 统一社会信用代码/纳税人识别号。**同时用作接口开票的销方税号** |
| invoiceAddress | string | 开票地址 |
| invoiceTel | string | 开票电话 |
| invoiceAppKey | string | 开票应用 appKey。**仅这三个接口返回**：获取单个组织 / 新建组织 / 更新组织 |
| invoiceAppSecret | string | 开票应用 appSecret（**机密**）。返回范围同上 |
| invoiceAccessToken | string | 开票令牌 accessToken（**机密**）。**固定值，人工维护，系统不会自动刷新**。返回范围同上 |
| orgBankAccounts | OrgBankAccountDto[] | 银行账户列表（仅 GetOrganizationUnitAsync 返回） |

> 标注【只读】的字段为后端自动关联填充，前端无需提交。

#### 关于 invoiceAppKey / invoiceAppSecret / invoiceAccessToken（接口开票用）

**每家公司在开票服务商那边是独立的应用，各配各的**，所以这三项按公司维护，不是全局配置。它们与 `unifiedSocialCreditCode`（作销方税号）一起构成该公司的开票凭据，缺任何一项都开不了票。

> ⚠️ **`invoiceAccessToken` 是固定值，必须人工维护，系统不会自动获取或刷新。** 服务商侧的硬限制：同一应用 30 天内取号超过 50 次会被判定为攻击、**直接锁死开不出票**，且只能由服务商人工重置。所以令牌改成向服务商索取一次、填在这里长期使用。令牌失效时开票会报错提示来这里更新，**不会自动重取**——宁可这张票先开不出来，也不能把账号锁死。

**返回范围被刻意收窄**——`invoiceAppSecret` 与 `invoiceAccessToken` 都是机密，只有下面三个接口返回，其余接口（组织列表、移动组织、以及所有返回 `OrganizationUnitSimpleDto` / `CompanySimpleDto` 的地方）**一律返回 null**：

| 接口                                    | 返回              | 可写入 |
| :-------------------------------------- | :---------------- | :----- |
| `GetOrganizationUnitAsync` 获取单个组织 | ✅                | —      |
| `CreateOrganizationUnitAsync` 新建组织  | ✅                | ✅     |
| `UpdateOrganizationUnitAsync` 更新组织  | ✅                | ✅     |
| `GetOrganizationUnitsAsync` 组织列表    | ❌ 返回 null      | —      |
| `MoveOrganizationUnitAsync` 移动组织    | ❌ 返回 null      | —      |
| 其余接口 / 各类 Simple 输出             | ❌ 不含这两个字段 | —      |

**前端注意**：

1. 只有公司资料的编辑页需要这两个输入项，且**只在 `isCompany = true` 的组织上有意义**（部门不开票）；
2. `invoiceAppSecret`、`invoiceAccessToken` 建议用密码框，别在列表或详情页明文展示；
3. 组织列表里这两个字段恒为 null，**不要拿列表数据去回显编辑表单**，要调 `GetOrganizationUnitAsync`。

## 二、组织主表接口

### 2.1 创建组织

**接口：** `POST /api/services/app/OrganizationUnit/CreateOrganizationUnitAsync`

**请求参数：**

| 字段名 | 类型 | 必填 | 最大长度 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| parentId | long? | 否 | - | 父级组织id，null表示根级 |
| displayName | string | **是** | 128 | 组织名称 |
| isCompany | bool | 否 | - | 是否是公司，false=部门，默认false |
| localCurrencyId | long? | 否 | - | 本位币id（需为有效的Currency记录） |
| shortName | string | 否 | 64 | 组织简称 |
| enName | string | 否 | 128 | 英文名。**2026-09-14 由 64 改为 128** |
| chargeUserId | long? | 否 | - | 负责人用户id（需为有效的User记录） |
| contactPhone | string | 否 | 64 | 联系电话 |
| email | string | 否 | 64 | 邮箱 |
| address | string | 否 | 64 | 办公地址 |
| webUrl | string | 否 | 128 | 官方网址 |
| enable | bool | 否 | - | 是否启用，默认true |
| unifiedSocialCreditCode | string | 否 | 128 | 统一社会信用代码/纳税人识别号（**接口开票时作销方税号**） |
| invoiceAddress | string | 否 | 256 | 开票地址 |
| invoiceTel | string | 否 | 64 | 开票电话 |
| invoiceAppKey | string | 否 | 128 | 开票应用 appKey（接口开票用，按公司各配各的） |
| invoiceAppSecret | string | 否 | 128 | 开票应用 appSecret（**机密**，建议密码框） |
| invoiceAccessToken | string | 否 | 512 | 开票令牌（**机密**，建议密码框）。**固定值，向服务商索取后填入，系统不会自动获取** |

**返回：** `OrganizationUnitDto`（含 `invoiceAppKey` / `invoiceAppSecret` / `invoiceAccessToken`）

**业务校验：**

- `localCurrencyId` 如传值，需存在于Currency表，否则报错："本位币不存在。"
- `chargeUserId` 如传值，需存在于User表，否则报错："负责人不存在。"

### 2.3 获取单个组织（含银行账户列表）

**接口：** `GET /api/services/app/OrganizationUnit/GetOrganizationUnitAsync?Id={id}`

**请求参数：**

| 字段名 | 类型 | 必填   | 说明   |
| :----- | :--- | :----- | :----- |
| id     | long | **是** | 组织id |

**返回：** `OrganizationUnitDto`（含 `orgBankAccounts` 银行账户数组，以及 `invoiceAppKey` / `invoiceAppSecret` / `invoiceAccessToken`）

> 这是**唯一一个能取到开票 appKey/appSecret/accessToken 的查询接口**，公司资料编辑页要回显必须调它，组织列表里这两个字段恒为 null。

**成员数说明（与 `GetOrganizationUnitsAsync` 一致）：**

| 字段 | 计算规则 |
| :-- | :-- |
| `memberCount` | 本组织直接成员数 = `UserOrganizationUnit` 关联行**内连用户表**（自动排除已删除用户/非本租户用户）后**按 `UserId` 去重**的人数 |
| `memberCountTotal` | 本组织及所有下级组织（`code` 以当前组织 `code` 为前缀）的 `memberCount` 之和 |

> 该口径与成员列表 `GetOrganizationUnitUserPagingListAsync` 的 `totalCount` **完全一致**，两处对不上就是 bug。详见第十二节。

### 2.4 获取组织列表

**接口：** `GET /api/services/app/OrganizationUnit/GetOrganizationUnitsAsync`

**请求参数：**

| 字段名     | 类型  | 必填 | 说明                                       |
| :--------- | :---- | :--- | :----------------------------------------- |
| isCompany  | bool? | 否   | 筛选：true=仅公司，false=仅部门，null=全部 |
| isDisabled | bool? | 否   | 筛选：true=仅禁用，false=仅启用，null=全部 |

**返回：** `OrganizationUnitDto[]`

> 说明：组织的禁用状态对应字段 `enable`（`enable=false` 即禁用）。组织选择器若只取可用组织，传 `isDisabled=false`。
>
> 其余各组织搜索/树接口（`GetOrganizationUnitsWithLevelAsync`、`GetCurrentOrganizationUnitsAsync`、`GetAllOrganizationUnitsAsync`、`GetCurrentOrganizationUnitUserAsync`、`GetAllOrganizationUnitUserAsync`、`GetOrganizationUnitsUserTreeAsync`、`GetOrganizationUnitTreeAsync`、`GetHandleCCTreeAsync`、`GetOrganizationUnitsTreeAsync`）入参统一改为 DTO 承载查询条件（`isCompany` + `isDisabled`，语义一致）。其中带用户id 的接口使用 `OrganizationUnitCurrentQueryDto`（含 `id`、`isCompany`、`isDisabled`）。
>
> **多组织(2026-07-22)**：一个用户可属于多个组织。以下原来依赖「用户单一组织 Code」的接口，改为取该用户**全部组织**的 Code 前缀并集：
>
> - `GetCurrentOrganizationUnitsAsync` / `GetCurrentOrganizationUnitUserAsync`（入参 `id`=用户id）：返回该用户**全部组织及其所有下属组织**的并集（用户无组织时返回空数组，不再抛「部门为多个」）。
> - `GetOrganizationUnitsUserTreeAsync` / `GetOrganizationUnitsTreeAsync`（当前登录人）：以当前登录人**全部组织**为根构建组织树的并集。
> - `GetHandleCCTreeAsync`：仍返回全部组织树，节点 `canHandle` 在其 Code 命中当前登录人**任一**组织前缀时为 `true`。
>
> 校验：新增/编辑用户分配组织时，若所选组织已禁用将报错「所选组织已被禁用，无法分配用户。」
>
> 列表接口不返回 `orgBankAccounts`，需查看银行账户请调用单独接口。

### 2.5 获取当前登录人有数据权限的公司列表

按**当前登录人的数据权限**返回其拥有权限的**分公司（公司）列表**，结果只包含公司（`isCompany=true`），**不含部门**。用于业务表单中的「所属公司」选择器等场景。

**接口：** `GET /api/services/app/OrganizationUnit/GetMyPermissionCompaniesAsync`

**权限：** 仅需登录（`[AbpAuthorize]`），无需额外功能权限。

**请求参数（Query）：**

| 参数 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| module | int（数据权限模块） | 否 | 传页面对应的模块，按该模块生效的规则算；该模块没单独配置时后端自动回退到通用规则，**前端只调一次**，不用判断模块配没配。不传只看通用规则。枚举值见《数据权限模块接口文档》2.3。**2026-09-29 新增** |

**返回：** `OrganizationUnitSimpleDto[]`（按组织 `code` 升序排列）

**数据权限规则（取 `ManageType=Get` 的查询权限）：**

规则的取法与数据权限过滤一致：本人和每个角色各自判断，有该模块的规则就用该模块的，没有就用通用规则，最后合并；角色上配的规则同样生效。「排除人员」规则不影响公司列表。

| 数据权限类型 | 枚举值 | 返回的公司范围 |
| :-- | :-- | :-- |
| 全部（All） | 5 | 系统内**所有公司**（不含部门） |
| 本人（My） | 0 | 仅**自己所属公司**（自动拥有，无需配置） |
| 自己部门（MyPart） | 1 | 自己部门所归属的公司（即自己所属公司） |
| 自己公司（MyCompany） | 2 | 自己所属公司 |
| 部分（ManyPart，多部门/多公司） | 4 | 所配置组织向上追溯得到的**所属公司**（部门→其所属公司；公司→自身） |
| 人员（ManyUser，多人） | 3 | 所配置人员的**所属公司** |

**逻辑说明：**

1. 命中 `All`（全部权限）时，直接返回所有 `isCompany=true` 的组织。
2. 非全部时，先并入**当前登录人自己所属公司**（本人权限自动拥有），再根据各权限项累加：
   - `ManyPart`：把每个配置的组织 id 向上追溯到最近的公司节点（自身即公司则取自身）；
   - `ManyUser`：把每个配置的人员映射到其所属公司（每条组织链取最靠近叶子的公司节点）。
3. 结果按公司 id 去重后返回。

**返回示例：**

```json
[
  {
    "id": 5,
    "name": "上海分公司",
    "localCurrencyId": 1,
    "localCurrencyCode": "CNY"
  },
  {
    "id": 8,
    "name": "青岛分公司",
    "localCurrencyId": 1,
    "localCurrencyCode": "CNY"
  }
]
```

## 四、组织成员相关接口

### 4.1 获取无组织用户分页列表（为添加组织成员查找用户）

在**组织机构管理**中，向某个组织添加成员时，需要从候选用户中挑选**尚未加入该组织**的用户。

> **变更(2026-07-22)：一个用户可属于多个组织。** 本接口不再返回「无任何组织」的用户，改为按入参 `organizationUnitId` 返回**所有不属于该组织及其全部父级(祖先)组织**的用户（这些用户即便已在别的无关组织，也可被添加到本组织）。`organizationUnitId` 为空或 &lt;=0 时返回全部用户。

本接口用于分页查询**不属于指定组织及其上级组织链**的用户列表，常用于组织成员添加弹窗中的用户选择器。

**与 `FindUserPagedListForOuAsync` 的区别：**

| 接口 | 筛选范围 | 典型用途 |
| :-- | :-- | :-- |
| `GetUserPagingListForOuAsync` | **返回不属于 `organizationUnitId` 及其父级组织的用户** | 向指定组织添加成员时，排除已在该组织或其上级组织的用户 |
| `FindUserPagedListForOuAsync` | 返回**全部用户**（可按关键字/角色/启用状态过滤） | 查找用户，不排除任何组织的用户 |

**接口：** `GET /api/services/app/OrganizationUnit/GetUserPagingListForOuAsync`

**权限：** 需登录（`OrganizationUnitAppService` 类级别 `[AbpAuthorize]`）

**请求方式：** `GET`（Query String 传参）

**入参模型：** `UsersForOuPagingQueryDto`（继承 `Paging`）

| 字段名 | 类型 | 必填 | 默认值 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| pageIndex | int | 否 | 1 | 当前页码，从 1 开始 |
| pageSize | int | 否 | 10 | 每页条数，范围 1～1000 |
| keyWords | string | 否 | null | 关键字，模糊匹配用户**邮箱**、**昵称** |
| organizationUnitId | long | 否 | 0 | **当前组织id**：返回所有【不属于该组织及其全部父级(祖先)组织】的用户；为空或 &lt;=0 返回全部用户 |

**筛选逻辑：**

1. 当 `organizationUnitId > 0` 时，先取「该组织 + 其全部上级(祖先)组织」的 id 集合，返回在 `UserOrganizationUnit` 表中**不属于该集合任一组织**的用户（用户可属于多个组织，只要不在本组织及其上级链上即可被添加）；`organizationUnitId` 未传时返回全部用户。
2. 传入 `keyWords` 时，额外按邮箱、昵称模糊过滤。
3. 结果按**昵称**（`NickName`）升序排列。

**返回模型：** `PagingList<NameValueDto>`

| 字段名     | 类型           | 说明                                          |
| :--------- | :------------- | :-------------------------------------------- |
| items      | NameValueDto[] | 当前页数据列表                                |
| totalCount | int            | 符合条件的总记录数                            |
| pageIndex  | int            | 当前页码                                      |
| pageSize   | int            | 每页条数                                      |
| totalPages | int            | 总页数（只读，由 totalCount / pageSize 计算） |

**列表项字段（NameValueDto）：**

| 字段名 | 类型   | 说明                           |
| :----- | :----- | :----------------------------- |
| name   | string | 展示名称，格式：`昵称(用户名)` |
| value  | string | 用户 Id（long 转字符串）       |

> `name` 由后端拼接：`{SafeNickName}({UserName})`。`SafeNickName` 在用户不存在时返回「佚名」。

**请求示例：**

```
GET /api/services/app/OrganizationUnit/GetUserPagingListForOuAsync?pageIndex=1&pageSize=10&organizationUnitId=5
GET /api/services/app/OrganizationUnit/GetUserPagingListForOuAsync?pageIndex=1&pageSize=20&keyWords=张三&organizationUnitId=5
```

**返回示例：**

```json
{

    {
      "name": "张三(zhangsan)",
      "value": "1001"
    },
    {
      "name": "李四(lisi)",
      "value": "1002"
    }
  ],
  "totalCount": 2,
```

**前端对接说明：**

1. 下拉/穿梭框的 `label` 使用 `name`，`value` 使用 `value`（用户 Id 字符串，提交添加成员接口时需转为 `long`）。
2. 本接口仅用于**查找候选用户**；选定用户后，需再调用 `AddUserToOrganizationUnitAsync` 或 `AddUsersToOrganizationUnitAsync` 将用户加入目标组织。请把当前正在添加成员的组织 id 作为 `organizationUnitId` 传入。
3. 分页参数使用 `pageIndex`、`pageSize`，不要使用 `skipCount`。
4. `keyWords` 建议在前端输入框做防抖后再请求。
5. 返回的是「不属于 `organizationUnitId` 指定组织」的用户；用户可同时属于多个组织，只要不在该组织即会返回。`organizationUnitId` 不传则返回全部用户。
6. 本接口不返回用户邮箱、手机号、角色、组织名称等扩展字段。若需要完整信息，请使用 `UserAdmin/GetUserPagedListAsync` 或 `OrganizationUnit/FindUserPagedListForOuAsync`。

1. **组织列表接口**（`GetOrganizationUnitsAsync`）不返回 `orgBankAccounts` 字段，需要银行账户请调用 `GetOrganizationUnitAsync`（单条）或 `GetOrgBankAccountListAsync`。

## 八、变更记录（2026-06-27）

> 模块：组织机构（OrganizationUnitAppService） + 用户后台（UserAdminAppService）

### 8.1 背景意图

测试反馈缺陷：**新增用户时，已被禁用的组织仍能被选择并保存。**

预期行为：

1. 禁用的组织不应被分配给用户。新增/编辑用户时若所选组织已禁用，应直接报错拦截。
2. 所有"搜索组织"的接口都应支持一个可空的"是否禁用"入参，便于前端在组织选择器中只拉取启用的组织。

> 组织的启用状态字段为 `OrganizationUnit.Enable`（`true`=启用，`false`=禁用）。本项目无 `IsDisabled` 实体字段，禁用即 `Enable == false`。

### 8.2 核心逻辑变更

**用户分配组织时校验禁用状态：**

`UserManager.AddToOrganizationUnitsDataPermissionAsync(long userId, long organizationId)` 中新增校验。该方法是新增/编辑用户统一的组织绑定入口：

- 组织不存在 → 抛 `所选组织不存在。`
- 组织已禁用（`Enable == false`）→ 抛 `所选组织已被禁用，无法分配用户。`

**组织搜索接口统一改用 DTO 承载查询条件：**

所有组织搜索接口的入参统一使用 DTO（不再使用散列的 `bool?` 参数），并把过滤条件（`IsCompany` + `IsDisabled`）都补全。

过滤语义：`IsDisabled` 为 `null` 查全部、`true` 只查禁用（`Enable==false`）、`false` 只查启用（`Enable==true`）；`IsCompany` 为 `null` 查全部、`true` 仅公司、`false` 仅部门。

DTO（位于 `Organizations/OrganizationUnitQueryDto.cs`）：

- `OrganizationUnitQueryDto`：`IsCompany`(bool?)、`IsDisabled`(bool?)
- `OrganizationUnitCurrentQueryDto : EntityDto<long>`：`Id`(long，用户id)、`IsCompany`(bool?)、`IsDisabled`(bool?)

| 接口（Async）                         | 入参 DTO                          |
| :------------------------------------ | :-------------------------------- |
| `GetOrganizationUnitsAsync`           | `OrganizationUnitQueryDto`        |
| `GetOrganizationUnitsWithLevelAsync`  | `OrganizationUnitQueryDto`        |
| `GetCurrentOrganizationUnitsAsync`    | `OrganizationUnitCurrentQueryDto` |
| `GetAllOrganizationUnitsAsync`        | `OrganizationUnitCurrentQueryDto` |
| `GetCurrentOrganizationUnitUserAsync` | `OrganizationUnitCurrentQueryDto` |
| `GetAllOrganizationUnitUserAsync`     | `OrganizationUnitQueryDto`        |
| `GetOrganizationUnitsUserTreeAsync`   | `OrganizationUnitQueryDto`        |
| `GetOrganizationUnitTreeAsync`        | `OrganizationUnitQueryDto`        |
| `GetHandleCCTreeAsync`                | `OrganizationUnitQueryDto`        |
| `GetOrganizationUnitsTreeAsync`       | `OrganizationUnitQueryDto`        |

> 带用户id的接口（`GetCurrent...`/`GetAll...`）改用 `OrganizationUnitCurrentQueryDto`，其继承 `EntityDto<long>`，`Id` 字段名保持不变，前端原有 `{ id }` 入参兼容。
>
> `GetOrganizationUnitAsync`（按 id 取单个组织详情）属于"详情"而非"搜索"，未加查询条件。

### 8.3 避坑指南

- **过滤方向易反**：`IsDisabled` 是"是否禁用"，映射到实体的 `Enable` 时需取反。前端组织选择器若只想要可用组织，传 `isDisabled=false`。
- **入参统一为 DTO**：所有组织搜索接口不再使用散列 `bool?` 参数，统一用 DTO 承载。带用户id 的接口用 `OrganizationUnitCurrentQueryDto : EntityDto<long>`，保持 `Id` 字段名以兼容旧调用。
- **`WhereIf` 命名空间区分**：
  - `IQueryable`（`GetAll()...`）的 `WhereIf` 来自 `Abp.Linq.Extensions`；
  - `IEnumerable/List`（`GetAllListAsync()` 返回值）的 `WhereIf` 来自 `Abp.Collections.Extensions`。
- **树形接口过滤后健壮性**：4 个树接口过滤后结果可能为空或出现"父节点被过滤、子节点保留"的情况。已补充防御：结果为空提前返回；挂载子节点时 `FindIndex` 为 -1 则跳过，避免数组越界崩溃。
- **校验集中在 UserManager**：组织禁用校验放在 `AddToOrganizationUnitsDataPermissionAsync`，新增、编辑用户两条路径都会被拦截，无需在每个 AppService 方法里重复写。

- **`OrganizationUnitSimpleDto` 命名空间**：该 DTO 在 `CsprojBuilder` 根命名空间，`Organizations` 子命名空间可直接使用，无需额外 `using`。

> 模块：组织机构（OrganizationUnitAppService）

- 新增 `EnsureUserOwnsCompanyAsync`：校验录入的公司存在、是公司、且在数据所属用户拥有的公司范围内。

### 11.3 避坑指南

- **按当前租户查询**：两个新方法均**不禁用**多租户过滤（曾一度禁用，已回退）。
- **扁平返回**：`GetAllOrganizationTreesAsync` 不再返回嵌套子树，只按需返回节点与其 `AllUsers`；取「某组织下所有用户」用 `节点.AllUsers`。
- **缓存失效依赖实体事件**：涉及组织/用户组织关系/用户的写入需经实体事件，才能触发缓存清理。

### 11.4 OrganizationUnitAppService 接口的多组织改造（2026-07-22）

因「一个用户可属于多个组织」，以下接口从单组织假设改为多组织：

| 接口 | 变更 |
| :-- | :-- |
| `GetUserPagingListForOuAsync` | 入参新增 `organizationUnitId`；由「返回无任何组织的用户」改为「返回**不属于该组织及其全部父级(祖先)组织**的用户」（`organizationUnitId` 为空则返回全部）。 |

## 十二、变更记录（2026-08-18）：成员数把已删除用户算进去了

> 模块：组织机构（`OrganizationUnitAppService.BuildOrganizationUnitMemberCountQuery`）影响接口：`GetOrganizationUnitsAsync`（组织列表/左侧树）、`GetOrganizationUnitAsync`（组织详情「成员数」）

### 12.1 背景意图

现场反馈：销售部左侧树和详情页都显示 **14 人**，但「成员列表」只有 **2 人**。

查库确认成员列表是对的。`freight2` 库里 `Sys_Users` 共 61 个用户，其中 **42 个已被软删除**（`IsDeleted = 1`），而 `Sys_UserOrganizationUnits` 里有 **48 行关联记录仍指向这些已删除用户**，销售部占其中 12 行。14 = 2 个在职 + 12 个已删除。

各部门当时的显示值与真实值：

| 部门           | 修复前显示 | 真实在职 |
| :------------- | :--------- | :------- |
| 空运操作部     | 16         | 4        |
| 销售部         | 14         | 2        |
| 管理部         | 5          | 3        |
| 财务部         | 6          | 2        |
| 航线部         | 5          | 2        |
| 鉴定部         | 4          | 2        |
| 海运操作部     | 3          | 3        |
| 公司（含下级） | 54         | 19       |

### 12.2 根本原因

两个接口取数口径不一致：

- **成员数**：`BuildOrganizationUnitMemberCountQuery` 只对组织表和 `UserOrganizationUnit` 做 left join 后 `g.Count()`，**全程不碰用户表**，数的是关联表行数。
- **成员列表**：`GetOrganizationUnitUserPagingListAsync` 内连了 `UserManager.Users`。

`UserOrganizationUnit` 只继承 `CreationAuditedEntity<long>` + `IMayHaveTenant`，**不是 `ISoftDelete`**，所以关联表没有软删除过滤；而 `UserManager.Users` 自带 `IsDeleted = 0` 和租户过滤。于是「用户已删、关联行还在」的脏行只会污染计数，不会出现在列表里。

同时 `g.Count()` 数的是行数而非人数：库里确实存在同一用户对同一组织的重复关联行（空运操作部 16 行关联只对应 15 个人，已删除的「操作部」里邵乾一人占 3 行），也会把人数算多。

### 12.3 核心逻辑变更

`BuildOrganizationUnitMemberCountQuery` 改为与成员列表同一口径，**不改任何数据**：

- 关联行**内连** `UserManager.Users`，让 `IsDeleted`/租户过滤自动生效，已删除用户的关联行不再计数；
- 按 `(OrganizationUnitId, UserId)` `Distinct()` 后再分组计数，重复关联行只算一个人；
- 顺带把原来「组织表 + 关联表两张表整表 `ToList()` 后内存 group join」改为一次带 join 的 `Distinct()` 查询 + 字典查找。

`GetOrganizationUnitsAsync`、`GetOrganizationUnitAsync`、创建/更新/移动组织的返回值都走这个方法，一并生效。

### 12.4 避坑指南

> [!IMPORTANT]
>
> 1. **脏数据没清，只是不再计入**：那 48 行指向已删除用户的关联行仍在库里。任何**直接读 `UserOrganizationUnit` 而不 join 用户表**的地方都还会踩坑——`GetOrganizationUnitUserListAsync`、`GetOrganizationUnitsUserTreeAsync`、`GetOrganizationUnitTreeAsync`、`GetHandleCCTreeAsync` 都是直接读关联行再用 `FindNickNameById` 取名字，遇到已删除用户会返回**人名为空的幽灵成员**。这些接口本次未改，后续要改请一律按本节口径 join 用户表。
> 2. **计数必须按 `UserId` 去重**：库里真实存在重复关联行，只 `Count()` 行数就会把一个人算成多个。
> 3. **判断标准**：`memberCount` 必须恒等于成员列表 `GetOrganizationUnitUserPagingListAsync` 的 `totalCount`，对不上就是又有人绕过用户表直接数关联行了。
> 4. **删用户为什么会留下关联行**：ABP 自带的 `UserOrganizationUnitRemover` 本应在用户删除事件里清关联行，但库里这 48 行说明历史上有删除路径没触发该事件（直接改库或早期数据）。若后续发现新增脏行，要去查删除用户的调用链是否走了实体事件。

## 十五、变更记录（2026-09-29）：公司下拉按数据权限模块取规则

> 模块：组织机构（`OrganizationUnitAppService.GetMyPermissionCompaniesAsync`）关联文档：《数据权限模块总逻辑文档》

数据权限规则加了可空的模块列（为空是通用规则），公司下拉随之加可选参数 `module`：传了按该模块生效的规则算，不传只看通用规则。接口签名 `GetMyPermissionCompaniesAsync(DataPermissionModule? module = null)`，接口 `IOrganizationUnitAppService` 同步修改。

规则改为走基类 `GetEffectiveDataPermissionsAsync(module, ManageType.Get)`，从规则缓存取，公司的换算算法（全部返回所有公司；本人所属公司；部分向上追溯所属公司；多人取其所属公司）不变。

**行为变化：** 原实现从 `GetCurrentUserAsync()` 返回的用户上读 `user.Roles`，该值恒为空，角色上配的规则在这里从未生效；现在角色规则会生效，配了角色规则的人下拉里的公司可能变多。「排除人员」规则不参与公司计算。
