# 1. 背景意图

小程序端此前只有 `WxOpenAuthenticate` / `WxOpenAuthenticateTenant` 两个登录接口，走的是微信**旧版**流程：前端调 `wx.login` 拿 code，后端 `jscode2session` 换出 `session_key`，再用 `session_key` 解密前端传来的 `encryptedData` + `iv`。这套流程有三个现实问题：

1. **拿不到手机号**。旧流程解出来的只有昵称、头像、地区，没有手机号，登录只能靠 openid/unionid，意味着用户必须先在别处完成绑定才能登录，第一次进小程序是登不进来的。
2. **`session_key` 存在内存里，多实例部署会丢**。Senparc 的 `SessionContainer` 是进程内缓存，应用池回收或多实例负载均衡时，解密那一步会随机失败。
3. **依赖 Senparc 的静态初始化**。`Config.SenparcWeixinSetting` 要在 Startup 里调用 `UseSenparcWeixin` 之后才有值，而本项目只做了 `AddSenparcWeixinServices`，没有那一步，`_wxOpenAppId` 实际取不到值。

本次新增的两个接口改用微信**新版**流程（基础库 2.21.2+）：手机号由微信验证后直接返回，不再需要 `session_key`，也完全不经过 Senparc，只依赖 appsettings + HttpClient。

同时解决一个成本问题：手机号快速验证组件是**按次收费**的（0.03 元/次），扣费发生在前端拿到 `bindgetphonenumber` 的 success 回调时。因此配套做了静默登录——首次用手机号登录时把 openid 绑到账号上，之后每次启动小程序只要 `wx.login` 就能登进来，把绝大部分收费调用省掉。

# 2. 核心逻辑

## 2.1 两个接口的分工

| 接口 | 何时调 | 是否产生费用 |
| :-- | :-- | :-- |
| `WxOpenSilentAuthenticate` | 小程序启动时**先调它** | 否 |
| `WxOpenPhoneAuthenticate` | 静默登录返回 `shouldBindingUser=true` 时才调 | 是（0.03 元/次） |

前端标准流程：启动 → `wx.login` 拿 code → 调静默登录 → 拿到 token 就直接进首页；返回 `shouldBindingUser=true` 才展示"手机号一键登录"按钮，用户点了之后再调手机号登录接口。

## 2.2 手机号登录链路

1. 前端 `<button open-type="getPhoneNumber" bindgetphonenumber="...">`，回调里取 `e.detail.code`。
2. 后端拿 `code` 调 `POST /wxa/business/getuserphonenumber?access_token=xxx` 换手机号，并校验返回的 `watermark.appid` 与本小程序一致。
3. 用 `purePhoneNumber`（不带区号）在租户 1 下查 `Sys_Users.PhoneNumber`。
4. 查到就签发 JWT；查不到直接报"尚未开通账号"，**不做自动注册**（账号由管理员统一创建）。
5. 前端若同时传了 `loginCode`（`wx.login` 的 code），登录成功后把 openid/unionid 写入 `Sys_UserLogins`。

## 2.3 静默登录链路

1. 前端 `wx.login` 拿 code 传过来。
2. 后端 `jscode2session` 换出 openid。
3. 用 `UserLoginInfo(WeappOpenId, openid)` 调 `LogInManager.LoginAsync`，命中 `Sys_UserLogins` 即登录成功。
4. 没命中返回 `shouldBindingUser=true`，**不抛异常**——这是用户第一次进来的正常状态。

## 2.4 微信凭据表与定时刷新

`App_WeixinAccessTokens` 是**微信应用的通用凭据表**，不是小程序专用表。小程序、订阅号、服务号各占一行，用 `AppType` 区分。这三类的取号方式完全相同（都是 `api.weixin.qq.com` 的 `/cgi-bin/stable_token`，只是 AppId/AppSecret 不同），所以由同一个定时任务统一刷新。

关键变化：**AppId/AppSecret 不再放 appsettings，改为人工录入到这张表**。业务代码要用哪个号，就按 `AppType` 查表，加一个公众号只是插一行数据，不用改配置也不用重启。

刷新策略：

- **定时任务** `WeixinAccessTokenWorker`，周期 100 分钟（微信给的有效期是 120 分钟，留 20 分钟余量，够扛过一两次取号失败的重试）。
- **进程启动立即取一次**（`AbpAsyncTimer.RunOnStart = true`）。应用池回收、发版重启之后，第一个访问登录接口的用户不用替所有人承担一次取号的耗时和失败风险。
- **不做内存缓存**。令牌在微信侧本来就是全局唯一的一份，库里那条就是唯一事实；内存缓存只会让多实例各持一份可能已被顶掉的旧令牌，排查时还看不出来谁在用哪个。每次多一次主键索引上的单行查询，代价可以忽略。
- **单个应用失败不连累其它应用**：`RefreshAllAsync` 逐行取号，异常吞掉并写入该行的 `LastError`。定时任务在后台跑，不记下来就没人知道它一直在失败。

取号用的是稳定版接口 `/cgi-bin/stable_token` 而不是老的 `/cgi-bin/token`，且 `force_refresh` 恒为 `false`：微信会返回**当前已经生效的**那个令牌，不会重新下发、也就不会把其它实例正在用的令牌顶掉。

`GetTokenAsync` 里保留了"库里没有或已过期就现取一次"的兜底——定时任务还没跑到或连续失败时，不至于让整个登录瘫掉。这不是缓存，是自愈。

落库一律走**独立的非事务工作单元**（`RequiresNew` + `IsTransactional=false`）：取号一旦发出去就在微信侧生效了，这个既成事实必须记下来，不能跟着外层登录事务一起回滚，否则登录失败一次就白取一次号。

## 3.4 数据库变更

新增表 `App_WeixinAccessTokens`，主键 `Guid`：

| 列 | 类型 | 可空 | 说明 |
| :-- | :-- | :-- | :-- |
| `Id` | uniqueidentifier | 否 | 主键 |

| `AppName` | nvarchar(128) | 是 | 仅供人工识别是哪个号，不参与逻辑 |
| `AppId` | nvarchar(64) | 否 | 微信应用 AppId，**唯一索引** |
| `AppSecret` | nvarchar(128) | 否 | 微信应用 AppSecret |
| `IsActive` | bit | 否 | 停用后不再取号，业务侧也查不到 |
| `Token` | nvarchar(2048) | 是 | 令牌值，人工刚录入凭据时为空 |
| `ExpireTime` | datetime2 | 是 | 过期时间（已提前 5 分钟留余量） |
| `FetchTime` | datetime2 | 是 | 最近一次取号时间 |
| `LastError` | nvarchar(512) | 是 | 最近一次取号失败原因，成功时清空 |

复合索引 `(AppType, IsActive)`，用于按类型取号。

> 迁移文件未生成，需自行执行 `dotnet ef migrations add`。

**上线必须先插数据**：AppId/AppSecret 不再走 appsettings，表里没有小程序那一行的话，登录接口会直接报"系统未配置小程序的微信应用"。

```sql
INSERT INTO App_WeixinAccessTokens (Id, AppType, AppName, AppId, AppSecret, IsActive)
VALUES (NEWID(), 0, N'货代小程序', N'你的小程序AppId', N'你的小程序AppSecret', 1);
```

openid 绑定关系复用 ABP 现有的 `Sys_UserLogins` 表（`LoginProvider` = `WeappOpenId` / `WeChatUnionId`），未新建表。

# 4. 避坑指南

> [!IMPORTANT] **两个 code 不是一回事，传混了必然失败** `getPhoneNumber` 回调里的 `code` 和 `wx.login` 返回的 `code` 是两套独立的令牌，微信不接受交叉使用。手机号登录接口的 `code` 字段收的是前者，`loginCode` 字段收的是后者。

> [!IMPORTANT] **前端不要一上来就调手机号登录** 扣费节点是前端拿到 `bindgetphonenumber` 的 success 回调，不是后端调接口。哪怕拿到 code 后什么都不做，这 0.03 元也已经扣掉了。必须先走静默登录，失败了才引导用户点授权按钮。

> [!IMPORTANT] **凭据表是配置源，上线前必须先插数据** AppId/AppSecret 已经从 appsettings 挪到 `App_WeixinAccessTokens`。忘了插那一行的话，登录和取号会直接报"系统未配置小程序的微信应用"。换密钥也是改这张表，不用改配置、不用重启。

> [!IMPORTANT] **同一类型有多行时只取第一条** 按 `AppType` 查询时用的是 `OrderBy(AppId).FirstOrDefault()`。如果哪天真的要同时接两个小程序，这套按类型取号的模型就不够用了，得改成按业务显式指定 AppId。

> [!IMPORTANT] **改密钥后旧令牌立刻作废，但库里那条按时间算还没到期** 微信后台重置 AppSecret 后，原有令牌立即失效，表现为持续报 40001。 `WxOpenApiClient` 收到 40001/40014/42001 会自动 `RefreshAsync` 重取一次再试，但更快的办法是改完密钥直接重启（`RunOnStart` 会立即取一次新号）。

> [!IMPORTANT] **定时任务失败是静默的，要看 `LastError` 列** Worker 在后台跑，取号失败（密钥填错、IP 没进白名单）不会有任何界面提示。怀疑令牌有问题时，先查 `App_WeixinAccessTokens` 的 `LastError` 和 `FetchTime`。

> [!IMPORTANT] **换人后必须清掉旧的 openid 绑定** 员工离职、手机号转给同事时，同一个 openid 可能已经绑在别人名下。`BindLoginProviderAsync` 会先删掉该 `(LoginProvider, ProviderKey)` 下属于其他用户的记录再绑新的，否则静默登录会顺着旧记录登进上一个人的账号。

> [!IMPORTANT] **租户号写死在服务端，不接受前端传** 小程序端没有输入租户编码的地方。租户号取自 `WxOpenConfig.TenantId`（恒为 1），不从入参读，避免调用方传个租户 id 就能登到别的租户去。

> [!IMPORTANT] **服务器出口 IP 要加进小程序后台的白名单** 若小程序后台开启了 IP 白名单，取 `access_token` 会直接失败。换服务器、加实例时都要同步更新白名单。
