# 1. 业务背景与数据结构

## 1.1 业务定义

海运进口（SeaImport）用于登记一票从境外港口运抵国内港口的整箱海运货物，覆盖接单、换单、提货、报关、转站的全过程单据信息，并承载该票的费用归属。

一票海运进口 = 一条业务主表记录 + 一条海运进口扩展记录 + 若干集装箱、商品、关联人员、费用。

## 1.2 两层表结构

系统的业务数据采用「**业务主表 + 业务类型扩展表**」两层结构：

- **业务主表 `App_TransportOrders`**：多种业务类型共用的容器，存放委托单位、收发通、货物描述、日期、危险品、冻柜、费用锁定等通用信息，用 `BizType` 字段区分业务类型（海运进口固定为 `1`）。
- **扩展表 `App_SeaImports`**：只存海运进口独有的信息，**与业务主表共享同一个主键**，即 `App_SeaImports.Id == App_TransportOrders.Id`，一对一。

写入次序固定：**先插业务主表拿到 Id，再用同一个 Id 插扩展表**。不存在「有扩展表记录但没有业务主表记录」的数据。

这个两层结构对使用者的直接影响：**同一票的字段分散在两层**。界面上并排的两个输入框，可能一个属于扩展表、一个属于业务主表。第 2 章的表结构和第 8 章的界面分区都标注了每个字段属于哪一层。

## 1.3 子表挂载关系

集装箱、商品、关联人员、改单、费用五张子表全部挂在**业务主表 Id** 上，与业务类型无关：

```
App_TransportOrders (Id)
├── App_SeaImports          (Id 相同，一对一)
├── App_OrderCtns           (TransportOrderId，一对多，集装箱)
├── App_OrderCodeGoodss     (TransportOrderId，一对多，商品/品名)
├── App_OrderUsers          (TransportOrderId，一对多，关联人员)
├── App_ChangeOrders        (TransportOrderId，一对多，改单)
└── App_OrderFees           (TransportOrderId，一对多，费用)
```

附件不是子表，走通用附件模块，通过「模块编码 + 归属键」关联（见 2.9）。

**集装箱是个例外，需要特别记住**：集装箱表虽然挂在业务主表上，但海运进口给它加了型号、规格、净重三列，这三列只有海运进口用。因此在海运进口的功能里，集装箱被当作**海运进口自己这一层**的数据来处理，而不是业务主表那一层。这一点在第 8 章和第 9 章还会反复提到。

## 1.4 「到港日期」的准确含义

海运进口界面上的「**到港日期**」，在数据库里对应的是业务主表的 `ETD` 字段。

- 它在系统中的定位是「这一票的业务日期」，会计期间、应结日期、转站日期、箱使日期全部以它为基准推算。
- 数据库里另有 `ETA`（预抵日期）字段，**海运进口界面不展示、不使用**。
- 测试提缺陷时请写清「到港日期（ETD）」，避免和 `ETA` 混淆。

## 1.5 本期范围

**本期要做**：海运进口的新增、编辑、详情、列表、分组统计、复制、删除、重新生成委托编号、附件的查询/新增/删除；业务主表的详情与删除按业务类型分流；基础资料删除时的引用校验。

**本期不做**（这些能力在海运进口界面上不出现）：服务项目与服务项任务、分单、派车、单据打印、费用模板自动生成、业务联系单转进口、外部对接（云当运踪、洋歌、单证识别 TextIn）、下游模块（业务费用列表分组、客户对账、开票申请、发票开出、付费申请）针对进口的适配、根据船名航次自动带出日期。

费用子表本身不做任何改造，现有费用模块按业务主表 Id 工作，对进口票天然可用。

# 2. 表结构

**通用约定**（适用于本章所有表）：

- 所有表都是**软删除**：删除只是把 `IsDeleted` 置为 `true`，所有查询自动过滤掉已删除数据。软删除**不会级联**到子表，需要删除的子表由后端逐条显式删除。
- `decimal` 未特殊说明的一律为 `decimal(18,2)`，即整数加小数共 18 位、小数 2 位。录入的小数会自动四舍五入到 2 位再入库。
- **重量体积类字段是 `decimal(20,4)`**（整数 16 位、小数 4 位）：海运进口层的净重合计 `TotalNetWeight`，业务主表的毛重 `Kgs` / 体积 `Cbm`，集装箱的毛重 `GrossWeight` / 皮重 `TareWeight` / 净重 `NetWeight` / 体积 `Volume`。这些列在表里逐个标注了。集装箱的超长 / 超宽 / 超高仍是 `decimal(18,2)`。
- `datetime` 对应 SQL Server 的 `datetime2`。
- 字符串长度均指**字符数**，超长直接报错，不截断。录入内容的首尾空格会被自动去掉，**长度是按去空格之后算的**。
- 「可空」列的「否」表示数据库非空；未录入时按该行说明的默认值处理。

## 2.7 App_OrderFees（费用子表）

海运进口**不新增也不修改任何费用逻辑**：费用的录入、审批、结算、开票全部由现有费用模块处理。海运进口只做三件与费用相关的事：

1. 列表和详情**只读展示**该票的费用清单与两个方向的费用状态汇总值（见 6.6）；费用清单按 `sortId` 升序、相同再按创建时间升序；
2. 复制时按用户选择决定是否把费用一起复制（见 7.5）；
3. 删除时校验该票不能还有费用（见 7.6）。

海运进口展示的费用信息包含：收付类型、费用状态、结算状态、开票状态、费用代码及名称、行业类别、结算对象及简称、客户对账 id、币别及名称、汇率、含税与不含税单价、含税与不含税金额、单位、数量、税率、已开票金额、发票申请金额、未开票金额、已结算金额、是否禁开发票、是否机密、录入方式、会计期间、备注、创建人及昵称、所属改单 id、排序 id。

其中三个金额是**海运进口查询时现场算出来的**，不是费用记录上的字段：

| 值           | 口径                                                       |
| :----------- | :--------------------------------------------------------- |
| 已开票金额   | 该费用在**已开票**状态的开票申请中的申请金额合计；没有则 0 |
| 发票申请金额 | 该费用在**所有状态**的开票申请中的申请金额合计；没有则 0   |
| 未开票金额   | 含税金额 − 已开票金额，**超额开票时会是负数**              |

> 海运进口展示的费用是**只读概览**，部分费用字段（组织、各类编码、本次结算金额、申请付款金额、未结算金额、对账单对象、审批任务明细等）在这里不填充。需要完整费用数据时请使用业务费用模块自己的功能。费用清单里每条还有一个「组合费用状态」属性，海运进口不填充它，**票级的应收/应付组合状态请看 6.6 的两个汇总值**。

## 2.9 附件

海运进口的附件通过通用附件模块管理，本模块只负责传递归属关系与分组结构。

- **模块编码**：`160070`。所有海运进口附件都用这个编码标记。
- **归属键**：海运进口 Id（与业务主表 Id 相同）。
- **分组键**：附件明细类型（例如托书、提单、发票），是已有的基础资料。**分组的展示规则由前端控制，后端不参与分组语义**，只按类型原样分组返回。
- 一个附件可以同时挂在多票上；**从某一票移除附件只解除这一票的关联**，既不删除文件本身，也不影响其它票。
- 附件关联不随主表软删除级联，删除票据时后端显式清理（见 7.6）。

**附件的组织形式**：每票的附件按附件明细类型分成若干组，组内按顺序号升序；组之间先按类型的排序号升序，没有类型的那一组排在最后。

**每个附件展示的信息**：文件名、文件大小、附件类型（图片/视频/Flash/音乐/文档/压缩包/其他，由扩展名推断）、下载直连地址、客户是否可见、顺序号、上传时间、上传人。

**附件的两种维护方式**（效果相同，选其一即可）：

1. 在保存单据（新增/编辑）时连同附件分组一起提交；
2. 单独使用附件的新增、删除功能。

# 4. 权限

海运进口的权限分三层，三层是叠加关系：**能不能用这个功能**（功能权限）→ **能看到哪些票**（数据权限）→ **票上能看到哪些字段**（字段级权限）。

## 4.1 功能权限点

| 权限标识 | 名称 | 覆盖的操作 |
| :-- | :-- | :-- |
| `Admin.SeaImport` | 海运进口（父级） | 菜单可见性 |
| `Admin.SeaImport.Add` | 添加 | 新增、复制 |
| `Admin.SeaImport.Get` | 查看 | 列表、分组统计、详情、查询附件 |
| `Admin.SeaImport.Edit` | 编辑 | 编辑、重新生成委托编号、新增附件、删除附件 |
| `Admin.SeaImport.Delete` | 删除 | 删除 |

四个权限点均为**租户级**。所有操作都要求已登录。

> 注意「复制」归在添加权限下，「附件的增删」归在编辑权限下，「重新生成委托编号」也归在编辑权限下。给角色配权限时容易漏掉这三处。

## 4.2 数据权限（行级）

列表、分组统计在功能权限之外，还会叠加行级数据权限过滤。规则如下：

1. 先解析当前用户在「查询」操作类型下的数据权限配置（用户自身的配置 + 其所有角色的配置）。
2. 若命中「全部数据」权限，不做任何过滤，能看到全部票。
3. 否则解析出两个集合：
   - **可见用户集合**：配置里指定的用户，**再加上自己**。
   - **可见组织集合**：配置里指定的组织、以及「我的部门」「我的公司」解析出的组织，每个组织**都展开为它自己及其全部下级组织**。
4. 一票只要满足下列任一条，就可见：
   - 该票的**所属人**在可见用户集合内；
   - 该票的**创建人**在可见用户集合内；
   - 该票的**所属组织**在可见组织集合内；
   - 该票的**业务关联人员**中，存在一条记录，其用户在可见用户集合内且属性属于：销售、商务、操作、客服、单证、海外客服、航线。

**列表的总条数是过滤之后的结果**，不同账号用同样的筛选条件，看到的总数可能不同。

### 按 Id 操作的接口同样做行级过滤（2026-08-19 起）

详情、编辑、删除、重新生成委托编号这四个按 Id 定位单票的接口，**此前不做任何行级过滤**，只要知道 Id 就能查看甚至改删任意一票。现已统一改为：先过行级数据权限、再过表级权限，两层都通过才继续。

| 接口                           | 解析数据权限时用的操作类型 |
| :----------------------------- | :------------------------- |
| 详情                           | 查询                       |
| 编辑 / 删除 / 重新生成委托编号 | **编辑**                   |

判定口径与上面第 1～4 条完全一致，只是解析配置时的操作类型不同。任一层不通过都直接报错，三种情况提示语不同，便于区分是数据问题还是权限问题：

| 情况                     | 提示语                                            |
| :----------------------- | :------------------------------------------------ |
| 这一票根本不存在         | 各接口原有的「不存在」提示                        |
| 票在，但没有行级数据权限 | 「没有这条数据的数据权限,不能查看 / 编辑 / 删除」 |
| 行级过了，被表级权限挡掉 | 「没有这条数据的表级权限,不能查看 / 编辑 / 删除」 |

> [!IMPORTANT] 数据权限的操作类型只有「查询」和「编辑」两种，**没有删除**，所以删除也按「编辑」判定。
>
> 「编辑」这个操作类型此前**从未被任何代码读取过**，本次是它第一次真正生效。这不是上线卡点，上线后由客服按需给用户和角色配置编辑口径的数据权限即可。
>
> 配置到位之前，用户只能改动「自己是所属人 / 创建人 / 干系人」的票，列表里其余行的「是否可编辑」都是否。有人反馈改不了单、编辑按钮是灰的，先查这里。

## 4.3 字段级权限

列表、分组统计的查询会额外叠加「表格字段级权限」过滤，模块标识为 `SeaImport`。

被屏蔽的字段分两层，独立配置，可能出现「进口层能看船名、业务层看不到主提单号」这种组合：

| 层级             | 作用范围             |
| :--------------- | :------------------- |
| 海运进口自身字段 | 海运进口这一层的字段 |
| 业务主表字段     | 业务主表那一层的字段 |

**编辑时有配套保护**：保存前，当前用户无权查看的字段会被后端用数据库原值回填，避免用户因为看不到该字段而没填、导致保存时把库里的值抹掉。这个回填对海运进口扩展表和业务主表分别执行一次。

# 5. 通用业务规则

## 5.1 提示语与错误

模块内所有业务校验失败都会返回一句用户可读的中文提示，界面直接展示即可。**本文各处引号内的文字就是最终展示给用户的原文，一字不差**，测试可以直接做字符串相等断言。

非预期的系统异常（数据库超时、空引用等）也会以同样的方式返回一句话。因此**看到不在本文档清单里的提示语，就是系统异常，应当提缺陷**，而不是当成业务规则。

## 5.2 列表的分页与排序口径

- 默认每页 10 条，第 1 页；每页条数上限 100000，页码从 1 开始，超出范围会被拦下。
- 默认按**创建时间倒序**。
- 支持多字段排序，前一个字段相同时用后一个字段续排。
- 支持按关联对象的字段排序，例如按委托单位名称排序。
- 排序字段应固定为列头绑定的白名单，不要把用户输入的任意文本当排序字段用。

## 5.3 筛选的匹配语义

| 匹配方式 | 行为 | 注意 |
| :-- | :-- | :-- |
| 模糊 | 包含匹配 | **不区分大小写**；该字段为空的记录**不会**被匹配到 |
| 精确 | 完全相等 |  |
| 区间 | 闭区间，两端可以只填一端 |  |
| 空白条件 | 不填、空字符串、全空白 | 一律视为**不筛选** |
| 多个条件之间 | 一律「并且」 | 唯一的「或者」是关键字搜索内部的多个字段之间 |

**关键字搜索**覆盖 9 个字段：船名、航次、发票号、批次号、外部备注、主提单号、订舱编号、合同号、委托编号。

## 5.4 「未填写」类筛选开关

船名、船公司、起运港、目的港、原产国、码头这六个字段，除了按值筛选，还各自提供一个「未填写」开关，用于筛出该字段为空的票。

规则：

- 只选值：筛选等于该值的票（船名是模糊匹配）；
- 只开「未填写」：筛出该字段为空的票；
- **两者同时使用**：直接报错，不做兜底。报错文案是「船公司筛选：未填写与指定id不可同时传入」，起运港、目的港、原产国、码头同格式，船名是「船名筛选：未填写与指定船名不可同时传入」；
- 「未填写」关掉：等同于不筛，**不会**反向筛出「已填写」的票；
- 两者都不用：不按该字段过滤。

这个校验在所有筛选逻辑最前面执行，一旦冲突，其它条件都不会生效。

## 5.5 日期处理

- 业务主表的到港日期、实际开船日期、预抵日期在保存时**只保留日期部分**，时分秒一律归零。
- 海运进口的换单、提货、报关、转站、箱使日期**原样保存，不截断**；界面如果带上了时分秒，回看时也会带回来。建议界面统一只录日期。
- 会计期间由后端算成「所在月 1 号」。
- 所有日期区间筛选都是**闭区间**。由于进口层日期不截断时分秒，筛选「止」端时建议取当天的最后一刻，否则当天带时分秒的数据会被漏掉。
- 系统不做任何时区换算，录入什么本地时间就存什么。

# 6. 计算与派生规则

## 6.1 前端计算的四个值（后端一律只存储）

以下四个值全部由**前端计算并允许用户手工覆盖**，后端接收什么存什么，**不重算、不校验、不覆盖**。

| 值 | 所在层 | 计算公式 | 边界处理 |
| :-- | :-- | :-- | :-- |
| 集装箱净重 | 集装箱子表 | 毛重 − 皮重 | 毛重或皮重任一为空 → 留空 |
| 净重合计 | 海运进口层 | 各集装箱净重求和 | 由用户点「计算」按钮触发；也允许直接手填。**手填之后再改箱子，不会自动覆盖手填值** |
| 转站日期 | 海运进口层 | 到港日期 + 9 天 | 9 是固定常量，不可配置；到港日期为空 → 留空 |
| 箱使日期 | 海运进口层 | 到港日期 + 免箱期 − 1 天 | 到港日期或免箱期任一为空 → 留空。**到港当天计为免箱期第 1 天** |

> [!IMPORTANT] **这四个值不会因为基准值变化而自动重算。** 用户改了到港日期、免箱期、毛重或皮重后，如果没有重新触发前端计算，保存下去的仍是旧值，后端不会纠正。这是既定行为，测试需覆盖并按此判定。

## 6.2 会计期间与应结日期（后端计算）

新增、复制、编辑时后端都会重新计算这两个值，**界面上填什么都会被覆盖**，因此这两项在界面上应做成只读。

**基准时间**：到港日期；到港日期为空时取当前时间。

**会计期间** = 基准时间所在月的 1 号（年月保留，日固定为 1，时分秒为 0）。

**应结日期**按委托单位的账期规则推算：

1. 查该委托单位下**当前生效**的账期规则。长期有效的直接算生效；否则生效时间不填=不限制起始、失效时间不填=不限制截止，填了的那一端才跟当前时间比。
2. 一条都没有 → 应结日期 = 基准时间的日期部分。
3. 有规则时，按下列四个条件筛出**第一条**全部匹配的规则（规则里某个条件没配就视为不限制）：
   - 业务类型：规则没配业务类型，或包含海运进口；
   - 销售：规则没配销售，或规则销售与本票销售有交集；
   - 组织：规则没配组织，或规则组织与本票所属组织及其下级组织有交集；
   - 业务来源：规则没配业务来源，或规则业务来源等于本票的业务来源。
4. 没筛出规则 → 应结日期 = 基准时间的日期部分。筛出的规则是**票结** → 应结日期 = 基准时间的日期部分；规则填了 `addDays` 则再往后加这些天，不填不加。
5. 筛出的规则是**月结** → 应结日期 = 基准时间往后推 N 个月（N 取规则的月数，未配置按 1）之后，取该月的第 D 天（D 取规则的结算日，未配置按 1，大于 31 按 31，小于 1 按 1）。
6. 筛出的规则是**约定天数** → 应结日期 = 基准时间 + 规则天数（未配置按 1 天）的日期部分。

> 计算过程中若发生任何异常，后端会静默跳过，应结日期保持调用前的值。

**编辑时的联动**：如果编辑导致会计期间发生变化，后端会把该票下**所有非改单费用**的会计期间同步更新为新值。**改单费用的会计期间不动**，因为改单本身就是为了独立记账。

## 6.3 委托编号

- 新增时**填了就用填的**（长度不超过 32），没填才由后端生成。
- 复制时**一律重新生成**，不沿用原票编号。
- 「重新生成委托编号」功能一律重新生成。
- 生成规则的配置键是 `SeaImport.CommissionNum`，需要管理员在「编号规则」里预先配置，**不与其它业务类型共用**。
- 规则的匹配优先级：先找绑定了当前用户的规则；找不到再按当前用户的组织路径**从最低层级向上**逐级找绑定该组织的规则；再找不到就用「既没绑组织也没绑用户」的全局规则。
- 三级都没找到 → 报「未配置生成规则」；找到规则但规则里没有自增编号项 → 报「未配置自增编号规则」。

## 6.4 船名规范化

保存船名时，如果值是空、空字符串或全是空白字符，一律存为空。目的是让按船名分组统计时不会出现「空」和「空字符串」两个重复分组。

## 6.5 组织归属校验

新增和编辑时都会执行，**复制不执行**（复制沿用源票的组织）。

规则：取本票业务关联人员中的**销售**（有且只有一个），校验所选的所属组织必须是该销售的**直属组织**。「直属」= 用户与组织的直接绑定关系，**不看父子继承**——销售挂在「上海分公司-海运部」下面时，选「上海分公司」也不通过。销售同时挂在多个组织下时，命中其中任意一个即可。

按顺序执行，任一条不满足立即报错：

| 顺序 | 条件 | 提示语（注意结尾有句号） |
| :-- | :-- | :-- |
| 1 | 所属组织没选、为空或非法 | 所属组织不能为空。 |
| 2 | 销售的用户为空 | 数据所属人不能为空，无法校验所属组织。 |
| 3 | 所选组织在组织树中不存在 | 所选组织不存在。 |
| 4 | 所选组织不是该销售的直属组织 | 所选组织不在数据所属人(本人)所属组织范围内。 |

> [!IMPORTANT] 第 1 条意味着**所属组织实际上是必填项**，尽管数据库列可空。界面必须把它做成必填。

另外，在执行本节校验之前，还会先判断销售本身是否有效，无效时报「销售不能为空」。这条与上表第 2 条的差别只在文案，实际先命中的是「销售不能为空」。

**这条规则的实际影响**：换销售时可能连带需要改所属组织。界面在切换销售之后，应重新加载该销售的直属组织列表，并清掉不在列表内的旧选择，否则用户会在保存时才撞上第 4 条报错。

## 6.6 组合费用状态的合成规则

列表和详情会展示四个费用相关的汇总值：

| 值 | 含义 |
| :-- | :-- |
| 应付费用状态最小值 | 该票所有**应付**费用的费用状态取最小值；没有应付费用时为空 |
| 应收费用状态最小值 | 该票所有**应收**费用的费用状态取最小值；没有应收费用时为空 |
| 应付组合费用状态 | 该票**应付**方向的组合状态（枚举见 3.12）；没有应付费用时为空 |
| 应收组合费用状态 | 该票**应收**方向的组合状态（枚举见 3.12）；没有应收费用时为空 |

组合状态的计算范围是该票该方向的**全部费用，包含改单费用**。计算前先查出该票所有费用中，存在**待审核**的「费用修改申请」和「费用删除申请」的费用集合。然后按下列顺序**逐条判断，命中即返回**：

1. 任意一条费用是**驳回** → `5 驳回`
2. 任意一条费用在**待审核的修改申请**集合内 → `6 申请修改`
3. 任意一条费用在**待审核的删除申请**集合内 → `7 申请删除`
4. 任意一条费用是**录入状态** → `0 录入状态`
5. 任意一条费用是**提交审核** → `1 提交审核`
6. **所有**费用都是**结算完毕** → `4 结算完毕`
7. 任意一条费用不是**未结算** → `3 部分结算`
8. 以上都不满足 → `2 审核通过`

> 顺序即优先级。只要有一条驳回，整票该方向就显示驳回，哪怕其它费用都已结算完毕。

# 7. 功能与操作逻辑

本章讲每个操作**做了什么、校验什么、按什么顺序、失败时说什么话**。参数与返回结构见《海运进口模块接口文档》。

海运进口共 9 类操作：新增、编辑、详情、列表、复制、删除、分组统计、重新生成委托编号、附件维护（查询/新增/删除）。

## 7.1 新增

**校验顺序与提示语**（命中即中断，不会一次返回多条）：

1. 没有任何输入 → 「输入信息不能为空」
2. 缺少业务主表信息 → 「业务信息不能为空」
3. 关联人员为空 → 「业务关联人员不能为空」
4. 关联人员中销售的条数**不等于 1** → 「销售有且只能有一个」。这是唯一的人员必填约束，操作、单证、客服等其它属性都可以不填
5. 委托单位不存在（含没选）→ 「委托单位不存在」
6. 字符串长度校验，超长报「{字段中文名}长度不能超过{N}个字符」：

   | 字段                                                   | 上限    |
   | :----------------------------------------------------- | :------ |
   | 委托编号                                               | 32      |
   | 主提单号 / 订舱编号 / 合同号 / 发票号                  | 各 64   |
   | 内部备注 / 收货人内容 / 发货人内容 / 通知人内容 / 备注 | 各 1024 |
   | 客户编号 / 联运单号 / 分单号                           | 各 32   |
   | 批次号                                                 | 64      |
   | 船名 / 航次                                            | 各 32   |
   | 起运港备注 / 目的港备注                                | 各 1024 |
   | 集装箱型号 / 规格                                      | 各 128  |
   | 集装箱箱号                                             | 32      |

7. 主提单号重复校验（长度通过后立刻做）：填了主提单号，且当前租户业务表已有相同号码 → 「主提单号【{号码}】已存在」。去首尾空格、忽略大小写；空值不校验；已软删除不参与。**海运出口、海运进口、空运出口共用业务表主提单号，三种业务互相也不能撞号。** 编辑时排除自身，保存自己原来的号不会拦。
8. 外键存在性校验，选了但基础资料不存在（或已被删除）时报错。**注意两种文案格式并存**：

   | 字段 | 提示语 |
   | :-- | :-- |
   | 业务主表的包装 | 包装ID:{id}不存在 |
   | 业务来源 | 业务来源不存在 |
   | 运输条款 | 运输条款不存在 |
   | 码头 | 码头不存在（只判客户存不存在，不判行业类别是不是码头） |
   | 船公司 | 船公司不存在 |
   | 起运港 | 起运港不存在 |
   | 目的港 | 目的港不存在 |
   | 原产国 | 原产国不存在 |
   | 车队 / 报关行 / 仓库 / 保险公司 / 收货人 / 发货人 / 通知人 | {字段中文名}不存在，例如「车队不存在」 |

   没选的外键跳过校验，不报错。

9. 商品子表逐条校验：商品没选 → 「商品信息(品名)ID不能为空」；商品不存在 → 「商品信息(品名)ID:{id}不存在」
10. 集装箱逐条校验（先校验长度，再校验外键）：箱型没选 → 「箱型ID不能为空」；箱型不存在 → 「箱型ID:{id}不存在」；包装不存在 → 「包装ID:{id}不存在」；箱内商品不存在 → 「箱内商品信息(品名)ID:{id}不存在」
11. 关联人员的用户不存在 → 「用户ID:{id}不存在」
12. 销售无效 → 「销售不能为空」
13. 组织归属校验（见 6.5，四条提示语在那里）

**必填与非必填的明确结论**（避免界面凭感觉加校验）：

| 字段 | 是否必填 | 说明 |
| :-- | :-- | :-- |
| 委托单位 | **必填** | 不选会走到「委托单位不存在」 |
| 所属组织 | **必填** | 见 6.5，报「所属组织不能为空。」 |
| 业务关联人员，且销售恰好 1 个 | **必填** | 见校验 3、4 |
| 集装箱的箱型 | 每条箱子必填 | 但**整个集装箱列表可以为空**，一条箱子都不加也能保存 |
| 商品子表的商品 | 每条必填 | 整个列表可以为空 |
| 起运港、目的港 | **都不必填** | 可以都不选直接保存；不选起运港时，航线名、国家名自然为空 |
| 船名、航次、船公司、原产国、码头、贸易方式、客户编号、联运单号、分单号、发票号、批次号 | 都不必填 |  |
| 到港日期 | 不必填 | 为空时会计期间按当前时间算 |
| 委托编号 | 不必填 | 不填由后端按规则生成，见 6.3 |

**保存过程**：

1. 规范化日期：到港日期、实际开船日期、预抵日期截断到日期部分。
2. 计算会计期间与应结日期（见 6.2）。
3. 委托编号：填了用填的，没填按规则生成（见 6.3）。
4. 插入业务主表，后端强制写入业务类型 = 海运进口、录入方式 = 手动录入、未完结 = false、租户、所属人、所属组织，拿到新 Id。
5. 三张子表（集装箱、商品、关联人员）随主表一起写入。
6. 用同一个 Id 插入海运进口扩展表，船名做规范化（见 6.4）。
7. 保存分组附件。

保存成功后返回新票的 Id，界面据此打开详情或跳转编辑。

## 7.2 编辑

**校验**：

1. 没有任何输入 → 「输入信息不能为空」
2. 缺少业务主表信息 → 「业务信息不能为空」
3. 关联人员为空 → 「业务关联人员不能为空」
4. 销售数量不等于 1 → 「销售有且只能有一个」
5. 海运进口记录不存在 → 「输入海运进口错误」
6. 对应的业务主表记录不存在 → 「对应的业务信息不存在」
7. 其余长度校验、主提单号重复校验、外键校验、子表校验、组织归属校验与新增**完全相同**（见 7.1 第 5～13 条，含全部提示语）

**字段级权限回填**：在业务校验之后、写库之前，后端会把当前用户无权查看的字段用数据库原值覆盖回来，扩展表和业务主表各执行一次。这样即使界面因为字段被屏蔽而没提交，也不会把库里的值抹成空。

**保存过程**：

1. 业务主表逐字段更新。到港日期变化会带动会计期间、应结日期重算，并同步该票所有非改单费用的会计期间（见 6.2）。
2. **三张子表按全量比对处理**，集装箱、商品、关联人员规则一致：
   - 带了主键的行 → 更新库中对应记录；
   - 没带主键的行 → 作为新记录插入；
   - **库里存在但本次没有出现的行 → 删除**。
   - 因此界面必须**提交完整的子表列表**，不能只提交发生变化的行。
3. 扩展表逐字段更新，船名做规范化。
4. 转站日期、箱使日期、集装箱净重、净重合计仍以界面提交值为准，后端不重算。

## 7.3 详情

用于打开一票的完整信息，编辑页也用它做回显。

**校验**：记录不存在 → 「输入海运进口错误」。

**展示的内容**：

| 部分 | 内容 |
| :-- | :-- |
| 海运进口层字段 | 2.1 的全部业务字段 + 创建/修改的审计信息 |
| 数据归属 | 所属人、所属组织，以及从最高级组织到所属组织的**组织串**（每级带本位币信息）；没选组织时组织串为空 |
| 起运港带出 | 起运港名、起运港 EDI 代码、**国家中文名、国家英文名、航线名**。**这五项全部取自起运港**；没选起运港时五项都为空 |
| 目的港带出 | 目的港名、目的港 EDI 代码 |
| 原产国带出 | 原产国中文名、英文名 |
| 船公司带出 | 船公司的中文名、中文简称、英文名、英文简称、EDI 代码，以及船公司 logo 图片；没选或已删除时为空 |
| 录入人 | 创建人昵称 |
| 业务主表层字段 | 2.2 中「进口展示 = 是」的全部字段，各基础资料带出名称 |
| 往来单位带出 | **码头**、委托单位、车队、报关行、仓库、保险公司、收货人、发货人、通知人，每个带简称、全称，以及**该单位的默认地址**（地址子表中标记为默认的那条，没有则为空）；另返回委托单位联系人对象 `ClientContact`（`ClientContactSimpleDto`）。九个里**只有码头在海运进口层**，其余八个都在业务主表层 |
| 集装箱 | 该票全部箱子，每条带箱型名、包装名、商品名与 HS 编码；没有箱子时是空列表 |
| 商品 | 该票品名清单，每条带商品名、HS 编码，以及**该商品的 TEU 合计** |
| 关联人员 | 每条带用户昵称；整体按排序号**降序**（大的在前），排序号相同的按数据库返回顺序 |
| 费用 | 该票全部费用（含改单费用），字段口径见 2.7；没有费用时是空列表 |
| 费用状态汇总 | 四个汇总值，规则见 6.6 |
| 箱型箱量合计 | 格式 `箱型名*数量`，多个箱型用**单个空格**分隔，例如 `20GP*2 40HQ*1`。没有箱子时是空字符串 |
| 整票 TEU | 各箱子箱型 TEU 之和；箱型查不到时该箱按 0 计 |
| 件数大写 | 「件数的英文单词 + 包装名」整体转大写，例如件数 12、包装名 `CARTONS` 时为 `TWELVECARTONS`。**件数为空时该值为空**。**只有详情有，列表没有** |
| 未解决问题数 | 该票未解决的业务问题数量 |
| 附件 | 分组附件，见 2.9；没有附件时是空列表 |
| 公司打印信息 | **仅在按「打印」方式打开详情时返回**：公司全称、简称、英文名、办公地址、联系电话、邮箱、统一社会信用代码、logo 图片（相对路径前拼 `GlobalServer:BaseUrl` 成直连地址）、默认银行账户（含人民币与美元账户）。由业务主表的所属组织向上解析到公司层级节点取得；没选组织时为空 |
| 上一票 / 下一票 | 按打开详情时带上的列表搜索条件与排序，给出全量顺序里的前一条、后一条 Id。没有则为空。**只有详情有，列表没有** |

**详情要过行级数据权限与表级权限**，口径见 4.2；查不到时按「不存在 / 没数据权限 / 没表级权限」分别报错。

**详情额外返回 `IsEditable`（是否可编辑）**：按「编辑」操作类型的数据权限 + 表级权限判定，与编辑接口的校验是同一套口径，前端可直接用它禁用编辑和删除按钮。能看到不等于能改，这两件事分开判。

**详情额外返回上一票 / 下一票 Id**：打开详情时要把当时列表的搜索条件和排序一起带上。后端按这份条件筛完、再按同一排序排完之后的**全量顺序**给出前一条和后一条的 Id，与当前在第几页无关。没有上一票或下一票、以及当前票已经不在这份结果里时，对应 Id 为空。按打印方式打开时不算这两项。翻票时搜索条件和排序保持不变，只换当前票 Id。

## 7.4 列表

列表是海运进口的主入口，支持关键字搜索、多维度筛选、排序、分页。

**筛选维度**（全部可选，多个条件之间是「并且」）：

| 分组 | 可筛的内容 |
| :-- | :-- |
| 关键字 | 一次模糊匹配 9 个字段：船名、航次、发票号、批次号、外部备注、主提单号、订舱编号、合同号、委托编号 |
| 组织 | 按所属组织筛，**自动包含其全部下级组织** |
| 海运进口层 | 船名（模糊，带「未填写」开关）、航次（模糊）、船公司（带开关）、起运港（带开关）、起运港备注（模糊）、目的港（带开关）、目的港备注（模糊）、客户编号（模糊）、**码头（精确，带「未填写」开关）**、**联运单号（模糊）**、**分单号（模糊）**、**贸易方式（精确）**、批次号（模糊）、原产国（带开关）、净重合计区间、换单日期区间、提货日期区间、报关日期区间、转站日期区间、免箱期区间、箱使日期区间、创建时间区间 |
| 业务主表层 | 委托编号（模糊）、会计期间区间、应结日期区间、业务来源、运输条款、是否业务锁定、是否未完结、主提单号（模糊）、订舱编号（模糊）、合同号（模糊）、发票号（模糊）、内部备注（模糊）、货物类型、唛头（模糊）、包装、货物描述（模糊）、委托单位、车队、报关行、仓库、保险公司、收货人及其内容（模糊）、发货人及其内容（模糊）、通知人及其内容（模糊）、**到港日期区间**、是否费用锁定 |
| 关联人员 | 销售、操作、单证、商务、客服，各按用户筛。命中条件是「该票存在对应属性且用户相符的关联人员」 |
| 集装箱 | 箱型（精确）、箱号（模糊）。命中条件是「该票存在符合条件的箱子」 |

**不提供筛选的字段**（明确列出，避免误提缺陷）：整票件数、毛重、体积、排序号、全部危险品字段、全部冻柜字段、集装箱除箱型与箱号外的其它字段、商品子表、费用状态。外部备注只能通过关键字间接搜。

**列表每行展示的内容**：2026-10-01 起列表单独用 `SeaImportListDto`，只带表格上的列。箱量文本和 TEU 仍由箱子算出，但箱子明细、费用明细、品名不返回。费用状态仍是票上的 `receiveFeeStatus`、`payFeeStatus`。有没有费用看 `transportOrder.hasOrderFee`。详情继续返回完整对象。

**过滤链的执行顺序**：先按筛选条件过滤 → 叠加行级数据权限（4.2）→ 叠加字段级权限（4.3）→ 排序 → 统计总数 → 取当前页。因此总条数是**已经过权限过滤的**条数。

## 7.5 复制

用于以现有票为模板快速开一张新票。用户可以选择是否把费用一起带过来。

**校验**：

1. 没有任何输入 → 「输入信息不能为空」
2. 没指定要复制的票 → 「海运进口id不能为空」
3. 源记录不存在 → 「海运进口不存在」
4. 源记录的业务主表不存在 → 「业务信息不存在」
5. 源票关联人员为空 → 「业务关联人员不能为空」
6. 源票销售数量不等于 1 → 「销售有且只能有一个」

**复制规则**：

| 处理 | 字段 |
| :-- | :-- |
| **重新生成** | 委托编号（走编号规则，见 6.3） |
| **重新计算** | 会计期间、应结日期（按新票的到港日期，规则见 6.2） |
| **清空** | 发票号、批次号、联运单号、分单号、主提单号、订舱编号、合同号（**都属于一票一号，复制不带**） |
| **重置为初始值** | 业务锁定 = 否、未完结 = 否、费用锁定 = 否、费用锁定人/锁定时间/解锁人/解锁时间 = 空、录入方式 = 复制、所属人 = 当前登录用户、租户 = 当前租户 |
| **原样复制** | 两层表的其余全部字段，包括换单日期、提货日期、报关日期、转站日期、免箱期、箱使日期、原产国、客户编号、码头、贸易方式、净重合计、船名、航次、船公司、起运港、目的港及其备注、收发通、货物信息、危险品、冻柜等 |
| **连子表一起复制** | 集装箱（含型号、规格、净重）、商品、关联人员。子表主键重新生成 |
| **不复制** | 附件、改单、业务问题 |

**费用复制**（用户勾选时）：

- 只复制源票的**非改单费用**，改单费用不复制。
- 每条新费用重置为录入初始状态：费用状态 = 录入、结算状态 = 未结算、开票状态 = 未开票、已结算金额 = 0、客户对账 = 空、所属改单 = 空、费用模板项 = 空、录入方式 = 业务复制、会计期间取新票的会计期间。
- 沿用源费用的：收付类型、费用代码、行业类别、结算对象、币别、汇率、含税单价、不含税单价、金额、不含税金额、单位、数量、税率、是否禁开发票、是否机密、备注。

**复制不执行组织归属校验**，直接沿用源票的所属组织。因此复制别人的票时，新票的所属人变成了自己，但所属组织仍是源票的组织，两者可能不匹配——**这种票下次编辑时会撞上组织归属校验**，需要先改所属组织。这是需要留意的边界。

## 7.6 删除

**校验**：

1. 记录不存在 → 「海运进口不存在」
2. **该票还存在未删除的费用** → 「当前票包含未删除费用，请先删除费用」。这是硬约束，无论费用处于什么状态、是不是改单费用，只要有一条就拒绝删除，没有强制删除的旁路

**删除范围**（软删除不级联，全部由后端显式执行）：

1. 该票的费用审批任务及其明细：任务类型为「提交费用」「修改费用」「删除费用」的任务
2. 改单记录
3. 商品子表
4. 集装箱子表
5. 关联人员子表
6. 业务问题及其附件关联
7. 本票的附件关联（**只解除关联，不删除附件文件**）
8. 最后软删除海运进口扩展表与业务主表

删除是软删除，数据库里记录仍在，只是所有查询都过滤掉了。

## 7.7 分组统计

按指定维度对**当前筛选结果**做票数统计，通常用于列表页上方的统计卡片或左侧分组树。

**处理**：先按与列表**完全相同**的条件过滤（含数据权限与字段级权限），再按指定维度分组统计。分页在这里无效，返回全部分组。

**支持的维度**见 3.6，传枚举以外的值报「不支持的分组字段」。

**每个分组返回**：分组值、分组显示名、票数、以及按船公司分组时的 logo 图片。**按票数降序排列**。

分组名的取值来源：

| 维度            | 显示名取自           |
| :-------------- | :------------------- |
| 委托单位        | 往来单位的**简称**   |
| 船公司          | 船公司的**中文简称** |
| 起运港 / 目的港 | 港口名               |
| 船名            | 船名文本本身         |
| 仓库 / 车队     | 往来单位的**简称**   |
| 原产国          | 国家**中文名称**     |

两个细节：

- **该字段为空的票会单独成一组**，分组值和显示名都为空，界面应显示成「未填写」之类的占位文案。
- **关联基础资料已被删除时，分组名仍能正常显示**（统计时临时关闭了软删除过滤），不会出现一堆空名分组。

## 7.8 重新生成委托编号

用于编号规则调整后，把某一票的委托编号按最新规则重新取号。**用户不能指定编号内容**，只能触发重新生成。

**校验**：

1. 没有任何输入 → 「输入不能为空」
2. 海运进口不存在 → 「海运进口不存在」
3. 对应业务主表不存在 → 「对应的业务信息不存在」
4. 规则未配置 → 「未配置生成规则」；规则里没有自增项 → 「未配置自增编号规则」

生成后立即写入该票并落库，返回新编号供界面刷新显示。原编号不保留、不可恢复。

## 7.9 附件维护

三个操作：查询、新增、删除。附件也可以在保存单据时一并提交（见 2.9），两种方式效果相同。

**查询**：票不存在 → 「输入海运进口错误」。返回分组附件，排序规则见 2.9。

**新增**：票不存在 → 「输入海运进口错误」。**附件集合为空时不报错，直接成功**；集合中无效的附件项被静默跳过，不报错也不入库。每个有效附件建立一条关联记录，标记模块编码与归属票据。

**删除**：票不存在 → 「输入海运进口错误」；没有指定要删的附件 → 「附件Id集合不能为空」。只解除**本票**与这些附件的关联，**不删除附件文件本身，也不影响该附件在其它票上的关联**。指定了不存在的附件不报错，只是什么都没删掉。

| 点击**净重合计计算**按钮 | 汇总各箱净重写入净重合计 |
| 切换**销售** | 应重新加载该销售的直属组织列表，并清掉不在列表内的所属组织选择（见 6.5） |
| 切换**货物类型** | 普通货隐藏危险品区与冻柜区；冻柜显示冻柜区；危险品显示危险品区；超限箱提示填写集装箱的超长/超宽/超高 |

**明确没有联动的地方**（不要自作主张加）：

- 委托单位与**客户编号**之间没有任何联动；
- 整票件数与集装箱件数之间没有联动，是两处独立录入；
- 整票毛重与集装箱毛重、净重合计之间没有联动；
- 收货人/发货人/通知人的**下拉选择**与对应的**抬头内容文本框**各存各的，选了单位不会自动填内容；
- 商品清单与集装箱内的商品是两处独立录入，不互相同步；
- **码头是往来单位下拉，但和其它往来单位互不影响**：选了码头不会带出任何别的字段，选了委托单位也不会自动带出码头；
- **贸易方式是纯前端枚举**，选了不触发任何联动，也不影响费用、统计、打印；
- 危险品的「危品净重」是文本字段，与集装箱净重、净重合计完全无关。

## 8.3 只读与后端接管的字段

以下字段界面应做成只读，用户填了也会被覆盖或忽略：会计期间、应结日期、件数大写、箱型箱量合计、整票 TEU、商品 TEU、未解决问题数、录入人、创建时间、是否未完结、费用锁定及其四个审计字段、业务类型、录入方式。

## 8.4 集装箱表格

- 集装箱在海运进口里属于**进口自己这一层**，型号、规格、净重三列只有进口有。
- 箱型是每行必填；**整张表可以一行都没有**。
- 净重默认由毛重减皮重算出，允许手改；改过之后再改毛重皮重，界面应再次覆盖计算结果（或明确提示用户），但**后端永远不会替你算**。
- 编辑保存时**整张表要完整提交**，包括没改动的行，否则漏掉的行会被删除。已有行必须带上自己的主键，新增行不带。

## 8.5 子表的整体提交原则

集装箱、商品、关联人员三张子表都遵循同一条规则：**保存时提交的列表就是保存后的最终状态**。

- 界面上删掉一行 = 提交时不带这一行；
- 界面上加一行 = 提交时带一行没有主键的数据；
- 没动的行也要原样带上，只提交改动行会导致其余行被删。

## 8.6 列表页交互

- 默认按创建时间倒序，支持列头排序（包括按委托单位名称这类关联字段排序）。
- 关键字框一次搜 9 个字段，见 5.3。
- 船名、船公司、起运港、目的港、原产国、码头六个筛选项各自带一个「未填写」开关，**开关与选值互斥**，界面应在选了值时禁用开关、开了开关时禁用选值，避免用户撞上报错。
- 模糊搜索**搜不到空值行**，想找空值必须用「未填写」开关。
- 日期筛选是闭区间；进口层的五个日期可能带时分秒，界面在传「止」端时应自动补到当天最后一刻。
- 统计卡片/分组树用分组统计功能，**筛选条件必须与列表保持一致**，否则两边数字对不上。
- 列表每行数据量较大，建议默认每页 10～20 条。

## 8.7 附件交互

- 附件按类型分组展示，组内可拖拽排序（顺序号），可标记「客户是否可见」。
- 附件可以随单据保存一起提交，也可以在详情页单独增删，两条路径效果相同。
- 从本票移除附件只是解除关联，**文件本身仍在**，同一附件挂在别的票上不受影响。
- 每个附件可直接下载或预览，图片类可直接内联显示。

## 8.8 提示语展示

所有业务校验失败都只返回一句话，界面直接把这句话弹出即可。**不要自行改写文案**，测试是按原文断言的。

校验是**命中即中断**的，一次只报一个错。界面自身的必填校验应尽量在提交前拦下（委托单位、所属组织、销售恰好一个、箱型），减少来回。

## 8.9 详情翻票

从列表点进详情时，把当时列表的搜索条件和排序一起带上。详情页的上一票 / 下一票按这份条件的全量顺序走，不是当前页的前后两条。点上一票或下一票时搜索条件和排序保持不变，只换当前票。对应 Id 为空时禁用该方向按钮。

# 9. 难点与风险点

这一章集中列出容易做错、容易误判为缺陷、容易在联调阶段卡住的地方。

## 9.1 四个派生值不会自动重算

转站日期、箱使日期、集装箱净重、净重合计**只在前端录入时按公式带出**。用户改了到港日期、免箱期、毛重或皮重却没有重新触发计算，保存下去的仍是旧值，后端不会纠正。

- 前端：所有基准字段的变更事件都要挂上重算逻辑。
- 测试：这是**既定行为**，不是缺陷。用例要覆盖「改基准值不重算 → 保存旧值」的场景并判定为通过。

## 9.2 子表全量比对，漏传即删除

编辑时三张子表按「提交什么就是最终状态」处理。前端如果做了增量提交优化，会静默删掉用户没动过的行，而且**不会有任何报错**，是最危险的一类问题。

## 9.3 集装箱不在业务主表那一层

业务主表本身也有一份通用的集装箱结构，但它不含型号、规格、净重。海运进口的集装箱**在提交和查看时都位于海运进口自己这一层**，业务主表那一层的集装箱对进口无效——提交会被忽略，查看恒为空。

## 9.4 「到港日期」的字段名是 ETD

界面文案是「到港日期」，底层字段名是 `ETD`。同时数据库里还有个真正的 `ETA`（预抵日期），进口不使用。查数据库、看日志、写排序字段时都要用 `ETD`。

## 9.5 销售的强约束会牵连组织

「销售恰好 1 个」是硬约束，0 个和 2 个都报同一句「销售有且只能有一个」。更麻烦的是所属组织必须是**该销售的直属组织**，父组织不算。换销售往往要连带换组织，界面要主动联动，否则用户在保存时才发现。

## 9.6 复制出来的票可能立刻编辑不了

复制不做组织归属校验，新票的所属人变成当前用户，但所属组织沿用源票。如果源票组织不是新销售的直属组织，**这张票一打开编辑保存就会报「所选组织不在数据所属人(本人)所属组织范围内。」**。复制别人的票之后应提示用户检查所属组织。

## 9.7 有费用的票删不掉

只要该票还有一条未删除的费用（任何状态、含改单费用），删除就被拒绝，没有强制删除的旁路。界面应在删除按钮上做前置提示，而不是让用户点了才报错。

## 9.8 编号规则未配置会导致三处功能不可用

委托编号规则未配置时：新增只要不手填编号就失败，复制和「重新生成委托编号」**无论如何都失败**。这是上线硬前置条件，测试环境也必须先配。

## 9.9 模糊搜索搜不到空值

包含匹配天然跳过空值行。「查一下船名没填的票」只能用「未填写」开关，不能靠搜索空字符串。而且开关和选值**同时使用会直接报错**，不是取并集。

## 9.10 日期区间的时分秒陷阱

业务主表的三个日期存的时候会被截成 00:00:00，但进口层的五个日期**原样保存**。如果用户录入时带上了时分秒（例如从其它系统导入），按「止 = 当天」筛选就会漏掉当天的数据。界面应统一只录日期，并在筛选时把「止」端补到当天最后一刻。

## 9.11 权限造成的字段缺失

字段级权限不是把值置空，而是让字段**整个不出现**。前端读取时必须容忍字段缺失，测试断言「无权限时看不到某字段」时也要按「字段不存在」判断，而不是「值为空」。

另注意：**详情、编辑、删除、重新生成委托编号自 2026-08-19 起都做行级数据权限**（口径见 4.2）。此前「拿到 Id 就能查改」的行为已经取消，按老行为写的用例要同步改。

## 9.12 费用只读概览，部分字段是空的

海运进口展示的费用是概览，一部分费用属性在这里不填充（见 2.7）。每条费用上那个「组合费用状态」属性也**不要用**，票级的应收/应付组合状态另有两个专门的值。需要完整费用数据时用费用模块自己的功能。

## 9.13 列表返回的数据量

列表每一行都带完整费用与三张子表，每页开太大会明显变慢。分页统计的总数还叠加了数据权限，不同账号看到的总数不同，这是预期。

## 9.14 可能存在没有扩展记录的进口票

业务主表自己的新增功能不创建海运进口扩展记录，因此库里可能出现「业务类型是海运进口但没有扩展记录」的票。这种票在业务主表详情里进口信息为空，**不报错**（见第 10 章）。测试遇到属预期。

## 9.15 码头的行业类别过滤只在前端

码头指向的是往来单位表，业务上要求只能选「码头」类的客户，但**后端只校验这个客户存不存在，不校验它的行业类别**。也就是说：接口层面传一个「车队」客户当码头是能存进去的，也能正常读回来。因此

- 下拉数据源必须由前端按行业类别含「码头」去过滤，这是唯一的把关点；
- 测试用接口直接构造脏数据（拿非码头客户当码头）不会报错，这是当前设计，不是缺陷；
- 客户的行业类别后来被改掉（从「码头」改成别的）时，历史票上的码头**不会**被清空或报错，照旧显示。

## 9.16 贸易方式后端完全不认识

贸易方式在库里就是一个可空整数，取值范围、中文文案、默认值、排序全部由前端定义和维护。后端不校验取值合法性，不参与费用、统计、分组、打印的任何逻辑，只做原样存取。带来两点：

- 前端改了枚举定义（比如删掉某个值）时，**历史数据里的旧数字不会被清理**，界面要能兜住「查不到对应文案」的情况，不要直接报错或显示空白；
- 筛选是按整数精确匹配的，前端传的必须是枚举的数值而不是文案。

## 9.17 存量重复主提单号下次保存会被拦住

上线前库里如果已经有多票共用同一个主提单号，读和列表不受影响。但其中任意一票下次保存都会报「主提单号【{号码}】已存在」，必须先把重复的号改掉。空主提单号（没填）不在这条限制里。

# 10. 业务主表功能的分流

业务主表自身也有一套对外功能。海运进口上线后，其中两个按业务类型分流：

| 功能 | 分流后的行为 |
| :-- | :-- |
| **详情** | 业务类型是海运进口时，在业务主表信息中填充海运进口扩展信息（内容与海运进口详情一致）；是海运出口时填充海运出口扩展信息 |
| **删除** | 业务类型是海运进口时，走海运进口的删除逻辑，包含 7.6 列出的全部校验与级联清理 |

业务主表的**新增和编辑保持原样**，不创建也不修改海运进口扩展记录。

因此数据库中可能存在「业务类型是海运进口、但没有扩展记录」的票。这种数据在详情里进口信息为空，**不报错**。

# 11. 基础资料删除的引用校验

以下基础资料在执行删除时，必须先检查是否被海运进口引用；被引用则禁止删除，提示「已被海运进口模块引用，禁止删除」。

| 船公司 | 海运进口的船公司 |

| 商品（品名） | 商品子表、集装箱子表的商品（限海运进口的票） |
| 包装 | 业务主表的包装、集装箱子表的包装（限海运进口的票） |

| 运输条款 | 业务主表的运输条款（限海运进口的票） |

| 用户 | 关联人员子表的用户（限海运进口的票） |

# 12. 上线前置条件与卡点

> [!IMPORTANT] **卡点 1：编号规则未配置，新建直接失败** 委托编号规则 `SeaImport.CommissionNum` 必须由管理员在「编号规则」中预先配置。未配置时，用户只要不手填委托编号，新建就直接报「未配置生成规则」；复制和「重新生成委托编号」**无论如何都会失败**。**这是上线的硬前置条件。**

> [!IMPORTANT] **卡点 2：销售有且只有一个** 关联人员中销售的记录数不等于 1 时，新增、编辑、复制全部被拒绝，提示「销售有且只能有一个」。0 个和 2 个都不行。

> [!IMPORTANT] **卡点 3：所属组织必须是销售的直属组织** 父组织不算直属。销售与组织的绑定关系必须先在组织架构里维护好，否则用户无法保存。

> [!IMPORTANT] **卡点 4：有费用的票删不掉** 删除前必须先把该票的费用删光，否则报「当前票包含未删除费用，请先删除费用」。这是防止费用变成孤儿数据的硬约束。

> [!IMPORTANT] **卡点 5：派生日期不会自动跟随基准值变化** 转站日期、箱使日期、集装箱净重、净重合计四个值只在前端录入时按公式带出。用户后续改了基准值却没有重新触发计算时，后端不会替他重算。**这是既定行为，不是缺陷。**

> [!IMPORTANT] **卡点 6：子表必须整体提交** 编辑对集装箱、商品、关联人员三张子表做全量比对：库里存在而本次没提交的行会被删除。

> [!IMPORTANT] **卡点 7：集装箱位于海运进口这一层** 海运进口的集装箱不在业务主表那一层，业务主表那一层的同名结构对进口无效。

> [!IMPORTANT] **卡点 8：主提单号不能重复** 新建和保存时，填了主提单号就要在当前租户业务表里查重（海运出口、海运进口、空运出口共用，互相也不能撞号）。冲突报「主提单号【{号码}】已存在」。空值不校验；已软删除不参与；编辑排除自身。存量里已经撞号的票，下次保存会被拦住，必须先改掉其中一个。
