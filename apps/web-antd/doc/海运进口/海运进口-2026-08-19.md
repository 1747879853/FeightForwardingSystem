# 1. 背景意图 (Background)

两件事：

**一是补一个越权口子。** 海运进口的详情、编辑、删除、重新生成委托编号这四个按 Id 定位单票的接口，此前**一层数据权限过滤都没有**——只要有模块的功能权限点，再知道一个 Id，就能查看、修改、删除任意一票，包括别的部门、别的公司的。行级数据权限只在列表和分组统计上生效，等于只挡了入口没挡门。

这一点此前是被当成「既定设计」写进总逻辑文档 4.2 和接口文档的（原文：详情不做行级过滤，不要当缺陷提）。本次认定它是缺陷并修掉，相关文档说明已一并订正。

**二是配合利润/欠费报表的需要。** 报表要按结算方式筛选和展示，而结算方式此前只在客户账期表上按规则匹配、算完即丢，没有落库。落库之后顺带对这三个业务模块开放为只读字段。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 按 Id 操作的四个接口补行级 + 表级权限

`DetailAsync`、`EditAsync`、`DeleteAsync`、`UpdateCommissionNumAsync` 统一改为先过行级数据权限、再过表级权限，两层都通过才继续。

| 接口                       | 解析数据权限时的操作类型 | 报错里的动作名 |
| :------------------------- | :----------------------- | :------------- |
| `DetailAsync`              | 查询                     | 查看           |
| `EditAsync`                | **编辑**                 | 编辑           |
| `DeleteAsync`              | **编辑**                 | 删除           |
| `UpdateCommissionNumAsync` | **编辑**                 | 编辑           |

判定口径与列表完全一致：所属人、创建人、所属组织（含下级）、业务干系人（销售/商务/操作/客服/单证/海外客服/航线）任一命中即通过。

**报错分三种**，便于区分是数据问题还是权限问题：

| 情况 | 提示语 |
| :-- | :-- |
| 这一票不存在 | 「输入海运进口错误」/「海运进口不存在」（各接口原有提示） |
| 票在，但没有行级数据权限 | 「没有这条数据的数据权限,不能查看 / 编辑 / 删除」 |
| 行级过了，被表级权限挡掉 | 「没有这条数据的表级权限,不能查看 / 编辑 / 删除」 |

**详情的实现是零额外开销的**：查询本身就带着两层过滤，取到数据直接返回；只有取不到时才回头做 1～2 次存在性判断去分辨原因。编辑和删除因为要拿可跟踪实体做局部更新，校验单独走一次 `AsNoTracking` 查询，不污染变更跟踪器。

## 2.2 列表与详情新增 `IsEditable`（是否可编辑）

`SeaImportDto` 新增 `bool IsEditable`。该 DTO 是列表和详情共用的，两个接口都会填。

- 判定 = 「编辑」口径的行级数据权限 + 表级权限，**与编辑接口的校验是同一套代码**，保证列表上显示能编辑的，点进去一定改得动
- 列表是**整页一次查询**批量判定，不在循环里逐条判
- 前端可直接用它禁用编辑和删除按钮

## 2.3 结算方式 `SettlementType`

业务主表新增只读列，海运进口这一侧的开放范围：

| 场景                                            |     是否开放     |
| :---------------------------------------------- | :--------------: |
| 列表查询条件 `SettlementType`                   |        ✓         |
| 列表 / 详情返回（挂在 `TransportOrder` 对象里） |        ✓         |
| `AddDto` / `EditDto`                            | **✗ 不接受录入** |

取值：0 票结、1 月结、2 约定天数。唯一写入口是应结日期的计算逻辑，两者同时生成。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT] **①「编辑」操作类型的数据权限，本次是第一次真正生效**
>
> 数据权限的操作类型只有「查询」和「编辑」两种（没有删除，所以删除按编辑判）。而「编辑」这个类型在本次改动之前**全项目没有任何一行代码读取过**——配置界面一直有，配了也不起作用。
>
> 现在它生效了。**这不是上线卡点**，上线后由客服按实际需要给用户和角色配置编辑口径的数据权限即可。
>
> 需要知道的是配置到位之前的表现：用户只能改动「自己是所属人 / 创建人 / 干系人」的票，列表里其余行的 `isEditable` 都是 `false`、编辑和删除按钮是灰的。所以有人反馈「单子改不了」「编辑按钮点不了」时，**第一个要查的就是编辑口径配了没有**：
>
> ```sql
> SELECT ManageType, COUNT(*) FROM App_UserDataPermissions WHERE IsDeleted = 0 GROUP BY ManageType;
> ```
>
> `ManageType = 0` 是查询，`1` 是编辑。

> [!IMPORTANT] **② 文档和用例里的旧结论已作废**
>
> 总逻辑文档 4.2、7.3、9.11 和接口文档 4.3、6、7.3 此前都写着「详情不做行级过滤，拿到 Id 就能查」，其中接口文档的用例 SI-D-011 直接断言「受限账号能查到」。这些说明本次已全部订正，按老行为写的自动化用例必须同步改成断言报错。

> [!IMPORTANT] **③「能看到」和「能编辑」是两件事**
>
> 详情能打开不代表能保存。详情按查询口径判，编辑按编辑口径判，两者的数据权限配置是分开的。前端不要用「详情打开成功」推断可编辑，要看 `isEditable`。

> [!IMPORTANT] **④ 结算方式的存量数据是空的**
>
> 新增列之前已存在的票该字段为 `null`，按结算方式筛选时这些历史票一条都查不出来。确认过不回刷。另外它是下单当时的快照，之后客户账期规则改了不会自动刷新。
