# 1. 业务背景说明 (Background)

客户联系人是**合作客户（`App_Clients`）下的人**：一个客户可以有多个联系人（老板、操作、财务、单证……），业务单据上「委托单位联系人」「订舱代理联系人」选的就是这张表里的人，对账、报价、发票也从这里取联系方式。

联系人自带联系方式（手机/邮箱/办公电话/座机/微信/QQ），是销售最核心的私有资源。为此本表有一个**对接人 `UserId`**：填了就只有指定人看得见，不填则所有人可见（详见第 3 节）。

# 3. 数据权限规则（对接人 UserId）★本模块核心

## 3.1 规则

| 联系人的对接人 `UserId` | 谁能看到/操作 |
| :-- | :-- |
| **为空（不填）** | **所有人**都能看到、都能改 |
| **有值** | 只有**该对接人本人**，以及**数据权限里能看到该用户的人** |
| 任意 | 拥有**全部数据权限**（`DataPermissionType.All`）的人**可见全部**（下一行除外） |
| **是当前用户排除人员名单里的人** | **看不到**，全部权限也挡；对接人为空的联系人不受影响 |

本表的数据权限模块是「客户联系人」（`DataPermissionModule.ClientContact = 20`），没有单独配置时用通用规则。排除人员只按对接人判定：被排除人名下客户的联系人，对接人是别人或为空时仍然可见。规则配置见 `文档/权限/用户或角色数据权限/数据权限模块总逻辑文档.md`。

「数据权限里能看到该用户的人」= 当前用户的数据权限解析出的**可见用户集合**（`GetDataPermissionUserIdsAsync`）包含该对接人：

- 恒定包含**自己**；
- 加上数据权限配置为「指定用户（`ManyUser`）」里勾选的那些用户。

## 3.2 组织权限（我的部门 / 我的公司 / 指定部门）**不参与**本表判定

这是本表和客户、业务单、费用最大的区别，**测试时最容易误判**：

本表**没有 `OrgId` 列**（需求明确要求不继承 `DataPermissionFullAuditedEntity`），所以只按「可见用户集合」判定。只配了「我的部门 / 我的公司 / 指定部门」的人，除了「未指定对接人」的联系人以外，**只能看到自己名下的**——这正是需求要的「填了对接人就只有指定人能看」。想让主管看到组员名下的联系人，必须给主管配「指定用户」把组员勾上，或者直接给「全部」。

## 3.3 查询口径 / 编辑口径分开

数据权限按 `ManageType` 分两套（查询 `Get`、编辑 `Edit`），本模块的用法：

| 接口 | 口径 |
| :-- | :-- |
| 列表 `GetPagedListAsync`、详情 `DetailAsync` | 查询 `Get` |
| 编辑 `EditAsync`、删除 `DeleteAsync`、启用禁用 `SetDisabledAsync`、批量保存 `BatchSaveAsync` | 编辑 `Edit` |
| 新增 `AddAsync` | 不判（还没有这条数据） |

## 3.4 只管本模块自己的接口，业务单据回显不过数据权限

判定入口只有一个：`CsprojBuilderAppServiceBase.ClientContactDataPermissionFilterAsync`， **只用在本模块自己的七个接口上**（列表/详情/编辑/删除/启用禁用/批量保存，新增无需判）。

业务单据（海运出口/进口、空运出口）、客户对账、海运出口服务任务、报价**回显已选定的联系人时不过这个过滤**：那些联系人已经落在单据上，属于单据自己的数据，可见性跟着单据走——能看到这一票，就能看到它上面的联系人姓名与联系方式。同理，单据保存时的联系人归属校验（`EnsureClientContactBelongsAsync`）也只校验「联系人存在」+「属于父客户」，不判数据权限。

所以对接人管的是「**能不能在联系人列表里翻到、能不能改它**」，不是「单据上能不能显示它」。

## 3.5 无权限时的表现（只在本模块）

| 场景 | 表现 |
| :-- | :-- |
| 联系人列表 | 该条**不出现**在列表里，`totalCount` 也不含它 |
| 联系人详情 | 报错「没有这条联系人的数据权限,不能查看」；数据本身不存在报「输入合作客户联系人错误」 |
| 编辑/删除/启用禁用 | 报错「没有这条联系人的数据权限,不能编辑 / 删除 / 启用/禁用」 |
| 批量保存 | **整批失败**，报「没有联系人【张三、李四】的数据权限,不能保存」 |
| 业务单据 / 对账 / 服务任务 / 报价的联系人回显 | **不受影响**，照常返回联系人对象与联系方式 |

## 3.6 `ClientContactSimpleDto`（单据回显用）不含对接人

对接人属于联系人自身的管理信息，只在联系人列表/详情里返回。

## 3.7 存量数据

新增列可空，存量联系人 `UserId` 全为 `NULL`，即**全部保持所有人可见**，上线后可见性不变。只有主动填了对接人的联系人才开始受限。

# 4. 字段全量说明

> 读写列：**写**=新增/编辑可提交；**只读**=仅输出，提交无效；**系统**=后端维护。

| 字段 | JSON | 类型/长度 | 读写 | 校验与规则 |
| :-- | :-- | :-- | :-- | :-- |
| 主键 | `id` | long | 系统 | 自增 |
| 租户 | — | int | 系统 | `IMustHaveTenant`，不出参 |
| 合作客户id | `clientId` | Guid | 写 | **必填**；客户必须存在，否则报「输入合作客户id错误」 |
| 名字 | `name` | string | 写 | **必填**（空白也算空），否则报「合作客户联系人名称不能为空」；库中未限长 |
| 手机 | `mobile` | string ≤64 | 写 | — |
| 邮箱 | `email` | string ≤512 | 写 | 不校验邮箱格式 |
| 办公电话 | `tel` | string ≤512 | 写 | 与 `mobile`、`landline` 相互独立 |
| 座机 | `landline` | string ≤64 | 写 | — |
| 职位 | `position` | string ≤512 | 写 | — |
| 微信号 | `weChat` | string ≤512 | 写 | — |
| QQ | `qq` | string ≤32 | 写 | — |
| 是否默认 | `isDefault` | bool | 写 | **不做唯一校验**，同一客户下可以有多个默认，按传入原样保存 |
| 备注 | `remark` | string ≤1024 | 写 | 列表 `keyword` 会模糊匹配它 |
| 发票可用 | `invoiceEnable` | bool | 写 | 供开票场景筛选 |
| 对账可用 | `statementEnable` | bool | 写 | 供对账场景筛选 |
| 是否禁用 | `isDisabled` | bool | 写 | 也可用 `SetDisabledAsync` 单独改 |
| **对接人id** | `userId` | long? | 写 | **可空**；`0`/负数/不传一律存 `null`（视为不指定）；有值时校验用户存在，否则报「对接人id错误」；**数据权限归属字段**，见第 3 节 |
| **对接人对象** | `user` | UserSimpleDto | **只读** | `userId` 为空时为 `null`；字段见第 5 节 |
| 创建时间 | `creationTime` | DateTime | 系统 | 基类 |
| 创建人id | `creatorUserId` | long? | 系统 | 基类 |
| **创建人昵称** | `creatorUserName` | string | **只读** | 取用户 `NickName` |
| 修改时间 | `lastModificationTime` | DateTime? | 系统 | 基类 |
| 修改人id | `lastModifierUserId` | long? | 系统 | 基类 |
| **修改人昵称** | `lastModifierUserName` | string | **只读** | 取用户 `NickName` |
| 是否删除 | — | bool | 系统 | 软删除（`ISoftDelete`），不出参 |

> **对接人 ≠ 创建人**：`userId` 是「谁负责对接这个联系人」，由用户主动选择，**不会**自动填成当前登录人； `creatorUserId` 是「谁录的这条数据」，由框架自动写。两者互不影响，数据权限只看 `userId`。

# 6. 接口逻辑

> 接口地址一律带 `Async` 后缀，见第 7 节。

| 接口 | 方法 | 数据权限口径 | 逻辑要点 |
| :-- | :-- | :-- | :-- |
| `GetPagedListAsync` | GET | 查询 | 筛选见 6.1；`AsNoTracking`；过滤后再排序分页（`totalCount` 已是过滤后的数量）；填充 `user`/`creatorUserName`/`lastModifierUserName` |
| `DetailAsync` | GET | 查询 | 先过数据权限再取数；取不到时分辨「数据不存在」与「没数据权限」报不同提示 |
| `AddAsync` | POST | 不判 | 校验客户存在、`name` 非空、`userId` 对应用户存在；`userId` 传 0 存 `null`；返回新 id |
| `EditAsync` | PUT | 编辑 | 校验客户存在、`name` 非空；按编辑口径取出联系人；逐字段赋值（**局部更新**，只 UPDATE 改动列）；`userId` 可改可清空 |
| `DeleteAsync` | DELETE | 编辑 | 只传 `id`（**不支持 `ids` 批量**）；软删除；**不做业务引用校验**（见 6.4） |
| `BatchSaveAsync` | POST | 编辑 | Id 存在则编辑、不存在则新增，**不处理删除**；见 6.2 |
| `SetDisabledAsync` | PUT | 编辑 | 只改 `isDisabled`，无返回体 |

## 6.1 列表筛选入参

`clientId`(Guid?)、`isDefault`(bool?)、`invoiceEnable`(bool?)、`statementEnable`(bool?)、`isDisabled`(bool?)、 **`userId`(long?，按对接人筛选)**、`keyword`（模糊匹配 `name` 或 `remark`）；分页 `pageIndex` / `pageSize`，排序 `sorting`。

- 所有筛选都是「不传则不筛」。
- **`userId` 是筛选、不是授权**：不传 `userId` 时返回的仍然只有「有权限的那些」（未指定对接人的 + 自己名下的）；传了别人的 `userId` 也不会因此看到他名下的联系人，两层是叠加的（先按筛选、再按数据权限）。

## 6.2 批量保存判定顺序

1. 校验 `clientId` 客户存在；`contacts` 为空直接返回空数组。
2. 逐项校验 `name` 非空（**任一项为空整批失败**）。
3. 取入参中 `id > 0` 的 id，一次性查出**本客户下**这些联系人。
4. **校验数据权限**：查出来的联系人里若有当前用户按编辑口径看不到的，**整批报错** 「没有联系人【xxx】的数据权限,不能保存」。（不能静默当成「库中不存在」走新增分支——那样会凭空多出一条重复联系人。）
5. 逐项 upsert：命中既有联系人 → 编辑（局部更新）；未命中（`id<=0` 或本客户下查不到）→ 新增。
6. 按输入顺序返回每项保存后的 id。

## 6.3 局部更新

编辑与批量保存都是「查出被 EF 跟踪的实体 → 只给改动属性赋值 → 依赖工作单元自动保存」， **不调用 `UpdateAsync`**，生成的 UPDATE 只含改动列。

## 6.4 删除的已知取舍

删除**不做**业务引用校验：联系人可能已被业务单据（`TransportOrder.ClientContactId`、 `SeaExport/AirExport.BookingAgentContactId`）和报价（`Quotation.ClientContactId`）引用，删掉后这些单据的 `clientContactId` 会指向一条已软删的记录，联系人对象回显为 `null`。这是 2026-08-09 起就有的既定取舍，本次未改。

另外：删除客户时（`ClientAdminAppService.DeleteAsync`）会按 `ClientId` 批量删掉其名下全部联系人，该处**不过联系人数据权限**——能删客户就能带走它的联系人。

# 8. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **卡点 1：填了对接人就只有指定人能在联系人列表里看到** 联系人填上对接人后，除对接人本人、数据权限「指定用户」勾了他的人、以及有「全部数据权限」的人以外，其他人在联系人列表里搜不到它，也改不动它。但**业务单据、对账、服务任务、报价上已选定的联系人照常显示**，不受对接人限制。

> [!IMPORTANT] **卡点 2：组织权限对本表无效** 只配「我的部门 / 我的公司」的主管**看不到**组员名下的联系人。要看必须配「指定用户」或「全部」。

> [!IMPORTANT] **卡点 3：批量保存是整批成败** 一份 `contacts` 里只要有一条没编辑权限，或有一条 `name` 为空，整批都不保存。
