# 1. 背景意图 (Background)

客户联系人自带手机、邮箱、办公电话、微信、QQ，是销售最核心的私有资源。此前这张表**完全没有可见性约束**：任何登录用户都能在联系人列表里翻到全部客户的全部联系人，也能只凭 id 改掉、删掉别人维护的联系人。

本次给联系人加一个**对接人 `UserId`**，把可见性收到「谁负责对接谁能看」：

| 对接人 `UserId` | 谁能看到                                               |
| :-------------- | :----------------------------------------------------- |
| 不填（`null`）  | 所有人（保持原样，不收紧）                             |
| 填了            | 只有该对接人本人，以及数据权限「指定用户」里勾了他的人 |
| 任意            | 有「全部数据权限」的人可见全部                         |

**范围只限联系人模块自己的接口**（列表/详情/编辑/删除/启用禁用/批量保存）。业务单据、客户对账、服务任务、报价里回显已选定的联系人**不过数据权限**，那些模块本次一行代码都没改：联系人已经落在单据上，属于单据自己的数据，可见性跟着单据走。对接人管的是「能不能在联系人列表里翻到、能不能改它」，不是「单据上能不能显示它」。

**明确不做的事**：本表**不继承** `DataPermissionFullAuditedEntity`，即**不加 `OrgId`**，所以组织权限（我的部门/我的公司/指定部门）不参与本表判定。这是需求定的——「填了对接人就只有指定人能看」，一旦掺进组织权限，同部门的人就都看得见了，等于没收紧。

# 3. 核心逻辑变更 (Core Logic Changes)

## 3.1 数据权限判定（新增）

`ClientContactDataPermissionFilterAsync`：

1. 取当前用户按 `manageType` 解析出的可见用户集合（`GetDataPermissionUserIdsAsync`）。
2. 命中「全部数据权限」直接原样返回。
3. 否则加条件：`UserId IS NULL OR UserId IN (可见用户集合)`。只解析出一个用户 id（最常见：没配数据权限的人只有自己）时改成 `UserId = @自己`，避免生成 `IN` 子查询。

**只用可见用户集合，丢掉 `orgIds`**——本表没有 `OrgId` 可比。

## 3.2 联系人自身七个接口的接入方式

| 接口 | 接法 | 口径 |
| :-- | :-- | :-- |
| 列表 | 筛选条件之后套过滤，再排序分页（所以 `totalCount` 已是过滤后的数量），并补 `AsNoTracking` | `Get` |
| 详情 | 先过过滤再取数；取不到时用 `ThrowContactNotVisibleAsync` 分辨「不存在」与「没权限」 | `Get` |
| 新增 | 不判权限（还没有这条数据），只校验 `userId` 对应用户存在 | — |
| 编辑 / 删除 / 启用禁用 | 统一改走 `GetContactForWriteAsync` 取可写实体 | `Edit` |
| 批量保存 | 查出本客户下待编辑联系人后，显式比对可编辑 id，缺任何一条整批报错 | `Edit` |

## 3.3 顺带修掉的两个既有问题

1. **编辑是全列 UPDATE**：原 `EditAsync` 结尾调了 `_clientContactRepository.UpdateAsync(clientContact)`，ABP 的 `Update` 内部会 `Entry(entity).State = Modified`，把整行所有列标成已改，生成全列 UPDATE。现改为「只给改动属性赋值 + 依赖工作单元自动保存」，与 `BatchSaveAsync` 一致。
2. **删除只按 id**：原 `DeleteAsync` 直接 `DeleteAsync(input.Id)`，既不判存在也不判权限。现改为先按编辑口径取出实体再删。

## 3.4 列表/详情补齐创建人与修改人昵称

`ClientContactDto` 之前只有 `creatorUserId` / `lastModifierUserId` 两个裸 id。本次补 `creatorUserName` / `lastModifierUserName`（取 `NickName`），与仓库其它模块口径一致。对接人对象、创建人昵称、修改人昵称**合并成一次用户查询**（`FillContactUsersAsync`），不要分三次查。

## 3.5 `userId` 为 0 一律当不指定

前端下拉清空时常送 `0`。`NormalizeContactUserIdAsync` 把 `null`/`0`/负数一律归一成 `null`，有值才去校验用户存在（不存在报「对接人id错误」）。**不要**让 `0` 落库——那会变成一条谁都看不见的联系人。

# 4. 避坑指南 (Pitfalls)

## 4.1 不要顺手给业务单据的联系人回显加上过滤

单据回显与保存校验（三种业务的 `EnsureClientContactBelongsAsync`、报价 Add/Edit 的联系人校验） **都不判数据权限**，这是有意的，别当成漏改去补。

一旦给回显加了过滤，接手别人单子的人就看不到该联系人对象；前端若因此把 `clientContactId` 清成 `null`，一保存就把单据上的联系人丢了。若再给保存校验也加过滤，则原样回传 id 会被判成「联系人id错误」， **整票业务从此改不动**。

防「选到别人名下联系人」靠的是**联系人列表查不出来**（选不到），不是靠回显或保存时拦。

## 4.2 批量保存不能把「无权限」当成「库中不存在」

`BatchSaveAsync` 原本的语义是「`Id>0` 但本客户下查不到 → 按新增处理」。如果直接把带权限过滤的查询结果丢进 `existingContacts`，无权限的那条就会命中「查不到」分支， **凭空多插一条重复联系人**。所以这里是「先无过滤查出来 → 再单独查一次可编辑 id 集合 → 有差集就整批报错」。

## 4.3 组织权限对本表无效，配权限时别配错

只配「我的部门 / 我的公司」的主管**看不到**组员名下的联系人（本表没有 `OrgId`）。要让主管看到，只有两条路：给他配「指定用户」把组员勾上，或者给「全部」。这是需求要的效果，不是 bug，测试提单前先看这一条。

## 4.4 存量数据不受影响

新列可空，存量全为 `NULL`，即全部保持所有人可见。上线后**可见性不变**，只有主动填了对接人的联系人才开始受限。所以「上线后联系人都不见了」这种现象不该出现，出现了先查是不是把 `0` 落库了（见 3.5）。

## 4.5 删除联系人仍不做业务引用校验

联系人可能已被业务单据、报价引用，删掉后这些单据的 `clientContactId` 指向一条已软删记录，联系人对象回显为 `null`。这是 2026-08-09 起的既定取舍，本次**没有**改动，别当成本次引入的问题。

# 6. 验收标准

| 序号 | 验收项 | 期望结果 |
| :-- | :-- | :-- |
| 1 | 新增联系人不传 `userId` | 落库为 `null`，任何账号都能在列表里看到 |
| 2 | 新增联系人传 `userId=0` | 落库为 `null`（不指定），不是 0 |
| 3 | 新增联系人传不存在的 `userId` | 报「对接人id错误」 |
| 4 | 甲把联系人对接人设为乙，用甲（无全部权限、未配指定用户含乙）查列表 | 该联系人不出现 |
| 5 | 同上，甲直接调详情 | 报「没有这条联系人的数据权限,不能查看」 |
| 6 | 同上，甲调编辑/删除/启用禁用 | 报「没有这条联系人的数据权限,不能编辑/删除/启用/禁用」 |
| 7 | 同上，用乙查列表/详情/编辑 | 全部正常 |
| 8 | 同上，用有「全部数据权限」的账号 | 全部正常 |
| 9 | 同上，用只配「我的部门」且与乙同部门的账号 | **看不到**（本表不参与组织权限） |
| 10 | 列表传 `userId=乙` 用甲调用 | 仍看不到乙名下的（筛选与权限叠加） |
| 11 | 批量保存里混入一条乙名下的联系人，用甲调用 | 整批不保存，报「没有联系人【xx】的数据权限,不能保存」，且**不会**新增重复联系人 |
| 12 | 业务单据（海运出口/进口、空运出口）详情里选的是乙名下联系人，用甲查看 | **照常返回** `clientContact` 对象与联系方式，不受对接人影响 |
| 13 | 客户对账选费用、海运出口服务任务、报价列表/详情 | 同第 12 条，均照常返回 |
| 14 | 编辑联系人只改手机号 | 生成的 UPDATE 只含改动列（局部更新） |
| 15 | 列表/详情返回 | 含 `user`（对接人对象）、`creatorUserName`、`lastModifierUserName` |
| 16 | 编辑时把 `userId` 传 `null` | 对接人被清空，改回所有人可见 |
