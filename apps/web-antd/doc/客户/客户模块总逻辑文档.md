# 3. 客户可见性规则（全部客户，按行判断）

- 涉及字段：`Client.IsShared`（共享类型）、`Client.UserId`（**所属人**，非创建人 `CreatorUserId`）、`Client.OrgId`（**归属公司id**）、干系人子表 `ClientStakeholder.UserId`。
- **对全部客户生效**：不按行业类别区分，含 `p`（委托单位）与不含 `p` 的客户一视同仁。
- 「可见」条件（满足其一即可见）：

| # | 条件 | 说明 |
| :-- | :-- | :-- |
| 1 | 拥有「全部数据权限」 | 不受共享类型限制，**非本公司的客户也能看**（全部就是全部） |
| 2 | `isShared == 2` 共享所有人 | 所有人可见 |
| 3 | `isShared == 1` 共享本公司 且 `orgId` 是当前用户所属公司之一 | 「本公司」判定见下 |
| 4 | `userId` 在当前用户数据权限可见用户集合内 | 所属人是自己/下属 |
| 5 | `orgId` 在当前用户组织数据权限（本组织及所有下属组织）内 | 我的部门 / 我的公司 / 指定部门 解析出来的组织集合 |
| 6 | 该客户干系人 `ClientStakeholder.UserId` 在可见用户集合内 | 干系人是自己 |

- **共享类型只负责放宽范围**：`isShared == 0`（不共享）时退回第 4/5/6 条——有数据权限或干系人关联才能看到。
- **「本公司」判定**：`Client.OrgId` 存的就是公司 id，直接和当前用户所属公司 id 比。当前用户所属公司 = 其每条组织链上的**全部公司节点（含上级公司）**。例：用户挂在「山东-青岛分公司-业务部」下，他属于青岛分公司也属于山东，共享到山东的客户他能看到；反过来只挂在山东公司节点下的人，看不到只共享给青岛分公司的客户（「上级看下级」交给组织数据权限「我的公司→本组织及下属」）。
- **统一入口**：`CsprojBuilderAppServiceBase.ClientListDataPermissionFilterAsync`。`ClientAdmin` 与 `Client`（含分组接口）均调用同一方法；所属公司集合由同一基类的 `GetMyCompanyOrgIdsAsync` 解析（走用户组织路径缓存，不额外查库）。
- **历史豁免已取消**：以前「`IndustryCategories` 不含 `p`」的客户一律不受限，是因为那时 `OrgId` 可空、非委托单位普遍没录归属组织，一过滤就全被挡掉；现在新增/编辑强制必填归属公司，所有客户都能按公司判定。
  > **测试注意**：历史数据中 `OrgId` 为空、或 `OrgId` 存的是部门而非公司的客户，若所属人不在可见用户集合内、也没共享，改动后**不再出现在列表里**，需要补录归属公司或把共享类型调成共享本公司/共享所有人。

# 3.5 客户审核（状态、工作流、可见性收窄）

客户建档要走审批。审批链路复用平台通用工作流（`WorkFlow` 定义 + `TaskItem` 任务 + `WorkFlowInstance` 实例）， **一条客户一个独立任务、一条独立工作流**——一次批量提交 10 条客户就是 10 个任务 10 条工作流，互不影响、各自推进。

## 3.5.1 客户审核状态 `clientStatus`

不可空，新建即 `0` 未提交。

| 值 | 名称 | 说明 |
| :-- | :-- | :-- |
| 0 | 未提交 | 录入状态。可编辑、可提交审核 |
| 1 | 待审核 | 已提交，审批流程进行中 |
| 2 | 已通过 | 审核通过。不可直接编辑，只能走申请修改 |
| 3 | 已驳回 | **业务上等同未提交**：可编辑、可重新提交审核 |
| 4 | 申请修改 | 已通过的客户发起了修改申请，审批进行中 |
| 5 | 申请修改驳回 | **业务上等同已通过**：客户本身仍是审核通过的，只是这次修改申请没批 |

> 两组等价关系（3≈0、5≈2）在代码里到处成对出现。**判「能不能做某操作」时必须两个一起判**，只判其中一个必然出现「驳回后改不了」或「申请修改驳回后再也申请不了修改」这类问题。

## 3.5.2 状态流转

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| — | 新增客户 / Excel 导入 | 未提交(0) | 一律录入态，不自动提交 |
| 未提交(0) / 已驳回(3) | 录入人编辑 | 不变 | 只有这两个状态能走编辑接口 |
| 未提交(0) / 已驳回(3) | 录入人提交审核（支持批量） | 待审核(1) | 新建一条 `SubmitClient` 任务与它自己的工作流 |
| 未提交(0) / 已驳回(3) | 提交审核，但工作流所有节点都是「直接通过」 | 已通过(2) | 不生成工作流实例，任务直接落通过 |
| 待审核(1) | 录入人撤回（支持批量） | 未提交(0) 或 已驳回(3) | 该轮任务与工作流实例一并删除；之前被驳回过的退回已驳回 |
| 待审核(1) | 工作流走完最后一级且通过 | 已通过(2) | 中间级通过只推进工作流，不改客户状态 |
| 待审核(1) | 任意一级审核人驳回 | 已驳回(3) | 工作流实例置拒绝 |
| 已通过(2) / 申请修改驳回(5) | 录入人申请修改（**只能单条**） | 申请修改(4) | 新建一条 `ModifyClient` 任务与它自己的工作流 |
| 申请修改(4) | 撤回（支持批量） | 已通过(2) 或 申请修改驳回(5) | 同上，之前被驳回过的退回申请修改驳回 |
| 申请修改(4) | 审核通过 | 已通过(2) | **此时才**把快照落到客户与全部子表上 |
| 申请修改(4) | 审核驳回 | 申请修改驳回(5) | 客户数据一个字不动 |
| 已通过(2) / 申请修改驳回(5) | 审核人通过后驳回 | 已驳回(3) | 仅限在该任务里投过通过票的人 |

## 3.5.3 任务与工作流

| 项 | 口径 |
| :-- | :-- |
| 任务载体 | `TaskItem`，`TaskBaseId` 恒为 `null`（客户没有需要汇总的主任务），`EntityId` = 客户id，`FrightModule = Client` |
| 任务类型 | `SubmitClient(90)` 客户提交、`ModifyClient(91)` 客户申请修改 |
| 工作流定义 | **要配两条**：`SubmitClient` 一条、`ModifyClient` 一条。缺哪条，对应的提交就被 `未配置或未启用XX工作流，无法提交审核` 拦下 |
| 工作流实例 | 一条任务一条 `WorkFlowInstance`，挂 `TaskItemId`，`TaskBaseId` 与 `ParentInstanceId` 都为 `null` |
| 每轮新建 | 驳回后重新提交是**新建**一条任务，旧任务与旧工作流实例原样保留留档；所有取任务的地方一律按 `CreationTime` 倒序取最新那一条（`TaskItem.Id` 是随机 Guid，不能当创建顺序用） |
| 历史怎么看 | 审核列表只显示最新那一轮；**全部轮次要调审核详情 `GetAuditDetailAsync`**，它按客户id返回每一轮的提交人、终审人、审批意见、逐级明细，申请修改的轮次还带那一轮的 `modifyTo` / `modifyFrom` |
| 审核人来源 | 支持按用户、按角色。**不支持用户属性**——客户上的销售/客服/操作是干系人，不是审批语义 |
| 无审核人 | 所有节点都配成「直接通过」时不生成实例，直接落终态（提交→已通过；申请修改→当场把修改落到客户上） |

## 3.5.4 工作流连线条件（客户提交与客户变更共用同一套）

| 枚举 | 条件 | 取值来源 | 支持的比较符 |
| :-- | :-- | :-- | :-- |
| `ClientUserId`(90001) | 客户所属人 | `Client.UserId`（建档时写入，不是实际点提交的人） | 等于 / 不等于 |
| `ClientOrgID`(90002) | 客户归属公司 | `Client.OrgId` 及其各级**上级**组织 | 属于 / 不属于 |
| `ClientClientType`(90003) | 客户性质 | `Client.ClientType`，**为空时该条件一律判为不满足** | 等于 / 不等于 |
| `ClientIsShared`(90004) | 共享类型 | `Client.IsShared` | 等于 / 不等于 |

配置端会拦：这四个条件只能配在 `SubmitClient` / `ModifyClient` 类型的工作流上，配到别处报 `非客户任务不可输入客户条件`。

## 3.5.5 申请修改的快照

| 列 | 存什么 |
| :-- | :-- |
| `TaskItem.Info` | `{ client: 要修改为的客户全量字段, applyRemark: 申请原因 }`。**全量**指含地址、账期、干系人、对账人、优质航线等全部子表，口径与编辑接口入参完全一致 |
| `TaskItem.OriginalInfo` | 发起申请那一刻客户的原值（同样是一份完整的编辑入参结构），供审核人逐字段对比与事后留档 |
| `TaskItem.Remark` | **审核意见**。申请原因不能写这一列——审核落结论时会把它覆盖掉，所以申请原因跟着 `Info` 走 |

两列都是 `nvarchar(max)`（2026-09-21 去掉了 4096 的长度注解，物理列本来就是 max），客户全量快照塞得下。

> `OriginalInfo` **只用于展示与留档，永远不会被反向应用回客户**。通过后驳回时不做数据回滚：快照只能还原改过的行，还不出这次删掉的子表行，半吊子回滚出来的客户既不是改前的也不是改后的，比不回滚更难排查。

## 3.5.6 业务侧选客户的可见性收窄

`ClientAppService` 三个选客户的接口（分页列表、按行业类别分组、失信与干系人摘要）在第 3 节可见性之上**再收窄一层**：

读 `Sys_Settings` 里当前租户的配置 **`可搜索未审核通过客户`**（`TenantId` = 当前租户 且 `UserId` 为空）：

- 值是 `true`（忽略大小写、去空格）→ 不收窄，与以前完全一样；
- 其余情况（配成 `false`、配了别的值、**压根没配过**）→ 只返回 `已通过(2)` 与 `申请修改驳回(5)` 的客户。

这三个接口**不接收 `clientStatus` 筛选**。`ClientQueryDto` 上虽然有这个字段，但只有 `ClientAdmin` 的列表认它；业务侧能选到哪些状态的客户完全由上面这个配置决定，不给调用方留一个自己传 `clientStatus=0` 就能把未审核客户捞出来的口子。

前端同样调 `TenantConfig/DetailAsync?name=可搜索未审核通过客户` 取这个开关：**取到 `true` 时不显示提交审核按钮** （能直接搜到未审核客户就等于没在用客户审核，这时候摆个提交按钮只会误导）。宿主用户（没有租户）不受该配置约束。

> [!IMPORTANT] **[卡点：上线前必须先处理这个开关，否则业务侧一个客户都选不出来]** 存量客户的 `clientStatus` 默认全是 `0` 未提交。只要该配置不是 `true`，上线当天业务单据里就选不到任何客户。上线前**二选一**：要么把 `可搜索未审核通过客户` 配成 `true`（等于暂不启用客户审核），要么先把存量客户的 `ClientStatus` 刷成 `2`（已通过）。

# 5. 只读计算字段规则（列表/详情共 8 个字段）

列表 `GetPagedListAsync`、详情 `DetailAsync`（及结算银行接口）额外返回委托单位 4 字段 + 供应商 4 字段。均按 **ETD** 实时计算，**不入库**（`App_Clients` 已删除 `YearTeu`/`YearTicketCount` 列）。

## 5.1 委托单位（`Client*`，`TransportOrder.ClientId = 客户Id`）

| 字段 | 规则 |
| :-- | :-- |
| `clientCoopSince` 首次合作 | `ETD` 有值订单的**最早 ETD** |
| `clientLastTxnTime` 最近交易 | `ETD` 有值订单的**最大 ETD** |
| `clientYearTicketCount` 年票数 | `ETD` 落在**本自然年** `[今年1/1, 明年1/1)` 的订单**数量** |
| `clientYearTeu` 年TEU | 上述今年订单的 `OrderCtn` 关联 `CtnCode.TEU` **求和** |

## 5.2 供应商（`Supplier*`，`SeaExport.BookingAgentId = 客户Id`）

`SeaExport.Id` 与 `TransportOrder.Id` 相同；取对应运输订单 `ETD` 与箱型，规则与委托单位一致：

| 字段 | 规则 |
| :-- | :-- |
| `supplierCoopSince` 首次合作 | 订舱代理=本客户且 `ETD` 有值的**最早 ETD** |
| `supplierLastTxnTime` 最近交易 | 同上，**最大 ETD** |
| `supplierYearTicketCount` 年票数 | 今年 ETD 订单**数量** |
| `supplierYearTeu` 年TEU | 今年订单 `OrderCtn`→`CtnCode.TEU` **求和** |

- 新增/编辑**不可填写**以上 8 个字段。
- 无匹配订单时：合作时间/交易时间为 `null`，年 TEU/年票数为 `0`。
- 性能：`CtnCode` 小表全量入内存字典；`OrderCtn` 仅查 `TransportOrderId`+`CtnCodeId` 两列后内存汇总。

# 7. 删除引用校验

`DeleteAsync` 前置校验，命中即禁止删除并提示：

| 引用来源 | 条件 | 提示 |
| :-- | :-- | :-- |
| 入库单 `EnterWarehouse` | `SupplierId` 命中待删客户 | 合作客户已被入库单关联 不可删除 |
| 贸易商合同 `Agreement` | `AgreementType==2` 且 `SettlementId` 命中 | 合作客户已被贸易商合同关联 不可删除 |
| 海运出口 / 空运出口 | `BookingAgentId` 命中 | 该合作客户已被【…】模块引用,禁止删除 |
| 海运进口 | `TerminalId` 命中 | 同上 |

校验通过后要显式清掉的从属数据：账期及其三张关联子表与附件、开票信息及银行、联系人、地址、干系人、对账人、优质航线、排除服务项、客户附件关联，以及**该客户全部轮次的审核任务 `TaskItem` 与工作流实例 `WorkFlowInstance` / `WorkFlowInstanceItem`**。审核痕迹不清干净，审核列表里会留下指向已删客户的幽灵行。
