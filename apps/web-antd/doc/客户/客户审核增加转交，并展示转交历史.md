## 目标

客户审核列表/详情里，当前登录人待审核的行要能把这条审核转给另一个人。转交后自己从待办消失，对方出现在待办。

**必须把转交历史做出来。** 审核路径上要能看到这条名额「谁转给了谁、什么时候转的」，连转多次按时间排。不要只接转交接口、不画历史。

接口是工作流通用的（费用/提单/提成单也走这个），本次先接客户审核页。

## 接口

```
POST /api/services/app/WorkFlowInstanceAdmin/TransferAsync
```

地址里的 `Async` **不能省**。登录即可，不要另外判 `Admin.Client.Audit`。

入参 body：

```json
{ "workFlowInstanceItemId": "明细id", "toUserId": 10002 }
```

- `workFlowInstanceItemId`：当前登录人待审核的那条工作流明细 id
- `toUserId`：被转交人用户 id

无出参。成功后重新拉审核列表/详情，不要本地猜状态，转交历史也从接口重新取。

## 明细 id 从哪拿

客户审核列表/详情行上已有 `workFlowInstance.levelGroup[].itemList[]`。

取 **当前登录人**且 `taskStatus == 0`（待他审）的那条 `id`，不要传客户 id，也不要传 `taskItem.id`。

会签同一级有多个人，只能转自己那一条。

## 按钮

- 只在审核列表/详情里 `myTaskStatus == 0`（待我审核）的行出现「转交」
- 跟「审核/驳回」同条件
- 选人后调上面接口

## 转交历史（必须做）

挂在该条审核人明细上，不另开接口。列表能看到即可，详情里也要有。

数据在 `itemList[].transfers`，按时间从早到晚。从未转过是 `[]`，不要当错误，也不要画一条空履历。

每一跳展示：

| 字段               | 说明     |
| :----------------- | :------- |
| `fromUserNickName` | 转出人   |
| `toUserNickName`   | 被转交人 |
| `creationTime`     | 转交时间 |

同一名额 A→B→C 就是两条，按数组顺序画。一级、二级各挂在自己那条 `itemList` 下面，不要把各级拼成一条大时间线。

建议文案：`张三 转交给 李四 2026-09-22 19:20`。连转就多行。

转交成功后刷新，新的一跳要马上出现在这条明细的历史上。

## 规则（后端已拦，前端接住报错即可）

| 提示                              | 情况                             |
| :-------------------------------- | :------------------------------- |
| 只能转交自己待审核的任务          | 不是自己的名额，或状态不是待审核 |
| 不能转交给自己                    | `toUserId` 是当前登录人          |
| 被转交人已在本级审核人中,不可转交 | 会签/或签本级已经有这个人        |
| 工作流已结束,不可转交             | 实例已经通过或拒绝               |
| 被转交人不存在                    | 用户 id 查不到                   |

## 不要做

- 不要调 `WorkFlowInstanceAdmin/GetAsync` 拼客户审批历史（客户用 `ClientAdmin/GetAuditDetailAsync`）
- 不要用海出服务项任务的 `SeServiceTaskAdmin/TransferAsync`，那是操作工作台，不是审核转交
- 不要自己拼转交历史，只展示接口返回的 `transfers`

## 验收标准

1. 待我审核的客户能转给别人；转完后这一行从我的待办消失。
2. 被转交人登录后能在审核列表看到待他审，能审核/驳回。
3. 还没轮到我、我已经审过、别人的任务不出转交按钮。
4. 不能转给自己；会签同级已有的人不能再转给他。
5. **审核路径上能看到转交历史**：谁转给谁、何时；从未转过的明细不显示空历史。
6. **连转多次**（A→B→C）按时间从早到晚全部展示，刷新后最新一跳也在。
