# 背景意图

业务表上的**应结日期**和**结算方式**是保存业务当时按账期规则算出来的快照，之后改账期规则不会回刷历史业务。于是出现「客户本该月结，但下单那会儿还没配账期，一批老单子全是票结」的情况，只能靠改单据一票票救。

本次给账期加一个手动回刷入口：选中一条账期，按它的规则把该客户**票结**的历史业务重算一遍。

# 新增接口

### `POST /api/services/app/ClientBillingPeriodAdmin/SyncBillingPeriodAsync`

- **权限**：`Admin.Client.BillingPeriod.Sync`（同步账期）
- **入参** Body `IdDto`

| 字段  | 类型     | 必填 | 说明                                         |
| :---- | :------- | :--: | :------------------------------------------- |
| `id`  | `long`   |  是  | 账期 id，客户由它带出，前端不用再传 clientId |
| `ids` | `long[]` |  否  | 本接口不用                                   |

- **出参** `result`：`int`，实际改动的业务票数。`0` 表示没有需要回刷的业务（不是失败）。
- **报错**：账期 id 找不到 → 「账期记录不存在」。

# 账期权限独立（不兼容变更）

账期原先共用客户的 `Admin.Client.Edit` / `Admin.Client.Get`，本次拆成自己的一套，挂在 `Admin.Client`（合作客户基本信息）下：

| 权限 | 汉化 | 管到哪些接口 |
| :-- | :-- | :-- |
| `Admin.Client.BillingPeriod` | 合作客户账期 | 父节点，不直接判 |
| `Admin.Client.BillingPeriod.Get` | 查看 | `GetListAsync`、`GetPagedListAsync`、`DetailAsync` |
| `Admin.Client.BillingPeriod.Add` | 添加 | `AddAsync` |
| `Admin.Client.BillingPeriod.Edit` | 编辑 | `EditAsync` |
| `Admin.Client.BillingPeriod.Delete` | 删除 | `DeleteAsync` |
| `Admin.Client.BillingPeriod.Sync` | 同步账期 | `SyncBillingPeriodAsync` |

**前端要做的事**：账期页面的按钮显隐从原来的客户增删改查权限，改判上面这组权限；同步账期按钮判 `Admin.Client.BillingPeriod.Sync`。

**上线要做的事**：新权限不会自动授给已有角色，需要在「角色/用户 → 权限」里重新勾选，否则账期接口一律 403。

# 核心逻辑变更

处理范围是三层筛选，任一层不过就跳过：

| 层 | 条件 | 不过的结果 |
| :-- | :-- | :-- |
| 账期本身 | 当前生效：长期有效，或落在生效/失效区间内（两端为空表示该端不限制） | 直接返回 `0`，一条都不动 |
| 业务范围 | 该账期客户下 `settlementType=0`（票结）的业务 | 月结/约定天数的业务不动 |
| 账期限定 | 业务类型、销售、组织机构、业务来源四个维度**全部**命中该账期；账期对应子表为空表示该维度不限定 | 跳过该票 |

命中后用与业务新增/编辑同一套算法重算（基准时间取业务开船日期 `ETD`，没填则取当前时间），算出来与库里一致的跳过，不一致的才写回应结日期与结算方式。

# 避坑指南

1. **返回 0 不等于失败**：账期未生效、客户没有票结业务、或算出来和原值一样，都会返回 0。
2. **只回刷票结**：票结既是「配了票结规则」也是「没匹配上任何规则」的兜底值，只有它可能是漏网单；月结/约定天数的业务属于当时确实命中了规则，本接口不动，避免把已对账的单据日期改飞。
3. **重算后可能还是票结**：规则本身是票结、只是配了 `addDays` 时，结算方式不变、应结日期变，这也会计入返回票数。
4. **没有开船日期的业务**：基准时间退化为当前时间，这类业务每次同步都可能算出新的应结日期，别把它当成 bug。
5. **不改会计期间**：本接口只写应结日期与结算方式，`accountDate` 等字段不动。
