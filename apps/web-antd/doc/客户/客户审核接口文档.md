# 0. 速查

| 接口 | 方法 | 地址 | 权限 |
| :-- | :-- | :-- | :-- |
| 提交审核（批量） | POST | `/api/services/app/ClientAdmin/SubmitAuditAsync` | `Admin.Client.Edit` |
| 申请修改（单条） | POST | `/api/services/app/ClientAdmin/ModifyAuditAsync` | `Admin.Client.Edit` |
| 撤回（批量） | POST | `/api/services/app/ClientAdmin/WithdrawAuditAsync` | `Admin.Client.Edit` |
| 审核（批量，含通过后驳回） | POST | `/api/services/app/ClientAdmin/AuditAsync` | `Admin.Client.Audit` |
| 审核任务分页列表 | GET | `/api/services/app/ClientAdmin/GetAuditPagedListAsync` | `Admin.Client.Audit` |
| 审核任务详情（含审批历史） | GET | `/api/services/app/ClientAdmin/GetAuditDetailAsync` | `Admin.Client.Audit` |

> 地址里的 `Async` 后缀**不能省**，本项目的动态 API 不会剥掉它。

## 0.1 两个必备枚举

**客户审核状态 `clientStatus`**（客户列表、详情、审核列表行里都有）

| 值  | 名称         | 前端判断                              |
| :-- | :----------- | :------------------------------------ |
| 0   | 未提交       | 可编辑、可提交审核                    |
| 1   | 待审核       | 可撤回                                |
| 2   | 已通过       | 可申请修改                            |
| 3   | 已驳回       | **与 0 完全同权**：可编辑、可提交审核 |
| 4   | 申请修改     | 可撤回                                |
| 5   | 申请修改驳回 | **与 2 完全同权**：可申请修改         |

**任务状态 `taskStatus` / `myTaskStatus`**：`0` 审核中（待我审核）、`1` 驳回（我已驳回）、`2` 通过（我已通过）。 `myTaskStatus` 为 `null` 代表还没轮到我。

## 0.2 按钮可用性

| 按钮 | 出现条件 |
| :-- | :-- |
| 提交审核 | 租户配置 `可搜索未审核通过客户` **不是 `true`**，且选中客户全部是 `clientStatus ∈ {0,3}` |
| 申请修改 | 选中**恰好一条**，且 `clientStatus ∈ {2,5}` |
| 撤回 | 选中客户全部是 `clientStatus ∈ {1,4}` |
| 审核 / 驳回 | 审核列表里 `myTaskStatus == 0` 的行 |
| 通过后驳回 | 审核列表里 `taskStatus == 2` 且 `myTaskStatus == 2` 的行（走同一个审核接口，`success` 传 `false`） |

> 配置开关通过 `GET /api/services/app/TenantConfig/DetailAsync?name=可搜索未审核通过客户` 取，返回 `null` 代表没配过。取到 `value === "true"` 时**不显示提交审核按钮**——能直接搜到未审核客户就等于没在用客户审核。

# 1. 提交审核

`POST /api/services/app/ClientAdmin/SubmitAuditAsync`

一条客户生成一个独立任务、一条独立工作流。提交 10 条就是 10 个任务，各自走各自的审批路径，互不影响。

## 1.1 入参

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `ids` | Guid[] | 是 | 客户id。会自动去空去重；一条有效的都没有报「请选择合作客户」 |

```json
{ "ids": ["3f2a...", "88c1..."] }
```

## 1.2 出参

`Guid[]`，本次生成的任务id，顺序与入参去重后的顺序一致。

## 1.3 报错

| 提示 | 触发 |
| :-- | :-- |
| 请选择合作客户 | `ids` 为空或全是空 Guid |
| 合作客户不存在 | 有 id 查不到 |
| 客户XX当前为YY,不可提交审核 | 有客户不是未提交/已驳回 |
| 未配置或未启用客户提交工作流，无法提交审核 | 没有启用中的 `SubmitClient` 工作流 |
| 客户数据不满足任何起始审批条件 | 工作流起始线一条都没匹配上，也没配默认线 |
| 未找到符合条件的审核人,请检查工作流节点X | 某个节点解析不出任何审核人 |
| 客户工作流不支持用户属性审核 | 节点配了按用户属性取审核人 |

# 2. 申请修改

`POST /api/services/app/ClientAdmin/ModifyAuditAsync`

**只支持单条**。提交的是客户的**全量**信息（含地址、账期、干系人、对账人、优质航线等全部子表），结构与客户编辑接口 `ClientAdmin/EditAsync` 的入参**完全一致**——前端直接复用编辑表单的提交体即可。子表按整份替换处理：入参里没出现的行，审核通过后就会被删掉。

## 2.1 入参

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `client` | ClientEditDto | 是 | 要修改为的客户完整信息，字段清单见《客户模块总逻辑文档.md》第 4 节 |
| `applyRemark` | string ≤4096 | 是 | 申请修改原因，为空报「申请修改原因不能为空」 |

```json
{
  "client": {
    "id": "3f2a...",
    "name": "青岛某某",
    "orgId": 6,
    "addresses": [],
    "billingPeriods": []
  },
  "applyRemark": "客户换了开票抬头"
}
```

## 2.2 出参

`Guid`，本次生成的任务id。

## 2.3 报错

| 提示 | 触发 |
| :-- | :-- |
| 输入不能为空 | `client` 没传 |
| 申请修改原因不能为空 / 申请修改原因长度不能超过4096个字符 | `applyRemark` 不合法 |
| 输入合作客户id错误 | `client.id` 查不到 |
| 客户当前为XX,不可申请修改 | 客户不是已通过/申请修改驳回 |
| 未配置或未启用客户变更工作流，无法提交审核 | 没有启用中的 `ModifyClient` 工作流 |

> 工作流所有节点都配成「直接通过」时，这次修改会**当场落到客户上**，客户状态直接回到已通过。

# 3. 撤回

`POST /api/services/app/ClientAdmin/WithdrawAuditAsync`

提交审核与申请修改共用这一个接口，支持批量。只要还没出最终结论就能撤，流程走到第几级都行。

撤回只删**最新那一轮**的任务与工作流实例，更早几轮留档不动。客户退回提交前的状态：

| 撤的是   | 之前被同类任务驳回过 | 退回到          |
| :------- | :------------------- | :-------------- |
| 提交审核 | 否                   | 未提交(0)       |
| 提交审核 | 是                   | 已驳回(3)       |
| 申请修改 | 否                   | 已通过(2)       |
| 申请修改 | 是                   | 申请修改驳回(5) |

## 3.1 入参

| 字段  | 类型   | 必填 | 说明                 |
| :---- | :----- | :--- | :------------------- |
| `ids` | Guid[] | 是   | 客户id，自动去空去重 |

## 3.2 出参

`bool`，恒 `true`。

## 3.3 报错

| 提示                    | 触发                                 |
| :---------------------- | :----------------------------------- |
| 客户XX当前为YY,不可撤回 | 有客户不是待审核/申请修改            |
| 审核任务不存在          | 有客户查不到任务                     |
| 审核已有结果,不可撤回   | 最新那一轮任务已经出了通过或驳回结论 |

# 4. 审核

`POST /api/services/app/ClientAdmin/AuditAsync`

**通过、驳回、通过后驳回三种动作与两种任务类型（客户提交 / 客户申请修改）全部合并在这一个接口里**，单条批量也是同一个接口。后端按每条客户**最新那一条任务**的状态自己分辨走哪条路：

- 任务还在审核中 → 常规审核，按工作流逐级推进，走完最后一级才落到客户上；
- 任务已经通过而 `success` 传了 `false` → 通过后驳回，只有在这条任务里投过通过票的人能驳，客户退回**已驳回(3)**。

批量一次会覆盖多条客户，当前登录人未必是每一条的当前审核人，**轮不到自己的那几条会被跳过而不是整批失败**；一条都轮不到才报「没有待您审核的客户」。

## 4.1 入参

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `ids` | Guid[] | 是 | 客户id（**不是任务id**），自动去空去重 |
| `success` | bool | 是 | `true` 通过、`false` 驳回 |
| `remark` | string ≤4096 | 驳回时必填 | 审核意见。通过时可不填 |

```json
{ "ids": ["3f2a..."], "success": false, "remark": "营业执照没传" }
```

## 4.2 出参

`bool`，恒 `true`。

## 4.3 结论落到客户上的规则

| 任务类型 | success | 客户状态 | 客户数据 |
| :-- | :-- | :-- | :-- |
| 客户提交 | true | 已通过(2) | 不变 |
| 客户提交 | false | 已驳回(3) | 不变 |
| 客户申请修改 | true | 已通过(2) | **把快照落到客户与全部子表上** |
| 客户申请修改 | false | 申请修改驳回(5) | 一个字不动 |
| 任意（通过后驳回） | false | 已驳回(3) | 不变，**不回滚已经合并进去的修改** |

## 4.4 报错

| 提示 | 触发 |
| :-- | :-- |
| 驳回原因不能为空 | `success=false` 且 `remark` 为空 |
| 没有待您审核的客户 | 选中的客户里一条都轮不到当前登录人 |
| 客户XX当前为YY,不可驳回 | 通过后驳回时客户已经不是审核通过态 |
| 客户XX不在待审核状态,不可审核 / 客户XX不在申请修改状态,不可审核 | 任务与客户状态对不上（并发操作） |

# 5. 审核任务分页列表

`GET /api/services/app/ClientAdmin/GetAuditPagedListAsync`

**一条客户一行**，挂该客户最新一条任务。客户提交与客户申请修改两种任务都在这一个列表里，靠行上的 `taskType` 区分。

只返回与当前登录人有关的行：最新那一轮任务的工作流明细里出现过当前登录人。 **不做客户数据权限过滤**——审核人本来就要能看到不属于自己的客户。

## 5.1 入参（query）

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `myAuditStatus` | int? | 我的审核状态。`0` 待我审核、`2` 我已审核。不传=两者并集（含还没轮到我的） |
| `taskType` | int? | 任务类型。`90` 客户提交、`91` 客户申请修改。不传=两种都要 |
| `taskStatus` | int? | 任务状态。`0` 审核中、`1` 驳回、`2` 通过 |
| `clientStatus` | int? | 客户审核状态 `0`~`5` |
| `keyword` | string | 模糊匹配客户简称/代码/全称/英文名 |
| `orgId` | long? | 客户归属公司，按「本组织+其所有下属组织」筛 |
| `submitTimeStart` | DateTime? | 提交时间起，含当天 |
| `submitTimeEnd` | DateTime? | 提交时间止，含当天 |
| `pageIndex` | int | 页码 |
| `pageSize` | int | 每页条数 |

## 5.2 出参：分页包装

| 字段         | 类型            | 说明                   |
| :----------- | :-------------- | :--------------------- |
| `totalCount` | int             | 总条数                 |
| `items`      | ClientTaskDto[] | 行列表，按提交时间倒序 |

## 5.3 出参：行 `items[]`

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | Guid | **任务id**（不是客户id，客户id在 `client.id`） |
| `taskType` | int | `90` 客户提交、`91` 客户申请修改 |
| `taskStatus` | int | `0` 审核中、`1` 驳回、`2` 通过 |
| `submitTime` | DateTime | 提交时间 |
| `submitUserName` | string | 提交人昵称 |
| `auditTime` | DateTime? | 终审时间，审核中为 null |
| `auditUserName` | string | 终审人昵称，审核中为 null |
| `remark` | string | 审核意见，审核中为 null |
| `applyRemark` | string | 申请修改原因。**仅 `taskType==91` 有值** |
| `myTaskStatus` | int? | 我在这条任务上的状态：`0` 待我审核、`1` 我已驳回、`2` 我已通过；`null` 代表还没轮到我 |
| `client` | ClientSimpleDto | 客户当前信息，见 5.4 |
| `modifyTo` | ClientEditDto | 要修改为的客户全量信息。**仅 `taskType==91` 有值** |
| `modifyFrom` | ClientEditDto | 发起申请那一刻客户的原值。**仅 `taskType==91` 有值**，与 `modifyTo` 逐字段比对即为本次改动 |
| `workFlowInstance` | 对象 | 审批路径，见 5.5。**工作流算不出审核人而直接通过时为 null** |

## 5.4 出参：`items[].client`

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | Guid | 客户id |
| `name` | string | 客户简称 |
| `code` | string | 客户代码 |
| `fullName` | string | 客户全称 |
| `enName` | string | 客户英文名 |
| `isDishonest` | bool | 是否失信 |
| `dishonestRemark` | string | 失信备注 |
| `enterpriseType` | int? | 企业类型（前端自定义枚举） |
| `clientType` | int? | 客户性质 `0` 同行、`1` 直客 |
| `isShared` | int | 共享类型 `0` 不共享、`1` 共享本公司、`2` 共享所有人 |
| `clientStatus` | int | 客户审核状态 `0`~`5` |
| `taxRate` | decimal? | 税率(%) |
| `orgId` | long? | 归属公司id |
| `orgs` | 对象[] | 归属组织串，顶→底，元素为 `{ id, displayName, ... }` |

> 行上只带客户简要信息。要看客户完整档案调 `GET /api/services/app/ClientAdmin/DetailAsync?id=客户id`。审申请修改时不用调详情：`modifyFrom` 与 `modifyTo` 已经是完整的前后两份。

## 5.5 出参：`items[].workFlowInstance`

| 字段         | 类型   | 说明                         |
| :----------- | :----- | :--------------------------- |
| `id`         | Guid   | 工作流实例id                 |
| `status`     | int    | `0` 活动、`1` 通过、`2` 拒绝 |
| `levelGroup` | 对象[] | 按层级分组的审批路径，见下   |

`levelGroup[]`：

| 字段         | 类型   | 说明                      |
| :----------- | :----- | :------------------------ |
| `level`      | int    | 层级，从 1 开始           |
| `passMethod` | int    | 本级通过方式（与签/或签） |
| `itemList`   | 对象[] | 本级的审核人明细，见下    |

`levelGroup[].itemList[]`：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | Guid | 明细id |
| `userId` | long | 审核人id |
| `userNickName` | string | 审核人昵称 |
| `taskStatus` | int? | `0` 审核中、`1` 驳回、`2` 通过；`null` 代表还没走到这一步（或签下别人先审掉了） |
| `comment` | string | 审批意见 |
| `auditTime` | DateTime? | 审批时间 |

# 6. 审核任务详情

`GET /api/services/app/ClientAdmin/GetAuditDetailAsync?id=客户id`

**按客户id查**（不是任务id），取审核列表行上的 `client.id`。

与列表不同的是**不限「与我有关」**：审完的批次、别人审的批次都能查出来看进度。

## 6.1 入参（query）

| 字段 | 类型 | 必填 | 说明   |
| :--- | :--- | :--- | :----- |
| `id` | Guid | 是   | 客户id |

## 6.2 出参：主体

主体就是该客户**最新那一条任务**，字段与审核列表的行（第 5.3~5.5 节）**完全一致**，不再重复列。在此之上多一个字段：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `histories` | 对象[] | 该客户**全部轮次**的审批历史，按提交时间**正序**，见 6.3 |

## 6.3 出参：`histories[]`

每一轮一条。字段与列表行同构，另加轮次序号与是否当前轮。

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `round` | int | 轮次序号，正序从 1 开始 |
| `isCurrent` | bool | 是否当前轮（= 主体那一条） |
| `id` | Guid | 任务id |
| `taskType` | int | `90` 客户提交、`91` 客户申请修改 |
| `taskStatus` | int | `0` 审核中、`1` 驳回、`2` 通过 |
| `submitTime` | DateTime | 这一轮的提交时间 |
| `submitUserName` | string | 这一轮的提交人昵称 |
| `auditTime` | DateTime? | 这一轮的终审时间 |
| `auditUserName` | string | 这一轮的终审人昵称 |
| `remark` | string | 这一轮的审核意见 |
| `applyRemark` | string | 这一轮的申请修改原因。**仅 `taskType==91` 有值** |
| `myTaskStatus` | int? | 我在这一轮的状态，`null` 代表那一轮没轮到我 |
| `modifyTo` | ClientEditDto | **这一轮**要改成什么。**仅 `taskType==91` 有值** |
| `modifyFrom` | ClientEditDto | **这一轮**发起申请时客户的原值。**仅 `taskType==91` 有值** |
| `workFlowInstance` | 对象 | 这一轮的审批路径，结构同 5.5 |
| `client` | null | **历史里恒为 null**。客户信息在主体上挂一份就够，每轮重复没意义 |

> 这一节就是「历次改了什么」的来源：驳回后重新提交过多次的客户，逐轮 `modifyFrom` → `modifyTo` 比对即可还原完整改动轨迹。旧任务与旧工作流实例永久留档，撤回只会删掉最新那一轮，历史不会因为撤回或重新提交而丢。

## 6.4 报错

| 提示 | 触发 |
| :-- | :-- |
| 请选择合作客户 | `id` 为空 |
| 该客户没有审核任务 | 这个客户一次都没提交过（`clientStatus` 还是未提交且从没提交过） |
