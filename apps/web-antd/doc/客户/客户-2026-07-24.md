# 1. 背景意图 (Background)

`ClientAdminAppService` 与 `ClientAppService` 各自维护了一份 `ClientListDataPermissionFilterAsync`，逻辑已基本一致但易漂移。通用列表原先仅在 `industryCategory=="p"` 时过滤，与 Admin「始终按行」不一致。本次统一为 Admin 逻辑，并评估后上移到 `CsprojBuilderAppServiceBase`。

# 2. 为何放基类 (Decision)

| 方案 | 结论 |
| :-- | :-- |
| **`CsprojBuilderAppServiceBase`（采用）** | 与已有 `DataPermissionFilterAsync` / `DataPermissionFilterOrderFeeAsync` 同模式；依赖基类 `GetDataPermissionUserIdsAsync`；属性注入 `ClientStakeholderRepository` |
| 独立 Domain Manager | 仅一处过滤方法，过重 |
| 留在 ClientAdmin 供 Client 注入调用 | AppService 互相注入易循环依赖，不推荐 |

# 3. 核心逻辑变更 (Core Changes)

- 基类新增 `ClientListDataPermissionFilterAsync`（正文与原 Admin 一致）：非全部权限时，含 `p` 的客户需满足所属人/组织/干系人/已共享之一。
- `ClientAdmin`、`Client` 删除私有副本，改为调用基类。
- `Client/GetPagedListAsync`：**始终**调用过滤（不再 `if industryCategory=="p"`）。
- `ClientAppService` 构造函数移除仅用于过滤的 `ClientStakeholder` 仓储（改由基类属性注入）。

# 4. 行为差异说明

搜非 `p` 行业时：若客户同时含 `p`，现在也会按委托单位权限过滤（与 Admin 一致）；以前通用列表会直接返回。纯非委托单位客户仍不受限。

# 5. 避坑指南 (Pitfalls)

- 基类依赖属性注入 `ClientStakeholderRepository`，勿在构造函数再注入一份仅做过滤用。
- 勿再在子类复制过滤条件；改规则只改基类一处。
