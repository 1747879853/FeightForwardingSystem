# 收费结算接口文档

**控制器**：`ReceiveSettlementAdmin`

**所有接口均需要登录认证**

> [!IMPORTANT] **按费用结算支持折币（2026-09-26）**：一张按费用结算（`type=0`）可以同时结算多种币别的费用。
>
> - 明细 `settledAmount` 永远填**该费用自己的原币**金额，费用已结算量按原币累加，口径不变。
> - 明细里与银行流水币别不同的**每个币别都要录汇率**（1 单位原币折合多少银行流水币别），与银行流水同币别的汇率恒为 1，可不传。汇率**不参与**额度校验和银行流水核销，只用于在列表/详情里把明细折成银行流水币别，算出**原始结算金额**和它与本次结算的**差值**（2026-09-26 追加）。
> - 主表新增 **`actualSettled` 本次结算**（实际到账金额，银行流水币别），由前端录入；**银行流水按各收费结算的 `actualSettled` 之和核销**。
> - 列表/详情的 `totalSettledAmount` 已删除，改读 `actualSettled`。
>
> **按发票结算同样支持折币（2026-09-26 第二部分）**：`type=1` 改为以**发票开出**为单位。
>
> - 拉取接口改名 `GetInvoiceIssueGroupForSettlementAsync`，入参只收发票开出的条件，出参按「发票开出 → 费用」两层嵌套：**同一费用在一张发票开出下分在几张开票申请里时合并成一行**，不再有开票申请这一层。
> - 新增/追加的一行 = 「发票开出 + 费用」（传 `invoiceIssueId` + `orderFeeId` + `settledAmount`）。后端保存时按该费用在这张发票开出下**各开票明细的开票金额比例**把结算金额拆开落库，拆分结果保存时定死；删除也按「发票开出 + 费用」整行删。
> - 费用币别不限（开票申请本身允许多币别，汇率录在开票申请上）；**所属发票开出的币别必须等于银行流水币别**；冲红中/已冲红的发票开出不能结算。
> - `actualSettled` 改为**前端录入**（新增、追加、删明细、修改主表都和按费用一样），后端不再按明细净额自动算。
> - 列表/详情不再返回开票申请维度，改为返回 `invoiceIssues`（详情里每张发票开出下直接是合并后的费用行）；详情另返回每张发票开出、每个费用行的**原始结算金额**，以及 `diffAmount = actualSettled − 原始结算金额合计`。
>
> 完整口径见 [收费结算模块总逻辑文档.md](./收费结算模块总逻辑文档.md)。

## 一、拉取剩余结算额度不为0的费用（按业务分组）

### `GET /api/services/app/ReceiveSettlementAdmin/GetOrderFeeGroupAsync`

**权限**：`Admin.ReceiveSettlement.Get`

**入参** `ReceiveSettlementFeeGroupQueryDto`（Query参数）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `receiveSettlementId` | `Guid?` | 否 | 收费结算ID（编辑时传入，排除此结算已关联的费用） |
| `settlementId` | `Guid?` | 否 | 结算对象ID |
| `currencyId` | `long?` | 否 | 币别ID；传了只返回该币别费用，不传返回全部币别（按费用结算允许多币别）。**2026-09-26 由必填改为可选**，不再报「币别不能为空」 |
| `commissionNum` | `string` | 否 | 委托编号（模糊） |
| `mblNum` | `string` | 否 | 主提单号（模糊） |

**`ReceiveSettlementFeeGroupDto`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `transportOrder` | `TransportOrderSimpleDto` | 业务信息。除 `id`/`orgId`/`commissionNum`/`mblNum`/`bookingNum`/`client` 与组织串外，**2026-09-27 起**还返回 `bizType`、`etd`（没有开船日期时为 null）、`totalCtn`、以及按 `bizType` 挂的 `seaExport`/`seaImport`/`airExport`/`breakBulk`（四者互斥，非当前类型为 null） |
| `orderFees` | `List<ReceiveSettlementFeeDto>` | 该业务下可结算的费用列表，按 `sortId` 升序、相同再按创建时间升序 |

**`ReceiveSettlementFeeDto`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `Guid` | 费用ID |
| `feeCodeId` | `long` | 费用代码ID |
| `feeCode` | `FeeCodeSimpleDto` | 费用代码 |
| `currencyId` | `long` | 费用币别ID（原币） |
| `currency` | `CurrencySimpleDto` | 费用币别（`code`/`cnName`/`enName`） |
| `amount` | `decimal` | 费用总金额（原币） |
| `paySide` | `PaySide` | 收付类型（0 收 / 1 付，用于收付互抵 净额=收−付） |
| `remainingAmount` | `decimal` | 剩余结算额度（原币）= Amount − Sum(付费申请.AppliedAmount) − Sum(按费用结算.SettledAmount) − Sum(开票申请.AppliedAmount) |
| `settlementId` | `Guid?` | 结算对象ID |
| `settlement` | `ClientSimpleDto` | 结算对象 |

**业务规则**：

- 收、付费用都返回（支持收付互抵）
- 按费用结算允许多币别：不传 `currencyId` 时各币别费用一起返回，前端按 `currency` 分组展示并为银行流水币别以外的币别录汇率
- 剩余结算额度 = 费用总金额 − 付费申请已申请金额 − 按费用结算已结算金额 − **开票申请已申请金额（全部状态）**（与付费申请共用池口径一致；覆盖“已开票申请但尚未进收费结算”的占用）
- 按费用所属业务做数据权限过滤
- 如果传入 `receiveSettlementId`，则排除该收费结算已关联的费用（编辑场景）
- 与第二之二节「按查询条件自动分配新建」用同一套筛选：这里用同样的 `commissionNum`/`mblNum`/`statementNum` 搜得到的费用，就是那边参与分配的费用（那边另外固定币别 = 银行流水币别、`settlementId` = 银行流水付款方）
- 传入 `statementNum` 时，按 `App_StatementFees` 反查：只保留至少进过一张对账单号命中该关键字的对账单的费用；一条费用可进多张对账单，命中任意一张即返回；已删除的对账单/对账明细不参与匹配；不传时行为不变
- **业务展示字段（2026-09-27）**，只补在分组的 `transportOrder` 上，费用行不变：
  - 开船日期：`transportOrder.etd`，没填为 null
  - 业务类型：`transportOrder.bizType`（0 海运出口 / 1 海运进口 / 2 空运出口 / 3 件杂货），决定下面四个对象哪一个有值，其余为 null
  - 海运出口：`transportOrder.seaExport.carrier`、`.pol`、`.pod`（对象，没填为 null）
  - 海运进口：`transportOrder.seaImport.carrier`、`.pol`、`.pod`
  - 空运出口：`transportOrder.airExport.pol`、`.pod`（空港对象，**没有船公司**）
  - 件杂货（2026-09-27 新增）：`transportOrder.breakBulk`（`BreakBulkSimpleDto`），字段为 `id`、`vessel`（船名）、`innerVoyno`（航次）、`terminalVoyno`（码头航次）、`pol`、`polRemark`、`pod`、`podRemark`；`pol`/`pod` 是海运港对象（`PortCodeSimpleDto`，与海运出口同一结构，没填为 null），**没有船公司**
  - 箱型箱量：`transportOrder.totalCtn`，多种都列出，如 `20GP*2 40HQ*1`。空运与件杂货不适用，为 null；海运没录箱子时也为 null
- 分页维度为 TransportOrder（按业务分组后分页），`totalCount` 为符合条件的 TransportOrder 总数

## 二、新增收费结算

### `POST /api/services/app/ReceiveSettlementAdmin/AddAsync`

**权限**：`Admin.ReceiveSettlement.Add`

**入参** `ReceiveSettlementAddDto`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `bankStatementId` | `Guid` | 是 | 银行流水ID |
| `orgId` | `long?` | **是** | 所属组织id（须为当前登录人直属组织） |
| `settlementTime` | `DateTime` | 是 | 结算时间，默认当前时间可自定义 |
| `actualSettled` | `decimal?` | **是** | **2026-09-26 新增** 本次结算：实际到账金额（银行流水币别，两位小数），银行流水按它核销。不传报「本次结算不能为空」 |
| `remark` | `string` | 否 | 备注 |
| `receiveSettlementItems` | `List<ReceiveSettlementItemAddDto>` | 是 | 收费结算明细列表 |
| `receiveSettlementExchangeRates` | `List<ReceiveSettlementExchangeRateInputDto>` | 条件必填 | **2026-09-26 新增** 各原币币别的汇率。明细里与银行流水币别不同的每个币别都必须给；同币别恒为 1 可不传；传了明细里没有的币别会被忽略 |

**`ReceiveSettlementItemAddDto`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `orderFeeId` | `Guid` | 费用ID |
| `settledAmount` | `decimal` | 本次结算的金额（**该费用自己的原币**，两位小数） |
| `remark` | `string` | 备注 |

**`ReceiveSettlementExchangeRateInputDto`**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `currencyId` | `long` | 原币币别ID（明细费用的币别） |
| `exchangeRate` | `decimal?` | 汇率：1 单位原币折合多少银行流水币别，必须大于 0，六位小数。与银行流水同币别的后端恒存 1，传什么都不影响 |

**入参示例**（银行流水币别 CNY，结算一条 USD 费用、一条 CNY 费用）：

```json
{
  "bankStatementId": "bs-guid",
  "orgId": 1,
  "settlementTime": "2026-09-26T00:00:00",
  "actualSettled": 7950.0,
  "remark": "9月收费结算",
  "receiveSettlementItems": [
    { "orderFeeId": "fee-guid-1", "settledAmount": 1000.0, "remark": "" },
    { "orderFeeId": "fee-guid-2", "settledAmount": 850.0, "remark": "" }
  ],
  "receiveSettlementExchangeRates": [{ "currencyId": 2, "exchangeRate": 7.1 }]
}
```

上例 `fee-guid-1` 按 1000 USD 结算、`fee-guid-2` 按 850 CNY 结算，费用已结算量各自按原币累加；银行流水已结算金额加 7950 CNY（取的是 `actualSettled`）。详情里两条明细的原始结算金额分别是 7100.00 和 850.00，整单原始结算金额 7950.00，差值 0。

**出参**：`Guid`（新建的收费结算ID，`type=0`）

**业务规则**：

- 校验银行流水存在、当前用户是该银行流水的操作人（或有银行流水编辑权限）、`orgId` 为当前用户直属组织
- 结算明细不能为空，且费用不能重复；本次结算必填
- 费用的结算对象必须与银行流水的付款方一致；**不再要求费用币别与银行流水币别一致**
- 费用所属公司的本位币必须与结算单所属公司的本位币一致
- 明细里与银行流水币别不同的每个币别都必须有大于 0 的汇率，缺了报「币别[xxx]与银行流水币别不同,汇率必填且必须大于0」
- 悲观锁锁定费用后，逐条校验剩余结算额度（原币）：Amount − 付费申请已申请 − 按费用收费结算已结算 − 开票申请已申请 ≥ 本次原币结算金额
- 汇率与本次结算**不参与**额度校验，保存时也不拿本次结算与「明细 × 汇率」做比对；两者的差额只在列表/详情的 `diffAmount` 里展示
- 结算单号自动生成；汇率按「明细里出现的每个币别一行」落库（银行流水同币别存 1）
- 新增后回写 `OrderFee.SettledAmount`（原币）与 `SettlementStatus`，重算最终结算时间，并按各收费结算 `actualSettled` 之和重算银行流水已结算金额与核销状态

## 二之二、按查询条件自动分配新建收费结算（新增 2026-09-28）

### `POST /api/services/app/ReceiveSettlementAdmin/AddByAutoAllocationAsync`

**权限**：`Admin.ReceiveSettlement.Add`

前端不用逐条选费用：传查询条件和本次结算金额，后端按第一节同样的条件把费用全部查出来，按下面的规则把本次结算分配到费用上，生成一张按费用结算（`type=0`）。

**入参** `ReceiveSettlementAddByAutoAllocationDto`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `bankStatementId` | `Guid` | 是 | 银行流水ID。只结币别等于这条流水币别、结算对象等于这条流水付款方的费用 |
| `orgId` | `long?` | 是 | 所属组织id（须为当前登录人直属组织），不传报「所属组织不能为空。」 |
| `settlementTime` | `DateTime?` | 是 | 结算时间，不传报「结算时间不能为空」 |
| `actualSettled` | `decimal?` | 是 | 本次结算：实际到账金额（银行流水币别，两位小数），必须大于 0。后端按它分配到费用上，银行流水按它核销 |
| `remark` | `string` | 否 | 备注 |
| `commissionNum` | `string` | 否 | 委托编号（模糊），同第一节 |
| `mblNum` | `string` | 否 | 主提单号（模糊），同第一节 |
| `statementNum` | `string` | 否 | 客户对账单号（模糊），同第一节 |

第一节的其余入参这里都不收：`settlementId`、`currencyId` 取银行流水的；不分页，`pageIndex`/`pageSize`/`sorting` 不收；只新建不追加，`receiveSettlementId` 不收。

**入参示例**：

```json
{
  "bankStatementId": "bs-guid",
  "orgId": 1,
  "settlementTime": "2026-09-28T00:00:00",
  "actualSettled": 1330.0,
  "remark": "",
  "commissionNum": "",
  "mblNum": "",
  "statementNum": "DZ2609"
}
```

**出参**：`Guid`（新建的收费结算ID，`type=0`）。结到了哪些费用、每条结了多少，用这个 ID 调第七节详情看。

**分配规则**：

1. **取费用**：与第一节同一套筛选（审核通过、剩余结算额度 > 0、不在申请修改/申请删除审核中、数据权限、委托编号/主提单号/对账单号），再固定两条：费用币别 = 银行流水币别，费用结算对象 = 银行流水付款方。不分页，符合条件的全部参与分配。
2. **按业务算净额**：同一业务（`transportOrder`）的费用放在一起，净额 = 收的剩余结算额度合计 − 付的剩余结算额度合计。
3. **净额小的业务先结，整笔结清**：业务按净额从小到大排，净额相同的先创建的业务在前。依次把整笔业务结清：每条费用都按剩余结算额度结，本次结算扣掉这笔业务的净额。
4. **最后一笔结不清的业务，先结付再用收凑**：剩下的额度不够结清下一笔业务时，这笔业务的付全部按剩余结算额度结清；收按费用顺序（与第一节 `orderFees` 的顺序相同：`sortId` 升序，相同再按创建时间）往上凑，凑到「剩下的额度 + 这笔业务付的合计」为止，最后一条收只结一部分。后面的业务不动。
5. 剩下的额度正好分完就停。

分完之后整张单「收 − 付」正好等于 `actualSettled`。

**示例**：本次结算 1330，查出三笔业务（金额都是剩余结算额度）：

| 业务 | 费用（按费用顺序）     | 净额 |
| ---- | ---------------------- | ---- |
| A    | 收 300                 | 300  |
| B    | 收 1000、付 200        | 800  |
| C    | 收 700、收 500、付 100 | 1100 |

按净额排序是 A → B → C：

- A 净额 300 ≤ 1330，整笔结清，剩 1030；
- B 净额 800 ≤ 1030，整笔结清，剩 230；
- C 净额 1100 > 230，结不清：付 100 结清，收要凑到 230 + 100 = 330，第一条收 700 结 330，第二条收 500 不结。

整张单：收（300 + 1000 + 330）− 付（200 + 100）= 1330。

**净额 ≤ 0 的业务一定会被整笔结清**：付大于或等于收的业务净额最小，排在最前面；净额为负的结清后，剩下的额度不减反增。例如上例再多一笔业务 D「付 50」：D 排第一个先结清，剩下的额度变成 1380，A、B 照样结清后剩 280，C 的收就要凑到 280 + 100 = 380。

**业务规则**：

- 本次结算必填且大于 0；结算时间必填；`orgId` 必填且为当前用户直属组织
- 银行流水必须存在；当前用户须是该银行流水的操作人（规则同第三节）
- 按条件一条可结算费用都查不到，报「没有可结算的费用」
- 本次结算大于全部业务净额之和，报「本次结算不能超过可结算费用的剩余净额(收-付)合计:xxx」，`xxx` 就是最多能结的金额

- 悲观锁锁住结到的费用后，按第二节同一口径复核剩余结算额度：分配完到落库前，如果这些费用又被别的结算、付费申请、开票申请占用了额度，报「费用剩余结算额度已变动,请重新提交」，整单不落库，重新提交即可

- 不校验本次结算是否超过银行流水未核销金额（与第二节一致，超过时核销状态停在部分核销）
- 落库后的回写同第二节：`OrderFee.SettledAmount`、`SettlementStatus`、最终结算时间，并重算银行流水已结算金额与核销状态
- 建出来的单与第二节新建的完全一样，之后的追加、删明细、修改、删除都走原接口

**原始结算金额怎么算**（把每条明细的原币结算额折成银行流水币别；列表与详情同一口径）：

**按费用结算**（汇率取本收费结算上录的那份）：

```
明细的原始结算金额     = round(settledAmount × 收费结算上该费用币别的汇率, 2)   与银行流水同币别的汇率为 1；与 settledAmount 同号(毛额)
收费结算的原始结算金额 = Σ 各明细原始结算金额(收为正、付为负)
差值 diffAmount        = actualSettled − 收费结算的原始结算金额
```

- 每条明细单独舍入、整单直接相加，所以前端把各明细的 `originalSettledAmount` 按收正付负加起来，正好等于整单的值
- 某个非银行流水币别取不到汇率（只可能是历史数据）时，该明细的汇率与原始结算金额为 `null`，整单原始结算金额和差值也为 `null`

**按发票结算**（汇率取开票申请上录的那份）：

```
费用行的原始结算金额   = round(Σ 各拆分行 settledAmount × 所在开票申请上该费用币别的汇率, 2)   费用币别与开票申请同币别的汇率为 1；与 settledAmount 同号(毛额)
费用行的汇率           = round(Σ 各拆分行 settledAmount × 汇率 / Σ 各拆分行 settledAmount, 6)   各份汇率相同时就是那个汇率
发票开出的原始结算金额 = Σ 本单在这张发票下各费用行原始结算金额(收为正、付为负)
收费结算的原始结算金额 = Σ 各发票开出原始结算金额
差值 diffAmount        = actualSettled − 收费结算的原始结算金额
```

- 「拆分行」是保存时按开票金额比例拆出来、落在各开票明细上的结算行（见第十二节）。费用在这张发票开出下只在一张开票申请里时只有一份，就是 `settledAmount × 那张申请上的汇率`
- 「按比例」就体现在这里：同一费用分在几张开票申请里、各申请汇率不同时，按开票金额比例分摊到各申请、各按各的汇率折算；只结了一部分时也只按这一部分折算
- 每个费用行单独舍入，发票开出和整单直接相加（与按费用结算同一种汇总），所以前端把各费用行的 `originalSettledAmount` 按收正付负加起来，正好等于发票开出和整单的值
- 汇率取**开票申请**上录的那一份（开票时定的），不是银行流水当天的汇率，所以差值反映的是「按开票汇率应收」与「实际到账」之间的汇兑差或少收
- 收付互抵：付方向费用行取负，与银行流水核销的净额方向一致
- 费用币别与开票申请同币别时不需要汇率行；非同币别而开票申请上缺这个币别的汇率（只可能是历史数据）时，该费用行的汇率与原始结算金额为 `null`，所在发票开出和整单的原始结算金额、差值也为 `null`

- 只取**还挂着开票申请**、且**不在冲红中/已冲红**（`InvoiceRedStatusHelper.IsLocked` 为假）的发票开出。冲红完成会解绑开票申请，冲红中的票也不能再拿来结算
- 「已开票」看挂靠关系（开票申请挂在发票开出上），不看开票申请的 `status`，与费用已开票金额同一口径
- 收、付方向费用都返回（开票申请本身支持收付互抵）
- `invoiceSettleableAmount` 口径：`Amount − 付费申请已申请 − 按费用收费结算(ReceiveSettlementItems) − 按发票收费结算(ReceiveSettlementInvoiceItems)`，**不扣开票申请占用**
- **该余额按费用聚合**：一张发票开出下同一费用只有一行，但同一费用可能开在几张发票开出上，这几行共享同一个余额，前端需把同一费用的剩余额度当作共享池

- 追加场景传 `receiveSettlementId` 时，排除该结算已结过的「发票开出 + 费用」；同一费用在别的发票开出下仍会返回

- 分页维度为发票开出，按开票时间倒序
- **前端录本次结算时的参考值**：每行**本次要结的金额**（即新增/追加入参 `items[].settledAmount`，原币）× 该行的 `exchangeRate`，四舍五入两位后按收正付负相加，就是原始结算金额。保存时拆分金额要舍到分，详情里的 `originalSettledAmount` 可能与这个参考值差 1 分左右。注意不要用本表的 `settledAmount`，那是该费用历史上累计已结算的金额

- 费用必须挂在这张发票开出下的开票申请里，否则报「存在费用不在发票开出[xxx]下,不能按发票结算」。「已开票」看挂靠关系，不看开票申请状态

- 费用结算对象必须与银行流水一致；**费用币别不限**（2026-09-26 起，折成开票申请币别靠开票申请上的汇率）
- 费用所属公司的本位币必须与结算单所属公司一致
- **保存时按开票金额比例拆开落库**：该费用在这张发票开出下有几条开票明细，就拆成几行存到 `App_ReceiveSettlementInvoiceItems`（每行记 `invoiceApplicationId`/`invoiceApplicationItemId`/`orderFeeId`）。开票明细按创建时间排序，前面各行 = `round(settledAmount × 该条开票金额 / 开票金额合计, 2)`，**尾差全给最后一行**，所以拆出来的各行加起来恰好等于录入的 `settledAmount`
  - 例：USD 费用在开票申请 A 里开票 60、B 里开票 40，结 100 → 拆成 A 60、B 40 两行
  - 拆分结果保存时定死，详情/列表只是把这几行合回一行，不会按当时的开票金额重拆
  - 同一费用在这张发票开出下有负数开票明细（合计仍大于 0）时会拆出负数行，合回一行后总额不变
- 悲观锁（`UPDLOCK, ROWLOCK`）锁定相关费用后**按费用聚合**校验剩余结算额度（原币）：
  - `Amount − 付费申请已申请 − 按费用收费结算 − 按发票收费结算`
  - **不扣开票申请占用**（按发票结算是兑现已开票金额，与按费用路径口径不同）
- 回写：按费用**毛额**累加 `OrderFee.SettledAmount`（收、付各记各自毛额），并更新 `SettlementStatus`
- 本次结算 `actualSettled` 直接取入参；银行流水按各收费结算 `actualSettled` 之和核销。本次结算**不与**明细金额做任何比对，差额看详情的 `diffAmount`

## 十三之二、费用冗余字段回写（已结算量 / 结算状态 / 最终结算时间）

收费结算的增删都会回写费用表 `App_OrderFees` 上的三个冗余字段，三者永远同进同退：

| 字段 | 含义 | 回写规则 | 由谁维护 |
| --- | --- | --- | --- |
| `settledAmount` | 已结算量（原币毛额，收付都累加各自毛额） | 新增明细累加，删除明细扣减，扣到负数按 0 兜底 | `OrderFeeSettlementHelper` |
| `settlementStatus` | 结算状态 | `已结算量 = 0` 未结算；`已结算量 ≥ 费用金额` 结算完毕；其余部分结算 | `OrderFeeSettlementHelper` |
| `finalSettlementTime` | 最终结算时间 | 结算完毕时取该费用**全部**关联结算里业务时间最大的那条；不是结算完毕时恒为 `null` | `OrderFeeSettlementManager` |

**最终结算时间是「最大」不是「最后一次」**：一条费用可以同时挂多条银行流水和多张付费结算单，后补的那次结算业务时间未必更晚。取的是所有关联结算里最大的那个业务时间，各来源取哪个时间：

| 关联结算 | 取的时间 |
| --- | --- |
| 收费结算（按费用明细、按开票申请明细都算） | 该结算单所属**银行流水的交易时间** `BankStatement.StatementTime`，**不是**收费结算自己的 `settlementTime` |
| 付费结算 | `PaymentSettlement.SettlementTime`，见 [付费结算模块总逻辑文档.md](../付费结算/付费结算模块总逻辑文档.md) |

因为是「最大值」，所以每次结算明细增删、每次结算单业务时间改动，都要**按来源重算**，不能在某一次结算里直接写。重算前会 `CurrentUnitOfWork.SaveChangesAsync()` 刷新挂起更改，保证本次新增/删除的明细对重算查询可见。

**什么时候被清空**：删除结算明细（按费用 / 按开票申请）、删除整张收费结算、从银行流水侧取消核销，只要费用退出“结算完毕”，最终结算时间立即置空。

**什么时候跟着改**：修改银行流水的交易时间，见 [银行流水.md](./银行流水.md) 第十节；修改付费结算的结算时间，见付费结算文档。收费结算 `EditAsync` 改的是结算单自己的 `settlementTime`，不参与计算，不影响费用的最终结算时间。

## 十三之三、客户超期历史（`App_ClientOverdueHistories`）

**它记什么**：一条**应收**费用结算完毕、且最终结算日期晚于业务的应结日期时，留一条记录，表示这个客户这笔钱付晚了多少天。应付费用不入表（那是我们欠别人的，不属于客户超期）。

**判定口径**：`最终结算日期 > TransportOrder.SettlementDate`，**舍掉小时只比日期** （应结日期本身就是零点的日期，当天结清不算超期，与欠费报表的超期天数口径一致）。

| 列 | 含义 | 来源 |
| --- | --- | --- |
| `orderFeeId` | 费用id | 一条费用最多一条记录 |
| `clientId` | 客户id | `OrderFee.SettlementId`（费用的**结算对象**，不是业务的委托单位） |
| `transportOrderId` | 业务id | `OrderFee.TransportOrderId` |
| `settlementDate` | 应结日期 | `TransportOrder.SettlementDate`（按委托单位账期算出来的） |
| `finalSettlementTime` | 最终结算日期 | `OrderFee.FinalSettlementTime` |
| `overdueDays` | 超期天数 | `最终结算日期.Date - 应结日期.Date`，有记录就恒大于 0 |

**维护时机**：和最终结算时间**同一次调用**完成，凡是会改动费用结算状态或最终结算时间的地方都会重算——新建/追加/删除收费结算明细（两种类型）、删除整张收费结算、银行流水侧取消核销、付费结算的新增/追加/删除明细/删除整单、以及银行流水交易时间与付费结算结算时间的改动。

重算是幂等的：该有就补（已有则重刷冗余快照），不该有就删。费用退出“结算完毕”，或改完时间后不再超期（例如把银行流水交易时间改早了），对应记录会被删掉，不留历史。

**为什么不留历史**：这张表的语义是“客户当前有哪些笔付晚了”，是给客户信用评估用的现状快照。结算被撤销意味着那笔钱实际并没有在那天到账，留着就是错账。

> [!NOTE] **已知边界：应结日期改动不会回刷已有记录。** 记录只在费用侧（结算状态、最终结算时间）变动时重算。业务的应结日期 `TransportOrder.SettlementDate` 会在海运出口/海运进口/空运出口的编辑、业务主单编辑、以及客户账期的「同步应结日期」里被重算，但这些入口目前不会触发超期记录重算：改完之后旧记录的应结日期与超期天数还是旧的，本该新增或本该消失的记录也不会动。对不上时按费用侧重新触发一次结算变动，或人工刷这张表。
