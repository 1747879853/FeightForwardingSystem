# 1. 业务背景说明 (Background)

**白话解释：**

客户把钱打进我司账户，财务先录一条**银行流水**（金额、币别、付款方），再在这条流水下面做**收费结算**：说明这笔钱核销的是哪些费用、每条费用结了多少。一条银行流水可以挂多张收费结算，一张收费结算只属于一条银行流水。

收费结算有两种做法：

| 类型 | `type` | 明细子表 | 选什么 |
| :-- | :-- | :-- | :-- |
| 按费用（按业务） | `0` ByFee | `App_ReceiveSettlementItems` | 直接挑费用 |
| 按发票 | `1` ByInvoice | `App_ReceiveSettlementInvoiceItems` | 按**发票开出**挑它下面的费用，一张发票开出下同一费用只有一行；保存时按开票金额比例拆到各开票明细上存 |

两种做法共用费用上的同一个已结算池 `OrderFee.SettledAmount`：按费用结过的额度不能再按发票结，反之亦然。

**折币**：客户经常用一种币别付多种币别的账（例如打人民币付美元海运费）。两种结算都支持一张单里结多种币别的费用：

- 每条明细仍然按**费用自己的原币**填结算量，费用的已结算量、结算状态都按原币算，口径和以前一样；
- 实际到账多少由财务录在主表的**本次结算 `ActualSettled`**（银行流水币别），**银行流水按它核销**；
- **按费用结算（第一部分）**：明细里和银行流水币别不同的每个币别都要在收费结算上录一个**汇率**（1 单位原币折合多少银行流水币别）。汇率不参与额度校验和银行流水核销，只用来在列表/详情里把明细折成银行流水币别，算出每条明细和整单的**原始结算金额**，以及整单与本次结算的**差值**；
- **按发票结算（第二部分）**：汇率不在收费结算上录，而是用**开票申请**上开票时录的那份（开票申请允许多币别费用，每个非主币别一个汇率）。所选发票开出的币别必须等于银行流水币别。详情按「发票开出 → 费用」返回**原始结算金额**（把原币结算额按开票申请汇率折回发票开出币别）以及它与本次结算的**差值**。

**负数费用（2026-10-02）**：客户会录金额为负的费用（折扣、返利等）。这类费用可以和正数费用开进同一张票抵减（申请合计为正即可），也可以按费用或按发票收费结算，结算金额填负数，口径见卡点 16。

# 2. 功能与操作说明 (Features & Operations)

- **拉可结算费用：** `GetOrderFeeGroupAsync` 按业务分组返回剩余结算额度与费用同号且不为 0 的已审核费用（收付都返回；正数费用剩余 > 0，负数费用剩余 < 0）。币别是可选筛选，不传就返回全部币别，方便一张单结多种币别。每个分组的 `transportOrder` 另带开船日期 `etd`、业务类型 `bizType`、按业务类型挂的船公司/起运港/目的港（`seaExport`/`seaImport`/`airExport`/`breakBulk` 四选一；件杂货在 `breakBulk` 下，只有船名、航次、码头航次与海运港，没有船公司），以及箱型箱量合计 `totalCtn`（空运与件杂货为 null）。
- **按费用新建：** 选费用、逐条填原币结算量，为非银行流水币别录汇率，录本次结算，生成结算单号，回写费用已结算量并重算银行流水核销状态。
- **按查询条件自动分配新建：** `AddByAutoAllocationAsync` 不用逐条选费用。前端传拉费用的查询条件（委托编号、主提单号、对账单号）、银行流水和本次结算，后端用同一套筛选再固定银行流水的币别与付款方，把费用全部查出来，按业务逐笔分配本次结算：净额小的业务先整笔结清，结不清的最后一笔先结让净额变小的（付、负数收）、再用让净额变大的（收、负数付）凑（见卡点 14）。生成的是一张普通的按费用结算，之后的追加、删明细、修改、删除都走原接口。
- **按费用追加明细：** 给已有按费用结算加费用。新加进来的非银行流水币别要带汇率，同时传追加后整张单的本次结算。
- **按费用删除明细：** 删掉部分明细，同时传删除后整张单的本次结算；删光了本次结算自动归 0。单上不再出现的币别，其汇率一并删除。银行流水详情页也能按收费结算批量删按费用明细（「取消核销」），规则相同。
- **按发票拉可结算费用：** `GetInvoiceIssueGroupForSettlementAsync` 按「发票开出 → 费用」两层返回，只取还挂着开票申请、未冲红的发票开出。同一费用在一张发票开出下分在几张开票申请里时合并成一行：开票金额相加，汇率按开票金额加权。每行的剩余可结算额度 `invoiceSettleableAmount` 先逐张开票申请算、再按发票开出求和，并且不超过费用剩余额度（见卡点 3）：这张票只开了 50，就最多结 50，不会按费用总额返回 100。
- **按发票新建 / 追加 / 删除明细：** 一行 = 「发票开出 + 费用」。保存时按该费用在这张发票开出下各开票明细的开票金额比例拆开落库（见卡点 10）；删除按「发票开出 + 费用」整对删。本次结算和按费用一样由前端录入（追加、删明细传操作后整张单的值，删光归 0）。所选发票开出须未冲红、币别等于银行流水币别；费用币别不限。
- **修改主表：** 改所属组织、结算时间、备注、本次结算（两种类型都能改）；汇率只有按费用结算能改。
- **删除整单：** 回滚全部明细的费用已结算量，显式删除两种明细子表和汇率子表，重算银行流水。
- **列表：** `GET ReceiveSettlementAdmin/GetPagedListAsync`，出参 `ReceiveSettlementListDto`。主表列全部返回，并带银行流水号、明细条数、原始结算金额、差值、创建人昵称。组织串每级只有名称，并带本位币代码。不返回发票开出简要、创建人 id、修改人昵称。银行流水下的两个收费结算列表同一份出参。
- **详情：** 返回本次结算 `actualSettled`，两种类型都返回原始结算金额 `originalSettledAmount` 与差值 `diffAmount`（与列表同一口径）。按费用另返回明细（每条带汇率与原始结算金额）和汇率列表。按发票按「发票开出 → 费用」返回，两层带原始结算金额。
- **锁定 / 解锁：** 锁定后禁止编辑、增删明细、删除。

## 4.5 银行流水上的核销冗余字段

| 字段 | 口径 |
| :-- | :-- |
| `BankStatement.SettledAmount` | 该流水下全部未删除收费结算的 `ActualSettled` 之和 |
| `BankStatement.WriteOffStatus` | 已结算金额为 0 → 待核销；等于流水金额 → 核销完成；否则部分核销 |

由 `BankStatementWriteOffManager.RecalculateAsync` 统一重算。收费结算新增、追加 / 删除明细（含银行流水侧删明细）、删整单、修改主表改了本次结算，以及银行流水本身的新增 / 修改，都会触发。

银行流水的金额随时能改（改完重算核销状态）；但流水下挂了收费结算之后，**币别和付款方不能再改**（卡点 11）。

## 4.6 原始结算金额与差值（2026-09-26，两种结算都有，只算不存）

「原始结算金额」回答的是：**按单上录的汇率，这次结的这些明细折成银行流水币别应该是多少钱**。它和实际到账（本次结算）之差就是汇兑差或少收。列表和详情都返回，两边调同一组私有方法，数值一定一致。

### 按费用结算（汇率取收费结算上录的那份）

```
明细层 = round(SettledAmount × 收费结算上该费用币别的汇率, 2, AwayFromZero)
         与银行流水同币别的汇率为 1（存量单没有汇率行也按 1）；与 SettledAmount 同号，付方向也是正数
         非银行流水币别取不到汇率 → null
主表   = Σ 各明细层（收为正、付为负）                  （有一个 null 即 null；没有明细为 0）
差值   = ActualSettled − 主表原始结算金额               （原始为 null 即 null）
```

- **逐条舍入、整单直接相加**：前端把各明细的原始结算金额按收正付负加起来，正好等于主表的值。按费用结算没有「开票总额」要对齐，所以不用按币别先合计。
- 代码：`ConvertByFeeItem`（明细层）与 `SumOriginalSettledAmount`（主表层，按发票结算也用它），详情 `BuildReceiveSettlementDetailAsync` 与列表 `FillListComputedFieldsAsync` 共用。

### 按发票结算（汇率取开票申请上录的那份）

```
费用行     = round(Σ 各拆分行 SettledAmount × 所在开票申请上该费用币别的汇率, 2, AwayFromZero)
             费用币别与开票申请同币别的汇率为 1；与 SettledAmount 同号，付方向也是正数；任一份缺汇率 → null
费用行汇率 = round(Σ 各拆分行 SettledAmount × 汇率 / Σ 各拆分行 SettledAmount, 6, AwayFromZero)   （只展示，各份汇率相同时就是那个汇率）
发票开出层 = Σ 本单在该发票开出下的各费用行（收为正、付为负）   （有一个 null 即 null）
主表       = Σ 各发票开出层                                     （有一个 null 即 null；没有明细为 0）
差值       = ActualSettled − 主表原始结算金额                    （原始为 null 即 null）
```

- 「拆分行」是同一「发票开出 + 费用」保存时拆到各开票明细上的那几行（4.3、卡点 10）。费用在这张发票开出下只在一张开票申请里时只有一份，费用行就是 `round(结算额 × 那张申请上的汇率, 2)`。
- **按比例**：同一费用分在几张开票申请里、各申请汇率不同时，按开票金额比例分摊到各申请、各按各的汇率折算；只结了一部分时也只按这一部分折算。
- **每个费用行舍入一次，上层直接相加**（与按费用结算同一种汇总），前端把各费用行的原始结算金额按收正付负加起来，正好等于发票开出层和主表。代码：`ConvertByInvoiceFee`（费用行）与 `SumOriginalSettledAmount`（发票开出层、主表），详情与列表共用。
- **与开票申请申请总额的舍入口径不同**：申请总额按「开票申请 + 币别」合计后再舍入（`InvoiceApplicationAmountRule`），这里一行费用可能跨几张开票申请，没法按申请合计。所以把整张开票申请结清时，原始结算金额与申请总额可能差几分（另见卡点 9 的收付符号差），差出来的会体现在 `diffAmount` 里，只提示不拦截。
- **能直接相减的前提**是发票开出币别 = 开票申请币别 = 银行流水币别，新增/追加时已卡死（卡点 4）。
- 开票申请已不挂在任何发票开出上（历史上冲红解绑、在卡点 8 生效前就结算了的）时，这些明细归到 `id = null` 的一组，排在最后，原始结算金额照算。
- 这些值**不落库**：每次查列表/详情现算，汇率改了也不会有旧值残留。按发票结算用的开票申请已是已开票状态，汇率事实上改不了；按费用结算的汇率可以在修改主表 / 追加明细时改，改完列表和详情立刻按新汇率算。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：两种结算的本次结算都由前端给，后端不推算]** 明细是原币，后端没有依据推算实际到账额（汇率只能算出「应该到多少」，到账多少只有财务知道），所以本次结算 `actualSettled` 一律由前端传：
>
> | 操作 | 本次结算怎么变 |
> | :-- | :-- |
> | 新增 `AddAsync` / `AddByInvoiceApplicationAsync` | 必填，直接写入 |
> | 按查询条件自动分配新建 `AddByAutoAllocationAsync` | 必填且大于 0，直接写入；明细由后端按它分配（卡点 14），明细净额恒等于本次结算 |
> | 追加明细 `AddItemsAsync` / `AddItemsByInvoiceApplicationAsync` | 必填，传追加后**整张单**的值，直接覆盖（不累加） |
> | 删除明细 `DeleteItemsAsync` / `DeleteInvoiceItemsAsync` / 银行流水侧 `DeleteReceiveSettlementItemsAsync` | 还剩明细时必填，直接覆盖；删光恒为 0 |
> | 修改主表 `EditAsync` | 可选，不传不改；没有明细时只能为 0（按类型分别看两张明细表） |
>
> 后端**不校验**本次结算与「Σ原币净额 × 汇率」是否相等，也不校验是否超过银行流水金额（超过时核销状态停在部分核销）。两种结算的差额都由列表/详情的 `diffAmount` 展示，只提示不拦截。

> [!IMPORTANT] **[卡点 2：非银行流水币别必须有汇率]** 操作完成后明细里出现的每个币别都要有汇率：与银行流水同币别的恒为 1（传什么都写 1）；其他币别优先取入参，入参没给就沿用单上已有的，都没有或不大于 0 报「币别[xxx]与银行流水币别不同,汇率必填且必须大于0」。入参里明细没有的币别直接忽略，同一币别传两次报「汇率中存在重复的币别」。汇率校验和其他校验一样放在落库之前，报错时不会留下半截数据。

> [!IMPORTANT] **[卡点 3：两种结算的剩余额度口径不同]** 都按费用原币算，都先用 `UPDLOCK, ROWLOCK` 锁费用再在锁内算：
>
> | 路径 | 剩余额度 |
> | :-- | :-- |
> | 按费用结算（与付费申请共用池） | `Amount − 付费申请已申请 − 按费用收费结算 − 开票申请已申请` |
> | 按发票结算（兑现已开票金额） | `Amount − 付费申请已申请 − 按费用收费结算 − 按发票收费结算`，**不扣**开票申请占用 |
>
> 汇率和本次结算都不参与额度校验。拉费用、按发票拉可结算费用的列表过滤与提交校验同口径。按发票结算拆出来的几行按费用合计后再比额度。按查询条件自动分配新建与拉费用共用同一个查询 `BuildSettleableFeeQueryAsync`，额度口径是按费用结算那一行。
>
> **按发票结算另有一道开票侧额度（2026-10-02 新增）**：上表那一行是费用剩余额度，各张发票开出共用。只用它的话，一张只开了 50 的票也能结满费用剩下的 100。所以每个「发票开出 + 费用」还要满足：
>
> ```
> 单张开票申请剩余 = 该开票明细.AppliedAmount − Σ 按发票结到这条开票明细上的 SettledAmount（按 InvoiceApplicationItemId 匹配）
> 这张票的剩余     = Σ 这张发票开出名下各开票明细的单张剩余          （发票开出这一层只是求和）
> 费用按发票可结   = Σ 开票申请已申请（全部状态） − Σ 按发票收费结算  （费用层面，各张发票开出共用，见卡点 15）
> 开票侧剩余       = Min(这张票的剩余, 费用按发票可结)
> 剩余可结算额度   = Min(开票侧剩余, 费用剩余额度)
> ```
>
> - **逐张开票申请算，再求和**：已结金额按开票明细 id 匹配。保存时按比例拆分会把结算额落到具体的开票明细上（卡点 10），所以能精确对上；同一张申请里同一费用出现两条明细也不会重复扣。
> - **单张剩余不截到 0**：同一费用在一张发票开出下有负数开票明细时，会拆出负数结算行，截到 0 会让合计偏大。
> - **费用按发票可结**守的是「按发票已结 ≤ 开票申请合计」，原因见卡点 15。平时它不比前两项小，只有费用开过负数开票申请时才起作用。
> - **唯一实现**：`IOrderFeeInvoicedProvider.GetIssueFeeSettleableMapAsync(invoiceIssueIds, orderFeeIds)`，返回 `(发票开出id, 费用id) → 开票侧剩余`（已和费用按发票可结取小），只算开票这一侧，和费用剩余额度取小由调用方做。费用按发票可结单独由 `GetFeeInvoiceSettleableMapAsync(orderFeeIds)` 给出。拉取接口 `GetInvoiceIssueGroupForSettlementAsync` 与按发票新建 / 追加的锁内校验 `EnsureIssueFeeQuotaAsync` 都调它们，两边口径一致。
> - 新建 / 追加时，在锁住费用、费用剩余额度校验通过之后、结算行落库之前调用（落库后再调会把本次也算成已结）。逐行比开票侧剩余，超了报「存在费用超出发票开出[xxx]的剩余可结算额度,可用额度:xxx」；同一费用挂在几张发票开出下一起结时，再按费用合计比一次费用按发票可结，超了报「费用按发票可结算额度不足(开票申请合计扣掉已按发票结算),可用额度:xxx」。
> - 拉取接口 `onlySettleable=true` 的 SQL 粗筛按单条开票明细判断（`AppliedAmount > 已结到这条明细上的额`，且费用的开票申请合计 > 已按发票结算），精确值以上面合并后的结果为准。
> - 例：安保费 100，在发票开出 0010FPKC 里只开了 50，从没结过 → 返回 `Min(50 − 0, 100) = 50`。之后另一张发票开出按发票结了它 30 → 0010FPKC 这一行变成 `Min(50, 70) = 50`，那张票自己这一行是 `Min(50 − 30, 70) = 20`。

> [!IMPORTANT] **[卡点 4：按发票结算以发票开出为单位，发票开出币别必须等于银行流水币别]** 按发票新建 / 追加时，每一行「发票开出 + 费用」：
>
> | 校验 | 不过时报错 |
> | :-- | :-- |
> | 入参里同一「发票开出 + 费用」只出现一次 | 结算明细中同一张发票开出下存在重复的费用 |
> | 追加时本单还没结过这对「发票开出 + 费用」 | 存在费用已在该收费结算的同一张发票开出下,不能重复添加 |
> | 发票开出存在 | 部分发票开出不存在 |
> | 发票开出不在冲红中 / 已冲红 | 发票开出[xxx]冲红中或已冲红,不能按发票结算 |
> | 发票开出币别 = 银行流水币别 | 发票开出[xxx]的币别与银行流水的币别不一致 |
> | 费用在这张发票开出所挂的开票申请里（看挂靠，不看开票申请状态） | 存在费用不在发票开出[xxx]下,不能按发票结算 |
> | 该费用在这张发票开出下的开票金额合计与费用同号且不为 0（否则没法按比例拆；正数费用 > 0，负数费用 < 0，见卡点 16） | 存在费用在发票开出[xxx]下的开票金额合计为0或与费用金额反号,不能按发票结算 |
> | 结算金额与费用同号（2026-10-02 新增） | 结算金额须与费用金额同号 |
> | 锁内：录入金额 ≤ 这张发票开出开票侧的剩余额度（2026-10-02 新增，口径见卡点 3） | 存在费用超出发票开出[xxx]的剩余可结算额度,可用额度:xxx |
> | 锁内：同一费用各行合计 ≤ 开票申请合计 − 已按发票结算（2026-10-02 新增，见卡点 15） | 费用按发票可结算额度不足(开票申请合计扣掉已按发票结算),可用额度:xxx |
>
> 发票开出币别 = 开票申请币别（发票开出只合并同币别申请，加挂时也卡），所以这条等价于「开票申请币别 = 银行流水币别」，原始结算金额才能和本次结算直接相减。 **费用币别不限**：费用折成开票申请币别用的是开票申请上录的汇率，收费结算上不再录汇率；修改主表传的汇率对按发票结算无效。拉取接口也按同样的挂靠与冲红条件过滤，但**不**按币别过滤（前端一般传 `currencyId` = 银行流水币别）。

> [!IMPORTANT] **[卡点 5：追加费用明细只对按费用结算]** 对 `type=1` 的单调用 `AddItemsAsync` 报「该收费结算不是按费用结算,不能追加费用明细」；反过来对 `type=0` 调 `AddItemsByInvoiceApplicationAsync` 报「该收费结算不是按开票申请结算,不能追加开票明细」。

> [!IMPORTANT] **[卡点 6：已锁定禁止改删]** `Locked == true` 时修改主表、增删明细、删除整单都会失败；银行流水侧删明细同样拦截。

> [!WARNING] **[卡点 7：上线前必须回填存量本次结算]** 银行流水已结算金额改成了取 `ActualSettled` 之和。新列加上后存量收费结算全是 0，**不回填的话，任何一次重算都会把老流水的已结算金额冲成 0、核销状态退回待核销**。回填 SQL 见 7.4。

> [!IMPORTANT] **[卡点 8：被按发票结算引用的开票申请，其发票开出不能反开票、不能冲红]** 按发票结算的明细靠「开票申请 → 发票开出」的挂靠找到发票开出，所以挂靠在被结算期间必须稳定：
>
> | 动作 | 结果 |
> | :-- | :-- |
> | 发票开出删除 / 编辑移除申请 / `RemoveApplicationsAsync` | 报「开票申请[xxx]已被收费结算引用,不能反开票,请先删除对应的收费结算明细」（原有） |
> | 发起冲红 `ApplyRedAsync`（2026-09-26 新增） | 报「开票申请[xxx]已被收费结算引用,不能冲红,请先删除对应的收费结算明细」 |
> | 按发票拉取 / 新增 / 追加 | 排除冲红中与已冲红的发票开出 |
>
> **为什么要拦冲红**：冲红完成是回调驱动的，完成时会自动解绑发票开出与开票申请（`DetachApplicationsAsync`），原来这一步不查收费结算引用，结果是收费结算明细还在、发票开出却已经不挂这些申请，详情里就只能归到「无发票开出」一组。回调里没法报错，只能在发起冲红时拦。顺序因此是：**先删收费结算明细，再冲红**。冲红中途被作废（确认单作废 / 申请失败）后发票开出解锁，可以重新结算。

> [!NOTE] **[卡点 9：原始结算金额收付带符号，开票申请总额不带]** 原始结算金额按「收为正、付为负」折算，与银行流水核销的方向一致；而开票申请的申请总额（以及开票申请提交时校验的商品金额）是把各明细 `AppliedAmount` 直接相加的，不区分收付（既有口径，本次未动）。开票申请里只有收方向费用时两者口径一致；混有付方向费用时，把整张开票申请结清，原始结算金额也会小于开票申请总额，差出来的就是付方向那部分的两倍。此外两边舍入口径不同，还可能再差几分（见 4.6）。

> [!IMPORTANT] **[卡点 10：一行「发票开出 + 费用」保存时按开票金额比例拆开，删除整对删]** 同一费用可能分在一张发票开出下的几张开票申请里（每张申请一条开票明细，汇率可能不同）。前端只录一个结算金额，后端保存时拆开：
>
> - 开票明细按创建时间排序，前面各条 = `round(结算金额 × 本条开票金额 / 开票金额合计, 2, AwayFromZero)`，**尾差全给最后一条**，拆出来的各行加起来恰好等于录入金额。例：USD 费用在申请 A 里开票 60、B 里开票 40，结 100 → 存 A 60、B 40 两行。
> - 拆分结果**保存时定死**：详情/列表只是把这几行合回一行，不按当时的开票金额重拆。
> - 有反号开票明细（合计仍与费用同号）时会拆出反号行，合回一行后总额不变；合计为 0 或与费用反号的直接拒绝（卡点 4）。负数费用的开票金额与结算金额都是负数，比例照算。
> - **删除按「发票开出 + 费用」整对删**，把拆出来的几行一起删：只删其中一行会让剩下的比例失真。详情里发票开出为 `null` 的那一组（历史上冲红解绑的），删除时发票开出 ID 传 `null`。
> - 「发票开出 + 费用」这个键不落库，是按「结算行 → 开票申请 → 挂靠 → 未删除的发票开出」现取的。拉取时的排除、追加查重、删除匹配、详情/列表分组都用同一口径，所以前端从详情拿到的键一定能删掉对应的行。

> [!IMPORTANT] **[卡点 11：银行流水下有收费结算后，币别和付款方不能再改]** 修改银行流水时，只要流水下还有收费结算，传入的 `currencyId` 或 `settlementId` 与原值不同就报「银行流水下存在收费结算,不能修改币别和付款方」。金额照样能改，改完重算核销状态。原因是这些数据都以流水当时的币别和付款方为基准：本次结算录的是流水币别的金额，按费用结算的汇率是「1 单位原币折合多少流水币别」，按发票结算要求发票开出币别等于流水币别，费用的结算对象要等于付款方。币别一改，核销金额、原始结算金额、差值全错；付款方一改，已结费用对不上，之后追加又按新付款方校验，一张单里会混进两个结算对象。要改就先删掉流水下的收费结算。

> [!IMPORTANT] **[卡点 12：已提交销售提成的费用不能取消核销]** 删明细（按费用、按发票两种）、删整张收费结算、银行流水侧删明细，都会回滚费用已结算量。只要被回滚的费用所在业务（主单）或更改单已提交销售提成，就报「已提交销售提成不可取消核销」：提成是按「这一票费用全部已结算」算的，钱可能已经发了，撤掉结算账就对不上。两侧共用 `BankStatementWriteOffManager.EnsureNoSalesCommissionAsync` 一套判断（2026-09-26 起收费结算侧也拦，之前只有银行流水侧拦）。

> [!IMPORTANT] **[卡点 13：收费结算的写操作都要是该银行流水的操作人]** 新增（两种）、追加（两种）、删明细（两种）、修改主表、删整单都会校验：有银行流水编辑权限（`Admin.BankStatement.Edit`）的不限；否则该流水配了操作人时，当前用户必须在操作人里，不然报「当前用户不是该银行流水的操作人,无权操作」；流水没配操作人时不拦。2026-09-26 之前只有按费用新建和修改主表校验，其余六个入口都漏了。按查询条件自动分配新建（2026-09-28）上线时就带这项校验。

> [!IMPORTANT] **[卡点 14：按查询条件自动分配新建由后端决定结哪些费用、各结多少]** `AddByAutoAllocationAsync` 只收查询条件与本次结算，分配规则：
>
> 1. 费用 = 拉费用 `GetOrderFeeGroupAsync` 的同一个查询（`BuildSettleableFeeQueryAsync`，两边共用，筛选不会漂），另固定币别 = 银行流水币别、结算对象 = 银行流水付款方，不分页全部参与。
> 2. 按业务分组，净额 = Σ收的剩余结算额度 − Σ付的剩余结算额度。按净额升序排，相同再按业务创建时间升序、业务 ID 升序。
> 3. 依次整笔结清（每条费用结它的剩余结算额度），本次结算扣掉净额；扣到正好为 0 就停。
> 4. 第一笔结不清的业务：按每条费用对净额的贡献分（收 = 剩余额度，付 = −剩余额度）。贡献为负的（付、负数收）全部结清；贡献为正的（收、负数付）按 `SortId`、创建时间的顺序凑到「剩下的额度 + 前者腾出的额度」，最后一条只结一部分，结算额换回与费用同号（负数付结出来是负数）；之后的业务不动。没有负数费用时就是「付全部结清，收往上凑」。
>
> 结果整单「收 − 付」恒等于本次结算。**净额 ≤ 0 的业务（付 ≥ 收）排在最前，一定被整笔结清**；净额为负的结清后，可分配的额度反而变大。第 4 步原来写死「付全部结清、收往上凑」，有负数付（贡献为正）时会被整笔结掉，结出来的净额超过剩下的额度，所以 2026-10-02 改成按贡献的正负分。
>
> | 校验 | 不过时报错 |
> | :-- | :-- |
> | 本次结算 > 0 | 本次结算必须大于0 |
> | 按条件查得到费用 | 没有可结算的费用 |
> | 本次结算 ≤ 全部业务净额之和 | 本次结算不能超过可结算费用的剩余净额(收-付)合计:xxx |
> | 结到的费用本位币与结算单所属公司一致（只查结到的，同 `AddAsync`） | 存在与当前公司本位币不一致的费用 不可添加 |
> | 锁内复核：结到的每条费用分配额 ≤ 锁内现算的剩余结算额度（负数费用比绝对值） | 费用剩余结算额度已变动,请重新提交 |
>
> 分配是在锁外按查询时的剩余额度算的，锁住结到的费用后再按按费用结算的口径逐条复核；分配后到落库前被别的单据占用了额度，就整单不落库，用户重新提交即可。锁费用按 2000 条一批（SQL Server 单条语句最多 2100 个参数，这个接口一次可能结几千条费用）；`LockOrderFeesAsync` 本身没改。费用都是银行流水币别，汇率只存一行（银行流水币别，1），原始结算金额 = 本次结算，差值恒为 0。

> [!IMPORTANT] **[卡点 15：按发票已结不能超过开票申请合计（2026-10-02）]** 按费用收费结算、付费申请的额度都是 `Amount − 付费申请 − 按费用结算 − 开票申请已申请`，**不扣按发票结算**。它们默认按发票结掉的钱都在开票申请占用里，所以不用再扣一次。这个默认只在下面这条成立时才对：
>
> ```
> Σ 按发票收费结算 ≤ Σ 开票申请已申请（全部状态，可以有负数）
> ```
>
> 一旦不成立，差出来的部分会被按费用结算或付费申请再放出来，同一笔钱结两次。例：费用 100，申请 A 开票 +100 并开出；申请 B 开票 −100（开票申请允许负数冲红）；按发票在 A 的票上结 100；这时开票申请合计为 0，按费用结算看到 `100 − 0 − 0 − 0 = 100`，又结了 100。B 在结算之前还是之后开的，结果都一样。
>
> 两头一起守：
>
> | 时机 | 校验 | 不过时报错 |
> | :-- | :-- | :-- |
> | 按发票新建 / 追加（锁内） | 同一费用各行合计 ≤ 开票申请合计 − 已按发票结算；拉取接口的剩余额度也和它取小（卡点 3） | 费用按发票可结算额度不足(开票申请合计扣掉已按发票结算),可用额度:xxx |
> | 开票申请新增 / 编辑 / 追加明细（锁内） | 该费用其他开票申请合计 + 本次金额 ≥ 已按发票结算 | 费用已按发票收费结算xxx,开票申请合计不能少于该金额,最小可用额度:xxx,请先删除对应的收费结算明细（负数费用显示「最大可用额度」） |
> | 开票申请编辑时去掉费用 / 移除明细 / 删除申请 | 移除后该费用开票申请合计 ≥ 已按发票结算（只查已按发票结算过的费用） | 费用已按发票收费结算xxx,移除后开票申请合计xxx少于该金额,请先删除对应的收费结算明细 |
>
> - **只在按发票结算过时才多拦**：已按发票结算为 0 时，开票申请那边的下限就是原来的「合计 ≥ 0」，新增、编辑、追加明细的行为和以前完全一样。先按费用结算、再开票申请不受影响：开票申请的上限从来不扣收费结算，新下限只看按发票结算。
> - 顺序与卡点 8 一致：**先删按发票收费结算明细，再冲红 / 改小 / 删除开票申请**。
> - 开票申请的移除明细、删除申请现在会先锁住涉及的费用行再校验（新增、编辑、追加明细本来就锁），与收费结算、开票申请的写入串行，防止两边并发时各自校验都通过。
> - 已按发票结算额由 `IOrderFeeInvoicedProvider.GetInvoiceSettledAmountMapAsync` 给出，费用按发票可结由 `GetFeeInvoiceSettleableMapAsync` 给出，开票申请与收费结算两边都只从这里取。
> - **为什么不改成按费用结算、付费申请也扣按发票结算**：那样要改按费用结算 4 处、付费申请几处以及 `IOrderFeeOccupiedProvider`，展示用的占用额度也会跟着变；守住上面这条不等式，它们原来的公式就一直是对的。
> - 负数费用按卡点 16 取反后同样适用：按发票已结的绝对值不能超过开票申请合计的绝对值。

> [!IMPORTANT] **[卡点 16：负数费用按方向取反后套用正数费用的规则（2026-10-02）]** 客户会录金额为负的费用（折扣、返利等）。改版前所有额度都按「剩余 > 0」「结算额 ≤ 剩余」写死，负数费用在选费用列表里看不到、开票申请上下限对不上、按发票结算拆分直接拒绝，结算状态也会算错（`−50 ≥ −100` 被判结清）。
>
> 统一做法：**费用方向 `sign` = 费用金额 < 0 ? −1 : 1**（`OrderFeeSettlementHelper.FeeSign`），所有金额乘上它之后按正数费用的规则比较，比完再乘回去。负数费用的剩余额度、结算额、开票额都与费用同号（负数）。
>
> | 环节 | 规则（负数费用） |
> | :-- | :-- |
> | 按费用拉费用 / 自动分配取费用 | 剩余结算额度 < 0 才返回（正数费用仍是 > 0） |
> | 按费用新建 / 追加 / 自动分配锁内复核 | 结算额 ≤ 0，且不小于剩余额度（如剩余 −100，可结 −1 到 −100） |
> | 自动分配 | 负数收和付一样让净额变小，负数付和收一样让净额变大，见卡点 14 |
> | 按发票拉取 | 开票侧剩余、费用剩余都是负数，取离 0 更近的那个；`onlySettleable` 要求剩余与开票金额都 < 0 |
> | 按发票新建 / 追加 | 这张发票开出下的开票金额合计须 < 0；结算额 ≤ 0；三道额度（费用剩余、这张票的剩余、费用按发票可结）都比绝对值；按比例拆分照算 |
> | 结算状态 | 已结 = 0 未结算；已结 × sign ≥ 金额 × sign 结算完毕；否则部分结算。回滚过头（与费用反号）归 0 |
>
> - **所有路径都加了同号校验**：结算金额与费用反号报「结算金额须与费用金额同号」。正数费用以前可以填负数结算额绕过额度校验，现在也会被拦。
> - 开票申请这一侧的规则（选费用、上下限、提交时申请合计 > 0 且每行商品金额 > 0）见《开票申请/逻辑.md》「负数费用」。
> - 付费申请、付费结算没有改（它们的选费用列表仍只列剩余 > 0 的费用）；结算状态的计算两边共用 `OrderFeeSettlementHelper`，负数费用的状态也会算对。

迁移文件不由本次提交生成，需人工 `dotnet ef` 生成。**生成后在 `Up()` 末尾用 `migrationBuilder.Sql(...)` 追加下面的回填**：

```sql
-- 1) 必须：存量收费结算的本次结算 = 两种明细的净额(收-付)
--    与改版前银行流水已结算金额的算法一致(只算未删除的明细、未删除的费用 PaySide 1=付)
UPDATE rs
SET rs.ActualSettled = ISNULL(fee.Net, 0) + ISNULL(inv.Net, 0)
FROM App_ReceiveSettlements rs
OUTER APPLY (
    SELECT SUM(CASE WHEN f.PaySide = 1 THEN -i.SettledAmount ELSE i.SettledAmount END) AS Net
    FROM App_ReceiveSettlementItems i
    INNER JOIN App_OrderFees f ON f.Id = i.OrderFeeId AND f.IsDeleted = 0
    WHERE i.ReceiveSettlementId = rs.Id AND i.IsDeleted = 0
) fee
OUTER APPLY (
    SELECT SUM(CASE WHEN f.PaySide = 1 THEN -i.SettledAmount ELSE i.SettledAmount END) AS Net
    FROM App_ReceiveSettlementInvoiceItems i
    INNER JOIN App_OrderFees f ON f.Id = i.OrderFeeId AND f.IsDeleted = 0
    WHERE i.ReceiveSettlementId = rs.Id AND i.IsDeleted = 0
) inv
WHERE rs.IsDeleted = 0;

-- 2) 可选：存量按费用结算补一行「银行流水币别 汇率1」(改版前按费用结算只允许同币别)
--    不补也不影响功能 只是这些老单详情里汇率列表为空 下次追加明细或改汇率时后端会自动补上
INSERT INTO App_ReceiveSettlementExchangeRates (Id, TenantId, ReceiveSettlementId, CurrencyId, ExchangeRate, CreationTime, IsDeleted)
SELECT NEWID(), rs.TenantId, rs.Id, bs.CurrencyId, 1, GETDATE(), 0
FROM App_ReceiveSettlements rs
INNER JOIN App_BankStatements bs ON bs.Id = rs.BankStatementId
WHERE rs.IsDeleted = 0 AND rs.Type = 0
  AND EXISTS (SELECT 1 FROM App_ReceiveSettlementItems i WHERE i.ReceiveSettlementId = rs.Id AND i.IsDeleted = 0);
```

回填后可用下面的查询核对：新口径算出的已结算金额应与银行流水上现存的冗余值一致，查出来的行需要人工看。

```sql
SELECT bs.Id, bs.BankStatementNo, bs.SettledAmount, ISNULL(x.Total, 0) AS NewSettledAmount
FROM App_BankStatements bs
OUTER APPLY (SELECT SUM(rs.ActualSettled) AS Total FROM App_ReceiveSettlements rs WHERE rs.BankStatementId = bs.Id AND rs.IsDeleted = 0) x
WHERE bs.IsDeleted = 0 AND bs.SettledAmount <> ISNULL(x.Total, 0);
```

上面第 1) 段对按发票结算同样适用：第二部分之前按发票结算的本次结算就是明细净额，回填出来的正是它当时的值，第二部分不需要另外回填。

**第二部分新增表** `App_InvoiceApplicationExchangeRates`（实体 `InvoiceApplicationExchangeRate : FullAuditedEntity<Guid>, IMustHaveTenant`，软删除）：

| 列名 | 类型 | 可空 | 说明 |
| :-- | :-- | :-- | :-- |
| `Id` | `uniqueidentifier` | 否 | 主键 |
| `TenantId` | `int` | 否 | 租户 |
| `InvoiceApplicationId` | `uniqueidentifier` | 否 | 开票申请id，外键 → `App_InvoiceApplications`（按约定生成索引） |
| `CurrencyId` | `bigint` | 否 | 费用币别id，无物理外键 |
| `ExchangeRate` | `decimal(10,6)` | 否 | 汇率：1 单位费用币别折合多少开票申请币别 |
| 审计列 | — | — | 同上 |

存量开票申请**不需要回填**：改版前开票申请只允许同币别费用，折算时主币别没有汇率行也按 1 处理。上线前可用下面的查询确认没有「费用币别与开票申请币别不同」的存量数据（只可能来自开票后又改了费用币别）；查出来的申请在列表里申请总额为 `null`，提交/开票时会提示缺汇率，需驳回后补汇率：

```sql
SELECT DISTINCT ia.Id, ia.ApplicationNo, ia.Status, ia.CurrencyId, f.CurrencyId AS FeeCurrencyId
FROM App_InvoiceApplications ia
INNER JOIN App_InvoiceApplicationItems it ON it.InvoiceApplicationId = ia.Id AND it.IsDeleted = 0
INNER JOIN App_OrderFees f ON f.Id = it.OrderFeeId AND f.IsDeleted = 0
WHERE ia.IsDeleted = 0 AND f.CurrencyId <> ia.CurrencyId;
```

另外建议核对一次「已被按发票结算引用、但发票开出已冲红解绑」的存量（卡点 8 生效前可能产生），这些明细在详情里会归到无发票开出的一组：

```sql
SELECT DISTINCT rs.SettlementNo, ia.ApplicationNo
FROM App_ReceiveSettlementInvoiceItems ri
INNER JOIN App_ReceiveSettlements rs ON rs.Id = ri.ReceiveSettlementId AND rs.IsDeleted = 0
INNER JOIN App_InvoiceApplications ia ON ia.Id = ri.InvoiceApplicationId
WHERE ri.IsDeleted = 0
  AND NOT EXISTS (
      SELECT 1 FROM App_InvoiceIssueItems ii
      INNER JOIN App_InvoiceIssues iss ON iss.Id = ii.InvoiceIssueId AND iss.IsDeleted = 0
      WHERE ii.InvoiceApplicationId = ri.InvoiceApplicationId AND ii.IsDeleted = 0);
```
