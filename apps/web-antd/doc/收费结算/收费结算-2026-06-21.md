# 1. 背景意图 (Background)

**白话解释：** 银行流水(`BankStatement`)上可以配置“操作人”(`BankStatementUsers`)。当某条银行流水配置了操作人后，针对其关联的收费结算的写操作应当受限——只有该流水的操作人（或拥有银行流水编辑权限的人）才能新增/修改对应的收费结算；若该流水未配置操作人，则不限制（沿用实体注释“操作人 没配置的话都能看”的口径）。

本次为 `ReceiveSettlementAdmin` 的 **新增(AddAsync)** 与 **修改(EditAsync)** 增加该校验。

# 2. 核心逻辑变更 (Core Changes)

新增私有方法 `ValidateBankStatementOperationPermissionAsync(Guid bankStatementId)`，校验规则：

1. 当前用户拥有 `FreightPermissions.Admin_BankStatement_Edit` 权限 → 放行，不受操作人限制。
2. 否则取该银行流水的操作人 `OperationId` 列表：
   - 操作人列表为空 → 放行。
   - 操作人列表非空 → 当前用户(`AbpSession.GetUserId()`)必须在其中，否则抛出 `当前用户不是该银行流水的操作人,无权操作`。

接入点：

| 接口        | 位置                       | 说明                              |
| :---------- | :------------------------- | :-------------------------------- |
| `AddAsync`  | 加载并校验银行流水存在之后 | 使用 `input.BankStatementId` 校验 |
| `EditAsync` | 校验主表存在/未锁定之后    | 使用 `data.BankStatementId` 校验  |

涉及文件：`src/CsprojBuilder.Application/App/ReceiveSettlement/ReceiveSettlementAdminAppService.cs`

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. 操作人取自 `BankStatement.BankStatementUsers[].OperationId`(long，用户Id)，与登录用户 `AbpSession.GetUserId()` 比对。
> 2. “无操作人即放行”是刻意设计（与银行流水可见性逻辑一致），不要改成“无操作人则禁止”。
> 3. 权限放行只认 `Admin_BankStatement_Edit`，不要误用收费结算自身的增删改权限。
