# 0. 文档说明

本文档是**提成单模块的唯一逻辑口径来源**，供开发、测试、前端共同使用。文档落地了《原始逻辑文档.txt》中已确认的全部逻辑，并把口径拆到字段级。

提成整体分两部分。第一部分「提成配置」配的是**规则**（谁按什么算），见 `文档\提成配置\提成配置模块总逻辑文档.md`。本模块是第二部分「提成单」，负责**按规则把钱算出来、走审批、发放**，并在算完之后把涉及的票锁住不让改。

本模块包含 17 个新增接口 + 4 张新增表 + 3 张存量表加 4 个字段 + 3 个新增枚举 + 7 个权限点。

# 1. 业务背景说明 (Background)

**白话解释：**

月底了要给员工发提成。发多少不是拍脑袋，是按第一部分配好的规则算出来的：

- **销售提成**看赚了多少钱。把这个销售名下、这个月（及之前月还没提过）的票挨个算利润，达到门槛的加起来得到总利润，套固定比例或阶梯算出提成，再把亏损票的钱按比例扣掉。
- **操作提成**看做了多少活。把这个操作名下的票挨个拿去比对条件（起运港是哪、货物类型是什么、或者干脆按票计费），命中的金额累加。

算完生成一张提成单，提交审核，审核通过后发放。**提成单一旦建立，它算过的那些票就被锁住**——费用不能再动、销售不能换、会计期间不能挪。道理很简单：钱都发了，凭据不能再变。

**一张提成单 = 一个提成人 + 一种提成类型 + 一个提成月。** 新建时可以一次传多个月，就生成多张。

# 2. 数据模型 (测试必读)

## 2.1 表关系

```
CommissionOrder (提成单主表 App_CommissionOrders)
  ├─ CommissionOrderItem[]  (参与计算的票 App_CommissionOrderItems)
  │     └─ CommissionOrderItemRule[] (该票命中的条件项 App_CommissionOrderItemRules) ← 仅操作提成
  └─ CommissionOrderStep[]  (计算步骤 App_CommissionOrderSteps)

存量表反向持有提成单id:
  TransportOrder.SalesCommissionOrderId      ← 主单原票被哪张销售提成单算过
  TransportOrder.OperationCommissionOrderId  ← 本业务被哪张操作提成单算过
  ChangeOrder.SalesCommissionOrderId         ← 本更改单被哪张销售提成单算过
```

**关键点：**

1. **主表分租户**（`IMustHaveTenant`）且**参与数据权限**（继承 `DataPermissionFullAuditedEntity<Guid>`）。**`UserId`（所属人）就是提成人**，与 `TransportOrder.UserId = 当票销售` 是同一个套路，数据权限因此天然生效，不用再开一套。
2. **主键全部是 `Guid`**。3 张子表都是**硬删除**实体（`Entity<Guid>`），主表软删除。
3. **金额与计算过程全部是新建时算好落库的快照。详情读快照，不实时重算。** 提成配置是可编辑的，实时重算会让历史提成单的金额跟着配置变。

## 2.2 一票的定义

贯穿全模块的核心概念。**一票 = 一个主单原票，或一个更改单。**

| 票 | `ChangeOrderId` | 会计期间取自 | 费用范围 |
| :-- | :-- | :-- | :-- |
| 主单原票 | 空 | `TransportOrder.AccountDate` | `OrderFee.ChangeOrderId` 为空的那批 |
| 更改单 | 更改单id | `ChangeOrder.AccountDate` | `OrderFee.ChangeOrderId` 等于该更改单 |

一个主单挂 3 个更改单，就产生 4 票，各自可能落在不同月份、进不同的提成单。这也是为什么 `ChangeOrder` 要单独持有一个销售提成单id。

**操作提成只按主单算，更改单不参与**——操作提成看的是「做了什么活」，不是费用。

# 3. 状态流转

| 当前状态 | 触发人/动作 | 目标状态 | 说明 |
| :-- | :-- | :-- | :-- |
| —— | 新建 | 录入状态 | 新建即把提成单id写回业务表，票被锁住 |
| 录入 / 驳回 | 提交审核 | 提交审核 | 走通用工作流；全节点都是「直接通过」时会直接跳到审核通过 |
| 提交审核 | 撤销提交 | 录入状态 | 只有**还没有任何人审过**才能撤 |
| 提交审核 | 审核-通过 | 审核通过 | 多级审批时前面几级通过不改单据状态 |
| 提交审核 | 审核-驳回 | 审核驳回 | 驳回原因必填 |
| 提交审核 / 审核通过 | 审核后驳回 | 审核驳回 | 已发放的不可驳回 |
| 审核通过 | 发放 | 发放完成 | **终态，不能再做任何操作** |
| 录入 / 驳回 | 删除 | —— | 删除时清空业务表上的提成单id，把票放开 |

> [!IMPORTANT] **驳回与录入在行为上完全等价**：都能提交、都能删除。分成两个枚举值只是为了让前端能区分显示「还没提过」和「被打回来了」。

**能删的只有录入与驳回。** 审核中、审核通过、发放完成都删不掉。

# 4. 配置命中 (核心)

## 4.1 一张提成单只命中一条配置

给定「提成人 + 提成类型 + 提成月」，按下面的顺序找**唯一一条**配置：

| 顺序 | 找什么 |
| :-- | :-- |
| 1 | 适用人里点名了提成人的配置 |
| 2 | **提成人自己的组织**，从组织层级低到高逐级往上找；提成人属于多个组织时，**默认组织所在的那条路径先走** |

参与候选的前提（与提成配置文档 3.3 一致）：配置已启用、提成类型匹配、生效期覆盖提成月。同一级命中多条时按配置 `SortId` 升序、再按创建时间升序取第一条。

**命中不到就不能新建**，确认接口会在「不能提交的原因」里说明。

> [!IMPORTANT] **这里改掉了提成配置文档原先的口径。**
>
> 提成配置文档 3.2 原本写的是「按**票的**所属组织匹配配置」。但销售提成是按总利润汇总再套阶梯的，一个销售的票分散在两个组织就会命中两条配置，两套阶梯没法合并成一个数。所以改成**按提成人自己的组织**匹配，一个人一个月只可能命中一条。
>
> 操作提成也一并改成按操作人自己的组织，两边口径统一。提成配置文档已同步。

## 4.2 适用业务类型是用来筛票的，不参与命中

配置的「适用业务类型」不参与「这条配置适不适用于这个人」的判定。命中配置之后，用它筛**哪些票参与计算**：票的业务类型必须在里面，配置里为空则不限。

# 5. 销售提成的算账口径

## 5.1 参与计算的票（第一部分）

```
会计期间 ≤ 提成月
  且 这一票下属费用全部已结算（每条费用 SettlementStatus == Settlemented）
  且 还没被任何销售提成单认领（SalesCommissionOrderId 为空）
  且 业务类型在配置的适用业务类型里（配置为空则不限）
  且 销售是提成人（OrderUser 里 UserAttribute.Sale）
```

> [!IMPORTANT] **注意是「≤ 提成月」而不是「= 提成月」。** 上个月的票这个月才结清的，会自然出现在本月提成单里——这就是「后补的放到下一个提成月」。明细里每票带自己的会计期间，能看出「这票是 8 月的，算在 9 月」。

**一条费用都没有的票直接排除**：既算不出利润，返回也只是噪音。

**不需要再单独筛费用审核状态。** 录入/待审/驳回状态的费用不会被结算，`SettlementStatus` 恒为未结算，这一票过不了「全部已结算」。所以「全部已结算」已经隐含了「全部审核通过」。

**机密费用照常参与计算**，跟操作人有没有查看权限无关。

## 5.2 未全部结算的票（第二部分）

```
会计期间 ≤ 提成月
  且 这一票下属费用未全部已结算
  且 销售是提成人
```

**往前追到底，不做历史数据处理。** 第二部分有值就不能提交——销售提成要求当月及之前月全部结清。

第一部分和第二部分正好互补：能提交时（第二部分为空），所有 ≤ 提成月的票要么早就提过了、要么落在第一部分。

## 5.3 汇率

**提成有自己独立的一列汇率：`ExchangeRate.CommissionValue`（提成汇率）。按会计期间月取，应收应付共用这一个值。**

```
折算率 = ExchangeRate 表中
           CurrencyId = 该费用币别
         且 LocalCurrency = 'RMB'
         且 Enable = true
         且 StartDate ≤ 该票会计期间月1号 ≤ EndDate（两端为空视为不限）
         的记录的 CommissionValue（提成汇率）
```

| 情况 | 处理 |
| :-- | :-- |
| 币别是人民币（`Currency.Code == "RMB"`） | **不查表，折算率恒为 1** |
| 区间重叠命中多条 | 取 `StartDate` 最晚的一条（最新生效） |
| 查不到 | **不能新建**，确认接口在第四部分给出「币别【X】缺少 yyyy-MM 的提成汇率 请先在汇率表配置」 |

> [!IMPORTANT] **提成汇率是为提成新加的一列，不复用应收汇率 `DRValue` 或应付汇率 `CRValue`。**
>
> 汇率表原有五列（应收、应付、海关、核算、发票）都是按业务口径分的，应收应付还各一列；提成算的是「利润」这个跨收付的口径，用哪一边都不对，所以单开一列，收付共用它。
>
> 这也意味着**汇率表要额外把提成汇率维护起来**——只配了应收应付、没配提成汇率，提成单就建不出来。

> [!NOTE] 这跟报表模块不一样。报表用的是**每条费用行自己存的 `ExchangeRate`**；提成用的是**按会计期间月查汇率表的提成汇率**，同一批费用两边算出来的本位币金额会不同，这是设计如此。

## 5.4 一票的利润

```
应收合计(本位币) = Σ(应收费用.Amount × 该票会计期间的提成汇率)
应付合计(本位币) = Σ(应付费用.Amount × 该票会计期间的提成汇率)
利润           = 应收合计 − 应付合计
```

**应收应付用的是同一个提成汇率**，不像别的模块那样应收取 `DRValue`、应付取 `CRValue`。

## 5.5 分类与算账

按门槛把票分三类：

| 分类 | 判定 | 作用 |
| :-- | :-- | :-- |
| 负利润扣减 | 利润 < 0 | **与门槛无关**，只要为负就参与扣减 |
| 达标计入 | 门槛比较符为「大于」时 利润 > 门槛；为「大于等于」时 利润 ≥ 门槛 | 计入总利润 |
| 未达门槛 | 其余（利润在 0 与门槛之间） | 既不计提也不扣减 |

然后：

```
总利润 P = Σ 达标票利润
提成    = f(P) − |Σ 亏损票利润| × 负利润提成比例%
```

`f(P)` 按配置的计算方式：

| 计算方式 | 算法 |
| :-- | :-- |
| 固定比例 | `P × 固定比例%` |
| 按阶梯(阶梯内分段计费) | 逐档拆开，每档取 `min(P, 档上限) − 档下限` 乘该档比例，各档相加 |
| 按阶梯(达标后整体到档) | `P` 落在哪一档（最后一个满足 `P ≥ 档下限` 的档），整体按该档比例计提 |

**算出来是负数就是负数，允许发负值**，不置 0、不结转。

## 5.6 计算步骤

每一步都结构化落库（见 2.4），前端直接渲染。销售提成的步骤序列：

```
1  达标利润汇总   达标票12票 总利润300000.00（门槛大于500.00；未达门槛3票不计）
2  阶梯档         阶梯 0.00~100000.00 落入100000.00 × 5.00% = 5000.00
3  阶梯档         阶梯 100000.00~无上限 落入200000.00 × 10.00% = 20000.00
4  负利润扣减     负利润扣减 亏损2票合计-8000.00 × 100.00% = -8000.00
5  底薪           提成与底薪取最大值 max(提成17000.00, 底薪5000.00) = 17000.00
6  合计           最终应发 17000.00
```

# 6. 操作提成的算账口径

## 6.1 参与计算的票

```
会计期间 ≤ 提成月（TransportOrder.AccountDate）
  且 还没被任何操作提成单认领（OperationCommissionOrderId 为空）
  且 业务类型在配置的适用业务类型里（配置为空则不限）
  且 操作是提成人（OrderUser 里 UserAttribute.Operation，前端限制一票只有一个操作）
```

**只有主单，更改单不参与。完全不看费用的审核与结算状态。**

跟销售提成一样是「≤ 提成月」：9 月才补录的 8 月会计期间业务，会进 9 月的操作提成单。

**一条条件项都没命中、金额为 0 的票也会返回**，便于对账（这个月做了 30 票，其中 12 票有提成）。

## 6.2 条件判定

一票把所有条件项挨个判一遍，**命中的金额全部累加**（不是取最高、不是命中一条就停）。

一个条件项的命中判定：**条件组之间为或，组内为且**。

| 条件字段 | 取值来源 |
| :-- | :-- |
| 海运起运港 / 海运目的港 | 海运出口取 `SeaExport.POLId/PODId`，海运进口取 `SeaImport.POLId/PODId` |
| 空运起运地 / 空运目的地 | 空运出口取 `AirExport.POLId/PODId` |
| 货物类型 | `TransportOrder.CargoId` |
| 按票 | **恒成立**，没有值也不看比较符 |

比较符：等于 / 不等于 / 包含于 / 不包含于。

> [!IMPORTANT] **该业务类型没有这个字段、或这票没填，一律判不命中**——包括「不等于」和「不包含于」也判不命中。没有值就谈不上比较。
>
> 所以海运起运港条件对空运出口的票恒不命中，空运起运地条件对海运的票恒不命中。配置时建议把适用业务类型一并选上。

## 6.3 计算步骤

按条件项汇总，一个条件项一条：

```
1  条件项命中   条件项【危险品或冻柜】命中12票 × 每票10.00 = 120.00
2  条件项命中   条件项【按票计费】命中30票 × 每票10.00 = 300.00
3  条件项命中   条件项【天津港】命中8票 × 每票5.00 = 40.00
4  底薪         底薪直接加 提成460.00 + 底薪3000.00 = 3460.00
5  合计         最终应发 3460.00
```

# 7. 底薪

底薪与底薪模式取自命中配置的快照，**两者都有值才计算底薪**，只填一个视为不计。

| 模式               | 算式                                             |
| :----------------- | :----------------------------------------------- |
| 直接加             | `最终 = 提成 + 底薪`                             |
| 提成与底薪取最大值 | `最终 = max(提成, 底薪)`；提成为负时结果就是底薪 |

**销售提成单与操作提成单各自独立计算底薪，不做跨类型去重。** 一个人两种提成都配了底薪就会各加一次——这是配置层面要规避的问题，本模块不管。

# 8. 新建前确认接口

## 8.1 销售提成：四部分

| 部分     | 内容                                                              |
| :------- | :---------------------------------------------------------------- |
| 第一部分 | 参与本月计算的票（见 5.1），每票带利润、分类、原币明细            |
| 第二部分 | 会计期间 ≤ 提成月但未全部结算的票（见 5.2），每票带未结清费用条数 |
| 第三部分 | `CanSubmit` 是否可提交                                            |
| 第四部分 | `CannotSubmitReasons` 不能提交的原因列表                          |

**第一部分同时带回本月算出来的完整计算结果**（含全部步骤）。

不能提交的原因目前有三类：

1. 提成人在该月没有命中任何启用中的销售提成配置
2. 某币别缺少该月的**提成汇率**
3. 存在 N 票在该月及之前的费用未全部结算

## 8.2 操作提成

结构类似，但只有票列表 + 计算结果 + 是否可提交 + 原因。不能提交的原因只有「没有命中配置」一类。

## 8.3 通用

- **输入几个提成月就返回几组**，按提成月升序
- **这两个接口只算不写库**
- 详情接口结构类似，但**只返回该月的、只读快照，不含第二部分和是否可提交**

# 9. 新建、删除与提成单id的写入清空

## 9.1 提成单id 新建就写，删除才清

| 时机 | 提成单id |
| :-- | :-- |
| 新建 | **写入**。销售提成写主单原票与各更改单，操作提成写主单 |
| 提交审核 | 不变 |
| 撤销提交 | **不清**。撤销后还能重新提交，这批票不该被别人改动 |
| 审核驳回 / 审核后驳回 | **不清**。驳回后还能二次提交，同上 |
| 发放完成 | 不变 |
| 删除 | **清空**，把这批票放开 |

「新建就锁」而不是「提交才锁」，是因为从新建到提交之间费用还能改，改完提成单里的金额就跟实际对不上了。

## 9.2 新建时的硬校验

| 校验 | 说明 |
| :-- | :-- |
| 提成人在数据权限范围内 | 按 `GetDataPermissionUserIdsAsync` 判，用户不在可见用户里时再按其所属组织放一次 |
| 提成月必须小于当前月 | 9月1日只能提8月及之前，当月不能提 |
| 同一提成人+提成类型+提成月只能有一张 | 已存在直接报错，**不允许同月开第二张补提单** |
| **提成月必须连续，不能跳月** | 已提到 7 月就只能接着提 8 月。直接提 9 月会把 8 月该算的票一起卷进来，谁都对不上账 |
| 销售提成：命中配置 | 命中不到不能新建 |
| 销售提成：汇率齐全 | 缺哪个币别哪个月的**提成汇率**就不能新建 |
| 销售提成：第二部分为空 | 当月及之前月的费用必须全部结清 |

**提成月一次可以传多个，按升序逐月生成，连续性沿着这一批往下推。**

第一部分为空（这个月一票都没有）**允许新建**，生成一张 0 元的提成单。

## 9.3 删除

删除时逐层清理：

```
清空业务表与更改单上的提成单id
  → 条件项命中(孙表) → 明细 → 计算步骤
  → 审核任务 TaskItem 与工作流实例 WorkFlowInstance
  → 主表(软删)
```

> [!IMPORTANT] **提成单id 必须先清。** 不清那批票就被永久锁死，谁都改不了。

# 10. 审批与发放

## 10.1 走通用工作流

接入方式与付费申请一致：`TaskItem`（`TaskType.CommissionOrder`，`EntityId` = 提成单id）+ `WorkFlowInstance` + `AuditWorkFlowInstanceAsync`。

**必须先在工作流模块配好并启用 `TaskType = 提成单` 的流程**，否则提交时报「未配置或未启用提成单工作流，无法提交审核」。

工作流可用的分流条件（`TaskTypeCondition`）：

| 条件 | 比较符 | 值 |
| :-- | :-- | :-- |
| `CommissionOrderUserId` 提成人 | 等于 / 不等于 | 用户id |
| `CommissionOrderOrgID` 提成人组织 | 属于 / 不属于 | 组织id（自动展开下级） |
| `CommissionOrderAmount` 最终应发金额 | 大于 / 大于等于 / 小于 / 小于等于 | 金额，允许为负 |

全节点都是「直接通过」时不插工作流实例，提交后单据直接变审核通过。

## 10.2 撤销提交

只有**审核中**且**没有任何人审过**（工作流实例里没有 Passed/Rejected 的记录）才能撤。撤销会删掉工作流实例与任务，状态回到录入。

## 10.3 审核与驳回

- **审核**：通过或驳回。多级审批时前面几级通过不改单据状态（`AuditWorkFlowInstanceAsync` 返回 true 就直接返回）。驳回原因必填。
- **审核后驳回**：审核中与审核通过都能驳；**已发放的不可驳回**。会同步把工作流实例与任务改成驳回。
- 驳回后可以二次提交，重新提交会删掉旧的工作流实例重新生成路径（审批人可能已经变了）。

## 10.4 审批历史：不保留，只留最近一轮的结论

**重新提交时会把提成单上的 `AuditUserId` / `AuditTime` / `AuditRemark` 一并清空**，所以「审核中」状态的单据这三个字段恒为空，不会顶着上一轮的审核人和驳回原因给人看。清空动作放在 `SubmitAsync` 进工作流**之前**，因为无审核人直接通过的分支会在 `CreateWorkFlowInstanceAsync` 里回填 `AuditTime`，顺序反了会被清掉。

由此带来的**已知取舍**：一旦重新提交，上一轮谁驳的、什么意见就查不到了。多级审批中前面几级由谁通过的也不保留——`WorkFlowInstance` 与 `WorkFlowInstanceItems` 在重新提交时被删除重建，这是平台层的既定行为（见 `WorkFlowInstance` 实体注释「一条的审核只保留一个 驳回再提交就删了新建」），付费申请与业务联系单同样如此。这些行是软删除，数据物理上还在库里，但被 ABP 全局过滤器挡住，应用层查不到。

**需要完整审批留痕的话要单独建一张提成单审批记录表，当前没做。**

`AuditTime` 有值而 `AuditUserId` 为空，代表该单匹配到的工作流没有配审核人、提交即通过，没有人工终审。

## 10.5 发放

只有审核通过的可发放。**实际发放金额由发放人自由填写，不校验是否等于应发金额，允许为负。**

发放完成是终态：不能撤销、不能驳回、不能删除。

## 10.6 批量：审核、审核后驳回、发放

这三个操作各有一个批量版本，行为与单条完全一致，只是一次处理多张。

**统一口径：先把整批校验一遍，任何一张不满足条件就整批报错、一条都不改。** 不做「能处理几条算几条」，跟付费申请的批量审核、提成单删除、汇率同步是同一套做法。代价是报错文案只能说「存在某某状态的提成单」，指不到具体哪一张——需要定位就先按状态筛列表再勾。

| 操作 | 与单条的差异 |
| :-- | :-- |
| 批量审核 | 一批共用同一个通过/驳回结论与同一条审核意见。一批里可以混着「审完了」和「还要下一级」的单子——某张还有下一级时它的状态先不动，同批其它单照常继续 |
| 批量审核后驳回 | 一批共用同一条驳回原因。与单条一样容忍任务缺失（找不到 `TaskItem` 的只改单据本身，不报错） |
| 批量发放 | **一律按各自的 `FinalAmount` 全额发放，没有金额入参**；**发放备注必填**（单条是选填）。要改金额只能走单条 |

批量发放做成全额发放 + 备注必填，是因为批量场景下既不填金额又不填备注的话，事后完全看不出这批是怎么回事——单条至少还有个可自由填写的金额能体现意图。

批量接口**不另开权限点**，跟对应的单条共用 `Admin.CommissionOrder.Audit` / `Admin.CommissionOrder.Grant`。

# 11. 提成单对存量模块的锁定 (守卫清单)

这是本模块对系统其它部分影响最大的一块，测试要重点覆盖。

## 11.1 销售提成锁（`SalesCommissionOrderId` 有值）

**这一票的费用不可做除查询外的任何操作，销售不可改，会计期间不可改。**

| 位置 | 拦什么 | 报错文案 |
| :-- | :-- | :-- |
| `OrderFeeAdminAppService.FeeLockedCheckAsync` | 一处覆盖：费用提交、申请修改、申请删除、审核后驳回、导入费用、收付转 | 已提交销售提成不可操作费用 |
| `OrderFeeAdminAppService.DeleteAsync` | 直接删费用，**逐票判**（待删费用可能横跨主单原票与多个更改单） | 已提交销售提成不可删除费用 |
| `OrderFeeAdminAppService.BatchEditAsync` | 批量编辑主单费用 | 已提交销售提成不可编辑费用 |
| `ChangeOrderAdminAppService.EditAsync` | 编辑更改单（费用 + 会计期间） | 已提交销售提成不可编辑更改单 |
| `ChangeOrderAdminAppService.DeleteAsync` | 删除更改单 | 已提交销售提成不可删除更改单 |
| `TransportOrderAdminAppService.EditAsync` | **会计期间变化时**才拦 | 已提交销售提成不可修改会计期间 |
| 海出/海进/空出 `EditAsync` | 改 ETD 导致会计期间变、改销售 | 已提交销售提成不可修改会计期间 / 不可修改销售 |
| 海出/海进/空出 `DeleteAsync` | 删除业务 | 已提交销售提成不可删除 |
| `BankStatementWriteOffManager` 取消核销 | 把 `SettledAmount` 减回去、结算状态退回 | 已提交销售提成不可取消核销 |
| `ExchangeRateAdminAppService` 同步费用汇率 | 批量刷 `OrderFee.ExchangeRate` | 已关联销售提成不可同步汇率 |

> [!IMPORTANT] **取消核销这一条最隐蔽。** 销售提成的前提是「这一票全部已结算」，钱可能已经发了；这时候把结算撤掉，账就再也对不上。这是整条链路上最容易漏的洞。

## 11.2 操作提成锁（`OperationCommissionOrderId` 有值）

| 位置 | 拦什么 | 报错文案 |
| :-- | :-- | :-- |
| 海出/海进/空出 `DeleteAsync` | 删除业务 | 已提交操作提成不可删除 |
| 海出/海进/空出 `EditAsync` | **被锁定的条件字段**发生变化 | 已提交操作提成不可编辑提成相关字段 |

**锁定哪些字段是动态的**：读的是提成单上的 `LockedConditionFields` 快照，它在新建那一刻从命中配置的条件里解析出来。

- 配置里只用了货物类型 → 只锁货物类型，港口照常能改
- 配置里用了海运起运港 → 起运港也锁上
- **「按票」条件不锁任何字段**（它对所有票恒成立，跟业务字段无关）
- 之后配置怎么改，都不影响已建提成单的锁定范围

## 11.3 换销售的防作弊校验

**该票还没被提成时**，销售可以改，但有一条限制：

> 新销售在这一票涉及的**任何会计期间**下都不能已经有销售提成单。

拿主单会计期间 + 它所有更改单的会计期间去查。报错：`该销售在会计期间【yyyy-MM】已存在销售提成单 不可把本业务改到他名下`。

**防的是这种玩法**：把亏损票临时划给别人 → 自己提完提成（少了这票的扣减）→ 再划回来。

反方向不用管：本票若已被提成，销售根本改不动。

# 12. 数据权限与权限点

## 12.1 数据权限

主表继承 `DataPermissionFullAuditedEntity<Guid>`，走项目统一口径。**`UserId`（所属人）就是提成人。**

| 项 | 口径 |
| :-- | :-- |
| 分页列表与详情 | `DataPermissionFilterAsync`：提成人在可见用户集合内，**或**所属组织在可见组织（含下属组织）内 |
| 删除 / 提交 / 撤销 | 同上过滤后按 id 取，取不到统一报「输入提成单错误或无权XX」 |
| **审核 / 审核后驳回 / 发放** | **不过数据权限**——审的就是别人的单子，能审到才是常态，由权限点控制 |
| **待我审核列表 / 待发放列表** | **不过数据权限**，与上一行保持一致 |
| 新建时选提成人 | 提成人必须在当前登录人的数据权限范围内 |

### 三个列表分别给谁用

审核和发放不过数据权限，如果只有一个走数据权限的分页列表，**审核岗和发放岗就会看不到该自己处理的单子**——接口调得通但列不出来。所以按岗位拆了三个列表：

| 列表 | 给谁 | 数据权限 | 取数口径 |
| :-- | :-- | :-- | :-- |
| `GetPagedListAsync` | 制单人 | **过** | 自己可见范围内的全部提成单 |
| `CommissionOrderTaskListAsync` | 审核岗 | 不过 | 从 `WorkFlowInstanceItem` 反查 `UserId = 当前登录人` 且 `TaskType = 提成单` 的任务 |
| `CommissionOrderGrantListAsync` | 发放岗 | 不过 | 状态写死为审核通过，入参里没有状态字段 |

待我审核列表的实现与 `PreOrderTaskListAsync`、`PayAppTaskListAsync` 同构，出参是「任务信息 + 提成单信息」：除提成单本身外还带 `MyStatus`（我这一级的状态）和 `TaskItemWorkFlowInstance`（逐级审批明细）。

两个要点：**出参的 `Id` 是任务id，`CommissionOrderId` 才是提成单id**，调审核接口要传后者。**`MyStatus` 不传时我这条为空的也要返回**——或签下别人先审我这条会被主动置空，多级审批里还没轮到我的同样为空，按状态筛会把这些单子漏掉。

提交时匹配到的工作流没有审核人的单据不会进待我审核列表：它们提交即通过，压根没有工作流实例。

## 12.2 权限点

| 权限常量 | 权限字符串 | 控制 |
| :-- | :-- | :-- |
| `Admin_CommissionOrder` | `Admin.CommissionOrder` | 提成单（父节点） |
| `Admin_CommissionOrder_Add` | `Admin.CommissionOrder.Add` | 新建 |
| `Admin_CommissionOrder_Get` | `Admin.CommissionOrder.Get` | 两个确认接口 + 列表 + 两个详情 |
| `Admin_CommissionOrder_Delete` | `Admin.CommissionOrder.Delete` | 删除 |
| `Admin_CommissionOrder_Submit` | `Admin.CommissionOrder.Submit` | 提交审核 + 撤销提交 |
