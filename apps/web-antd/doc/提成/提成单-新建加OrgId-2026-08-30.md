# 1. 背景意图 (Background)

提成单算利润要把各币别的费用按**提成汇率**（`ExchangeRate.CommissionValue`）折算成本位币。原来这个本位币是写死的：

```csharp
private const string LocalCurrencyCode = "RMB";
```

汇率表的本位币已改成显式外键并由所属公司解析（见 [汇率-本位币改外键-2026-08-30.md](../汇率/汇率-本位币改外键-2026-08-30.md)），提成这边也得跟上，否则本位币不是人民币的公司算不出提成。

要按公司解析本位币，就得先知道是哪个公司。而提成单的所属组织原来是**自动推的**：

```csharp
var orgId = (await GetUserOrganizationPathsAsync(input.UserId))
    .FirstOrDefault()?.OneOrganizationPath?.LastOrDefault()?.Id;
```

提成人挂在多个组织时，`FirstOrDefault` 取到哪个组织是不确定的，跟着解析出的公司和本位币也就不确定。所以本次把 `OrgId` 改成**由前端必填传入**。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 两个接口新增必填 `orgId`

| 接口 | 入参 DTO | 新增字段 |
| :-- | :-- | :-- |
| `POST /api/services/app/CommissionOrderAdmin/GetSalesPreviewAsync` | `CommissionPreviewQueryDto` | `orgId`(`long?`，**必填**) |
| `POST /api/services/app/CommissionOrderAdmin/GetOperationPreviewAsync` | `CommissionPreviewQueryDto` | 同上 |
| `POST /api/services/app/CommissionOrderAdmin/AddAsync` | `CommissionOrderAddDto` | `orgId`(`long?`，**必填**) |

> [!IMPORTANT] **新建前确认接口也必须传，而且要与新建时传的一致。**
>
> 确认接口与新建走的是**同一个** `BuildRateMapAsync`。如果确认时不传（或传了别的组织），确认页上算出来的利润会跟真正生成的提成单对不上——一个用 A 公司的汇率、一个用 B 公司的，用户核对完点确定，拿到的是另一个数。
>
> 前端应把「所属公司/组织」做成新建流程开头就选定的一个值，确认与提交复用同一个。

校验放在 `ValidatePreviewInputAsync`（两个接口共用），用的是项目通用的 `EnsureUserOwnsOrgAsync(input.OrgId, new List<long>{ input.UserId })`：**所属组织必须是提成人（不是当前登录人）的直属组织**。这与提成单「数据所属人 = 提成人」的口径一致。

报错文案沿用基类：为空报「所属组织不能为空。」，不在提成人组织范围内报「所选组织不在数据所属人(本人)所属组织范围内。」。

## 2.2 提成汇率按公司本位币解析

```csharp
// 旧
BuildRateMapAsync(tickets)                     // 内部写死 LocalCurrency == "RMB"
// 新
BuildRateMapAsync(tickets, localCurrencyId)    // 本位币由 OrgId 所属公司解析
```

`localCurrencyId` 来自 `EnsureCompanyLocalCurrencyIdAsync(orgId)`，公司没配本位币直接报「当前公司未配置本位币」。

同时改掉了**两处**按币别代码判断的地方，不是只有查询条件那一处：

| 位置 | 旧 | 新 |
| :-- | :-- | :-- |
| 汇率查询条件 | `r.LocalCurrency == "RMB"` | `r.LocalCurrencyId == localCurrencyId` |
| 「费用币别即本位币则折算率恒为 1」的短路 | 按 `Code == "RMB"` 反查出一组 id 再判 | 直接 `pair.CurrencyId == localCurrencyId` |

其余口径不变：仍然只认 `Enable = true` 且 `CommissionValue` 有值的记录，区间重叠取 `StartDate` 最晚的一条，查不到的币别记进 `CannotSubmitReasons`（文案不变：`币别【XXX】缺少YYYY-MM的提成汇率 请先在汇率表配置`）。

## 2.3 只算本组织范围内的业务（过滤，不报错）

取票时**只纳入「所属组织落在提成单 `OrgId` 及其所有下级组织范围内」的业务**，其余的直接不算。组织范围用基类的 `GetOrgAndDescendantIdsAsync(orgId)` 取，过滤条件直接下推到 SQL。

> [!NOTE] **按组织过滤就够了，不需要再逐票比本位币。**
>
> 本位币配在公司节点上，同一公司下所有业务的本位币必然相同。既然 `OrgId` 已经把范围圈定在一个公司（或其下某个部门）内，圈进来的票本位币天然一致，再去逐票解析公司本位币做比对是多余的一层，还得把票捞回内存才能筛。

> [!IMPORTANT] **这里是过滤，不是报错，是有意的。**
>
> 销售提成的票是按「该销售名下的全部业务」自动收集的，用户没法逐票勾选取消。如果改成「有别的组织的票就报错」，一个在两个公司都有业务的销售将**彻底建不了提成单**。
>
> 按组织过滤之后，他可以在两个公司各建一张——这正是把 `OrgId` 改成必填的意义。

过滤统一放在 `LoadSalesTicketsAsync` 里（入参是解析好的 `orgIds` 集合），**5 个调用点全部生效**：

| 调用点                    | 组织范围取自                     |
| :------------------------ | :------------------------------- |
| 新建前确认 - 已结算的票   | 入参 `orgId` 及其下级            |
| 新建前确认 - 未结算的票   | 入参 `orgId` 及其下级            |
| 新建 - 未结算校验         | 入参 `orgId` 及其下级            |
| 新建 - 取参与计算的票     | 入参 `orgId` 及其下级            |
| **提交审核 - 未结算复查** | `commissionOrder.OrgId` 及其下级 |

> [!IMPORTANT] **未结算校验也必须过滤，尤其是提交审核那一处。**
>
> 漏掉的话，A 公司的提成单会被 B 公司未结算的票卡住，报「存在 N 票在某月及之前的费用未全部结算」，而用户在 A 公司的范围里怎么找都找不到那 N 票，完全无从下手。

> 传空集合代表不限组织（老数据 `OrgId` 为空时的兜底），提交审核那处保留了这个分支。

## 2.4 提成单的 `OrgId` 落库来源变了

`NewOrderAsync` 不再自动推组织，直接落 `input.OrgId`。这个值同时影响三件事：

1. 提成单的所属组织（数据权限）；
2. **提成单号生成**——`GenerateNumAsync` 的 `OrgId` 用它，编号分段可能与以前不同；
3. 工作流按组织分流。

> [!NOTE] 操作提成不折算汇率（按规则金额直接累加），所以本位币对它没有实际影响。但 `orgId` 对它同样必填——提成单实体要落这个值，编号与工作流也要用。

# 3. 避坑指南 (Pitfalls)

- **确认与新建必须传同一个 `orgId`**，见 2.1 的警告框。这是本次最容易出线上问题的一处，且症状很隐蔽：不报错，只是数字对不上。
- **`orgId` 校验的是「提成人」的直属组织，不是当前登录人的。** 帮别人建提成单时，选的组织要落在**提成人**名下，不是操作人名下。
- **提成单号可能变段。** 以前编号按自动推出来的组织取号，现在按用户选的组织。如果编号规则按组织分了段，同一个提成人选不同组织会拿到不同段的号。
- **本位币不是人民币的公司现在能算提成了，但前提是汇率表里有对应本位币的提成汇率。** 只配了「XXX→RMB」的汇率，对本位币是 HKD 的公司无效，会直接报「缺少提成汇率」。
- **`CommissionOrder.OrgId` 仍是可空列**（继承自 `DataPermissionFullAuditedEntity`），但业务上现在必填。存量数据里自动推出来的 `OrgId` 不会被回改。
- **票会被静默过滤掉，用户看不出「少算了几票」。** 确认接口返回的就是过滤后的结果，所以确认页看到多少票就是多少票，不会与最终生成的对不上。但如果用户反馈「我这个月明明有 10 票，怎么只算了 6 票」，先查另外 4 票业务的所属组织是不是不在提成单 `OrgId` 及其下级范围内，或者那 4 票的业务压根没填所属组织。
- **`orgId` 传部门会把范围收得比公司更窄。** `GetOrgAndDescendantIdsAsync` 取的是「本组织 + 所有下级」，传部门就只算这个部门及其子部门的票，同公司其它部门的票不算。这是该方法的既定语义（与「按组织搜索」的口径一致），前端选组织时要让用户清楚选的是哪一级。
