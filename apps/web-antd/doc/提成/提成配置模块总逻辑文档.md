# 0. 文档说明

本文档是**提成配置模块的唯一逻辑口径来源**，供开发、测试、前端共同使用。文档落地了《原始逻辑文档.txt》中已确认的全部逻辑，并把口径拆到字段级。

提成整体分两部分，**本模块只做第一部分「提成配置」**：配置「谁按什么规则拿提成」。第二部分「提成单」（按月生成、提交审核、发放）不在本次范围内。

本模块包含 5 个新增接口 + 8 张新增表 + 6 个新增枚举 + 5 个新增权限点，**不改动任何存量表**。

| 序号 | 内容             | 类型     |
| :--- | :--------------- | :------- |
| 1    | 提成配置新增     | 新增接口 |
| 2    | 提成配置编辑     | 新增接口 |
| 3    | 提成配置删除     | 新增接口 |
| 4    | 提成配置分页列表 | 新增接口 |
| 5    | 提成配置详情     | 新增接口 |

> [!IMPORTANT] **本模块只存规则，不算钱。** 「一票利润怎么算」「取哪些费用」「多币种怎么折算」「统计周期怎么切」这些口径全部由第二部分提成单落地，见 `文档\提成单\提成单模块总逻辑文档.md`。
>
> 测试本模块时只测「能不能正确存取和校验」，算出来的提成金额去提成单模块测。

# 1. 业务背景说明 (Background)

**白话解释：**

公司要给员工发提成。发多少，取决于事先给这个人（或这个人所在的部门）设定的一条规则。这条规则就是「提成配置」。

提成分两种，**互不相干、规则完全不同**：

- **销售提成**：按**赚了多少钱**算。数据来源是费用表 `OrderFee`（应收 − 应付 = 利润）。一票一票地看利润够不够门槛，够的加起来得到总利润，再按固定比例或阶梯算出提成，最后把亏损票的钱扣掉。
- **操作提成**：按**做了什么活**算。数据来源是业务表 `TransportOrder`。事先配好若干条「满足什么条件就提多少钱」，一票业务把所有条件挨个判一遍，命中的钱加起来。

一个人可能既是销售又做操作，那就给他建两条配置，两笔提成分别算。

# 2. 数据模型 (测试必读)

## 2.1 表关系

```
CommissionConfig (提成配置主表 App_CommissionConfigs)
  ├─ CommissionConfigUser[]     (适用人 App_CommissionConfigUsers)
  ├─ CommissionConfigOrg[]      (适用组织 App_CommissionConfigOrgs)
  ├─ CommissionConfigBizType[]  (适用业务类型 App_CommissionConfigBizTypes)
  ├─ CommissionConfigTier[]     (提成阶梯 App_CommissionConfigTiers)          ← 仅销售提成
  └─ CommissionConfigRule[]     (操作提成条件项 App_CommissionConfigRules)     ← 仅操作提成
        └─ CommissionConfigRuleCondition[]      (条件 App_CommissionConfigRuleConditions)
              └─ CommissionConfigRuleConditionValue[] (条件值 App_CommissionConfigRuleConditionValues)
```

**关键点：**

1. **主表分租户**（`IMustHaveTenant`）且**参与数据权限**（继承 `DataPermissionFullAuditedEntity<Guid>`，带 `UserId` 所属人 + `OrgId` 所属组织）。7 张子表都不分租户、不参与数据权限，只能经由主表访问。
2. **主键全部是 `Guid`**。子表都是**硬删除**实体（`Entity<Guid>`，没有 `IsDeleted`），主表是软删除。
3. **条件是三层结构**：条件项 → 条件 → 条件值。库里条件用 `GroupId` 平铺存（组内为且、组间为或），接口返回时后端按 `GroupId` 聚合成嵌套结构，前端不用自己分组。

# 3. 配置命中规则 (核心)

## 3.1 一条配置给谁用

一条配置的适用范围 = **适用人**（可多选）+ **适用组织**（可多选），两者**至少填一个**，可以同时填。

## 3.2 一个人命中哪条配置：找到第一条就停

给定「某个人 + 某种提成类型 + 某个会计期间」，按下面的顺序找，**找到第一条就停，不叠加、不合并**：

| 顺序 | 找什么 |
| :-- | :-- |
| 1 | 适用人里点名了这个人的配置 |
| 2 | **这个人自己所属的组织**，沿组织层级**从低到高**逐级向上找，适用组织包含该级组织的配置 |

**这个人属于多个组织时**，先走**默认组织**（`User.DefaultOrgId`）所在的那条组织路径，再走其余路径。同一层级命中多条时按 `SortId` 升序取第一条，`SortId` 相同再按创建时间升序取第一条。

> [!IMPORTANT] **按组织匹配时看的是「这个人自己的组织」，不是「票的所属组织」。一个人一个会计期间只可能命中一条配置。**
>
> 曾经定过「按票的所属组织 `TransportOrder.OrgId` 匹配」，做提成单时发现走不通：销售提成是把一个人当月所有票的利润**汇总**之后再套阶梯的，票分散在两个组织就会命中两条配置，两套阶梯合不出一个数。改成按人的组织之后，「一人一月一条配置」成立，汇总才有意义。
>
> 操作提成也一并按操作人自己的组织匹配，两种提成类型口径统一。

## 3.3 参与命中的前提

一条配置要能被命中，必须同时满足：

1. `IsEnabled = true`（**停用的配置永不参与命中**）
2. 目标会计期间落在生效期内：`EffectiveStartDate == null || 目标月 >= EffectiveStartDate`，且 `EffectiveEndDate == null || 目标月 <= EffectiveEndDate`

> [!NOTE] **适用业务类型不参与「配置命不命中这个人」的判定。** 它是命中配置之后用来**筛哪些票参与计算**的：票的业务类型必须在里面，配置里为空则不限。

## 3.4 生效期按「会计期间月」，不是按天

`EffectiveStartDate` / `EffectiveEndDate` 虽然是 `DateTime`，但**只精确到月**。后端在保存时统一归一化为**当月1号**，传 `2026-08-17` 存进去就是 `2026-08-01`。

这么设计的原因：提成本身就是按月算的，生效期精确到天会造成「8月15号改了规则，8月这一整月按新的还是旧的」的歧义。按月切就没有中间态。

**改规则的正确做法是新增一条带新生效期的配置**，把老配置的截止期间设成上个月，而不是直接改老配置。直接改老配置会让已经发过的历史月份口径跟着变。

## 3.5 冲突校验：保存时就拦，不留到运行时

**同一个适用人（或同一个适用组织）+ 同一提成类型 + 业务类型有交集 + 生效期有重叠**，不允许存在第二条**已启用**的配置，保存时直接报错。

| 判定项 | 口径 |
| :-- | :-- |
| 是否参与校验 | 本条 `IsEnabled = false` 时**整个校验跳过**；比对时也**只跟已启用的配置比** |
| 提成类型 | 必须完全相同才可能冲突。同一个人一条销售、一条操作，不冲突 |
| 生效期重叠 | 两端都可空，空代表该方向不限制。`(aStart == null \|\| bEnd == null \|\| aStart <= bEnd) && (bStart == null \|\| aEnd == null \|\| bStart <= aEnd)` |
| 业务类型交集 | 任一方为空（=全部）即视为有交集；两方都非空则取交集判断 |
| 适用人 | 两条配置的适用人 id 有交集即冲突 |
| 适用组织 | 两条配置的适用组织 id 有交集即冲突 |

报错文案：`适用人【张三】在配置【XXX】里已有生效期重叠的销售提成规则,不允许重复设置`。

> [!NOTE] 冲突校验只拦得住「同一个人/同一个组织被配了两次」。「人在 A、B 两个平级组织，A 和 B 各有一条配置」这种情况**校验不出来**（两条配置的组织不同，本来就不冲突），只能由 3.2 的「找到第一条就停」在运行时决定用哪条。

# 4. 销售提成规则 (`CommissionType = Sales`)

只有提成类型为销售提成时才填这一组，操作提成时**必须不传**（传了报错）。

## 4.1 利润门槛

| 字段 | 说明 |
| :-- | :-- |
| `ProfitThreshold` | **必填，不能为负**。一票利润达到该值才把这一票的利润计入总利润 |
| `ProfitThresholdOperator` | **必填**。0大于（严格高于门槛才算）、1大于等于（等于门槛也算） |

「一票」的粒度是**原票和每个更改单各算一票**，因为它们各有各的会计期间，提成本来就是按会计期间算的。

## 4.2 负利润扣减

`NegativeProfitRate`（**必填**，取值 **0 ~ 1000**，单位是百分比）。

亏损票（利润 < 0）**不受门槛约束**，只要利润为负就参与扣减。计算顺序是：

```
正利润票中达到门槛的求和  →  P
亏损票(利润<0)求和        →  N (负数)
提成 = f(P) − |N| × NegativeProfitRate%
```

**算出来是负数就是负数，允许发负值**，不置0、不结转。

区间语义：`[负无穷, 0)` 直接按比例扣；`[0, 门槛]` 既不算提成也不扣；`(门槛, 正无穷)` 计入总利润算提成。

## 4.3 计算方式与阶梯

`SalesCommissionType` **必填**，三选一：

| 值 | 含义 | 要填什么 |
| :-- | :-- | :-- |
| 0 固定比例 | 总利润 × 固定比例 | `FixedRate` 必填，`Tiers` 必须为空 |
| 1 按阶梯(阶梯内分段计费) | 总利润逐档拆开，各档按各档比例计提后相加 | `Tiers` 必填至少一档，`FixedRate` 必须不传 |
| 2 按阶梯(达标后整体到档) | 总利润落在哪一档，就整体按该档比例计提 | 同上 |

**举例**（档位：0–10万 5%，10万以上 10%；总利润 30 万）：

- 阶梯内分段计费 = `10万 × 5% + 20万 × 10%` = **2.5 万**
- 达标后整体到档 = `30万 × 10%` = **3 万**

**阶梯的强校验**（不满足直接报错，因为阶梯是拿总利润去套档的，留缝或重叠会让总利润落到没有比例的区间）：

1. 至少一档
2. 第一档的 `MinAmount` 必须为 **0**
3. 区间是**左闭右开** `[MinAmount, MaxAmount)`
4. 每档 `MaxAmount > MinAmount`
5. 相邻两档必须**首尾相接**：上一档的 `MaxAmount` == 下一档的 `MinAmount`
6. **只有最后一档**的 `MaxAmount` 可以为空（代表无上限），且最后一档**必须**为空
7. 每档 `Rate` 取值 0 ~ 1000

后端会按 `MinAmount` 升序重排并重新生成 `SortId`，前端不用管顺序。

> [!NOTE] 阶梯**只有比例，没有「本档固定金额」这一列**。如果以后需要「达到某档额外奖 5000 元」这种，需要加字段。

# 5. 操作提成条件 (`CommissionType = Operation`)

只有提成类型为操作提成时才填这一组，销售提成时**必须不传**（传了报错）。

## 5.1 条件项

`Rules` **必填至少一条**。一票业务会把所有条件项**挨个判一遍，命中的金额全部累加**（不是取最高、不是命中一条就停）。

| 字段 | 说明 |
| :-- | :-- |
| `Name` | 条件项名称，选填，最长128，仅用于识别 |
| `Amount` | 命中后**每票**提成金额（人民币），**必填且必须 > 0** |
| `ConditionGroups` | 条件组，**必填至少一组**。不带任何筛选的「每票10元」用一个**按票**条件表达，不是传空数组 |

**举例**（原始逻辑文档里的三条）：

| 条件项 | 条件                           | 金额 |
| :----- | :----------------------------- | :--- |
| 条件1  | 货物类型 包含于 (危险品, 冻柜) | 10   |
| 条件2  | **按票**                       | 10   |
| 条件3  | 海运起运港 等于 天津港         | 5    |

一票是天津港出的危险品 → `10 + 10 + 5` = **25 元**。

## 5.2 条件的逻辑结构：两层，组内且、组间或

条件表达式是**两层结构**，不支持任意括号嵌套：

```
条件项命中 = (组1条件A 且 组1条件B) 或 (组2条件C 且 组2条件D) 或 ...
```

原始逻辑文档里的 `海运出口 且 (危险品 或 冻柜)` 用两层表达就是拆成两组：

```
组1: 业务类型=海运出口 且 货物类型=危险品
组2: 业务类型=海运出口 且 货物类型=冻柜
```

表达力和任意嵌套等价，但前端和后端都简单得多。这套建模跟项目里已有的 `UserTablePermissionCondition`（`GroupId` 分组）保持一致。

> [!NOTE] 上面的例子里出现了「业务类型」，但**业务类型不是条件字段**，它在规则级别（`BizTypes` 适用业务类型）表达。所以这个例子实际的配法是：配置的适用业务类型选「海运出口」，条件项里只写「货物类型 包含于 (危险品, 冻柜)」。
>
> 副作用是：**同一条配置里的所有条件项共用同一个业务类型范围**，做不到「条件1限海运出口、条件3不限」。真需要的话就拆成两条配置，或者后续把业务类型加进 `CommissionConditionField` 枚举。

## 5.3 条件字段（本期只开放六个）

| 字段 | 值 | 取自哪张表 | 前端从哪选 |
| :-- | :-- | :-- | :-- |
| `SeaPOL=0` 海运起运港 | 港口id | `App_PortCodes` | 海运港口列表 |
| `SeaPOD=1` 海运目的港 | 港口id | `App_PortCodes` | 海运港口列表 |
| `AirPOL=2` 空运起运地 | 港口id | `App_AirPorts` | 空运港口列表 |
| `AirPOD=3` 空运目的地 | 港口id | `App_AirPorts` | 空运港口列表 |
| `CargoId=4` 货物类型 | `CargoType` 枚举 | — | 0普通货 1冻柜 2危险品 3超限箱 |
| `PerOrder=5` 按票 | **没有值** | — | 不用选，勾上即可 |

> [!IMPORTANT] **「按票」这个条件不需要比较符也不需要比较值。** 一条业务就是一票，所以这个条件对任何票都成立。它就是用来表达「每票提10元」这种不带筛选的计费的。
>
> 传了比较值直接报错（`「按票」条件不需要比较值`）；比较符传什么都会被存成 0（等于），返回时恒为 0，前端不要显示这个字段。
>
> **按票必须独占整个条件项**：既不能和别的条件放同一组（那是空写，一个恒真项 AND 掉），也不能自己单独一组跟别的组并列（那会让整个条件项恒命中，通常不是配置人想要的）。违反直接报错。

> [!IMPORTANT] **海运港口和空运港口是两个独立的条件字段，不是一个字段加个标记。**
>
> 海运港 `App_PortCodes` 和空运港 `App_AirPorts` 是两张独立的表，主键都是 `long`，**id 会重复且互不相干**。所以起运港/目的港各拆成海运、空运两个字段，**字段本身就决定了去哪张表查**，条件值上不需要再带「是否海运港」，也不存在传了 id 没传标记而匹配到错误港口的可能。
>
> 相应地，输出结构里 `SeaPort` 和 `AirPort` 是两个不同的对象，按条件字段只有其中一个有值。

**扩展方式**：条件字段是枚举，加一个值 + 在提成单的计算逻辑里加一段解析即可。加字段时注意三种业务类型的字段覆盖不一致——空运出口没有船公司/场站/装运方式/船名航次，海运进口没有订舱代理/场站/装运方式，届时需明确「该业务类型没有这个字段时算不命中」。

港口字段本身也有这个问题：**海运起运港/海运目的港对空运出口的票恒不命中，空运起运地/空运目的地对海运出口和海运进口的票恒不命中**。配置时建议把适用业务类型一并选上，避免配了一个永远命中不了的条件。

## 5.4 比较符

| 值         | 含义             | 值的个数     |
| :--------- | :--------------- | :----------- |
| 0 等于     | 相等即成立       | **只能一个** |
| 1 不等于   | 不相等即成立     | **只能一个** |
| 2 包含于   | 命中任一即成立   | 一个或多个   |
| 3 不包含于 | 全部不命中才成立 | 一个或多个   |

等于/不等于传了多个值直接报错，提示改用包含于/不包含于。条件字段为**按票**时比较符不参与判定。

## 5.5 计费方式只有「每票固定金额」

本期不支持「每箱 5 元」「每吨 2 元」这类按量计费。需要的话要给条件项加「计费方式 + 单价 + 计量字段」三列。

# 6. 底薪

底薪对两种提成类型都适用，挂在主表上（不在 `Sales`/`Operation` 里）。

| 字段             | 说明                                        |
| :--------------- | :------------------------------------------ |
| `BaseSalary`     | 底薪金额，可空，不能为负                    |
| `BaseSalaryMode` | 底薪模式，可空。0直接加 1提成与底薪取最大值 |

**两个字段都有值才计算底薪。只填一个不报错，照实存下来，但计算时不生效。** 输出 DTO 里有一个只读字段 `IsBaseSalaryEnabled` 直接告诉前端这条配置到底算不算底薪，前端不用自己判两个字段。

计算口径（供第二部分参考）：

```
直接加   : 最终 = f(P) − 负利润扣减 + BaseSalary
取最大值 : 最终 = max(f(P) − 负利润扣减, BaseSalary)
```

取最大值模式下，如果提成算出来是负数，结果就是底薪。

> [!IMPORTANT] **一个人既有销售提成配置又有操作提成配置，两条上都填了底薪，底薪会被算两次。** 本模块不拦这种配法（两条配置提成类型不同，不构成冲突），需要在第二部分合并发放时决定怎么处理。

# 10. 编辑与删除的行为

## 10.1 编辑：子表整棵重建

所有子表都是**全量提交**，输入 DTO 里**不带子表id**。编辑时后端先把这条配置下的 7 张子表全部清空，再按本次提交重新插入。

**副作用（测试注意）：编辑之后子表的 `Id` 会全部变掉**（阶梯id、条件项id、条件id、条件值id）。目前没有任何东西引用这些 id，所以不构成问题；前端也不要缓存这些 id 跨编辑使用。

这么做的原因是条件是三层嵌套结构，按 id 逐层比对增删改的复杂度远高于重建，而配置数据量极小，重建的代价可以忽略。

## 10.2 删除：逐层显式删子表

`AbpDbContext` 在软删主表时会把主表 `EntityState` 从 `Deleted` 改回 `Modified`，**EF 级联到这一步已经失效，子表一条都不会被删**。所以删除时必须逐层显式删：

```
条件值 → 条件 → 条件项 → 阶梯 → 适用业务类型 → 适用组织 → 适用人 → 主表(软删)
```

编辑重建和删除**共用同一个清理方法**，不会出现「编辑删得干净、删除漏一片」。

## 10.3 引用校验：暂时是空的

按项目规范，删除前要校验是否被其它模块引用。但提成单（第二部分）**还没建表，当前系统里没有任何东西引用提成配置**，所以校验点在代码里已经留好（`DeleteAsync` 的「引用校验」区块），实现是空的。

**提成单落地后必须在这个区块补上**「已被提成模块引用,禁止删除」，不要放到调用方去做。
