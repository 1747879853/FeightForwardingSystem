# 付费申请-发票接口文档

**控制器**：`PaymentApplicationAdmin`

**所有接口均需要登录认证**

本文是付费申请**发票子域**的活文档，只写发票相关的接口与字段：挑选进项发票、发票子表的入参出参、仅编辑发票与附件、批量下载发票附件、以及发票相关的全部校验规则。付费申请自身的费用关联、银行、审核流程不在本文范围内。

> 路由里的 `Async` 后缀不能省，本项目动态 API 不会剥掉它。写成不带 `Async` 的地址会 404。

---

# 1. 业务背景说明 (Background)

**白话解释：** 付费申请是「我们要付钱给供应商」的单子。供应商开给我们的发票要登记在这条申请下面，一条申请可能有多张发票，每张发票单独一行、各自挂一个附件。

- 发票行存在子表 `App_PaymentApplicationInvoices`，**不在主表上**。
- **一个发票号只能被一条付费申请引用**：同一笔进项被认领两次会让已开票金额翻倍。
- 供应商开给我们的票同时也会被后台定时拉进**进项发票**（`App_InputInvoices`）。所以录发票时可以直接从进项发票里挑，挑完把发票号、开票日期、销售方抬头、金额和 pdf 附件回填到发票行，不用手抄。

# 2. 数据结构

| 表 | 说明 |
| :-- | :-- |
| `App_PaymentApplications` | 付费申请主表，`InvoiceProcess`（发票流程）在这里 |
| `App_PaymentApplicationInvoices` | 付费申请发票子表，一张发票一行 |
| `App_AttachmentItems` | 发票附件，`ModuleTypeId=160110`、`ItemId` 为发票行 id，业务上限定一行只挂一个 |
| `App_InputInvoices` | 进项发票，后台从开票接口发票池定时拉取，`OrgId` 固定是公司 |

## 一、拉取可选用的进项发票

### `GET /api/services/app/PaymentApplicationAdmin/GetInputInvoiceListAsync`

**权限**：`Admin.PaymentApplication.Get`

供付费申请录发票时挑选。返回的每一条都可以直接回填成一行付费申请发票，**不需要再判重**。

**入参** `PayAppInputInvoiceQueryDto`（Query 参数）：

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `orgId` | `long?` | **是** | 所属公司 id。与进项发票的 `OrgId` **直接相等比对**，后端**不会**向上解析组织串。为空报「所属公司不能为空」 |
| `settlementId` | `Guid?` | **是** | 结算对象 id（客户表）。为空报「结算对象不能为空」 |
| `clientInvoiceInfoId` | `Guid?` | 否 | 客户开票信息 id。传了就**只用这一条**开票信息的纳税人识别号去匹配；不传则用结算对象名下**全部**开票信息的 |
| `excludeInvoiceNos` | `string[]` | 否 | 要排除的发票号。一般传当前付费申请**已录**的发票号，免得重复挑到。空串与空白项会被忽略 |

**出参** `InputInvoiceSimpleDto[]`（不分页，直接是数组，无结果时为 `[]`）：

### 行级（`InputInvoiceSimpleDto`）

| 字段 | 类型 | 说明 | 回填到发票行的哪个字段 |
| :-- | :-- | :-- | :-- |
| `id` | `Guid` | 进项发票 id。只用于前端标识选中项，**不要提交给付费申请** | — |
| `invoiceNo` | `string` | 发票号码，数电票存 20 位号码 | `invoiceNo` |
| `invoiceCode` | `string` | 发票代码，数电票为空串 | — |
| `elecInvoiceNumber` | `string` | 数电号码 | — |
| `invoiceTime` | `DateTime?` | 开票时间 | `invoiceDate` |
| `sellerHeader` | `string` | 销售方抬头，即销方名称 | `sellerHeader` |
| `sellerTaxNo` | `string` | 销方税号。就是靠它与结算对象对上的 | — |
| `totalAmount` | `decimal?` | 含税总金额 | `amount` |
| `exTaxAmount` | `decimal?` | 不含税总金额 | — |
| `taxAmount` | `decimal?` | 税额 | — |
| `invoiceLine` | `InputInvoiceLine?` | 发票种类，JSON 为数字（如电子普票 `12`） | — |
| `invoiceStatus` | `InputInvoiceStatus?` | 发票状态 1正常 2红冲 … 9已全部冲红 | — |
| `attachment` | `AttachmentItemDto?` | 版式文件附件，**只给首个 pdf**；没有 pdf 时为 `null` | `attachment.attachmentId` |

### `attachment`（`AttachmentItemDto`，有 pdf 时才有值）

| 字段               | 类型        | 说明                                |
| :----------------- | :---------- | :---------------------------------- |
| `id`               | `long`      | 附件关联主键                        |
| `attachmentId`     | `long`      | 附件文件 id。**回填时提交的是这个** |
| `itemId`           | `string`    | 进项发票 id                         |
| `moduleTypeId`     | `string`    | 固定 `160120`（进项发票的版式文件） |
| `clientVisible`    | `bool`      | 客户是否可见。进项固定 `false`      |
| `isFirstShow`      | `bool`      | 是否优先展示                        |
| `displayOrder`     | `int`       | 顺序                                |
| `url`              | `string`    | 文件下载地址，可直接预览            |
| `mediaType`        | `int`       | 1图片 5文档，pdf 为 `5`             |
| `friendlyFileName` | `string`    | 显示名，形如 `{发票号}.pdf`         |
| `fileLength`       | `long?`     | 文件大小                            |
| `creationTime`     | `DateTime?` | 写入时间                            |
| `creatorUserId`    | `long?`     | 上传人。系统拉取的为空              |
| `creatorUserName`  | `string`    | 上传人 nickname。系统拉取的为空     |

**筛选口径**（五个条件同时满足才返回）：

| # | 条件 | 说明 |
| :-- | :-- | :-- |
| 1 | 所属公司一致 | 进项发票 `OrgId` **直接等于**入参 `orgId`，不向上解析组织串 |
| 2 | 销方税号命中结算对象 | 取该结算对象**开票信息子表**里全部非空的纳税人识别号（`TaxNum`），与进项发票 `SellerTaxNo` 精确比对。传了 `clientInvoiceInfoId` 时再加一条 `Id` 相等，收窄成那一条开票信息的税号 |
| 3 | 开票时间在最近一个月内 | `InvoiceTime >= 当前时间往前推一个月`。没有开票时间的票不返回 |
| 4 | 发票号未被任何付费申请用掉 | 按**发票号**精确比对付费申请发票子表；指向已删付费申请的孤儿行不算占用 |
| 5 | 不在 `excludeInvoiceNos` 里 | — |

排序：按开票时间**倒序**。

> [!IMPORTANT] **`orgId` 必须传公司节点的 id。** 进项发票是后台按公司去发票池拉的，`OrgId` 落的一定是公司；本接口按 `OrgId` **直接相等**比对，传部门 id 一张票都查不到，且**不会报错**，只会返回空数组。当前单据的 `orgId` 若可能是部门，前端要取它所属公司的 id 再传。

> [!IMPORTANT] **结算对象没维护开票信息（开票信息子表里一个纳税人识别号都没有）时，接口返回空数组，不会报错。** 这不是 bug——没有纳税人识别号就无法与任何进项发票对上；此时**不会**退化成「不按结算对象过滤」，否则会把整个公司的进项发票摆到别人的付费申请上。前端遇到空列表可提示「该结算对象未维护纳税人识别号」。
>
> 传了 `clientInvoiceInfoId` 但那条开票信息没维护税号、或它不属于该结算对象时，同样是**空数组、不报错**。后端不为「开票信息属不属于结算对象」单独报错——一条开票信息只对应一个税号，两个条件直接一起查即可，对不上就是查不出税号，与「没维护税号」走的是同一条空结果分支。

> 条件 4 与保存时的发票号唯一性校验是**同一套口径**，所以这里挑得到的一定存得进去，不会出现「列表里有、点保存报已被占用」。

**前端接入建议**：

1. 入口放在发票明细区的「从进项发票选择」按钮，带上当前单据的**所属公司** id 作为 `orgId`、`settlementId`，以及明细区已有的全部 `invoiceNo` 作为 `excludeInvoiceNos`。单据上已经选定了开票信息（抬头/税号）时，把它的 id 一并作为 `clientInvoiceInfoId` 传上来，结果会收窄到该税号的票；没选就不传。
2. 用户勾选后按上表的「回填」列生成发票行；`attachment` 有值时把 `attachment.attachmentId` 放进该行的 `attachment.attachmentId`，`null` 时该行就是没有附件。
3. 一次可多选，回填成多行；回填后仍走 `AddAsync` / `EditAsync` / `EditInvoiceAsync` 保存。

## 二、发票子表（新增 / 编辑 / 仅编辑发票共用）

发票部分的入参结构在 `AddAsync`、`EditAsync`、`EditInvoiceAsync` 三个接口里**完全一致**。

| 方法名 | 路由 |
| :-- | :-- |
| `AddAsync` | `POST /api/services/app/PaymentApplicationAdmin/AddAsync` |
| `EditAsync` | `PUT /api/services/app/PaymentApplicationAdmin/EditAsync` |
| `EditInvoiceAsync` | `PUT /api/services/app/PaymentApplicationAdmin/EditInvoiceAsync` |

```json
{
  "invoiceProcess": 0,
  "paymentApplicationInvoices": [
    {
      "invoiceNo": "INV-001",
      "invoiceDate": "2026-09-01",
      "sellerHeader": "上海某某国际物流有限公司",
      "amount": 12800.0,
      "sortId": 0,
      "attachment": {
        "attachmentId": 123,
        "attachmentDtlTypeId": 10,
        "clientVisible": true,
        "displayOrder": 0
      }
    },
    {
      "invoiceNo": "INV-002",
      "invoiceDate": "2026-09-02",
      "sellerHeader": null,
      "amount": null,
      "sortId": 1,
      "attachment": null
    }
  ]
}
```

### 2.1 `paymentApplicationInvoices[]` 入参（`PaymentApplicationInvoiceInputDto`）

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `invoiceNo` | `string` | **是** | 发票号，最长 128 字符。**全部付费申请之间不可重复**，不只是当前这条申请内 |
| `invoiceDate` | `DateTime?` | 否 | 开票日期 |
| `sellerHeader` | `string` | 否 | 销售方抬头，即开票方（供应商）在发票上的名称，最长 256 字符。**纯文本，不与客户表关联**——开票方未必是本系统里的客户，不要做成客户下拉 |
| `amount` | `decimal?` | 否 | 发票金额，**允许负数**（红字发票）。与申请金额彼此独立，**不参与任何额度计算与校验** |
| `sortId` | `int` | 否 | 排序 id，出参按它升序返回 |
| `attachment` | `object?` | 否 | 该发票的附件，**单个对象不是数组**；不传或 `null` 即该发票没有附件 |

### 2.2 `attachment` 入参（`AttachmentItemForItemInputDto`）

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `attachmentId` | `long` | 附件 id，必填；`<=0` 会被忽略（等于没传附件） |
| `attachmentDtlTypeId` | `long?` | 附件详细类型 id |
| `clientVisible` | `bool` | 客户是否可见 |
| `displayOrder` | `int` | 排序 |

> **不传 `id`。** 三个接口对发票子表都是**全量覆盖**（先删旧发票及其附件，再按数组重建），所以每次都要把该申请的**全部**发票完整传回来，漏传的会被删掉，连附件一起。要换某行的附件，整条重新提交即可。

### 2.3 `paymentApplicationInvoices[]` 出参（`PaymentApplicationInvoiceDto`）

`DetailAsync` 与 `GetPagedListAsync` 的每条付费申请上都带这个数组，无发票时为 `[]`。

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `id` | `Guid` | 发票行 id |
| `paymentApplicationId` | `Guid` | 所属付费申请 id |
| `invoiceNo` | `string` | 发票号 |
| `invoiceDate` | `DateTime?` | 开票日期 |
| `sellerHeader` | `string` | 销售方抬头（开票方名称），未填时为 `null` |
| `amount` | `decimal?` | 发票金额，未填时为 `null`，可能为负数（红字发票） |
| `sortId` | `int` | 排序 id，数组已按它升序 |
| `creationTime` | `DateTime` | 录入时间 |
| `creatorUserId` | `long?` | 录入人 id |
| `attachment` | `AttachmentItemDto?` | 该发票的附件，没有时为 `null`；`moduleTypeId` 为 `160110` |

> **付费结算选单列表**（`GetPagedListForSettlementAsync` / `GetPagedListByCurrencyForSettlementAsync`）的 `paymentApplicationInvoices` **恒为 `null`**，那两个列表里不要读发票信息，需要就走详情。

### 2.4 列表按发票筛选

参数在 `GetPagedListAsync` 上，查的是发票子表，**命中任意一张发票即返回该付费申请**：

| 参数               | 类型        | 说明                                     |
| :----------------- | :---------- | :--------------------------------------- |
| `invoiceProcess`   | `int?`      | 按发票流程精确过滤（查主表）             |
| `invoiceNo`        | `string`    | 模糊匹配，任意一张发票的发票号命中即返回 |
| `invoiceDateStart` | `DateTime?` | 任意一张发票的开票日期 `>=` 该值即返回   |
| `invoiceDateEnd`   | `DateTime?` | 任意一张发票的开票日期 `<=` 该值即返回   |

> 起止两个条件是**分别判断**的：一条申请只要有某张票满足起、另有某张票满足止，也会被返回，不要求同一张票同时满足。

## 三、仅编辑发票与附件

### `PUT /api/services/app/PaymentApplicationAdmin/EditInvoiceAsync`

**权限**：`Admin.PaymentApplication.Edit`

**本接口不判断 `status`**。无论付费申请是录入、审核中、驳回、已通过、部分结算还是已结算，只要单据存在即可调用。完整编辑 `EditAsync` 仍只允许录入/驳回状态，二者不要混用预期。审核通过后补录发票走本接口。

**入参** `PaymentApplicationInvoiceEditDto`：

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `id` | `Guid` | **是** | 付费申请 id |
| `invoiceProcess` | `InvoiceProcess` | **是** | 发票流程 0先票后付 1先付后票 2不开票 |
| `paymentApplicationInvoices` | `array` | 否 | 发票列表，结构见 2.1，**全量覆盖** |
| `attachmentGroup` | `array` | 否 | 付费申请自身的分组附件（按 `attachmentDtlTypeId` 分组），**全量覆盖** |

```json
{
  "id": "付费申请Guid",
  "invoiceProcess": 0,
  "paymentApplicationInvoices": [
    { "invoiceNo": "INV-001", "sortId": 0, "attachment": null }
  ],
  "attachmentGroup": [
    {
      "attachmentDtlTypeId": 10,
      "items": [{ "attachmentId": 1, "clientVisible": true, "displayOrder": 0 }]
    }
  ]
}
```

**出参**：无（`void`）。

> `attachmentGroup` 是付费申请**自身**的附件（`ModuleTypeId=160005`），与发票行各自的 `attachment` （`ModuleTypeId=160110`）是两回事，互不影响。两者都是全量覆盖：只改发票时也要把详情里的 `attachmentGroup` 原样带回，否则附件会被清空；要清空就传 `[]` 或 `null`。

| 接口 | 用途 | 是否判断 Status |
| :-- | :-- | :-- |
| `EditAsync` | 完整编辑 | 是（仅录入/驳回） |
| `EditInvoiceAsync` | 只改发票流程、发票子表、分组附件 | **否** |
| `AddAttachmentsAsync` | 平铺追加附件，不删旧、不改发票字段 | 否 |

## 四、批量下载发票附件

### `POST /api/services/app/PaymentApplicationAdmin/DownloadInvoicesAsync`

**权限**：`Admin.PaymentApplication.Get`

**入参** `PaymentApplicationInvoiceDownloadDto`：

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `ids` | `Guid[]` | **是** | **付费申请** id 集合（不是发票 id），取这些申请下全部发票的附件；内部会去重 |

**出参** `PaymentApplicationInvoiceDownloadResultDto`：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `url` | `string` | 压缩包下载地址，直接用它下载 |
| `fileName` | `string` | 建议的另存文件名 |
| `fileCount` | `int` | 实际打进压缩包的附件数 |
| `missingInvoiceNos` | `string[]` | 没有附件、或附件文件在服务器上已缺失的发票号；都正常时为 `[]` |

包内按「付费申请单号」分目录，文件名用发票号，撞名时自动追加序号：

```
付费申请发票_20260904132015.zip
├── PY260904001/
│   ├── INV-0001.pdf
│   └── INV-0002.jpg
└── PY260904002/
    ├── INV-0005.pdf
    └── INV-0005(1).pdf
```

| 报错                                          | 触发条件                   |
| :-------------------------------------------- | :------------------------- |
| 「付费申请不能为空」                          | `ids` 没传或为空数组       |
| 「付费申请不存在」                            | 传的 id 一个都查不到       |
| 「所选付费申请没有发票信息」                  | 这些申请下一张发票都没有   |
| 「所选付费申请的发票都没有附件 无可下载内容」 | 有发票但一个附件都打不进去 |

> **部分缺失不会报错**：只要有一个附件成功打包接口就正常返回，缺的那些放在 `missingInvoiceNos` 里，前端要提示，不要静默忽略。打包在服务端同步完成，附件多时耗时明显，按钮要置灰防重复点击。后端没有数量上限，建议前端限制在几十张以内。

## 五、发票校验规则

### 5.1 `invoiceProcess` 与发票数组的搭配

**两条规则卡在不同的接口**：

| `invoiceProcess` | 含义 | 发票数组要求 | 卡在哪个接口 | 报错文案 |
| :-- | :-- | :-- | :-- | :-- |
| `0` | 先票后付 | 提交前必须**至少一条**，新增/编辑时可以为空 | **仅 `SubmitAsync`** | 「发票流程为先票后付时 提交前必须录入发票信息」 |
| `1` | 先付后票 | 不限制（可空） | — | — |
| `2` | 不开票 | **必须为空** | 新增 / 编辑 / 仅编辑发票 | 「发票流程为不开票时 不能录入发票信息」 |

> [!IMPORTANT] 先票后付**可以先存草稿再补发票**——这是刻意放开的，因为先票后付的正常节奏就是先建单、等对方开票、再回来补录。但提交那一步一定会拦，前端应在点提交前自行预判并提示，别让用户走到最后才被拦。

### 5.2 行内校验（新增 / 编辑 / 仅编辑发票，三个接口都卡）

| 情况 | 报错 |
| :-- | :-- |
| `invoiceNo` 为空或全空格 | 「发票号不能为空」 |
| `invoiceNo` 超 128 字符 | 「发票号长度不能超过128个字符」 |
| `sellerHeader` 超 256 字符 | 「销售方抬头长度不能超过256个字符」 |
| 本次提交的数组内 `invoiceNo` 重复 | 「同一付费申请下发票号不可重复」 |
| `invoiceNo` 已被**其它**付费申请用掉 | 「发票号 {发票号} 已被付费申请 {申请单号} 使用 不可重复」 |

> [!IMPORTANT] **发票号是全局唯一的，不只是单内唯一。** 一张对方发票只能被一条付费申请引用，否则同一笔进项会被认领两次、已开票金额也会翻倍。报错里会带上占用它的那条付费申请的**申请单号**，可直接提示用户去查。校验会自动排除当前这条申请自己的发票行，所以编辑时原样保存不会撞自己；指向已删除付费申请的发票行不占号，删掉的单子不会永久占住发票号。

### 5.3 表单建议

- `invoiceProcess` 做成必选下拉。
- 选「不开票」时把发票明细区禁用并清空——这一条保存时就会报错，不能等到提交。
- 选「先票后付」时明细区可以为空，但建议标注「提交前需补录发票」，并在提交按钮上做前置校验。
- `sellerHeader` 用普通文本框，**不要做成客户下拉**（开票方未必是系统里的客户）。
- `amount` 允许负数，不要在前端加「必须大于0」或「必须等于申请金额」的限制。
- 发票号优先引导用户走「从进项发票选择」（第一节），手输容易抄错、也容易撞已被占用的号。
