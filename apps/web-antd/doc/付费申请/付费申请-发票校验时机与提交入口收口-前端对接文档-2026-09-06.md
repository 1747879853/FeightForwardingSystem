# 二、变更 1 — 发票校验时机

## 2.1 现在各条规则在哪一步报错

| 规则 | 新增 | 编辑 | 仅编辑发票 | 提交 |
| :-- | :-- | :-- | :-- | :-- |
| 发票流程=先票后付时必须有发票 | — | — | — | **报错** |
| 发票流程=不开票时不能有发票 | **报错** | **报错** | **报错** | — |
| 发票号必填 / 不超过128字符 / 同一申请下不重复 | **报错** | **报错** | **报错** | — |

## 2.2 报错文案

| 文案 | 触发接口 | 变化 |
| :-- | :-- | :-- |
| `发票流程为先票后付时 提交前必须录入发票信息` | SubmitAsync | **文案与接口都变了**（原为 `发票流程为先票后付时 发票信息不能为空`，在新增/编辑报） |
| `发票流程为不开票时 不能录入发票信息` | AddAsync / EditAsync / EditInvoiceAsync | 不变 |
| `发票号不能为空` / `发票号长度不能超过128个字符` / `同一付费申请下发票号不可重复` | 同上 | 不变 |

## 2.3 前端要做什么

1. **新增/编辑页面：选了「先票后付」不必再强制填发票**，可以直接保存。发票信息建议做成「非必填但提示待补录」的样式。
2. **提交按钮那一步要预判。** 先票后付且发票列表为空时，点提交必然报错。建议提交前在前端就提示「请先录入发票信息」，避免用户走到最后一步才被拦。
3. **「不开票」仍然要当场拦。** 用户把发票流程切到「不开票」时，如果已经录了发票行，前端应立即提示先清空，否则保存就会报错。

# 三、变更 2 — 取消「保存并提交」（破坏性）

## 3.1 入参变化

以下两个字段已从 `AddAsync` / `EditAsync` 的入参中移除：

| 字段名     | JSON Key     | 原说明                           |
| :--------- | :----------- | :------------------------------- |
| Status     | `status`     | 「输入1代表保存并提交 其余不管」 |
| SubmitTime | `submitTime` | 提交时间                         |

> [!WARNING] **传了不会报错，会被静默忽略。** ABP 对未声明的字段直接丢弃，所以继续传 `status: 1` **不会有任何错误提示**，但单据会停在**录入状态**，而前端可能以为已经提交成功了。请务必检查并改掉所有传这两个字段的地方。

## 3.2 改成两步调用

```
原来：AddAsync({ ..., status: 1 })           // 一步「保存并提交」
现在：const id = await AddAsync({ ... })      // 落录入状态
      await SubmitAsync({ id })               // 再提交
```

编辑同理：先 `EditAsync`，再 `SubmitAsync`。

`SubmitAsync` 入参只有一个 `id`（`PayAppSubmitDto`）。

## 3.3 为什么要去掉

原先 `status=1` 这条路**只把状态改成审核中，不创建审核任务、也不生成工作流实例**（建任务的代码只在 `SubmitAsync` 里）。这样产出的付费申请会：

- 状态显示「审核中」
- 但在**审核列表里查不到**
- 也**永远审不掉**，只能撤销提交

所以这不是功能精简，是在堵一个会产出坏数据的入口。

> [!IMPORTANT] 如果历史上用过这条路，库里可能已经存在「审核中但没有审核任务」的付费申请。这类单据需要后端单独排查修复，前端遇到「状态审核中却在审核列表找不到」时不必当成查询 bug 上报。
