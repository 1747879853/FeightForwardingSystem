# 1. 业务背景说明 (Background)

**白话解释：**

付费申请是「我们要付钱给供应商」的单子。财务按结算对象挑费用、填申请金额，提交审核通过后才能做付费结算。一张申请只对应一个结算对象；币别可以指定一种结算币别（固定币别申请），也可以不指定（原币申请）。供应商开给我们的发票挂在发票子表上，银行按申请涉及的币别挂收款账户。

主表：`App_PaymentApplications`；费用明细：`App_PaymentApplicationItems`；银行：`App_PaymentApplicationBanks`；发票：`App_PaymentApplicationInvoices`。

发票子域的现行口径以 [付费申请-发票接口文档.md](./付费申请-发票接口文档.md) 为准，本文不重复发票字段。

# 2. 功能与操作说明 (Features & Operations)

- **列表：** `GET PaymentApplicationAdmin/GetPagedListAsync`，出参 `PaymentApplicationListDto`。主表列全部返回。结算对象只留简称，申请币别只留代码，业务分组只留主提单号和委托编号，关联付费结算、发票、币别合计只留列表和弹窗要读的字段。组织串每级只有名称，并带本位币代码。详情、审批列表仍用 `PaymentApplicationDto`。
- **详情：** `GET PaymentApplicationAdmin/DetailAsync`。按业务（`TransportOrder`）分组返回费用明细、币别合计、附件、关联付费结算、发票子表。业务组 `transportOrder` 在 ProjectTo 简要字段（含按 `bizType` 四选一的业务类型简要对象，件杂货为 `breakBulk`）之外，另填销售/操作/客服昵称，以及**应收整票结算状态** `recSettlementStatus`。组内明细按费用 `sortId` 升序、相同再按创建时间升序。
- **选可申请费用：** `GET PaymentApplicationAdmin/GetOrderFeeGroupAsync`。按业务分组挑费用；**起运港/目的港 `polId`/`podId` 同时匹配海运出口与件杂货的港口**（两者都是海运港 `PortCode`，命中任一即可），传了港口条件时海运进口、空运出口的业务不会出现；每行的业务类型简要 `seaExport`/`seaImport`/`airExport`/`breakBulk` 由 `ITransportOrderBizSimpleFiller` 按 `bizType` 填充；不填 `recSettlementStatus`。
- **新增 / 按对账单新建 / 编辑 / 增删费用 / 删除：** `AddAsync` / `AddByStatementAsync` / `EditAsync` / `PayAppItemAddAsync` / `PayAppItemDelAsync` / `DeleteAsync`。
- **提交 / 撤回 / 审批列表 / 审核 / 驳回：** `SubmitAsync` / `UnSubmitAsync` / `PayAppTaskListAsync` / `AuditAsync` / `RejectAsync`。审批列表的业务分组同样只填 `transportOrder` 简要，**不填** `recSettlementStatus`。工作流「申请人组织」条件配在大组织上时，下属部门的申请也算属于（配青岛分公司，青岛业务部的申请会走这条线）。
- **付费结算选申请：** `GetPagedListForSettlementAsync` / `GetPagedListByCurrencyForSettlementAsync`。

# 3. 状态流转说明 (Status Transitions)

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 录入 `Entering=0` | 新增保存 | 录入 | 新增一律落录入，没有「保存并提交」 |
| 录入 / 驳回 | `SubmitAsync` | 审核中 `Auditing=1` | 建审核任务与工作流实例 |
| 审核中 | `UnSubmitAsync` | 录入 | 撤回提交 |
| 审核中 | `AuditAsync` | 审核通过 `Passed=3` |  |
| 审核中 | `RejectAsync` | 驳回 `Rejected=2` |  |
| 审核通过 | 付费结算核销部分申请量 | 部分结算 `Partial=4` | 由结算回写，不在本模块手改 |
| 部分结算 | 申请量全部结完 | 结算完毕 `Settlemented=5` | 由结算回写 |
| 部分结算 / 结算完毕 | 结算删明细或删整单 | 审核通过 / 部分结算 | 按剩余未结量重算 |

业务行的应收整票结算状态（`recSettlementStatus`，**仅详情** `DetailAsync` 返回）：

| 汇总结果   | 条件                            |
| :--------- | :------------------------------ |
| null       | 该业务下没有应收费用            |
| 0 未结算   | 整票应收费用全部 `UnSettled`    |
| 2 结算完毕 | 整票应收费用全部 `Settlemented` |
| 1 部分结算 | 其他                            |

**「整票」按该业务下的全部应收费用算，不限于本付费申请收录的那几条。** 付费申请里常见的是应付费用，整票应收状态仍按该票业务的全部应收费用汇总，所以可能出现「本申请全是应付未结，业务行却显示部分结算/结算完毕」。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点：整票应收结算状态只在详情有值]** `recSettlementStatus` 复用 `TransportOrderSimpleDto` 已有字段，不另起名字。赋值只发生在 `PaymentApplicationAdmin/DetailAsync` 的 `payAppFeeBySeaExportGroup[].transportOrder`。列表业务分组只有主提单号和委托编号，没有这一列。审批列表和选费用不算这一列，恒为 null。前端不要在列表上读这一列，也不要把它显示成「未结算」。

> [!IMPORTANT] **[卡点：整票口径不跟着本申请费用走]** 计算时另查 `PaySide=收` 的全部费用的 `SettlementStatus`，再交给 `CombinedFeeStatusHelper.ComputeSettlementStatusForFees`。不复用本申请已查出的应付明细——否则一票里只有应付费用时这一列会永远是 null，看不出该票应收结到哪了。因此详情里「本申请费用的 settlementStatus」和「业务行 recSettlementStatus」对不上是正常的。

> [!IMPORTANT] **[卡点：null 表示没有应收，不是未结算]** 该业务一条应收费用都没有时返回 `null`。`0` 才是「有应收、全部未结算」。展示时 `null` 应留空或显示「-」。

> [!IMPORTANT] **[卡点：选费用的港口筛选只覆盖海运出口与件杂货]** `GetOrderFeeGroupAsync` 的 `polId`/`podId` 只比对海运出口与件杂货扩展表上的港口。两者都是海运港（`PortCode`），同一个港口 id 会同时命中这两类业务。海运进口、空运出口的港口不参与，所以一旦传了港口条件，这两类业务整票不会出现——不是费用被筛掉，而是业务在港口这一步就被排除了。

> [!IMPORTANT] **[卡点：组织条件是「配大组织覆盖下属」]** 工作流配「属于青岛分公司」时，青岛分公司自己以及青岛业务部等下属部门的申请都会走这条线。票/申请在分公司、条件却配成业务部，匹配不上，会落到其它线或默认线；对不上任何起始线时报「业务数据不满足任何起始审批条件」。
