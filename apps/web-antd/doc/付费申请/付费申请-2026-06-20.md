# 1. 背景意图 (Background)

`PaymentApplicationAdminAppService.GetOrderFeeGroupAsync`（付费申请加费用时的「可申请费用按业务分组列表」）此前的分组维度是**按业务（`TransportOrder`）**：一个 `TransportOrder` 一条，其下挂该业务的全部可申请费用。

业务调整后需要细化分组维度：同一业务下不同**结算对象（`OrderFee.SettlementId`）**的费用不能混在一条里。因此改为**按 `OrderFee` 的 `TransportOrderId` + `SettlementId` 联合分组**：两者都相同的费用归为一条，每条仍挂若干条费用，并在返回结构中补充结算对象信息。

# 2. 核心逻辑变更 (Core Logic)

涉及文件：

- `src/CsprojBuilder.Application/App/PaymentApplication/PaymentApplicationAdminAppService.cs`（`GetOrderFeeGroupAsync`）
- `src/CsprojBuilder.Application/App/PaymentApplication/Dto/PaymentApplicationDto.cs`（`PayAppFeeGroupDto`）

## 2.1 返回结构变更（`PayAppFeeGroupDto`）

新增结算对象相关字段：

| DTO 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `SettlementId` | `Guid` | 结算对象id（客户表），分组键之一 |
| `Settlement` | `ClientSimpleDto` | 结算对象的客户外键实体（Id/Name/Code/FullName/EnName） |

> `OrderFees` 仍为该分组（业务+结算对象）下的费用集合，但内容已按 `SettlementId` 过滤，不再是该业务的全部费用。

## 2.2 分组与分页逻辑变更

1. 业务查询（过滤 + 数据权限 + 表权限 + 排序）后，先取**排序后的业务id列表**（不分页），保证分组顺序稳定。
2. 依据内存中的费用集合 `items`，按 `TransportOrderId` 归集每条业务涉及的 `SettlementId`（去重）。
3. 按业务排序顺序展开为分组键 `(TransportOrderId, SettlementId)`，`totalCount` 改为**分组键总数**（不再是业务条数）。
4. 对分组键执行 `Skip/Take` 分页，仅物化当前页涉及的业务实体与费用，并按 `SettlementId` 批量加载结算客户（`ProjectTo<ClientSimpleDto>`）。
5. 结果由「遍历业务」改为「遍历分组键」生成：同一业务会因多个结算对象出现多条；每条的 `OrderFees` 取 `TransportOrderId == key.OrderId && SettlementId == key.SettlementId` 的费用。

# 3. 避坑指南 (Pitfalls)

- **分页维度变了**：`totalCount` 现在是分组键（业务+结算对象）数量，不是业务数量。`Skip/Take` 已下移到分组键级别，前端分页计数据此调整。
- **同一业务多条**：返回中 `Id`（业务id）可能在多条记录中重复，前端列表 key 不能只用业务 `Id`，需结合 `SettlementId`。
- **`OrderFees` 已被结算对象过滤**：每条分组只含对应 `SettlementId` 的费用，金额合计等需基于过滤后的集合。
- **`items` 被重新赋值**：在分组分页后 `items` 仅保留当前页分组涉及的费用，后续费用 DTO 构建、数据权限、本位币计算均基于该子集，避免对全量费用做无谓计算。
