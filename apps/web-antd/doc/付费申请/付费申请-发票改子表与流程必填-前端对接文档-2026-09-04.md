## 三、入参结构

### 3.1 新增 / 编辑 / 仅编辑发票

三个接口的发票部分结构完全一致。

变更前：

```json
{
  "invoiceProcess": 0,
  "invoiceNo": "INV-001",
  "invoiceDate": "2026-09-01"
}
```

变更后：

```json
{
  "invoiceProcess": 0,
  "paymentApplicationInvoices": [
    {
      "invoiceNo": "INV-001",
      "invoiceDate": "2026-09-01",
      "sellerHeader": "上海某某国际物流有限公司",
      "amount": 12800.0,
      "sortId": 0,
      "attachment": {
        "attachmentId": 123,
        "attachmentDtlTypeId": 10,
        "clientVisible": true,
        "displayOrder": 0
      }
    },
    {
      "invoiceNo": "INV-002",
      "invoiceDate": "2026-09-02",
      "sellerHeader": null,
      "amount": null,
      "sortId": 1,
      "attachment": null
    }
  ]
}
```

### 3.2 `paymentApplicationInvoices[]` 字段

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `invoiceNo` | `string` | **是** | 发票号，最长 128 字符。**全部付费申请之间不可重复**，不只是当前这一条申请内 |
| `invoiceDate` | `datetime?` | 否 | 开票日期 |
| `sellerHeader` | `string?` | 否 | 销售方抬头，即开票方（供应商）在发票上的名称，最长 256 字符。**纯文本，不与客户表关联**——开票方未必是本系统里的客户，所以不要做成客户下拉选择 |
| `amount` | `decimal?` | 否 | 发票金额，**允许负数**（红字发票）。与付费申请的申请金额彼此独立，**不参与任何额度计算与校验**，后端不会拿它和申请金额比对 |
| `sortId` | `int` | 否 | 排序id，出参按它升序返回 |
| `attachment` | `object?` | 否 | 该发票的附件，**单个对象不是数组**；不传或传 `null` 即该发票没有附件 |

### 3.3 `attachment` 字段

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `attachmentId` | `long` | 附件Id，必填；`<=0` 会被忽略（等于没传附件） |
| `attachmentDtlTypeId` | `long?` | 附件详细类型Id |
| `clientVisible` | `bool` | 客户是否可见 |
| `displayOrder` | `int` | 排序 |

> **一条发票只能挂一个附件**，所以这里是单个对象。要换附件就整条重新提交（编辑是全量覆盖）。

> 不传 `id`。编辑是**全量覆盖**（先删旧发票及其附件，再按数组重建），所以每次编辑都要把该申请的**全部**发票完整传回来，漏传的会被删除。

## 四、校验规则

### 4.1 `invoiceProcess` 与发票数组的搭配

**两条规则卡在不同的接口**，这是 2026-09-06 调整的重点：

| `invoiceProcess` | 含义 | 发票数组要求 | 卡在哪个接口 | 报错文案 |
| :-- | :-- | :-- | :-- | :-- |
| `0` | 先票后付 | 提交前必须**至少一条**，新增/编辑时可以为空 | **仅 `SubmitAsync`** | 「发票流程为先票后付时 提交前必须录入发票信息」 |
| `1` | 先付后票 | 不限制（可空） | — | — |
| `2` | 不开票 | **必须为空** | 新增 / 编辑 / 仅编辑发票 | 「发票流程为不开票时 不能录入发票信息」 |

> [!IMPORTANT] 先票后付**可以先存草稿再补发票**——这是刻意放开的，因为先票后付的正常节奏就是先建单、等对方开票、再回来补录。但提交那一步一定会拦，所以前端应在点提交前自行预判并提示，别让用户走到最后才被拦。

### 4.2 行内校验（新增 / 编辑 / 仅编辑发票，三个接口都卡）

| 情况 | 报错 |
| :-- | :-- |
| `invoiceNo` 为空或全空格 | 「发票号不能为空」 |
| `invoiceNo` 超 128 字符 | 「发票号长度不能超过128个字符」 |
| `sellerHeader` 超 256 字符 | 「销售方抬头长度不能超过256个字符」 |
| 本次提交的数组内 `invoiceNo` 重复 | 「同一付费申请下发票号不可重复」 |
| `invoiceNo` 已被**其它**付费申请用掉 | 「发票号 {发票号} 已被付费申请 {申请单号} 使用 不可重复」 |

> [!IMPORTANT] **发票号是全局唯一的，不只是单内唯一。** 一张对方发票只能被一条付费申请引用，否则同一笔进项会被认领两次、已开票金额也会翻倍。报错里会带上占用它的那条付费申请的**申请单号**，可以直接提示给用户去查。校验会自动排除当前这条申请自己的发票行，所以编辑时原样保存不会撞自己。指向已删除付费申请的发票行不占号，删掉的单子不会永久占住发票号。

### 4.3 表单建议

- `invoiceProcess` 做成必选下拉。
- 选「不开票」时把发票明细区禁用并清空——这一条保存时就会报错，不能等到提交。
- 选「先票后付」时明细区可以为空，但建议标注「提交前需补录发票」，并在提交按钮上做前置校验。
- 选「先付后票」时明细区可填可不填。
- `sellerHeader` 用普通文本框，**不要做成客户下拉**（开票方未必是系统里的客户）。
- `amount` 允许负数，不要在前端加「必须大于0」或「必须等于申请金额」的限制。

## 六、列表筛选

参数名和类型都没变，但语义变了——现在查的是发票子表，**命中任意一张发票即返回该付费申请**：

| 参数               | 类型        | 说明                                     |
| :----------------- | :---------- | :--------------------------------------- |
| `invoiceProcess`   | `int?`      | 按发票流程精确过滤（查主表，不变）       |
| `invoiceNo`        | `string`    | 模糊匹配，任意一张发票的发票号命中即返回 |
| `invoiceDateStart` | `datetime?` | 任意一张发票的开票日期 `>=` 该值即返回   |
| `invoiceDateEnd`   | `datetime?` | 任意一张发票的开票日期 `<=` 该值即返回   |

> 起止两个条件是**分别判断**的：一条申请只要有某张票满足起、另有某张票满足止，也会被返回，不要求同一张票同时满足。若业务上需要「必须有一张票的日期落在区间内」，提需求即可改。

## 七、前端改动清单

1. **列表页**：原来直接取 `item.invoiceNo` / `item.invoiceDate` 的地方全部要改。一条申请可能多张票，建议展示为多行、逗号拼接，或只显示第一张加「共 N 张」。
2. **详情页**：发票信息由单组字段改为表格；每行末尾放附件的预览/下载（取 `attachment.url`、`attachment.friendlyFileName`），`attachment` 为 `null` 时显示「无附件」。
3. **新增/编辑表单**：发票区改成可增删行的明细表；每行一个发票号、一个开票日期、一个销售方抬头、一个发票金额、一个附件上传（**单文件**）。`invoiceProcess` 改必选，并按第四节联动明细区的必填/禁用。
4. **编辑是全量覆盖**：提交时必须回传全部发票行，不能只传改动的那几行，否则未传的会被删掉（连附件一起）。
5. **附件上传流程不变**：先调通用附件上传拿到 `attachmentId`，再把它放进对应发票行的 `attachment.attachmentId` 一起提交。
6. **付费结算选单列表**（`GetPagedListForSettlementAsync` / `GetPagedListByCurrencyForSettlementAsync`）的 `paymentApplicationInvoices` **恒为 `null`**，不要在那两个列表里读发票信息；需要就走详情。
