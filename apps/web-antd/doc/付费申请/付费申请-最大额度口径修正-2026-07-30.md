# 1. 背景意图 (Background)

新建付费申请、按对账单新建、编辑费用明细、以及给现有付费申请追加费用时，系统都会校验每条费用的“最大可申请额度”。

原实现仅扣减：

- 已存在的付费申请金额
- 按费用生成的收费结算金额
- 已进入 `ReceiveSettlementInvoiceItem` 的按开票申请收费结算金额

这样会遗漏一段占用额度：**已经存在于 `InvoiceApplicationItem`，但尚未进入 `ReceiveSettlementInvoiceItem` 的金额**，导致剩余额度被高估。

| 新增付费申请 | `POST /api/services/app/PaymentApplicationAdmin/AddAsync` | 锁内额度校验修正 |
| 编辑付费申请 | `PUT /api/services/app/PaymentApplicationAdmin/EditAsync` | 锁内额度校验修正 |
| 按对账单新建 | `POST /api/services/app/PaymentApplicationAdmin/AddByStatementAsync` | 自动取最大额度时修正 |
| 追加费用 | `POST /api/services/app/PaymentApplicationAdmin/PayAppItemAddAsync` | 锁内额度校验修正 |

## 2.2 最新 remaining 口径

每条费用的最大可申请额度统一为：

`remaining = Amount - Sum(PaymentApplicationItems.AppliedAmount) - Sum(ReceiveSettlementItems.SettledAmount) - Sum(InvoiceApplicationItems.AppliedAmount)`

说明：

- `PaymentApplicationItems.AppliedAmount`：该费用已被其他付费申请占用的金额。
- `ReceiveSettlementItems.SettledAmount`：该费用已按“费用维度”做过收费结算的金额。
- `InvoiceApplicationItems.AppliedAmount`：该费用已被开票申请占用的金额，**无论是否已进入收费结算**，都要扣减。

## 2.3 代码实现点

1. `GetOrderFeeGroupAsync`
   - 查询可选费用时，把 `InvoiceApplicationItems.Sum(AppliedAmount)` 纳入过滤条件。
2. `AddAsync` / `EditAsync` / `PayAppItemAddAsync`
   - 锁内按 `OrderFeeId` 聚合 `InvoiceApplicationItem.AppliedAmount`，参与剩余额度校验。
3. `AddByStatementAsync`
   - 自动生成明细时，按同一公式计算 `remaining`，并把该值写入 `AppliedAmount` / `UnSettledAmount`。
4. 展示侧
   - `UnRqstPaymentAmount` / `UnSettledAmount` 的扣减口径同步使用 `InvoiceApplicationItems.AppliedAmount`，避免前端看到的额度与提交校验不一致。

# 3. 避坑指南 (Pitfalls)

- **不要再用 `ReceiveSettlementInvoiceItem` 代替开票申请占用额**：它只覆盖“已进收费结算”的子集，不能代表完整的开票申请占用。
- **锁内聚合不能少**：付费申请提交类接口仍需在加锁后重算 `remaining`，不能只信前端或列表页返回值。
- **显示与校验口径必须一致**：否则前端会出现“列表还能选、提交时报额度不足”的体验问题。
