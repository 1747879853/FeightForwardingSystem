# 1. 背景意图 (Background)

付费申请原来把发票号、开票日期两个字段直接放在主表上，等于假定「一条付费申请只对应一张发票」。实际业务里一次付费常常对着对方开来的多张发票，主表单值放不下；而且每张发票各自有扫描件/PDF，附件也需要跟着发票逐张挂，挂在付费申请这一层分不清哪个附件属于哪张票。

同时发票流程原来可空，导致「这单到底走不走票、什么时候开」在数据上没有确定答案，后续按流程分支做校验也无从下手。

本次把发票拆成子表、发票流程改必填，并按流程约束子表的填写。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 数据库变更

| 变更 | 对象 | 说明 |
| :-- | :-- | :-- |
| 新增表 | `App_PaymentApplicationInvoices` | 付费申请发票子表 |
| 字段改必填 | `App_PaymentApplications.InvoiceProcess` | `InvoiceProcess?` → `InvoiceProcess` |
| **删除字段** | `App_PaymentApplications.InvoiceNo` | 移到子表 |
| **删除字段** | `App_PaymentApplications.InvoiceDate` | 移到子表 |

子表 `PaymentApplicationInvoice`（`FullAuditedEntity<Guid>, IMustHaveTenant`）：

| 字段                   | 类型          | 说明       |
| :--------------------- | :------------ | :--------- |
| `Id`                   | `Guid`        | 主键       |
| `TenantId`             | `int`         | 租户       |
| `PaymentApplicationId` | `Guid`        | 付费申请id |
| `InvoiceNo`            | `string(128)` | 发票号     |
| `InvoiceDate`          | `DateTime?`   | 开票日期   |
| `SortId`               | `int`         | 排序id     |

## 2.2 发票附件：不进子表，走附件模块

每张发票的附件**不作为子表字段**，沿用仓库既有的弱关联附件机制。新增附件模块类型：

```csharp
/// <summary>
/// 付费申请发票的附件(ItemId为PaymentApplicationInvoice.Id 一条发票只挂一个附件)
/// 与付费申请自身的附件(PaymentApplication)分开 因为它是按发票逐条挂的
/// </summary>
public const string PaymentApplicationInvoice = "160110";
```

`ItemId` 就是发票行的 `Id`。这套「专用 ModuleTypeId + ItemId 为子表行 Id」的做法照的是既有先例 `OrderCtnLoading = "160100"`（监装附件挂在 `OrderCtn.Id` 上）。

「一条发票只能有一个附件」是**业务层约束**，不是库层约束：入参与出参都用单个对象而非数组，读取时若同一发票查出多条附件则取 `DisplayOrder` 最小的那条兜底。

## 2.3 校验规则

> [!WARNING] **本节的校验时机已于 2026-09-06 修订。** 「先票后付必须有至少一条」已改为**只在提交时校验**，新增/编辑/仅编辑发票不再拦。现行口径见 `付费申请-发票校验时机与提交入口收口-2026-09-06.md`，下表保留当时的实现供追溯。

新增、编辑、仅编辑发票三个入口共用 `ValidatePaymentApplicationInvoices`：

| 发票流程                          | 子表要求                 |
| :-------------------------------- | :----------------------- |
| 先票后付 `InvoiceBeforePayment=0` | **必须有至少一条**       |
| 先付后票 `PaymentBeforeInvoice=1` | 不限制（可空，事后再补） |
| 不开票 `NoInvoice=2`              | **必须为空**             |

另加两条行内校验：发票号不能为空、长度不超过 128；同一付费申请下发票号不可重复。

## 2.4 影响接口

| 接口 | 改动 |
| :-- | :-- |
| `POST .../PaymentApplicationAdmin/AddAsync` | 入参改子表结构 + 校验 + 子表随主表插入 + 逐条存发票附件 |
| `PUT .../PaymentApplicationAdmin/EditAsync` | 同上，子表全量覆盖（先删后写，删时连附件一起清） |
| `PUT .../PaymentApplicationAdmin/EditInvoiceAsync` | 同上，仍不校验单据状态 |
| `GET .../PaymentApplicationAdmin/DetailAsync` | 出参改子表结构，每条带自己的单个附件 |
| `GET .../PaymentApplicationAdmin/GetPagedListAsync` | 出参改子表结构；`invoiceNo` / `invoiceDate` 筛选改为查子表 |
| `DELETE .../PaymentApplicationAdmin/DeleteAsync` | 删主表时显式清子表 + 子表附件 |
| `POST .../PaymentApplicationAdmin/AddByStatementAsync` | 不录发票，固定给「先付后票」，见下文 |

## 2.5 列表筛选改为查子表

一条付费申请可能有多张发票，命中任意一张即返回该申请：

```csharp
//发票号与开票日期已移到发票子表 一条付费申请可能有多张发票 命中任意一张即返回
.WhereIf(!string.IsNullOrWhiteSpace(input.InvoiceNo), m => m.PaymentApplicationInvoices.Any(i => i.InvoiceNo.Contains(input.InvoiceNo)))
.WhereIf(input.InvoiceDateStart.HasValue, m => m.PaymentApplicationInvoices.Any(i => i.InvoiceDate >= input.InvoiceDateStart.Value))
.WhereIf(input.InvoiceDateEnd.HasValue, m => m.PaymentApplicationInvoices.Any(i => i.InvoiceDate <= input.InvoiceDateEnd.Value));
```

> 注意日期区间是**两个独立的 `Any`**：起止分别命中任意一张即可，不要求同一张发票同时落在区间内。若业务要求「必须有一张发票的日期落在区间内」，需改成单个 `Any` 里带两个条件，告知即可调整。

## 2.6 报表的连带修改

`ReportAdminAppService.LoadInvoiceNoMapAsync` 的应付分支原来直接读 `application.InvoiceNo`，字段删除后编译不过，改为经导航属性下钻子表逐张展开：

```csharp
//发票号已从付费申请主表移到发票子表 一条申请可能有多张发票 这里逐张展开
//走导航属性而不是另外注入子表仓储 主表与子表的软删过滤都能生效
from invoice in application.PaymentApplicationInvoices
where invoice.InvoiceNo != null && invoice.InvoiceNo != ""
```

选择导航属性而不是新注入子表仓储，一是不动报表服务的构造函数，二是主表与子表的软删过滤都自动生效。报表原有「一个分组键返回多个发票号」的口径不变，只是来源从一条变成多条。

# 3. 避坑指南 (Pitfalls)

## 3.1 存量数据必须先搬迁再删列 ⚠️

迁移会 DROP 主表那两列，**直接跑迁移会丢掉现有的发票号与开票日期**。正确顺序是：建新表 → 搬数据 → 再删旧列。搬迁语句：

```sql
-- 1) 主表已有发票号的 搬到子表
INSERT INTO App_PaymentApplicationInvoices
    (Id, TenantId, PaymentApplicationId, InvoiceNo, InvoiceDate, SortId, IsDeleted, CreationTime, CreatorUserId)
SELECT NEWID(), pa.TenantId, pa.Id, pa.InvoiceNo, pa.InvoiceDate, 0, 0, pa.CreationTime, pa.CreatorUserId
FROM App_PaymentApplications pa
WHERE pa.IsDeleted = 0
  AND pa.InvoiceNo IS NOT NULL
  AND LTRIM(RTRIM(pa.InvoiceNo)) <> '';

-- 2) 发票流程原来可空 存量NULL统一给「先付后票」
UPDATE App_PaymentApplications SET InvoiceProcess = 1 WHERE InvoiceProcess IS NULL;
```

第 2 步**只能给先付后票（1）**，不能给别的值：给「先票后付」会让没有发票的存量单据在下次编辑时被校验卡死；给「不开票」又会让已经有发票号的单据自相矛盾、且以后不许补票。先付后票不触发任何校验，是唯一不会把存量数据逼进死角的取值。

## 3.2 按对账单新建必须显式指定发票流程

`InvoiceProcess` 枚举的默认值 `0` 恰好是「先票后付」，而 `AddByStatementAsync` 不录发票。若不显式赋值，这条路径建出来的单据一落地就违反「先票后付必须有发票」，之后任何编辑都会被拦。所以固定给了先付后票：

```csharp
// 本接口不录发票 只能给先付后票:枚举默认值0是先票后付 那样会与「先票后付必须有发票」冲突
// 不开票也不行 那会禁止事后补发票 先付后票既不校验又保留了后续补录的余地 用户可在编辑里改
InvoiceProcess = InvoiceProcess.PaymentBeforeInvoice,
```

**以后凡是新增「不经过发票录入的建单入口」，都必须显式给发票流程**，否则会重蹈同一个坑。

## 3.3 删除必须清子表与附件

子表是 `ISoftDelete`，主表软删不会级联；附件是弱关联（`ModuleTypeId + ItemId`），更不会跟着走。所以 `DeleteAsync`、以及编辑时的全量覆盖，都必须显式清理：先按发票 id 删附件关联，再删发票行。统一收在 `DeletePaymentApplicationInvoicesAsync` 里，三处复用，不要各写一份。

## 3.4 附件写入必须在发票行 Id 确定之后

附件的 `ItemId` 是发票行的 `Id`，所以顺序是：先 `BuildPaymentApplicationInvoices` 生成实体（Id 在内存里就定下来了）→ 插入 → 再 `SaveInvoiceAttachmentsAsync` 写附件。`SaveInvoiceAttachmentsAsync` 依赖「实体集合与输入集合下标一一对应」，两者都过滤掉了 null 元素以保持对齐，调用时不要单独重排其中一个。

## 3.5 付费结算选单列表不返回发票

`GetPagedListForSettlementAsync` 与 `GetPagedListByCurrencyForSettlementAsync` 返回的 DTO 上有 `PaymentApplicationInvoices` 字段（继承自 `PaymentApplicationDto`），但**本次没有填充，恒为 null**。这两个接口是结算选单用的，原先虽然会随 AutoMapper 自动带出主表的发票号，但选单场景用不到。若前端确实需要，需另行填充。
