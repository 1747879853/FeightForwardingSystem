# 1. 背景意图 (Background)

发票改子表后（见《付费申请-发票改子表与流程必填-2026-09-04》），每张发票各自挂一个附件。财务对账或归档时往往要一次性拿到多张付费申请下的全部发票扫描件，原来只能在详情页里一张一张点开下载，几十张票就是几十次点击。

本次新增一个批量下载接口：传付费申请 id 集合，服务端把命中的发票附件打成 zip，返回压缩包地址，前端拿地址直接下载。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 新增接口

| 接口 | 地址 | 权限 |
| :-- | :-- | :-- |
| 批量下载发票附件 | `POST /api/services/app/PaymentApplicationAdmin/DownloadInvoicesAsync` | `Admin.PaymentApplication.Get` |

入参 `PaymentApplicationInvoiceDownloadDto`：只有一个付费申请 id 集合。出参 `PaymentApplicationInvoiceDownloadResultDto`：压缩包地址、建议文件名、实际打包数、缺附件的发票号清单。

## 2.2 取数链路

结算明细里没有文件，附件是弱关联，所以要逐层反查：

```
付费申请ids
  → App_PaymentApplicationInvoices（发票子表，按 SortId、CreationTime 排序）
  → 附件关联（ModuleTypeId = PaymentApplicationInvoice「160110」，ItemId = 发票行id）
  → App_Attachments（拿到 FileName 即存储相对路径）
  → IStoreProvider.GetFullLocalPath 还原物理路径
```

一条发票只挂一个附件是业务层约束、库层没有唯一约束，因此这里与详情口径保持一致：同一发票查出多条附件时取 `DisplayOrder` 最小的那条兜底。

## 2.3 打包与落地

用 `System.IO.Compression.ZipArchive` 在内存里打包，再通过 `IStoreProvider.AddOrUpdateFile` 写回文件存储，最后用 `GetDirectlyUrl` 换成可访问地址。

存储路径规则沿用 `UploadController` 与发票开出那边的既有约定：`{媒体类型}/{yyyyMMdd}/{唯一名}.zip`。

```csharp
using (var zipStream = new MemoryStream())
{
    //leaveOpen=true 让 ZipArchive 释放后仍能读到 zipStream 的内容
    using (var archive = new ZipArchive(zipStream, ZipArchiveMode.Create, true))
    {
        // ... 逐张发票写 entry ...
    }
    zipBytes = zipStream.ToArray();
}
```

`leaveOpen` 必须传 `true`：`ZipArchive` 释放时会把中央目录写完并默认关掉底层流，不留开就读不到 `ToArray()`。

## 2.4 包内命名

包内路径为 `{付费申请单号}/{发票号}{原扩展名}`：

- 一个包可能来自多张付费申请、多张发票，扁平摆放容易撞名，所以按申请单号分一层目录；
- 同名时自动追加 `(1)`、`(2)`，避免相互覆盖；
- 单号/发票号里的非法文件名字符会被清掉，空值用「未知申请单」「未知发票号」兜底——否则 `ZipArchive` 会抛异常或生成怪路径；
- 扩展名优先取 `Attachment.FriendlyFileName` 的，取不到再退回 `FileName` 的。

## 2.5 新增依赖

`PaymentApplicationAdminAppService` 构造函数新增两个注入：

| 依赖 | 用途 |
| :-- | :-- |
| `IRepository<Attachments.Attachment, long>` | 由附件关联拿到附件实体的 `FileName`（存储相对路径），`AttachmentItemDto` 上没有这个字段 |
| `IStoreProvider` | 还原物理路径、写回压缩包、生成直连地址 |

# 3. 避坑指南 (Pitfalls)

## 3.1 只在本地存储下有效 ⚠️

打包依赖 `IStoreProvider.GetFullLocalPath` 读物理文件。当前配置 `FileServer:Local:IsEnabled=true`、七牛关闭，注册的是 `DefaultStoreProvider`，该方法返回 `StoreRootPath` 下的真实路径，正常。

但 `QiniuStoreProvider.GetFullLocalPath` 只是把相对路径原样返回，**不是本地文件**：

```csharp
public string GetFullLocalPath(FileStoreOptions option)
{
    var fullLocalPath = option.RelativePath;
    if (string.IsNullOrEmpty(option.RelativePathWithFileName))
        fullLocalPath = option.RelativePathWithFileName;
    return fullLocalPath;
}
```

一旦切到七牛，`File.Exists` 全是 false，所有发票都会进 `missingInvoiceNos`，接口最终报「所选付费申请的发票都没有附件」。**不会崩，但功能静默失效**。届时要改成按 `GetDirectlyUrl` 拉流再打包。

## 3.2 部分缺附件不让整体失败

某张发票没传附件、或附件文件被物理删除，只把发票号记进 `missingInvoiceNos` 后继续打包；只有**一张都没打进去**时才抛异常。这是有意的：批量导出时因为一张票缺文件就整批失败，用户无从下手。前端应把 `missingInvoiceNos` 提示出来。

## 3.3 压缩包不建附件记录

zip 只是导出产物，**没有**调 `CreateOrUpdateAttachmentAsync`，也**没有**挂 `AttachmentItem`。这是刻意的：挂上去会污染业务附件列表，用户在详情页会看到一堆莫名其妙的 zip。

代价是压缩包在存储里不受附件体系管理，见下条。

## 3.4 压缩包不会自动清理

每次调用都在 `{媒体类型}/{yyyyMMdd}/` 下留一个 zip，没有任何清理机制。如果这个接口使用频繁，磁盘会持续增长。两个可选方向，按需再定：

- 加定时任务清理 N 天前的导出 zip；
- 改成不落地、直接返回文件流（那样出参就不是地址而是下载响应，前端交互也要跟着改）。

## 3.5 大批量下载没有上限保护

目前对入参 id 数量、附件总大小都没有限制，全部内容会先进内存（`MemoryStream` + `ToArray()` 会有一份拷贝）。选中几百张申请、附件又都是大 PDF 时有内存压力。如果实际会这么用，需要加「最多多少张申请」或「总大小上限」的校验，或者改成边写边落盘的流式打包。
