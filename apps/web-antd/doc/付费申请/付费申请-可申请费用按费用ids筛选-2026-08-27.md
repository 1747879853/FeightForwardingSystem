# 1. 背景意图 (Background)

新建付费申请的流程是「先拉可申请费用列表 → 勾选费用 → 生成申请」。前端在别处（业务费用列表、客户对账详情等）已经拿到一批费用 id 后，没办法只用这些 id 把对应的可申请费用明细捞回来，只能带着其它业务条件重新翻页去找。

本次给拉取接口加一个费用 id 集合筛选条件，前端拿着已选中的费用 id 直接回捞明细即可，**不新增任何生成申请的接口**。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 影响接口

| 接口 | 地址 |
| :-- | :-- |
| 可进行付费申请的费用按业务分组列表 | `GET /api/services/app/PaymentApplicationAdmin/GetOrderFeeGroupAsync` |

## 2.2 入参新增

| DTO | 字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `PayAppFeeGroupInputDto` | `OrderFeeIds` | `List<Guid>` | 费用 id 集合，可空；只返回这些费用。不传时行为完全不变 |

GET 传数组须**重复键名**：`?orderFeeIds=guid1&orderFeeIds=guid2`。

## 2.3 过滤实现

条件紧跟在「审核通过」这条固定条件之后，与其它 `WhereIf` 是**与**关系：

```csharp
.WhereIf(input.OrderFeeIds != null && input.OrderFeeIds.Count > 0, x => input.OrderFeeIds.Contains(x.Id))
```

判空沿用同一方法内 `FeeCodeIds` 的 `!= null && Count > 0` 写法，空集合等价于不筛选。

筛选发生在 SQL 层的费用查询上，后续的「排除有待审核任务的费用」内存过滤、分组键构建、分页与费用 DTO 组装全部基于同一份 `items`，所以分组数量、`totalCount` 与组内明细口径一致，不会互相错位。

# 3. 避坑指南 (Pitfalls)

- **返回条数不一定等于传入条数，前端必须以返回结果为准。** 本接口的固定条件照旧全部生效：费用必须 `FeeStatus=Passed`、无审核中的提交/申请修改/申请删除任务、且剩余可申请额度大于 0（`Amount > 已付费申请额 + 按费用收费结算额 + 开票申请已申请额`），业务侧还要过数据权限与表权限。任何一条不满足，传了 id 也不会返回。
- **默认只回一页，跨业务多选时极易踩坑。** 分页单位是**「业务 + 结算对象」组合**（同一票下不同结算对象会拆成多行），`PageSize` 默认 **10**。选中的费用若分布在 10 个以上组合上，默认参数下只会返回前 10 组的费用。回捞时请把 `pageSize` 放大（上限 100000）或按 `totalCount` 翻页，**不要**沿用列表页的默认分页参数。
- **同时传 `id`（当前付费申请id）会再挖掉一批。** 该参数会排除「已经挂在这张付费申请上的费用」，与 id 筛选叠加后可能一条都不剩，这是预期行为。
- **id 筛选与其它筛选是「与」关系。** 又传 `settlementId`/`currencyId`/`paySide` 时，两边都要命中才返回。
- 软删除的费用由 ABP 全局查询筛选器自动排除，不需要也不应手写 `IsDeleted` 判断。
- 本接口**不按收付方向硬过滤**，传混了应收费用的 id 也会照样返回；要只看应付请自行再传 `paySide=1`。
