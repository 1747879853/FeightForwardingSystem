# 1. 背景意图 (Background)

付费申请需按本次申请涉及的**每一种付费币别**分别指定一条收款银行。此前保存时可不传银行或只传部分币别，接口仍返回成功；详情中未指定银行的币别分组无法展示收款账户信息。

# 2. 核心逻辑变更 (Core Logic)

涉及文件：

- `src/CsprojBuilder.Application/App/PaymentApplication/PaymentApplicationAdminAppService.cs`

## 2.1 新增共享校验方法 `ValidatePaymentApplicationBanksAsync`

`AddAsync` 与 `EditAsync` 统一调用，校验规则：

| 规则         | 说明                                              |
| :----------- | :------------------------------------------------ |
| 必填         | 银行列表不可为空                                  |
| 不可重复     | 同一 `clientInvoiceBankId` 不可重复提交           |
| 归属         | 银行须属于当前结算对象的开票银行                  |
| 主数据完整   | `bankName`、`bankAccount`、`swiftCode` 均不可为空 |
| 原币申请     | 每种费用原币须对应恰好一条银行，币别一一匹配      |
| 指定币别申请 | 须恰好一条银行，币别与结算币别一致                |

## 2.2 AddAsync

在插入前调用校验；原币模式下从申请明细费用汇总去重得到币别集合，与银行条数及币别对应关系比对。

## 2.3 EditAsync

**先校验、后删除再插入**（修复原先先删后验导致校验失败时银行已丢失的问题）；校验逻辑与新增一致，费用币别取自当前申请已有明细。

## 2.4 DetailAsync

无代码变更。详情仍通过 `currencyGroup[].paymentApplicationBank.clientInvoiceBanks[0]` 返回 `bankName`（开户行）、`bankAccount`（账号）、`swiftCode`（SWIFT），由后端根据已保存银行 ID 关联主数据带出。

# 3. 避坑指南 (Pitfalls)

- **历史数据**：已保存但缺少银行 ID 的旧单，详情仍可能返回 `paymentApplicationBank: null`；新单保存阶段会拦截。
- **编辑须全量提交银行**：`EditAsync` 每次保存均按全量银行 ID 校验，不可省略 `paymentApplicationBanks`。
- **添加费用不触发银行校验**：`PayAppItemAddAsync` 仅增费用明细；若新增费用带来新原币，须再通过 `EditAsync` 补录对应银行。
- **前端只需传 `clientInvoiceBankId`**：无需重复传开户行、账号、SWIFT。
