# 1. 背景意图 (Background)

**白话解释：** 付费申请加费用时,原来必须先选结算对象(客户)才能拉取费用。实际客户可能不输入这个,所以改为**选填**:不传则不按结算对象过滤,返回全部可付费申请的费用。

为防止把不同结算对象的费用混进同一张付费申请,在**新增付费申请**和**给付费申请加费用**时,新增校验:所选费用的 `SettlementId` 必须与付费申请的 `SettlementId` 一致,否则报错。

# 2. 核心逻辑变更 (Core Logic)

| 接口 | 方法 | 变更 |
| :-- | :-- | :-- |
| 拉取可付费申请费用 | `GetOrderFeeGroupAsync` | 入参 `PayAppFeeGroupInputDto.SettlementId` 由 `Guid` 改为 `Guid?`(选填);查询由 `Where(==)` 改为 `WhereIf(HasValue)` |
| 新增付费申请 | `AddAsync` | 锁内取费用时一并取 `SettlementId`,校验所有费用 `SettlementId == input.SettlementId`,不一致报错 |
| 给付费申请加费用 | `PayAppItemAddAsync` | 同上,校验 `SettlementId == paymentApplication.SettlementId` |

**口径更新说明**：当前 `AddAsync` / `PayAppItemAddAsync` / `EditAsync` / `AddByStatementAsync` 的最大可申请额度已进一步统一为：`Amount - PaymentApplicationItems.AppliedAmount - ReceiveSettlementItems.SettledAmount - InvoiceApplicationItems.AppliedAmount`。不再依赖 `ReceiveSettlementInvoiceItem`，从而覆盖“已进开票申请、但尚未进收费结算”的占用额度。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT] 结算对象选填后,前端若不传 `settlementId` 会返回所有客户的费用;但提交(新增/加费用)时仍会按"费用结算对象与付费申请结算对象一致"强校验,跨结算对象的费用无法混入同一付费申请。

> [!IMPORTANT] 错误提示:`存在费用的结算对象与付费申请的结算对象不一致`。
