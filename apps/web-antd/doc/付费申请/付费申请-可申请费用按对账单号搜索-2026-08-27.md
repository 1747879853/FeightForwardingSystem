# 1. 背景意图 (Background)

新建付费申请时经常是「先跟对方对完账，再照着这张对账单付费」。原来拉取可申请费用只能按委托编号/主提单号/订舱编号等业务字段找，无法按对账单号一次性把这张对账单里的费用捞出来，只能人工比对，容易漏费用。

同时，既然支持了按对账单号搜索，列表上就必须能看出**每条费用到底进过哪几张对账单**，否则搜出来的结果无从核对。因此本次一并把每条费用的已对账列表返回出来。

搜索能力与开票申请同款（见 `文档/开票申请/开票申请-可开票费用按对账单号搜索-2026-08-27.md`），过滤写法完全一致；已对账信息复用客户对账模块的统一填充器（见 `文档/客户对账/客户对账-选费用返回已对账信息-2026-08-14.md`）。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 影响接口

| 接口 | 地址 |
| :-- | :-- |
| 拉取可付费申请的费用（按业务+结算对象分组） | `GET /api/services/app/PaymentApplicationAdmin/GetOrderFeeGroupAsync` |

## 2.2 入参

| DTO | 字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `PayAppFeeGroupInputDto` | `StatementNum` | `string` | 客户对账单号，模糊匹配，可空；不传时行为完全不变 |

> **注意：该字段不是本次新增的，而是本次才真正生效。** `PayAppFeeGroupInputDto.StatementNum` 早就声明在 DTO 上（注释原为「对账编号」），但接口从未读取它，属于死字段。因此**此前若前端已经在传 `statementNum`，后端是静默忽略、返回全量费用的**；本次接上过滤后，同样的请求会开始真正筛选，结果条数会变少。这是预期行为，但对已有调用方而言是行为变化，需要前端确认传参场景。

## 2.3 过滤实现

对账关系在子表 `App_StatementFees`（一条费用可被多张对账单包含），因此走 `OrderFee.StatementFees` 导航反查，命中任意一张对账单即保留：

```csharp
//一条费用可进多张对账单 命中任意一张对账单号即返回
.WhereIf(!string.IsNullOrWhiteSpace(input.StatementNum),
    x => x.StatementFees.Any(sf => sf.Statement.StatementNum.Contains(input.StatementNum)));
```

条件挂在费用查询（`_orderFeeRepository`）与其它费用字段同一条 `WhereIf` 链的末尾，与「金额大于已申请+已结算+已开票」「费用状态=审核通过」「排除已关联当前申请的费用」「排除待审核任务费用」「数据权限过滤」等既有条件是**与**关系。

## 2.4 出参新增：每条费用的已对账列表

分组下的每条费用（`items[].orderFees[]`，类型 `OrderFeeDto`）新增返回：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `statements` | `StatementSimpleDto[]` | 该费用进过的全部客户对账单，按对账单号升序；**未对账时为空数组而不是 null** |
| `isStatemented` | `bool` | 是否已对账，等价于 `statements` 非空 |

`StatementSimpleDto` 字段：

| 字段              | 类型       | 说明                                        |
| :---------------- | :--------- | :------------------------------------------ |
| `id`              | `Guid`     | 对账单id                                    |
| `statementNum`    | `string`   | 对账单号                                    |
| `creationTime`    | `DateTime` | 对账时间，取**对账单主表**的创建时间        |
| `creatorUserName` | `string`   | 对账人昵称，取对账单主表创建人的 `NickName` |

这两个字段在 `OrderFeeDto` 上早已声明，本接口此前从未填充（`statements` 恒为 `null`、`isStatemented` 恒为 `false`）。本次不新增 DTO 字段，只是接上填充：

```csharp
//一条费用可被多张对账单包含(允许多次对账) 已对账列表与是否已对账统一由填充器给出
//items 上面已按本页分组键裁剪过 orderFeeResult 即本页实际返回的费用 无需再按分组二次收敛
await _orderFeeStatementFiller.FillAsync(orderFeeResult);
```

填充器为客户对账模块既有的 `IOrderFeeStatementFiller`（`App/Statement/OrderFeeStatementFiller.cs`），本次仅在 `PaymentApplicationAdminAppService` 注入并调用，未改填充器本身，因此与 `OrderFeeAdmin/GetPagedListAsync`、`ChangeOrderAdmin/DetailAsync`、`StatementAdmin/GetOrderFeeGroupAsync` 的口径天然一致。

# 3. 避坑指南 (Pitfalls)

- **不要用 `StatementId` 单表等值查**：一条费用可进多张对账单，且需求是按单号模糊搜，必须走子表 `Any` + `Contains`。
- **条件必须挂在费用查询上，不能挂到业务查询上**。本接口是两段式：先查 `OrderFee` 得到 `orderIds`，再查 `TransportOrder` 做分组分页。若挂到业务查询，会变成「该业务只要有任意一条费用进过该对账单，就把这条业务下的全部可申请费用都带出来」，与需求不符。
- 软删除的对账单与对账明细由 ABP 全局查询筛选器自动排除，不需要也不应手写 `IsDeleted` 判断。
- 该条件只做**筛选**，不改变分组维度：分页仍以 `业务(TransportOrderId) + 结算对象(SettlementId)` 为单位，命中的费用按所属分组返回。
- 同一分组下未进该对账单的费用会被过滤掉，所以搜出来的分组里费用条数可能少于该分组的全部可申请费用，这是预期行为。
- 客户对账单本身是面向客户（`App_Statements.ClientId`）的，一张对账单里未必含有可付费申请的费用；搜不到结果时先确认该对账单内的费用是否满足本接口其余筛选条件（尤其是「剩余可申请金额 > 0」与「费用状态=审核通过」）。
- **`FillAsync` 的入参不要照抄 `StatementAdminAppService`**。客户对账那边的 `orderFeeResult` 装的是全部命中费用（含分页外业务），所以必须写成 `result.SelectMany(x => x.OrderFees ...)` 才不会为分页外费用白查；而本接口在分组分页后已执行 `items = items.Where(x => pagedKeySet.Contains(...))`，`orderFeeResult` 本身就只有本页费用，直接整个传进去即可。反过来若在本接口写 `SelectMany`，结果一样但多绕一层。
- 已对账信息只做**展示**，不参与任何筛选或金额计算；`isStatemented=true` 不影响该费用能否被付费申请选中。
- `statements` 未对账时是空数组而非 `null`，前端可直接 `.length` 判断，不必判空。
