# 背景意图

2026-09-04 把发票信息拆成子表时，「发票流程 ↔ 发票子表」的两条搭配规则都卡在了录入阶段（新增/编辑/仅编辑发票，见 `付费申请-发票改子表与流程必填-2026-09-04.md`）。实际用起来，其中一条卡错了时机：

**先票后付要求「必须有发票」，但先票后付的正常节奏恰恰是先建单、等对方开票、再回来补录发票。** 卡在录入等于要求用户在还没拿到发票时就填出发票号，只能编一个假的先存着，之后未必改回来——反倒把数据搞脏。

另一条「不开票不能有发票」不一样，它不是「还没填完」而是**自相矛盾**，必须当场拦。

本次把这两条拆到不同时机。改完后又发现已开票量的应付侧判定依赖了「先票后付必然有票」这个前提，一并修掉；顺带把提交入口收口。

# 核心逻辑变更

## 1. 两条规则拆到不同时机

文件：`src/CsprojBuilder.Application/App/PaymentApplication/PaymentApplicationAdminAppService.cs`

| 规则 | 校验方法 | 时机（改动后） |
| :-- | :-- | :-- |
| **先票后付必须有发票** | `ValidateInvoiceRequiredOnSubmit`（新增的私有方法） | **只在 `SubmitAsync`** |
| 不开票不能有发票 | `ValidatePaymentApplicationInvoices` | 新增 / 编辑 / 仅编辑发票，照旧 |
| 发票号必填、不超长、同一申请下不重复 | 同上 | 同上，照旧 |

提交时发票已经落库，所以按 `App_PaymentApplicationInvoices` 的条数判，多一次 `CountAsync`：

```csharp
var invoiceCount = await _paymentApplicationInvoiceRepository.GetAll().AsNoTracking()
    .CountAsync(x => x.PaymentApplicationId == input.Id);
ValidateInvoiceRequiredOnSubmit(paymentApplication.InvoiceProcess, invoiceCount);
```

报错文案跟着改：从「发票流程为先票后付时 发票信息不能为空」改成「发票流程为先票后付时 **提交前**必须录入发票信息」，让用户知道当下还能存。

两个方法的 XML 注释里**互相写明了对方为什么在另一个时机**，防止下一个人再把它们合回一处。

## 2. 已开票量的应付侧判定改为只看子表

文件：`src/CsprojBuilder.Application/App/InvoiceIssue/OrderFeeInvoicedProvider.cs`，`GetInvoicedAmountMapAsync`

原条件把「先票后付」当成了「已取得发票」的替身：

```csharp
// 改动前 —— 先票后付不再保证有票 这个条件就错了
.Where(x => x.PaymentApplication.InvoiceProcess == InvoiceProcess.InvoiceBeforePayment
            || (x.PaymentApplication.InvoiceProcess == InvoiceProcess.PaymentBeforeInvoice
                && x.PaymentApplication.PaymentApplicationInvoices.Any()))

// 改动后
.Where(x => x.PaymentApplication.PaymentApplicationInvoices.Any())
```

上一步放开录入校验之后，「先票后付 + 零发票」成了合法的录入态，旧条件会把这种草稿算成**已开票**，进而顶高费用的已开票量和落库的 `InvoiceStatus`。

`GetOrderInvoiceAmountMapAsync`（发票申请量）**不受影响**：它本来就三种流程一律计入，不判子表。

## 3. 发票子表新增两列，发票号改为全局唯一

文件：`src/CsprojBuilder.Core/Entites/PaymentApplication.cs`

| 列 | 类型 | 说明 |
| :-- | :-- | :-- |
| `SellerHeader` | `nvarchar(256)?` | 销售方抬头。**纯文本不关联客户表**——开票方未必是本系统里的客户，所以没做成外键 |
| `Amount` | `decimal(18,2)?` | 发票金额，允许负数（红字发票）。**不参与任何额度计算**，也不与申请金额比对 |

`Amount` 刻意不与付费申请的申请金额做校验：对方发票金额与我方申请付款额本就可以不等（多张票拼一笔付款、一张票分批付），加比对只会误报。

发票号的唯一性范围从「同一次提交的数组内」扩大到**全部付费申请之间**：

```csharp
var duplicated = await _paymentApplicationInvoiceRepository.GetAll().AsNoTracking()
    .WhereIf(paymentApplicationId != null, x => x.PaymentApplicationId != paymentApplicationId.Value)
    .Where(x => invoiceNos.Contains(x.InvoiceNo))
    //挡掉指向已删付费申请的孤儿发票行 否则删掉的单子会永久占住发票号
    .Where(x => _paymentApplicationRepository.GetAll().Any(p => p.Id == x.PaymentApplicationId))
    .Select(x => new { x.InvoiceNo, x.PaymentApplication.ApplicationNo })
    .FirstOrDefaultAsync();
```

三个细节都是必须的：

| 细节 | 不这么做会怎样 |
| :-- | :-- |
| 排除当前申请自己的发票行（新增传 `null`，编辑传 `input.Id`） | 编辑是全量覆盖（先删后写），不排除的话**原样保存都会撞自己** |
| 用 `Any(p => p.Id == ...)` 要求父单还在 | 已删付费申请的发票行会**永久占住发票号** |
| 报错带上占号申请的 `ApplicationNo` | 只说「重复」用户无从下手，带上单号能直接去查 |

校验方法因此改为异步，重命名 `ValidatePaymentApplicationInvoicesAsync`，三个调用点跟着改。

## 4. 提交入口收口到 `SubmitAsync`

`PaymentApplicationAddDto` / `PaymentApplicationEditDto` 的 `Status` 与 `SubmitTime` 两个入参下线（在 DTO 里注释掉并留了原因），对应地：

| 方法 | 改动 |
| :-- | :-- |
| `AddAsync` | 一律 `data.Status = Entering`、`data.SubmitTime = null` |
| `EditAsync` | 删掉整个「传 `Status=Auditing` 就置审核中」的分支，不再碰 `Status` / `SubmitTime` |

原先这两个接口支持传 `Status=1` 做「保存并提交」（DTO 注释就是这么写的），但**只把状态改成审核中，从不创建 `TaskItem` 和工作流实例**——`CreateWorkFlowInstanceWithPaths` 全项目只在 `SubmitAsync` 里被调用。产出的单据卡在「审核中但没有任何审核任务」：审核列表搜不到，也永远审不掉，只能撤销提交。

`SubmitTime` 一并下线的原因：`AddAsync` 走 `ObjectMapper.Map` 整体映射，这个字段本来能被调用方任意传入；去掉 `Status` 之后再没有分支会覆盖它，会留下「录入状态却已有提交时间」的脏数据。

# 避坑指南

- **「已取得发票」只能看子表，不能看 `InvoiceProcess`。** `InvoiceProcess` 只表示**意图**，不代表**事实**：先票后付的发票必填只卡在提交，录入阶段是空的。这条踩过一次了（本次修的就是它），新写聚合时别再用流程当替身。
- **`Any()` 这个简化依赖「不开票不能有票」仍卡在录入。** 若哪天把那条也挪到提交，「不开票 + 有票」就会成为合法录入态，从另一头把已开票量顶上去。两条规则是**一组**，动其中一条必须回头看 provider。
- **发票号唯一性是查库比对，不是数据库唯一索引。** 并发下两个人同时提交同一个发票号仍可能双写成功。**这是已确认的取舍，不要再去加唯一索引**：业务上不需要那么严格，挡住正常操作路径就够了；存量数据里本就可能有重复（这条规则今天才加），加索引还得先清理，收益不值。
- **`Amount` 不要拿去和申请金额对账。** 它只是抄录对方发票上的金额，与 `PaymentApplicationItem.AppliedAmount` 没有任何约束关系，多张票拼一笔付款、一张票分批付都是正常的。
- **改口径之后存量 `InvoiceStatus` 要刷一次。** 之前「先票后付 + 零发票」的付费申请曾被算成已开票，对应费用的 `InvoiceStatus` 锈在旧值上。批量调 `RecalcByOrderFeesAsync`，不要手写 SQL。
- **前端不能再靠 `status=1` 提交。** 传了不会报错，ABP 直接丢弃未知字段，所以是**静默失效**——单子会停在录入状态而前端以为提交了。必须改成先 `AddAsync`/`EditAsync` 再 `SubmitAsync`。
- **仅编辑发票 `EditInvoiceAsync` 仍然不校验先票后付。** 它的用途就是事后补票/改票，任意状态都能调。这意味着一张已提交甚至已通过的先票后付申请，理论上可以被这个接口把发票清空。当前刻意不拦（拦了就把这个接口自己堵死了），如果将来发现被误用，应当按「申请状态是否已过提交」来判，而不是无条件拦。
