**本文不写接口。** 接口地址、鉴权方式、入参出参结构、报文样例、权限点与接口的对应关系，全部在同目录下的《空运出口模块接口文档》里。本文提到某个能力时只说「新增」「列表」这样的功能名，不写路径和参数。

# 1. 业务背景与数据结构

## 1.1 业务定义

空运出口（AirExport）用于登记一票从国内机场发往境外机场的空运货物，覆盖接单、订舱、报关、送仓、起飞的全过程单据信息，并承载该票的费用归属。

一票空运出口 = 一条业务主表记录 + 一条空运出口扩展记录 + 若干货物明细、商品、关联人员、费用。

## 1.2 两层表结构

系统的业务数据采用「**业务主表 + 业务类型扩展表**」两层结构：

- **业务主表 `App_TransportOrders`**：多种业务类型共用的容器，存放委托单位、收发通、货物描述、日期、危险品、冻柜、费用锁定等通用信息，用 `BizType` 字段区分业务类型（空运出口固定为 `2`）。
- **扩展表 `App_AirExports`**：只存空运出口独有的信息，**与业务主表共享同一个主键**，即 `App_AirExports.Id == App_TransportOrders.Id`，一对一。

写入次序固定：**先插业务主表拿到 Id，再用同一个 Id 插扩展表**。不存在「有扩展表记录但没有业务主表记录」的数据。

这个两层结构对使用者的直接影响：**同一票的字段分散在两层**。界面上并排的两个输入框，可能一个属于扩展表、一个属于业务主表。第 2 章的表结构和第 8 章的界面分区都标注了每个字段属于哪一层。

## 1.3 子表挂载关系

```
App_TransportOrders (Id)
├── App_AirExports              (Id 相同，一对一，空运出口扩展表)
│   └── App_AirExportOrderCtns  (AirExportId，一对多，货物明细)
├── App_OrderCodeGoodss         (TransportOrderId，一对多，商品/品名)
├── App_OrderUsers              (TransportOrderId，一对多，关联人员)
├── App_ChangeOrders            (TransportOrderId，一对多，改单)
└── App_OrderFees               (TransportOrderId，一对多，费用)
```

附件不是子表，走通用附件模块，通过「模块编码 + 归属键」关联（见 2.8）。

> [!IMPORTANT] **货物明细的挂载方式和其它子表都不一样。** 商品、关联人员、改单、费用都挂在**业务主表 Id** 上，而货物明细挂在**空运出口扩展表 Id** 上（字段名 `AirExportId`）。虽然这两个 Id 的值是同一个，但外键指向的表不同，写代码和查数据库时别搞混。这也意味着：没有空运出口扩展记录的票，不可能有货物明细。

**业务主表那一层的集装箱表 `App_OrderCtns` 空运出口完全不用**：空运没有箱型，箱型是必填的，进不来。空运出口的货物明细是全新的一张表，字段完全不同（见 2.3）。

## 1.4 三个日期字段的准确含义

空运出口界面上的三个日期，底层字段名沿用了海运的命名，**名字和界面文案对不上**，这是最容易搞混的地方：

| 界面文案 | 数据库字段 | 说明 |
| :-- | :-- | :-- |
| **起飞日期** | `ETD` | 字段在系统中的定位是「这一票的业务日期」，会计期间与应结日期都以它为基准推算。海运出口那边这个字段叫「开船日期」 |
| **实际起飞日期** | `ATD` | 海运出口那边叫「实际开船日期」 |
| **预抵日期** | `ETA` | 名称与海运一致，不改 |

测试提缺陷时请写清「起飞日期（ETD）」，避免歧义。

## 1.5 本期范围

**本期要做**：空运出口的新增、编辑、详情、列表、分组统计、复制、删除、重新生成委托编号、附件的查询/新增/删除；业务主表的详情与删除按业务类型分流；基础资料删除时的引用校验；客户模块的订舱代理统计纳入空运出口。

**本期不做**（这些能力在空运出口界面上不出现）：服务项目与服务项任务、分单、派车、单据打印、费用模板自动生成、业务联系单转空运出口、外部对接中的洋歌与单证识别 TextIn、下游模块（业务费用列表分组、客户对账、开票申请、发票开出、付费申请）针对空运出口的适配、根据航班自动带出日期。

> **后续已追加的能力**：外部运踪对接已经做了两家——**云当空运运单**与**飞驼航空货运跟踪**，列表与详情都会返回运踪信息，详见 7.10。

费用子表本身不做任何改造，现有费用模块按业务主表 Id 工作，对空运出口票天然可用。

> **打印**：本期不做打印功能，但详情保留了「按打印方式打开」的开关与公司打印信息的返回位置，后续接打印时不用再改接口契约。本期该开关打开时返回的仍是完整的公司信息，只是界面上没有用它的入口。

# 2. 表结构

**通用约定**（适用于本章所有表）：

- 业务主表与空运出口扩展表都是**软删除**：删除只是把 `IsDeleted` 置为 `true`，所有查询自动过滤掉已删除数据。软删除**不会级联**到子表，需要删除的子表由后端逐条显式删除。
- 货物明细表、商品表、关联人员表**没有软删除标记**，是物理行，编辑时按全量比对增删。
- `decimal` 未特殊说明的一律为 `decimal(18,2)`。业务主表毛重 `Kgs` / 体积 `Cbm`，以及货物明细的单件重量 `KGS` / 单件体积 `CBM`，均为 `decimal(20,4)`（整数 16 位、小数 4 位）。空运出口扩展表泡比、货物明细长宽高/体积重/计费重仍是 `decimal(18,6)`，在表里逐个标注了。
- `datetime` 对应 SQL Server 的 `datetime2`。
- 字符串长度均指**字符数**，超长直接报错，不截断。录入内容的首尾空格会被自动去掉，**长度是按去空格之后算的**。
- 「可空」列的「否」表示数据库非空；未录入时按该行说明的默认值处理。

## 2.3 App_AirExportOrderCtns（货物明细表）

**挂在空运出口扩展表上**（外键是 `AirExportId`，不是 `TransportOrderId`），一票多行，用来登记每一种规格货物的尺寸与重量。

| 字段 | 类型 | 长度 | 可空 | 含义 | 生成逻辑 / 外键 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| Id | Guid | - | 否 | 主键 | 后端生成，非自增。编辑入参中该字段**可空**，不传或传 `null` 视为新增行，传值视为更新行 |
| AirExportId | Guid | - | 否 | 空运出口id | 外键 → `App_AirExports.Id`，后端赋值 |
| PKGS | int? | - | 是 | **件数** | 本行有多少件。用户手填 |
| KGS | decimal? | **20,4** | 是 | **重量（千克）** | **单件重量**，不是整行合计。用户手填 |
| Length | decimal? | **18,6** | 是 | **长（厘米）** | 单件尺寸。用户手填 |
| Width | decimal? | **18,6** | 是 | **宽（厘米）** | 单件尺寸。用户手填 |
| Height | decimal? | **18,6** | 是 | **高（厘米）** | 单件尺寸。用户手填 |
| CBM | decimal? | **20,4** | 是 | **体积（立方米）** | **单件体积**。前端按长×宽×高÷1000000 计算，允许手改，后端只存不算（见 6.1） |
| VolumeWeight | decimal? | **18,6** | 是 | **体积重（千克）** | **整行合计值**。前端按单件体积×167×件数计算，允许手改，后端只存不算（见 6.1） |
| ChargeWeight | decimal? | **18,6** | 是 | **计费重（千克）** | **整行合计值**。前端按 max(体积重, 单件重量×件数) 再按 0.5 千克向上进位，允许手改，后端只存不算（见 6.1） |
| SortId | int | - | 否 | 排序id | 界面传，不传为 0。查询返回时按 SortId **升序**排列（小的在前），SortId 相同的按主键升序 |

> [!IMPORTANT] **主键是 Guid 不是自增整数**，由后端在插入时生成。因此 SortId 相同的行之间，兜底的主键排序是**随机顺序**，不代表录入先后。要保证行序稳定，界面必须给每行分配**唯一且连续**的 SortId。

> [!IMPORTANT] **同一行里单位是混着的**：件数、重量、长、宽、高、体积都是**单件**的值，而体积重和计费重是**整行合计**的值。界面上这三类列一定要在表头标注清楚（例如「重量/件(KGS)」「体积重合计(KGS)」），否则用户很容易把重量也当成整行合计来填，算出来的运费会差几十倍。

**这张表上没有的东西**：没有备注列、没有箱型/包装/商品外键、没有软删除标记、没有审计字段。

**行序由 `SortId` 升序决定**，界面上下移动行或往中间插行时，要把整表的 `SortId` 重排后一起提交。主键是 Guid，排不出录入先后，`SortId` 是唯一可靠的顺序依据。

**与业务主表完全不联动**：业务主表上也有件数、毛重、体积三个字段，那是整票的申报值，和这张明细表**互不影响**。改明细不会更新主表，改主表也不会更新明细，两边对不上也不会报错。

## 2.7 App_OrderFees（费用子表）

空运出口**不新增也不修改任何费用逻辑**：费用的录入、审批、结算、开票全部由现有费用模块处理。空运出口只做三件与费用相关的事：

1. 列表和详情**只读展示**该票的费用清单与两个方向的费用状态汇总值（见 6.6）；费用清单按 `sortId` 升序、相同再按创建时间升序；
2. 复制时按用户选择决定是否把费用一起复制（见 7.5）；
3. 删除时校验该票不能还有费用（见 7.6）。

空运出口展示的费用信息包含：收付类型、费用状态、结算状态、开票状态、费用代码及名称、行业类别、结算对象及简称、客户对账 id、币别及名称、汇率、含税与不含税单价、含税与不含税金额、单位、数量、税率、已开票金额、发票申请金额、未开票金额、已结算金额、是否禁开发票、是否机密、录入方式、会计期间、备注、创建人及昵称、所属改单 id、排序 id。

其中三个金额是**空运出口查询时现场算出来的**，不是费用记录上的字段：

| 值           | 口径                                                       |
| :----------- | :--------------------------------------------------------- |
| 已开票金额   | 该费用在**已开票**状态的开票申请中的申请金额合计；没有则 0 |
| 发票申请金额 | 该费用在**所有状态**的开票申请中的申请金额合计；没有则 0   |
| 未开票金额   | 含税金额 − 已开票金额，**超额开票时会是负数**              |

> 空运出口展示的费用是**只读概览**，部分费用字段（组织、各类编码、本次结算金额、申请付款金额、未结算金额、对账单对象、审批任务明细等）在这里不填充。需要完整费用数据时请使用业务费用模块自己的功能。费用清单里每条还有一个「组合费用状态」属性，空运出口不填充它，**票级的应收/应付组合状态请看 6.6 的两个汇总值**。

## 2.8 附件

空运出口的附件通过通用附件模块管理，本模块只负责传递归属关系与分组结构。

- **模块编码**：`160080`。所有空运出口附件都用这个编码标记。
- **归属键**：空运出口 Id（与业务主表 Id 相同）。
- **分组键**：附件明细类型（例如托书、运单、发票），是已有的基础资料。**分组的展示规则由前端控制，后端不参与分组语义**，只按类型原样分组返回。
- 一个附件可以同时挂在多票上；**从某一票移除附件只解除这一票的关联**，既不删除文件本身，也不影响其它票。
- 附件关联不随主表软删除级联，删除票据时后端显式清理（见 7.6）。

**附件的组织形式**：每票的附件按附件明细类型分成若干组，组内按顺序号升序；组之间先按类型的排序号升序，没有类型的那一组排在最后。

**每个附件展示的信息**：文件名、文件大小、附件类型（图片/视频/Flash/音乐/文档/压缩包/其他，由扩展名推断）、下载直连地址、客户是否可见、顺序号、上传时间、上传人。

**附件的两种维护方式**（效果相同，选其一即可）：

1. 在保存单据（新增/编辑）时连同附件分组一起提交；
2. 单独使用附件的新增、删除功能。

# 4. 权限

空运出口的权限分三层，三层是叠加关系：**能不能用这个功能**（功能权限）→ **能看到哪些票**（数据权限）→ **票上能看到哪些字段**（字段级权限）。

## 4.1 功能权限点

| 权限标识 | 名称 | 覆盖的操作 |
| :-- | :-- | :-- |
| `Admin.AirExport` | 空运出口（父级） | 菜单可见性 |
| `Admin.AirExport.Add` | 添加 | 新增、复制 |
| `Admin.AirExport.Get` | 查看 | 列表、分组统计、详情、查询附件 |
| `Admin.AirExport.Edit` | 编辑 | 编辑、重新生成委托编号、新增附件、删除附件 |
| `Admin.AirExport.Delete` | 删除 | 删除 |

四个权限点均为**租户级**。所有操作都要求已登录。

> 注意「复制」归在添加权限下，「附件的增删」归在编辑权限下，「重新生成委托编号」也归在编辑权限下。给角色配权限时容易漏掉这三处。

## 4.2 数据权限（行级）

列表、分组统计在功能权限之外，还会叠加行级数据权限过滤。规则如下：

1. 先解析当前用户在「查询」操作类型下的数据权限配置（用户自身的配置 + 其所有角色的配置）。
2. 若命中「全部数据」权限，不做任何过滤，能看到全部票。
3. 否则解析出两个集合：
   - **可见用户集合**：配置里指定的用户，**再加上自己**。
   - **可见组织集合**：配置里指定的组织、以及「我的部门」「我的公司」解析出的组织，每个组织**都展开为它自己及其全部下级组织**。
4. 一票只要满足下列任一条，就可见：
   - 该票的**所属人**在可见用户集合内；
   - 该票的**创建人**在可见用户集合内；
   - 该票的**所属组织**在可见组织集合内；
   - 该票的**业务关联人员**中，存在一条记录，其用户在可见用户集合内且属性属于：销售、商务、操作、客服、单证、海外客服、航线。

**列表的总条数是过滤之后的结果**，不同账号用同样的筛选条件，看到的总数可能不同。

### 按 Id 操作的接口同样做行级过滤（2026-08-19 起）

详情、编辑、删除、重新生成委托编号这四个按 Id 定位单票的接口，**此前不做任何行级过滤**，只要知道 Id 就能查看甚至改删任意一票。现已统一改为：先过行级数据权限、再过表级权限，两层都通过才继续。

| 接口                           | 解析数据权限时用的操作类型 |
| :----------------------------- | :------------------------- |
| 详情                           | 查询                       |
| 编辑 / 删除 / 重新生成委托编号 | **编辑**                   |

判定口径与上面第 1～4 条完全一致，只是解析配置时的操作类型不同。任一层不通过都直接报错，三种情况提示语不同，便于区分是数据问题还是权限问题：

| 情况                     | 提示语                                            |
| :----------------------- | :------------------------------------------------ |
| 这一票根本不存在         | 各接口原有的「不存在」提示                        |
| 票在，但没有行级数据权限 | 「没有这条数据的数据权限,不能查看 / 编辑 / 删除」 |
| 行级过了，被表级权限挡掉 | 「没有这条数据的表级权限,不能查看 / 编辑 / 删除」 |

> [!IMPORTANT] 数据权限的操作类型只有「查询」和「编辑」两种，**没有删除**，所以删除也按「编辑」判定。
>
> 「编辑」这个操作类型此前**从未被任何代码读取过**，本次是它第一次真正生效。这不是上线卡点，上线后由客服按需给用户和角色配置编辑口径的数据权限即可。
>
> 配置到位之前，用户只能改动「自己是所属人 / 创建人 / 干系人」的票，列表里其余行的「是否可编辑」都是否。有人反馈改不了单、编辑按钮是灰的，先查这里。

## 4.3 字段级权限

列表、分组统计的查询会额外叠加「表格字段级权限」过滤，模块标识为 `AirExport`。

被屏蔽的字段分两层，独立配置，可能出现「空运层能看航班、业务层看不到主提单号」这种组合：

| 层级             | 作用范围                           |
| :--------------- | :--------------------------------- |
| 空运出口自身字段 | 空运出口这一层的字段（含货物明细） |
| 业务主表字段     | 业务主表那一层的字段               |

**编辑时有配套保护**：保存前，当前用户无权查看的字段会被后端用数据库原值回填，避免用户因为看不到该字段而没填、导致保存时把库里的值抹掉。这个回填对空运出口扩展表和业务主表分别执行一次。

# 5. 通用业务规则

## 5.1 提示语与错误

模块内所有业务校验失败都会返回一句用户可读的中文提示，界面直接展示即可。**本文各处引号内的文字就是最终展示给用户的原文，一字不差**，测试可以直接做字符串相等断言。

非预期的系统异常（数据库超时、空引用等）也会以同样的方式返回一句话。因此**看到不在本文档清单里的提示语，就是系统异常，应当提缺陷**，而不是当成业务规则。

## 5.2 列表的分页与排序口径

- 默认每页 10 条，第 1 页；每页条数上限 100000，页码从 1 开始，超出范围会被拦下。
- 默认按**创建时间倒序**。
- 支持多字段排序，前一个字段相同时用后一个字段续排。
- 支持按关联对象的字段排序，例如按委托单位名称排序。
- 排序字段应固定为列头绑定的白名单，不要把用户输入的任意文本当排序字段用。

## 5.3 筛选的匹配语义

| 匹配方式 | 行为 | 注意 |
| :-- | :-- | :-- |
| 模糊 | 包含匹配 | **不区分大小写**；该字段为空的记录**不会**被匹配到 |
| 精确 | 完全相等 |  |
| 区间 | 闭区间，两端可以只填一端 |  |
| 空白条件 | 不填、空字符串、全空白 | 一律视为**不筛选** |
| 多个条件之间 | 一律「并且」 | 唯一的「或者」是关键字搜索内部的多个字段之间 |

**关键字搜索**覆盖 6 个字段：航班、外部备注、主提单号、合同号、发票号、委托编号。

## 5.4 「未填写」类筛选开关

航班、订舱代理、起运地、中转地、目的地这五个字段，除了按值筛选，还各自提供一个「未填写」开关，用于筛出该字段为空的票。

规则：

- 只选值：筛选等于该值的票（航班是模糊匹配）；
- 只开「未填写」：筛出该字段为空的票；
- **两者同时使用**：直接报错，不做兜底。报错文案是「起运地筛选：未填写与指定id不可同时传入」，中转地、目的地、订舱代理同格式，航班是「航班筛选：未填写与指定航班不可同时传入」；
- 「未填写」关掉：等同于不筛，**不会**反向筛出「已填写」的票；
- 两者都不用：不按该字段过滤。

这个校验在所有筛选逻辑最前面执行，一旦冲突，其它条件都不会生效。

## 5.5 日期处理

- 业务主表的起飞日期、实际起飞日期、预抵日期、货好时间在保存时**只保留日期部分**，时分秒一律归零。
- 空运出口层的报关日期、送仓日期**原样保存，不截断**；界面如果带上了时分秒，回看时也会带回来。建议界面统一只录日期。
- 会计期间由后端算成「所在月 1 号」。
- 所有日期区间筛选都是**闭区间**。由于空运层的两个日期不截断时分秒，筛选「止」端时建议取当天的最后一刻，否则当天带时分秒的数据会被漏掉。
- 系统不做任何时区换算，录入什么本地时间就存什么。**空运港口基础资料上虽然有时区字段，业务单据完全不使用它。**

# 6. 计算与派生规则

## 6.1 前端计算的四个值（后端一律只存储）

以下四个值全部由**前端计算并允许用户手工覆盖**，后端接收什么存什么，**不重算、不校验、不覆盖**。

| 值 | 所在层 | 计算公式 | 边界处理 |
| :-- | :-- | :-- | :-- |
| 体积 CBM | 货物明细行 | 长 × 宽 × 高 ÷ 1000000 | 长宽高任一为空 → 留空。单位换算：长宽高是厘米，体积是立方米 |
| 体积重 | 货物明细行 | **单件体积 × 167 × 件数** | 体积或件数任一为空 → 留空 |
| 计费重 | 货物明细行 | **max(体积重, 单件重量 × 件数)**，再按 **0.5 千克向上进位** | 两个都算不出来 → 留空；只算得出一个 → 取算得出的那个再进位 |
| 泡比 | 空运出口层 | **业务主表毛重 Kgs ÷ 业务主表体积 Cbm** | 毛重为空、体积为空、体积为 0 → **留空（null）**，不要存 0 |

**几个必须记住的口径**：

- **167 是写死的常量**，不可配置，不随航司或航线变化。
- **体积重和计费重是整行合计值**，公式里已经乘过件数了；而重量和体积是单件值，公式里的「单件重量 × 件数」就是这一行的实际总重。
- **计费重的进位**：先取两者最大值，再向上进到 0.5 的整数倍。例如 12.1 进位成 12.5，12.5 保持 12.5，12.6 进位成 13.0。
- 所有这些值都是 **6 位小数**，界面不要按 2 位截断显示。
- **票级没有计费重合计字段**，不要在扩展表上找，也不要指望后端返回。需要整票计费重时由界面自行把各行相加显示。

> [!IMPORTANT] **这四个值不会因为基准值变化而自动重算。** 用户改了长宽高、件数、重量，或改了业务主表的毛重体积之后，如果没有重新触发前端计算，保存下去的仍是旧值，后端不会纠正。这是既定行为，测试需覆盖并按此判定。

## 6.2 会计期间与应结日期（后端计算）

新增、复制、编辑时后端都会重新计算这两个值，**界面上填什么都会被覆盖**，因此这两项在界面上应做成只读。

**基准时间**：起飞日期（ETD）；起飞日期为空时取当前时间。

**会计期间** = 基准时间所在月的 1 号（年月保留，日固定为 1，时分秒为 0）。

**应结日期**按委托单位的账期规则推算：

1. 查该委托单位下**当前生效**的账期规则。长期有效的直接算生效；否则生效时间不填=不限制起始、失效时间不填=不限制截止，填了的那一端才跟当前时间比。
2. 一条都没有 → 应结日期 = 基准时间的日期部分。
3. 有规则时，按下列四个条件筛出**第一条**全部匹配的规则（规则里某个条件没配就视为不限制）：
   - 业务类型：规则没配业务类型，或包含空运出口；
   - 销售：规则没配销售，或规则销售与本票销售有交集；
   - 组织：规则没配组织，或规则组织与本票所属组织及其下级组织有交集；
   - 业务来源：规则没配业务来源，或规则业务来源等于本票的业务来源。
4. 没筛出规则 → 应结日期 = 基准时间的日期部分。筛出的规则是**票结** → 应结日期 = 基准时间的日期部分；规则填了 `addDays` 则再往后加这些天，不填不加。
5. 筛出的规则是**月结** → 应结日期 = 基准时间往后推 N 个月（N 取规则的月数，未配置按 1）之后，取该月的第 D 天（D 取规则的结算日，未配置按 1，大于 31 按 31，小于 1 按 1）。
6. 筛出的规则是**约定天数** → 应结日期 = 基准时间 + 规则天数（未配置按 1 天）的日期部分。

> 计算过程中若发生任何异常，后端会静默跳过，应结日期保持调用前的值。

**编辑时的联动**：如果编辑导致会计期间发生变化，后端会把该票下**所有非改单费用**的会计期间同步更新为新值。**改单费用的会计期间不动**，因为改单本身就是为了独立记账。

> 客户账期规则里的「业务类型」需要能选到空运出口，配置界面上要有这一项。

## 6.3 委托编号

- 新增时**填了就用填的**（长度不超过 32），没填才由后端生成。
- 复制时**一律重新生成**，不沿用原票编号。
- 「重新生成委托编号」功能一律重新生成。
- 生成规则的配置键是 `AirExport.CommissionNum`，需要管理员在「编号规则」里预先配置，**不与其它业务类型共用**（海运出口、海运进口各有各的键）。
- 规则的匹配优先级：先找绑定了当前用户的规则；找不到再按当前用户的组织路径**从最低层级向上**逐级找绑定该组织的规则；再找不到就用「既没绑组织也没绑用户」的全局规则。
- 三级都没找到 → 报「未配置生成规则」；找到规则但规则里没有自增编号项 → 报「未配置自增编号规则」。

## 6.4 航班的规范化

保存航班时，如果值是空、空字符串或全是空白字符，一律存为空。目的是让筛选「未填写」时不会出现「空」和「空字符串」两种都算未填写却匹配不到的情况。

## 6.5 组织归属校验

新增和编辑时都会执行，**复制不执行**（复制沿用源票的组织）。

规则：取本票业务关联人员中的**销售**（有且只有一个），校验所选的所属组织必须是该销售的**直属组织**。「直属」= 用户与组织的直接绑定关系，**不看父子继承**——销售挂在「上海分公司-空运部」下面时，选「上海分公司」也不通过。销售同时挂在多个组织下时，命中其中任意一个即可。

按顺序执行，任一条不满足立即报错：

| 顺序 | 条件 | 提示语（注意结尾有句号） |
| :-- | :-- | :-- |
| 1 | 所属组织没选、为空或非法 | 所属组织不能为空。 |
| 2 | 销售的用户为空 | 数据所属人不能为空，无法校验所属组织。 |
| 3 | 所选组织在组织树中不存在 | 所选组织不存在。 |
| 4 | 所选组织不是该销售的直属组织 | 所选组织不在数据所属人(本人)所属组织范围内。 |

> [!IMPORTANT] 第 1 条意味着**所属组织实际上是必填项**，尽管数据库列可空。界面必须把它做成必填。

另外，在执行本节校验之前，还会先判断销售本身是否有效，无效时报「销售不能为空」。这条与上表第 2 条的差别只在文案，实际先命中的是「销售不能为空」。

**这条规则的实际影响**：换销售时可能连带需要改所属组织。界面在切换销售之后，应重新加载该销售的直属组织列表，并清掉不在列表内的旧选择，否则用户会在保存时才撞上第 4 条报错。

## 6.6 组合费用状态的合成规则

列表和详情会展示四个费用相关的汇总值：

| 值 | 含义 |
| :-- | :-- |
| 应付费用状态最小值 | 该票所有**应付**费用的费用状态取最小值；没有应付费用时为空 |
| 应收费用状态最小值 | 该票所有**应收**费用的费用状态取最小值；没有应收费用时为空 |
| 应付组合费用状态 | 该票**应付**方向的组合状态（枚举见 3.12）；没有应付费用时为空 |
| 应收组合费用状态 | 该票**应收**方向的组合状态（枚举见 3.12）；没有应收费用时为空 |

组合状态的计算范围是该票该方向的**全部费用，包含改单费用**。计算前先查出该票所有费用中，存在**待审核**的「费用修改申请」和「费用删除申请」的费用集合。然后按下列顺序**逐条判断，命中即返回**：

1. 任意一条费用是**驳回** → `5 驳回`
2. 任意一条费用在**待审核的修改申请**集合内 → `6 申请修改`
3. 任意一条费用在**待审核的删除申请**集合内 → `7 申请删除`
4. 任意一条费用是**录入状态** → `0 录入状态`
5. 任意一条费用是**提交审核** → `1 提交审核`
6. **所有**费用都是**结算完毕** → `4 结算完毕`
7. 任意一条费用不是**未结算** → `3 部分结算`
8. 以上都不满足 → `2 审核通过`

> 顺序即优先级。只要有一条驳回，整票该方向就显示驳回，哪怕其它费用都已结算完毕。

## 6.7 客户模块的供应商统计

客户详情里有四个供应商维度的统计值，原先只统计海运出口的订舱代理，**本期要把空运出口的订舱代理也统计进去**：

| 统计值 | 口径 | 空运出口的处理 |
| :-- | :-- | :-- |
| 合作起始时间 | 该客户作为订舱代理的最早一票的业务日期 | **纳入统计** |
| 最后交易时间 | 该客户作为订舱代理的最晚一票的业务日期 | **纳入统计** |
| 年票数 | 该客户作为订舱代理，本年度的票数 | **纳入统计** |
| **年 TEU** | 该客户作为订舱代理，本年度各票的箱型 TEU 之和 | **不纳入统计**。空运没有集装箱，TEU 无从算起，空运票对这个值的贡献恒为 0 |

> 结果就是：一个只做空运的订舱代理，年票数会有数字，年 TEU 是 0。这是预期行为，不是漏算。

# 7. 功能与操作逻辑

本章讲每个操作**做了什么、校验什么、按什么顺序、失败时说什么话**。参数与返回结构见《空运出口模块接口文档》。

空运出口共 9 类操作：新增、编辑、详情、列表、复制、删除、分组统计、重新生成委托编号、附件维护（查询/新增/删除）。

## 7.1 新增

**校验顺序与提示语**（命中即中断，不会一次返回多条）：

1. 没有任何输入 → 「输入信息不能为空」
2. 缺少业务主表信息 → 「业务信息不能为空」
3. 关联人员为空 → 「业务关联人员不能为空」
4. 关联人员中销售的条数**不等于 1** → 「销售有且只能有一个」。这是唯一的人员必填约束，操作、单证、客服等其它属性都可以不填
5. 委托单位不存在（含没选）→ 「委托单位不存在」
6. 字符串长度校验，超长报「{字段中文名}长度不能超过{N}个字符」：

   | 字段                                                   | 上限    |
   | :----------------------------------------------------- | :------ |
   | 委托编号                                               | 32      |
   | 主提单号 / 订舱编号 / 合同号 / 发票号                  | 各 64   |
   | 内部备注 / 收货人内容 / 发货人内容 / 通知人内容 / 备注 | 各 1024 |
   | 航班                                                   | 64      |
   | 起运地备注 / 中转地备注 / 目的地备注                   | 各 1024 |

   货物明细表**没有任何字符串字段**，不涉及长度校验。

7. 主提单号重复校验（长度通过后立刻做）：填了主提单号，且当前租户业务表已有相同号码 → 「主提单号【{号码}】已存在」。去首尾空格、忽略大小写；空值不校验；已软删除不参与。**海运出口、海运进口、空运出口共用业务表主提单号，三种业务互相也不能撞号。** 编辑时排除自身，保存自己原来的号不会拦。
8. 外键存在性校验，选了但基础资料不存在（或已被删除）时报错。**注意两种文案格式并存**：

   | 字段 | 提示语 |
   | :-- | :-- |
   | 业务主表的包装 | 包装ID:{id}不存在 |
   | 业务来源 | 业务来源不存在 |
   | 运输条款 | 运输条款不存在 |
   | 起运地 | 起运地不存在 |
   | 中转地 | 中转地不存在 |
   | 目的地 | 目的地不存在 |
   | 订舱代理 / 车队 / 报关行 / 仓库 / 保险公司 / 收货人 / 发货人 / 通知人 | {字段中文名}不存在，例如「订舱代理不存在」 |

   没选的外键跳过校验，不报错。

9. 商品子表逐条校验：商品没选 → 「商品信息(品名)ID不能为空」；商品不存在 → 「商品信息(品名)ID:{id}不存在」
10. **货物明细不做任何校验**：没有必填项、没有外键、没有长度限制、不校验数值范围（负数、0、超大值都能存进去）。空列表也允许
11. 关联人员的用户不存在 → 「用户ID:{id}不存在」
12. 销售无效 → 「销售不能为空」
13. 组织归属校验（见 6.5，四条提示语在那里）

**必填与非必填的明确结论**（避免界面凭感觉加校验）：

| 字段 | 是否必填 | 说明 |
| :-- | :-- | :-- |
| 委托单位 | **必填** | 数据库列非空，不选会走到「委托单位不存在」 |
| 所属组织 | **必填** | 见 6.5，报「所属组织不能为空。」 |
| 业务关联人员，且销售恰好 1 个 | **必填** | 见校验 3、4。**这是关联人员里唯一的必填约束** |
| 商品子表的商品 | 每条必填 | 整个列表可以为空 |
| 货物明细的所有列 | **全都不必填** | 一行只填件数、其它全空也能存 |
| 起运地、中转地、目的地 | **都不必填** | 可以都不选直接保存 |
| 航班、订舱代理、泡比、报关日期、送仓日期 | 都不必填 |  |
| 起飞日期 | 不必填 | 为空时会计期间按当前时间算 |
| 委托编号 | 不必填 | 不填由后端按规则生成，见 6.3 |

**保存过程**：

1. 规范化日期：起飞日期、实际起飞日期、预抵日期、货好时间截断到日期部分。
2. 计算会计期间与应结日期（见 6.2）。
3. 委托编号：填了用填的，没填按规则生成（见 6.3）。
4. 插入业务主表，后端强制写入业务类型 = 空运出口、录入方式 = 手动录入、未完结 = false、租户、所属人、所属组织，拿到新 Id。
5. 两张挂在业务主表上的子表（商品、关联人员）随主表一起写入。
6. 用同一个 Id 插入空运出口扩展表，航班做规范化（见 6.4）。
7. **用扩展表的 Id 写入货物明细**。
8. 保存分组附件。

保存成功后返回新票的 Id，界面据此打开详情或跳转编辑。

## 7.2 编辑

**校验**：

1. 没有任何输入 → 「输入信息不能为空」
2. 缺少业务主表信息 → 「业务信息不能为空」
3. 关联人员为空 → 「业务关联人员不能为空」
4. 销售数量不等于 1 → 「销售有且只能有一个」
5. 空运出口记录不存在 → 「输入空运出口错误」
6. 对应的业务主表记录不存在 → 「对应的业务信息不存在」
7. 其余长度校验、主提单号重复校验、外键校验、子表校验、组织归属校验与新增**完全相同**（见 7.1 第 5～13 条，含全部提示语）

**字段级权限回填**：在业务校验之后、写库之前，后端会把当前用户无权查看的字段用数据库原值覆盖回来，扩展表和业务主表各执行一次。这样即使界面因为字段被屏蔽而没提交，也不会把库里的值抹成空。

**保存过程**：

1. 业务主表逐字段更新。起飞日期变化会带动会计期间、应结日期重算，并同步该票所有非改单费用的会计期间（见 6.2）。
2. **三张子表按全量比对处理**，货物明细、商品、关联人员规则一致：
   - 带了主键的行 → 更新库中对应记录；
   - 没带主键的行 → 作为新记录插入（货物明细的主键是可空 Guid，不传或传 `null` 算新增；商品与关联人员的主键是可空自增整数，不传、传 `null` 或传 0 算新增）；
   - **库里存在但本次没有出现的行 → 删除**。
   - 因此界面必须**提交完整的子表列表**，不能只提交发生变化的行。
3. 扩展表逐字段更新，航班做规范化。
4. 泡比、体积、体积重、计费重仍以界面提交值为准，后端不重算。

## 7.3 详情

用于打开一票的完整信息，编辑页也用它做回显。

**校验**：记录不存在 → 「输入空运出口错误」。

**展示的内容**：

| 部分 | 内容 |
| :-- | :-- |
| 空运出口层字段 | 2.1 的全部业务字段 + 创建/修改的审计信息 |
| 数据归属 | 所属人、所属组织，以及从最高级组织到所属组织的**组织串**（每级带本位币信息）；没选组织时组织串为空 |
| 起运地 / 中转地 / 目的地 | 各返回一个**空港对象**（id、三字码、英文名、中文名），没选时为空；**不带出国家、城市、时区** |
| 订舱代理带出 | 简称、全称，以及该单位的默认地址；另返回订舱代理联系人数组 `BookingAgentContacts`（`ClientContactSimpleDto`，可多个，按联系人 id 升序，没有为空数组） |
| 录入人 | 创建人昵称 |
| 录入方式 | 手动录入 / 复制，界面要显示 |
| 业务主表层字段 | 2.2 中「空运展示 = 是」的全部字段，各基础资料带出名称 |
| 往来单位带出 | 委托单位、车队、报关行、仓库、保险公司、收货人、发货人、通知人，每个带简称、全称，以及**该单位的默认地址**（地址子表中标记为默认的那条，没有则为空）；另返回委托单位联系人数组 `ClientContacts`（`ClientContactSimpleDto`，可多个，按联系人 id 升序，没有为空数组） |
| 货物明细 | 该票全部明细行，原样返回 10 个字段，按排序号升序；没有明细时是空列表 |
| 商品 | 该票品名清单，每条带商品名、HS 编码。**没有 TEU** |
| 关联人员 | 每条带用户昵称；整体按排序号**降序**（大的在前），排序号相同的按数据库返回顺序 |
| 费用 | 该票全部费用（含改单费用），字段口径见 2.7；没有费用时是空列表 |
| 费用状态汇总 | 四个汇总值，规则见 6.6 |
| 件数大写 | 「件数的英文单词 + 包装名」整体转大写，例如件数 12、包装名 `CARTONS` 时为 `TWELVECARTONS`。**件数为空时该值为空**。**只有详情有，列表没有** |
| 未解决问题数 | 该票未解决的业务问题数量 |
| 附件 | 分组附件，见 2.8；没有附件时是空列表 |
| 公司打印信息 | **仅在按「打印」方式打开详情时返回**：公司全称、简称、英文名、办公地址、联系电话、邮箱、统一社会信用代码、logo 图片（相对路径前拼 `GlobalServer:BaseUrl` 成直连地址）、默认银行账户（含人民币与美元账户）。由业务主表的所属组织向上解析到公司层级节点取得；没选组织时为空。**本期没有打印功能，这部分是为后续预留的** |
| 上一票 / 下一票 | 按打开详情时带上的列表搜索条件与排序，给出全量顺序里的前一条、后一条 Id。没有则为空。**只有详情有，列表没有** |
| 外部运踪 | 云当运踪节点、飞驼运踪摘要，**外加飞驼的完整轨迹与异常预警明细**（这两项只有详情有，列表没有）。详见 7.10 |

**不返回的内容**（海运有、空运没有，界面别去取）：箱型箱量合计、整票 TEU、商品 TEU、集装箱列表、航线、国家。

**详情要过行级数据权限与表级权限**，口径见 4.2；查不到时按「不存在 / 没数据权限 / 没表级权限」分别报错。

**详情额外返回 `IsEditable`（是否可编辑）**：按「编辑」操作类型的数据权限 + 表级权限判定，与编辑接口的校验是同一套口径，前端可直接用它禁用编辑和删除按钮。能看到不等于能改，这两件事分开判。

**详情额外返回上一票 / 下一票 Id**：打开详情时要把当时列表的搜索条件和排序一起带上。后端按这份条件筛完、再按同一排序排完之后的**全量顺序**给出前一条和后一条的 Id，与当前在第几页无关。没有上一票或下一票、以及当前票已经不在这份结果里时，对应 Id 为空。按打印方式打开时不算这两项。翻票时搜索条件和排序保持不变，只换当前票 Id。

## 7.4 列表

列表是空运出口的主入口，支持关键字搜索、多维度筛选、排序、分页。

**筛选维度**（全部可选，多个条件之间是「并且」）：

| 分组 | 可筛的内容 |
| :-- | :-- |
| 关键字 | 一次模糊匹配 6 个字段：航班、外部备注、主提单号、合同号、发票号、委托编号 |
| 组织 | 按所属组织筛，**自动包含其全部下级组织** |
| 空运出口层 | 航班（模糊，带「未填写」开关）、订舱代理（带开关）、起运地（带开关）、起运地备注（模糊）、中转地（带开关）、中转地备注（模糊）、目的地（带开关）、目的地备注（模糊）、泡比区间、报关日期区间、送仓日期区间、创建时间区间 |
| 业务主表层 | 委托编号（模糊）、会计期间区间、应结日期区间、业务来源、运输条款、是否业务锁定、是否未完结、录入方式、主提单号（模糊）、合同号（模糊）、发票号（模糊）、内部备注（模糊）、货物类型、唛头（模糊）、包装、货物描述（模糊）、委托单位、车队、报关行、仓库、保险公司、收货人及其内容（模糊）、发货人及其内容（模糊）、通知人及其内容（模糊）、**起飞日期区间**、**实际起飞日期区间**、**预抵日期区间**、货好时间区间、是否费用锁定 |
| 关联人员 | 销售、操作、单证、商务、客服，各按用户筛。命中条件是「该票存在对应属性且用户相符的关联人员」 |
| 货物明细 | 件数、重量、长、宽、高、体积、体积重、计费重，**各一个区间**。命中条件是「该票**存在**符合条件的明细行」，不是整票汇总后再比较 |

**不提供筛选的字段**（明确列出，避免误提缺陷）：

- 空运出口界面上**不展示**的三个业务主表字段：订舱编号、付费方式、贸易条款；
- 整票件数、毛重、体积、排序号；
- 全部危险品字段、全部冻柜字段；
- 商品子表、费用状态。

外部备注只能通过关键字间接搜。

**列表每行展示的内容**：2026-10-01 起列表单独用 `AirExportListDto`，只带表格上的列。货物明细只留每行的体积重和计费重，合计仍由前端把这两列加出来。费用明细不返回，有没有费用看 `transportOrder.hasOrderFee`，删除前提示改读这个字段。列表不再查、不再返回云当。飞驼只留弹窗要用的摘要。详情继续返回完整对象。

**过滤链的执行顺序**：先按筛选条件过滤 → 叠加行级数据权限（4.2）→ 叠加字段级权限（4.3）→ 排序 → 统计总数 → 取当前页。因此总条数是**已经过权限过滤的**条数。

## 7.5 复制

用于以现有票为模板快速开一张新票。用户可以选择是否把费用一起带过来。

**校验**：

1. 没有任何输入 → 「输入信息不能为空」
2. 没指定要复制的票 → 「空运出口id不能为空」
3. 源记录不存在 → 「空运出口不存在」
4. 源记录的业务主表不存在 → 「业务信息不存在」
5. 源票关联人员为空 → 「业务关联人员不能为空」
6. 源票销售数量不等于 1 → 「销售有且只能有一个」

**复制规则**：

| 处理 | 字段 |
| :-- | :-- |
| **重新生成** | 委托编号（走编号规则，见 6.3） |
| **重新计算** | 会计期间、应结日期（按新票的起飞日期，规则见 6.2） |
| **清空** | 主提单号、订舱编号、合同号、发票号 |
| **重置为初始值** | 业务锁定 = 否、未完结 = 否、费用锁定 = 否、费用锁定人/锁定时间/解锁人/解锁时间 = 空、**录入方式 = 复制**、所属人 = 当前登录用户、租户 = 当前租户 |
| **原样复制** | 两层表的其余全部字段，包括航班、订舱代理、起运地/中转地/目的地及其备注、泡比、报关日期、送仓日期、起飞日期、实际起飞日期、预抵日期、货好时间、收发通、货物信息、危险品、冻柜等 |
| **连子表一起复制** | 货物明细、商品、关联人员，**全部整表复制**。子表主键重新生成 |
| **不复制** | 附件、改单、业务问题 |

**费用复制**（用户勾选时）：

- 只复制源票的**非改单费用**，改单费用不复制。
- 每条新费用重置为录入初始状态：费用状态 = 录入、结算状态 = 未结算、开票状态 = 未开票、已结算金额 = 0、客户对账 = 空、所属改单 = 空、费用模板项 = 空、录入方式 = 业务复制、会计期间取新票的会计期间。
- 沿用源费用的：收付类型、费用代码、行业类别、结算对象、币别、汇率、含税单价、不含税单价、金额、不含税金额、单位、数量、税率、是否禁开发票、是否机密、备注。

**复制不执行组织归属校验**，直接沿用源票的所属组织。因此复制别人的票时，新票的所属人变成了自己，但所属组织仍是源票的组织，两者可能不匹配——**这种票下次编辑时会撞上组织归属校验**，需要先改所属组织。这是需要留意的边界。

## 7.6 删除

**校验**：

1. 记录不存在 → 「空运出口不存在」
2. **该票还存在未删除的费用** → 「当前票包含未删除费用，请先删除费用」。这是硬约束，无论费用处于什么状态、是不是改单费用，只要有一条就拒绝删除，没有强制删除的旁路

**删除范围**（软删除不级联，全部由后端显式执行）：

1. 该票的费用审批任务及其明细：任务类型为「提交费用」「修改费用」「删除费用」的任务
2. 改单记录
3. 商品子表
4. **货物明细（按空运出口 Id 删）**
5. 关联人员子表
6. 业务问题及其附件关联
7. 本票的附件关联（**只解除关联，不删除附件文件**）
8. 最后软删除空运出口扩展表与业务主表

删除是软删除，数据库里记录仍在，只是所有查询都过滤掉了。

## 7.7 分组统计

按指定维度对**当前筛选结果**做票数统计，通常用于列表页上方的统计卡片或左侧分组树。

**处理**：先按与列表**完全相同**的条件过滤（含数据权限与字段级权限），再按指定维度分组统计。分页在这里无效，返回全部分组。

**支持的维度**见 3.6，传枚举以外的值报「不支持的分组字段」。

**每个分组返回**：分组值、分组显示名、票数。**按票数降序排列**。

分组名的取值来源：

| 维度 | 显示名取自 |
| :-- | :-- |
| 委托单位 / 订舱代理 / 车队 / 保险公司 / 报关行 / 仓库 | 往来单位的**简称** |
| 起运地 / 中转地 / 目的地 | 空运港口的「**三字码/中文名**」拼接，例如 `PVG/上海浦东国际机场`；两项缺一项时只用有的那一项 |

两个细节：

- **该字段为空的票会单独成一组**，分组值和显示名都为空，界面应显示成「未填写」之类的占位文案。
- **关联基础资料已被删除时，分组名仍能正常显示**（统计时临时关闭了软删除过滤），不会出现一堆空名分组。

## 7.8 重新生成委托编号

用于编号规则调整后，把某一票的委托编号按最新规则重新取号。**用户不能指定编号内容**，只能触发重新生成。

**校验**：

1. 没有任何输入 → 「输入不能为空」
2. 空运出口不存在 → 「空运出口不存在」
3. 对应业务主表不存在 → 「对应的业务信息不存在」
4. 规则未配置 → 「未配置生成规则」；规则里没有自增项 → 「未配置自增编号规则」

生成后立即写入该票并落库，返回新编号供界面刷新显示。原编号不保留、不可恢复。

## 7.9 附件维护

三个操作：查询、新增、删除。附件也可以在保存单据时一并提交（见 2.8），两种方式效果相同。

**查询**：票不存在 → 「输入空运出口错误」。返回分组附件，排序规则见 2.8。

**新增**：票不存在 → 「输入空运出口错误」。**附件集合为空时不报错，直接成功**；集合中无效的附件项被静默跳过，不报错也不入库。每个有效附件建立一条关联记录，标记模块编码与归属票据。

**删除**：票不存在 → 「输入空运出口错误」；没有指定要删的附件 → 「附件Id集合不能为空」。只解除**本票**与这些附件的关联，**不删除附件文件本身，也不影响该附件在其它票上的关联**。指定了不存在的附件不报错，只是什么都没删掉。

## 7.10 外部运踪（云当 + 飞驼）

空运出口的列表与详情会一并带出外部运踪，**不需要前端再单独调外部接口**。目前对接了两家，它们互相独立、可以同时订阅。

### 7.10.1 两家的区别

|  | 云当空运运单 | 飞驼航空货运跟踪 |
| :-- | :-- | :-- |
| 订阅单号 | 主运单号 `MblNum` 原样上传 | 主运单号**剥离非数字字符**后必须恰好 11 位 |
| 列表返回 | 最后一个有实际时间的节点 | 运踪摘要（当前节点、整票状态、航司、货物、起降机场、预警条数） |
| 详情额外返回 | 无 | 完整轨迹 + 异常预警明细 |
| 数据更新 | 云当推送 | 飞驼推送全量快照，后端整体覆盖落库 |

### 7.10.2 飞驼运踪的展示口径

- **是否订阅**看 `IsFeituoSubscribed`，**是否订阅成功**看 `IsFeituoSubscribeSuccess`。未订阅时运踪对象为空。
- **订阅成功不代表马上有轨迹**：刚订阅时飞驼往往还没抓到数据，此时运踪对象存在但当前节点是空的，界面应提示「数据获取中」而不是报错。
- **当前节点是后端算出来的**：飞驼空运不返回"当前状态"，后端取所有事件里**时间最新的实际事件**（`eventClassifier=ACT`）；一条实际事件都没有才退回最新的预计事件。因此当分类是 `EST` 时，说明这是个**预计**节点，展示上建议与实际节点区分。
- **起降机场**取运输路径的第一段装货地与最后一段卸货地，中转票也能正确显示首末两端。
- **时间一律是字符串**（飞驼原样返回 `yyyy-MM-dd HH:mm:ss`），直接展示，不要解析成日期再格式化，否则会因时区偏移显示错时间。
- **异常预警**列表只给条数与最近一条，明细要进详情看。

### 7.10.3 订阅入口

订阅、重新订阅都在飞驼/云当各自的对接接口上，不在空运出口的接口里。飞驼那两个接口的入参出参见《飞驼对接-航空货运跟踪-前端对接.md》。

# 8. 界面交互说明

本章描述界面上应有的行为。字段属于哪一层（空运层 / 业务主表层）在第 2 章已标注，这里只讲交互。

## 8.1 表单分区建议

| 区域 | 主要字段 |
| :-- | :-- |
| 表头 | 委托编号、录入方式（只读）、所属组织、销售等关联人员、委托单位、业务来源、运输条款、业务锁定 |
| 航段 | 航班、起运地及备注、中转地及备注、目的地及备注、订舱代理、主提单号、合同号 |
| 日期 | 起飞日期、实际起飞日期、预抵日期、货好时间、报关日期、送仓日期、会计期间（只读）、应结日期（只读） |
| 往来单位 | 车队、报关行、仓库、保险公司、收货人及内容、发货人及内容、通知人及内容 |
| 货物 | 唛头、货物描述、件数、件数大写（只读）、包装、毛重、体积、泡比、商品清单、货物类型、危险品区、冻柜区 |
| 货物明细 | 可编辑表格 |
| 其它 | 发票号、内部备注、外部备注 |
| 费用 | 只读展示 + 状态汇总 |
| 附件 | 按类型分组展示 |

## 8.2 字段联动

| 触发 | 联动结果 |
| :-- | :-- |
| 选择**起运地 / 中转地 / 目的地** | 展示为「三字码/中文名」。**不带出国家、城市、时区，也没有航线概念** |
| 修改整票**毛重**或**体积** | 应重新算泡比（毛重 ÷ 体积）；体积为空或 0 时把泡比清空，**不要填 0** |
| 修改明细行的**长、宽、高** | 应重新算该行体积，进而重新算体积重和计费重 |
| 修改明细行的**件数** | 应重新算该行体积重和计费重（两者都乘件数） |
| 修改明细行的**重量** | 应重新算该行计费重 |
| 手改明细行的**体积** | 应重新算该行体积重和计费重（体积重以手改后的体积为准） |
| 手改明细行的**体积重** | 应重新算该行计费重 |
| 切换**销售** | 应重新加载该销售的直属组织列表，并清掉不在列表内的所属组织选择（见 6.5） |
| 切换**货物类型** | 普通货隐藏危险品区与冻柜区；冻柜显示冻柜区；危险品显示危险品区；**超限箱什么也不显示**（空运没有超长超宽超高的录入位） |

**明确没有联动的地方**（不要自作主张加）：

- **货物明细与业务主表的件数、毛重、体积之间没有任何联动**，是两处独立录入，对不上也不报错；
- 报关日期、送仓日期**没有任何自动带出规则**，不要按起飞日期推算；
- 航班与起运地、目的地之间没有联动，航班是纯文本，不校验格式；
- 收货人/发货人/通知人的**下拉选择**与对应的**抬头内容文本框**各存各的，选了单位不会自动填内容；
- 商品清单与货物明细是两处独立录入，货物明细里根本没有商品字段；
- 危险品的「危品净重」是文本字段，与货物明细的重量完全无关。

## 8.3 只读与后端接管的字段

以下字段界面应做成只读，用户填了也会被覆盖或忽略：会计期间、应结日期、件数大写、未解决问题数、录入人、创建时间、是否未完结、费用锁定及其四个审计字段、业务类型、录入方式。

## 8.4 货物明细表格

- 每行的列顺序建议：件数、重量（单件）、长、宽、高、体积（单件）、体积重（合计）、计费重（合计）。
- 行序由排序号升序决定。**上下移动行、往中间插行时要把整表排序号重排后一起提交**，只改被拖动的那一行会导致序号重复，重复时按主键升序兜底——主键是 Guid，兜出来是随机顺序，所以排序号必须保证唯一。
- **表头必须标注单位和口径**：重量和体积是「每件」，体积重和计费重是「整行合计」。这是最容易被用户误填的地方。
- 体积、体积重、计费重默认自动算出，**允许手改**；手改之后再改基准列，界面应再次覆盖计算结果（或明确提示用户），但**后端永远不会替你算**。
- 一行都不填也能保存，全表为空是合法的。
- 编辑保存时**整张表要完整提交**，包括没改动的行，否则漏掉的行会被删除。已有行必须带上自己的主键，新增行不带。
- 数值全部保留 **6 位小数**，不要按 2 位显示或提交。

## 8.5 子表的整体提交原则

货物明细、商品、关联人员三张子表都遵循同一条规则：**保存时提交的列表就是保存后的最终状态**。

- 界面上删掉一行 = 提交时不带这一行；
- 界面上加一行 = 提交时带一行没有主键的数据；
- 没动的行也要原样带上，只提交改动行会导致其余行被删。

三张表的主键类型不一样，判断「是不是新行」的写法要区分：**货物明细的主键是可空 Guid**，新行不带主键或传 `null`（**不要传全零 Guid**，那会被当成传了主键，去库里找不到对应行后这一行会被静默丢弃）；商品与关联人员的主键是可空自增整数，新行不带主键、传 `null` 或传 0。表格组件的行 key 建议用前端自己维护的临时行号，不要直接用主键，否则新行会因为没有主键而 key 冲突。

## 8.6 列表页交互

- 默认按创建时间倒序，支持列头排序（包括按委托单位名称这类关联字段排序）。
- 关键字框一次搜 6 个字段，见 5.3。
- 航班、订舱代理、起运地、中转地、目的地五个筛选项各自带一个「未填写」开关，**开关与选值互斥**，界面应在选了值时禁用开关、开了开关时禁用选值，避免用户撞上报错。
- 模糊搜索**搜不到空值行**，想找空值必须用「未填写」开关。
- 日期筛选是闭区间；报关日期、送仓日期可能带时分秒，界面在传「止」端时应自动补到当天最后一刻。
- 货物明细的八个区间筛选是「**存在满足条件的行**」语义，例如「计费重 ≥ 1000」筛出的是「至少有一行计费重不低于 1000」的票，不是整票合计不低于 1000 的票。界面上要把这个含义写清楚。
- 统计卡片/分组树用分组统计功能，**筛选条件必须与列表保持一致**，否则两边数字对不上。
- 列表每行数据量较大，建议默认每页 10～20 条。

## 8.7 附件交互

- 附件按类型分组展示，组内可拖拽排序（顺序号），可标记「客户是否可见」。
- 附件可以随单据保存一起提交，也可以在详情页单独增删，两条路径效果相同。
- 从本票移除附件只是解除关联，**文件本身仍在**，同一附件挂在别的票上不受影响。
- 每个附件可直接下载或预览，图片类可直接内联显示。

## 8.8 提示语展示

所有业务校验失败都只返回一句话，界面直接把这句话弹出即可。**不要自行改写文案**，测试是按原文断言的。

校验是**命中即中断**的，一次只报一个错。界面自身的必填校验应尽量在提交前拦下（委托单位、所属组织、销售恰好一个），减少来回。

## 8.9 详情翻票

从列表点进详情时，把当时列表的搜索条件和排序一起带上。详情页的上一票 / 下一票按这份条件的全量顺序走，不是当前页的前后两条。点上一票或下一票时搜索条件和排序保持不变，只换当前票。对应 Id 为空时禁用该方向按钮。

# 9. 难点与风险点

这一章集中列出容易做错、容易误判为缺陷、容易在联调阶段卡住的地方。

## 9.1 明细行里单件值和合计值混在一起

一行里，件数、重量、长、宽、高、体积是**单件**的，体积重和计费重是**整行合计**的。这是空运出口最容易出错的地方：

- 前端：表头必须标清楚，公式里的「重量 × 件数」不能漏掉件数；
- 测试：造数据时按「重量填单件、体积重看合计」验证，例如 10 件、每件 5 KGS、每件 0.03 CBM，则体积重 = 0.03 × 167 × 10 = 50.1，实重合计 = 5 × 10 = 50，计费重 = max(50.1, 50) = 50.1，进位后 **50.5**。

## 9.2 四个派生值不会自动重算

体积、体积重、计费重、泡比**只在前端录入时按公式带出**。用户改了长宽高、件数、重量、整票毛重体积却没有重新触发计算，保存下去的仍是旧值，后端不会纠正。

- 前端：所有基准字段的变更事件都要挂上重算逻辑，包括手改中间值之后往下游传导。
- 测试：这是**既定行为**，不是缺陷。用例要覆盖「改基准值不重算 → 保存旧值」的场景并判定为通过。

## 9.3 货物明细挂在扩展表上，不是业务主表

其它子表（商品、关联人员、改单、费用）挂业务主表 Id，**货物明细挂空运出口扩展表 Id**。两个 Id 值虽然相同，但外键指向不同的表。查数据库、写关联查询、做数据订正时都要用 `AirExportId`，并且要意识到：**没有扩展记录的票不可能有明细**。

## 9.4 空运出口没有集装箱

业务主表那一层有一张集装箱表，**空运出口完全不用它**（箱型是必填的，空运没有箱型）。因此空运出口没有箱型箱量合计、没有整票 TEU、没有商品 TEU。界面上不要留这几个位置，接口里也不会返回。

顺带的影响：客户模块的「年 TEU」统计对空运票恒为 0（见 6.7）。

## 9.5 三个日期字段名和界面文案对不上

界面写「起飞日期」，字段是 `ETD`；界面写「实际起飞日期」，字段是 `ATD`；预抵日期就是 `ETA`。会计期间和应结日期都以 `ETD` 为基准。查数据库、看日志、写排序字段时都要用字段名。

## 9.6 航班不是航次

海运有个「航次」字段叫 `InnerVoyno`，**空运出口表里根本没有这个字段**。空运的「航班」是新字段 `FlightNo`，两者没有任何关系，不要试图复用、映射或对齐。

## 9.7 销售的强约束会牵连组织

「销售恰好 1 个」是硬约束，0 个和 2 个都报同一句「销售有且只能有一个」。更麻烦的是所属组织必须是**该销售的直属组织**，父组织不算。换销售往往要连带换组织，界面要主动联动，否则用户在保存时才发现。

## 9.8 复制出来的票可能立刻编辑不了

复制不做组织归属校验，新票的所属人变成当前用户，但所属组织沿用源票。如果源票组织不是新销售的直属组织，**这张票一打开编辑保存就会报「所选组织不在数据所属人(本人)所属组织范围内。」**。复制别人的票之后应提示用户检查所属组织。

## 9.9 子表全量比对，漏传即删除

编辑时三张子表按「提交什么就是最终状态」处理。前端如果做了增量提交优化，会静默删掉用户没动过的行，而且**不会有任何报错**，是最危险的一类问题。

## 9.10 有费用的票删不掉

只要该票还有一条未删除的费用（任何状态、含改单费用），删除就被拒绝，没有强制删除的旁路。界面应在删除按钮上做前置提示，而不是让用户点了才报错。

## 9.11 编号规则未配置会导致三处功能不可用

委托编号规则 `AirExport.CommissionNum` 未配置时：新增只要不手填编号就失败，复制和「重新生成委托编号」**无论如何都失败**。这是上线硬前置条件，测试环境也必须先配。**它和海运出口、海运进口的键是分开的，配了海运不等于配了空运。**

## 9.12 模糊搜索搜不到空值

包含匹配天然跳过空值行。「查一下航班没填的票」只能用「未填写」开关，不能靠搜索空字符串。而且开关和选值**同时使用会直接报错**，不是取并集。

## 9.13 日期区间的时分秒陷阱

业务主表的四个日期存的时候会被截成 00:00:00，但空运层的报关日期、送仓日期**原样保存**。如果用户录入时带上了时分秒，按「止 = 当天」筛选就会漏掉当天的数据。界面应统一只录日期，并在筛选时把「止」端补到当天最后一刻。

## 9.14 明细的区间筛选是「存在」语义

货物明细的八个区间筛选，命中条件是「该票至少有一行满足」，不是整票汇总后比较。用户以为在按整票计费重筛，实际是按单行筛，结果会超出预期。界面文案要说明白。

## 9.15 权限造成的字段缺失

字段级权限不是把值置空，而是让字段**整个不出现**。前端读取时必须容忍字段缺失，测试断言「无权限时看不到某字段」时也要按「字段不存在」判断，而不是「值为空」。

另注意：**详情、编辑、删除、重新生成委托编号自 2026-08-19 起都做行级数据权限**（口径见 4.2）。此前「拿到 Id 就能查改」的行为已经取消，按老行为写的用例要同步改。

## 9.16 费用只读概览，部分字段是空的

空运出口展示的费用是概览，一部分费用属性在这里不填充（见 2.7）。每条费用上那个「组合费用状态」属性也**不要用**，票级的应收/应付组合状态另有两个专门的值。需要完整费用数据时用费用模块自己的功能。

## 9.17 列表返回的数据量

列表每一行都带完整费用与三张子表，每页开太大会明显变慢。分页统计的总数还叠加了数据权限，不同账号看到的总数不同，这是预期。

## 9.18 可能存在没有扩展记录的空运票

业务主表自己的新增功能不创建空运出口扩展记录，因此库里可能出现「业务类型是空运出口但没有扩展记录」的票。这种票在业务主表详情里空运信息为空，**不报错**（见第 10 章），而且它一定没有货物明细。测试遇到属预期。

## 9.19 存量重复主提单号下次保存会被拦住

上线前库里如果已经有多票共用同一个主提单号，读和列表不受影响。但其中任意一票下次保存都会报「主提单号【{号码}】已存在」，必须先把重复的号改掉。空主提单号（没填）不在这条限制里。

# 10. 业务主表功能的分流

业务主表自身也有一套对外功能。空运出口上线后，其中两个按业务类型分流：

| 功能 | 分流后的行为 |
| :-- | :-- |
| **详情** | 业务类型是空运出口时，在业务主表信息中填充空运出口扩展信息（内容与空运出口详情一致，含货物明细）；是海运出口/海运进口时分别填充各自的扩展信息 |
| **删除** | 业务类型是空运出口时，走空运出口的删除逻辑，包含 7.6 列出的全部校验与级联清理 |

业务主表的**新增和编辑保持原样**，不创建也不修改空运出口扩展记录。

因此数据库中可能存在「业务类型是空运出口、但没有扩展记录」的票。这种数据在详情里空运信息为空，**不报错**。

# 11. 基础资料删除的引用校验

以下基础资料在执行删除时，必须先检查是否被空运出口引用；被引用则禁止删除。提示语格式统一为「**该{基础资料名称}已被【空运出口】模块引用,禁止删除**」，例如「该空运港口已被【空运出口】模块引用,禁止删除」。一份资料同时被多个模块引用时，模块名在方括号内用顿号连接，例如「该客户信息已被【海运出口、空运出口】模块引用,禁止删除」。

> 注意提示语里的逗号是**半角**的，测试断言时别写成全角。

**需要新增校验的有两处**：

| 基础资料 | 需要检查的引用位置 | 提示语 |
| :-- | :-- | :-- |
| **空运港口** | 空运出口的起运地、中转地、目的地 | 该空运港口已被【空运出口】模块引用,禁止删除 |
| **往来单位（客户）** | 空运出口的订舱代理，**以及海运出口的订舱代理** | 该合作客户已被【海运出口、空运出口】模块引用,禁止删除（按实际命中的模块拼接） |

> 客户删除原先**完全不校验业务单据引用**，本次一并把海运出口和空运出口的订舱代理都补上。这意味着**已有的、被海运出口用作订舱代理的客户从此也删不掉了**，是既有行为的变更，回归测试要覆盖。

**已经自动覆盖、不需要改动的**：业务来源、运输条款、包装、商品（品名）、用户这几项，现有的删除校验是**按业务主表和公共子表整体查的，不区分业务类型**，命中时提示的模块名是「业务委托单」。空运出口的票天然落在这个范围内，删除时照样会被拦住，不需要为空运出口单独加一条。

| 基础资料     | 现有校验查的位置                 | 命中时的模块名 |
| :----------- | :------------------------------- | :------------- |
| 业务来源     | 业务主表的业务来源               | 业务委托单     |
| 运输条款     | 业务主表的运输条款               | 业务委托单     |
| 包装         | 业务主表的包装、集装箱子表的包装 | 业务委托单     |
| 商品（品名） | 商品子表、集装箱子表的商品       | 业务委托单     |
| 用户         | 关联人员子表的用户               | 业务委托单     |

**国家表**：空运出口**不直接引用**国家（国家挂在空运港口基础资料上）。国家表已有的删除校验覆盖了港口信息、空运港口、合作客户、海运进口四处，其中「空运港口」这一条已经间接保护了空运出口的数据——要删某个国家，得先删掉它下面的空运港口，而只要还有空运票用着那个空运港口，空运港口就删不掉。**因此国家表不需要为空运出口新增校验项。**

**货物明细表不引用任何基础资料**（没有箱型、包装、商品外键），不涉及删除校验。

# 12. 上线前置条件与卡点

> [!IMPORTANT] **卡点 1：编号规则未配置，新建直接失败** 委托编号规则 `AirExport.CommissionNum` 必须由管理员在「编号规则」中预先配置。未配置时，用户只要不手填委托编号，新建就直接报「未配置生成规则」；复制和「重新生成委托编号」**无论如何都会失败**。这个键与海运出口、海运进口互相独立。**这是上线的硬前置条件。**

> [!IMPORTANT] **卡点 2：销售有且只有一个** 关联人员中销售的记录数不等于 1 时，新增、编辑、复制全部被拒绝，提示「销售有且只能有一个」。0 个和 2 个都不行。这是关联人员里唯一的必填约束。

> [!IMPORTANT] **卡点 3：所属组织必须是销售的直属组织** 父组织不算直属。销售与组织的绑定关系必须先在组织架构里维护好，否则用户无法保存。

> [!IMPORTANT] **卡点 4：空运港口基础资料必须先建好** 起运地、中转地、目的地全部取自空运港口基础资料。上线前要把常用机场的三字码和中文名维护完整，否则界面上选不到地点，分组统计也没有意义。

> [!IMPORTANT] **卡点 5：有费用的票删不掉** 删除前必须先把该票的费用删光，否则报「当前票包含未删除费用，请先删除费用」。这是防止费用变成孤儿数据的硬约束。

> [!IMPORTANT] **卡点 6：派生值不会自动跟随基准值变化** 体积、体积重、计费重、泡比四个值只在前端录入时按公式带出。用户后续改了基准值却没有重新触发计算时，后端不会替他重算。**这是既定行为，不是缺陷。**

> [!IMPORTANT] **卡点 7：子表必须整体提交** 编辑对货物明细、商品、关联人员三张子表做全量比对：库里存在而本次没提交的行会被删除。

> [!IMPORTANT] **卡点 8：客户账期规则要能选到空运出口** 应结日期按委托单位账期规则推算，规则里的「业务类型」条件必须能配置空运出口，否则配了业务类型的规则永远匹配不上空运票，应结日期会退化成起飞日期当天。

> [!IMPORTANT] **卡点 9：主提单号不能重复** 新建和保存时，填了主提单号就要在当前租户业务表里查重（海运出口、海运进口、空运出口共用，互相也不能撞号）。冲突报「主提单号【{号码}】已存在」。空值不校验；已软删除不参与；编辑排除自身。存量里已经撞号的票，下次保存会被拦住，必须先改掉其中一个。
