# 背景意图

业务联系单列表页需要直接看到每票的销售、操作是谁以及备注内容，并支持按销售、操作、备注筛选。原来这些信息只在详情的 `preOrderUsers` 子表里，列表拿不到；筛选条件也只有创建人，无法按干系人查。

命名与实现方式对齐仓库既有约定（`StatementQueryDto.SaleIds`/`OperatorIds`、`TransportOrderDto.SaleNames`/`OperatorNames`）。

# 核心逻辑变更

## 1. 列表新增返回：销售昵称集合、操作昵称集合

`PreOrderDto` 新增两个字段：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `SaleNames` | `List<string>` | `PreOrderUser` 中用户属性为销售的用户 `NickName` 集合 |
| `OperatorNames` | `List<string>` | `PreOrderUser` 中用户属性为操作的用户 `NickName` 集合 |

`FillNamesAsync`（列表与 `PreOrderTaskListAsync` 共用）的填充方式：

1. 用本页 `PreOrderId` 集合独立查 `PreOrderUser`（只取销售/操作两种属性，`AsNoTracking`），避免主查询 JOIN 子表；
2. 把干系人 `UserId` 与创建人 `CreatorUserId` 合并成一个 id 集合，一次查出 `NickName`；
3. 原先的 `users` 从 `List` 改为 `Dictionary<long, string>`，创建人昵称与干系人昵称共用同一字典，避免逐行 `FirstOrDefault` 线性查找。

详情 `FillDetailSimpleDtosAsync` 也补了这两个字段，直接用已加载的 `result.PreOrderUsers` 计算，保证列表与详情返回结构一致。

新增私有静态方法 `BuildUserNickNames(userIds, userNickNames)`：按 id 集合取昵称，取不到的丢弃，列表与详情共用。

> **备注 `remark` 原本就在返回里**（`PreOrderDto.Remark` 由 `ObjectMapper` 自动映射），本次未改动，只是补了筛选。

## 2. 列表新增筛选：销售、操作、备注

`PreOrderQueryDto` 新增三个字段，`PreOrderGroupQueryDto` 因继承关系自动同步（分组统计同样可用）：

| 字段          | 类型         | 说明                           |
| :------------ | :----------- | :----------------------------- |
| `SaleIds`     | `List<long>` | 销售id集合，多选，命中任一即可 |
| `OperatorIds` | `List<long>` | 操作id集合，多选，命中任一即可 |
| `Remark`      | `string`     | 备注，模糊匹配                 |

`BuildPreOrderFilterQuery` 追加三个 `WhereIf`：

- 备注：`m.Remark.Contains(input.Remark)`；
- 销售：`m.PreOrderUsers.Any(u => u.UserAttribute == UserAttribute.Sale && input.SaleIds.Contains(u.UserId))`；
- 操作：同上，属性换成 `UserAttribute.Operation`。

# 避坑指南

- **`saleIds`/`operatorIds` 传的是用户id，不是 `PreOrderUser` 子表行id。** 与结算模块 `SaleIds`/`OperatorIds` 语义一致，匹配的是 `PreOrderUser.UserId`。
- **多选是「命中任一」，不是「同时满足」。** 传多个销售id返回的是其中任意一个为销售的单据；销售与操作两个条件之间才是 AND 关系。
- **干系人筛选与数据权限是两回事。** `saleIds`/`operatorIds` 只是筛选条件，能不能看到该单据仍由 `PreOrderListDataPermissionFilterAsync` 决定；筛了自己不在权限范围内的销售，结果依然为空。
- **没有销售/操作时返回空数组而非 null**，前端可直接遍历。业务上销售必填且唯一，所以 `saleNames` 正常只有一个元素；操作 0-1 个，审核通过前可能为空。
- **`saleNames`/`operatorNames` 是昵称快照，不带用户id。** 需要 id 的场景走详情的 `preOrderUsers`（含 `user` 对象）。
