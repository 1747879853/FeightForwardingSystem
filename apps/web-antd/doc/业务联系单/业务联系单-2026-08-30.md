# 背景意图

两件事：

1. 业务联系单费用没填汇率时，生成到业务费用的 `OrderFee.ExchangeRate` 原来兜底成 **1**。这是个假汇率，会让费用带着看似正常的数值直接进审核，事后很难发现汇率其实没维护过。应当记 **0**，让它显式地"缺值"。
2. 汇率记 0 之后，必须同时把自动提交的门槛与手工提交对齐，否则会生成一批汇率为 0 的在审费用——而 `SubmitOrderFeeAsync` 本身是明令禁止汇率为 0 提交的，等于绕过了这条校验。

顺带补上 8-27 那次撤销提交报错文案的记录。

# 核心逻辑变更

## 1. 汇率缺失记 0（`GenerateBizFromPreOrderAsync`）

```csharp
// 业务联系单没填汇率就记0(不是1) 由下面的提交校验拦住 不会带着假汇率进审核
var exchangeRate = fee.ExchangeRate ?? 0M;
```

## 2. 自动提交沿用提交侧校验

`OrderFeeAdminAppService.SubmitOrderFeeAsync` 的两条硬拦截是「结算对象必填」与「汇率为0的费用不可提交」。自动提交这边原先只判了结算对象，现在补齐汇率：

```csharp
var canSubmit = fee.SettlementId.HasValue && exchangeRate != 0M;
...
FeeStatus = canSubmit ? FeeStatus.Submitted : FeeStatus.Entering,
```

不满足条件的费用**照常生成**，只是停在 `Entering` 录入状态，不进 `submittedFees`，因而不会为它建审核任务。整个过程不报错。

## 3. 撤销提交报错带上实际提交人（8-27 补记）

`OrderFeeTaskWithdrawAsync` 原来只报「只能撤回自己提交的费用」，用户看着费用创建人是自己却撤不了，也不知道该找谁。现在文案带上实际提交人昵称：

```csharp
throw new UserFriendlyException($"只能撤回自己提交的费用,当前提交人为{string.Join("、", submitterNames)}");
```

昵称走基类带缓存的 `GetUserInfoMapAsync()` + `GetNickName` 扩展；多个提交人以「、」分隔；`CreatorUserId` 为空或查不到用户时显示「未知」。

# 避坑指南

- **汇率 0 不是"没生成"，费用还在，只是没提交。** 审核通过后费用列表里会出现录入状态的费用，需要人工补汇率再提交，不要以为费用漏建了。
- **手工提交前必须补汇率。** 这类费用走 `SubmitOrderFeeAsync` 会被 `汇率为0的费用不可提交` 拦下，这是既有校验，不是本次新增。
- **别再把缺失汇率兜底成 1。** 汇率参与利润与对账计算（`Amount * ExchangeRate`），假汇率算出来的数看着合理却是错的，比缺值更难排查。
- **自动提交与手工提交的校验要一起改。** 自动提交这条路径是直接建 `TaskBase`/`TaskItem`，不经过 `SubmitOrderFeeAsync`，它的任何校验都不会自动生效，只能手动对齐。目前已对齐「结算对象必填」「汇率不为0」两条；`SubmitOrderFeeAsync` 里还有一条 `金额为0的费用不可提交` **尚未纳入**自动提交的过滤，若业务上也不允许，需要另行补。
- **撤销提交的报错文案已变，前端不要用全等比较。** 文案尾部会拼接提交人昵称，匹配请改前缀匹配，详见 `文档/业务费用/业务费用-审核工作流-前端对接文档-2026-08-07.md`。
