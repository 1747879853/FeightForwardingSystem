# 业务联系单接口文档（第一部分：增删改查）

**控制器**：`PreOrderAdmin`

**所有接口均需要登录认证**

> 本文档覆盖业务联系单（`PreOrder`）的增删改查接口（第一部分）以及提交审核、撤回、审核（通过/驳回）、审核后驳回等审核流程接口（第二部分，见文末）。审核逻辑与付费申请（`PaymentApplication`）一致。

---

# 1. 数据结构

- 主表：`PreOrder`（`App_PreOrders`），继承 `DataPermissionFullAuditedEntity<Guid>`，含租户 `IMustHaveTenant`。
- 子表（均在 `PreOrder.cs` 中）：
  - `PreOrderCodeGoods`（`App_PreOrderCodeGoodss`）商品信息(品名)
  - `PreOrderCtn`（`App_PreOrderCtns`）箱型箱量
  - `PreOrderUser`（`App_PreOrderUsers`）业务关联用户
  - `PreOrderService`（`App_PreOrderServices`）服务项目
  - `PreOrderFee`（`App_PreOrderFees`）业务联系单费用
- 已在 `CsprojBuilderDbContext` 注册 `DbSet`（**迁移文件由人工生成**）。

> 说明：新增/编辑/详情接口均携带全部子表；列表接口不携带子表。详情与列表均返回创建人昵称 `creatorUserName`；关联用户返回昵称 `userNickName`。

## 一、获取列表（不带子表）

### `GET /api/services/app/PreOrderAdmin/GetPagedListAsync`

**权限**：`Admin.PreOrder.Get`

**数据权限**：独立方法 `PreOrderListDataPermissionFilterAsync`（对齐海运出口 `SeaExportListDataPermissionFilterAsync`）。非「全部」权限时，满足任一即可见：所属人 `userId`、创建人 `creatorUserId`、所属组织 `orgId`，或干系人 `PreOrderUser`（角色为销售/商务/操作/客服/单证/海外客服/航线）。

**入参** `PreOrderQueryDto`（Query）：

| 字段 | 类型 | 必填 | 说明 |

## 一.1、分组统计

### `GET /api/services/app/PreOrderAdmin/GetGroupedListAsync`

**权限**：`Admin.PreOrder.Get`

**说明**：查询条件与列表接口 `GetPagedListAsync` **完全一致**（复用同一套筛选与 `PreOrderListDataPermissionFilterAsync` 干系人数据权限），并额外指定一个 `groupField` 分组字段。先用查询条件筛出全部数据，再按指定字段分组，返回每个分组的 id、名称及数据总条数。结果按 `count` 倒序排列。

**入参** `PreOrderGroupQueryDto`（Query）：继承 `PreOrderQueryDto` 全部字段，额外：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `groupField` | `PreOrderGroupField` | 是 | 分组字段（与海运出口同名字段取值一致）：3=委托单位，4=船公司，5=起运港，6=目的港，11=业务类型（业务联系单专属） |

**出参** `List<PreOrderGroupDto>`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `string` | 分组值id（业务类型为枚举值，委托单位为Guid，港口/船公司为long；无值时为 null） |
| `name` | `string` | 分组名称（业务类型取枚举描述，委托单位取客户简称，船公司取中文简称，港口取 PortName；无值时为 null） |
| `count` | `int` | 该分组下的数据总条数 |
| `logo` | `AttachmentItemDto` | 船公司 logo；**仅 groupField=4（船公司）时有值**，其余为 null |

| groupField | 含义 | 分组依据 | id 来源 | name 来源 |
| --- | --- | --- | --- | --- |
| 3 | 委托单位 | `ClientId` | Guid 字符串；空Guid为 null | 客户简称 `Name` |
| 4 | 船公司 | `CarrierId` | long 字符串；空为 null | 船公司中文简称 `CnShortName` |
| 5 | 起运港 | `POLId` | long 字符串；空为 null | 港口 `PortName` |
| 6 | 目的港 | `PODId` | long 字符串；空为 null | 港口 `PortName` |
| 11 | 业务类型 | `BizType` | 枚举 int | 枚举 Description（海运出口/海运进口/空运出口/件杂货） |

**权限**：`Admin.PreOrder.Get`

**入参** `GuidIdDto`（Query）：

| 字段 | 类型   | 必填 | 说明         |
| ---- | ------ | ---- | ------------ |
| `id` | `Guid` | 是   | 业务联系单id |

> **服务项对比（仅海运出口且已审核通过生成业务表时）**：详情返回的 `preOrderServices` 每项带 `compareStatus`（0=相同、1=海运出口新增、2=海运出口删除）。计算方式：取海运出口(`SeaExport`)服务项与主服务项(`ServiceType` 枚举 `extra1=true` 的 `value`)的交集作为“主服务项目”；业务联系单已有项在主服务项目中则为“相同”，否则为“海运出口删除(2)”；主服务项目中业务联系单没有的，追加一条 `id=0` 的记录标记为“海运出口新增(1)”。未生成业务表(`transportOrderId` 为空)或非海运出口时全部为“相同(0)”。

## 三、新增（带全部子表）

### `POST /api/services/app/PreOrderAdmin/AddAsync`

**权限**：`Admin.PreOrder.Add`

新建后状态固定为 **录入状态**；`preOrderNum` 由后端按编号规则生成（未配置规则时为空，可后续补填）；`tenantId`、`userId`（所属人）由后端赋值。

> **入参校验（新增/修改共用 `ValidatePreOrderInputAsync`）**：全部字符串按实体列长校验，超长报「{字段}长度不能超过{n}个字符」；全部外键有值则查库，不存在报「{名称}不存在」或「{名称}ID:{id}不存在」。长度口径见各字段说明。
>
> **海运出口服务项校验（新增/修改均生效）**：当 `bizType=0(海运出口)` 时，`polId`（起运港）不能为空，否则报“海运出口业务联系单起运港不能为空”；`preOrderServices` 的服务项不能超出“最大集合”（可少不可多），超出报“服务项目超出允许范围(只能少于或等于海运出口主服务项)”。 **最大集合** = （`SeServiceConfig` 按 `polId` 命中的服务项，未命中取默认港口配置 `polId=null` − `ClientExceptService` 按 `clientId+polId` 的排除项）∩（`ServiceType` 枚举中 `enable=true` 且 `extra1=true`(主服务流程) 的 `value`）。
>
> **件杂货（新增/修改均生效）**：当 `bizType=3(件杂货)` 时，后端在**一切校验之前**先改写入参：`blType` 置 0、`carrierId` 置 null、`cargoId` 置 0(普通货)、`preOrderCtns` 与 `preOrderServices` 清空。这些字段传了不报错、也不会存下来。之后 `polId`（起运港）不能为空，否则报“件杂货业务联系单起运港不能为空”。
>
> **箱型（新增/修改均生效）**：`preOrderCtns[].ctnCodeId` 海运出口、海运进口必填，空报“箱型ID不能为空”；空运出口可以不填；件杂货整组被清空。

# 7. 避坑指南 (Pitfalls)

- **销售必填且唯一**：`preOrderUsers` 中 `userAttribute=16(销售)` 必须恰好一个，否则报“销售必填且只能指派一个用户”。
- **属性不可重复/不可为空**：同一 `userAttribute` 不可出现两次；`userAttribute` 不可为 `None(0)`。
- **状态限制**：编辑、删除仅允许在“录入状态/驳回”下进行；待审核、通过状态受限（提交审核/审核逻辑见后续部分）。
- **子表全量覆盖**：`EditAsync` 会先删除后重建全部子表，前端须提交完整子表数据。
- **费用为主表子表**：`PreOrderFee` 已作为主表导航属性 `preOrderFees`，随主表级联新增，详情中一并返回。
- **附件全量覆盖**：附件复用通用附件模块（`ModuleTypeId=160050`）；新增/编辑通过 `attachmentGroup` 提交，编辑会先删旧关联再重建；`attachmentId<=0` 会被忽略。
- **审核通过附件带入业务**：审核整体通过生成业务时，业务联系单附件会复用同一附件文件、以对应业务维度新建关联（itemId=业务表id），`ModuleTypeId` 按业务类型取：海运出口 `160040`、海运进口 `160070`、空运出口 `160080`、件杂货 `160150`。
- **海运出口、件杂货起运港必填**：`bizType=0(海运出口)` 或 `bizType=3(件杂货)` 时新增/修改起运港 `polId` 不能为空。
- **件杂货的无用字段会被改掉**：`bizType=3` 时 `blType`/`carrierId`/`cargoId`/`preOrderCtns`/`preOrderServices` 在校验前被改成默认值或清空，保存后再查详情看到的是改过的值，前端不要拿它们和提交值比对。
- **空运出口箱型可空**：空运出口联系单的箱型行可以只有箱量不填箱型，详情里这样的行 `ctnCodeId`、`ctnCode` 都是 null，渲染时要判空。
- **服务项可少不可多**：海运出口服务项不能超出“最大集合”（起运港配置去除委托单位排除项后，与主服务项枚举取交集）。
- **服务项对比只读**：详情 `preOrderServices.compareStatus` 由后端对比海运出口服务项实时计算，前端只读展示，无需回传。
- **分页参数**：使用 `pageIndex` / `pageSize`，非 `skipCount`。

# 8. 审核流程接口（第二部分）

> 审核流程与付费申请（`PaymentApplication`）一致：提交后生成审核任务(`TaskItem`)与工作流实例(`WorkFlowInstance`)。提交审核、撤回、审核、审核后驳回**均使用编辑权限** `Admin.PreOrder.Edit`。

## 状态流转

| 当前状态 | 动作 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| 录入状态(0)/驳回(3) | 提交审核 `SubmitAsync` | 待审核(1) | 生成任务与工作流；无工作流或全自动通过时直接到“通过(2)”并生成业务表 |
| 待审核(1) | 撤回 `UnSubmitAsync` | 录入状态(0) | 删除审核任务与工作流实例 |

| 待审核(1) | 审核驳回 `AuditAsync(success=false)` | 驳回(3) |  |
| 通过(2) | 审核后驳回 `RejectAsync` | 驳回(3) | 须先手动删除关联的 `TransportOrder` 与对应业务类型表（海运出口/海运进口/空运出口/件杂货）数据后方可驳回 |

## 三、审核（通过/驳回）

### `POST /api/services/app/PreOrderAdmin/AuditAsync`

**权限**：`Admin.PreOrder.Edit`

**入参** `PreOrderAuditDto`（Body JSON）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `Guid` | 是 | 业务联系单id |
| `success` | `bool` | 是 | true=通过，false=驳回 |
| `remark` | `string` | 否 | 审核意见/备注 |
| `operationUserId` | `long?` | 否 | 指定/修改操作干系人的用户id；传了则将该用户设为该业务联系单的“操作”（有且只有一个操作） |

**出参**：无。说明：

- 仅当前审核人可审核；多级工作流下未到最后一步时仅记录本步结果。
- 审核每一步都可通过 `operationUserId` 重新指派“操作”干系人。
- **整个业务联系单通过时**校验“操作”干系人是否存在，不存在报错：`需要指定操作后方能审核通过`。
- 通过后生成业务表 `TransportOrder`（`InputType=1` 业务联系单导入）及对应 BizType 表（海运出口 `SeaExport` / 海运进口 `SeaImport` / 空运出口 `AirExport` / 件杂货 `BreakBulk`）；**生成的 `TransportOrder.Id` 与业务联系单 `PreOrder.Id` 完全一致**（扩展表 Id 亦与之相同）；委托编号按业务类型各用一套规则（件杂货为 `BreakBulk.CommissionNum`）；`OrderCtns` **只有海运出口、海运进口生成**，按 `PreOrderCtn.Count` 逐箱生成（几个箱子几条），且只取填了箱型的行；费用表生成失败时静默跳过，不回滚不报错。联系单备注：海运出口写入 `TransportOrder.internalRemark`（外部备注留空），海运进口、空运出口、件杂货仍写入 `TransportOrder.remark`；备注为空则对应字段为空。通过后再改联系单备注不回写已生成的业务。
- **件杂货**：生成件杂货扩展表，带入船名、航次、订舱代理，以及收货地、起运港、中转港1、中转港2、目的港、交货地及备注；地面代理、签单方式、第二通知人等件杂货专属字段联系单上没有，留空由操作补录。随后建主单提单，签单方式为空，所以按非正本建成「已签入」。件杂货没有服务项目与服务项任务。
- 审核后驳回(`RejectAsync`)：**不再自动删除**业务表；若 `transportOrderId` 已生成且对应 `TransportOrder` 或其业务类型表仍存在，则禁止驳回，按 `bizType` 提示：`请先删除海运出口数据`(海运出口) / `请先删除海运进口数据`(海运进口) / `请先删除空运出口数据`(空运出口) / `请先删除件杂货数据`(件杂货)；用户须先在业务侧删除对应数据后，方可执行审核后驳回。
- **附件带入业务**：生成业务时，将业务联系单的附件复用同一附件文件、以对应业务维度新建关联（itemId=业务表id），`ModuleTypeId` 按业务类型取：海运出口 `160040`、海运进口 `160070`、空运出口 `160080`、件杂货 `160150`，带入对应业务的详情/附件接口。
- **费用数量与金额**：生成 `OrderFee` 时按费用“单位字符串”重算数量（`票=1`、`毛重=Kgs`、`尺码=Cbm`、`TEU=Σ箱型TEU`、其余按箱型名 `CtnName` 匹配箱子数量，公共方法 `ResolveQuantityByUnit`）；金额随之重算 `amount=单价×数量`、`noTaxAmount=不含税单价×数量`（财务四舍五入）。
- **箱型单位未匹配跳过**：费用单位是箱型名（非 `票`/`毛重`/`尺码`/`TEU` 一律按箱型名处理）但本单箱子里没有该箱型时，**该条费用整条不生成**（不再生成数量为 0 的空费用），也不进入费用审核提交列表；静默跳过不报错。单位为空则仍按数量 0 生成。
- **费用自动提交审核**：若本次有费用生成，先 `SaveChangesAsync` 将费用落库，落库成功后再提交费用审核（费用状态置 `Submitted`，创建 `TaskType=SubmitOrderFee` 的任务，每条费用一条 `TaskItem`，`FrightModule=OrderFee`、`TaskStatus=Auditing`），参考 `OrderFeeAdminAppService.SubmitOrderFeeAsync`；该过程失败同样静默不回滚不报错。
- **汇率口径与提交条件**：业务联系单费用没填汇率时，生成的 `OrderFee.exchangeRate` 记为 **0**（不是 1，避免带着假汇率进审核）。自动提交沿用 `SubmitOrderFeeAsync` 的提交校验：**结算对象必填、汇率不能为 0**，两个条件都满足才置为 `Submitted` 并生成审核任务；任一不满足的费用**照常生成**但只是 `Entering` 录入状态，不提交、不报错。这类费用需先在费用页补齐汇率/结算对象再手工提交，否则手工提交会被拦下并报 `汇率为0的费用不可提交`。
- **费用创建人与提交人都记当票销售**：生成的 `OrderFee.CreatorUserId` 以及费用审核任务 `TaskBase`/`TaskItem.CreatorUserId` 均显式记为业务联系单的销售干系人（不是审核人、也不是费用录入人）。原因是撤销提交接口 `OrderFeeTaskWithdrawAsync` 校验 `TaskItem.CreatorUserId` 必须等于当前登录人，两者口径不一致会导致费用无法撤销提交。
- **海运出口服务项生成规则**：先按 **起运港 + 委托单位** 取出本票可用的服务项集合 = `SeServiceConfig`（按 `polId` 命中，未命中取默认港口配置 `polId=null`）− `ClientExceptService`（按 `clientId + polId` 的排除项）；该集合再与 `ServiceType` 枚举中 `enable=true` 的项按 `extra1` 分为 `valuesTrue`(主服务流程)/`valuesFalse`(非主服务流程) 两组。**第一部分** = `valuesTrue` ∩ 业务联系单服务项；**第二部分** = `valuesFalse` 全量；两部分合并即海运出口生成的全部服务项，`sortId` 直接取自对应 `SeServiceConfigItem.SortId`（与海运出口新建一致；服务项在配置中找不到顺序时报 `服务项{value}顺序未配置`）。
- **同步生成首个服务项任务**：服务项落库后，按海运出口新建同样的逻辑调用 `GenerateFirstServiceTaskAsync`，取本票服务项涉及的最小 `sortId`，为该优先级下的全部启用服务项生成待处理任务（`SeServiceTask`，状态 `Pending`）。处理人由业务关联用户(`OrderUser`)按服务项配置的用户属性(`UserAttribute`)匹配得出；**匹配不到处理人会直接报错**：`[{起运港}]港的[{服务项}]服务项任务需要用户属性为[{属性名}]的处理人，当前票未配置此用户属性`。
- **审核时改“操作”会同步到海运出口**：`operationUserId` 更新干系人后会先 `SaveChangesAsync` 落库，再生成业务表，保证 `TransportOrder.OrderUsers` 与服务项任务处理人取到的是**本次审核最新指定的操作**，而不是旧值。
- **订舱代理带入业务**：业务联系单的 `bookingAgentId` 会原样写入 `SeaExport` / `AirExport` / `BreakBulk` 的 `BookingAgentId`（海运进口没有这个字段，不带）。
- **船名/航次带入业务**：业务联系单的 `vessel`/`innerVoyno` 会原样写入 `SeaExport`、`SeaImport` 或 `BreakBulk` 的 `Vessel`/`InnerVoyno`（空运出口没有这两个字段，不带）。
- **车队带入业务主表**：业务联系单的 `teamId` 会原样写入 `TransportOrder.TeamId`，各业务类型都带。

## 五、工作流条件说明

- 业务联系单工作流条件字段（`TaskTypeCondition`）**只接受** `8001`(`PreOrderUserId` 申请人，仅等于/不等于) 与 `8002`(`PreOrderOrgID` 申请人组织，仅属于/不属于)。
