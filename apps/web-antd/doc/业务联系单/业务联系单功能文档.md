# 1. 业务背景说明 (Background)

**白话解释：** 业务联系单（`PreOrder`）是销售/操作在正式建立运输业务（`TransportOrder` 及对应业务类型表，如海运出口 `SeaExport`）之前，用于登记一票业务的意向信息与费用预估的“前置单据”。它汇总了委托单位、装运方式、港口、船公司、船名/航次（海运进出口与件杂货）、车队、收发通、货物、箱型箱量、服务项目、关联人员与预估费用等信息。

**业务类型**（`bizType`）可选 0 海运出口、1 海运进口、2 空运出口、3 件杂货。件杂货联系单没有装运方式、船公司、箱型箱量、服务项目，货物类型固定按普通货，这些输入在新增/编辑时直接丢弃（见卡点 10）。件杂货本身见 `文档/件杂货/件杂货模块总逻辑文档.md`。

整体流程（分多期实现，本期仅实现增删改查）：

1. 新建业务联系单，携带全部子表，初始为 **录入状态**，可修改、可提交审核。
2. 提交审核后进入 **待审核**，不可修改，走工作流审核（与付费申请 `PaymentApplicationAdminAppService` 审核逻辑一致）。
3. 审核中可撤销回 **录入状态**；每一步审核均可重新指派“操作”（新增/修改 `PreOrderUser` 中的操作）。
4. 审核完成变为 **通过**，此时不可撤销，并生成 `TransportOrder` 及对应业务类型表（海运出口 / 海运进口 / 空运出口 / 件杂货，件杂货还会同时建出主单提单）。
5. 审核通过后如需驳回，需删除关联的 `TransportOrderId` 与对应业务类型表。

> 本文档已覆盖「第一部分」增删改查与「第二部分」提交审核/撤回/审核/审核后驳回全部能力。审核流程与付费申请 `PaymentApplicationAdminAppService` 一致，提交审核、撤回、审核、审核后驳回均使用编辑权限 `Admin.PreOrder.Edit`。

# 2. 功能与操作说明 (Features & Operations)

- **新增业务联系单（AddAsync）：** 携带全部子表创建，初始为“录入状态”，业务编号由编号规则自动生成。件杂货联系单在校验之前先丢弃用不上的输入（装运方式置默认、船公司置空、货物类型置普通货、箱型箱量与服务项目清空，见卡点 10）。新增/编辑共用 `ValidatePreOrderInputAsync`：主表+子表全部字符串按实体长度校验、全部外键查库是否存在，再校验销售唯一、海运出口/海运进口服务项最大集合（海运进口 2026-10-02 起）、件杂货起运港必填、所属组织。箱型箱量每行的箱型：海运出口/海运进口必填，空运出口可不填（见卡点 11）。
- **修改业务联系单（EditAsync）：** 仅“录入状态/驳回”可改，子表全量覆盖。入参处理与校验同新增（件杂货同样先丢弃无用输入）。主表只更新改动的字段，不做整行覆盖。
- **删除业务联系单（DeleteAsync）：** 仅“录入状态/驳回”可删，同时删除全部子表。
- **详情（DetailAsync）：** 返回主表 + 全部子表（品名、箱型箱量、关联用户、服务项目、费用、分组附件）。海运出口、海运进口已生成业务表时，服务项返回与生成出的业务服务项的对比标记 `compareStatus`。
- **附件（AttachmentGroup）：** 新增/编辑/详情携带分组附件，结构与海运出口一致（按附件详细类型分组）；编辑时附件全量覆盖；审核通过生成业务时附件带入对应业务，模块号按业务类型取：海运出口 `160040`、海运进口 `160070`、空运出口 `160080`、件杂货 `160150`。
- **列表（GetPagedListAsync）：** 分页查询，不含业务联系单自身子表，但**返回审核通过后生成的业务 `transportOrder`**（未通过为 null），其下按业务类型挂海运出口（服务项 `seaExportServices` + 云当运踪 + 飞驼运踪）／海运进口（服务项 `seaImportServices` + 飞驼运踪）／空运出口（云当运踪 + 飞驼运踪）／件杂货（飞驼运踪）对象，四个对象按 `bizType` 互斥，运踪取值与四个业务模块各自的列表完全一致；支持关键字（业务编号/主提单号/船名/航次）/业务类型/状态/委托单位/船公司/车队/港口/开船日期/创建人/组织/备注（模糊）等筛选，以及按销售 `saleIds`、操作 `operatorIds` 多选筛选（命中任一即可，匹配 `PreOrderUser.UserId`）；支持委托单位/船公司/起运港/目的港的「未填写」筛选（`*Empty=true`，与同名字段互斥）。列表返回完整 `carrier`（含中英文名/简称/EDI）及 `carrierLogo`（对齐海运出口），返回车队 `team`，并返回销售昵称集合 `saleNames`、操作昵称集合 `operatorNames` 与备注 `remark`。数据权限使用独立方法 `PreOrderListDataPermissionFilterAsync`（对齐海运出口）：所属人/创建人/所属组织 或 干系人（销售/商务/操作/客服/单证/海外客服/航线）命中即可见。
- **分组统计（GetGroupedListAsync）：** 查询条件与列表一致（含同一套干系人数据权限），按 `groupField`（3委托单位/4船公司/5起运港/6目的港/11业务类型，与海运出口同名字段取值一致）分组，返回每组 id、名称、条数；按船公司分组时额外返回 logo。使用查看权限。
- **提交审核（SubmitAsync）：** “录入状态/驳回”可提交，进入“待审核”，生成任务与工作流实例；无工作流或全自动通过时直接“通过”并生成业务表。使用编辑权限。工作流「申请人组织」配在大组织上时，下属部门的单据也算属于（配青岛分公司，青岛业务部的单据会走这条线）。
- **撤回（UnSubmitAsync）：** “待审核”撤回到“录入状态”，删除审核任务与工作流实例。使用编辑权限。
- **审核（AuditAsync）：** 通过或驳回，可通过 `operationUserId` 每步重新指派“操作”干系人（改后立即落库，保证生成的业务取到最新操作）；整个业务联系单通过时校验操作干系人并生成 `TransportOrder`（`InputType=1`）+ 对应业务类型表，订舱代理 `bookingAgentId`（海运出口、空运出口、件杂货）、车队 `teamId`、船名 `vessel`/航次 `innerVoyno`（海运进出口、件杂货）一并带入。委托编号按业务类型各用一套规则（`SeaExport.CommissionNum` / `SeaImport.CommissionNum` / `AirExport.CommissionNum` / `BreakBulk.CommissionNum`），各自独立计数。业务集装箱只有海运出口、海运进口生成，且只取填了箱型的行，按箱量拆成逐箱记录。海运出口的服务项按「起运港 + 委托单位」计算后生成，并同步生成首个优先级的服务项任务；**海运进口（2026-10-02 起）按「目的港 + 委托单位」计算后生成海运进口服务项与首个优先级的海进服务项任务**，规则同海运出口，配置取海运进口港口服务项配置、排除项取委托单位排除海运进口服务项。联系单备注按业务类型分开写入：海运出口写入业务主表内部备注 `InternalRemark`（外部备注留空），海运进口、空运出口、件杂货仍写入外部备注 `Remark`；备注为空则对应字段为空。通过之后再改联系单备注不会回写已经生成的业务，已通过的旧单也不把外部备注搬到内部备注。生成费用时按单位字符串重算数量与金额，并将本次生成的费用自动提交费用审核。使用编辑权限。
- **件杂货联系单审核通过：** 生成件杂货扩展表 `BreakBulk`（与业务表同 id），带入船名、航次、订舱代理，以及收货地、起运港、中转港1、中转港2、目的港、交货地及各自备注；地面代理、签单方式、第二通知人等件杂货专属字段联系单上没有，留空由操作在件杂货里补录。随后建主单提单：签单方式为空，按非正本建成「已签入」，操作补录签单方式后由提单模块纠正状态（见 `文档/提单/提单模块总逻辑文档.md` 3.2）。件杂货没有服务项目与服务项任务，也不生成业务集装箱，所以费用单位为箱型名的那些费用会被跳过。附件以模块 `160150` 带入件杂货。
- **审核后驳回（RejectAsync）：** “通过”后反悔驳回；**若已生成 `TransportOrder`/对应业务类型表且仍存在，禁止驳回**，按 `bizType` 提示 `请先删除海运出口数据`、`请先删除海运进口数据`、`请先删除空运出口数据` 或 `请先删除件杂货数据`，须先在业务侧删除后方可执行。使用编辑权限。
- **待我审核任务列表（PreOrderTaskListAsync）：** 查询“待我审核 / 我审核过”的业务联系单任务分页列表，输入=业务联系单列表条件+任务条件，输出=任务信息+业务联系单信息。可按销售 `saleIds` 多选筛选（命中任一，口径与普通列表一致），筛选发生在分页之前。`preOrder.saleNames`、`preOrder.operatorNames`、`preOrder.mblNum` 继续返回。使用审核权限 `Admin.PreOrder.Audit`。
- **查询业务详情（PreOrderAdmin/TransportOrderDetailAsync）：** 在业务联系单接口中查询对应业务(TransportOrder)详情，返回结构与业务详情完全相同；按 `bizType` 挂对应业务类型简要（SimpleDto）：海运出口填 `seaExport`、海运进口填 `seaImport`、空运出口填 `airExport`、件杂货填 `breakBulk`，四者互斥，非当前类型恒为 `null`。填充统一走 `ITransportOrderBizSimpleFiller`，与业务详情、客户对账等接口口径一致。需要完整业务详情时另调对应业务模块自身的 `DetailAsync`。使用查看权限 `Admin.PreOrder.Get`。
- **业务侧反查业务联系单（TransportOrderAdmin/PreOrderDetailAsync）：** 挂在业务接口下，返回结构与业务联系单详情完全相同（直接委托 `PreOrderAdmin.DetailAsync`）。使用业务查看权限 `Admin.TransportOrder.Get`。
- **单证识别预填（GeminiAdmin/ExtractPreOrderToAddDtoAsync）：** 上传单证由 AI 识别后组装成新增入参给前端预填，`bizType` 由前端选好后传入。`bizType=3`（件杂货）时**不回填船公司，箱型箱量恒为空数组**；船名、航次照常回填，港口按海运港口匹配。接口细节见 `文档/外部Api对接/Gemini/Gemini对接-前端对接.md`。
- **权限：** 增删改查审核权限已在 `FreightAuthorizationProvider` 注册并汉化；提交/撤回/审核/审核后驳回统一使用“编辑”权限，审核任务列表使用“审核”权限，查询业务详情使用“查看”权限。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 0：新增/编辑统一校验长度与外键]** 新增、编辑都走同一个 `ValidatePreOrderInputAsync`。字符串超长报「{字段}长度不能超过{n}个字符」（船名/航次海运进口 32、其余 64；港口备注 128；收发通内容/主表备注/箱型备注/关联用户备注 1024；费用单位 16、费用备注 4096；主提单号 64）。外键不存在报「{名称}不存在」或「{名称}ID:{id}不存在」。委托单位必填；其余往来单位、港口、船公司、付费方式、运输条款、包装、组织、品名、箱型、关联用户、费用代码、币别、结算对象有值才查。

> [!IMPORTANT] **[卡点 1：销售必填且唯一]** `preOrderUsers` 必须包含且仅包含一个 `userAttribute=销售(16)` 的用户 -> 否则新增/编辑报错“销售必填且只能指派一个用户”。

> [!IMPORTANT] **[卡点 2：关联用户属性唯一]** 同一 `userAttribute` 只能出现一次（操作等各 0-1），且属性不可为空(None) -> 否则报“{属性} 只能指派一个用户 / 用户属性不能为空”。

> [!IMPORTANT] **[卡点 3：状态限制编辑/删除]** 仅“录入状态/驳回”可编辑或删除；待审核、通过状态下受限。

> [!IMPORTANT] **[卡点 4：通过前必须指定操作]** 整个业务联系单审核通过时，`PreOrderUser` 必须存在“操作(1)”干系人 -> 否则报错“需要指定操作后方能审核通过”。可在审核每一步通过 `operationUserId` 指派。

> [!IMPORTANT] **[卡点 5：工作流审批人用户属性需有对应干系人]** 工作流节点审批人配置了 `UserAttribute` 时，须能在 `PreOrderUser` 中找到相同属性的干系人 -> 否则报错“审核人需要{属性名}干系人属性请先设置该干系人”。工作流条件字段只接受 `8001`(申请人)/`8002`(申请人组织)。`8002` 配大组织时覆盖其下属部门：配「属于青岛分公司」，青岛业务部的单据也会走这条线。

> [!IMPORTANT] **[卡点 6：海运出口起运港必填 + 服务项可少不可多]** `bizType=海运出口` 时新增/修改：起运港为空报“海运出口业务联系单起运港不能为空”；服务项超出“最大集合”报“服务项目超出允许范围(只能少于或等于海运出口主服务项)”。最大集合 = (`SeServiceConfig` 起运港配置，未命中取默认配置 − `ClientExceptService` 该委托单位针对命中那份配置的排除项，命中默认配置时取起运港为空的排除项) ∩ (`ServiceType` 枚举启用且 `Extra1=true` 的 value)。排除项口径 2026-10-02 修正：原先按票的起运港取，落到默认配置的港口查不到针对默认配置设置的排除项。

> [!IMPORTANT] **[卡点 6.1：海运进口目的港必填 + 服务项可少不可多（2026-10-02）]** `bizType=海运进口` 时新增/修改：目的港为空报“海运进口业务联系单目的港不能为空”；服务项超出最大集合报“服务项目超出允许范围(只能少于或等于海运进口主服务项)”。最大集合 = (`SiServiceConfig` 目的港配置，未命中取默认配置 − `ClientSiExceptService` 该委托单位针对命中那份配置的排除项) ∩ (`ServiceType` 枚举启用且 `Extra1=true` 的 value)。审核通过时同样要求目的港，空报同一句。

> **[卡点 7：服务项与业务对比标记（详情只读）]** 详情返回服务项时，与生成出的海运出口/海运进口主服务项目对比得出 `compareStatus`：相同(0)/业务新增(1)/业务删除(2)。仅海运出口、海运进口且已审核通过生成业务表(`transportOrderId` 有值)时计算，前端只读展示。

> [!IMPORTANT] **[卡点 8：列表数据权限含干系人]** 列表/分组不再用基类通用 `DataPermissionFilterAsync`，改用独立 `PreOrderListDataPermissionFilterAsync`。非「全部」权限时，所属人/创建人/所属组织命中，或 `PreOrderUser` 中角色为销售/商务/操作/客服/单证/海外客服/航线的干系人命中，均可看见该单据。

> [!IMPORTANT] **[卡点 9：审核通过生成服务项任务，缺处理人直接失败]** 审核通过生成海运出口服务项后会同步生成首个优先级的服务项任务，处理人由 `OrderUser` 按服务项配置的 `UserAttribute` 匹配。匹配不到时抛错 `[{港口}]港的[{服务项}]服务项任务需要用户属性为[{属性}]的处理人，当前票未配置此用户属性`，**整个审核通过失败**。另外服务项在起运港配置里找不到顺序时报 `服务项{value}顺序未配置`。海运进口（2026-10-02 起）同理：港口取目的港；服务项在目的港配置里找不到时报 `服务项{value、value}在目的港的海运进口服务项配置里不存在`（审核期间配置被改掉才会出现）。海运进口的服务项与任务在写海运进口扩展表之前算好，报错时不会留下半截数据。

> [!IMPORTANT] **[卡点 10：件杂货联系单先丢弃用不上的输入，再校验]** `bizType=件杂货(3)` 时，新增/编辑在一切校验之前先把用不上的输入改掉：装运方式置默认值 0、船公司置空、货物类型置普通货(0)、箱型箱量与服务项目清空。所以前端传了这些值也不会报错，也不会存进联系单；详情里看到的就是改过之后的值。起运港必填，空报「件杂货业务联系单起运港不能为空」（件杂货新建时起运港必填，这里提前拦住，免得审核通过生成出一票不合规的件杂货）。审核通过生成件杂货与主单提单；审核后驳回前须先删掉件杂货，否则报「请先删除件杂货数据」。

> [!IMPORTANT] **[卡点 11：空运出口联系单的箱型可以不填]** 箱型箱量每行的 `ctnCodeId`：海运出口、海运进口必填（审核通过要按它生成业务集装箱），空报「箱型ID不能为空」；空运出口可以只填箱量、卖价不填箱型（空运没有集装箱，箱型只作报价参考），存进库里 `ctnCodeId` 为空，详情里 `ctnCode` 为 null。填了箱型的照常校验存在性。审核通过时空运出口、件杂货都不生成业务集装箱，单位为箱型名的费用因此被跳过。
