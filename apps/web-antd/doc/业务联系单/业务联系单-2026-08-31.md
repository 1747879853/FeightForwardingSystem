# 1. 背景意图 (Background)

业务联系单审核通过时会生成业务表，但之前只实现了海运出口一种：

```csharp
// 旧代码
transportOrder.CommissionNum = await GenerateNumAsync(new GetGenerateTextDto()
{
    TableName = "SeaExport.CommissionNum",// 写死
    ...
});
await _transportOrderRepository.InsertAsync(transportOrder);

#region 生成对应BizType表(现仅海运出口)
if (preOrder.BizType == BizType.SeaExport) { ... }
#endregion
```

业务类型是海运进口或空运出口时会出现两个问题：

1. **生成的是半成品业务**。`TransportOrder` 主表插进去了，`App_SeaImports` / `App_AirExports` 扩展表没有。三个业务模块的列表都是从扩展表起查的，所以这条业务在任何列表里都查不到；但它挂着的费用会被按主表直查的费用/报表/对账逻辑读到，成了查不到又删不掉的幽灵单。审核后驳回也会被卡住（校验到主表还在就报「请先删除海运进口数据」，可用户在海运进口里根本找不到它）。
2. **占掉海运出口的委托编号**。编号规则名写死成 `SeaExport.CommissionNum`，海运进口/空运出口的单子会去消耗海运出口的计数器。它们又不在海运出口列表里，于是海运出口那边看着就是跳号。

本次把三种业务类型全部补齐。

# 2. 核心逻辑变更 (Core Logic)

涉及文件：`src/CsprojBuilder.Application/App/PreOrder/PreOrderAdminAppService.cs`

## 2.1 委托编号按业务类型取规则

新增 `GetCommissionNumRuleName(BizType)`，三种业务类型各取各自规则、各自独立计数：

| 业务类型           | 编号规则名(`App_GenerateNums.TableName`) |
| :----------------- | :--------------------------------------- |
| 海运出口 SeaExport | `SeaExport.CommissionNum`                |
| 海运进口 SeaImport | `SeaImport.CommissionNum`                |
| 空运出口 AirExport | `AirExport.CommissionNum`                |

规则名与 `SeaImportAdminAppService.CommissionNumRuleName`、`AirExportAdminAppService.CommissionNumRuleName` 完全一致，保证业务联系单导入的单子和模块内手动新建的单子共用同一个计数器。

## 2.2 生成对应扩展表改为三分支

`if (BizType == SeaExport)` 改为 `switch`，未知业务类型直接抛 `业务类型{xx}暂不支持生成业务`（原先是静默跳过）：

| 业务类型 | 新增私有方法 | 生成内容 |
| :-- | :-- | :-- |
| 海运出口 | `GenerateSeaExportFromPreOrderAsync` | `SeaExport` 扩展表 + `SeaExportService` 服务项 + 首个优先级服务项任务（逻辑原样搬移，未改动） |
| 海运进口 | `GenerateSeaImportFromPreOrderAsync` | 仅 `SeaImport` 扩展表 |
| 空运出口 | `GenerateAirExportFromPreOrderAsync` | 仅 `AirExport` 扩展表 |

海运进口与空运出口只写扩展表，是因为这两个模块本身就没有服务项机制——`SeaImportAdminAppService.AddAsync` 与 `AirExportAdminAppService.AddAsync` 手动新建时也不生成服务项、服务项任务、审核任务和自动费用。

## 2.3 字段映射覆盖范围

业务联系单表(`App_PreOrders`)上只有海运出口那一套字段，能对上的按下表映射，对不上的留空由操作在对应业务模块里补录。

**海运进口** 能映射的字段：

| SeaImport 字段                  | 取值                              |
| :------------------------------ | :-------------------------------- |
| `Id`                            | `preOrder.Id`（与业务表共享主键） |
| `TenantId` / `OrgId` / `UserId` | 取自业务联系单                    |
| `CarrierId`                     | `preOrder.CarrierId`              |
| `POLId` / `POLRemark`           | `preOrder.POLId` / `POLRemark`    |
| `PODId` / `PODRemark`           | `preOrder.PODId` / `PODRemark`    |

留空的海运进口专属字段：船名、航次、码头、客户编号、联运单号、分单号、贸易方式、发票号、批次号、原产国、净重合计、换单/提货/报关/转站日期、免箱期、箱使日期。

**空运出口** 能映射的字段：

| AirExport 字段                  | 取值                              |
| :------------------------------ | :-------------------------------- |
| `Id`                            | `preOrder.Id`（与业务表共享主键） |
| `TenantId` / `OrgId` / `UserId` | 取自业务联系单                    |
| `BookingAgentId`                | `preOrder.BookingAgentId`         |

留空的字段：起运地、中转地、目的地及各自备注、航班号、泡比、报关日期、送仓日期、货物明细(`AirExportOrderCtn`)。

## 2.4 附件按业务类型带到对应模块

`CopyPreOrderAttachmentsToSeaExportAsync` 泛化为 `CopyPreOrderAttachmentsToBizAsync(preOrderId, bizId, bizModuleTypeId)`，并从原来的海运出口分支里移到 `switch` 外面，三种业务类型都会带附件。目标模块类型由新增的 `GetBizAttachmentModuleTypeId(BizType)` 给出：

| 业务类型 | ModuleTypeId                                   |
| :------- | :--------------------------------------------- |
| 海运出口 | `ModuleTypeIds.Bussiness.SeaExport` = `160040` |
| 海运进口 | `ModuleTypeIds.Bussiness.SeaImport` = `160070` |
| 空运出口 | `ModuleTypeIds.Bussiness.AirExport` = `160080` |

## 2.5 集装箱：空运不生成

`PreOrderCtn` 按箱量拆成 `OrderCtn` 的逻辑加了业务类型判断，空运出口不生成集装箱，与 `AirExportAdminAppService.AddAsync` 里 `transportOrder.OrderCtns = null` 保持一致。

## 2.6 审核后驳回按业务类型校验扩展表

`RejectAsync` 里原先只查 `App_SeaExports`（还留着「海运进口上线后补充」的 TODO），现改为按业务类型分别查各自扩展表；`GetRejectBlockedMessage` 补上空运出口的提示文案「请先删除空运出口数据」。

## 2.7 新增注入

`IRepository<Entites.SeaImport, Guid>`、`IRepository<Entites.AirExport, Guid>`。

# 3. 避坑指南 (Pitfalls)

- **空运出口的起运/中转/目的地不能从业务联系单搬**。`PreOrder.POLId`/`POT1Id`/`POT2Id`/`PODId` 的外键都指向海港表 `PortCode`，而 `AirExport.POLId`/`POTId`/`PODId` 指向机场表 `AirPort`，是两张完全不同的表。直接赋值等于把海港 id 当机场 id 用，前端解析出来会是错的港口甚至查不到。真要带过来，必须先给 `PreOrder` 加空运专属的机场字段（实体 + 迁移 + DTO + 前端），本次没做。
- **编号规则要先配齐**。`SeaImport.CommissionNum` 和 `AirExport.CommissionNum` 两条规则如果 `App_GenerateNums` 里没有，且也没有「组织和适用用户都不设置」的全局规则，审核通过会报「未配置生成规则」，整个审核失败。上线前先在编号生成里把两条规则建好。
- **插扩展表必须置空 `TransportOrder` 导航**，空运还要额外置空 `AirExportOrderCtns`，否则 EF 会级联重复插入（三个扩展表与 `TransportOrder` 共享主键）。
- **历史脏数据要单独修**。本次修复只保证以后不再产生半成品业务。之前审核通过的海运进口/空运出口业务联系单，库里已经有「有 `TransportOrder`、没扩展表」的行，它们仍然查不到、驳回也仍会被卡。需要按下面的 SQL 找出来，再决定是补扩展表还是把主表连同费用一起清掉：

```sql
SELECT t.Id, t.CommissionNum, t.BizType, t.CreationTime, t.OrgId, t.UserId
FROM App_TransportOrders t
WHERE t.IsDeleted = 0
  AND t.InputType = 1 -- 业务联系单导入
  AND ((t.BizType = 1 AND NOT EXISTS (SELECT 1 FROM App_SeaImports s WHERE s.Id = t.Id))
    OR (t.BizType = 2 AND NOT EXISTS (SELECT 1 FROM App_AirExports a WHERE a.Id = t.Id)))
ORDER BY t.CreationTime DESC;
```

- **海运进口/空运出口没有服务项**，所以这两类不会生成服务项任务，也就不会触发「缺处理人导致审核通过整体失败」那个卡点（见功能文档卡点 9）。该卡点只对海运出口成立。
- 费用生成逻辑本来就与业务类型无关，未改动；但空运没有集装箱，单位是箱型名的费用会被跳过不生成，单位为 TEU 的会算出数量 0。
- 无需数据库迁移。
