# 背景意图

业务联系单列表此前只有业务联系单自身的信息，审核通过后生成的业务（`TransportOrder`）以及这票货的运踪状态都看不到，前端要么逐行再调业务接口，要么干脆展示不了。

本次让列表把关联的业务和运踪一并带出来，并且**运踪的取值逻辑必须与各业务模块自己的列表完全一致**，避免同一票货在业务联系单列表和海运出口列表看到不同的节点。

# 核心逻辑变更

## 1. 返回结构：按「业务主表 → 业务类型扩展表」真实层级嵌套

`PreOrderDto` 新增 `TransportOrder`（仅列表返回，未审核通过或业务表已删除时为 null）：

```
PreOrderDto
└── transportOrder : PreOrderTransportOrderDto     主表关键字段 + bizType
    ├── seaExport  : PreOrderSeaExportDto          仅 bizType=海运出口
    ├── seaImport  : PreOrderSeaImportDto          仅 bizType=海运进口
    └── airExport  : PreOrderAirExportDto          仅 bizType=空运出口
```

三个业务类型对象互斥，由 `bizType` 决定哪个有值。字段覆盖差异由结构本身表达，不靠「某字段在某业务类型下恒为 null」的口头约定：

| 业务类型 | 服务项 | 云当运踪 | 飞驼运踪 |
| :-- | :-: | :-: | :-: |
| 海运出口 | ✅ `seaExportServices` | ✅ `yundangShipmentOceanNode` | ✅ `FeituoTrackingSimpleDto` |
| 海运进口 | ❌ 无 | ❌ 无 | ✅ `FeituoTrackingSimpleDto` |
| 空运出口 | ❌ 无 | ✅ `yundangAirShipmentNode` | ✅ `FeituoAirTrackingSimpleDto` |

主表 `PreOrderTransportOrderDto` 只取关键字段：`id`、`bizType`、`inputType`、`commissionNum`、`mblNum`、`bookingNum`、`accountDate`、`etd`、`atd`、`eta`、`isUnfinished`、`feeLocked`。不返回干系人、箱型、品名等子表，列表不需要且会显著拖慢查询。

## 2. 为什么新建专用 DTO 而不复用 SimpleDto

仓库里 `ITransportOrderBizSimpleFiller` 负责给 `TransportOrderDto`/`TransportOrderSimpleDto` 填三个 `XxxSimpleDto`，但那三个 SimpleDto **没有运踪与服务项字段**，且被费用、结算、发票、付费申请等一大批模块共用。给它们加运踪字段会让所有这些模块的返回多出一批恒为 null 的字段，若改成在 Filler 里统一填充，则所有列表都要多付云当/飞驼的批量查询开销。

因此本次采用**业务联系单专用 DTO**（`PreOrderTransportOrderDto` + 三个子 DTO），与仓库已有的 `TransportOrderFeeOrderDto`（费用批量引入专用）做法一致。

## 3. 填充逻辑

新增私有方法 `FillPreOrderTransportOrdersAsync`，在 `GetPagedListAsync` 里紧跟 `FillNamesAsync` 调用。整体是「按本页 id 批量取数 + 内存组装」，没有逐行查库：

1. 取本页所有 `TransportOrderId`，一次投影出主表关键字段；
2. 按 `BizType` 分成三组 id，分别调用 `FillPreOrderSeaExportsAsync` / `FillPreOrderSeaImportsAsync` / `FillPreOrderAirExportsAsync`；
3. 每个业务方法先确认扩展表记录存在（业务表可能已被删），再批量取运踪。

各业务的取数口径（与对应模块列表逐行对齐）：

| 数据 | 来源与规则 |
| :-- | :-- |
| 海运出口服务项 | `SeaExportService` 按 `sortId` 升序；任务独立查 `SeServiceTask`（`Include(SeServiceConfigItem)`），靠 `SeServiceConfigItem.ServiceType == SeaExportService.ServiceType` 匹配；列表不返回任务处理人列表 |
| 云当海运节点 | 订阅按 `SubscribeTime` 最新一条定状态；节点走 `SeaExportId → 订阅.YundangId → 运单动态.Id → 节点.ShipmentId`，只取有 `ActualityTime` 的，按实际时间最晚取一条 |
| 云当空运节点 | 同上，换成空运三张表，排序多一层 `Sno` 降序 |
| 飞驼海运 | `IFeituoTrackingQueryManager.GetTrackingSummariesAsync(bizType, ids)`，出口传 `SeaExport`、进口传 `SeaImport` |
| 飞驼空运 | `IFeituoAirTrackingQueryManager.GetTrackingSummariesAsync(ids)` |

飞驼两个 QueryManager 是只读查询器（不打外部接口），设计上就是给各模块列表调的，直接注入复用。云当没有对应的公共查询器，其取数方法在海运出口/空运出口的 AppService 里是私有的，因此**复制**了一份到 `PreOrderAdminAppService`（`GetLatestYundangOceanNodeBySeaExportIdAsync`、`GetLatestYundangAirNodeByAirExportIdAsync` 及其配套的 `PickLatest*` / `MapYundang*` / `ParseYundangDateTime`）。

# 避坑指南

- **云当取数是复制来的，改动必须三处同步。** `PreOrderAdminAppService` 里的云当私有方法与 `SeaExportAdminAppService`、`AirExportAdminAppService` 的同名方法是同一份逻辑的三个副本，方法上已加注释标明。哪天云当口径要改，三处都得改，否则同一票货在不同列表会显示不同节点。更彻底的做法是仿照飞驼把云当也提成公共 QueryManager，本次没做是为了不动其它两个模块。
- **飞驼海运与空运的摘要 DTO 不是一个类型。** 海运是 `FeituoTrackingSimpleDto`（箱号、甩柜、船名航次），空运是 `FeituoAirTrackingSimpleDto`（航班、机场、航司），字段差异大，前端不能共用一套渲染。
- **「未订阅」和「已订阅但没数据」要分开处理。** `feituoTracking` 为 null 才是未订阅；非 null 但内部字段全空表示飞驼还没回数据，应显示「数据获取中」。
- **运踪时间是外部系统的原始字符串，不是 DateTime。** 云当、飞驼的节点时间都原样返回，只有业务表上的 `etd`/`atd`/`eta` 是 `DateTime?`。
- **业务表可能已被删除。** 三个填充方法都先查扩展表确认记录存在再填，所以 `transportOrderId` 有值也可能拿到 `transportOrder=null`（主表被删）或业务对象为 null（扩展表被删）。
- **只有列表接口返回 `transportOrder`。** 详情接口另有 `TransportOrderDetailAsync` 返回完整业务详情，两者不要混用。任务列表 `PreOrderTaskListAsync` 本次未加，如需要再说。
