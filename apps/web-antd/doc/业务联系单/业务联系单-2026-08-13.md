# 背景意图

本轮集中修复并补齐「业务联系单审核通过 → 生成海运出口」这条链路上的四个问题：

1. 审核时重新指派了「操作」干系人，生成到海运出口的操作却还是旧的（Bug）。
2. 生成的海运出口服务项不是本票真正可用的服务项，没有按起运港和委托单位过滤。
3. 生成了服务项，却没有像海运出口新建那样生成首个服务项任务，任务链起不来。
4. 业务联系单缺少「订舱代理」字段，海运出口建单需要的这项信息无法从业务联系单带过来。

# 核心逻辑变更

## 1. 审核改「操作」后同步到海运出口（Fix）

`AuditAsync` 中传入 `operationUserId` 时，原来只调用 `UpsertOperationUserAsync` 在内存里删旧插新，同一次请求随后生成业务表时再查库，读到的仍是**旧的操作干系人**，导致海运出口的 `OrderUser` 没跟着变。

现在在 `UpsertOperationUserAsync` 之后立即 `await CurrentUnitOfWork.SaveChangesAsync()` 落库，再走工作流结束判断与业务表生成。

## 2. 服务项按「起运港 + 委托单位」取值

`GetServiceTypeValuesByExtra1Async` 原来只按 `ServiceType` 枚举的 `Extra1` 拆分**全量**服务项，没有做任何港口/客户维度过滤，生成到海运出口的服务项因此不准确。

改造后签名为 `GetServiceTypeValuesByExtra1Async(Guid clientId, long polId)`，计算顺序：

1. 取 `SeServiceConfig` 按 `POLId` 命中的服务项配置，未命中取默认港口配置（`POLId = null`）；
2. 减去 `ClientExceptService` 中该 `ClientId + POLId` 的排除项；
3. 结果再与 `ServiceType` 枚举里 `Enable = true` 的项取交集，并按 `Extra1` 拆成 `valuesTrue`（主服务流程）/ `valuesFalse`（非主服务流程）。

服务项组成规则本身不变：**主服务 ∩ 业务联系单服务项 + 非主服务全量**。

新增/编辑校验用的最大主服务集合 `GetSeaExportAllowedServiceTypesAsync` 改为直接复用该方法的 `valuesTrue`。详情对比用的 `GetMainServiceTypeValuesAsync` 保持「不按港口/客户过滤」的原语义，单独查询枚举。

## 3. 生成首个服务项任务

服务项落库后，按海运出口新建同样的逻辑生成任务。`PreOrderAdminAppService` 新增三个私有方法（逻辑对齐 `SeaExportAdminAppService` 同名方法）：

| 方法 | 职责 |
| :-- | :-- |
| `GetSeServiceConfigItemsByPolAsync` | 取起运港服务项配置项（未命中取默认港口），并校验服务项均在配置中 |
| `GenerateServiceTasksAsync` | 为指定配置项批量生成 `SeServiceTask`（`Pending`），处理人按 `UserAttribute` 匹配 `OrderUser` |
| `GenerateFirstServiceTaskAsync` | 取最小 `SortId`，为该优先级下全部启用服务项生成任务 |

`SeaExportService.SortId` 也随之改为直接取 `SeServiceConfigItem.SortId`（与海运出口新建一致），不再用原先的 `sortMap` + 兜底 0。

## 4. 新增订舱代理 `BookingAgentId`

`PreOrder` 新增 `Guid? BookingAgentId` 及指向 `Client` 的外键导航 `BookingAgent`。

- 输入：`PreOrderAddDto`（`PreOrderEditDto` 继承）新增该字段，新增走 `ObjectMapper` 自动映射，`EditAsync` 补手动赋值；
- 输出：`PreOrderDto` 新增 `bookingAgentId`，详情额外返回 `bookingAgent`（`ClientSimpleDto`），`FillDetailSimpleDtosAsync` 把它并入客户 id 集合一起批量查询回填；
- 生成海运出口：`GenerateBizFromPreOrderAsync` 构造 `SeaExport` 时 `BookingAgentId = preOrder.BookingAgentId`。

> **字段归属**：`BookingAgentId` 只有海运出口（`SeaExport`）和空运出口（`AirExport`）有，进口业务（`SeaImport`）没有该字段。

# 避坑指南

- **同请求内改了干系人必须先落库再查库。** ABP 的仓储写入在 `SaveChanges` 前不可见，`UpsertOperationUserAsync` 之后若直接进入生成业务表流程，查出来的还是旧数据。凡是「本次请求内先改子表、后按子表生成其他数据」的场景都要注意这一点。
- **服务项一定要带 `clientId` + `polId` 去算。** 不带这两个维度拿到的是全量枚举，会把该港口没配置、或该委托单位已排除的服务项一并生成到海运出口。
- **生成任务时匹配不到处理人会直接抛错，导致整个审核失败。** 服务项配置的 `UserAttribute` 在本票 `PreOrderUser` 里必须有对应干系人，否则报 `[{港口}]港的[{服务项}]服务项任务需要用户属性为[{属性}]的处理人，当前票未配置此用户属性`。这与海运出口新建行为一致，属于预期的强校验。
- **服务项顺序未配置会报错。** `SeaExportService.SortId` 直接取配置项，取不到时报 `服务项{value}顺序未配置`，不再静默按 0 处理。
- **订舱代理是出口字段，不要在进口业务上找它。** `SeaImport` 没有这一列，业务联系单上填了也只在生成海运出口/空运出口时有意义。
- **列表不返回 `bookingAgent` 对象。** 与收货人、发货人一致，只有详情才展开为 `ClientSimpleDto`，列表仅有 `bookingAgentId`。
