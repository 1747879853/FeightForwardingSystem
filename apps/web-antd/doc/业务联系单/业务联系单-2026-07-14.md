# 3. 避坑指南 (Pitfalls)

- **迁移文件由人工生成**：已注册 `DbSet`，未生成 Migration。
- **`PreOrderFee` 为主表导航属性**：主表 `PreOrder` 已声明 `List<PreOrderFee> PreOrderFees`，费用子表随主表级联新增，详情通过 Include 返回。
- **编辑/删除状态限制**：仅“录入状态/驳回”允许。
- **编号规则**：`PreOrder.PreOrderNum` 未配置生成规则时业务编号为空，不阻断新增。
- **审核相关未实现**：提交审核、工作流、撤销、通过生成 `TransportOrder`/业务类型表、通过后驳回均属后续部分。

# 4. 第二部分：审核流程与 TransportOrder.InputType

## 4.1 TransportOrder 新增 InputType（录入方式）

- `OrderInputType` 枚举：`手动录入=0`、`业务联系单导入=1`。
- `TransportOrder.InputType` 字段**不可修改**：手动新建固定为 `0`；由业务联系单审核通过生成时固定为 `1`。
- 查询返回：`TransportOrderDto`、`TransportOrderSimpleDto` 均新增 `inputType` 输出字段；`SeaExportDto.transportOrder` 随之返回。
- 涉及文件：
  - `App/TransportOrder/Dto/TransportOrderDto.cs`：`TransportOrderDto`/`TransportOrderSimpleDto` 增加 `InputType` 输出。
  - `App/TransportOrder/TransportOrderAdminAppService.cs`：`AddAsync` 显式置 `InputType=手动录入`。
  - `App/SeaExport/SeaExportAdminAppService.cs`：新建与复制业务时显式置 `InputType=手动录入`。

## 4.2 业务联系单审核流程（提交/撤回/审核/审核后驳回）

全部使用 **编辑权限** `Admin.PreOrder.Edit`。审核逻辑复用付费申请工作流（`TaskItem` + `WorkFlowInstance` + 基类 `AuditWorkFlowInstanceAsync`）。

| 方法 | 路由 | 说明 |
| :-- | :-- | :-- |
| `SubmitAsync` | `POST .../PreOrderAdmin/SubmitAsync` | 录入/驳回→待审核，生成任务+工作流 |
| `UnSubmitAsync` | `POST .../PreOrderAdmin/UnSubmitAsync` | 待审核→录入，删除任务+工作流 |
| `AuditAsync` | `POST .../PreOrderAdmin/AuditAsync` | 通过/驳回，可 `operationUserId` 指派操作；通过生成 `TransportOrder`+`SeaExport` |
| `RejectAsync` | `POST .../PreOrderAdmin/RejectAsync` | 通过后驳回；若 `TransportOrder`/海运出口(或海运进口)仍存在则禁止，提示先删除 |

关键规则：

- 通过时校验“操作”干系人，缺失报错“需要指定操作后方能审核通过”。
- 通过生成 `TransportOrder`（`InputType=1`）；`OrderCtns` 按 `PreOrderCtn.Count` 逐箱生成；BizType 表现仅海运出口 `SeaExport`（`Id` 与业务表共享）。
- **海运出口服务项分两部分生成**：`ServiceType` 枚举启用的 `value` 按 `Extra1` 分为 `valuesTrue`/`valuesFalse`；第一部分=`valuesTrue`∩业务联系单服务项，第二部分=`valuesFalse` 全量；合并即全部服务项，`SortId` 取自 `SeServiceConfig`（未命中取默认港口配置，未配置到的排最后）。见 4.6。
- 费用表 `OrderFee` 生成失败静默跳过（跳过 `FeeCodeId/CurrencyId/PaySide` 缺失的费用），不回滚不报错。
- 工作流条件字段只接受 `8001`(PreOrderUserId)/`8002`(PreOrderOrgID)。
- 工作流审批人 `UserAttribute` 需匹配 `PreOrderUser` 干系人，缺失报错“审核人需要{属性名}干系人属性请先设置该干系人”。

## 4.3 涉及实体变更

新增接口（逻辑与结构对齐付费申请 `PayAppTaskListAsync`）：

| 接口 | 路径 | 权限 | 说明 |

# 4.5 第三部分：海运出口服务项校验与对比

## 4.5.1 新增/修改校验（起运港 + 服务项最大集合）

当 `BizType=海运出口` 时，`AddAsync`/`EditAsync` 增加校验（`ValidateSeaExportServiceTypesAsync`）：

- 起运港 `POLId` 为空 -> 报“海运出口业务联系单起运港不能为空”。
- 服务项不能超出“最大集合”（可少不可多），超出 -> 报“服务项目超出允许范围(只能少于或等于海运出口主服务项)”。

**最大集合计算**（`GetSeaExportAllowedServiceTypesAsync`）：

1. `SeServiceConfig` 按 `POLId` 命中（未命中取默认港口 `POLId=null`）取其 `SeServiceConfigItems.ServiceType`；
2. 减去 `ClientExceptService`（按 `ClientId + POLId`）的排除项；
3. 与主服务项 `values` 取交集。`values` = `Enumeration.Name="ServiceType"` 下 `Enable=true 且 Extra1=true` 的 `EnumerationItem.Value`（`GetMainServiceTypeValuesAsync`）。

## 4.5.2 详情服务项对比（compareStatus）

`DetailAsync` 返回服务项时执行对比（`ApplyPreOrderServiceCompareAsync`），仅 `BizType=海运出口` 且 `TransportOrderId` 有值时生效：

1. 海运出口服务项(`SeaExportService`，按 `SeaExportId=TransportOrderId`) 与主服务项 `values` 取交集 = 主服务项目集合；
2. 业务联系单已有项：在主服务项目中 -> `相同(0)`；不在 -> `海运出口删除(2)`；
3. 主服务项目中业务联系单没有的 -> 追加一条 `id=0` 记录，标记 `海运出口新增(1)`；
4. 未生成业务表或非海运出口时，全部为 `相同(0)`。

新增枚举 `PreOrderServiceCompareStatus`(相同=0/海运出口新增=1/海运出口删除=2)；`PreOrderServiceDto` 增 `CompareStatus`（详情只读，前端无需回传）。

# 4.6 第三部分补充：审核通过生成海运出口的服务项组成

审核通过生成海运出口时，`SeaExportService` 服务项不再直接照搬业务联系单服务项，而是分两部分组成（`GenerateBizFromPreOrderAsync`）：

1. 取 `ServiceType` 枚举中 `Enable=true` 的 `Value` → `values`，按 `Extra1` 分组：`valuesTrue`(=true 主服务流程) 与 `valuesFalse`(=false 非主服务流程)（`GetServiceTypeValuesByExtra1Async`）。
2. **第一部分** = `valuesTrue` ∩ 业务联系单服务项(`PreOrderService.ServiceType`)。
3. **第二部分** = `valuesFalse` 全量。
4. 两部分合并去重 = 海运出口生成的全部服务项。
5. 顺序(`SortId`)取自 `SeServiceConfig`（按起运港，未命中取默认港口 `POLId=null`）的服务项配置；未配置到的服务项 `SortId` 记 0 且排在最后（`GetServiceTypeSortMapAsync`）。

> 注：`valuesTrue` 与 `valuesFalse` 天然互斥（按 `Extra1` 划分），两部分无重叠。

# 4.7 第三部分补充：审核通过生成费用的数量/金额与自动提交审核

审核通过生成 `OrderFee` 时（`GenerateBizFromPreOrderAsync` 费用区，整体 `try/catch` 静默，失败不回滚不报错）：

1. **数量按单位重算**（新增私有静态方法 `ResolveQuantityByUnit`，逻辑等同 `SeServiceTaskAdminAppService.ResolveQuantityByUnit`）：`票=1`、`重量=TransportOrder.Kgs`、`体积=TransportOrder.Cbm`、`TEU=Σ 箱型 CtnCode.TEU`、其余按单位=箱型名(`CtnName`)匹配本单箱子数量。箱型/TEU 数据来自本单展开后的 `OrderCtn` + `CtnCode`。
2. **金额随数量变**：`Amount=ToFinancialRound(单价×数量)`、`NoTaxAmount=ToFinancialRound(不含税单价×数量)`。
3. **自动提交费用审核**：若本次有费用生成，将这批费用 `FeeStatus=Submitted`，并创建 `TaskBase(TaskType=SubmitOrderFee, Processed=false, EntityId=业务id)` + 每条费用一个 `TaskItem(TaskType=SubmitOrderFee, FrightModule=OrderFee, TaskStatus=Auditing, EntityId=费用id)`，参考 `OrderFeeAdminAppService.SubmitOrderFeeAsync` 的任务生成部分。

新增注入仓储：`CtnCode`、`TaskBase`。

# 4.8 第三部分补充：业务↔业务联系单互查与业务详情携带海运出口

三项跨服务查询能力（**不使用 IocResolver**，避免多余的 SeaExport 详情 enrich 查询）：

1. **业务详情携带海运出口**（`TransportOrderAdminAppService.DetailAsync`）：当 `BizType=SeaExport` 且存在海运出口数据时，**直接查询** `TransportOrder`（`.Include(x=>x.SeaExport).ThenInclude(s=>s.SeaExportServices)`）后 `ObjectMapper.Map<SeaExportDto>(transportOrder.SeaExport)`，赋给字段 `TransportOrderDto.SeaExport`，并将其 `TransportOrder` 置空以避免循环嵌套。
   - `TransportOrderDto` 由 `[AutoMapFrom]` 自动映射，实体存在同名 `SeaExport` 导航；若被自动映射会与 `SeaExportDto.TransportOrder` 形成 `SeaExport⇄TransportOrder` 循环（默认 Newtonsoft `ReferenceLoopHandling=Error` 会报自引用错误）。故在 `CsprojBuilderApplicationModule` 配置器中 `cfg.CreateMap<TransportOrder, TransportOrderDto>().ForMember(d => d.SeaExport, o => o.Ignore())` **禁止该成员自动映射，改为代码手动赋值**（本仓库既有约定：要 ignore 就在配置器加）。
2. **业务联系单查业务详情**（新增 `PreOrderAdminAppService.TransportOrderDetailAsync`，权限 `Admin.PreOrder.Get`）：先取 `TransportOrder` 判断 `bizType`；海运出口时**调用海运出口详情方法**(`SeaExportAdmin/DetailAsync`)填充 `seaExport`（与海运出口详情完全一致、带全部字段），`seaImport=null`；海运进口预留 `seaImport`（暂未实现）；其余类型两字段均为 `null`。
3. **业务查业务联系单详情**（新增 `TransportOrderAdminAppService.PreOrderDetailAsync`，权限 `Admin.TransportOrder.Get`，文档在《业务联系单接口文档》第八节）：`TransportOrderAdminAppService` **构造函数注入** `IPreOrderAdminAppService`，直接委托 `PreOrderAdmin.DetailAsync`，返回结构与业务联系单详情完全一致。

> 为何 2、3 一个直查一个委托：业务详情较轻(映射+内嵌海运出口)，直查即可且省查询；业务联系单详情逻辑复杂(子表/服务项对比/分组附件/名称回填)，委托 `PreOrderAdmin.DetailAsync` 复用逻辑保证“完全相同”。因 PreOrder 侧不再反向依赖 TransportOrder 服务，故 `TransportOrder → PreOrder` 单向构造函数注入**不构成循环依赖**。

# 4.9 第三部分补充：附件(分组)与审核带入海运出口

1. **新增/编辑/详情携带分组附件**：`PreOrderAddDto`(被 `PreOrderEditDto` 继承) 与 `PreOrderDto` 分别新增 `AttachmentGroup`(输入 `AttachmentGroupInputDto` / 输出 `AttachmentGroupDto`)，结构与海运出口完全一致（按 `AttachmentDtlTypeId` 分组）。复用通用附件模块，`ModuleTypeId=ModuleTypeIds.Bussiness.PreOrder("160050")`，itemId=业务联系单id。
2. **编辑附件全量覆盖**：`EditAsync` 先 `DeleteAttachmentItemsAsync(PreOrder, id)` 删除旧关联，再 `SaveAttachmentGroupsAsync` 按入参重建（与子表全量覆盖一致）。
3. **审核通过带入海运出口**：`GenerateBizFromPreOrderAsync` 生成海运出口后调用 `CopyPreOrderAttachmentsToSeaExportAsync(preOrderId, transportOrderId)`——读取业务联系单附件关联，复用同一 `AttachmentId`，以海运出口维度(`ModuleTypeId=SeaExport 160040`，itemId=业务表id)新建关联，保留 `AttachmentDtlTypeId/ClientVisible/DisplayOrder/IsFirstShow`。
4. **附件批量改可见**：`AttachmentAppService` 新增 `UpdateAttachmentItemsClientVisibleAsync(IEnumerable<UpdateAttachmentItemClientVisibleDto>)`，按 `AttachmentItem.Id` 批量更新 `ClientVisible`，逐条独立取值（同 id 取最后一条），空/无效集合直接返回。

新增注入：`IAttachmentAppService`（构造函数注入，无循环依赖）；新增私有方法 `SaveAttachmentGroupsAsync`/`GetAttachmentGroupsAsync`/`BuildAttachmentGroups`/`CopyPreOrderAttachmentsToSeaExportAsync`。

# 5. 避坑指南补充 (Pitfalls)

- **InputType 只读**：编辑接口不含该字段，AutoMapper 不覆盖；请勿在前端提交。
- **无工作流即自动通过**：未配置/未启用 PreOrder 工作流时，提交审核会直接“通过”并生成业务表——此时若无“操作”干系人，提交会报错。
- **共享主键**：`SeaExport.Id == TransportOrder.Id`，插入 SeaExport 时须置 `TransportOrder=null` 防止级联重复插入。
- **循环嵌套/映射环**：`TransportOrderDto.SeaExport` 与实体导航同名，必须在 `CsprojBuilderApplicationModule` 配置器里 `ForMember(d=>d.SeaExport, o=>o.Ignore())` 禁止自动映射后手动赋值，并置空嵌套的 `SeaExport.TransportOrder`，否则触发 `SeaExport⇄TransportOrder` 自引用序列化错误。
- **不要用 IocResolver 做互查**：会引发大量非必要 enrich 查询。业务详情/查业务详情直接查询内嵌海运出口；业务查业务联系单详情用**单向构造函数注入** `IPreOrderAdminAppService` 委托（PreOrder 侧不反向依赖，无循环）。
