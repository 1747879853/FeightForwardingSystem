# 背景意图

业务联系单审核通过时会自动生成费用并提交费用审核，但生成出来的费用**谁都撤销不了提交**，报「只能撤回自己提交的费用」。

原因是费用的创建人和费用审核任务的提交人被记成了两个不同的人：

| 数据 | 原来记的人 | 怎么来的 |
| :-- | :-- | :-- |
| `OrderFee.CreatorUserId` | 业务联系单费用的录入人 | 代码显式赋值 `fee.CreatorUserId` |
| `TaskBase`/`TaskItem.CreatorUserId` | 未显式指定，交给 ABP 审计填充 | 取当前登录人，即业务联系单的**审核人** |

而撤销提交接口 `OrderFeeAdminAppService.OrderFeeTaskWithdrawAsync` 的校验只看**任务**的创建人：

```csharp
if (taskItems.Any(x => x.CreatorUserId != AbpSession.UserId.Value))
    throw new UserFriendlyException("只能撤回自己提交的费用");
```

于是费用列表上显示的创建人（录入人）与实际能撤销的人（审核人）对不上，界面上看着是自己的费用却撤不了。

# 核心逻辑变更

统一口径：**费用创建人与费用审核任务提交人都记「当票销售」**。

`GenerateBizFromPreOrderAsync` 中：

1. 加载子表后取出当票销售（销售必填且唯一，由 `ValidatePreOrderUsers` 保证）：

```csharp
var saleUserId = users.FirstOrDefault(x => x.UserAttribute == UserAttribute.Sale)?.UserId;
```

2. 生成 `OrderFee` 时 `CreatorUserId = saleUserId`（原为 `fee.CreatorUserId`）。
3. 生成费用审核任务时，`TaskBase` 与其下每条 `TaskItem` 均显式 `CreatorUserId = saleUserId`。

# 避坑指南

- **撤销提交校验的是 `TaskItem.CreatorUserId`，不是 `OrderFee.CreatorUserId`。** 以后凡是代码里自动提交费用审核的场景（不是用户本人点的提交），都要显式指定任务的创建人，否则 ABP 会填成当次操作人，导致费用归属与撤销权限错位。
- **必须显式赋值，不能指望 ABP 审计。** `EntityAuditingHelper.SetCreationAuditProperties` 只在 `CreatorUserId == null` 时才填充，显式赋值会被保留；反过来，不赋值时填的是当前登录人，且 `TaskItem` 未实现 `IMustHaveTenant`，多租户下的填充行为还会再受一层判断影响。显式写死可以完全绕开这些不确定性。
- **费用创建人的展示口径变了。** 费用列表的创建人取 `OrderFee.CreatorUserId`（`OrderFeeAdminAppService.cs` 第 3181 行），改动后由业务联系单自动生成的费用，创建人显示为当票销售，不再是业务联系单的录入人。
- **销售缺失时的兜底是自洽的。** 若 `saleUserId` 为 null，费用与任务的创建人都不显式指定，行为退回原样（由 ABP 填当次操作人），两者仍然一致，撤销由审核人执行。业务上销售必填，正常不会走到这里。
