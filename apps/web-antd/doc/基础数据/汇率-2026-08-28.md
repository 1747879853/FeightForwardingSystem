# 1. 背景意图 (Background)

费用录入时的汇率是**当时**按币别 + 会计期间从汇率表带出来的，带出来之后就存死在 `OrderFee.ExchangeRate` 上。后续如果发现某个月的汇率配错了、或者补配了之前没维护的汇率，**已经录好的费用不会自动跟着变**，只能一条条手工改。

本次给汇率模块加一个批量刷的口子：选定一条汇率记录，把它的应收汇率、应付汇率刷到「会计期间落在这条汇率有效期内、且币别匹配」的那批费用上。

功能拆成两个接口：先查出**能刷哪些票**让人核对勾选，再对勾中的执行。

## 2.1 「一票」的定义

沿用提成模块的口径：**一票 = 一个主单原票（`ChangeOrderId` 为空）或一个更改单**。返回与勾选的粒度都是票，但实际改的是费用。

| 票 | 会计期间取自 | 费用范围 |
| :-- | :-- | :-- |
| 主单原票 | `TransportOrder.AccountDate` | `OrderFee.ChangeOrderId` 为空的那批 |
| 更改单 | `ChangeOrder.AccountDate` | `OrderFee.ChangeOrderId` 等于该更改单 |

> [!IMPORTANT] 会计期间取的是**主单/更改单单据上的那一列**，不是 `OrderFee.AccountDate`。
>
> 这两者实际会漂——`TransportOrderAdminAppService.EditAsync` 改主单会计期间时并不级联所有费用，更改单编辑也只同步「录入/驳回」状态的费用。以单据上的为准。

## 2.2 接口一：查询可同步的票

| 项 | 值 |
| :-- | :-- |
| 接口地址 | `GET /api/services/app/ExchangeRateAdmin/GetSyncOrderFeeRateListAsync` |
| 方法名 | `GetSyncOrderFeeRateListAsync` |
| 入参 | `ExchangeRateSyncQueryDto`（`[FromQuery]`） |
| 出参 | `ExchangeRateSyncPreviewDto` |
| 权限 | `Admin.ExchangeRate.Get` |

**入参 `ExchangeRateSyncQueryDto`**

| 字段名     | 类型     | 必填 | 含义       | 说明     |
| :--------- | :------- | :--: | :--------- | :------- |
| `Id`       | `long`   |  是  | 汇率id     |          |
| `MblNum`   | `string` |  否  | 主提单号   | 模糊匹配 |
| `ClientId` | `Guid?`  |  否  | 委托单位id | 精确匹配 |

**筛选口径**

```
币别      = 该汇率的 CurrencyId
会计期间   ∈ [StartDate 所在月1号, EndDate 所在月1号]
汇率不相等 = 应收费用的 ExchangeRate ≠ DRValue，或 应付费用的 ExchangeRate ≠ CRValue
可选       = 主提单号模糊、委托单位精确
```

只返回**有费用需要改**的票；一票下该币别的费用汇率全都已经等于目标值时，这一票不返回。会计期间的比较用月初1号（会计期间本来就存月初）。

**出参 `ExchangeRateSyncPreviewDto`**

| 字段名 | 类型 | 含义 |
| :-- | :-- | :-- |
| `SyncableTickets` | `List<ExchangeRateSyncTicketDto>` | 可同步的票，按会计期间、主单id 升序 |
| `BlockedTickets` | `List<ExchangeRateSyncTicketDto>` | 不可同步的票，每条带原因，前端应置灰不让勾 |

**`ExchangeRateSyncTicketDto`**

| 字段名 | 类型 | 含义 |
| :-- | :-- | :-- |
| `TransportOrderId` | `Guid` | 业务主单id |
| `ChangeOrderId` | `Guid?` | 更改单id，为空代表主单原票 |
| `AccountDate` | `DateTime` | 这一票的会计期间 |
| `TransportOrder` | `TransportOrderSimpleDto` | 业务主单信息 |
| `ReceivableFeeCount` | `int` | 需要同步的应收费用条数（汇率已一致的不计入） |
| `PayableFeeCount` | `int` | 需要同步的应付费用条数（同上） |
| `BlockedReason` | `string` | 不可同步的原因，可同步时为 `null` |

前四个字段同级，业务信息挂在 `TransportOrder` 对象下。

## 2.3 接口二：执行同步

| 项       | 值                                                               |
| :------- | :--------------------------------------------------------------- |
| 接口地址 | `POST /api/services/app/ExchangeRateAdmin/SyncOrderFeeRateAsync` |
| 方法名   | `SyncOrderFeeRateAsync`                                          |
| 入参     | `ExchangeRateSyncDto`（`[FromBody]`）                            |
| 出参     | `ExchangeRateSyncResultDto`                                      |
| 权限     | `Admin.ExchangeRate.Edit`                                        |

**入参 `ExchangeRateSyncDto`**（继承 `ExchangeRateSyncQueryDto`，多一个列表）

| 字段名 | 类型 | 必填 | 含义 |
| :-- | :-- | :-: | :-- |
| `Id` / `MblNum` / `ClientId` | — | — | 同接口一，**必须与查询时传的一致** |
| `Tickets` | `List<ExchangeRateSyncTicketInputDto>` | 是 | 勾选的票，至少一条 |

`ExchangeRateSyncTicketInputDto`：`TransportOrderId`（`Guid`）+ `ChangeOrderId`（`Guid?`）。

**执行逻辑**

1. 重跑一遍接口一的校验与筛选；
2. 与 `Tickets` 取交集，**只处理交集**；
3. 勾中任何一条落在 `BlockedTickets` 的 → **整个接口报错，一条都不改**；
4. 交集为空 → 报「勾选的票均不在可同步范围内 请重新查询」；
5. 逐条改：`PaySide = 收` 写 `DRValue`，`PaySide = 付` 写 `CRValue`；已经等于目标值的跳过。

**出参 `ExchangeRateSyncResultDto`**

| 字段名               | 类型  | 含义                   |
| :------------------- | :---- | :--------------------- |
| `TicketCount`        | `int` | 实际同步的票数         |
| `ReceivableFeeCount` | `int` | 实际改动的应收费用条数 |
| `PayableFeeCount`    | `int` | 实际改动的应付费用条数 |

## 2.4 汇率记录本身的校验

两个接口共用 `ValidateSyncExchangeRateAsync`，按顺序：

| 校验                                      | 报错文案                        |
| :---------------------------------------- | :------------------------------ |
| 汇率存在                                  | 输入汇率错误                    |
| `Enable == true`                          | 汇率已停用不可同步汇率          |
| `DRValue` 与 `CRValue` **都有值且都 > 0** | 应收/应付汇率未维护不可同步汇率 |

> [!IMPORTANT] **应收应付必须同时维护**，只配了一边不给同步。**汇率是 0 或负数也按「未维护」拦掉**——`decimal?` 的 0 是"有值"，但同步下去这批费用本位币金额全变 0，而且系统另有「汇率为 0 的费用不可提交」的规则，等于批量制造出一堆提交不了的费用。

## 2.5 唯一的业务拦截：已关联销售提成

不可同步的原因目前只有一条：**这一票已被销售提成单算过**（主单原票看 `TransportOrder.SalesCommissionOrderId`，更改单看 `ChangeOrder.SalesCommissionOrderId`），文案为 `已关联销售提成不可同步汇率`。

**其余的费用守卫一律不拦**——费用锁定、费用审核状态、已结算、已对账、已开票申请、已付费申请全都放行。

理由是这些下游单据**都不读 `OrderFee.ExchangeRate`**，各自有自己填的汇率：开票走 `InvoiceValue`、付费申请自带汇率、结算金额 `SettledAmount` 是原币。改费用行汇率只影响「按费用行汇率现算本位币」的地方（主要是报表与对账展示），而那本来就是这个功能想要的效果。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT] **接口二必须传与查询时相同的筛选参数，而且后端会拿它重新筛一遍。**
>
> `Tickets` 是前端传的，内容可以是任意 `TransportOrderId + ChangeOrderId` 组合。如果后端只按列表干活，这就是一个「把任意费用的汇率改成任意值」的后门。所以参数在这里的作用是**重新校验**，不是二次过滤——以后别看它"冗余"就删掉。

- **拦销售提成的理由是操作一致性，不是金额会变。** 提成单算利润用的是 `ExchangeRate.CommissionValue`（按会计期间月查汇率表），**根本不读 `OrderFee.ExchangeRate`**，所以同步费用汇率对已生成的提成单金额没有任何影响。拦它是为了跟已有的「已提成的票，费用除查询外任何操作都不许」保持一致（见 `OrderFeeAdminAppService.FeeLockedCheckAsync`）。
- **操作提成不拦。** 它锁的是业务字段（港口、货物类型），跟费用无关。
- **起止日期为空 = 无界区间，且本功能不分页。** `StartDate` / `EndDate` 都是可空的，为空时按不限处理（`DateTime.MinValue` / `MaxValue`）。一条两端都空的 USD 汇率会把全库所有 USD 费用的票一次拉回来。实际维护中起止日期总该填，但前端别做成「随便点一条汇率就查」。
- **一票可能横跨多个币别，只改该币别的费用。** 一票里既有 USD 又有 RMB 的费用时，只有 USD 那几条被改。返回的 `ReceivableFeeCount` / `PayableFeeCount` 就是"这一票会动几条"，前端把它显示出来，用户勾之前心里有数。
- **汇率已一致的费用不会出现也不会被改。** 筛选阶段就在库里过滤掉了，执行阶段还会再判一次。这样返回的条数是真实改动数，也不会白刷一遍 `LastModifierUserId` / `LastModificationTime`。
- **没有数据权限过滤、没有分页、没有操作日志。** 这个功能定位是「权限最大的人用的批量修数工具」，刻意没加这三样。放权限时注意 `Admin.ExchangeRate.Edit` 的含金量比看上去高。
