# 发票开出汇率校验（前端对接）

**控制器**：`InvoiceIssueAdmin`

本次共 2 个破坏性变更 + 1 个新接口：

> **破坏性变更 1**：`AddAsync` 出参从 `Guid` 改为对象 `InvoiceIssueAddResultDto`。原来直接把返回值当ID用的地方，改成取 `result.id`。
>
> **破坏性变更 2**：`AddApplicationsAsync` 出参从 `bool` 改为对象 `InvoiceIssueExchangeRateCheckDto`。原来 `if (res)` 判断成功的地方，改成判断 `result.code === 0`。
>
> **新接口**：`SyncApplicationGoodsDtlByExchangeRateAsync`，按当前发票汇率修正开票申请商品明细的金额。

**统一交互模型（两个新增接口一致）**：提交 → 服务端先做汇率校验 → `code=0` 才真正执行；`code` 不为 `0` 时**什么都不做**，只把 `code` 和两组开票申请ID返回给前端。前端据此走「调修正接口 → 刷新 → 重新提交」或「引导驳回」。

## 一、`POST /api/services/app/InvoiceIssueAdmin/AddAsync`

**权限**：`Admin.InvoiceIssue.Add`

### 入参 `InvoiceIssueAddDto`（Body JSON）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `orgId` | `long?` | 是 | 所属组织id，需为本人所属组织 |
| `invoiceIssueType` | `InvoiceIssueType` | 是 | 发票开出方式：`0`=诺诺接口开票，`1`=手动记录 |
| `invoiceNo` | `string` | 否 | 发票号 |
| `invoiceIssueTime` | `DateTime` | 是 | 开票时间 |
| `require` | `string` | 否 | 开票要求 |
| `remark` | `string` | 否 | 备注 |
| `invoiceIssueItems` | `List<InvoiceIssueItemInputDto>` | 是 | 合并的开票申请，至少一条，不可重复 |
| `invoiceIssueGoodsDtls` | `List<InvoiceIssueGoodsDtlInputDto>` | 否 | 发票开出商品明细，可为空；金额合计须与开票申请一致 |

`InvoiceIssueItemInputDto`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `invoiceApplicationId` | `Guid` | 是 | 开票申请ID |
| `remark` | `string` | 否 | 备注 |

`InvoiceIssueGoodsDtlInputDto`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `codeInvoiceId` | `long` | 是 | 发票商品编码ID |
| `specification` | `string` | 否 | 规格型号 |
| `unit` | `string` | 否 | 发票单位 |
| `quantity` | `decimal` | 是 | 数量（2位小数） |
| `unitPrice` | `decimal` | 是 | 含税单价（4位小数） |
| `amount` | `decimal` | 是 | 金额（2位小数） |
| `noTaxAmount` | `decimal` | 是 | 不含税金额（2位小数） |
| `taxRate` | `decimal` | 是 | 税率(%)（4位小数） |
| `taxAmount` | `decimal` | 是 | 税额（2位小数） |
| `remark` | `string` | 否 | 备注 |

### 出参 `InvoiceIssueAddResultDto`

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | `int` | `0`=正常，已新增成功；`1`=汇率已变动，且金额对不上的开票申请**都只有一条**商品明细（可调修正接口）；`2`=存在金额对不上且商品明细**不止一条**的开票申请（只能驳回） |
| `id` | `Guid?` | 新建的发票开出ID；`code` 不为 `0` 时为 `null` |
| `singleGoodsDtlApplicationIds` | `Guid[]` | 金额对不上、且只有一条商品明细的开票申请ID列表 |
| `multiGoodsDtlApplicationIds` | `Guid[]` | 金额对不上、且商品明细不止一条的开票申请ID列表 |

两个ID列表任何情况下都会返回数组（不会是 `null`）：`code=0` 时都为空数组，`code=1` 时 `multiGoodsDtlApplicationIds` 为空数组。

### 报错提示

| 提示 | 触发条件 |
| :--- | :--- |
| `请至少选择一个开票申请` | `invoiceIssueItems` 为空 |
| `开票申请存在重复` | `invoiceApplicationId` 有重复 |
| `部分开票申请不存在` | 有ID查不到对应开票申请 |
| `未维护xx币种的发票汇率，请先维护本位币为RMB的对应币种的发票汇率` | 开票申请的币别没有当前有效的发票汇率 |
| `金额合计不一致：开票申请合计 x，商品明细合计 y` | `code=0` 时前端传入的商品明细金额合计与开票申请不一致 |
| 其余（申请状态、四要素一致、已被其他发票开出关联等） | 与改动前一致 |

## 二、`POST /api/services/app/InvoiceIssueAdmin/AddApplicationsAsync`

给已存在的发票开出加挂开票申请。

**权限**：`Admin.InvoiceIssue.Edit`

### 入参 `InvoiceIssueAddApplicationsDto`（Body JSON）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | `Guid` | 是 | 发票开出ID |
| `invoiceIssueItems` | `List<InvoiceIssueItemInputDto>` | 是 | **本次新增**的开票申请，至少一条，不可重复、不可与已关联的重复 |
| `invoiceIssueGoodsDtls` | `List<InvoiceIssueGoodsDtlInputDto>` | 否 | **合并后全部**开票申请对应的完整商品明细，用于金额校验并全量替换；可传空（相当于清空） |

### 出参 `InvoiceIssueExchangeRateCheckDto`

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | `int` | 含义与口径同 `AddAsync`。**`code=0` 就代表加挂成功**，它替代了原来的 `bool` 返回值 |
| `singleGoodsDtlApplicationIds` | `Guid[]` | 对不上且只有一条商品明细的开票申请ID |
| `multiGoodsDtlApplicationIds` | `Guid[]` | 对不上且商品明细不止一条的开票申请ID |

> 本接口没有单独的 `success` 字段：校验没过会提前返回、出错会抛异常，能拿到 `code=0` 就说明加挂已经执行完了，再挂一个布尔标志只是重复同一个信息。

**只校验本次新增的开票申请**（`invoiceIssueItems` 里的那些）。已关联的申请已经是"已开票"、开票时校验过，不参与本次汇率校验，所以历史汇率变动不会阻塞加挂新申请。

### 报错提示

| 提示 | 触发条件 |
| :--- | :--- |
| `请至少选择一个开票申请` | `invoiceIssueItems` 为空 |
| `发票开出不存在` | `id` 查不到 |
| `开票申请存在重复` | 本次新增的 `invoiceApplicationId` 有重复 |
| `开票申请已关联本发票开出` | 本次新增的申请已经挂在这张发票开出上 |
| `部分开票申请不存在` | 有ID查不到对应开票申请 |
| `未维护xx币种的发票汇率，请先维护本位币为RMB的对应币种的发票汇率` | 本次新增的申请币别没有当前有效的发票汇率 |
| `金额合计不一致：开票申请合计 x，商品明细合计 y` | `code=0` 时合并后申请与传入商品明细金额合计不一致 |
| 其余（申请状态、四要素一致、已被其他发票开出关联等） | 与改动前一致 |

## 三、`PUT /api/services/app/InvoiceIssueAdmin/SyncApplicationGoodsDtlByExchangeRateAsync`

按当前发票汇率修正开票申请商品明细的金额。专门配合上面两个接口返回的 `code=1` 使用。

**权限**：`Admin.InvoiceIssue.Add` 或 `Admin.InvoiceIssue.Edit`（任一即可）

### 入参 `InvoiceIssueSyncApplicationGoodsDtlDto`（Body JSON）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `invoiceApplicationIds` | `List<Guid>` | 是 | 待修正的开票申请ID列表，至少一条。直接把校验结果的 `singleGoodsDtlApplicationIds` 传进来 |

### 出参 `InvoiceIssueSyncApplicationGoodsDtlResultDto`

| 字段 | 类型 | 说明 |
|------|------|------|
| `updatedApplicationIds` | `Guid[]` | 实际修正了金额的开票申请ID列表 |
| `unchangedApplicationIds` | `Guid[]` | 金额本来就对得上、无需修正的开票申请ID列表（不改数据也不写备注） |

### 会改什么

只动那**唯一一条**商品明细的三个金额字段：

```
amount      = round(sum(费用明细.appliedAmount) × 当前发票汇率, 2)
noTaxAmount = round(amount / (1 + taxRate/100), 2)
taxAmount   = amount - noTaxAmount
```

`quantity`、`unitPrice`、`taxRate`、`codeInvoiceId` 等其余字段不变。**不会**动发票开出的任何数据。

### 备注留痕

每次实际修正都会在该条商品明细的 `remark` **末尾追加一行**（原备注保留）：

```
更新时间：2026-08-04 15:36:12；更新方式：汇率变动（张三提交的更新）；更新字段：金额（更新前 1000.00，更新后 1050.00）、不含税金额（更新前 917.43，更新后 963.30）、税额（更新前 82.57，更新后 86.70）
```

> `更新字段` 只列本次真正变了的字段。零税率（`taxRate=0`）的商品明细，`noTaxAmount` 恒等于 `amount`、`taxAmount` 恒为 0，值没变就不会出现在这一行里，所以字段个数可能是 1~3 个，前端不要按固定三段解析。

`remark` 上限 1024 字符，追加后超长时按行丢弃最早的记录。前端展示商品明细备注时注意可能是多行文本。

### 报错提示

| 提示 | 触发条件 |
| :--- | :--- |
| `请至少选择一个开票申请` | `invoiceApplicationIds` 为空 |
| `部分开票申请不存在` | 有ID查不到 |
| `开票申请[xxx]非待审核(已提交)状态 不能按汇率修正商品明细` | 申请不是 `Auditing` 状态（已开票的不允许改，否则与已开出的发票脱节） |
| `开票申请[xxx]的商品明细不止一条 无法按汇率自动修正 请驳回后手工调整` | 传了商品明细多于一条的申请。**不要把 `multiGoodsDtlApplicationIds` 传进来** |
| `未维护xx币种的发票汇率，请先维护本位币为RMB的对应币种的发票汇率` | 币别没有当前有效的发票汇率 |

> 任一条校验不通过都是整批失败，不存在"部分成功"。

## 四、推荐前端交互流程

两个新增接口共用同一套流程，成功的判断依据都是 `code === 0`（`AddAsync` 成功时还能从 `id` 拿到新建的发票开出主键）：

1. **提交**：用户填好表单后正常调 `AddAsync` 或 `AddApplicationsAsync`。
2. **按 `code` 分支**：
   - `code=0`：成功。`AddAsync` 取 `id` 跳详情；`AddApplicationsAsync` 直接刷新详情。
   - `code=1`：弹确认框——「所选开票申请的发票汇率已变动，确认按当前汇率更新其商品明细金额？」，可用 `singleGoodsDtlApplicationIds` 高亮受影响的开票申请。用户确认后走第 3 步。
   - `code=2`：提示「以下开票申请的发票汇率已变动，且商品明细不止一条，无法自动更新，请先驳回后重新调整商品明细」，用 `multiGoodsDtlApplicationIds` 列出这些申请，引导去开票申请页驳回。**不要重试**，重试结果一样。
3. **修正**：把 `singleGoodsDtlApplicationIds` 传给 `SyncApplicationGoodsDtlByExchangeRateAsync`。
4. **刷新**：重新拉取这些开票申请（`GetSubmittedApplicationListAsync` 或发票开出详情）拿到修正后的商品明细金额，让用户确认/调整发票开出商品明细 `invoiceIssueGoodsDtls`。
5. **重新提交**：再调一次第 1 步的接口，此时应返回 `code=0`。

> 混合场景（既有 single 又有 multi）会返回 `code=2`。此时先让用户处理 multi 那部分（驳回或从选择中移除），再重新提交。
