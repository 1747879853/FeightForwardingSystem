# 1. 业务背景说明 (Background)

**白话解释：**

以前【发票开出】只是一条记录，发票号是人工在税局/开票软件里开完票再手工填回系统的（这就是"手动记录"方式）。现在接了开票服务商的接口，可以直接在系统里点"开发票"，由服务商去税局开出**数电发票**，开完票把发票号、开票日期、发票版式文件（OFD/XML/PDF/图片）自动回填到系统里。

数电发票有两个和纸质时代完全不同的地方，整套设计都围绕它们：

1. **异步**。点"开发票"只是把报文报到税局，同步只拿到一个"开票流水号"，**这时候还没有发票号**。真正的结果几秒到几十分钟后才回来（税局繁忙时更久），靠回调推送或手动查询才能拿到。
2. **不能作废，只能冲红**。而且冲红不是一步到位——要先向税局申请一张【红字确认单】，确认单生效（可能还需要购方点头）之后才会开出红票。

所以业务上要接受两件事：**开票不是点一下就有号**，**开错了只能冲红、不能改也不能删**。

# 2. 功能与操作说明 (Features & Operations)

控制器 `InvoiceIssueAdmin`，**全部复用 `Admin.InvoiceIssue.Edit` 权限，没有新增权限项**。

| 功能 | 接口 | 操作路径与结果 |
| :-- | :-- | :-- |
| **开发票** | `POST /api/services/app/InvoiceIssueAdmin/IssueByInterfaceAsync` | 发票开出详情/列表点"开发票"。成功后 `issueStatus=1`（已提交待开票），**此时无发票号**；开票方式被自动改成"接口开票" |
| **查询开票结果** | `POST .../QueryIssueResultAsync` | 手动刷新。查到开票完成时**顺带完成回填与存附件** |
| **申请冲红** | `POST .../ApplyRedAsync` | 对已开出的票发起冲红，需选冲红原因。成功后 `redStatus=15`（申请中） |
| **查询冲红结果** | `POST .../QueryRedResultAsync` | 手动刷新冲红进度。这个接口会**推进整条链路**：查确认单 → 调快捷冲红拿红票流水号 → 回填红票号与附件。查红票失败（`redFailCause` 有值）时按原流水号走开票重试一次；重试成功则用重试接口的返回落地 |
| **接收回调** | `POST /api/invoice-issue/callback` | 匿名接口，服务商直接推送到本机公网地址。不对前端开放 |

## 2.1 蓝票（正常开票）完整流程

```
① 建发票开出（挂上开票申请、填商品明细）        issueStatus=0 未开票
② 点"开发票" → 组报文报到税局                   issueStatus=1 已提交待开票   ← 此后只能查询
③ 税局开票（几秒~几十分钟）
④ 服务商回调 /api/invoice-issue/callback
   → 本机回查【发票详情查询接口】以其结果为准
   → 回填发票号/发票代码/开票日期
   → 回填关联开票申请的发票号、状态置已开票
   → 下载全部版式文件存附件                     issueStatus=2 开票完成
```

回调迟迟不来时，点"查询开票结果"手动走一遍④，效果完全一样。

## 2.2 冲红完整流程

数电票**不能作废、只能冲红**，税局要求先立一张【红字确认单】，所以整条链路是四个接口、五步，中间每一步都可能停下来等。**操作人只点一次「冲红」，后面全靠服务商推送自动推进。**

```
第0步  点"冲红" + 选冲红原因            ← 唯一一次人工操作
         │  前置校验不过 → 当场报错，状态不变(见 2.2.1)
         ▼
第1步  提交【红字确认单申请】
         │  服务商报错 → 直接报给操作人，状态留在"未冲红"，改完可重来
         ▼  受理成功 → redStatus=15 申请中
         ┊
         ┊ (以下 2~4 步由【确认单推送】【开票推送】或人工点"查询冲红结果"触发，三者行为完全一致)
         ┊
第2步  查【红字确认单】状态 ── 五个分叉(见 2.2.2)
         │  ├ 无需确认(1) / 双方已确认(4)   → 生效，往下走
         │  ├ 待购方确认(2) / 待销方确认(3) → 停住，系统推不动，要人去电子税局确认
         │  ├ 各种作废(5~11) / 申请失败(16) → 失败终态，解锁，可重新申请
         │  └ 申请中(15) / 查不到           → 保持原状态，等下次
         ▼
第3步  调【快捷冲红】拿红票流水号 ── 两个分叉
         │  ├ 税局【已】自动开票 → 服务商按申请时传的订单号修复红票并落库
         │  └ 税局【未】自动开票 → 由它执行开票任务
         ▼  确认单编号/uuid 还没回来 → 本次跳过、不报错，等下次
第4步  查【发票详情】拿红票号码 ── 四个分叉
         │  ├ 开票完成(2) / 签章失败(24) → 落地红票号码/代码/日期 + 存红票附件
         │  ├ 开票中(20)/签章中(21)/开票失败(22)且有失败原因
         │  │     └ 按原流水号/订单号走开票重试一次；重试成功则用重试接口的返回落地
         │  ├ 开票中/失败但没有失败原因 → 只记原因，保持冲红中，等下次
         │  └ 查不到(税局还没生成)        → 等下次
         ▼
第5步  redStatus=99 冲红完成 → 自动解除与开票申请的挂靠、重算费用(见 2.3)
```

**正常情况是"一次点击走完"**：购方还没勾选抵扣、没入账时确认单就是「无需确认」，提交后立即生效、税局随即自动开红票，两条推送在几秒到几分钟内先后到达，全程不用人管。「查询冲红结果」是推送漏了或购方迟迟不确认时的兜底，**不是每次都要点**。

**但界面不能承诺"点一下就冲红完成"**：点完「冲红」同步返回的 `redStatus` 是 15、红票号是空的，红票号码与附件都是后续异步回填的。要么等推送后刷新，要么轮询一次查询。

### 2.2.1 点「冲红」时会被当场拒绝的情况

| 校验 | 提示 |
| --- | --- |
| 没选冲红原因 | 请选择冲红原因 |
| 还没通过接口开出发票（开票状态不是开票完成/签章失败） | 该发票开出还没有通过接口开出发票，不能冲红 |
| 没有发票号 | 该发票开出没有发票号，不能冲红，请先查询开票结果 |
| 已在冲红中或已冲红 | 已冲红(红票号 xxx)，不能重复冲红／正在冲红中，请勿重复申请 |
| 客户开票信息没抬头 | 取不到客户开票信息的抬头，无法作为购方申请冲红 |
| 所属公司缺税号或 appKey/appSecret | 公司[xxx]未维护统一社会信用代码…／未维护开票应用的 appKey/appSecret |
| 取不到蓝票的20位数电票号码 | 取不到蓝票的数电票号码，无法申请冲红 |

### 2.2.2 确认单状态的五个分叉

| 确认单状态 | 系统怎么做 | 这条发票开出能不能改 |
| --- | --- | --- |
| 无需确认(1)、双方已确认(4) | 自动往下走，去开/认领红票 | 锁定，只能查询 |
| 待购方确认(2) | **停住**，等购方去电子税局确认；超72小时未确认自动作废 | 锁定，只能查询 |
| 待销方确认(3) | **停住**，等销方去电子税局确认（本系统只发起销方申请，这个状态只会查到） | 锁定，只能查询 |
| 各种作废(5~11)、申请失败(16) | 失败终态，界面显示失败原因 | **解锁**，「冲红」按钮重新可用，可再申请一次 |
| 申请中(15)、查不到 | 保持不动，等下一次推送或手动查询 | 锁定，只能查询 |

> **②这一步系统推不动**：是否需要购方确认由税局按开票时间、购方是否已勾选抵扣/已入账等规则判定，本系统无从预知，只能查。界面上把 `redStatusText` 直接显示出来即可，它已经写清了下一步该做什么。

### 2.2.3 谁在推进这些步骤

| 触发源 | 说明 |
| --- | --- |
| 【确认单推送】`operater=confirmCallback` | 确认单状态每次变更都推，是最主要的推进源 |
| 【开票推送】`operater=callback` | 红票开出后推，按红票号命中红票分支 |
| 人工点「查询冲红结果」 | 兜底，走同一段代码，行为一致 |

两种推送**打的是同一个回调地址**，靠 `operater` 与字段名区分（开票推送是 `c_` 前缀键，确认单推送是驼峰键）。所以**正常一次冲红会收到至少两条推送，不是一条**。

推送只当触发器用，收到后仍然去查确认单、查发票详情，以查询结果为准写库。任何一步重复执行都是幂等的：状态到 99 后不会被推回去、红票号只增不清、附件按文件名去重。

## 2.3 冲红完成后会发生什么（重要，测试必看）

红票落地时系统会自动做三件事：

1. **软删**这张发票开出的全部挂靠明细（`InvoiceIssueItem`）
2. 关联开票申请 `Status` 退回 `待审核(已提交)`、`InvoiceNo` 清空 → **重新出现在"可开票的申请列表"里**
3. 重算这些申请所关联费用的开票状态与已开票金额 → 费用自动退回未开票/部分开票

发票开出这条记录**保留**（蓝票号 `invoiceNo` 与红票号 `redInvoiceNo` 都还挂在上面），只是不再挂着申请，且已被红冲状态锁死、不能再改。详情页会出现"已冲红 + 关联申请为空"，这是正常的，不是数据异常。

# 3. 状态流转说明 (Status Transitions)

## 3.1 开票方式 `InvoiceIssueType`

| 值  | 含义     | 说明                                                  |
| :-- | :------- | :---------------------------------------------------- |
| `0` | 接口开票 | 走本模块开票                                          |
| `1` | 手动记录 | 人工在别处开票后录号，本模块的开票状态恒为 `0 未开票` |

| 当前 | 触发 | 目标 | 说明 |
| :-- | :-- | :-- | :-- |
| 手动记录 | 点"开发票"并**受理成功** | 接口开票 | **不校验开票方式**，手动记录也能走接口开；受理失败时保持原样 |

## 3.2 接口开票状态 `IssueStatus`

`2/3/20/21/22/24/31` 直接沿用服务商发票详情查询接口的 `status`，便于对账；`0/1` 是本地状态。

| 值 | 含义 | 终态 | 只能查询 | 界面建议 |
| :-- | :-- | :-- | :-- | :-- |
| `0` | 未开票（没调过接口） | — | 否 | "未开票"，可开票、可编辑删除 |
| `1` | 已提交待开票 | — | **是** | "开票中…" |
| `20` | 开票中 | — | **是** | "开票中…" |
| `21` | 开票成功签章中 | — | **是** | "签章中…" |
| `2` | 开票完成 | ✅ | **是** | "已开票"（绿）+ 发票号 + 附件 |
| `24` | 开票成功签章失败 | ✅ | **是** | "签章失败"（橙）——**票已开出来了**，发票号有值 |
| `22` | 开票失败 | ✅ | 否 | "开票失败"（红）+ 失败原因，**可编辑可删除** |
| `3` | 已作废 | ✅ | **是** | "已作废"（灰）。本系统无作废流程，只有别处作废后查回来才出现 |
| `31` | 发票作废中 | — | **是** | "作废中…" |

## 3.3 红冲状态 `RedStatus`

`1~9 / 15 / 16` 沿用服务商红字确认单查询接口的 `billStatus`（去前导零）；`0` 与 `99` 是本地状态。

| 值 | 含义 | 类别 | 界面建议 |
| :-- | :-- | :-- | :-- |
| `0` | 未冲红 | 初始 | 不显示冲红标签 |
| `15` | 红字确认单申请中 | 进行中 | "冲红申请中…" |
| `1` | 无需确认（确认单已生效） | 进行中 | "冲红中·确认单已生效" |
| `2` | 销方录入待购方确认 | 进行中 | **醒目提示联系购方，超72小时未确认自动作废** |
| `3` | 购方录入待销方确认 | 进行中 | 提示去电子税局确认 |
| `4` | 购销双方已确认 | 进行中 | "冲红中·已确认，待开红票" |
| `5` | 作废（销方录入购方否认） | **失败终态** | "冲红失败"+原因，**可重新冲红** |
| `6` | 作废（购方录入销方否认） | **失败终态** | 同上 |
| `7` | 作废（超72小时未确认） | **失败终态** | 同上 |
| `8` | 作废（发起方已撤销） | **失败终态** | 同上 |
| `9` | 作废（确认后撤销） | **失败终态** | 同上 |
| `16` | 红字确认单申请失败 | **失败终态** | 同上 |
| `99` | 冲红完成（红票已开出） | 终态 | "已冲红"+红票号+红票附件 |

**失败终态会解除冲红锁定**：确认单作废等于冲红没发生，这张蓝票在税局那边还有效，可以重新申请冲红。但此时 `editLocked` 仍为 `true`（蓝票还在），编辑删除依旧不放开。

## 3.4 冲红原因 `RedReason`

`1` 销货退回、`2` 开票有误、`3` 服务中止、`4` 销售折让。**必填，界面必须让用户选，不要默认或写死。**

## 3.5 费用开票状态与开票申请状态的联动

| 当前 | 触发 | 目标 |
| :-- | :-- | :-- |
| 费用 未开票 | 新建发票开出并挂上该申请 | 部分开票 / 已开票 |
| 费用 已开票 | 从发票开出移除该申请 / 删除发票开出 | 部分开票 / 未开票 |
| 费用 已开票 | 该发票开出**冲红完成** | 部分开票 / 未开票（挂靠被解除） |
| 开票申请 待审核 | 被发票开出挂上 | 已开票 |
| 开票申请 已开票 | 移除 / 删除发票开出 / **冲红完成** | 待审核 |

## 3.6 组合状态 `CombinedStatus`（列表/详情出参与列表筛选）

两个原枚举取值有重叠（例如两边都有 `2`），合到一个下拉里必须把冲红段整体平移 **+100**。

**计算公式**：`RedStatus == 未冲红` 时返回 `IssueStatus`；否则返回 `RedStatus + 100`。

未冲红（`0`）不会作为组合值返回——没冲过红时返回的是开票状态本身。因此 **没有 `100`**。

| 值 | 含义 | 来源 |
| :-- | :-- | :-- |
| `0` / `1` / `2` / `3` / `20` / `21` / `22` / `24` / `31` | 同 3.2 开票状态 | 仅当 `RedStatus=未冲红` |
| `101`～`104` | 无需确认 / 待购方 / 待销方 / 双方已确认 | `RedStatus` 1～4 + 100 |
| `105`～`111` | 各种作废 | `RedStatus` 5～11 + 100 |
| `115` / `116` | 申请中 / 申请失败 | `RedStatus` 15 / 16 + 100 |
| `199` | 冲红完成 | `RedStatus` 99 + 100 |

列表筛选：`combinedStatus` 单值、`combinedStatuses` 多选。一组内部多个值是 OR；单值与多选同时传是 AND。

> 筛 `2` = 开票完成且从未冲红。已冲红完成的票是 `199`，不会出现在 `2` 里。「开票中」传 `1/20/21`；「冲红中」传 `115/101/102/103/104`。

# 4. 核心字段说明 (Field Definitions)

## 4.1 `App_InvoiceIssues`（发票开出）——接口开票

| 字段名 | 📖 含义 | 🔌 数据来源 | 🔗 联动 | 🛡️ 校验/说明 |
| :-- | :-- | :-- | :-- | :-- |
| **InvoiceIssueType** | 开票方式 | 录入 / 系统改写 | 受理成功后自动置 `0` | — |
| **IssueStatus** | 接口开票状态 | 服务商返回 | 决定 `editLocked` | 手动记录恒为 `0` |
| **IssueOrderNo** | 提交给服务商的订单号 | 由发票开出Id派生 | 回调按它定位 | 同一销方税号下不可重复、≤20位 |
| **IssueSerialNum** | 开票流水号 | 受理时返回 | 查询与回调都靠它 | — |
| **IssueRequestTime** | 提交开票请求的时间 | 系统 | — | — |
| **IssueFailCause** | 开票失败原因 | 服务商返回 | — | 只记**异步阶段**的失败；提交阶段失败直接抛给操作人 |
| **InvoiceNo** | 发票号 | 服务商返回 | 回填到关联开票申请 | 电票=20位数电票号码；纸票=8位纸票号码 |
| **InvoiceCode** | 发票代码 | 服务商返回 | 纸票冲红要用 | **电票恒为空**，纸票12位 |
| **InvoiceIssueTime** | 开票时间 | 服务商返回（毫秒时间戳） | — | — |

## 4.2 `App_InvoiceIssues`（发票开出）——冲红

| 字段名 | 📖 含义 | 🔌 数据来源 | 🛡️ 说明 |
| :-- | :-- | :-- | :-- |
| **RedStatus** | 红冲状态 | 确认单查询接口 | 见 3.3 |
| **RedReason** | 冲红原因 | 操作人选择 | 必填 |
| **RedBillId** | 红字确认单申请号 | 本地生成后提交 | 后续查确认单靠它 |
| **RedBillNo** | 红字确认单编号 | 确认单进税局后返回 | 纸票开红票必传 |
| **RedBillUuid** | 红字确认单uuid | 同上 | 纸票开红票必传；内部标识，一般不展示 |

| :-- | :-- |

## 4.5 发票附件

开票/冲红完成后**服务商返回几个文件地址就存几个**，挂在 `ModuleTypeId=160090` / `ItemId=发票开出Id`，`ClientVisible=true`。

| 附件名 | 性质 |
| :-- | :-- |
| `{发票号}.ofd` | **法定原始凭证**，入账归档用 |
| `{发票号}.xml` | 税局原始数据格式，对接财务/税务归档系统用 |
| `{发票号}.pdf` | 版式转换产物，**不能作原始凭证**，只用于查看/打印/发客户 |
| `{发票号}-纸质.pdf` | 含底图的纸票打印版（本系统只开电票，实际不会出现） |
| `{发票号}-{8位哈希}.jpg` | 发票图片；多张时用地址哈希区分，不用序号 |

冲红完成后同一套文件，只是发票号换成红票号。**同一条发票开出下的附件是一个扁平列表、不分组**，蓝红靠文件名里的发票号区分（蓝票号 / 红票号）。

⚠️ **这几种格式不是都会有**：哪些地址有值由服务商侧的企业资质配置决定（文档原话：xml 是"企业配置成支持获取xml时返回"、ofd 是"公共服务平台签章及数电电票时返回"），沙箱环境更可能只给一两个。 **前端按实际返回渲染，不要写死假设有 PDF。**

**开票申请**（`InvoiceApplicationAdmin`）的列表与详情也返回 `attachments`，内容是它所挂那张发票开出下的附件，同样不分组；申请没挂发票开出时为空；冲红解绑后也会消失。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **卡点 1：开票报文一发出去，发票开出就只能查询** 判定：`IssueStatus` 不是 `0 未开票` 也不是 `22 开票失败`，**或**处于冲红中/已冲红。命中后 `editLocked=true`，编辑、仅改主表、加挂/移除开票申请、删除、重新开票**全部拒绝**。注意是"报文发出去"不是"开完票"——`1 已提交待开票`、`20 开票中`、`21 签章中` 一样锁，因为报文已经在税局那边了，本地再改就与那张票对不上。 `22 开票失败` 故意留开：订单号按Id派生固定不变，失败后重开会被 `E9106 订单号重复` 挡死， **唯一的恢复路径就是删掉重建**，锁上就没法恢复了。手动记录方式 `IssueStatus` 恒为 `0`，这条规则对手工录票没有任何影响。

> [!IMPORTANT] **卡点 2：不可能重复开票** 提交给服务商的订单号 = 发票开出Id的前20位十六进制，**同一条记录每次算出来都一样**。万一请求已经发出去、税局也开了票，但本地没记下来（HTTP超时/进程回收/事务回滚），重试用的还是同一个订单号，会被 `E9106` 直接挡住，**结构上不可能开出第二张**。这时改用"查询开票结果"按订单号问服务商那张票到底开没开即可。红票订单号带 `R` 前缀（十六进制里不会出现 R），与蓝票订单号不可能相同。

> [!IMPORTANT] **卡点 3：冲红只做全额冲红、只做销方发起** 不传明细即全额冲红。业务上要部分冲红，正确做法是全额冲红后重新开一张。购方发起的确认单（状态 `3`）本系统只会**查到**、不会**发起**，需要销方去电子税局确认。撤销确认单也没接，发错了只能去电子税局撤销，撤销后系统查到 `8`/`9` 会自动解锁、可重新申请。

> [!IMPORTANT] **卡点 4：费用"已开票"看的是挂靠关系，不是状态字段** 一条费用算不算已开票，看它的开票申请**有没有真的挂在某张发票开出上**（存在未删除的 `InvoiceIssueItem`），而不是看 `InvoiceApplication.Status`。所以：
>
> - 发票开出一建好、申请一挂上，费用立刻算已开票（**此时还没有发票号**，这是有意的）；
> - 移除申请、删除发票开出、冲红解绑，费用自动退回，不依赖任何人记得同步状态。 `开票失败` 的发票开出仍占着这些申请，费用仍算已开票——因为那些申请确实挂不到别的发票开出上，显示成"未开票"反而会诱导用户去开票然后被拦。清理掉那条失败记录即可释放。

> [!IMPORTANT] **卡点 5：回调直接落地，认不出来才回查（2026-08-18 起）** 拿到服务商给的回调字段说明后，改成**推送本身就能落地**，不再无条件回查一次发票详情。依据是 `c_status` 的三个取值**全是终态**：`1` 开票完成、`2` 开票失败、`3` 开票成功签章失败(电票)， **没有开票中/签章中这类中间态**，所以不存在"把中间态误判成开票完成"的风险；失败时 content 只返回 发票流水号、发票状态、销方税号、失败原因 四个字段，**失败原因也在推送里**。
>
> ⚠️ **回调的 `c_status` 与【发票详情查询接口】的 `status` 是两套不同的编码，别搞混**：
>
> |  | 字段 | 取值 | 为什么 |
> | :-- | :-- | :-- | :-- |
> | 查询接口 | `status` | `2` 开票完成 / `20` 开票中 / `21` 签章中 / `22` 开票失败 / `24` 签章失败 / `3` 已作废 / `31` 作废中 | **能随时调用**，所以必须能表达中间态。这套就是 `InvoiceIssueStatus`，原样入库不转换 |
> | 回调 | `c_status` | `1` 开票完成 / `2` 开票失败 / `3` 签章失败 | **只在票走到终态时才推送**，所以只需要三个值 |
>
> 最要命的是 **`2` 在两套里含义正好相反**（回调=开票失败，查询=开票完成），没法靠值判断是哪套，**只能靠字段名**。换算只在 `BuildResultFromCallback` 一处做， **别在别处直接拿 `c_status` 当开票状态用**。
>
> 仍会回查的两种情况：
>
> 1. **推送里没有 `c_status`**——该字段只在"企业资质-开票失败是否回调"为是时才返回，认不出状态就回查；
> 2. **失败推送读不到失败原因**——服务商没给失败原因的键名，代码里试了几种常见写法，都读不到就回查，避免界面上只有一个"开票失败"没法排查。
>
> 红票推送不走这条捷径：冲红要的是**红字确认单状态**，那不在开票回调里，仍走查询。

> [!IMPORTANT] **卡点 6：令牌是人工维护的固定值，系统绝不自动取号（2026-08-28 起）** 服务商官方口径：同一应用 **30 天内取号超过 50 次会被判定为攻击、直接锁死开不出票**，而且只能由服务商人工重置。
>
> 所以令牌改成向服务商索取一次、填在**公司资料的开票令牌**（组织表 `InvoiceAccessToken`）里长期使用，与 appKey/appSecret 放一起。
>
> **令牌失效(070301)时不会自动重取**，而是直接报错："开票令牌已失效…请向开票服务商索取新令牌，并更新到公司资料的开票令牌里"。这是刻意的：代价不对称——**锁死账号 ≫ 这张票先开不出来**。原来那套"两级缓存 + 失效自动重取"看着省次数，但只要出现一次 "令牌被判失效 → 自动重取 → 又失效" 的循环，几分钟就能把 50 次烧光并锁死账号。
>
> 原自动取号实现（内存 + 数据库两级缓存）在 `NuonuoTokenProvider` 里整段注释保留， `App_NuonuoAccessTokens` 表也留着没删，万一服务商放开限制可直接恢复。配置项 `Nuonuo:TokenUrl` 目前已不再使用。

> [!IMPORTANT] **卡点 7：只传分机号、不传开票员，分机号按人维护（2026-09-01 起）** 与服务商确认过：**报文里只传分机号，服务商会按分机号自动匹配开票员**，所以系统不传开票员。
>
> 不传是有好处的：`clerk` 传了就要求与该开票账号的开票员姓名**完全一致**，对不上直接开票失败。那等于把"系统里的用户昵称"和"服务商侧的开票员姓名"绑成一条必须人工对齐的隐性约定，谁改个昵称就能把开票搞崩。交给服务商按分机号匹配，这条约定就不存在了。
>
> **开票员的代码没删**：`ResolveClerkAsync()` 与组报文处的 `Clerk = clerk` 都原样注释保留着，服务商日后若又要求传，解开两行注释即可，不用重新实现。
>
> 分机号从原来的全局配置 `Nuonuo:ExtensionNumber`（全公司一个值）改成**按人维护**：用户表新增 `ExtensionNumber`（`int` 可空——服务商规定只能是数字，就直接用数字类型，不做"字符串 + 正则校验"那一套），开票时取**当前登录人**的分机号， **有值才传，没值就不带这个字段**——分机号不是必传项，不带则服务商按企业默认开票员处理，不该因为某个人没维护分机号就拦住开票。
>
> 回调链路里（如冲红时调快捷冲红）"当前登录人"是该发票开出的创建人，取到的就是他的分机号。

> [!IMPORTANT] **卡点 8：查询红票失败时走开票重试（2026-09-02 起）** 查发票详情后本地 `redFailCause` 有值（常见如税局回「需登录电子发票服务平台」），说明这次红票没开成。 `QueryRedResultAsync` / 回调推进到这一步时，按**原流水号或订单号**调开票重试（`nuonuo.OpeMplatform.reInvoice`），号与失败那次一致，一次查询只重试一次。
>
> **重试接口成功时以它的返回落地**：带回发票号/状态就按这次结果写红票字段、存附件；只是受理、没有发票信息则保持原来的失败原因，等回调或下次查询。重试本身失败只记日志，不把整次查询冲掉。确认单作废等失败终态不会走到这一步。

## 6.1 全局（`appsettings.json` 的 `Nuonuo` 节点）

| 键 | 说明 | 上正式要改成 |
| :-- | :-- | :-- |
| `BaseUrl` | 业务接口地址 | `https://sdk.nuonuo.com/open/v1/services` |

| `CallbackAllowedIps` | 回调来源IP白名单，逗号分隔，留空=不校验 | 服务商回调IP（沙箱实测 `61.164.41.82`） |

`CallbackBaseUrl` **只填 IP+端口**，接口路径由代码用常量拼（`/api/invoice-issue/callback`），控制器路由引用同一组常量，**路径改一处两边同时生效**，不会出现配置写的地址和实际路由对不上。

## 6.2 按公司（公司资料界面维护）

InvoiceAppKey、InvoiceAppSecret、InvoiceAccessToken、UnifiedSocialCreditCode。**每家要开票的公司都要单独维护。**

其中 InvoiceAccessToken 要向服务商索取，是固定值；系统不会自动获取，失效了要人工来这里换。

## 6.3 按人（用户资料界面维护）

`AbpUsers.ExtensionNumber` 开票分机号，`int` 可空。**不是必填**：没维护的人照样能开票，只是报文里不带分机号、由服务商按企业默认开票员处理。要让发票落到指定开票员名下才需要维护。

## 6.4 上线检查清单

1. 全局配置 4 项按上表改完
2. 每家开票公司的 appKey/appSecret/令牌/税号维护到位
3. 完整回调地址报给服务商确认放行，并确保**公网可达**
4. 需要区分开票员的操作人，把服务商分配的分机号维护到用户资料（不维护也能开票，见 6.3）
5. 发票商品编码维护好"税收分类编码"（不传会报 `E9138`）
6. 客户开票信息维护抬头/税号，结算客户维护邮箱

| ~~`App_NuonuoAccessTokens`~~ | **已停用**：令牌改为人工维护在公司资料里，本表不再写入（表结构保留） |
| 发票开出 `IssueFailCause` / `RedFailCause` | 服务商返回的失败原因 |
| 发票开出 `IssueSerialNum` / `IssueOrderNo` / `RedBillId` | 拿去服务商工作台或电子税局对账 |
| 应用日志 `发票版式文件存附件失败` | 某个文件下载失败，日志里带文件名与地址 |
| 应用日志 `开票结果里没有任何版式文件地址` | 服务商一个文件地址都没给，多半是企业资质没开版式文件 |

排查顺序建议：先看 `App_NuonuoPushLogs` 的 `Success` 和 `Remark`，不用一上来就啃 `RawJson`。 `RawJson` 是 `application/x-www-form-urlencoded`、`content` 里是 URL 编码的 JSON，看之前要先解码。

## 8.2 常见错误码

| 码 | 原因 | 处理 |
| :-- | :-- | :-- |
| `E9302` | 公参 `userTax` 与私参 `salerTaxNum` 不一致 | 本实现两处同一个变量，出现说明配置被改坏了 |
| `E9301` | 销方税号在服务商没有企业资质 | 沙箱要用测试税号；正式找航信开资质 |
| `E9106` | 订单号重复 | 见卡点 2，改用"查询开票结果"确认那张票开没开 |
| `E9138` | 商品编码没传 | 发票商品编码要维护"税收分类编码" |
| `E9309` | 购方手机号不能为空 | 企业资质里设成了必填，维护 `ClientInvoiceInfo.Mobile` |
| `E9500` | 发票不存在 | **不当异常**：开票刚受理、服务商还没落库时就是这个码，属于"还没好" |
| `070301` | 令牌过期或不匹配 | **不会自动重取**。向服务商索取新令牌，更新到该公司资料的开票令牌里 |
| `070101` | appkey 无效 | 公司的 `InvoiceAppKey` 填错；沙箱要用 SD 开头那组 |
| `070601` | 签名不匹配 | appKey/appSecret 配对错了，或密钥里混进了不可见字符 |
| `9999` | 风险监控/实人认证，或「需登录电子发票服务平台」 | 去服务商网页做登录/认证。查询冲红若因此失败（`redFailCause` 有值），会按原流水号走开票重试，成功则以重试返回落地（见卡点 8） |

## 8.3 状态卡住了怎么判断

| 现象 | 判断 |
| :-- | :-- |
| `issueStatus` 长期停在 `1` | 查 `App_NuonuoPushLogs` 有没有回调进来；手动点一次"查询开票结果" |
| `redStatus` 停在 `2` | **不是系统问题**，在等购方在税局端确认，超72小时会自动作废 |
| `redStatus` 停在确认单已生效，`redFailCause` 有值 | 再点一次「查询冲红结果」。后端会按原流水号走开票重试；成功则用重试返回落地，本次不一定立刻变成冲红完成 |
| 附件只有 OFD 没有 PDF | 先手动查一次（会自动补下载）；仍没有就是服务商侧没给 `pdfUrl`，找航信确认企业资质开了哪些版式文件 |
