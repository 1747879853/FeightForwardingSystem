# 1. 业务背景说明 (Background)

**白话解释：** 一票货的每条费用，要么是我方收客户的钱（应收），要么是我方付供应商的钱（应付）。两种钱都要有发票，但发票的方向和流程完全相反：

|            | 应收侧                 | 应付侧                          |
| :--------- | :--------------------- | :------------------------------ |
| 谁开票给谁 | **我方开给客户**       | **对方开给我方**                |
| 载体单据   | 开票申请 → 发票开出    | 付费申请（发票流程 + 发票子表） |
| 发票号来源 | 开票系统实际开出后回填 | 人工录入对方给的发票            |
| 是否走审核 | 开票申请有状态流转     | 付费申请有审核工作流            |

**同一笔钱只能开一次票。** 一条费用如果已经在应付侧取得了对方的发票，就不该再从应收侧开票给客户，反之亦然。这条约束是整套额度计算的出发点。

# 3. 状态流转说明 (Status Transitions)

## 3.1 发票流程 `InvoiceProcess`（付费申请必填）

| 值 | 含义 | 发票子表要求 | 卡在哪 | 是否视为「已取得发票」 |
| :-- | :-- | :-- | :-- | :-- |
| `0` | 先票后付 | **提交前必须有至少一条**，录入阶段可为空 | **仅提交** | 子表有记录才算**是**，为空算**否** |
| `1` | 先付后票 | 不限制 | — | 同上 |
| `2` | 不开票 | **必须为空** | 新增/编辑/仅编辑发票 | **否**（且永远不会有） |

**两条规则刻意卡在不同时机**，别再往一处合：

| 规则 | 校验方法 | 时机 | 为什么 |
| :-- | :-- | :-- | :-- |
| 先票后付必须有发票 | `ValidateInvoiceRequiredOnSubmit` | **只在 `SubmitAsync`** | 这只是「还没填完」。先建单、等拿到对方发票再回来补录是正常节奏，卡在录入会逼着用户为了存草稿去编假发票号 |
| 不开票不能有发票 | `ValidatePaymentApplicationInvoices` | 新增/编辑/仅编辑发票 | 这是**自相矛盾**，不是中间态。而且「已取得发票」只看子表有没有记录（见 4.1），放过这种数据会让不开票的草稿把费用算成已开票、连带顶高落库的 `InvoiceStatus` |

行内格式校验（发票号必填、不超长、同一申请下不重复）三个录入入口照旧每次都卡。

## 3.2 费用开票状态 `InvoiceStatus`

由「费用金额」与「已开票量」推出，全项目只有 `InvoicedAmountRule.ResolveInvoiceStatus` 一个算法：

```csharp
if (invoicedAmount == 0M) return InvoiceStatus.NotIssued;
return feeAmount - invoicedAmount == 0M ? InvoiceStatus.Issued : InvoiceStatus.PartiallyIssued;
```

判「已开票」用 `feeAmount - invoicedAmount == 0` 而不是 `>=`，是为了兼容负数金额（冲红）的费用：正负号一致时「剩余为 0」即完全开票，与方向无关。

## 3.3 开票申请状态 `InvoiceApplicationStatus`

`0` 录入 → `1` 审核中 → `2` 驳回 / `3` 已开票（通过后直接开，通过了不能驳回）。

> **注意：判断一条开票申请明细算不算「已开票」，看的不是这个状态，而是它所属申请有没有真的挂在某张发票开出上。** 理由见 4.1。

# 4. 两个核心金额 (Core Amounts)

两个金额都由 `IOrderFeeInvoicedProvider` **统一出口**，全项目禁止各处自己写聚合。

## 4.1 已开票量 `InvocedAmount`

```
已开票量 = 应收侧已挂发票开出的开票申请明细金额之和
         + 应付侧「已取得发票」的付费申请明细金额之和
```

**应收侧看挂靠、不看状态。** 遍历方向是 发票开出 → 挂靠明细 → 开票申请 → 开票申请明细 → 费用。为什么不看 `InvoiceApplicationStatus`：状态是冗余标记，挂靠才是事实。两者一旦不同步（漏改、并发、异常中断），看状态就会算出与发票开出对不上的金额。改看挂靠后，发票开出那边加挂/移除/删除/冲红解绑，费用金额天然跟着变。

**应付侧只看发票子表有没有记录，与发票流程无关**：子表非空即计入，为空计 0。

不要拿 `InvoiceProcess = 先票后付` 当「已有票」的替身——该流程的发票必填只卡在提交（见 3.1），录入阶段完全可以是空的，拿流程判定会把没票的草稿算成已开票。反过来，「不开票 + 子表有票」这种自相矛盾的数据由录入阶段的校验挡住，所以这里不必再判流程。

方法：`GetInvoicedAmountMapAsync`

## 4.2 发票申请量 `OrderInvoiceAmount`

```
发票申请量 = 应收侧全部状态的开票申请明细金额之和（不要求已挂发票开出）
           + 应付侧全部付费申请明细金额之和（三种发票流程一律计入）
```

与已开票量的区别是**不看开票结果、只看是否已处理开票事宜**。应付侧三种流程都计入的原因：先票后付与先付后票是「会有票」，不开票是「已确定不开票」，都属于开票事宜已有结论。

方法：`GetOrderInvoiceAmountMapAsync`

## 4.3 未开票量 `UnInvoicedAmount`

```
未开票量 = 费用金额 - 已开票量
```

各处直接现算，随已开票量自动变化，无需单独维护。

## 4.4 为什么这两个金额不落库

它们在全项目没有任何筛选或排序用途，纯展示；实时算的值结构上不可能过期。而 `OrderFee.InvoiceStatus` 要进 WHERE（费用列表筛选、对账单按下属费用汇总），计算值没法分页筛选，所以它必须是冗余列、必须回写。

# 5. 额度体系 (Quota) ⚠️ 最容易搞错的部分

系统里有**两套互不相干的额度**，都以「费用金额」为预算，但参与扣减的项不同。**混用会算错钱。**

## 5.1 发票额度（决定还能不能开票）

```
开票剩余额度 = 费用金额 - 开票申请已申请 - 付费申请已申请
```

**不扣收费结算。** 收费结算是资金结算，与发票无关；发票只有开票申请与付费申请两侧。（下限有一个例外，见 5.3。）

## 5.2 资金额度（决定还能不能申请付款/结算）

```
资金剩余额度 = 费用金额 - 付费申请已申请 - 收费结算已结算 - 开票申请已申请
```

三池共享一个预算。付费申请与收费结算的选费用列表、额度校验都用这个口径。

## 5.3 上下两个边界的基数不同（冲红陷阱）

开票申请的金额允许为负（冲红）。校验有上下两个边界，**基数不同，不能用同一个值**：

| 边界 | 基数 |
| :-- | :-- |
| 可申请**上限** | 费用金额 − 开票申请已申请 − **付费申请已申请** |
| 冲红**下限** | −开票申请已申请（**不含应付侧**） |
| 冲红**下限 2**（2026-10-02） | 已按发票收费结算 − 开票申请已申请：冲红后开票申请合计不能低于已按发票收费结算 |

如果把应付侧算进冲红下限，就会允许开票申请把付费申请占用的额度冲红掉。所以校验时必须用 `GetPayableInvoiceAppliedMapAsync` 单独取应付侧减，**不能图省事用 `GetOrderInvoiceAmountMapAsync` 的合并值**。

**下限 2 是收费结算唯一参与发票额度的地方。** 资金额度（5.2）扣的是开票申请已申请，不扣按发票收费结算，它默认按发票结掉的钱都在开票申请占用里。开票申请合计一旦被冲到按发票已结以下，差额就会被按费用收费结算、付费申请再放出来，同一笔钱结两次。所以：

- 开票申请新增、编辑、追加明细时按下限 2 校验本次金额；编辑去掉费用、移除明细、删除申请时，按它校验移除后的合计（只查已按发票结算过的费用）。
- 只认按发票结算（`ReceiveSettlementInvoiceItem`），按费用收费结算不算，所以只按费用结算过的费用，下限 2 就等于原下限。
- 另一头由收费结算守：按发票结算时同一费用合计不能超过「开票申请已申请 − 已按发票结算」。详见《收费结算模块总逻辑文档》卡点 15。

**负数费用（2026-10-02）**：金额为负的费用（折扣、返利等）可以开票，上面三个边界按费用方向取反（`OrderFeeSettlementHelper.FeeSign`）：上限变成「最多申请到费用金额为止」（−100 的费用最多填 −100），冲红下限变成「合计不能冲成正数」，下限 2 比绝对值。选费用列表返回剩余与费用同号且不为 0 的费用。负数费用只在费用明细里抵减：提交时整张申请折算合计须 > 0、商品明细每行须 > 0，开出的发票不会是负数。

## 5.4 相加为什么不会超过费用金额

两侧的额度校验现在互相扣减，形成闭环：

- 付费申请侧：`费用金额 - 付费申请 - 收费结算 - 开票申请`，已扣开票申请；
- 开票申请侧：`费用金额 - 开票申请 - 付费申请`，已扣付费申请。

所以 `开票申请已申请 + 付费申请已申请 ≤ 费用金额` 是**代码保证的不变式**，展示层不需要做 `Min` 截断。

> 历史上开票申请侧只扣自己、不扣付费申请，存在「先做付费申请 100，再做开票申请 100」突破预算的顺序。已于 2026-09-04 补齐。

# 7. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **卡点 1：禁开发票的费用不能开票** `OrderFee.InvoiceBlocked = true` → 不出现在开票申请选费用列表，写入时报「费用不允许开票」。

> [!IMPORTANT] **卡点 2：应付侧已占用的额度不能再开应收票** 费用已被付费申请占用时，开票剩余额度相应减少；占满后该费用**不再出现**在开票申请的选费用列表里。

> [!IMPORTANT] **卡点 3：先票后付「提交前」必须录发票，不开票任何时候都不许录发票** 见 3.1。先票后付**只在提交时**卡，报「发票流程为先票后付时 提交前必须录入发票信息」，录入阶段可以先存着；不开票在新增/编辑/仅编辑发票三处都卡，报「发票流程为不开票时 不能录入发票信息」。

> [!IMPORTANT] **卡点 4：申请修改/申请删除审核中的费用不参与开票** 审核通过后金额会变或费用被删，这时拉进开票申请会导致申请金额失真。

# 9. 避坑指南 (Pitfalls)

- **不要自己写 `InvoiceApplicationItem` 聚合。** 现在应付侧也计入两个金额，自己聚合必然漏。全部走 provider。
- **发票额度与资金额度不能混用。** 发票额度不扣收费结算，资金额度扣。看到 `费用金额 - 三项` 的表达式，先确认它是资金池还是发票池。
- **冲红下限不能含应付侧**（见 5.3），否则开票申请能把付费申请的额度冲红掉。
- **冲红、改小、移除、删除开票申请都不能让合计低于已按发票收费结算**（见 5.3 下限 2），否则按费用收费结算、付费申请会把同一笔钱再结一次。新增会减少开票申请金额的入口时，记得接上这条校验。
- **删除发票开出时必须同步软删 `InvoiceIssueItem`。** 残留的孤儿挂靠明细会让费用一直被算成已开票。发票开出的删除逻辑里已经这么做了，别改掉。
- **付费申请的发票信息一变就要重算 `InvoiceStatus`。** 它是落库冗余列，不重算就会锈在旧值上，而费用列表筛选和对账单汇总都读它。
- **新增「不经过发票录入的建单入口」时必须显式给 `InvoiceProcess`。** 枚举默认值 `0` 是先票后付，不显式赋值会让单据一落地就是先票后付且没有发票——现在录入阶段不再拦（校验挪到了提交），所以单子能建成功，但**提交时才报错**，用户到了最后一步才发现要去补发票。`AddByStatementAsync` 已踩过这个坑，固定给了先付后票。
- **「已取得发票」的判定只能看子表，不能看发票流程。** 先票后付的发票必填只卡在提交，录入阶段是空的；拿流程当替身会把没票的草稿算成已开票。这一条与上一条是同一个根因：`InvoiceProcess` 只表示**意图**，不代表**事实**。
- **口径变更后存量 `InvoiceStatus` 需要刷一次。** 建议批量调 `RecalcByOrderFeesAsync` 而不是手写 SQL，保证与代码口径一致。
