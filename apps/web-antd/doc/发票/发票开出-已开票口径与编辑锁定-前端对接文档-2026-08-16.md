# 发票开出-已开票口径与编辑锁定（前端对接）

**没有新增接口，没有新增权限，没有删改任何已有字段。** 本次是 **1 个新出参字段** + **1 条新的禁用规则** + **一批金额口径变化（前端无需改代码，但要知道数字会变）**。

> **新字段**：`editLocked` —— 发票开出列表与详情都有，`true` 表示这条只能查询。 **新规则**：接口开票**发出去之后**（不只是开完），发票开出禁止编辑与删除。 **口径变化**：费用的"已开票金额 `invoicedAmount`"与"开票状态 `invoiceStatus`"改为按【发票开出】统计。

---

## 一、`editLocked`：什么时候只能查询

`InvoiceIssueListDto`（`GetPagedListAsync`）与 `InvoiceIssueDetailDto`（`DetailAsync`）都新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `editLocked` | `bool` | **只能查询**。为 `true` 时，编辑、编辑主表、加挂开票申请、移除开票申请、删除、开发票的按钮**全部禁用** |

它等价于 `issueStatus 不是 0/22` **或** `redLocked === true`，但**请直接用 `editLocked`**，别自己拼这两个条件——后端也是用同一份规则算的，自己拼早晚会漏掉某个状态。

`redLocked` 仍然保留，用来单独区分"是因为冲红被锁的"（比如想在界面上给不同的提示文案）。

### 对照表

| `issueStatus` | `editLocked` | 说明 |
| --- | --- | --- |
| `0` 未开票 | `false` | 还没提交，随便改 |
| `1` 已提交待开票 | **`true`** | ⚠️ **本次新增的拦截**：报文已经发到税局了 |
| `20` 开票中 / `21` 签章中 | **`true`** | ⚠️ 本次新增 |
| `2` 开票完成 / `24` 签章失败 | **`true`** | 原来就禁止删除，本次连编辑也禁止 |
| `31` 作废中 | **`true`** | 原来就禁止删除 |
| `3` 已作废 | **`true`** | ⚠️ 本次新增（原来漏了，能删） |
| `22` 开票失败 | `false` | 税局没有票，可以改、可以删 |

> **手动记录的发票开出不受影响**：`invoiceIssueType === 1` 时 `issueStatus` 恒为 `0`， `editLocked` 只会因为冲红而变 `true`。手工录票的编辑、删除行为完全没变。

### 被拒绝时的提示

按钮该禁用就禁用，不要靠报错兜底。真的调到了，后端返回的是 `UserFriendlyException`，直接弹 message：

| 情况 | 提示 |
| --- | --- |
| 已开出发票 | `发票开出[单号]已开出发票(发票号 xxx)，只能查询，不能编辑或删除，开错了请冲红` |
| 开票中 | `发票开出[单号]已提交开票、正在开票中，只能查询，不能编辑或删除，请稍后查询开票结果` |
| 已作废 | `发票开出[单号]的发票已作废，只能查询，不能编辑或删除` |
| 已冲红 | `发票开出[单号]已冲红，只能查询，不能编辑或删除` |
| 冲红中 | `发票开出[单号]正在冲红中(状态)，只能查询，不能编辑或删除` |

批量删除时会**一次列出所有被挡下的单号与各自原因**，用 `；` 分隔。

## 二、冲红完成后，开票申请会被放开

这是本次的行为变化，界面上要能解释得通：

**一张发票开出冲红完成（`redStatus=99`）后，它关联的开票申请会自动解绑**：

- 该发票开出的 `invoiceIssueItems` / `invoiceIssueApplications` 变成**空**（详情页的"关联开票申请"列表会空掉）
- 那些开票申请的 `status` 退回 `待审核(已提交)`、`invoiceNo` 清空，**重新出现在"可开票的申请列表"里**
- 那批费用的 `invoiceStatus` / `invoicedAmount` 自动退回

发票开出这条记录本身**保留**，蓝票号 `invoiceNo` 与红票号 `redInvoiceNo` 都还在上面，只是不再挂着申请、也不能再改。

> 界面建议：详情页发现 `redStatus === 99` 且关联申请为空时，别显示成"数据异常"，给一句说明，比如"该发票已冲红，关联的开票申请已释放，可重新开票"。

## 三、费用"已开票"的口径变了（前端不用改代码）

**变化本身**：以前判一条开票申请算不算"已开票"，看的是申请自己的状态；现在看的是**这条申请有没有真的挂在某张【发票开出】上**。

**影响到的字段**（都是已有字段，类型和名字都没变）：

| 字段 | 出现在哪 |
| --- | --- |
| `invoicedAmount` 已开票金额 | 业务费用、付费申请、付费结算、收费结算、客户对账、更改单、海运出口/进口、空运出口、服务任务、开票申请、发票开出 |
| `unInvoicedAmount` 未开票金额 | 同上（= 费用金额 − 已开票金额） |
| `invoiceStatus` 费用开票状态 | 业务费用及各列表的筛选项 |

**前端要做的事：没有。** 字段结构完全没动，只是数字更准了。

### 新出参 `invoices`：费用开在了哪些发票上

所有返回 `invoicedAmount` 的地方，同时多返回一个 `invoices` 数组（未开票时为空/不返回）。与 `invoicedAmount` 同源，两者永远对得上。

| 字段               | 类型       | 说明                                 |
| ------------------ | ---------- | ------------------------------------ |
| `id`               | `Guid`     | 发票开出ID，可用于跳转到发票开出详情 |
| `applicationNo`    | `string`   | 发票开出的申请单号，**恒有值**       |
| `invoiceNo`        | `string`   | 发票号。**可能为空**，见下           |
| `invoiceIssueTime` | `DateTime` | 开票时间                             |
| `appliedAmount`    | `decimal`  | 本张发票上属于这条费用的金额         |

按开票时间升序。一条费用可以拆到多张发票上，所以是数组。

⚠️ **`invoiceNo` 可能为空**：费用在挂上发票开出的那一刻就算已开票，但那时接口开票可能还在开票中、手动记录可能还没填号。界面上建议 `invoiceNo || applicationNo` 这样兜底显示，别显示成空白。

> 已冲红的发票不会出现在这个数组里（冲红完成时挂靠会被解除），不需要前端过滤。

带这个字段的出参：`OrderFeeDto`（业务费用、付费申请、付费结算、客户对账、更改单、海运出进口、空运出口、服务任务、发票开出等模块的费用行都用它）、`InvoiceApplicationFeeDto`（开票申请选费用）、 `InvoiceAppSettleItemDto`（按开票申请收费结算）。

**可能会看到的差异**：如果历史数据里存在"申请状态是已开票、但其实没挂在任何发票开出上"的脏数据（例如以前删发票开出时留下的孤儿数据），这些费用现在会从"已开票"退回"未开票/部分开票"。这是修正，不是 bug。

## 四、界面上要注意的

1. 列表行与详情页的操作按钮，统一用 `editLocked` 控制禁用，替换掉原来那套"`issueStatus` 是 2/24/31 就禁用删除"的判断。
2. 「开发票」按钮的可用条件就是 `editLocked === false`。**不要再按 `invoiceIssueType` 过滤**——后端已取消开票方式校验，手动记录的发票开出也能走接口开，提交成功后开票方式会被自动改成"接口开票"。
3. 「冲红」按钮不受 `editLocked` 影响——`editLocked === true` 但 `redLocked === false` 且 `issueStatus` 为 `2`/`24` 时，**冲红是可用的**（这正是冲红存在的意义）。
4. 开票失败（`issueStatus === 22`）时按钮全部恢复可用，让用户改完数据重来。
