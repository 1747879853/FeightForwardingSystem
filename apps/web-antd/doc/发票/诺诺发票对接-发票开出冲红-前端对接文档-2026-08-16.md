# 发票开出冲红（前端对接）

**控制器**：`InvoiceIssueAdmin`

本次 **2 个新接口** + **详情/列表出参新增红冲字段** + **一条新的禁用规则**，无破坏性变更。

> **新接口 1**：`ApplyRedAsync` —— 点"冲红"，提交红字确认单申请。 **新接口 2**：`QueryRedResultAsync` —— 手动刷新冲红进度（回调没到时的兜底）。 **新规则**：`redLocked === true` 的发票开出，**编辑、删除、加挂/移除开票申请、开发票全部禁用**，只能查看。

**核心交互模型**：冲红比开票还慢，是**两段异步**。点"冲红"只是提交了一张【红字确认单】申请，`redStatus=15`（申请中），**这时候连确认单都还没进税局**。之后要等税局判定要不要购方点头，确认单生效后才会开出红票。

```
点"冲红" → redStatus=15(申请中)                     ← 界面显示"冲红申请中"
   ↓ 税局受理确认单
redStatus=1(无需确认) 或 2(待购方确认)               ← 2 的话要提示"请联系购方在税局端确认"
   ↓ 确认单生效（1 或 4）后，电票由税局自动开红票
   ↓ 回调自动落地
redStatus=99(冲红完成) + 红票号 + 红票附件
```

⚠️ **`redStatus=2`（待购方确认）可能停留很久（最长72小时），不要做无限轮询。** 建议：点完"冲红"后短轮询几次（拿到 `1`/`2`/`4` 就停），之后只保留手动"刷新冲红进度"按钮。

## 一、`POST /api/services/app/InvoiceIssueAdmin/ApplyRedAsync`

**权限**：`Admin.InvoiceIssue.Edit`（复用发票开出的编辑权限，**没有新增权限**）

### 入参 `InvoiceIssueApplyRedDto`（Body JSON）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `Guid` | 是 | 发票开出ID |
| `redReason` | `int` | 是 | 冲红原因：`1` 销货退回 / `2` 开票有误 / `3` 服务中止 / `4` 销售折让。**界面上必须让用户选，不要写死** |

### 出参 `InvoiceIssueRedStateDto`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `Guid` | 发票开出ID |
| `redStatus` | `int` | 红冲状态，见下方枚举表。本接口成功时是 `15` |
| `redStatusText` | `string` | **状态说明（含下一步该做什么），直接显示这个字符串即可**，不用自己拼文案 |
| `isFinal` | `bool` | 是否已到终态（冲红完成 或 确认单作废/申请失败）。`true` 就不用再查了 |
| `redLocked` | `bool` | 是否"冲红中或已冲红"。`true` 时这条记录**只能查询** |
| `redReason` | `int?` | 冲红原因 |
| `redBillId` | `string` | 红字确认单申请号（对账用） |
| `redBillNo` | `string` | 红字确认单编号。**进入税局后才有值** |
| `redOrderNo` | `string` | 红票订单号 |
| `redSerialNum` | `string` | 红票开票流水号。**红票开出后才有值** |
| `redInvoiceNo` | `string` | 红票发票号码。**冲红完成后才有值** |
| `redInvoiceCode` | `string` | 红票发票代码。电票为空，只有纸票（发票类型 `c`）有值 |
| `redInvoiceTime` | `DateTime?` | 红票开票时间 |
| `redFailCause` | `string` | 冲红失败/确认单作废的原因，成功时为空 |
| `invoiceNo` | `string` | 被冲红的**蓝票**发票号（方便界面上红蓝对照显示） |

### 前端处理建议

- 调用成功后 `redStatus=15`，把"冲红"按钮禁掉，其余写操作按钮（编辑/删除/加挂申请/移除申请/开发票）也一并禁掉。
- 直接把 `redStatusText` 显示出来，它已经写清楚了"要等税局""要联系购方确认"这类下一步动作。
- `isFinal === false` → 可以给一个"刷新冲红进度"按钮调 `QueryRedResultAsync`；不要做长时间自动轮询（见上方说明）。
- `redStatus` 是失败态（`5`~`9`、`16`）→ 显示 `redFailCause`，**"冲红"按钮重新可用**，用户改完/沟通完可以再申请一次。

### 会报错的情况（都是 `UserFriendlyException`，直接把 message 弹出来即可）

| 提示 | 原因 |
| --- | --- |
| 请选择冲红原因 | `redReason` 没传或传了 1~4 以外的值 |
| 该发票开出的开票方式不是接口开票，不能通过接口冲红 | `invoiceIssueType` 得是 `0` |
| 该发票开出还没有开出发票，不能冲红 | `issueStatus` 不是 `2`/`24`，没有票可冲 |
| 该发票开出没有发票号，不能冲红，请先查询开票结果 | 先调 `QueryIssueResultAsync` 把发票号拿回来 |
| 该发票已冲红(红票号 xxx)，不能重复冲红 | 已是 `99` |
| 该发票正在冲红中(当前 xxx)，请勿重复申请，可查询冲红结果 | 别重复点 |
| 取不到客户开票信息的抬头，无法作为购方申请冲红 | 去客户开票信息维护抬头 |
| 取不到蓝票的数电票号码，无法申请冲红 | 纸票冲红时后端会回查一次蓝票详情取20位数电票号码，查不到会报这个 |
| 公司[xxx]未维护开票应用的 appKey/appSecret… | 去公司资料维护 |
| 申请冲红失败[Exxxx]: xxx | 服务商侧的业务校验没过，按提示改 |

## 二、`POST /api/services/app/InvoiceIssueAdmin/QueryRedResultAsync`

**权限**：`Admin.InvoiceIssue.Edit`

主动查一次冲红进度。这个接口不只是"查"——它会顺带把整条链路往前推：

1. 查红字确认单的最新状态
2. 确认单已生效且是**纸票**时，自动调冲红接口开红票
3. 红票已开出时，回填红票号码/发票代码/开票日期并**存红票附件**

所以调完这个接口再刷详情就能看到红票号和红票附件了。

### 入参 `InvoiceIssueIdInputDto`（Body JSON）

| 字段 | 类型   | 必填 | 说明       |
| ---- | ------ | ---- | ---------- |
| `id` | `Guid` | 是   | 发票开出ID |

### 出参

同 `InvoiceIssueRedStateDto`（见上）。

### 说明

- 确认单刚提交、服务商还没落库时，接口**不报错**，原样返回当前状态（`redStatus` 保持 `15`），前端继续等就行。
- 没申请过冲红的记录调这个接口会报"该发票开出还没有申请过冲红，无从查询冲红结果"。
- 正常情况下不需要前端轮询——回调会自动落地。这个接口是回调迟到/漏掉时的兜底，以及给用户一个"刷新"的手动入口。

## 三、`redStatus` 枚举

| 值 | 含义 | 类别 | 界面建议 |
| --- | --- | --- | --- |
| `0` | 未冲红 | — | 不显示冲红标签，"冲红"按钮可用（前提是已开票） |
| `15` | 红字确认单申请中 | 进行中 | "冲红申请中…"（橙） |
| `1` | 无需确认（确认单已生效） | 进行中 | "冲红中·确认单已生效"（橙） |
| `2` | 销方录入待购方确认 | 进行中 | "冲红中·待购方确认"（橙）+ **醒目提示联系购方，超72小时未确认会自动作废** |
| `3` | 购方录入待销方确认 | 进行中 | "冲红中·待我方确认"（橙）+ 提示去电子税局确认 |
| `4` | 购销双方已确认 | 进行中 | "冲红中·已确认，待开红票"（橙） |
| `5` | 作废（销方录入购方否认） | **失败终态** | "冲红失败"（红）+ `redFailCause`，可重新冲红 |
| `6` | 作废（购方录入销方否认） | **失败终态** | 同上 |
| `7` | 作废（超72小时未确认） | **失败终态** | 同上 |
| `8` | 作废（发起方已撤销） | **失败终态** | 同上 |
| `9` | 作废（确认后撤销） | **失败终态** | 同上 |
| `16` | 红字确认单申请失败 | **失败终态** | 同上 |
| `99` | 冲红完成 | 终态 | "已冲红"（红/灰）+ 展示红票号与红票附件 |

> 别自己硬编码这些值做判断，用出参上的两个布尔量： **`isFinal`** 决定要不要继续查；**`redLocked`** 决定按钮要不要禁用。只有这两个能保证和后端的判定完全一致（后端也是同一份 `InvoiceRedStatusHelper` 算出来的）。

## 四、`DetailAsync` 出参新增字段

`InvoiceIssueDetailDto` 新增：

**`DetailAsync` 与 `GetPagedListAsync` 返回的字段完全一致**，下面这些两边都有：

| 字段 | 类型 | 说明 |

| `redLocked` | `bool` | 是否"冲红中或已冲红" |
| `editLocked` | `bool` | **是否只能查询**（含"开票报文已发出"），所有写操作按钮据此禁用 |
| `redReason` | `int?` | 冲红原因 |
| `redBillId` | `string` | 红字确认单申请号 |
| `redBillNo` | `string` | 红字确认单编号 |
| `redBillUuid` | `string` | 红字确认单uuid（内部标识，一般不展示） |
| `redOrderNo` | `string` | 红票订单号 |
| `redSerialNum` | `string` | 红票开票流水号 |
| `redInvoiceNo` | `string` | 红票发票号码 |

| `redInvoiceTime` | `DateTime?` | 红票开票时间 |

| `redApplyUserId` | `long?` | 发起冲红申请的人 |

接口开票那组字段（`issueStatus` / `issueOrderNo` / `issueSerialNum` / `issueRequestTime` / `issueFailCause` / `invoiceCode`）同样**列表与详情都有**。

> `redStatusText` **只有两个冲红接口的出参里有**，详情/列表出参里没有。详情页要显示状态说明的话，用 `redStatus` 自己映射一份文案，或者进页面时调一次 `QueryRedResultAsync`。

### `attachments` 会多出红票文件

红票开出后自动存入，与蓝票附件在同一个 `attachments` 列表里，靠文件名区分：

| `friendlyFileName`     | 说明                  |
| ---------------------- | --------------------- |
| `发票OFD-{蓝票号}.ofd` | 蓝票原始凭证          |
| `发票PDF-{蓝票号}.pdf` | 蓝票，供查看/打印     |
| `红票OFD-{红票号}.ofd` | **红票**原始凭证      |
| `红票PDF-{红票号}.pdf` | **红票**，供查看/打印 |

界面上建议分成"发票"和"红票"两组展示，别混在一个列表里让用户自己认。

## 六、⚠️ 新的禁用规则（本次重点）

> **2026-08-16 更新**：这条规则已经并入更大的一条——请统一改用出参上的 **`editLocked`**，它同时覆盖"冲红中/已冲红"与"发票已经开出去了"两种情况。详见《发票开出-已开票口径与编辑锁定-前端对接文档-2026-08-16.md》。 `redLocked` 仍然保留，用来单独区分"是因为冲红被锁的"。

**`editLocked === true` 的发票开出只能查询。** 以下操作后端会直接拒绝，界面上请**直接禁用按钮并给出提示**，不要等报错：

| 操作         | 对应接口                  |
| ------------ | ------------------------- |
| 编辑（全量） | `EditAsync`               |
| 编辑主表     | `EditMainAsync`           |
| 加挂开票申请 | `AddApplicationsAsync`    |
| 移除开票申请 | `RemoveApplicationsAsync` |
| 删除         | `DeleteAsync`             |
| 开发票       | `IssueByInterfaceAsync`   |

被拒绝时的提示文案：

- 已冲红：`发票开出[申请单号]已冲红，只能查询，不能再做其他操作`
- 冲红中：`发票开出[申请单号]正在冲红中(状态)，只能查询，不能再做其他操作`
- 批量删除时会**一次列出所有被挡下的单号**：`发票开出[单号A、单号B]已冲红或正在冲红中，只能查询，不能再做其他操作`

**仍然可用的**：详情、列表、查询开票结果、查询冲红结果、下载附件。

> 失败态（`5`~`9`、`16`）时 `redLocked` 会变回 `false`——确认单作废了等于冲红没发生，这张蓝票在税局那边还是有效的，可以重新申请冲红。但注意此时 `editLocked` **仍然是 `true`**（蓝票还在），编辑和删除依旧不放开。

### 冲红完成后关联申请会被清空

`redStatus=99` 后，这张发票开出的关联开票申请会**自动解绑**：详情页的关联申请列表变空，那些申请退回"待审核"、重新出现在可开票列表里，对应费用的已开票金额也退回来。发票开出这条记录保留，蓝票号与红票号都还在。界面上遇到"已冲红 + 关联申请为空"不要当成数据异常。

## 七、界面上要注意的

1. **"冲红"按钮**在 `issueStatus` 为 `2`/`24`（票已开出）且 `redLocked === false` 时可用。不用再判 `invoiceIssueType`——能走到"开票完成"的必然是接口开出来的，开票时后端已经把开票方式落成接口开票了。
2. **冲红原因必须让用户选**（4 个选项），不要默认或写死。选错了税局那边不好改。
3. **冲红是不可逆的重操作**，点之前建议加二次确认弹窗，把蓝票号和冲红原因再显示一遍。
4. `redStatus === 2`（待购方确认）要做**醒目**提示：这一步系统推不动，得人去联系购方，**超 72 小时未确认确认单会自动作废**，白等一场。
5. 红票号建议在列表和详情上与蓝票号**并排显示**（`invoiceNo` / `redInvoiceNo`），一眼能看出这张票已经被冲掉了。
6. ⚠️ **界面文案不得出现服务商名称**，与蓝票开票一致。冲红相关文案统一说"冲红""红字确认单""红票"。
7. 权限用现成的 `Admin.InvoiceIssue.Edit`（发票开出-编辑），**没有新增权限**，不用改权限树。
