# 发票开出接口文档

**控制器**：`InvoiceIssueAdmin`

**所有接口均需要登录认证**

---

# 1. 业务背景说明 (Background)

**白话解释：** 开票申请（`InvoiceApplication`）经提交审核后，可由开票人合并成一张实际开出的发票，即"发票开出"（`InvoiceIssue`）。

- 多个开票申请可以合并成一个发票开出，但这些开票申请的 `SettlementId`（结算对象）、`InvoiceType`（发票类型）、`CurrencyId`（币别）、`OrgBankAccountId`（我司银行）必须完全相同，否则不允许合并。
- 开票申请的商品明细与发票开出商品明细的 `Amount`（金额）合计必须相等，不一致时提示「金额合计不一致」（含双方合计数值）。`NoTaxAmount`（不含税金额）与 `TaxAmount`（税额）不参与校验。
- 开票申请明细与商品明细都允许为空：两者都为空时合计都是 0，天然相等；只有一边为空而另一边合计不为 0 时，会被金额校验拦下。唯一例外是新增接口仍要求至少一条开票申请，原因见新增接口的业务规则。
- 发票开出新建成功后，关联的开票申请状态会被改为"已开票"（`Invoiced`）。

# 2. 数据结构

- 主表：`InvoiceIssue`（发票开出）
- 子表1：`InvoiceIssueItem`（发票开出明细，关联开票申请）
- 子表2：`InvoiceIssueGoodsDtl`（发票开出商品明细）

| `amount`        | `decimal` | 是   | 金额           |
| `noTaxAmount`   | `decimal` | 是   | 不含税金额     |
| `taxRate`       | `decimal` | 是   | 税率(%)        |
| `taxAmount`     | `decimal` | 是   | 税额           |
| `remark`        | `string`  | 否   | 备注           |

**出参** `InvoiceIssueAddResultDto`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | `int` | 汇率校验结果：`0`=正常（已新增）；`1`=汇率已变动，且金额对不上的开票申请**都只有一条**商品明细；`2`=存在金额对不上且商品明细**不止一条**的开票申请（只能驳回） |
| `id` | `Guid?` | 新建的发票开出ID；`code` 不为 `0`（未执行新增）时为 `null` |
| `singleGoodsDtlApplicationIds` | `List<Guid>` | 因汇率变动金额对不上、且只有一条商品明细的开票申请ID列表 |
| `multiGoodsDtlApplicationIds` | `List<Guid>` | 因汇率变动金额对不上、且商品明细不止一条的开票申请ID列表（只能驳回） |

> `code=0` 时两个ID列表均为空数组；`code=1` 时 `multiGoodsDtlApplicationIds` 为空数组；两个列表任何情况下都会返回。

**汇率校验（`AddAsync` 与 `AddApplicationsAsync` 口径完全一致）**：

新增前先按 `invoiceIssueItems.invoiceApplicationId` 拉取全部开票申请（含费用明细与商品明细），逐条按**当前**发票汇率校验：

```
费用申请金额折算人民币 = round(sum(invoiceApplicationItems.appliedAmount) × 当前发票汇率, 2, 四舍五入)
是否对得上 = (费用申请金额折算人民币 == sum(invoiceApplicationGoodsDtls.amount))
```

口径与开票申请提交审核时的校验、以及已提交列表的 `amountMatched` 完全一致。对不上的按其商品明细条数分入 `singleGoodsDtlApplicationIds`（只有一条）与 `multiGoodsDtlApplicationIds`（不止一条），再据此得出 `code`。

> [!IMPORTANT] **只要 `code` 不为 `0`，接口一律不做任何操作**，直接返回校验结果——不新增、不改数据，后续校验（申请状态、四要素一致、金额合计等）全都不执行。修正数据是独立接口 `SyncApplicationGoodsDtlByExchangeRateAsync` 的职责：`code=1` 时前端用 `singleGoodsDtlApplicationIds` 调它按汇率改金额，改完再重新提交；`code=2` 的申请只能驳回后手工调整商品明细。

**业务规则（校验）**：

- `invoiceIssueItems` 至少一条，且开票申请不能重复。**新增接口不能没有开票申请**：主表的 `SettlementId`、`InvoiceType`、`CurrencyId`、`ClientInvoiceBankId`、`OrgBankAccountId` 全部取自第一条开票申请，且实体上这几个字段非空并带外键约束，没有申请就无从取值。
- `invoiceIssueGoodsDtls` 可以为空，此时要求开票申请的商品明细金额合计为 0，否则金额校验不通过。
- 所有开票申请必须存在，且未被其他发票开出关联。
- 所有开票申请的币别都必须已维护当前有效的发票汇率（`ExchangeRate.InvoiceValue`，`LocalCurrency=RMB`），否则提示「未维护xx币种的发票汇率，请先维护本位币为RMB的对应币种的发票汇率」。
- 开票申请状态必须为"待审核（已提交）"（`Auditing`）。
- 所有开票申请的 `SettlementId`、`InvoiceType`、`CurrencyId`、`OrgBankAccountId` 必须一致，否则报错。
- 开票申请商品明细与发票开出商品明细的 `Amount` 合计需相等，不一致时提示「金额合计不一致」。
- 主表的 `SettlementId`、`InvoiceType`、`CurrencyId`、`OrgBankAccountId`、`ClientInvoiceBankId`、`OrgId`（归属组织id）取自开票申请（已校验一致）。
- 开出单号 `ApplicationNo` 由编号生成规则（`InvoiceIssue.ApplicationNo`）自动生成。
- 新建成功后，关联的开票申请状态改为"已开票"（`Invoiced`）。

## 二、修改发票开出

### `PUT /api/services/app/InvoiceIssueAdmin/EditAsync`

**权限**：`Admin.InvoiceIssue.Edit`

**入参** `InvoiceIssueEditDto`（Body JSON）：在 `InvoiceIssueAddDto` 基础上增加：

| 字段 | 类型   | 必填 | 说明       |
| ---- | ------ | ---- | ---------- |
| `id` | `Guid` | 是   | 发票开出ID |

**出参**：`bool`

**业务规则**：

- 子表（开票申请明细、商品明细）全量替换。
- 校验逻辑同新增（排除自身的关联校验），但 `invoiceIssueItems` 与 `invoiceIssueGoodsDtls` **都可以传空**，只要两边金额合计相等。
- 清空 `invoiceIssueItems` 时，主表的 `SettlementId`、`InvoiceType`、`CurrencyId`、`ClientInvoiceBankId`、`OrgBankAccountId` **保持原值不变**（没有申请可供取值）；其余主表字段照常按入参更新。
- 新关联的开票申请改为"已开票"；被移除的开票申请回退为"待审核"（`Auditing`），回退前会做「已被收费结算引用则禁止」校验。
- **兼容保留**；局部改主表/加减申请请用下列拆分接口（见 `发票开出-编辑拆分-前端对接文档-2026-07-24.md`）。

### `PUT /api/services/app/InvoiceIssueAdmin/EditMainAsync`

**权限**：`Admin.InvoiceIssue.Edit`

**入参** `InvoiceIssueEditMainDto`：`id`、`orgId`、`invoiceIssueType`、`invoiceNo`、`invoiceIssueTime`、`require`、`remark`

**出参**：`bool`

**业务规则**：仅更新主表；不改开票申请/商品明细；`invoiceNo` 变更时同步回填已关联开票申请。

### `POST /api/services/app/InvoiceIssueAdmin/AddApplicationsAsync`

**权限**：`Admin.InvoiceIssue.Edit`

**入参** `InvoiceIssueAddApplicationsDto`：`id`、`invoiceIssueItems`（本次新增）、`invoiceIssueGoodsDtls`（合并后完整商品明细）

**出参** `InvoiceIssueExchangeRateCheckDto`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | `int` | 汇率校验结果，含义与口径同新增接口：**`0`=正常，已加挂成功**（替代原来的 `bool` 返回值，判断成功就看这个）；`1`=汇率已变动，且对不上的开票申请都只有一条商品明细；`2`=存在对不上且商品明细不止一条的开票申请（只能驳回） |
| `singleGoodsDtlApplicationIds` | `List<Guid>` | 对不上且只有一条商品明细的开票申请ID |
| `multiGoodsDtlApplicationIds` | `List<Guid>` | 对不上且商品明细不止一条的开票申请ID（只能驳回） |

**汇率校验**：口径与 `AddAsync` 完全一致，同样是「`code` 不为 `0` 就什么都不做、直接返回」。唯一区别是**只校验本次新增的开票申请**（`invoiceIssueItems` 里的），已关联的申请早已是"已开票"、开票时已校验过，不重复校验——否则历史汇率变动会永久堵住"加挂新申请"这个动作。

**业务规则**：`invoiceIssueItems`（本次新增）至少一条；`code=0` 时与已有申请合并后做四要素与金额校验；全量替换商品明细（`invoiceIssueGoodsDtls` 可传空，相当于清空）；新申请改已开票。本次新增的开票申请币别必须已维护当前有效的发票汇率。

### `PUT /api/services/app/InvoiceIssueAdmin/RemoveApplicationsAsync`

**权限**：`Admin.InvoiceIssue.Edit`

**入参** `InvoiceIssueRemoveApplicationsDto`：`id`、`invoiceApplicationIds`、`invoiceIssueGoodsDtls`（剩余完整商品明细）

**出参**：`bool`

**业务规则**：允许移除全部开票申请（不再要求至少保留一条），全部移除时 `invoiceIssueGoodsDtls` 须一并传空或合计为 0，主表四要素保持原值不变；金额与剩余申请一致；反开票结算引用校验；申请回退待审核。

### `PUT /api/services/app/InvoiceIssueAdmin/SyncApplicationGoodsDtlByExchangeRateAsync`

按当前发票汇率修正开票申请商品明细的金额。专门配合 `AddAsync` / `AddApplicationsAsync` 返回的 `code=1` 使用。

**权限**：`Admin.InvoiceIssue.Add` 或 `Admin.InvoiceIssue.Edit`（`RequireAllPermissions=false`，任一即可——新增与加挂两条流程都会用到它）

**入参** `InvoiceIssueSyncApplicationGoodsDtlDto`（Body JSON）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `invoiceApplicationIds` | `List<Guid>` | 是 | 待修正的开票申请ID列表，至少一条。直接把校验结果的 `singleGoodsDtlApplicationIds` 传进来即可 |

**出参** `InvoiceIssueSyncApplicationGoodsDtlResultDto`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `updatedApplicationIds` | `List<Guid>` | 实际修正了金额的开票申请ID列表 |
| `unchangedApplicationIds` | `List<Guid>` | 金额本来就对得上、无需修正的开票申请ID列表（不改数据也不写备注） |

**修正规则**（只动那**唯一一条**商品明细）：

```
amount      = round(sum(invoiceApplicationItems.appliedAmount) × 当前发票汇率, 2)
noTaxAmount = round(amount / (1 + taxRate/100), 2)
taxAmount   = amount - noTaxAmount
```

`quantity`、`unitPrice`、`taxRate`、`codeInvoiceId` 等其余字段不动。

**备注留痕**：每次实际修正都会在该条商品明细的 `remark` **末尾追加一行**变更记录（不覆盖原备注），格式为：

```
更新时间：2026-08-04 15:36:12；更新方式：汇率变动（张三提交的更新）；更新字段：金额（更新前 1000.00，更新后 1050.00）、不含税金额（更新前 917.43，更新后 963.30）、税额（更新前 82.57，更新后 86.70）
```

提交人昵称取自用户信息缓存的 `NickName`，取不到时写 `系统`。

> **`更新字段` 只列本次真正变了的字段。** 例如零税率（`taxRate=0`）的商品明细，`noTaxAmount` 恒等于 `amount`、`taxAmount` 恒为 0，这两个字段值没变就不会出现在记录里，只会写「更新字段：金额（…）、不含税金额（…）」。

`remark` 字段上限 1024 字符，追加后超长时按行丢弃最早的记录，保留最近的。

**业务规则（校验）**：

- `invoiceApplicationIds` 至少一条；所有ID必须存在，否则提示「部分开票申请不存在」。
- 每条开票申请必须为**待审核（已提交）**（`Auditing`）状态，否则提示「开票申请[xxx]非待审核(已提交)状态 不能按汇率修正商品明细」。已开票的申请不允许改，否则会与已开出的发票脱节。
- 每条开票申请的商品明细必须**恰好一条**，否则提示「开票申请[xxx]的商品明细不止一条 无法按汇率自动修正 请驳回后手工调整」。所以不要把 `multiGoodsDtlApplicationIds` 传进来。
- 币别必须已维护当前有效的发票汇率。
- 金额本来就对得上的申请会被跳过，只进 `unchangedApplicationIds`，不改数据、不写备注。
- 接口只改开票申请的商品明细，**不会**动发票开出。修正完前端需重新拉取开票申请拿到新金额、重算发票开出商品明细，再调 `AddAsync` / `AddApplicationsAsync`。

## 三、删除发票开出

### `DELETE /api/services/app/InvoiceIssueAdmin/DeleteAsync`

**权限**：`Admin.InvoiceIssue.Delete`

**入参** `InvoiceIssueDeleteDto`（Body JSON）：

| 字段  | 类型         | 必填 | 说明                       |
| ----- | ------------ | ---- | -------------------------- |
| `ids` | `List<Guid>` | 是   | 发票开出ID列表（批量删除） |

**出参**：`bool`

**业务规则**：删除后，关联的开票申请回退为"待审核"（`Auditing`）状态；若开票申请已被收费结算引用则禁止删除。没有关联任何开票申请的发票开出可以直接删除，会跳过反开票校验与费用开票状态回写。

**核心业务卡点（汇率变动导致金额不匹配）**：

> [!IMPORTANT] 开票申请创建时，商品明细金额合计（人民币）= 费用明细申请金额合计（原币）× 当时的发票汇率。由于发票汇率会随时间变动，开出发票时若汇率已变，则 `totalGoodsAmount ≠ appliedAmountRmb`，此时 `code` 不为 `0`：商品明细只有一条时 `code=1`（可调修正接口按当前汇率更新金额后重试），不止一条时 `code=2`（只能驳回后手工调整）。无有效发票汇率时 `code=2`。口径与 `AddAsync`/`AddApplicationsAsync` 返回的 `InvoiceIssueExchangeRateCheckDto.Code` 完全一致。
