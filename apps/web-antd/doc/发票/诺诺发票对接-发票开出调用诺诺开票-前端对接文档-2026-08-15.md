# 发票开出调用诺诺开票（前端对接）

**控制器**：`InvoiceIssueAdmin`

本次 **2 个新接口** + **若干字段新增**，无破坏性变更。

> **新接口 1**：`IssueByInterfaceAsync` —— 点"开发票"，调诺诺开票。 **新接口 2**：`QueryIssueResultAsync` —— 手动刷新开票结果（回调没到时的兜底）。

**核心交互模型**：数电发票是**异步**的。点"开发票"只是**提交受理**，同步返回的 `issueStatus=1`（已提交待开票），**这时候还没有发票号**。真正的发票号、开票日期、发票PDF/OFD 是诺诺开完票后回调过来自动落地的，前端需要**轮询或让用户手动刷新**才能看到。

```
点"开发票" → issueStatus=1(已提交待开票)  ← 此时无发票号，界面显示"开票中"
   ↓ 诺诺开票(通常几秒到几十秒，税局繁忙时更久)
   ↓ 回调自动落地
刷新详情 或 调 QueryIssueResultAsync → issueStatus=2(开票完成) + 发票号 + 附件
```

---

## 一、`POST /api/services/app/InvoiceIssueAdmin/IssueByInterfaceAsync`

**权限**：`Admin.InvoiceIssue.Edit`（复用发票开出的编辑权限，**没有新增权限**）

### 入参 `InvoiceIssueIdInputDto`（Body JSON）

| 字段 | 类型   | 必填 | 说明       |
| ---- | ------ | ---- | ---------- |
| `id` | `Guid` | 是   | 发票开出ID |

### 出参 `InvoiceIssueStateDto`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `Guid` | 发票开出ID |
| `invoiceIssueType` | `int` | 开票方式。**本接口成功后恒为 `0`（接口开票）**，见下方"开票方式不再校验" |
| `issueStatus` | `int` | 诺诺开票状态，见下方枚举表。本接口成功时通常是 `1` |
| `isFinal` | `bool` | 是否已到终态。`true` 就不用再查了 |
| `issueOrderNo` | `string` | 提交给诺诺的订单号 |
| `issueSerialNum` | `string` | 诺诺发票流水号 |
| `issueFailCause` | `string` | 开票失败原因，成功时为空 |
| `invoiceNo` | `string` | 发票号。**开票完成后才有值** |
| `invoiceCode` | `string` | 发票代码。**电票为空**，只有纸票（发票类型 `c`）有值；纸票要"代码+号码"配对才能定位一张票 |
| `invoiceIssueTime` | `DateTime` | 开票时间。开票完成后是诺诺返回的实际开票时间 |

### 前端处理建议

调用成功后：

- `isFinal === false`（一般是 `issueStatus=1`）→ 状态标签显示"开票中…"，禁用"开发票"按钮，起一个轮询（建议 3 秒一次、最多 20 次）调 `QueryIssueResultAsync`，或者只放一个"刷新开票结果"按钮让用户点。
- `issueStatus === 22 || issueStatus === 24` → 显示 `issueFailCause`，允许用户改完数据后重新点"开发票"。

### 会报错的情况（都是 `UserFriendlyException`，直接把 message 弹出来即可）

| 提示 | 原因 |
| --- | --- |
| ~~该发票开出的开票方式不是接口开票…~~ | **2026-08-16 起这条报错已取消**，见下方"开票方式不再校验" |
| 该发票开出已开票完成(发票号 xxx)，不能重复开票 | 已是终态，要冲红 |
| 该发票开出已提交诺诺、正在开票中，请稍后查询开票结果 | 别重复点 |
| 发票开出没有商品明细，不能开票 | — |
| 商品明细金额合计不大于0，不能开票；要开红票请对原蓝票发起冲红 | 红票走冲红那条链路，见《…-发票开出冲红-前端对接文档-2026-08-16.md》 |
| 发票开出[xxx]已冲红/正在冲红中，只能查询… | 冲红中或已冲红的记录不能再开票，`redLocked === true` 时按钮就该禁用 |
| 公司[xxx]未维护统一社会信用代码/纳税人识别号… | 去公司资料维护 |
| 公司[xxx]未维护开票应用的 appKey/appSecret… | 去公司资料维护。**每家公司在服务商那边是独立应用，各配各的**，公司资料界面需要新增这两个输入项 |
| 当前登录人未维护昵称，无法作为开票员提交给诺诺 | **开票员取的是当前登录人昵称**，且需与诺诺侧开票员姓名一致 |
| 客户[xxx]未维护邮箱… | 发票按邮箱推送给购方，取的是**客户表的邮箱** |
| 客户开票信息未维护抬头… | — |
| 诺诺开票失败[Exxxx]: xxx | 诺诺侧的业务校验没过，按提示改 |

## 二、`POST /api/services/app/InvoiceIssueAdmin/QueryIssueResultAsync`

**权限**：`Admin.InvoiceIssue.Edit`

主动查一次诺诺开票结果。查到开票完成时会**顺带完成回填与存附件**，所以调完这个接口再刷详情就能看到发票号和附件了。

### 入参 `InvoiceIssueIdInputDto`（Body JSON）

| 字段 | 类型   | 必填 | 说明       |
| ---- | ------ | ---- | ---------- |
| `id` | `Guid` | 是   | 发票开出ID |

### 出参

同 `InvoiceIssueStateDto`（见上）。

### 说明

- 诺诺侧还没生成时，接口**不报错**，原样返回当前状态（`issueStatus` 保持 `1`），前端继续等就行。
- 没提交过诺诺开票的记录调这个接口会报"该发票开出还没有提交过诺诺开票，无从查询开票结果"。
- 正常情况下不需要前端轮询——回调会自动落地。这个接口是回调迟到/漏掉时的兜底，以及给用户一个"刷新"的手动入口。

---

## 三、`issueStatus` 枚举

| 值 | 含义 | 是否终态 | 界面建议 |
| --- | --- | --- | --- |
| `0` | 未开票 | — | 显示"未开票"，"开发票"按钮可用 |
| `1` | 已提交待开票 | — | "开票中…"，按钮禁用 |
| `2` | 开票完成 | ✅ | "已开票"（绿），展示发票号与附件 |
| `3` | 已作废 | ✅ | "已作废"（灰） |
| `20` | 开票中 | — | "开票中…" |
| `21` | 开票成功签章中 | — | "签章中…" |
| `22` | 开票失败 | ✅ | "开票失败"（红）+ `issueFailCause`，可重开 |
| `24` | 开票成功签章失败 | ✅ | "签章失败"（橙）——**票已开出来了**，发票号有值 |
| `31` | 发票作废中 | — | "作废中…" |

> 直接用出参的 `isFinal` 判断要不要继续轮询，别自己硬编码这几个值。

## 四、`DetailAsync` 出参新增字段

`InvoiceIssueDetailDto` 新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `issueStatus` | `int` | 诺诺开票状态 |
| `issueOrderNo` | `string` | 提交给诺诺的订单号 |
| `issueSerialNum` | `string` | 诺诺发票流水号 |
| `issueRequestTime` | `DateTime?` | 提交开票请求的时间 |
| `issueFailCause` | `string` | 开票失败原因 |
| `invoiceCode` | `string` | 发票代码。电票为空，只有纸票有值 |
| `attachments` | `List<AttachmentItemDto>` | **发票版式文件附件**，结构与其它模块的附件一致（含 `url` / `friendlyFileName` / `mediaType` 等） |

### 关于 `attachments`

诺诺开票完成后自动存入，不需要前端上传。**服务商返回几个地址就存几个文件**，可能出现的有：

| `friendlyFileName` | 说明 |
| --- | --- |
| `发票OFD-{发票号}.ofd` | **法定原始凭证**，入账归档用（数电电票） |
| `发票XML-{发票号}.xml` | 税局认的原始数据格式，对接财务/税务归档系统用 |
| `发票PDF-{发票号}.pdf` | 版式转换产物，**不能作原始凭证**，只用于查看/打印/发客户 |
| `发票纸质PDF-{发票号}.pdf` | 含底图的纸票打印版（数电纸票才有） |
| `发票图片1-{发票号}.jpg`、`发票图片2-…` | 发票图片，可能多张 |

⚠️ **这几个不是都会有**。哪些格式有值由服务商侧的企业资质配置决定（诺诺文档原话：xml 是"企业配置成支持获取xml时返回"），沙箱环境更可能只给其中一两个。前端**按实际返回的渲染，不要写死假设有 PDF**。

界面上给"下载发票"时：入账/归档指向 OFD 或 XML，查看/打印指向 PDF。某个文件这次没下来也不用管——下次回调或手动点"查询开票结果"会自动把缺的那个补上（按文件名去重，已有的不会重复下载）。

冲红完成后这里还会多出同一套红票文件（`红票OFD-…`、`红票XML-…`、`红票PDF-…`、`红票图片1-…` 等）。 **这个数组是一条发票开出下的全部附件，不分组**，前端要区分蓝票/红票按 `friendlyFileName` 前缀判断（`发票` / `红票`）。

### 开票申请也能拿到发票附件

`InvoiceApplicationAdmin` 的 `DetailAsync` 与 `GetPagedListAsync` 同样新增了 `attachments`，内容是**这条开票申请所挂的那张发票开出下的附件**（申请自己没有附件）。

- 结构与上面完全一致，同样**不分组**、拉平成一个数组；
- 申请没挂发票开出（还没开票）时为空；
- 冲红完成后挂靠会被解除，那张票的附件也就不再出现在申请上了。

## 五、`GetPagedListAsync` 出参新增字段

`InvoiceIssueListDto` 与 `InvoiceIssueDetailDto` **返回同一套字段**（2026-08-16 起列表已补齐），包括 `attachments`（发票版式文件附件）——列表页不用为了显示开票状态、订单号、发票代码或下载发票再逐条查详情。

> 列表查询入参 `InvoiceIssueQueryDto` **未新增**筛选项。如果需要按"诺诺开票状态"筛列表，说一声再加。

## 六、开票申请（`InvoiceApplicationAdmin`）——**没有任何字段变化**

开票申请的出参、入参、表结构都**没有改动**，仍然只有 `invoiceNo`（开票时回填、反开票时置空），行为与改造前完全一致。

> 需要在开票申请相关界面上显示**开票日期 / 开票方式**时，不要指望申请对象上有这两个字段，请通过发票开出取：发票开出详情的 `invoiceIssueApplications` 就是它关联的申请列表，反过来从申请找开票信息时，用发票开出列表按 `invoiceNo` 或关联关系去取 `invoiceIssueTime` / `invoiceIssueType`。这样避免同一份信息在两张表里各存一份、各自维护。

## 七、界面上要注意的

1. **开票方式不再校验（2026-08-16 变更）**：`IssueByInterfaceAsync` 不再要求 `invoiceIssueType === 0`。手动记录（`1`）的发票开出也能点"开发票"，**提交成功后后端会把 `invoiceIssueType` 自动改成 `0`（接口开票）**。所以"开发票"按钮不用再按开票方式过滤，只看 `editLocked === false`；调用成功后请用出参里的 `invoiceIssueType` 刷新这一列，别继续显示"手动记录"。
2. **手填发票号的输入框**在接口开票方式下应该**只读**——号码由开票接口返回，手填会被覆盖。⚠️ 手动记录转接口开票时同理：原来手填的发票号会被接口开出来的真实号码覆盖。
3. **删除**：`issueStatus` 为 `2`/`24`/`31` 的记录后端会拒绝删除（税局在册的票，要先冲红），按钮建议直接禁用并给提示。另外 `redLocked === true`（冲红中/已冲红）的记录，编辑、删除、加挂/移除申请、开发票**全部**会被拒绝，详见《诺诺发票对接-发票开出冲红-前端对接文档-2026-08-16.md》第六节。
4. 权限用现成的 `Admin.InvoiceIssue.Edit`（发票开出-编辑），**没有新增权限**，不用改权限树。
5. 开票员用的是**当前登录人昵称**，界面上如果要展示"开票员"，直接显示当前用户昵称即可（不需要选）。
6. ⚠️ **界面文案不得出现服务商名称**。状态、按钮、提示语一律用中性说法（"开票中…"/"已开票"/"开票失败"），后端抛出的错误消息已经统一去掉了服务商名称，直接透出即可。`invoiceIssueType === 0` 建议显示为"**接口开票**"而不是服务商名。
7. **公司资料界面要加两个字段**：`invoiceAppKey`、`invoiceAppSecret`（组织新增/编辑接口的入参与出参都已加好）。每家公司在服务商那边是独立应用，各配各的密钥；销方税号继续用已有的"统一社会信用代码"字段，不用新增。 `invoiceAppSecret` 是机密，建议用密码框展示。
