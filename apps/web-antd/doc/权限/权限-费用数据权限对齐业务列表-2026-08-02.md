# 背景意图

现场反馈：普通用户在「海运出口列表」里能正常看到一批业务单，但进入「开票申请 → 拉费用」(`GetOrderFeeGroupAsync`) 却永远返回空列表。

连库排查（用户 `shaoshao`，UserId=5，租户 1，角色 `admin`+`user`）定位到两个互相叠加的缺陷：

1. **角色维度的数据权限从未生效。** `App_UserDataPermissions` 中已给 `admin` 角色配置了 `DataPermissionType=All / ManageType=Get`（全部数据·查询），但该用户实际落进了「只能看自己」的分支。
2. **费用可见性口径比业务列表窄。** 费用只认主单的「所属人」，不认「创建人」和「业务关联人员（干系人）」，而业务列表三者都认。用户 5 只是这些单子的商务/销售/单证，所以看得到单、看不到费。

两者叠加的结果就是空列表。实测数据（`paySide=0`，审核通过、未禁开票、剩余未开票金额>0 的候选费用共 71 条 / 25 张主单）：

| 判定口径                           | 可见费用 | 可见主单 |
| :--------------------------------- | :------- | :------- |
| 修复前（仅主单所属人）             | 0        | 0        |
| 补上主单创建人                     | 3        | 1        |
| 再补上业务关联人员（业务列表口径） | 30       | 11       |
| 角色 All 权限生效（allowAll）      | 71       | 25       |

# 核心逻辑变更

## 一、修复角色数据权限失效（`CsprojBuilderAppServiceBase.GetDataPermissionUserIdsAsync`）

原实现从 `GetCurrentUserAsync()` 返回的实体上取 `user.Roles`：

```csharp
var user = await GetCurrentUserAsync();
var roleIds = user.Roles?.Select(r => r.RoleId).ToList() ?? new List<int>();
```

`GetCurrentUserAsync()` 走 `UserManager.FindByIdAsync`，其底层 `AbpUserStore.FindByIdAsync` 只做 `UserRepository.FirstOrDefaultAsync(id)`，**不会 Include `Roles` 导航集合**；项目也未启用延迟加载代理（全仓无 `UseLazyLoadingProxies`）。因此 `user.Roles` 恒为 `null`，`roleIds` 恒为空集合，所有 `RoleId` 维度的数据权限配置被静默丢弃。

现改为直查关联表，并顺带去掉一次不必要的用户查库（只需要 `AbpSession.GetUserId()`）：

```csharp
var userId = AbpSession.GetUserId();
var roleIds = (await UserRoleRepository.GetAllListAsync(ur => ur.UserId == userId))
    .Select(ur => ur.RoleId)
    .ToList();
```

基类同步新增属性注入 `public IRepository<UserRole, long> UserRoleRepository { get; set; }`。

> 该修复影响**所有**走数据权限的模块，不限于费用。上线后按角色配置的「全部/多部门/多人」等权限会真正开始生效，可见范围会变大，属预期行为。

## 二、费用可见性对齐业务列表（`CsprojBuilderAppServiceBase`）

新增两个公共成员，把「业务关联人员」的口径收敛到唯一定义处：

| 成员 | 说明 |
| :-- | :-- |
| `DataPermissionRelatedUserAttributes` | `private static readonly UserAttribute[]`，参与数据权限的干系人角色集合：销售 / 商务 / 操作 / 客服 / 单证 / 海外客服 / 航线 |
| `GetRelatedTransportOrderIdsQuery(List<long> userIds)` | `protected IQueryable<Guid>`，指定用户担任上述任一角色的主单 id 子查询；独立查 `OrderUser` 表避免主查询 JOIN，单用户时用 `==` 而非 `Contains` 以规避 IN 子查询的执行计划劣化 |
| `DataPermissionFilterTransportOrderAsync` | `protected`，主单查询过滤：所属人 / 创建人 / 所属组织 / 业务关联人员任一命中即可见 |

`DataPermissionFilterOrderFeeAsync` 重写为同一口径（费用跟随主单）：

```csharp
var relatedOrderIdsQuery = GetRelatedTransportOrderIdsQuery(userids);
return query.Where(x => userids.Contains(x.TransportOrder.UserId)
    || (x.TransportOrder.CreatorUserId.HasValue && userids.Contains(x.TransportOrder.CreatorUserId.Value))
    || (x.TransportOrder.OrgId.HasValue && orgids.Contains(x.TransportOrder.OrgId.Value))
    || relatedOrderIdsQuery.Contains(x.TransportOrderId));
```

# 避坑指南

> [!IMPORTANT] **禁止再从 `User` 实体上读 `Roles`。** `UserManager.FindByIdAsync` / `GetCurrentUserAsync()` 返回的用户实体**不带** `Roles` 导航集合，读出来是 `null` 而不是抛异常，属于典型的静默失效。需要角色 id 一律直查 `IRepository<UserRole, long>`。同类写法此前已在 `PropMaskProvider` 中踩过一次并留有注释。

> [!IMPORTANT] **新增费用相关的列表接口，必须复用基类方法，不要自己写 `Where`。** 费用查询用 `DataPermissionFilterOrderFeeAsync`；先按主单圈范围再取费用的场景用 `DataPermissionFilterTransportOrderAsync`。三大业务列表的干系人口径也已指向 `GetRelatedTransportOrderIdsQuery`，需要调整可见范围时只改 `DataPermissionRelatedUserAttributes` 一处。

> [!IMPORTANT] **「列表能看到单、下钻却是空」是口径漂移的典型信号。** 业务列表（海运出口/进口、空运出口）认四类关系：所属人、创建人、所属组织、业务关联人员；下钻的子数据若只认所属人，对「自己只是干系人」的用户就会全空。排查此类问题时优先对比两侧的过滤谓词，而不是先怀疑业务条件。

> [!NOTE] **本次未改动的既有权限缺口**（`OrderFeeAdminAppService` 的 `GetPagedListAsync` / `DetailAsync` / 各审核任务列表等仍未接入费用数据权限），属独立问题，需要时另行评估。
