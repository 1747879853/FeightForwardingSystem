# 1. 业务背景说明 (Background)

**白话解释：** 数据权限决定「一个用户能查、能改哪些数据」。规则配在用户或角色上（角色下所有用户共享），一个人最终的数据权限 = 本人规则 + 本人所有角色的规则合并。

每条规则由四部分组成：

- **数据范围类型** `DataPermissionType`：自己 / 自己部门 / 自己公司 / 多人 / 部分（多部门、多公司）/ 全部 / 排除人员。
- **操作类型** `ManageType`：查询 / 编辑。
- **模块** `Module`：规则作用于哪个业务模块。**为空是通用规则**，所有没有单独配置的模块都用它。
- **子表** `Items`：多人、排除人员存用户 id；部分存组织 id；其他类型不用。

两个关键能力：

- **按模块单独配置**：例如一个人在海运出口能看全公司，在海运进口只能看自己。没单独配置的模块自动用通用规则，新模块上线不需要每家重新配。
- **排除人员**：在范围权限里扣掉某些人的数据，例如「能看全公司，但看不到老板的单」。排除优先于所有范围权限，包括「全部」。

接口地址、入参出参见《数据权限模块接口文档》。

# 2. 功能与操作说明 (Features & Operations)

## 2.1 配置规则

- **新增 / 编辑 / 删除 / 列表 / 详情：** 在数据权限配置页维护，子表通过主表接口的 `entityIds` 一次性提交，没有单独维护子表的接口。
- **一个用户或角色可以配多条规则**，唯一性是「用户或角色 + 操作类型 + 权限类型 + 模块」只能一条（模块为空也算一个值）。例如同一个人在查询口径下可以同时有「通用：全部」「通用：排除人员」「海运出口：自己部门」三条。

## 2.2 规则怎么生效

查某个模块的数据时，按以下步骤算出当前用户的可见范围（`CsprojBuilderAppServiceBase.GetEffectiveDataPermissionsAsync` + `GetDataPermissionUserIdsAsync`）：

1. 取出本人规则和本人所有角色的规则。角色直接查 `UserRole` 关联表，不能读 `User.Roles`（恒为空）。
2. **范围规则按来源回退**：本人一组、每个角色一组。各组有本模块、本操作类型的范围规则就用本模块的，没有就用通用规则。最后各组合并。
3. **排除名单**：所有来源里，模块为空或等于本模块的「排除人员」规则，子项全部合并。编辑口径还要并上查询口径的（看不到的也不能改）。最后去掉当前用户自己。
4. 合并后的范围规则算出三样东西：
   - 是否「全部」；
   - **可见用户**：多人里的用户 + 自己；
   - **可见组织**：自己部门、自己公司、部分折算出的组织，以及它们的所有下属组织。
5. 各模块的过滤方法用这三样加排除名单过滤数据，口径见第 5 节。

判断一组「有没有配置本模块」**只看范围规则，不看排除规则**。否则只给某模块配一条「排除老板」，这个人在该模块的范围就会从通用的「我的公司」掉到只剩自己。

例子：

| 配置 | 查海运出口 | 查客户 |
| :-- | :-- | :-- |
| 本人无规则；角色 A：通用「自己部门」、海运出口「全部」 | 全部 | 自己部门 |
| 本人：海运出口「多人：张三」；角色 A：通用「自己公司」 | 自己公司 + 张三（本人的模块规则收窄不了角色的通用规则） | 自己公司 |
| 角色 A：通用「自己公司」、海运出口「排除人员：老板」 | 自己公司，排除老板 | 自己公司，不排除 |
| 本人：通用「排除人员：老板」；角色 A：通用「全部」、海运出口「排除人员：张三」 | 全部，排除老板和张三 | 全部，排除老板 |

## 2.3 各模块用哪份配置

**数据按它自己所属的模块取配置，不按当前页面。** 例如收费结算页面里查发票开出，用的是发票开出的配置；银行流水页面列收费结算，用的是收费结算的配置。

| 数据权限模块 | 值 | 过滤方法 | 用在哪 |
| :-- | :-- | :-- | :-- |
| 海运出口 | 0 | `SeaExportListDataPermissionFilterAsync` | 海运出口列表、分组、详情、上下条、编辑删除校验；提单；报表；监装工单列表（跟随海运出口） |

- **业务主单、业务费用**：按每票的业务类型走对应业务列表的过滤，见 2.4。
- **提单、监装工单、件杂货分单**：跟随所属业务单。

## 2.4 业务主单与费用

主单和费用没有自己的模块配置，**按每票的业务类型走对应业务列表的过滤**：海运出口的单和费用用海运出口的权限，海运进口的用海运进口的，空运出口、件杂货同理。业务列表、主单、费用三处用的是同一段过滤代码 `ApplyBizOrderDataPermission`，改一处三处一起生效。

唯一出口是 `GetVisibleTransportOrdersAsync`，做法是把四个业务列表的过滤结果合在一起：

1. 四种业务类型分别解析对应模块的权限。业务类型到模块用 `DataPermissionBizTypeModules` 映射，两个枚举的数值不一样，不能强转。
2. 「全部权限且没有排除人员」的业务类型不查扩展表，直接按业务类型放行。
3. 其余业务类型在各自扩展表上跑业务列表的过滤，取出可见单号后拼在一起。一票业务只在自己那张扩展表里有记录，所以每票只会被它自己业务类型的那套过滤判定。

两个过滤方法只是比较的列不同：

| 方法 | 比较的列 | 调用方 |
| :-- | :-- | :-- |
| `DataPermissionFilterTransportOrderAsync` | 主单 `Id`、`BizType` | 对账单、付费申请的 `GetOrderFeeGroupAsync`（先按业务单分页再带出费用）；业务费用 `GetTransportOrderFeesAsync` |
| `DataPermissionFilterOrderFeeAsync` | 费用 `TransportOrderId`、所属主单 `BizType` | 收费结算 `BuildSettleableFeeQueryAsync`；开票申请 `GetOrderFeeGroupAsync` |

挂到查询上的条件分三种：四种业务类型都直接放行时不加任何条件；都需要过滤时是「单号在可见单号里」；部分放行时是「业务类型是放行的那几种，或者单号在可见单号里」。

对账单拉费用时，当前用户是该结算对象的对账人则跳过数据权限、返回全部。

# 4. 核心字段说明 (Field Definitions)

## 4.1 规则主表 `App_UserDataPermissions`

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🔗 联动规则 | 🛡️ 校验限制 |
| :-- | :-- | :-- | :-- | :-- |

| **items** | 子表 | 子表 `App_UserDataPermissionItems` | —— | 排除人员不能为空，且用户规则不能排除自己 |

| **userDataPermissionId** | 所属规则 | —— |
| **entityId** | 多人、排除人员时是用户 id；部分时是组织 id | 同一规则下自动去重 |

## 4.3 枚举

### DataPermissionType（数据范围类型）

| 值 | 名称 | 说明 | 子表 `entityIds` |
| :-- | :-- | :-- | :-- |
| 0 | My | 自己（自动拥有，无需配置） | 不使用 |
| 1 | MyPart | 自己部门：本人每条组织链上最后一级部门及其下属组织 | 不使用 |
| 2 | MyCompany | 自己公司：本人每条组织链上第一级公司及其下属组织 | 不使用 |
| 3 | ManyUser | 多人 | 用户 id |
| 4 | ManyPart | 部分（多部门、多公司），含所选组织的下属组织 | 组织 id |
| 5 | All | 全部 | 不使用 |
| 6 | ExcludeUser | 排除人员：这些人的数据不可见，优先于所有范围权限 | 用户 id，不能为空 |

### ManageType（操作类型）

| 值  | 名称 | 说明                                               |
| :-- | :--- | :------------------------------------------------- |
| 0   | Get  | 查询：列表、详情、分组                             |
| 1   | Edit | 编辑：编辑、删除等写操作的校验（删除也用编辑口径） |

### DataPermissionModule（数据权限模块）

值与 `FrightModule` 是同一个模块的必须同名同值；13 起是 `FrightModule` 暂时没有的模块。完整列表见 2.3 的表。

`FrightModule` 里有、这里不放的：1 业务费用、2 业务表（按业务类型走，见 2.4）；10 提单（跟随海运出口、件杂货）；6 空运进口、7 运价、11 运价箱型（没有数据权限过滤）。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：排除人员的人员口径按各模块自己的过滤方法定]** 被排除的人在这条数据上是下表任一角色，这条数据就不可见：
>
> | 过滤方法 | 人员口径 |
> | :-- | :-- |
> | 业务扩展表（海运出口、海运进口、空运出口、件杂货）、主单、费用 | 所属人、创建人、干系人（销售/商务/操作/客服/单证/海外客服/航线） |
> | 业务联系单 | 所属人、创建人、干系人（同上七种） |
> | 客户 | 所属人、干系人 |
> | 客户联系人 | 对接人 |
> | 通用 `DataPermissionFilterAsync` | 所属人 |
> | 进项发票 | 不参与（只按公司过滤） |

> [!IMPORTANT] **[卡点 2：排除一律生效，包括自己经手的]** 被排除人只要是某票的任一干系人或创建人（哪怕只是航线），这票对被限制的人就不可见，包括他自己当销售的单。全部权限也挡。

> [!IMPORTANT] **[卡点 3：共享的客户不受排除影响]** 客户设成「共享所有人」或「共享本公司」（且当前用户属于该公司）时照样可见，共享是所属人主动放开的。

> [!IMPORTANT] **[卡点 4：「全部」加排除名单时不能直接返回整表]** 所有过滤方法只有在「全部且排除名单为空」时才直接返回原查询。监装工单列表「全部权限不挂海运出口子查询」的捷径同样只在没有排除人员时走。

> [!IMPORTANT] **[卡点 5：提成人被排除时不能新建]** 新建提成单选提成人时，提成人在排除名单里直接报「提成人不在您的数据权限范围内」，全部权限也拒。

> [!IMPORTANT] **[卡点 6：保存规则的校验]** 报错文案见接口文档第 4 节。
>
> - 用户和角色不能同时传，也不能都不传；用户或角色必须存在。
> - 模块有值时必须存在。
> - 排除人员子项不能为空；用户规则不能排除规则所属用户自己（角色规则保存时判断不了，解析时会把当前用户自己去掉）。
> - 唯一性按「用户或角色 + 操作类型 + 权限类型 + 模块」。

> [!IMPORTANT] **[卡点 7：新实体接数据权限前必须登记模块]** 通用过滤和业务扩展表过滤按被过滤的实体从 `DataPermissionEntityModules` 取模块，没登记的直接抛「实体 xxx 没有登记数据权限模块」。不回退到通用规则：回退不会泄露数据，但给该模块配的规则会静默失效。以后放开 `OrderFeeTemplate`、`Agreement` 等现在被注释掉的过滤时，要先在表里登记。

> [!IMPORTANT] **[卡点 8：模块枚举的编号约定（没有启动校验）]** `FrightModule` 的 13～20 已被 `DataPermissionModule` 占用（收费结算、付款结算、发票开出、开票申请、银行流水、提成单、进项发票、客户联系人）。`FrightModule` 以后加值要跳过这一段；加的正好是其中某个模块时，用同一个值。两边枚举上都写了注释。

## 5.9 自己读规则的两处

| 位置 | 规则怎么取 | 说明 |
| :-- | :-- | :-- |
| `OrganizationUnitAppService.GetMyPermissionCompaniesAsync`（按数据权限返回公司下拉） | `GetEffectiveDataPermissionsAsync(module, 查询)`，前端不传模块时只看通用规则 | 公司的换算算法不变，排除人员不影响公司列表。接口说明见组织机构文档 2.5 |
| `BankStatementAppService.GetPermissionUserIdsAsync`（银行流水列表按操作人过滤、操作校验） | 银行流水模块在查询、编辑两种口径下生效的「多人」子项，加上自己 | 只取「多人」：部门 id、排除人员不能当成可操作的人 |

## 5.10 已知限制（本次不处理）

1. **财务单据按做单人判定。** 收费结算、付费申请、发票开出、开票申请、付款结算、银行流水按单据自己的所属人（做单的财务）过滤。排除 B 以后，B 的业务单和费用看不到了，但财务做的这些单据里仍会带出 B 的客户和金额。
2. **客户联系人只按对接人判定。** 被排除人名下客户的联系人，对接人是别人或为空时仍然可见。
3. **费用模块自己的列表没接数据权限。** `OrderFeeAdminAppService.GetPagedListAsync` 的业务单 id 选填，不传能查到所有费用；审核页可能按费用 id 调它，接上会让审核人看不到无权限单的费用，所以保持现状。`DetailAsync` 与各审核任务列表同样未接。
4. **表级权限的角色规则不生效。** `TablePermissionsAsync` 仍从 `user.Roles` 取角色（恒为空），角色上配的表级权限不生效，属表级权限的现存问题。
