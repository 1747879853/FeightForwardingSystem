## 一、核心组件与文件清单

## 二、完整执行流程

```
HTTP 请求到达（携带用户 Token）
       │
       ▼
[PropMaskActionFilter.OnActionExecutionAsync]
       │
       ├─ PropMaskProvider.GetCurrentUserMaskedFieldsAsync()
       │    ├─ IAbpSession 取当前用户 ID
       │    ├─ UserManager 取用户，再直接查 AbpUserRoles 拿角色列表
       │    ├─ IUnitOfWorkManager.Begin() 开启独立工作单元（ActionFilter 在 ABP UoW 之前执行）
       │    ├─ 查询 UserPropPermission 表:
       │    │    WHERE (UserId = 当前用户) OR (RoleId IN 用户角色列表)
       │    ├─ 每条规则的 ConditionJson 解析成条件树（按 JSON 原文静态缓存）
       │    └─ 组装成 PropMaskRuleSet：模块 -> (属性名 -> 该属性的规则列表)
       │
       ├─ 存入 HttpContext.Items["PropMaskedFields"]（键名常量 PropMaskActionFilter.ItemsKey）
       │
       ▼
[Controller Action 正常执行]（业务代码无任何屏蔽逻辑）
       │
       ▼
[ASP.NET Core 序列化 JSON 响应]
       │
       ├─ PropMaskContractResolver.CreateProperty（每个类型首次序列化时触发，后续缓存）
       │    ├─ 检查 member.DeclaringType 上的 [PropMaskModule] 属性
       │    ├─ 有该属性 → 设置 ShouldSerialize 委托，属性名取 property.UnderlyingName
       │    └─ 无该属性 → 不拦截
       │
       ├─ ShouldSerialize 委托（每个实例每个属性序列化时触发）
       │    ├─ 从 HttpContext.Items 读取 PropMaskRuleSet
       │    ├─ PropMaskRuleSet.IsMasked(module, propName, instance)
       │    │    └─ 遍历该属性的规则，任一命中即屏蔽
       │    │         ├─ 无条件规则 → 恒命中
       │    │         └─ 带条件规则 → 从 instance 上取判据属性的值递归求值
       │    ├─ 命中 → return false → 字段从 JSON 中消失
       │    └─ 未命中 → return true → 正常输出
       │
       ▼
JSON 响应返回（被屏蔽字段完全不存在于 JSON 中，不是 null）
```

**关键点**：`ShouldSerialize` 的入参 `instance` 就是**正在序列化的那一行对象**，条件里的判据属性直接从它身上取值。所以条件屏蔽是**逐行判定**的：同一个列表里，满足条件的行没有这个字段，不满足的行照常返回。

### 输入侧流程（编辑提交）

```
[编辑接口] 从库里查出既有实体 dbEntity
       │
       ├─ PropMaskInputGuard.RestoreMaskedFieldsAsync(inputDto, dbEntity, module)
       │    ├─ 遍历该模块下所有配了规则的属性名
       │    ├─ IsMasked(module, propName, dbEntity)  ← 注意求值对象是 dbEntity 而非 inputDto
       │    └─ 命中 → 用 dbEntity 上的原值覆盖 inputDto 的同名属性
       │
       ▼
[业务代码正常校验、正常 entity.X = input.X]（赋的已经是原值，等于没改）
```

## 三、数据模型

**数据库表：UserPropPermission**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| Id | long | 主键 |
| UserId | long? | 用户 ID，与 RoleId 二选一 |
| RoleId | int? | 角色 ID，与 UserId 二选一 |
| FrightModule | enum | 模块枚举 |
| PropName | string | 要屏蔽的属性名（PascalCase） |
| Description | string | 规则描述（管理备注，不影响逻辑） |
| ConditionJson | string(2000) | 条件表达式，**为空表示无条件屏蔽**（存量数据全为空，行为不变） |

**条件表达式结构**（递归条件树，只有两种节点）：

```json
{
  "logic": "and",
  "items": [
    { "prop": "IndustryCategory", "op": "In", "value": [1, 4] },
    { "prop": "PaySide", "op": "Equals", "value": 1 }
  ]
}
```

- 分组节点：`logic`（`and`/`or`，缺省 `and`）+ `items`
- 叶子节点：`prop`（判据属性名）+ `op`（操作符）+ `value`（比较值）+ `showName`/`showValue`（纯回显）
- 顶层可以直接是叶子节点，嵌套最多 5 层（保存时校验）

**`showName` / `showValue` 只用于前端回显，不参与求值。** `PropMaskConditionEvaluator` 从头到尾只读 `prop`/`op`/`value`，改了展示文本不会影响屏蔽行为。存在的原因是 `value` 里是原始值（枚举存数字、外键存 id），前端再次编辑这条规则时光靠 `5` 没法显示成「马士基」。

| 判据类型 | showValue 来源 |
| --- | --- |
| 枚举 | 保存时**后端自动补全**（从枚举成员的 Display/Description 取），前端不传也有 |
| 外键 id（客户/港口/费用代码…） | **必须前端提交时一并传**，后端不知道该查哪张表 |
| 数字/字符串/日期/布尔 | 一般不需要 |

`showName` 后端一律兜底（`ResolveShowName` 取属性上的 Display/Description）。

保存流程是 `ValidateAndNormalizeRule`：校验 → 补全 showName/showValue → 用 `NullValueHandling.Ignore` 重新序列化 → **回写 ConditionJson 落库**。所以库里存的一定是补全后的版本。 `Op` 上挂了 `StringEnumConverter`，读取时数字和枚举名都认，写回统一用枚举名，方便直接看懂库里的配置。

这套约定与表级别权限的 `UserTablePermissionCondition.ShowName` / `ShowValue` 一致。

> **展示文本是保存时的快照**，客户改名后旧规则里的 `showValue` 会过期，与表级别权限行为一致。只影响显示，不影响屏蔽——求值只认 `value` 里的 id。

> **`ConditionJson` 列长度是 2000，加了展示字段之后没变。** 需要留意的是：一个 `In` 条件如果带几十个 Guid（每个 38 字符）再加同样数量的展示文本，单个节点就接近 1000 字符，两三个这样的节点会超长。真遇到超长报错时，优先考虑把条件拆成多条规则（同一字段的多条规则是「任一命中即屏蔽」，等价于 or），而不是无限堆 `In` 列表。

**操作符**（`PropMaskConditionOperator`，命名与表级别权限的 `UserTablePermissionOperator` 对齐，JSON 里可写枚举名或数字）：

| 枚举名             | 值  | 说明                                   |
| ------------------ | --- | -------------------------------------- |
| Equals             | 0   | 等于                                   |
| NotEquals          | 1   | 不等于                                 |
| In                 | 2   | 属于，`value` 必须是数组               |
| NotIn              | 3   | 不属于，`value` 必须是数组             |
| IsNull             | 4   | 为空，不需要 `value`；字符串空白也算空 |
| IsNotNull          | 5   | 不为空，不需要 `value`                 |
| GreaterThan        | 6   | 大于                                   |
| GreaterThanOrEqual | 7   | 大于等于                               |
| LessThan           | 8   | 小于                                   |
| LessThanOrEqual    | 9   | 小于等于                               |
| Contains           | 10  | 字符串包含，不区分大小写               |

**值比较的归一化规则**（`PropMaskConditionEvaluator.Compare`）：

| 属性实际类型 | 归一化方式 | 条件值可写成 |
| --- | --- | --- |
| 枚举 | 转 decimal 比数值 | 数字，或枚举成员名（如 `"船公司"`） |
| 数值 / 布尔 | 转 decimal | 数字字面量、`true`/`false` |
| DateTime | 转 DateTime | ISO 8601 字符串 |
| Guid / 字符串 / 其它 | `ToString()` 后按 **OrdinalIgnoreCase** 比较 | 字符串 |

**FrightModule 枚举**（定义在 `Core/CsprojBuilderEnum.cs`）：

| 枚举名             | 值  | 说明       |
| ------------------ | --- | ---------- |
| SeaExport          | 0   | 海运出口   |
| OrderFee           | 1   | 业务费用   |
| TransportOrder     | 2   | 业务表     |
| PaymentApplication | 3   | 付费申请   |
| SeaImport          | 4   | 海运进口   |
| AirExport          | 5   | 空运出口   |
| AirImport          | 6   | 空运进口   |
| SeFreiPrice        | 7   | 运价       |
| PreOrder           | 8   | 业务联系单 |
| Client             | 9   | 客户       |

> `PaymentApplication`、`AirImport`、`PreOrder`、`Client` 目前**没有任何 DTO 标 `[PropMaskModule]`**，给这些模块配规则不会有任何效果，保存时也会跳过属性/判据校验（见坑点 B11）。

**规则合并逻辑**：

```
用户最终屏蔽字段 = 直接为该用户配置的规则 ∪ 该用户所有角色配置的规则
```

只能做加法（更多屏蔽），无法通过用户级规则覆盖/取消角色级规则。

### 报表模块的处理方式

**报表自身的字段不参与屏蔽。** `ProfitReportDto` / `ArrearsReportDto` / `ProfitCurrencyDto` / `ArrearsCurrencyDto` （合计金额、币别明细、超期天数、发票号等）都**没有**标 `[PropMaskModule]`，也没有为报表新增 FrightModule。

**报表里的业务信息复用所属业务模块的规则**，按数据真正的归属分配，而不是按"它出现在报表里"分配：

- 业务主单字段（委托单位、主提单号、委托编号、销售/操作/客服/单证、件数重量尺码等）→ `TransportOrder`
- 船名、航次、港口、船公司、场站、签单方式 → 各归 `SeaExport` / `SeaImport` / `AirExport`

**收益**：一条规则同时管住业务列表和报表。给 `SeaExport` 配了 `Vessel` 屏蔽，海运出口列表和报表里的船名一起看不到，不需要在报表上重复配一遍，也不会出现"列表屏了、报表漏了"的不一致。

**代价与注意点**：

1. **两张报表之间无法区分。** `ReportTransportOrderDto` 等 5 个类是利润报表和欠费报表共用的，一个类只能标一个模块，所以做不到「委托编号在欠费报表显示、在利润报表不显示」。真要区分只能把这 5 个类复制成两套（约 255 行翻倍），或者给它们加一个报表类型判据字段走条件屏蔽。当前判断都不值得。
2. **报表与业务列表也无法区分。** 屏了就是两边都屏。
3. **字段名要对得上。** 屏蔽按属性名匹配，报表 DTO 与业务 DTO 同名的字段（`Vessel`、`MblNum`、`CommissionNum`、 `POLRemark` 等）现有规则直接生效；名字不同的要单独配，典型的是报表的 `BizDate`（业务日期，按业务类型取开船/到港/起飞日期），业务 DTO 那边叫 `ETD`，所以要在 `TransportOrder` 模块下单独加一条 `BizDate`。
4. **上线即生效。** 库里已有的 `SeaExport` / `TransportOrder` 等规则，上线后会立刻开始作用于报表。如果不希望某条规则影响报表，只能把该字段从规则里去掉——没有"只屏列表不屏报表"的开关。
5. **共享简易 DTO 内部的字段仍屏不到。** `Client`、`Carrier`、`POL`、`Orgs`、`Sales` 这些是 `ClientSimpleDto` / `CarrierSimpleDto` / `SeaAirPortSimpleDto` / `OrganizationUnitSimpleDto` / `UserSimpleDto`，全项目共享、没标特性。能屏掉整个对象（属性声明在报表 DTO 上），屏不掉对象里的 `Name`、`Code`。

**报表只读，输入侧不需要任何处理**：没有编辑接口，不用调 `PropMaskInputGuard`，坑点 B10 / B10-1 那套「回填要早于校验」在报表上不存在。

## 四之二、条件判据可以用哪些属性

**该模块 DTO 上的任何标量属性都可以当判据，不需要标任何特性、不需要后端事先声明。**

保存规则时只校验两件事（`PropMaskTypeRegistry`）：

1. 该属性在这个模块的某个 DTO 上真实存在（含从基类继承来的公共属性）
2. 该属性的类型可以做值比较

可以做判据的类型：枚举、数值、布尔、`DateTime`、`Guid`、`string`（含各自的可空形式）。不可以的：集合（`List<T>` 等）、嵌套 DTO 对象——它们没法做值比较，配了会在保存时报错。

**注意区分两个角色**（这是最容易混淆的地方）：

| 角色       | 位置              | 限制             |
| ---------- | ----------------- | ---------------- |
| 被屏蔽字段 | 规则的 `PropName` | 任何属性         |
| 判据属性   | 条件里的 `prop`   | 任何**标量**属性 |

管理端可以调 `GetConditionSourcesAsync` 一次性拿到候选属性列表、类型分类以及枚举的可选值，展示名取属性上已有的 `[Display]` 或 `[Description]` 特性（例如 `OrderFeeDto.IndustryCategory` 已经标了 `[Description("行业类别")]`），都没有就回退到属性名。

## 七、坑点清单

### 7.1 后端坑点

#### 坑点 B1：继承属性无法屏蔽（重要）

`PropMaskContractResolver` 中使用 `member.DeclaringType` 检查 `[PropMaskModule]`。对于继承来的属性，`DeclaringType` 是基类而非当前 DTO。

```
SeaExportDto [有 PropMaskModule]
  └── 继承自 DataPermissionFullAuditedEntityDto<Guid> [无 PropMaskModule]
       └── 继承自 FullAuditedEntityDto<Guid> [无 PropMaskModule]
            └── 继承自 AuditedEntityDto<Guid> [无 PropMaskModule]
```

**结果**：以下属性**无法被屏蔽**：

- `Id`、`CreationTime`、`CreatorUserId`、`LastModificationTime`（来自 ABP 基类）
- `IsDeleted`、`DeleterUserId`、`DeletionTime`（来自 ABP 基类）
- `UserId`、`OrganizationUnits`、`Companys`（来自 `DataPermissionFullAuditedEntityDto`）

**只有直接声明在标记了 `[PropMaskModule]` 的类上的属性才能被屏蔽。**

如果未来需要屏蔽继承属性，需要修改 `PropMaskContractResolver`，将 `member.DeclaringType` 改为遍历检查实际序列化类型及其继承链。

#### 坑点 B2：PropName 已有校验，但只在"已标注模块"上生效

保存规则时 `ValidateRule` 会校验 `PropName` 真实存在于该模块的 DTO 上，拼写错误会直接报「模块【X】下不存在属性【Y】」。

**但有一个前提**：该模块必须至少有一个 DTO 标了 `[PropMaskModule]`。对于还没标注的模块（`PaySide`… 即 `PaymentApplication`、`AirImport`、`PreOrder`、`Client`），`PropMaskTypeRegistry.HasModule` 返回 false，属性和判据校验会**整体跳过**，此时拼错仍然静默不生效。

这是故意的：这些模块本身不会发生屏蔽，如果硬校验会把正常配置也挡住。见坑点 B11。

#### 坑点 B3：PropName 不区分大小写

匹配使用 `HashSet<string>(StringComparer.OrdinalIgnoreCase).Contains()`，不区分大小写。

- 数据库存 `vessel`、`Vessel`、`VESSEL` 均可匹配 C# 属性 `Vessel`
- 建议统一存 PascalCase 保持规范，但大小写写错不影响功能

#### 坑点 B4：ActionFilter 在 ABP UnitOfWork 之前执行

`PropMaskActionFilter` 作为 MVC Filter 注册，执行时 ABP 的 `UnitOfWorkActionFilter` 还未创建工作单元。`PropMaskProvider` 内部已通过 `IUnitOfWorkManager.Begin()` 手动开启独立 UoW 解决此问题。

**如果修改 PropMaskProvider 的 DB 查询逻辑，务必保留 `using (var uow = _unitOfWorkManager.Begin())` 包裹。**

#### 坑点 B5：每次请求都查 DB

`PropMaskActionFilter` 对**所有请求**都执行（包括不涉及屏蔽 DTO 的接口，如登录、文件上传、SignalR 等），每次都查一次数据库。

当前无缓存，好处是规则修改即时生效，坏处是有额外的 DB 开销。如果性能成为问题，可以考虑加内存缓存（按用户 ID 缓存，规则变更时失效）。

#### 坑点 B6：规则只能做加法，不能做减法

用户屏蔽 = 用户直接规则 ∪ 角色规则。如果角色 A 屏蔽了 `Amount`，无法通过用户级配置"取消"这个屏蔽。要取消，只能删除角色上的规则或将用户移出该角色。

#### 坑点 B7：同模块同属性名影响所有 DTO

如果 `OrderFeeDto` 和 `OrderFeeAndTaskDto` 都标记为 `FrightModule.OrderFee`，配置 `PropName = "Remark"` 会同时屏蔽两个 DTO 的 `Remark` 属性。同一模块下所有 DTO 共享屏蔽规则。

#### 坑点 B8：PropMaskProvider 异常会阻断整个请求

如果 `PropMaskProvider` 抛异常（如 DB 连接失败），`PropMaskActionFilter` 会把异常向上抛出，导致整个 API 请求返回 500，而不是"跳过屏蔽正常返回数据"。

如需容错，可在 `PropMaskActionFilter` 中 catch 异常并 log，让请求继续但不做屏蔽。

#### 坑点 B10：编辑会把无查看权限的字段覆盖成空（已修复）

屏蔽只在**输出侧**生效，被屏蔽字段不出现在响应 JSON 中。前端编辑表单因此拿不到这些字段，提交时输入 DTO 对应属性为 `null`/默认值。若编辑方法直接 `entity.X = input.X`，会把数据库原值覆盖成空。

**修复**：新增 `PropMaskInputGuard`（输入侧保护），在编辑方法**赋值之前**调用，使被屏蔽字段不被改动。根据编辑写法选用两个方法之一：

- `RestoreMaskedFieldsAsync(input, dbEntity, module)`：单条/逐条编辑（有一一对应的数据库实体、无条件赋值 `entity.X = input.X`）。用数据库原值回填输入。
- `ClearMaskedFieldsAsync(input, module)`：共享一份输入批量更新多条记录、按 `if (input.X.HasValue)` 决定是否更新的场景。把输入中被屏蔽字段清空为默认值，使其不参与更新（不能用回填，否则会把单条记录的值写到所有记录上）。

已覆盖的编辑方法：

| AppService | 方法 | 方式 | 模块 |
| --- | --- | --- | --- |
| SeaExportAdminAppService | `EditAsync` | 回填 ×2 | SeaExport + TransportOrder |
| SeaImportAdminAppService | `EditAsync` | 回填 ×2 | SeaImport + TransportOrder |
| AirExportAdminAppService | `EditAsync` | 回填 ×2 | AirExport + TransportOrder |
| TransportOrderAdminAppService | `EditAsync` | 回填 | TransportOrder |
| SeFreiPriceAdminAppService | `EditAsync`、`BatchEditSimpleAsync`、`ChangeRecommendAsync` | 回填 | SeFreiPrice |
| SeFreiPriceAdminAppService | `BatchEditAsync` | 清空 | SeFreiPrice |
| OrderFeeAdminAppService | `BatchEditAsync`、`SubmitOrderFeeAsync`、`ModifyOrderFeeAsync` | 回填 | OrderFee |
| ChangeOrderAdminAppService | `EditAsync` | 回填 | OrderFee（跨模块改费用） |

**新增可屏蔽模块时务必两侧都处理**：输出侧加 `[PropMaskModule]`，输入侧在**每一个**编辑方法里调用 `PropMaskInputGuard`（单条/逐条用 `RestoreMaskedFieldsAsync`，共享输入批量更新用 `ClearMaskedFieldsAsync`）。一个 AppService 可能有多个编辑方法（如 SeFreiPrice 有 4 个），都要覆盖。

**别的模块改本模块的实体时也要调**：`ChangeOrderAdminAppService.EditAsync` 改的是 `OrderFee` 实体，所以要用 `FrightModule.OrderFee` 调回填。判断依据是**被赋值的实体属于哪个模块**，不是当前 AppService 叫什么。

#### 坑点 B10-1：回填必须早于校验和外键批量查询（极易踩，会导致用户完全无法提交）

被屏蔽字段提交上来是 `null`/`0`。如果回填放在业务校验之后，这些值会先撞上必填/存在性校验：

| 位置 | 校验代码 | 屏蔽 SettlementId 的后果 |
| --- | --- | --- |
| `OrderFeeAdminAppService.SubmitOrderFeeAsync` | `if (!item.SettlementId.HasValue) throw "提交时结算对象不能为空"` | 该用户**永远无法提交费用** |
| `OrderFeeAdminAppService.ModifyOrderFeeAsync` | `if (!item.SettlementId.HasValue) throw "结算对象不能为空"` | 该用户**永远无法申请修改** |
| `ChangeOrderAdminAppService.EditAsync` | `if (settlementIds.Count != existClientIds.Count) throw "结算对象id错误"` | 该用户**永远无法保存更改单** |

还有第二层：这些方法会先按**入参里的 id** 批量查 `feeCodes`/`clients` 做存在性校验。如果回填晚于这个查询，回填出来的 id 不在查询结果里，会被误判成「结算对象id=x不存在」。

**所以回填的正确位置是：实体查出来之后、收集外键 id 之前**。上表三个方法已按此调整。

`ModifyOrderFeeAsync` 的校验写在同步的 `orderFees.Select(...)` lambda 里没法 `await`，所以回填提到了 `Select` 之前用独立 `foreach` 做。

> **既有遗留**：`OrderFeeAdminAppService.BatchEditAsync` 的回填仍在校验之后（第 487 行左右）。它的 `SettlementId` 校验是宽松的（`item.SettlementId.HasValue &&` 才校验存在性），所以屏蔽结算对象不受影响；但如果将来去屏蔽 `FeeCodeId` 或 `CurrencyId`，会撞上第 456-457 行的 `<= 0` 必填校验。届时需要同样上移。

#### 坑点 B9：非 HTTP 场景不生效

本方案依赖 `HttpContext`，以下场景**无法自动屏蔽**：

- 后台 Job / Hangfire 任务
- SignalR Hub 直接推送的数据
- 数据导出（如果在 Service 层直接序列化）

这些场景如需屏蔽，需手动调用 `PropMaskProvider` 获取规则并处理。

#### 坑点 B11：判据必须与被屏蔽字段在**同一个对象**上（架构硬边界）

`ShouldSerialize` 的入参只有当前正在序列化的那个对象，**拿不到它的父对象**。所以条件只能引用同一个 DTO 上的属性。

可以：`OrderFeeDto.SettlementId` 的条件引用 `OrderFeeDto.IndustryCategory`（同一个 DTO）不可以：`OrderFeeDto.SettlementId` 的条件引用 `TransportOrderDto.BizType`（父对象上的字段）

**将来要跨层级条件时的推荐做法**（按成本从低到高）：

1. 把父对象的判据字段冗余一份到子 DTO（可以 `[JsonIgnore]`，只为求值用），条件退化成同对象比较。冗余关系必须写进本文档，否则是隐性耦合。
2. 实在撑不住，再改成请求级对象树遍历：在 `PropMaskActionFilter` 的 `await next()` **之后** 拿到 `ObjectResult.Value` 递归遍历。代价是要写反射遍历，深层嵌套 + 大列表开销明显。

#### 坑点 B12：条件求值失败一律按"屏蔽"处理（fail-closed）

以下情况都会判定为**命中（屏蔽）**，而不是放行：

| 情况                              | 原因                                     |
| --------------------------------- | ---------------------------------------- |
| 判据属性在当前对象上不存在        | 同模块下多个 DTO 字段覆盖不一致时会出现  |
| `ConditionJson` 解析失败          | 退化成无条件规则，即恒屏蔽               |
| 操作符未知                        | 库里存了代码不认识的值                   |
| 条件值与属性类型不可比            | 例如给枚举字段配了一个解析不出来的字符串 |
| `In`/`NotIn` 的所有条件值都不可比 | 同上                                     |

理由：字段级权限属于安全功能，宁可多屏不可漏屏。保存时的校验已经能拦住绝大多数脏配置，所以运行时走到 fail-closed 分支通常意味着**规则和 DTO 已经不同步了**（比如改了属性名但没改库里的规则）。

**排查现象**：某字段莫名对某用户整体消失了 → 先看它的规则条件里的 `prop` 是否还存在于该 DTO 上。

#### 坑点 B13：输入侧的条件必须拿 dbEntity 求值，不能拿 inputDto

`RestoreMaskedFieldsAsync` 里 `IsMasked(module, propName, dbEntity)` 传的是**数据库实体**。因为决定"用户当初看没看到这个字段"的是库里的旧值，不是他这次提交上来的新值。

反例（如果错写成拿 `inputDto` 求值）：

1. 规则：`IndustryCategory = 船公司` 时屏蔽 `SettlementId`
2. 某条费用原本是船公司，用户看不到 `SettlementId`
3. 用户把类别改成发货人并提交，`SettlementId` 是 null
4. 拿新值（发货人）求值 → 判定未屏蔽 → 不回填
5. 结果：他从没见过的 `SettlementId` 被清空

拿旧值求值则第 4 步判定屏蔽、回填原值，第 5 步类别更新为发货人、结算对象保留原值，正确。

另外注意：判据属性要在**实体**上也存在。`IndustryCategory` 在 `Entites.OrderFee` 上有，所以能求值；如果判据是 DTO 上的计算字段，实体上取不到 → 走 fail-closed → 回填（安全方向）。

#### 坑点 B14：批量编辑不做条件求值，一律保守跳过

`ClearMaskedFieldsAsync` 用于「一份输入作用到多条记录」的批量编辑，此时拿不到单条数据库实体， **没有对象可以拿来求值**。所以它的策略是：该字段只要对当前用户存在**任何**规则（无条件的或带条件的），就一律清空跳过，不做条件求值。

后果：这些字段该用户永远无法批量编辑（即使某些行并不满足屏蔽条件）。这是有意选择的保守策略——代价是功能受限，收益是绝不会出现"条件命中的那几行被越权覆盖"。

### 7.2 前端坑点

#### 坑点 F1：字段是"消失"而不是"null"

被屏蔽的字段**不出现在 JSON 中**，不是值为 `null`。

```javascript
// 正常
{ "vessel": "MSC", "remark": "备注" }

// 屏蔽 vessel 后
{ "remark": "备注" }
// response.vessel === undefined（不是 null）
```

前端如果用 `if (data.vessel === null)` 判断，会漏掉 `undefined` 的情况。应该用 `if (!data.vessel)` 或 `if (data.vessel == null)`（双等号同时匹配 null 和 undefined）。

#### 坑点 F2：PropName 与 JSON 字段名格式不同

- 后端 PropName 是 PascalCase：`CommissionNum`
- JSON 响应是 camelCase：`commissionNum`
- 前端做字段映射时需注意转换

如果前端调用 `GetCurrentUserMaskedFields` 拿到的 `propName` 是 PascalCase（如 `Vessel`），需要转成 camelCase（`vessel`）才能跟 JSON 数据的 key 匹配。

#### 坑点 F3：一个页面需要合并多个模块的屏蔽规则

海运出口详情页需要合并 `SeaExport` + `TransportOrder` + `OrderFee` 三个模块的规则。不能只检查 `SeaExport` 就认为处理完了。

各页面涉及的模块：

| 页面     | 需要检查的模块            |
| -------- | ------------------------- |
| 海运出口 | SeaExport, TransportOrder |
| 业务费用 | OrderFee, TransportOrder  |
| 业务表   | TransportOrder, OrderFee  |
| 运价     | SeFreiPrice               |

#### 坑点 F4：数值计算受影响

如果 `Amount`（金额）字段被屏蔽，JSON 中该字段不存在。前端如果做合计/小计计算：

```javascript
// 错误：undefined 参与计算结果是 NaN
let total = items.reduce((sum, item) => sum + item.amount, 0); // NaN

// 正确：兜底处理
let total = items.reduce((sum, item) => sum + (item.amount || 0), 0);
```

#### 坑点 F5：表格列/表单字段需双重隐藏

屏蔽后：

1. 表格列应隐藏（否则显示空列）
2. 详情/编辑表单的对应字段也应隐藏
3. 搜索/筛选条件中如果有该字段，也应隐藏

三处都要处理，漏掉任意一处体验都会不一致。

#### 坑点 F6：缓存与实时性

后端无缓存，管理员改规则后下次请求即生效。但如果前端在登录时缓存了屏蔽列表，则需要：

- 管理员修改规则后通知前端刷新
- 或在关键页面进入时重新拉取屏蔽列表
- 或设置缓存过期时间

#### 坑点 F8：条件字段不能整列隐藏（条件屏蔽引入的新坑）

`GetCurrentUserMaskedFieldsAsync` 返回的字段语义从"一定看不到"变成了"**可能**看不到"。响应结构：

```json
{
  "propName": "SettlementId",
  "alwaysMasked": false,
  "rules": [
    { "description": "...", "conditionJson": "{...}", "isConditional": true }
  ]
}
```

| `alwaysMasked` | 含义 | 前端处理 |
| --- | --- | --- |
| `true` | 存在无条件规则，所有行都看不到 | 可以直接隐藏整列 / 整个表单项 |
| `false` | 只有条件规则，部分行看不到 | **绝不能隐藏整列**，只能按行判断单元格 |

如果对 `alwaysMasked = false` 的字段隐藏整列，本来能看的那些行也被藏了，属于过度屏蔽。

**按行判断的正确写法**：看该行响应里有没有这个 key。

```javascript
// 正确
const canSee = 'settlementId' in row;

// 错误：值为 null 可能是业务上就是空，不代表被屏蔽
const canSee = row.settlementId != null;
```

#### 坑点 F9：前端不要自己解析 conditionJson

`conditionJson` 返回给前端只是为了展示规则和排查问题。**不要**用它在前端预判某行会不会被屏蔽——前端的实现很容易和后端的求值细节产生偏差（大小写不敏感、枚举名/数值两种写法、类型归一化、以及 fail-closed 的各种分支）。屏蔽已经由后端在序列化时做完了，前端只需要看 key 在不在。

#### 坑点 F7：导出/打印场景

如果前端基于 API 返回的数据做导出（Excel、PDF），被屏蔽的字段在数据中不存在，导出结果也会缺少这些列。这是期望行为，但需要向用户说明。

### 7.3 测试坑点

#### 坑点 T1：必须测试的场景矩阵

| 场景 | 验证点 |
| --- | --- |
| 用户级规则 | 配置给用户 A → 用户 A 看不到，用户 B 正常看到 |
| 角色级规则 | 配置给角色 X → 该角色下所有用户看不到 |
| 用户+角色叠加 | 用户自身屏蔽 A，角色屏蔽 B → 用户同时看不到 A 和 B |
| 嵌套 DTO | 屏蔽 TransportOrder 的字段 → 海运出口中嵌套的 TransportOrderDto 也被屏蔽 |
| 列表页 | 列表中每条记录的相同字段都被屏蔽（不是只屏蔽第一条） |
| 详情页 | 详情接口的响应同样受屏蔽 |
| 无规则用户 | 没有任何屏蔽规则 → 所有字段正常返回 |
| 未登录 | 未登录请求 → 不屏蔽（PropMaskProvider 判断无 UserId 直接返回空规则） |

#### 坑点 T8：条件屏蔽必须测的场景（新增）

| 场景 | 验证点 |
| --- | --- |
| 条件命中 | 行业类别=船公司的费用 → 响应里**没有** settlementId 这个 key |
| 条件未命中 | 同一个列表里行业类别=发货人的费用 → 响应里**有** settlementId 且值正确 |
| 同列表混合 | 一次列表请求里两种行都有 → 逐行判定正确，不是整列消失或整列保留 |
| 多规则叠加 | 同一字段配一条无条件 + 一条带条件 → 任一命中即屏蔽，实际表现为恒屏蔽 |
| and / or 分组 | 两个条件 and → 都满足才屏蔽；改成 or → 任一满足就屏蔽 |
| 枚举值两种写法 | `"value":[1,4]` 与 `"value":["船公司","航空公司"]` 效果一致 |
| 判据本身也被屏蔽 | 同时屏蔽 IndustryCategory 和条件依赖它的 SettlementId → 条件仍能正确求值（屏蔽只影响输出，不改对象） |
| 保存校验 | `prop` 填不存在的属性 → 报错；`prop` 填集合/嵌套对象属性 → 报错；`In` 的 `value` 填非数组 → 报错；枚举字段填乱字符串 → 报错 |
| 嵌套超限 | 条件嵌套超过 5 层 → 报错 |

#### 坑点 T9：编辑回写必须专门测（最容易出事故的地方）

| 场景 | 验证点 |
| --- | --- |
| 编辑不清空 | 屏蔽 SettlementId 后编辑该费用并保存 → 数据库里 SettlementId **保持原值** |
| 改判据字段逃逸 | 原本命中条件（船公司），编辑时把类别改成发货人并保存 → 类别更新成功，**SettlementId 仍保留原值**且没被清空 |
| 提交费用 | 屏蔽 SettlementId 后调 `SubmitOrderFeeAsync` → **能提交成功**，不报"提交时结算对象不能为空" |
| 申请修改 | 屏蔽 SettlementId 后调 `ModifyOrderFeeAsync` → **能提交成功**，不报"结算对象不能为空" |
| 更改单保存 | 屏蔽 SettlementId 后保存更改单 → **能保存成功**，不报"结算对象id错误" |
| 批量编辑 | 屏蔽字段在批量编辑里被跳过，其它字段正常更新 |

其中"能提交成功"这几条是回归重点：回填位置放错（晚于校验）就会让该用户完全无法提交，而且报的是"结算对象不能为空"这种看起来跟权限毫无关系的错误，很难联想到字段屏蔽。

#### 坑点 T2：验证"字段消失"而非"字段为 null"

测试时不能只看界面上是否显示，要检查 API 响应的 JSON：

- 被屏蔽的字段应该**不存在于 JSON 中**（key 不存在）
- 而不是 `"vessel": null`

可以用浏览器 F12 Network 或 Postman 直接查看原始响应。

#### 坑点 T3：PropName 拼写错误不报错

如果管理员输入了 `Vessal`（拼写错误），不会有任何错误提示，接口正常返回，但 `Vessel` 字段不会被屏蔽。

测试时需验证：配置规则后实际看到字段确实消失了。

#### 坑点 T4：同名属性在不同 DTO 中的影响

`Remark` 属性在 `SeaExportDto`、`OrderFeeDto`、`TransportOrderDto`、`SeFreiPriceOutDto` 中都存在，但属于不同 `FrightModule`。

- 屏蔽 `SeaExport` 的 `Remark` → 只影响海运出口的 Remark
- 屏蔽 `OrderFee` 的 `Remark` → 只影响费用的 Remark
- 要全部屏蔽需要每个模块都配置

#### 坑点 T5：规则修改即时生效

修改/删除规则后，不需要重新登录，下一个 API 请求即可验证效果。

#### 坑点 T6：继承属性不可屏蔽

配置 `SeaExport` 模块的 `PropName = "Id"` 或 `PropName = "CreationTime"` → **不生效**。因为这些属性声明在 ABP 基类中，不在标记了 `[PropMaskModule]` 的类上。（参见坑点 B1）

#### 坑点 T7：全部属性被屏蔽的极端情况

如果一个 DTO 的所有属性都被屏蔽，JSON 返回的是空对象 `{}`，而不是 `null`。嵌套场景中，父对象的该属性值是 `{}`（空对象），不是不存在。

## 八、性能说明

| 环节 | 频率 | 开销 |
| --- | --- | --- |
| PropMaskActionFilter DB 查询 | 每次 HTTP 请求 | 2 次 DB 查询（角色 + 规则，无缓存） |
| ConditionJson 解析 | 每个不同的 JSON 原文一次 | `ConcurrentDictionary` 静态缓存，跨请求复用 |
| PropMaskTypeRegistry 扫描 | 进程内一次 | `Lazy` 扫描整个 Application 程序集，之后纯字典查找 |
| CreateProperty | 每个 DTO 类型首次序列化 | 反射读取 Attribute，后续被 Newtonsoft 缓存 |
| ShouldSerialize | 每个实例每个属性 | Dictionary.TryGetValue + 字典查找，O(1) |
| 条件求值 | 每个**带条件规则**的属性每行一次 | 编译委托取值 + 值比较，无反射 |

**判据取值不走反射**：`PropMaskAccessor` 按 `(类型, 属性名)` 缓存 `Expression.Lambda` 编译出来的 `Func<object, object>`，性能接近直接属性访问。缓存键用 `instance.GetType()`，所以派生 DTO（如 `OrderFeeAndTaskDto : OrderFeeDto`）会各自缓存，不会互相干扰。

## 九、PropName 大小写说明

| 场景 | 格式 | 示例 |
| --- | --- | --- |
| 数据库 PropName | 建议 PascalCase | `CommissionNum` |
| C# 属性名 | PascalCase | `CommissionNum` |
| JSON 响应字段名 | camelCase | `commissionNum` |
| 屏蔽匹配 | **不区分大小写** | `commissionNum` = `CommissionNum` = `COMMISSIONNUM` |

匹配使用 `StringComparer.OrdinalIgnoreCase`，大小写写错不影响屏蔽生效。建议统一存 PascalCase 保持规范。

## 十、AI 修改指引

### 修改屏蔽逻辑时

1. 核心文件见第一节，改之前先把 `PropMaskProvider`、`PropMaskContractResolver`、`PropMaskCondition`、`PropMaskInputGuard` 这四个读全
2. `PropMaskContractResolver.CreateProperty` 中的 `ShouldSerialize` 委托是运行时执行的，但 `CreateProperty` 本身被 Newtonsoft 缓存，只在首次序列化该类型时调用。**所以任何依赖当前用户的判断都必须写在委托里面，不能写在 `CreateProperty` 里**
3. `PropMaskProvider` 中的 DB 查询必须包裹在手动 UoW 中（坑点 B4）
4. 属性名匹配一律用 `property.UnderlyingName`，**不要**用 `property.PropertyName`——基类 `DecimalPrecisionContractResolver` 设了 `CamelCaseNamingStrategy`，后者已经是小驼峰，跟库里的 PascalCase 对不上

### 新增可屏蔽 DTO 时

输出侧：在 DTO 类上加 `[PropMaskModule(FrightModule.XXX)]`。输入侧：该模块**每一个**编辑方法都要调 `PropMaskInputGuard`，且位置要早于校验（坑点 B10、B10-1）。

### 新增可作条件判据的属性时

**什么都不用做。** 只要属性声明在该模块某个标了 `[PropMaskModule]` 的 DTO 上、且是标量类型，就自动可用作判据，`PropMaskTypeRegistry` 扫描时会带上它。

想让管理端下拉里显示中文名，就在属性上加 `[Description("中文名")]`（很多 DTO 属性本来就有）。

如果要扩大可比较类型的范围（例如支持 `TimeSpan`），改 `PropMaskTypeRegistry.IsComparableType`，同时要在 `PropMaskConditionEvaluator.Compare` 里加上对应的比较分支，否则保存能过但运行时会走 fail-closed 恒屏蔽。

### 修改屏蔽规则匹配逻辑时

匹配入口是 `PropMaskRuleSet.IsMasked(module, propName, instance)`，内层字典用 `StringComparer.OrdinalIgnoreCase`，属性名不区分大小写。条件求值在 `PropMaskConditionEvaluator.IsMatch`，值比较在同文件的 `Compare`。

改求值语义时注意 fail-closed 的一致性（坑点 B12）：目前所有"无法求值"的分支都返回**命中**。如果要改成 fail-open，必须同时评估输入侧的影响——输入侧 fail-open 意味着**不回填**，会导致数据被覆盖成空。

### 要支持继承属性屏蔽时

当前 `member.DeclaringType` 的口径是**有意保留**的（继承自 ABP 基类的 `Id`、`CreationTime` 等不参与屏蔽，见坑点 B1、T6）。如果确实要支持，改法是把 `CreateProperty` 换成重写 `CreateProperties(Type type, MemberSerialization)`——它的 `type` 参数就是正在建合约的具体类型，可以用 `type.GetCustomAttribute<PropMaskModuleAttribute>(inherit: true)` 判断，且合约同样按类型缓存。

**改之前先查库里现有规则**：一旦支持，那些原本静默无效的规则会突然开始生效。

### 要加缓存时

在 `PropMaskProvider` 中加 `IMemoryCache`，key 为 `userId`，修改规则时清除对应用户的缓存。注意角色规则变更时需清除该角色下所有用户的缓存。

### 要支持继承属性屏蔽时

需修改 `PropMaskContractResolver` 第 28 行：

```csharp
// 当前：只检查声明该属性的类
var maskAttr = member.DeclaringType?.GetCustomAttribute<PropMaskModuleAttribute>();

// 改为：检查实际序列化的类型（需获取 property.DeclaringType 或通过其他方式获取运行时类型）
```

注意 Newtonsoft 的 `CreateProperty` 中没有直接提供"正在为哪个类型创建合约"的信息，可能需要 override `CreateProperties` 来传递类型上下文。

### 要加缓存时

在 `PropMaskProvider` 中加 `IMemoryCache`，key 为 `userId`，修改规则时清除对应用户的缓存。注意角色规则变更时需清除该角色下所有用户的缓存。
