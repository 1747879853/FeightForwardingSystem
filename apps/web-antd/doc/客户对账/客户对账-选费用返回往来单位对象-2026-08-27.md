# 背景意图

`StatementAdminAppService.GetOrderFeeGroupAsync`（对账单加费用时的「选择费用」）返回 `TransportOrderDto`，其中的往来单位对象字段（委托单位、委托单位联系人、车队、报关行、仓库、保险公司、收货人、发货人、通知人）**一直没有赋值，恒为 `null`**，前端只能拿到 `xxxId`，展示名称还得再换一次接口。本次按「外键以对象返回、禁止平铺」的规范全部补齐。

# 核心逻辑变更

1. 新增注入 `IRepository<Entites.ClientContact, long> _clientContactRepository`。
2. 按本页业务（`orderResult`）汇总去重 8 类客户 id（`ClientId`/`TeamId`/`CustBrokerId`/`WarehouseId`/`InsuranceId`/`ConsigneeId`/`ShipperId`/`NotifierId`），一次性投影成 `ClientSimpleDtoForOrder` 字典；`Address` 取客户地址子表 `IsDefault=true` 的那条。
3. 同理汇总 `ClientContactId` 一次性投影成 `ClientContactSimpleDto` 字典。
4. 组装 `TransportOrderDto` 时用局部函数 `MapOrderClient` / `MapOrderContact` 按 id 取字典赋值，未维护则为 `null`。
5. 取值口径与 `SeaImportAdminAppService` 的 `MapClient` / `MapContact` 完全一致，字段含义在各模块之间保持统一。

# 避坑指南

- **必须批量查再查字典**：往来单位有 9 个外键，若在 `Select` 里逐个查库就是每行 9 次查询，分页 20 行即 180 次。现按本页 id 汇总去重后只查两次（客户一次、联系人一次）。
- **地址不是客户主表字段**：`ClientSimpleDtoForOrder.Address` 来自 `ClientAddresses` 子表 `IsDefault=true` 的记录，直接读 `Client` 上的其它地址字段口径会和海运进口/空运出口不一致。
- **收发通有两套数据**：`consignee`/`shipper`/`notifier` 是客户对象，`consigneeContent`/`shipperContent`/`notifierContent` 是抬头自由文本，两者互不替代，都要返回。
- **联系人 id 用 `> 0` 判有效**：`ClientContactId` 是 `long?`，历史数据存在 `0` 的情况，只判 `HasValue` 会查出空结果并误判。
