# 背景意图

客户对账「加费用」弹窗调用 `StatementAdmin/GetOrderFeeGroupAsync` 拉取可对账费用时，关联人员筛选只支持**单选**（`SaleId` / `OperatorId` / `CustomerServiceId` 各一个 id）。实际对账场景里，财务经常要一次性把**某几个销售名下**、或**某个操作小组（多人）**的业务费用一起捞出来对账，单选只能反复查多次再人工拼，效率低且容易漏。

本次把这三个筛选项改为**多选**，并**删除原有的单选字段**（不做兼容保留，避免同一语义存在两套入参）。

# 核心逻辑变更

## 1. 入参字段替换（破坏性）

文件：`src/CsprojBuilder.Application/App/Statement/Dto/StatementDto.cs` → `GetOrderFeeGroupInputDto`

| 原字段 | 原类型 | 新字段 | 新类型 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| `SaleId` | `long?` | `SaleIds` | `List<long>` | 销售 多选 命中任一即可 |
| `OperatorId` | `long?` | `OperatorIds` | `List<long>` | 操作 多选 命中任一即可 |
| `CustomerServiceId` | `long?` | `CustomerServiceIds` | `List<long>` | 客服 多选 命中任一即可 |

三个字段均**选填**，不传或传空数组等价于不筛选。

## 2. 查询逻辑

文件：`src/CsprojBuilder.Application/App/Statement/StatementAdminAppService.cs` → `GetOrderFeeGroupAsync`（业务查询段）

```csharp
//销售/操作/客服均为多选 命中任一即可 关联的是用户id(OrderUser.UserId) 不是子表行id
.WhereIf(input.SaleIds != null && input.SaleIds.Count > 0, m => m.OrderUsers.Any(u => input.SaleIds.Contains(u.UserId) && u.UserAttribute == UserAttribute.Sale))
.WhereIf(input.OperatorIds != null && input.OperatorIds.Count > 0, m => m.OrderUsers.Any(u => input.OperatorIds.Contains(u.UserId) && u.UserAttribute == UserAttribute.Operation))
.WhereIf(input.CustomerServiceIds != null && input.CustomerServiceIds.Count > 0, m => m.OrderUsers.Any(u => input.CustomerServiceIds.Contains(u.UserId) && u.UserAttribute == UserAttribute.CustomerService));
```

判空口径沿用本文件既有的 `FeeCodeIds` 写法（`!= null && Count > 0`），保持与同一方法内其他集合入参一致。

**组间是 AND，组内是 OR**：同时传 `saleIds` 与 `operatorIds` 时，业务必须「销售命中其中之一」**且**「操作命中其中之一」才返回；同一个字段内的多个 id 之间是 OR。这与三个 `WhereIf` 各自独立叠加的写法一致，也符合前端多选筛选的直觉。

`OrderUsers` 已在主查询上 `Include`，`Any` 走 EF 的 `EXISTS` 子查询，不额外产生查询。

## 3. 顺带修复：筛选比对的是子表行id而非用户id

改造前三个条件写的是 `u.Id == input.SaleId.Value`：

- `OrderUser.Id` 是子表 `App_OrderUsers` 的行主键（`Entity<long>` 自增）；
- `OrderUser.UserId` 才是关联的用户id。

前端传的一直是用户id，却被拿去比子表行主键，因此这三个筛选**改造前基本查不到正确结果**（只会在行主键与用户id偶然相等时误中）。本次改为 `u.UserId`，与 `SeaExportAdminAppService`、`SeaImportAdminAppService`、`AirExportAdminAppService` 三处业务列表的正确口径对齐。

## 4. 未受影响的部分

- 数据权限：多选筛选在 `DataPermissionFilterTransportOrderAsync` / `TablePermissionsAsync` **之前**叠加，对账人绕过全量数据权限的既有逻辑不变。
- 出参：`PagedList<TransportOrderDto>` 结构、费用分组、业务类型简要（`seaExport` / `seaImport` / `airExport`）赋值口径全部不变。
- 费用侧过滤（`IncludeStatemented`、`StatementId`、排除审核中费用）不变。

# 避坑指南

- **前端必须同步改造，旧参数直接失效。** `saleId` / `operatorId` / `customerServiceId` 已从 DTO 删除，继续传旧参数不会报错、只会被模型绑定**静默忽略**，表现为「筛选了但没生效、返回全量」。这是本次最容易漏的坑，务必全局搜一遍调用点。
- **`List<long>` 走 GET 查询串必须重复键名**：`?saleIds=1&saleIds=2`。传 `saleIds=1,2` 这种逗号串不会被绑定成两个元素。
- **不要拿 `OrderUser.Id` 当用户id用。** 同一坑位在以下三处仍然存在（本次未在需求范围内，未改动，后续修同类问题时一并处理）：
  - `PaymentApplicationAdminAppService.cs` `GetOrderFeeGroupAsync`（付费申请选费用）
  - `OrderFeeAdminAppService.cs` 费用任务列表相关的两处查询
- **`UserAttribute` 在 `OrderUser` 上只存单值**（实体注释明确「在这里不能存多个 只能一个一个存」），所以判定用 `==` 而非位运算 `HasFlag`；一个用户在同一业务里兼任销售与操作时是**两行**记录，多选筛选天然能覆盖。
- 传了不存在的用户id不会报错，只会筛不出数据，接口不做用户id有效性校验。
