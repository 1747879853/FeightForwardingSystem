# 背景意图

`GetOrderFeeGroupAsync`（选可对账费用）原来强制要求先传 `settlementId`，界面上必须先选定结算对象才能看到任何费用，没法先按业务/单号把费用捞出来再决定对哪一家的账。

本次把 `settlementId` 改成非必填。放开之后列表里就可能同时出现多个结算对象的费用，而**一张对账单只能对一个结算对象**（对账单头的 `clientId` 就是它，后续按对账单生成开票申请/付费申请时还会逐条比对），因此把这道约束从「查询时隐式过滤」搬到「写入时显式校验」。

# 核心逻辑变更

## 1. `GetOrderFeeGroupInputDto.SettlementId` 改为可空

文件：`src/CsprojBuilder.Application/App/Statement/Dto/StatementDto.cs`

`Guid` → `Guid?`。费用查询由固定条件改为条件过滤：

```csharp
.WhereIf(input.SettlementId.HasValue, x => x.SettlementId == input.SettlementId.Value)
```

## 2. 对账人免数据权限的判定跟着改

同一个方法里还有一处用 `input.SettlementId`：当前登录人若是该结算对象的对账人（`App_ClientReconcilers`），则跳过数据权限返回全部费用。

不传结算对象时无从判定「是谁的对账人」，因此直接判为不是对账人、老老实实走数据权限：

```csharp
var isReconciler = AbpSession.UserId.HasValue && input.SettlementId.HasValue
    && await _clientReconcilerRepository.GetAll().AnyAsync(x => x.ClientId == input.SettlementId.Value && x.UserId == AbpSession.UserId.Value);
```

这是**收紧**不是放宽：对账人不传 `settlementId` 时看到的费用会比传了少。要享受对账人免权限，就得把 `settlementId` 传上。

## 3. 新建 `AddAsync` 与加费用 `AddFeesAsync` 显式校验结算对象

两处原来都是在查费用时顺手加一个 `x.SettlementId == 对账单客户` 的过滤，然后靠「查出来的条数 != 传入条数」报一句笼统的 `关联费用输入错误`。现在去掉该过滤，改为查回来后逐项判：

```csharp
if (orderFees.Any(x => x.SettlementId == null)) throw new UserFriendlyException("存在未设置结算对象的费用 不可对账");
if (orderFees.Select(x => x.SettlementId.Value).Distinct().Count() > 1) throw new UserFriendlyException("所选费用的结算对象不一致 不可对账");
if (orderFees[0].SettlementId.Value != 对账单客户Id) throw new UserFriendlyException("费用的结算对象与对账单客户不一致");
```

| 方法           | 比对基准                                 |
| :------------- | :--------------------------------------- |
| `AddAsync`     | `input.ClientId`（新建时传入的对账客户） |
| `AddFeesAsync` | `statement.ClientId`（对账单已有的客户） |

`AddFeesAsync` 只跟对账单客户比即可，不必再跟单里已有费用两两比——已有费用当初也是过了同一道校验才进来的，三方必然一致。

费用查询的投影相应多取一列 `SettlementId`（`OrderFeeDto` 上本来就有这个字段）。

# 避坑指南

- **报错文案变了，前端别再按老文案匹配。** 以前跨结算对象选费用报的是 `关联费用输入错误`，现在按原因分成三句：`存在未设置结算对象的费用 不可对账` / `所选费用的结算对象不一致 不可对账` / `费用的结算对象与对账单客户不一致`。`关联费用输入错误` 现在只剩「费用 id 不存在或已被删除」这一种含义。
- **录入状态的费用结算对象可空。** `OrderFee.SettlementId` 是 `Guid?`（录入可空、提交必填），不传结算对象浏览时这类费用也会被列出来，选中后会撞上第一条报错。前端若想避免，可自行按 `settlement` 是否为空置灰。
- **不传 `settlementId` 时费用查询会全表扫。** 该方法里 `var items = await orderQuery.ToListAsync();` 是**不分页**的（分页发生在后面的业务表查询上），而且费用查询这一层**没有数据权限过滤**（权限加在随后的 `TransportOrder` 查询上）。原来靠必填的 `settlementId` 把范围压住，现在放开后，如果其它筛选条件也全不传，这一句会把全租户「未对账 + 无审核中修改删除任务」的费用整批拉进内存。界面上请尽量至少带一个筛选条件（结算对象/会计期间/单号/委托单位等）。
- **一张对账单仍然只能有一个结算对象。** 放开的只是查询，不是对账单的结构。跨结算对象混选出来的费用必然在提交时被拦，前端最好在选择阶段就限制成单一结算对象，别等报错。
- 本次没有动 `EditAsync`：它只改对账单主表，不碰费用关联，也不允许改 `ClientId`（该行代码本来就是注释掉的），所以不存在「改客户后费用结算对象对不上」的问题。

# 已知问题（本次未改）

- **`AddAsync` / `AddFeesAsync` 里的「不可添加不同本位币的费用」校验实际上是失效的。** 这两处把费用投影成 `new OrderFeeDto { Id = ..., OrgId = ... }` 时**没有带 `TransportOrderId`**，而 `SetOrderFeeOrgsFromOrderAsync` 是按 `TransportOrderId` 去匹配主单组织并填充 `Orgs` 的，匹配不上就 `continue`，于是 `Orgs` 恒为 null、`localCurrencyIds` 恒为空集合，`Count > 1` 永远不成立。付费申请的 `AddAsync` / `AddByStatementAsync` 用的是同一套写法，同样失效。修法是在投影里补一列 `TransportOrderId = x.TransportOrderId`，但这会让一条**从未真正生效过**的校验突然开始拦人，可能挡住现有数据与操作习惯，因此本次只记录、不改动。
