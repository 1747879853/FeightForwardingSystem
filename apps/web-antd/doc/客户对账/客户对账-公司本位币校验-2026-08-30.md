# 1. 背景意图 (Background)

客户对账原来的本位币校验是这么写的：

```csharp
var localCurrencyIds = orderFees
    .Select(m => m.Orgs?.FirstOrDefault(o => o.LocalCurrencyId.HasValue)?.LocalCurrencyId)
    .Where(x => x.HasValue).Select(x => x.Value).Distinct().ToList();
if (localCurrencyIds.Count > 1) throw new UserFriendlyException("不可添加不同本位币的费用");
```

这段有三个问题，每一个都能让本位币不同的费用混进同一张对账单：

1. **没有基准。** 它只保证「这批费用彼此本位币一致」，**完全没有跟对账单自己所属公司的本位币比过**。整批都是 B 公司的费用照样能挂进 A 公司的对账单。
2. **`.Where(x => x.HasValue)` 把判不出来的静默放行了。** 费用所属业务没有组织、或所属公司没配本位币时，这条费用直接从集合里消失，等于把「不知道本位币」当成了「本位币一致」。
3. **`FirstOrDefault(o => o.LocalCurrencyId.HasValue)` 取的不是公司。** 组织串是从顶到底排的，这取的是最顶层那个配了本位币的节点。本位币按规定只配在公司上，但集团节点一旦配过就会取到集团的。

本次改成：**先由对账单所属公司解析出本位币作为基准，再逐条比对每一笔费用所属公司的本位币，有一条对不上就报错。**

# 2. 核心逻辑变更 (Core Logic)

## 2.1 新的校验口径

```
基准本位币 = 对账单 OrgId → 向上找到所属公司 → 该公司的 LocalCurrencyId
            取不到 → 报「当前公司未配置本位币」

逐条费用   = 费用所属业务 TransportOrder.OrgId → 所属公司 → LocalCurrencyId
            为空          → 报「存在未设置所属组织的费用 无法校验本位币」
            公司没配本位币 → 报「存在所属公司未配置本位币的费用」
            与基准不等     → 报「存在与当前公司本位币不一致的费用 不可添加」
```

统一封装在基类 `EnsureOrgsLocalCurrencyAsync(orgIds, localCurrencyId)`，基准取值用 `EnsureCompanyLocalCurrencyIdAsync(orgId)`。

## 2.2 三个入口全部要校验

> [!IMPORTANT] **只改新建是不够的，另外两个入口能绕过校验。**

| 接口 | 基准取自 | 校验范围 | 说明 |
| :-- | :-- | :-- | :-- |
| `POST …/StatementAdmin/AddAsync` | `input.OrgId` | 入参的全部费用 | 新建 |
| `PUT …/StatementAdmin/EditAsync` | `input.OrgId` | 本单**已有**的全部费用 | 编辑虽然「只改主表」，但它能改 `OrgId`。组织一换所属公司就换了，本位币可能与单里已挂的费用对不上，所以拿新 `OrgId` 去比现有费用 |
| `PUT …/StatementAdmin/AddFeesAsync` | `statement.OrgId` | 新加的费用 | **这才是往对账单里塞费用的真正入口**，不改这里，新建拦住的东西可以从这里绕进来 |

`AddFeesAsync` 只校验新加的费用——单里已有的当初进来时就已经比过同一个基准了。

## 2.3 全部财务模块统一口径

**凡是能往单据里塞费用的入口，一律按同一口径校验**，避免出现「同一批费用在对账里被拦、在别处能过」。每个模块内各有一个私有方法 `EnsureFeesLocalCurrencyAsync(orderFeeIds, orgId)` 承载这段逻辑。

| 模块 | 接口 | 基准取自 | 校验范围 |
| :-- | :-- | :-- | :-- |
| 客户对账 | `AddAsync` | `input.OrgId` | 入参费用 |
| 客户对账 | `EditAsync` | `input.OrgId` | 本单**已有**费用（它能改 `OrgId`） |
| 客户对账 | `AddFeesAsync` | `statement.OrgId` | 新加费用 |
| 付费申请 | `AddAsync` | `input.OrgId` | 入参费用 |
| 付费申请 | `AddByStatementAsync` | `statement.OrgId`（付费申请的 `OrgId` 本就取自对账单） | 对账单下全部费用 |
| 付费申请 | `PayAppItemAddAsync` | `paymentApplication.OrgId` | 新加费用 |
| 付费结算 | `AddByCurrencyAsync` | `input.OrgId` | 本次结算行涉及的费用 |
| 付费结算 | `AddItemsByCurrencyAsync` | `settlement.OrgId` | 新加结算行涉及的费用 |
| 收费结算 | `AddAsync` | `input.OrgId` | 入参费用 |
| 收费结算 | `AddItemsAsync` | `settlement.OrgId` | 新加费用 |
| 收费结算 | `AddByInvoiceApplicationAsync` | `input.OrgId` | 开票明细对应的费用 |
| 收费结算 | `AddItemsByInvoiceApplicationAsync` | `settlement.OrgId` | 新加开票明细对应的费用 |

> [!NOTE] **付费结算的 `AddAsync` / `AddItemsAsync` 没有改**，因为它们已经整块注释停用了（源码注明「已停用 改走按『付费申请+原币币别』的 AddByCurrencyAsync」），活的只有按币别那两个入口。

## 2.4 销售提成走的是「按组织过滤」，不是本位币校验

销售提成的票是**按销售自动收集**的，用户没法逐票勾选取消。所以这里刻意不报错，而是在取数时 **只取所属组织落在提成单 `OrgId` 及其所有下级组织范围内的业务**，其余的直接不纳入。

> [!NOTE] **提成这边不需要逐票比本位币。** 本位币配在公司节点上，同一公司下所有业务的本位币必然相同， `OrgId` 一旦把范围圈定在某个公司（或其下的部门）内，圈进来的票本位币天然一致。所以这里用 `GetOrgAndDescendantIdsAsync` 取组织范围、条件直接下推 SQL，而不像结算类单据那样把费用捞回内存逐条解析公司本位币。

理由：跨公司的销售如果报错，就彻底建不了提成单了；而按组织过滤之后，他可以在两个公司各建一张——这正是新建时把 `OrgId` 改成必填的意义。

过滤点统一在 `LoadSalesTicketsAsync` 里，5 个调用点全部覆盖：新建前确认（已结算/未结算两次）、新建（未结算校验 + 取票两次）、以及**提交审核时的未结算复查**。

> [!IMPORTANT] **未结算校验也必须一起过滤。** 漏掉的话，A 公司的提成单会被 B 公司未结算的票永久卡住，报「存在 N 票未全部结算」但用户在 A 公司里怎么找都找不到那些票。提交审核那处最容易漏。

## 2.5 数据权限基类返回本位币

`DataPermissionFullAuditedEntityDto<TPrimaryKey>` 新增两个字段：

| 字段名              | 类型     | 含义                               |
| :------------------ | :------- | :--------------------------------- |
| `localCurrencyId`   | `long?`  | `orgId` **所属公司**配置的本位币id |
| `localCurrencyCode` | `string` | 同上，币别代码                     |

由 `SetDataPermissionPropsAsync` 与 `orgs` 一并填充，**各模块不用自己写**。同理 `SetOrderFeeOrgsFromOrderAsync` 也统一填了费用的 `localCurrencyId` / `localCurrency`。

`OrganizationUnitSimpleDto`（`orgs` 数组的元素）新增 `isCompany` 字段，用来定位组织串里哪一级是公司。

> [!NOTE] 这两个字段会出现在**所有继承 `DataPermissionFullAuditedEntityDto` 的返回体**上，共 29 个 DTO：客户对账、业务简要、海运出口/进口、空运出口、预配单、提成单、提成配置、合同、付费申请、付费结算、收费结算、开票申请、发票开出、银行流水、自动费用模板、发票备注模板。
>
> `orgId` 为空、未归属公司、或公司没配本位币时为 `null`。

### `StatementDto` 去掉了两个重复字段

| 原字段 | 现在 |
| :-- | :-- |
| `localCurrencyId`(`long?`) | **删除**，改由基类提供（值与口径都变了，见下） |
| `localCurrency`(`CurrencySimpleDto`) | **删除**，改用基类的 `localCurrencyCode` |

> [!IMPORTANT] 前端原来读 `statement.localCurrency.code` 的地方要改成读 `statement.localCurrencyCode`。
>
> 另外 `localCurrencyId` 虽然名字没变，**取值口径变了**：以前是「组织串上第一个有本位币的节点」，现在是「所属公司」。集团节点配过本位币的租户，这个值会跟着变。

# 3. 避坑指南 (Pitfalls)

- **本位币一律由基类填，不要在模块里再写一遍。** 本次删掉了 8 处散落的 `Orgs.FirstOrDefault(o => o.LocalCurrencyId.HasValue)`（客户对账 3 处、付费申请 2 处、业务费用 2 处、更改单 1 处）。再写一份就会出现「同一个响应里 `orderFee.localCurrencyId` 是老口径、`statement.localCurrencyId` 是新口径」。
- **新校验会拦住以前能过的数据。** 以前静默放行的两种情况（费用所属业务没组织、所属公司没配本位币）现在直接报错。上线前应确认存量业务的 `OrgId` 都有值、且各公司都配了本位币，否则用户会大面积撞「存在未设置所属组织的费用」。
- **不要用「去重后种类数 > 1 才报错」的写法。** 那样写永远会把「判不出本位币」当成「一致」，这正是本次修掉的 bug。基类 `EnsureOrgsLocalCurrencyAsync` 是逐条判的，判不出来就报错。
- **`EditAsync` 的校验范围是「本单已有费用」而不是入参。** 因为它根本不收费用列表，它的风险来自改 `OrgId`。读代码时别以为这里写反了。
- **29 个 DTO 会多两个字段，但只有真的填了 `orgId` 的才有值。** 数据权限已停用的模块（如提成配置，见其总逻辑文档第 8 章）`orgId` 不写库，这两个字段自然恒为 `null`，不是 bug。
