# 一、变更概述

| # | 变更 | 影响 |
| :-- | :-- | :-- |
| 1 | 业务（整票）行新增 `recSettlementStatus`（应收整票结算状态）、`paySettlementStatus`（应付，本次恒为 `null`） | 新增字段 |
| 2 | 每条费用的 `combinedFeeStatus`（组合费用状态）**开始返回正确值**（以前恒为 `0`） | **行为修复，值会变** |
| 3 | 后端枚举 `SeaExportFeeStatus` 更名为 `CombinedFeeStatus` | **前端零改动**，JSON 仍是 int，取值不变 |

受影响接口只有两个：

| # | 接口 | 方法 | 路径 |
| :-- | :-- | :-- | :-- |
| 1 | GetOrderFeeGroupAsync | GET | `/api/services/app/StatementAdmin/GetOrderFeeGroupAsync` |
| 2 | DetailAsync | GET | `/api/services/app/StatementAdmin/DetailAsync` |

**入参一个都没改**，两个接口的请求参数与之前完全一致。

# 二、新增字段

## 2.1 业务（整票）层

`GetOrderFeeGroupAsync` 挂在 `items[]` 上，`DetailAsync` 挂在 `orderFeeGroups[].transportOrder` 上，字段名与含义一致。

| 字段名 | JSON Key | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| RecSettlementStatus | `recSettlementStatus` | int \| null | **应收整票结算状态**。按该业务下**全部应收费用**汇总，无应收费用为 `null` |
| PaySettlementStatus | `paySettlementStatus` | int \| null | 应付整票结算状态。**本次两个接口都不赋值，恒为 `null`**，先不要用 |

### 取值（SettlementStatus，与费用行的 `settlementStatus` 同一套枚举）

| 值     | 含义     | 何时出现                         |
| :----- | :------- | :------------------------------- |
| `null` | 无       | 该业务下一条应收费用都没有       |
| 0      | 未结算   | 全部应收费用都是未结算           |
| 1      | 部分结算 | 既不是全未结算，也不是全结算完毕 |
| 2      | 结算完毕 | 全部应收费用都已结算完毕         |

## 2.2 费用层

| 字段名 | JSON Key | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| CombinedFeeStatus | `combinedFeeStatus` | int | 单条费用的**组合费用状态**。字段本身早就有，本次才开始返回正确值 |

### 取值（CombinedFeeStatus，原 SeaExportFeeStatus，取值未变）

| 值  | 含义     |
| :-- | :------- |
| 0   | 录入状态 |
| 1   | 提交审核 |
| 2   | 审核通过 |
| 3   | 部分结算 |
| 4   | 结算完毕 |
| 5   | 驳回     |
| 6   | 申请修改 |
| 7   | 申请删除 |

**计算优先级：** 驳回 > 申请修改 > 申请删除 > 录入状态 > 提交审核 > 结算完毕 / 部分结算 / 审核通过。

与业务费用列表 `OrderFeeAdmin/GetPagedListAsync` 的 `combinedFeeStatus` 完全同源同规则，**展示映射表可以直接复用，不要另写一套**。

# 三、接口 1 — GetOrderFeeGroupAsync

**Summary：** 可对账费用按业务分组列表（给对账单加费用时用）。

**权限：** `Admin.Statement.Get` + `Admin.OrderFee.Get`

## 3.1 请求参数

**无变化**，沿用 `GetOrderFeeGroupInputDto`（`settlementId`、`includeStatemented`、`statementId`、`paySide`、`feeStatus`、`settlementStatus`、`saleIds`/`operatorIds`/`customerServiceIds` 等）。

## 3.2 响应示例（节选，只标出新增/变化字段）

```json
{
  "result": {
    "items": [
      {
        "id": "order-guid-001",
        "commissionNum": "SE2608200001",
        "bizType": 0,
        "recSettlementStatus": 1,
        "paySettlementStatus": null,
        "seaExport": {},
        "orderFees": [
          {
            "id": "fee-guid-001",
            "paySide": 0,
            "feeStatus": 2,
            "settlementStatus": 0,
            "combinedFeeStatus": 2,
            "amount": 1000.0
          },
          {
            "id": "fee-guid-002",
            "paySide": 0,
            "feeStatus": 2,
            "settlementStatus": 2,
            "combinedFeeStatus": 4,
            "amount": 500.0
          }
        ]
      }
    ],
    "totalCount": 1

  "success": true

```

> 上例里整票有两条应收费用（一条未结算、一条结算完毕），所以 `recSettlementStatus = 1`（部分结算）；而列表本身可能只返回其中一条（另一条已对过账被过滤掉），**整票状态不会因此变化**。

# 五、前端改动建议

1. **业务分组行加一列「整票结算状态」**，读 `recSettlementStatus`；`null` 显示为「-」或留空，不要显示成「未结算」。
2. **费用行的状态标签改读 `combinedFeeStatus`**，复用业务费用列表已有的颜色/文案映射；`feeStatus`、`settlementStatus` 原样保留，用于筛选与明细展示。
3. **`paySettlementStatus` 先别接**，现在恒为 `null`。

---

# 六、注意事项

> [!IMPORTANT] **1. `combinedFeeStatus` 的值会“突然变了”。** 这两个接口以前也返回该字段，但从未赋值，恒为 `0`（录入状态）。如果页面此前照着它渲染过标签，看到的一直是错的，本次是修复。

> [!IMPORTANT] **2. `recSettlementStatus` 和费用行的 `settlementStatus` 对不上是正常的。** 前者是整票全部应收费用的汇总，后者是单条费用自己的状态，两者不存在「加总相等」关系。

> [!IMPORTANT] **3. 整票状态不受列表筛选影响。** 后端是另查一次该业务下的全部应收费用算出来的，与结算对象、是否已对账、`settlementStatus` 等筛选条件无关。所以会出现「筛了未结算，但整票显示部分结算」的情况，这是预期行为。

> [!NOTE] **4. 枚举改名不影响前端。** 后端 `SeaExportFeeStatus` 更名为 `CombinedFeeStatus`，只是 C# 类型名，JSON 仍是 int，0~7 的含义一个没变；海运出口/海运进口/空运出口列表的 `receiveFeeStatus`、`payFeeStatus` 也是同一枚举，同样不受影响。
