# 背景意图

对账界面（选费用弹窗、对账单详情）按业务分组展示费用，但业务那一行只有单号、船名、港口这些静态信息，**看不出这票钱到底收没收回来**。要判断得靠人一条条去看费用行的结算状态，一票十几条费用时基本没法看。

同时，两个接口返回的 `OrderFeeDto` 里其实已经有 `combinedFeeStatus`（组合费用状态）字段，但**这两个接口从来没给它赋过值**，序列化出去恒为 `0`，也就是「录入状态」——前端如果照着 `orderFeeAdmin` 那套渲染标签，会把一条早就结算完毕的费用显示成「录入状态」，属于**返回了错误数据**，不是单纯的缺失。

本次做三件事：

1. 业务（整票）行新增**应收整票结算状态**，按该业务下**全部应收费用**汇总；
2. 两个接口的每条费用**补齐** `combinedFeeStatus`；
3. 枚举 `SeaExportFeeStatus` 更名为 `CombinedFeeStatus`（命名纠偏，海进/空出/业务费用早就都在用了）。

# 核心逻辑变更

## 1. 枚举更名 `SeaExportFeeStatus` → `CombinedFeeStatus`

文件：`src/CsprojBuilder.Core/CsprojBuilderEnum.cs`（region 名也由「海运出口组合费用状态」改为「组合费用状态」）

**纯类型改名，8 个取值、数值、`Description` 全部原样保留**，JSON 上是 int，前端零改动。跟着改的引用点：

| 文件 | 改动 |
| :-- | :-- |
| `Core/Helpers/CombinedFeeStatusHelper.cs` | 三个方法的返回类型与全部 `return` 分支 |
| `Application/App/SeaExport/Dto/SeaExportDto.cs` | `ReceiveFeeStatus` / `PayFeeStatus` |
| `Application/App/SeaImport/Dto/SeaImportDto.cs` | `ReceiveFeeStatus` / `PayFeeStatus` |
| `Application/App/AirExport/Dto/AirExportDto.cs` | `ReceiveFeeStatus` / `PayFeeStatus` |
| `Application/App/OrderFee/Dto/OrderFeeDto.cs` | `CombinedFeeStatus` 属性的类型 |

`OrderFeeDto` 上因此出现 `public CombinedFeeStatus CombinedFeeStatus { get; set; }`——属性名与类型名同名是 C# 合法写法（Color Color 规则），本仓库 `public SettlementType? SettlementType` 早就是这么写的。

## 2. `CombinedFeeStatusHelper` 新增整票结算状态计算

文件：`src/CsprojBuilder.Core/Helpers/CombinedFeeStatusHelper.cs`

```csharp
public static SettlementStatus? ComputeSettlementStatusForFees(IEnumerable<SettlementStatus> settlementStatuses)
```

| 条件                | 结果                     |
| :------------------ | :----------------------- |
| 没有费用            | `null`                   |
| 全部 `UnSettled`    | `UnSettled`（0）         |
| 全部 `Settlemented` | `Settlemented`（2）      |
| 其余                | `PartialSettlement`（1） |

入参刻意收成 `IEnumerable<SettlementStatus>` 而不是 `IEnumerable<OrderFee>`：调用方只需要结算状态一列，用投影查询（`Select(x => new { x.TransportOrderId, x.SettlementStatus })`）就够，不必把整票费用实体全部拉进内存。

## 3. DTO 新增字段

文件：`src/CsprojBuilder.Application/App/TransportOrder/Dto/TransportOrderDto.cs`，`TransportOrderDto` 与 `TransportOrderSimpleDto` **各加两个**：

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `RecSettlementStatus` | `SettlementStatus?` | 应收整票结算状态，本次两个接口赋值 |
| `PaySettlementStatus` | `SettlementStatus?` | 应付整票结算状态，**本次不赋值，恒为 null**，给以后的应付场景留位 |

这两个 DTO 被很多接口共用，其它接口不受影响（新字段一律 `null`）。

## 4. `GetOrderFeeGroupAsync`

- **整票结算状态**：在分页拿到 `orderResult` 之后，按 `pagedOrderIds` 单独查一次本页业务下的**全部应收费用**的结算状态，按业务分组算成 `receiveSettlementStatusMap`，映射时赋给 `data.RecSettlementStatus`。
- **每条费用的组合费用状态**：`data.CombinedFeeStatus = ComputeForFee(orderFee.FeeStatus, data.SettlementStatus, false, false)`。这里直接传两个 `false`，因为该接口在费用查询阶段就已经用 `pendingTaskFeeIdQuery` 把「申请修改/申请删除审核中」的费用整条排除了，**返回的费用不可能带待审任务**，再查一次 `TaskItem` 是纯浪费。
- 顺带把原本声明在「业务类型简要」region 里的 `pagedOrderIds` 上提到整票查询处，避免重复声明。

## 5. `DetailAsync`

- **待审任务**：对账单里的费用是**可以**事后被申请修改/申请删除的（费用侧的五条拦截是拦「已对账费用的改动动作」，任务本身可能早于对账建立），所以这里必须老老实实按 `detailOrderFeeIds` 查一次 `TaskItem`（`ModifyOrderFee`/`DeleteOrderFee` + `Auditing`），拆成 `pendingModifyFeeIds` / `pendingDeleteFeeIds` 传给 `ComputeForFee`。这是与选费用接口口径不同的唯一一处。
- **整票结算状态**：`transportOrderIds` 的声明从「获取业务数据」处上提到费用映射之前（整票查询要用），按业务下全部应收费用算 `receiveSettlementStatusMap`，在 `foreach (var transportOrder in transportOrders)` 里赋给 `transportOrder.RecSettlementStatus`，最终随 `orderFeeGroups[].transportOrder` 返回。

# 避坑指南

- **「整票」是真的整票，不是接口返回的那几条费用。** 两个接口都另起一次查询，条件只有 `TransportOrderId in (...)` + `PaySide = 收`，**完全不带**结算对象、是否已对账、费用状态、会计期间等本接口的筛选条件。若跟着筛选走，选费用接口默认只返回没对过账的费用，算出来永远是「未结算」，这一列就没有任何意义了。
- **`recSettlementStatus` 与费用行的 `settlementStatus` 不是同一口径，对不上是正常的。** 前者是整票应收的汇总，后者是这一条费用自己的状态；一票里只要有一条应收结算完毕、其余未结算，整票就是「部分结算」。
- **没有应收费用时返回 `null`，不是 0。** 全付费用的业务、或应收费用全被删掉的业务都会是 `null`，前端要按「无」渲染，不能当成「未结算」。
- **`paySettlementStatus` 恒为 `null`。** 字段先加上了，但两个接口都没赋值，前端现在不要拿它做任何展示或判断。
- **`combinedFeeStatus` 是本次才开始正确返回的。** 以前这两个接口也返回该字段，但恒为 `0`（录入状态）。如果前端此前拿它渲染过标签，看到的都是错的；改完之后值会突然“变化”，这是修复不是回归。
- **枚举改名不影响前端。** `SeaExportFeeStatus` → `CombinedFeeStatus` 只是 C# 类型名，序列化仍是 int，0~7 的含义一个没动。但**后端别的分支若正在用旧名字会编译不过**，合并时统一改成 `CombinedFeeStatus` 即可。
- **多了两次查询。** 每个接口各多一次「按业务查应收费用结算状态」的投影查询，`DetailAsync` 另多一次待审任务查询。投影只取两列且都是按主键/外键 `IN`，成本可控；但若以后把 `GetOrderFeeGroupAsync` 的 `pageSize` 放得很大，这一票票的应收费用量会跟着涨。
