# 背景意图

允许多次对账后，`StatementAdmin/GetOrderFeeGroupAsync` 传 `includeStatemented=true` 会把**已经在其他对账单里的费用**一起列出来。但该接口从来没有填充过 `OrderFeeDto.Statements`（返回恒为 `null`），前端在选费用弹窗里既分不清哪条费用已经对过账，也看不到它进了哪张单、是谁什么时候对的，只能盲选，容易把同一条费用重复挂进多张对账单。

本次让该接口返回每条费用的**已对账列表**（对账单号 + 对账时间 + 对账人昵称）以及一个**是否已对账**的布尔标记。

# 核心逻辑变更

## 1. `StatementSimpleDto` 新增两个字段

文件：`src/CsprojBuilder.Application/App/Statement/Dto/StatementDto.cs`

| 字段 | 类型 | 取值来源 | 说明 |
| :-- | :-- | :-- | :-- |
| `CreationTime` | `DateTime` | `Statement.CreationTime` | 对账时间，即对账单的创建时间 |
| `CreatorUserName` | `string` | `Statement.CreatorUserId` → `User.NickName` | 对账人昵称，即对账单的创建人 |

对账单号 `StatementNum` 与对账单id `Id` 原本就有，不变。

**取的是对账单主表的创建审计字段，不是对账明细子表 `StatementFee` 的。** 也就是说同一张对账单下的所有费用，`creationTime` / `creatorUserName` 完全相同；后续用 `AddFeesAsync` 往老单里补费用，这两个值仍然是对账单最初的创建时间与创建人，不会变成补费用那次操作的时间与操作人。

## 2. `OrderFeeDto` 新增 `IsStatemented`

文件：`src/CsprojBuilder.Application/App/OrderFee/Dto/OrderFeeDto.cs`

`IsStatemented`（bool）：该费用只要存在于**任意一张**对账单即为 `true`，与 `Statements` 非空完全等价。口径与费用侧「已参与对账的费用不可编辑/删除/申请修改/申请删除/驳回」五条卡点一致，都是「查子表是否命中」。

## 3. 新增统一填充器 `IOrderFeeStatementFiller`

新文件：`src/CsprojBuilder.Application/App/Statement/OrderFeeStatementFiller.cs`

改造前，「按费用id聚合出对账单集合」这段查询在 `OrderFeeAdminAppService`（私有方法 `GetStatementMapByOrderFeeIdsAsync`）和 `ChangeOrderAdminAppService`（内联）各写了一份，本次 `StatementAdminAppService` 又要用第三份。为避免三处口径漂移，抽成 `ITransientDependency` 填充器，对齐既有的 `ITransportOrderBizSimpleFiller` 模式：

```csharp
public interface IOrderFeeStatementFiller : ITransientDependency
{
    Task FillAsync(IEnumerable<OrderFeeDto> orderFees);
}
```

实现要点：

- 按费用id批量查 `App_StatementFees`，`OrderBy(x => x.Statement.StatementNum)` 保证列表按对账单号升序；
- 对账人昵称按 `Statement.CreatorUserId` 去重后批量查 `User`，不做 N+1；
- 未对账的费用 `Statements` 给**空数组**（不是 `null`），`IsStatemented = false`；
- `IsStatemented` 由 `Statements.Count > 0` 推导，两个字段不可能自相矛盾。

三处调用点全部收敛到它：

| 服务 | 方法 | 改动 |
| :-- | :-- | :-- |
| `StatementAdminAppService` | `GetOrderFeeGroupAsync` | **本次新增填充**（原先 `statements` 恒为 null） |
| `OrderFeeAdminAppService` | `GetPagedListAsync` | 删除私有方法 `GetStatementMapByOrderFeeIdsAsync` 与 `data.Statements = ...`，改调填充器；顺带获得新字段与 `isStatemented` |
| `ChangeOrderAdminAppService` | `DetailAsync` | 删除内联的 `statementRows`/`statementMap` 与失效的 `_statementFeeRepository` 注入，改注入填充器 |

## 4. 只填本页费用

`GetOrderFeeGroupAsync` 里的 `orderFeeResult` 装的是**全部命中费用**（含分页之外业务的费用），分页后由 `data.OrderFees = orderFeeResult.FindAll(...)` 挂到本页业务上。因此填充放在 `result` 组装完成之后、按实际返回的费用集合调用：

```csharp
await _orderFeeStatementFiller.FillAsync(result.SelectMany(x => x.OrderFees ?? new List<OrderFeeDto>()));
```

若图省事直接对 `orderFeeResult` 填充，会为用不到的费用白查一大批对账明细。

# 避坑指南

- **`isStatemented` 在默认模式下恒为 `false`。** 不传 `includeStatemented` 时接口只返回从未对账过的费用，所以这两个新字段只在 `includeStatemented=true` 时才有信息量。前端不要拿它当「本条费用是否已在本对账单中」用。
- **传了 `statementId` 时，`statements` 里不会出现该对账单。** 本对账单已包含的费用在费用查询阶段就被排除了，能返回的费用要么没对过账，要么只进过**别的**对账单。
- **`statements` 未做数据权限过滤。** 一条费用可能挂在当前登录人看不到的对账单上，对账单号照样会返回。这与 `OrderFeeAdmin/GetPagedListAsync`、`ChangeOrderAdmin/DetailAsync` 改造前的行为一致，本次未收紧。若业务上要求「看不到的单不给单号」，需要另开需求在填充器里统一加过滤。
- **对账时间/对账人不是「这条费用被对账的时间/操作人」**，是对账单本身的创建时间与创建人，详见上文第 1 节。用 `AddFeesAsync` 往老单补费用不会刷新这两个值。
- **新增字段是加法，不改也不删老字段**，但 `OrderFeeAdmin/GetPagedListAsync` 与 `ChangeOrderAdmin/DetailAsync` 的 `statements[]` 也会跟着多出这两个字段、费用上多出 `isStatemented`，回归时一并看一眼。
- 填充器返回的 `List<StatementSimpleDto>` 在同一条费用重复出现（同一费用挂在多个分组下）时是**同一个列表引用**，只读消费没问题，不要在调用侧原地改这个列表。
