# 二、两个额度是什么（先看这一节）

费用上有**两套口径不同的额度**，本次两个都给：

| 字段 | 建议列名 | 等于什么 |
| :-- | :-- | :-- |
| `orderInvoiceAmount` | 发票已占用额度 | 开票申请已申请 **+** 付费申请已申请（三种发票流程都算）。**不含**收费结算 |
| `settlementOccupiedAmount` | 结算已占用额度 | 付费申请已申请 **+** 收费结算已结算 **+** 开票申请已申请 |

> [!IMPORTANT] 两列**不能互相加减、也不能比大小**得出结论。它们参与项不同：发票额度不看收费结算，结算额度看。同一条费用两列不相等是正常的，差额就是收费结算掉的部分。
>
> `settlementOccupiedAmount` 也**不等于** `settledAmount`（已结算量）。前者含「被申请占住但还没结算」的钱，后者只含真结算掉的钱。

# 三、币别分组新增的 4 列

`statementCurrencyGroup` 数组的**每个元素**（即每个币别）新增：

| 字段名 | JSON Key | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| ReceiveInvoiceOccupiedAmount | `receiveInvoiceOccupiedAmount` | decimal | 该币别下**应收**费用的 `orderInvoiceAmount` 合计 |
| PayInvoiceOccupiedAmount | `payInvoiceOccupiedAmount` | decimal | 该币别下**应付**费用的 `orderInvoiceAmount` 合计 |
| ReceiveSettlementOccupiedAmount | `receiveSettlementOccupiedAmount` | decimal | 该币别下**应收**费用的 `settlementOccupiedAmount` 合计 |
| PaySettlementOccupiedAmount | `paySettlementOccupiedAmount` | decimal | 该币别下**应付**费用的 `settlementOccupiedAmount` 合计 |

该元素上原有字段（`currency` / `receiveAmount` / `payAmount` / `balanceAmount` / `currencyId` / `currencySortId`）**全部不变**。

> [!IMPORTANT] **没有**为这 4 列提供「应收−应付」的差额字段。已有的 `balanceAmount` 仍然只是 `receiveAmount - payAmount`，与占用额度无关，别误用。

## 3.1 挂载位置

| 接口 | 路径 | 层级含义 |
| :-- | :-- | :-- |
| 列表 | `items[].statementCurrencyGroup[]` | 整张对账单按币别 |
| 详情 | `orderFeeGroups[].statementCurrencyGroup[]` | **业务组内**按币别 |
| 详情 | `orderFeeGroups[].statementCurrencyGroupSummary[]` | 同上，见下方提示 |

> [!IMPORTANT] `statementCurrencyGroupSummary` 与同一业务组的 `statementCurrencyGroup` **内容完全一样**（它是对后者按币别再分组求和，而后者已经按币别分过组了）。这不是本次引入的，本次只是把新字段一并填上。
>
> 两者都是**业务组内**的汇总，**都不是整张对账单的合计**。详情接口不返回整单的币别合计，需要整单数据请前端自行把各业务组相加。

## 3.2 收 / 付 是按什么拆的

按**费用自己的 `paySide`** 拆，不是按占用来源拆。

> [!WARNING] 不要把 `payInvoiceOccupiedAmount` 理解成「付费申请占用的额度」。**付费申请和结算单都允许收付混选**（应收费用进付费申请是做冲抵的），所以一条**应收**费用的占用里也可能有付费申请的份额。
>
> 唯一被强制的是开票申请：它只能选应收费用，混进应付费用时提交会报「存在应付费用 不可提交开票申请」。
>
> 正确读法：`receive*` = 应收费用上的占用，`pay*` = 应付费用上的占用。

# 四、费用行新增/修正的字段

以下字段在 `OrderFeeDto` 上**早就存在**，本次只是从「恒 0 的错值」变成真值。字段名、类型都没变，前端若已在用，会看到数值从 0 变成实际值。

| 字段名 | JSON Key | 类型 | 详情 `DetailAsync` | 选费用 `GetOrderFeeGroupAsync` | 等于什么 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| SettlementOccupiedAmount | `settlementOccupiedAmount` | decimal | **本次补真值** | **本次补真值** | 付费申请+收费结算+开票申请 |
| OrderInvoiceAmount | `orderInvoiceAmount` | decimal | 原本就有 | 原本就有 | 开票申请+付费申请 |
| SettledAmount | `settledAmount` | decimal | 原本就有 | **本次补真值** | 已结算量（结算回写） |
| UnSettledAmount | `unSettledAmount` | decimal | 原本就有 | **本次补真值** | `amount - settledAmount` |
| RqstPaymentAmount | `rqstPaymentAmount` | decimal | 原本就有 | **本次补真值** | **只**付费申请已申请 |
| UnRqstPaymentAmount | `unRqstPaymentAmount` | decimal | 原本就有 | **本次补真值** | `amount - settlementOccupiedAmount` |

费用行位置：详情为 `orderFeeGroups[].orderFees[]`，选费用为 `items[].orderFees[]`。

> [!IMPORTANT] `unRqstPaymentAmount`（未付费申请量）的减数是 **`settlementOccupiedAmount`**，不是 `rqstPaymentAmount`。这样它才等于付费申请侧「这条费用还能申请多少」的真实可用额度——同一笔钱被开票申请或收费结算占掉了，也就不能再拿去付费申请。
>
> 所以 `rqstPaymentAmount + unRqstPaymentAmount` 一般**不等于** `amount`，别用这个等式做校验。

# 五、前端改动建议

1. **对账单列表/详情的币别汇总区**可以按需加「占用开票合计」「占用结算合计」两组列，各分收/付两栏。全付或全收的对账单里对侧那栏会是 0。
2. **选费用弹窗**建议展示 `unRqstPaymentAmount`（真实可用额度）而不是 `unSettledAmount`，后者只扣已结算、不扣被申请占住的部分，会让用户以为额度比实际多。
3. **未对账的费用出现占用是正常的。** 占用来自付费申请/开票申请/收费结算，与是否对过账没有先后关系，不要当脏数据提 bug。
4. 详情侧的 4 列合计是从费用行直接求和的，与行**一定对得上**；列表侧不返回费用行，要核对请进详情。
