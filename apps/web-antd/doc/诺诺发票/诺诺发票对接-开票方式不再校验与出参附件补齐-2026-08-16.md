# 1. 背景意图 (Background)

四件事，都是"开票相关的出参与文件没给全"：

1. **开票方式挡住了手动记录**。`IssueByInterfaceAsync` 原来要求 `InvoiceIssueType == 接口开票`，已经录成"手动记录"的发票开出没法改走接口开票。
2. **列表出参缺一大截**。接口开票与冲红一共 19 个实体字段，详情返回了 17 个， **列表只返回了 5 个**——当初只补了"够列表显示状态用"的那几个，这个判断是错的：出参该给全，前端要不要显示是前端的事。
3. **附件只有详情有**。列表拿不到发票版式文件，开票申请更是完全拿不到（附件挂在发票开出上）。
4. **版式文件只存了 OFD 和 PDF**。XML 从来没存过（DTO 里声明了但全项目零引用），发票图片连字段都没声明，纸质 PDF 只在前两者都没有时才当兜底、等于纸票基本拿不到。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 开票方式不再校验，受理成功后自动落地

`NuonuoInvoiceManager.IssueAsync` 删掉了开票方式校验。点了"开发票"就是要走接口开，原来记的是不是手动记录都不拦。

**受理成功后**（拿到开票流水号、置 `IssueStatus = 已提交待开票` 之后）把开票方式改成接口开票：

```csharp
data.IssueSerialNum = serialNum;
data.IssueStatus = InvoiceIssueStatus.已提交待开票;
data.InvoiceIssueType = InvoiceIssueType.接口开票;
```

放在受理成功之后改，是为了让提交失败时开票方式保持原样（异常会连同 `IssueOrderNo`、`IssueRequestTime` 一起回滚）。

`InvoiceIssueStateDto` 同时新增 `InvoiceIssueType` 出参，前端调完接口能直接刷新这一列，不用重查详情。

`ApplyRedAsync` 里同样的开票方式校验也一并删了——开票方式现在是开票时自动落的，能走到"开票完成"的必然已经是接口开票，那句已是死代码；真正该判的是下一行的"有没有真开出票"。

## 2.2 出参补齐：列表与详情返回同一套字段

用脚本把实体上 19 个字段与两个 DTO 逐项比对，补齐后**完全一致**：

|  | 补之前 | 补的内容 |
| :-- | :-- | :-- |
| **详情** | 缺 2 个 | `RedBillUuid`、`RedApplyUserId` |
| **列表** | 缺 14 个 | `IssueOrderNo`、`IssueRequestTime`、`InvoiceCode`、`RedReason`、`RedBillId`、`RedBillNo`、`RedBillUuid`、`RedOrderNo`、`RedSerialNum`、`RedInvoiceCode`、`RedInvoiceTime`、`RedApplyTime`、`RedApplyUserId`、`RedFailCause` |

另按项目约定（关联 User 一律返回 nickname）两边都加了 `RedApplyUserName`： `DetailAsync` 把 `RedApplyUserId` 并进原来那批 userIds，`GetPagedListAsync` 并进 `allUserIds`， **复用已有的那一次用户查询，没有多打一次库**。

列表 DTO 的字段按 `#region 接口开票` / `#region 冲红` 分了组，与详情 DTO 结构对齐，以后加字段一眼能看出两边有没有同步。

## 2.3 附件返回

| 出口          | 内容                                         |
| :------------ | :------------------------------------------- |
| 发票开出 详情 | 原本就有                                     |
| 发票开出 列表 | **新增**，本页一次批量取回再按 `ItemId` 分派 |
| 开票申请 详情 | **新增**，返回它所挂发票开出下的附件         |
| 开票申请 列表 | **新增**，同上                               |

发票开出列表用 `AttachmentItemQueryDto(moduleTypeId, IEnumerable<string> itemIds)` 这个批量构造函数，本页多少条都只查一次。

开票申请那边抽了私有方法 `GetInvoiceAttachmentMapAsync(applicationIds)`，列表与详情共用，同样两段批量：先一把捞出这批申请的挂靠明细，再一把捞出对应发票开出的附件，最后按申请分派。为此给 `InvoiceApplicationAdminAppService` 注入了 `IRepository<InvoiceIssueItem, Guid>`（原来没有）。

**不分组**：一条申请理论上只挂一张发票开出，真挂了多张也直接把附件拉平成一个数组。

## 2.4 版式文件全量存档

`SaveInvoiceFilesAsync` 改成"服务商返回几个地址就存几个"：

| 服务商字段 | 附件名 | 存储类型 | 之前 |
| :-- | :-- | :-- | :-- |
| `ofdUrl` | `发票OFD-{发票号}.ofd` | `Document` | 已存 |
| `xmlUrl` | `发票XML-{发票号}.xml` | `Document` | **DTO 里声明了但从没用过** |
| `pdfUrl` | `发票PDF-{发票号}.pdf` | `Document` | 已存 |
| `paperPdfUrl` | `发票纸质PDF-{发票号}.pdf` | `Document` | 只在前两者都没有时兜底 |
| `pictureUrl` + `imgUrls` | `发票图片{n}-{发票号}.jpg` | `Image` | **两个字段都没声明** |

红票走同一套逻辑，前缀换成 `红票`。

配套的几处修正：

- **图片有两个字段**：`pictureUrl` 单张、`imgUrls` 多张逗号分隔，合并后按地址去重再按序号命名（中英文逗号都拆）。
- **图片地址可能不带协议**（文档示例就是 `nnfpkf.jss.com.cn/xxx`），直接请求会被当成相对地址抛异常，下载前统一补 `http://`。
- **图片地址可能没有扩展名**，从 URL 路径推，推不出来按 `.jpg`。
- **MIME 类型原来写死** `extension == ".pdf" ? "application/pdf" : "application/ofd"`，加了 XML 与图片后这个判断就错了（XML 会被标成 ofd），换成完整映射表；图片同时走 `MediaType.Image` 而不是 `Document`。
- **地址全为空时写 Warn 日志**，把六个字段名记下来。原来是静默跳过，导致"为什么只有 OFD 没有 PDF"这种问题只能靠猜。

# 3. 避坑指南 (Blockers & Pitfalls)

> [!IMPORTANT] **坑点 1：手动记录转接口开票会覆盖手填的发票号** 手动记录的发票开出如果**已经手填了发票号**，现在点"开发票"不会被拦——会去税局真开一张新票，落地后把手填的号覆盖掉。如果那个手填号对应的是线下已经开出去的真票，就变成一笔业务开了两张发票。本次按需求**没有**加这道拦截，如果实际业务有这种录法，需要补一条"已填写发票号的手动记录须先清空发票号"的校验。

> [!IMPORTANT] **坑点 2：版式文件不是都会有，别写死假设** 哪些格式有值由服务商侧的企业资质配置决定——文档原话：xml 是"企业配置成支持获取xml时返回"、ofd 是"公共服务平台签章及数电电票时返回"。沙箱环境更可能只给一两个。少了某个格式先别怀疑这段代码，看那条 Warn 日志或直接问服务商这个税号开了哪些版式文件。

> [!NOTE] **缺文件会自动补** 附件按 `FriendlyFileName` 去重，已存在的跳过、缺失的重新下载。所以某个文件这次没下来，下次回调或手动点"查询开票结果"会自动补上，不需要人工干预。

> [!IMPORTANT] **坑点 3：开票申请自己没有附件** 附件挂在发票开出上（`ModuleTypeId=160090` / `ItemId=发票开出Id`）。开票申请要拿附件，必须走 申请 → `InvoiceIssueItem` 挂靠明细 → 发票开出 → 附件 这条链路。因此**冲红完成解绑后，那张票的附件也就不再出现在申请上了**——这是挂靠口径的自然结果，不是 bug。

> [!IMPORTANT] **坑点 4：出参补齐时两个 DTO 要对着改** 列表与详情是两个独立的类，加字段极易只加一边。本次已把两边都按 `#region 接口开票` / `#region 冲红` 分组，加字段时对照着加；改完可以用脚本比对实体字段是否两边都有。
