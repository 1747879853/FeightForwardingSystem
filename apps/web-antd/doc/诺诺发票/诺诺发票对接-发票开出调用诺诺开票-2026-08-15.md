# 诺诺发票对接（后端逻辑）

在【发票开出】上点"开发票"，调诺诺开放平台开具数电发票，开完票自动回填发票号/开票日期/开票方式，并把发票版式文件存进附件。

---

## 一、总体流程

数电发票是**异步**开具的：`requestBillingNew` 只做受理，同步返回的只有**发票流水号**，真正的发票号码与版式文件要等税局那边生成。因此整个对接分两段：

```
① 提交    业务服务器 ──requestBillingNew──> 诺诺     (用该公司的 appKey/appSecret 取token+签名)
          拿到发票流水号，状态=已提交待开票

② 落地    诺诺 ──callBackUrl 直接回调──> 业务服务器 /api/invoice-issue/callback
          业务服务器 ──queryInvoiceResult──> 诺诺     以查询结果为准
          回填发票号/开票日期 + 下载 PDF/OFD 存附件
```

**不经中转站。** 业务服务器直连诺诺，回调也由诺诺直接打到业务服务器的公网地址。

回调迟迟没到时，可以调"查询开票结果"接口手动走一次②的落地逻辑，效果完全一样。

### 配置分两层：按公司 + 全局

| 层级 | 内容 | 放在哪 |
| --- | --- | --- |
| **按公司** | `appKey`、`appSecret`、销方税号 | 组织(公司)表：`InvoiceAppKey`、`InvoiceAppSecret`、`UnifiedSocialCreditCode`，在公司资料界面维护 |
| **全局** | 接口地址、取令牌地址、回调地址、是否需要 token、回调IP白名单 | `appsettings.json` 的 `Nuonuo` 节点 |
| **按人** | 开票分机号 | 用户表 `ExtensionNumber`，在用户资料界面维护（2026-09-01 起，原为全局配置） |

**每家公司在诺诺那边是独立的应用**，各用各的 appKey/appSecret 取令牌与签名。这一点很关键：诺诺"重新取一次 token 会让之前的 token 立即失效"的限制是**按应用**算的，各公司各一套应用，各取各的 token 互不影响，所以**不需要中转站集中取号**。

（历史：早期设计过让中转站集中取号 + 全代理签名，前提是所有公司共用一套密钥。改成按公司独立密钥后这个前提不成立了，中转站相关代码已全部移除，`Freight.Relay` 已还原到对接诺诺之前的状态。）

### token 两级缓存：内存 + 数据库

诺诺对取号的限制：**每重新取一次 token，同一应用之前的 token 立即失效**，且每 30 天最多 50 次。所以取号要尽可能少。

| 层级 | 位置 | 挡住什么 |
| --- | --- | --- |
| 一级 | 进程内存，按 `appKey` 分桶（`ConcurrentDictionary` + 每桶一把 `SemaphoreSlim`） | 同一进程内的重复取号、并发首次取号 |
| 二级 | 数据库 `App_NuonuoAccessTokens`，一个 `appKey` 一行 | **进程重启**导致的重复取号 |

**二级缓存是必需的，不是优化。** 只放内存的话，IIS 应用池的定期回收（默认 1740 分钟）、空闲回收（默认 20 分钟无请求）、以及每次发版重启，都会让下次开票重新取一次号。按默认回收策略一个月很容易就把 50 次用光，用光之后那家公司直接开不了票。落库后重启只需读库复用，不消耗配额。

`expires_in` 为负数表示应用建成"永久有效"，此时 `ExpireTime` 存 `null`，永不过期；否则按 `expires_in` 计算并提前 1 小时失效。

#### 落库为什么要走独立的非事务工作单元

```csharp
new UnitOfWorkOptions { Scope = TransactionScopeOption.RequiresNew, IsTransactional = false }
```

取号一旦发出去，就在服务商侧生效并**作废了旧 token**，这是既成事实、必须记下来。如果 token 记录跟着开票的事务走，开票失败回滚时会把它一起回滚掉，下次又得重新取——联调期间失败多，配额会烧得飞快。

用 `RequiresNew + IsTransactional=false` 而不是别的组合，是因为 ABP 的 EF Core 工作单元用的是 `DbContext.Database.BeginTransaction()`（单连接的普通事务），**不是 `System.Transactions.TransactionScope`**。非事务工作单元会拿到独立 DbContext 直接 `SaveChanges` 自动提交，既独立于外层事务，又完全不牵扯 MSDTC。

> 注意 `Scope` 必须显式给 `RequiresNew`：ABP 的 `UnitOfWorkManager.Begin` 在 `Scope=Required`（默认）且已有外层工作单元时会直接**加入外层**而不新建，那样就达不到独立提交的效果。

#### 多进程并存时的兜底

同一家公司若有多个进程共用同一套 appKey（典型场景：IIS 应用池**重叠回收**，新旧工作进程短暂并存），新进程取号会把旧进程缓存的 token 顶掉，旧进程的请求就会收到 `070301 令牌不匹配`。

`NuonuoApiClient` 对此做了处理：收到 `070301` 时调 `ForceRefreshAsync` 强制重取一次并重试，**只重试一次**（避免两个进程来回顶号打转）。

`FetchCount` 列记录累计取号次数，增长异常就说明有进程在反复取号，可以据此排查。

#### 为什么只留 `InvoiceCode`、不留 `AllElectronicInvoiceNumber`

诺诺发票详情查询接口返回三个号码类字段，含义随票种变化：

| 诺诺字段 | 数电电票（pc / bs） | 数电纸票（ec / es） |
| --- | --- | --- |
| `invoiceNo` 发票号码 | 20位数电票号码 | **8位**纸票号码 |
| `invoiceCode` 发票代码 | **空** | 12位发票代码 |
| `allElectronicInvoiceNumber` 数电票号码 | 20位数电票号码（**与 invoiceNo 相同**） | 20位数电票号码 |

- 电票下 `allElectronicInvoiceNumber` 与 `invoiceNo` 完全重复，没有单独存的价值 → **不落库**。只在 `invoiceNo` 万一没返回时当兜底读一下（见 `ApplyResultAsync`），报文 DTO 里字段还留着用于解析。
- 纸票的发票号码只有8位、本身不唯一，必须"**发票代码 + 发票号码**"配对才能定位一张票；而且给纸票开红票时，诺诺要求 `invoiceCode` 与 `invoiceNum` **都是必填** → `InvoiceCode` **落库**。

注意票种映射里 `c`（普通发票-纸票）→ `ec`（数电纸票），所以只要开 `c` 类型就会真的走到纸票分支。

### `App_InvoiceApplications`（开票申请）**不加列**

开票申请表保持原样，只回填原有的 `InvoiceNo`（开票时写入、反开票时置空），行为与改造前一致。

> 开票日期与开票方式**不落到开票申请表**。需要展示时通过 `InvoiceIssueItem` 关联到 `InvoiceIssue`，取那边的 `InvoiceIssueTime` / `InvoiceIssueType`，避免同一份信息两处存储、两处维护。

## 四、开票报文怎么组出来的

### 销方

| 诺诺字段 | 取值来源 |
| --- | --- |
| `salerTaxNum` / 消息头 `userTax` | 所属公司的 `UnifiedSocialCreditCode`（两处同一个值，不一致会报 `E9302`） |
| 签名用的 `appKey` / `appSecret` | 所属公司的 `InvoiceAppKey` / `InvoiceAppSecret` |
| `salerTel` | 所属公司 `InvoiceTel` |
| `salerAddress` | 所属公司 `InvoiceAddress` |
| `salerAccount` | 发票开出的我司银行：`BankName + " " + BankAccount` |
| `clerk`（开票员） | **不传**（2026-09-01 起） |
| `extensionNumber`（分机号） | **当前登录人**的 `User.ExtensionNumber`，没维护则报文里不带该字段 |

> ⚠️ **只传分机号、不传开票员**：与诺诺确认过，诺诺会按分机号自动匹配开票员。传 `clerk` 反而要求它与诺诺开票登录账号的**开票员姓名完全一致**，对不上直接开票失败——那等于要求系统里的用户昵称跟诺诺侧的开票员姓名长期人工对齐，谁改个昵称就能把开票搞崩。 `ResolveClerkAsync()` 与组报文处的 `Clerk` 赋值都注释保留着，诺诺日后要求传时解开即可。

### 购方

| 诺诺字段       | 取值来源                                                |
| -------------- | ------------------------------------------------------- |
| `buyerName`    | 客户开票信息 `ClientInvoiceInfo.Header`（抬头）         |
| `buyerTaxNum`  | `ClientInvoiceInfo.TaxNum`                              |

### 票种映射（按《请求开具发票接口》文档）

| 本系统 `InvoiceType` | 诺诺 `invoiceLine`  |
| -------------------- | ------------------- |
| `p` 普通发票(电票)   | `pc` 数电普票(电子) |
| `c` 普通发票(纸票)   | `ec` 数电普票(纸质) |
| `s` 专用发票         | `bs` 数电专票(电子) |

> 注意：《对接开发流程》那份文档说"数电专票 = es"，与《请求开具发票接口》文档的 `bs=数电专票(电子)` / `es=数电专票(纸质)` **相互矛盾**。这里按接口文档取 `bs`。若正式环境开专票报票种错误，改 `MapInvoiceLine` 里的这一行即可。

### 商品明细

来自 `InvoiceIssueGoodsDtl` + `CodeInvoice`：

| 诺诺字段 | 取值 |
| --- | --- |
| `goodsName` | `CodeInvoice.Name` |
| `goodsCode` | `CodeInvoice.TaxClassificationCode`（税收分类编码，不传会报 E9138） |
| `specType` / `unit` | 明细的规格型号 / 单位 |
| `withTaxFlag` | `1`（本系统单价是**含税**单价） |
| `taxRate` | `明细税率 / 100`（本系统按百分数存 `6`，诺诺要小数 `0.06`） |
| `taxExcludedAmount` / `tax` / `taxIncludedAmount` | 明细的不含税金额 / 税额 / 金额，**原样上传** |
| `price` / `num` | 单价与数量。**两者只要有一个为0就都不传**——诺诺规定单价为空时数量也必须为空，此时靠金额三项开票 |
| `favouredPolicyFlag`（优惠政策标识） | **免税与不征税靠这个字段表达**，仅税率为0时传：`ZeroTaxRateEnum` 免征→`03`免税、不征收→`04`不征税；普通零税率(3)与出口退税(4)**不传**（数电票的取值里没有这两项，税率填0且不带优惠政策，票面就是0%） |
| ~~`zeroRateFlag`（零税率标识）~~ | **不传**。官方《请求开具发票接口》在该字段末尾注明"（数电票时为空）"，本系统开的全是数电票(pc/ec/bs)，所以免税不能靠它，只能靠 `favouredPolicyFlag`。（2026-09-01 修正：此前误传了本字段，等于免税没表达出来） |
| `invoiceLineProperty` | `0`（正常行） |

> 金额三项一律原样上传、不让诺诺按单价×数量自己算，避免分位误差被 `E9130`（不含税+税额≠含税）/`E9131`（金额×税率−税额>0.06）拦下。

## 五、落地回填做了什么

只有状态为**开票完成**或**签章失败**（票已经开出来了，只是签章没成）才回填号码与附件；开票中/签章中/失败/作废只更新状态与失败原因。

1. **发票开出**：`InvoiceNo`（数电电票取20位数电票号码，数电纸票取8位纸票号码）、`InvoiceCode`（仅纸票有值）、`InvoiceIssueTime`（取诺诺返回的开票时间，毫秒时间戳）
2. **关联的开票申请**（经 `InvoiceIssueItem` 找到的全部）：`InvoiceNo`、`Status=Invoiced`
3. **附件**：把返回的**全部**文件地址都下载存档，挂在 `ModuleTypeId=160090` / `ItemId=发票开出Id` 下，`ClientVisible=true`

| 诺诺字段 | 附件名 | 性质 | 存储类型 |
| --- | --- | --- | --- |
| `ofdUrl` | `发票OFD-{发票号}.ofd` | 法定原始凭证 | `MediaType.Document` |
| `xmlUrl` | `发票XML-{发票号}.xml` | 税局原始数据格式 | `MediaType.Document` |
| `pdfUrl` | `发票PDF-{发票号}.pdf` | 版式转换产物，不能作原始凭证 | `MediaType.Document` |
| `paperPdfUrl` | `发票纸质PDF-{发票号}.pdf` | 含底图纸票打印版 | `MediaType.Document` |
| `pictureUrl` + `imgUrls` | `发票图片{n}-{发票号}.jpg` | 发票图片，两个字段合并去重后按序号命名 | `MediaType.Image` |

> **哪些地址有值由服务商的企业资质配置决定**，文档原话：xml 是"企业配置成支持获取xml时返回"、ofd 是"公共服务平台签章及数电电票时返回"。所以少了某个格式先别怀疑代码，看日志里那条 Warn（全为空时会记下来）或直接问服务商这个税号开了哪些版式文件。附件按 `FriendlyFileName` 去重，回调重复到达不会存出多份；反过来，某个文件这次没下来，下次回调或手动"查询开票结果"会自动补上缺的那个。 `imgUrls` 是逗号分隔的多个地址，`pictureUrl` 实测可能不带协议，下载前会补 `http://`。文件下载失败只记日志、不抛异常——号码已经开出来并回填了，不能因为拿不到文件就让整笔开票结果落不了地。

### 防重复开票：订单号为什么用 Id 派生而不是随机号

`orderNo` = 发票开出 Id 的前20位十六进制，**同一条发票开出每次算出来都一样**。

这是为了兜住最危险的一种情况：**请求已经发到诺诺、诺诺也开了票，但本地没记下来**（HTTP 超时、进程被回收、事务回滚）。此时：

- 订单号是随机号 → 重试会用新号，诺诺侧真的开出**第二张票**。发票重开是税务问题。
- 订单号由 Id 派生 → 重试用的还是同一个号，诺诺以 `E9106 订单编号或流水号不能重复` 直接挡住，**结构上不可能开出第二张**。这时改用"查询开票结果"按订单号问诺诺那张票到底开没开即可（`QueryAndApplyAsync` 在流水号为空时会自动按订单号查）。

代价是：诺诺已经记下这个订单号之后就没法用同一条发票开出再开一次了。考虑到"开票完成"本身就禁止重开、冲红要走另一套流程，这个代价可以接受——**宁可挡住，也不能重开**。

## 六点五、回调报文实测格式（诺诺没给文档，2026-08-15 沙箱实测）

⚠️ **回调不是 JSON，是 `application/x-www-form-urlencoded`**：

```
operater=callback&content=<URL编码的JSON>&orderno=ccc41bb8f344459ca72b
```

三个表单字段：`operater`（固定 `callback`）、`content`（URL 编码的 JSON）、`orderno`（订单号，即我们的 `IssueOrderNo`）。

而 `content` 里的字段名是**另一套 `c_` 前缀的命名**，跟发票详情查询接口完全不同：

| content 里的字段 | 含义 | 对应查询接口的字段 |
| --- | --- | --- |
| `c_fpqqlsh` | 发票请求流水号 | `serialNo` |
| `c_orderno` | 订单号 | `orderNo` |
| `c_fphm` | 发票号码 | `invoiceNo` |
| `c_fpdm` | 发票代码（电票为空） | `invoiceCode` |
| `allElectronicInvoiceNumber` | 数电票号码 | 同名 |
| `c_kprq` / `dt_invoicedate` | 开票日期（毫秒时间戳） | `invoiceTime` |
| `c_url` / `c_ofd_url` / `c_paper_pdf_url` / `c_imgUrls` | PDF / OFD / 纸票PDF / 图片地址 | `pdfUrl` / `ofdUrl` / `paperPdfUrl` / `imgUrls` |
| `xmlUrl` | XML 地址（**不带 `c_` 前缀**，与 `c_imgUrls`、`c_paper_pdf_url` 同级） | `xmlUrl` |
| `c_status` | 状态（**取值口径与查询接口的 `status` 不一样**，实测开票完成回传 `1`） | `status` |
| `c_bhsje` / `c_hjse` / `c_hjje` | 不含税金额 / 合计税额 / 价税合计 | `exTaxAmount` / `taxAmount` / `orderAmount` |

> **2026-08-18 更新**：服务商后来给出了 `c_status` 的编码说明（`1` 开票完成 / `2` 开票失败 / `3` 签章失败，全是终态，失败时带失败原因），也确认了回调带 `xmlUrl`。**下面这一节的结论已被推翻**，现在改成"推送直接落地、认不出来才回查"，见《诺诺发票对接-回调直接落地不再回查-2026-08-18.md》。本节保留下来，是为了记录当初为什么不敢直接用——**在拿到编码表之前，那个判断是对的**。

### 为什么不直接用回调字段写库（重要，别"优化"掉那次回查）

上表看得出来：**成功场景的字段其实是齐的**——发票号、发票代码、开票日期、PDF/OFD 地址、金额三项，回调里全都有，理论上可以不回查、直接写。**但本实现刻意不这么做**，一律回查 `queryInvoiceResult`，原因有两条：

1. **`c_status` 的取值口径没有文档，而且与查询接口冲突。** 实测开票完成时回传 `c_status=1`，而查询接口里 `2` 才是开票完成、`1` 在我们枚举里是"已提交待开票"。两套编码撞在一起。诺诺《对接开发流程》把"回传开票结果接口"列为常用接口第 7 条，却没提供该接口文档，所以 `c_status` 还有哪些取值、有没有"签章中"这类中间态，目前是猜。**万一把中间态当成开票完成，就会把一张还没最终确定的票标成已开票——这是税务记录，代价远大于省一次 HTTP 调用。**
2. **失败场景的报文没见过。** `callBackUrl` 说明是"开票完成、开票失败"都回传，但实测的成功报文里**没有任何失败原因字段**（没有 `failCause` / `c_failCause`）。失败时多哪个字段、`c_status` 变成什么值，都未知，直接写会拿不到 `IssueFailCause`。

因此回调只当**触发器**：只取 `c_fpqqlsh` 与 `orderno`/`c_orderno` 两个号用于定位，其余字段一概不读，状态与号码全部以文档化的 `queryInvoiceResult` 返回为准。

> 代价是每次回调多一次查询调用。开票不是高频操作，这个代价换"税务数据只认文档化字段"是值得的。若将来诺诺给出了"回传开票结果接口"的正式文档、`c_status` 编码表和失败报文样例，可以再考虑改成「回调带发票号+版式文件就直接写、否则回查」的混合模式。

解析要点（中转站 `NuonuoService.ReadCallbackKeys`、业务端 `NuonuoInvoiceManager.ReadCallbackKeys` 各实现一份，两个项目不互相引用）：

- 先判断报文是不是以 `{` / `[` 开头：不是就按表单解析，是就走 JSON 分支（保留 JSON 分支以防日后诺诺改格式或换企业配置）。
- 表单解码**必须先把 `+` 还原成空格再做 URL 解码**，否则 `content` 里被编成 `+` 的空格会丢（如 `美利坚银行+123456`）。因此没用 `HttpUtility`，自己实现了 `ParseFormUrlEncoded`。
- 顶层 `orderno` 通常就够定位，`content` 解析失败也不影响路由。

> 这个格式问题第一次联调就暴露了：中转站日志出现 `[路由回退] 开票结果回调报文解析失败，改为广播给全部 6 个下游`。广播兜底让回调没有丢，但会打到别家下游（各自匹配不到就忽略），修好解析后即可精确路由。
