# 一、背景意图

与开票服务商确认过一件事：**报文里只要传了分机号，服务商就会按分机号自动匹配开票员**，开票员（`clerk`）根本不用传。

之前是反过来的：开票员传当前登录人的昵称，分机号取全局配置 `Nuonuo:ExtensionNumber`（全公司一个值）。这套做法有两个毛病：

1. **`clerk` 传了就必须对得上。** 服务商要求 `clerk` 与该开票登录账号维护的开票员姓名**完全一致**，对不上直接开票失败。这等于在系统里埋了一条隐性约定——"用户昵称必须等于服务商侧的开票员姓名"，谁在用户资料里改一下昵称就能把开票搞崩，而且改的人根本不知道有这回事。
2. **分机号全公司一个值，等于没区分开票员。** 分机号本来就是用来区分人的，配在 `appsettings.json` 里全公司共用一个，那不管谁开的票在服务商侧都归到同一个开票员名下，失去意义。

既然服务商能按分机号自动匹配，那就把 `clerk` 撤掉、把分机号落到人身上，两个毛病一起解决。

# 二、核心逻辑变更

## 2.1 开票员：不传，但代码保留

组报文处的 `Clerk = clerk` 与取值方法 `ResolveClerkAsync()` **整段注释保留，没有删**。服务商日后若又要求传开票员，解开注释即可，不用重新实现。相关注释已写明为什么现在不传。

`NuonuoBillingOrder.Clerk` 这个字段本身也留着（它是服务商的报文契约），只是不赋值。

## 2.2 分机号：从全局配置改为按人维护

|  | 改前 | 改后 |
| :-- | :-- | :-- |
| 存哪 | `appsettings.json` → `Nuonuo:ExtensionNumber` | 用户表 `AbpUsers.ExtensionNumber` |
| 粒度 | 全公司一个值 | 每人一个值 |
| 取值 | 读配置 | `ResolveExtensionNumberAsync()` 取**当前登录人**的 |
| 没值时 | 不带该字段 | 不带该字段（不拦开票） |

**没维护分机号不拦开票**：分机号不是必传项，没有就不带这个字段，服务商按企业默认开票员处理。不能因为某个人没维护分机号就让他开不出票——这跟不传 `clerk` 是同一个道理，不要为了一个可选字段去制造新的人工对齐约定。

**回调链路里的"当前登录人"**：像纸票冲红后自动开红票这种由回调触发的场景，当前登录人是该发票开出的创建人，取到的就是他的分机号，行为符合直觉。

三处报文都改了：蓝票开具、红字确认单申请、纸票快捷冲红。

## 2.3 字段类型直接用 `int?`，不用"字符串 + 正则校验"

服务商规定分机号**只能为空或数字**。既然如此就直接用数字类型，让类型系统去保证，而不是存成字符串再挂 `[RegularExpression(@"^\d*$")]` 去运行时校验。后者是拿运行时校验补一件类型本来就能保证的事，属于多余。

报文字段 `NuonuoBillingOrder.ExtensionNumber` 仍是 `string`（服务商的线上格式如此），在 `ResolveExtensionNumberAsync()` 里 `ToString(InvariantCulture)` 转一下。

# 四、避坑指南

> [!IMPORTANT] **用户新增/编辑有两条并行路径，两个入参 DTO，别只改一个。** `CreateOrUpdateUserAsync` 收 `UserInAdminInputDto`， `CreateOrUpdateUserInAdminAsync` 收 `UserInAdminDataPermissionInputDto`，这两个 DTO **没有继承关系**，字段是各写各的。只给其中一个加字段，前端调另一个接口时字段会被静默丢掉——不报错，只是存不进去。本次两个都加了，对应的 4 处赋值也都补了。

> [!IMPORTANT] **别把 `ResolveClerkAsync()` 当成死代码删掉。** 它现在没有调用方，IDE 会提示"未使用"。这是刻意保留的，注释里写了原因。

> [!IMPORTANT] **升级后原来配置的分机号会失效。** `Nuonuo:ExtensionNumber` 已从 `appsettings.json` 删除。若之前依赖它把发票归到某个开票员名下，上线后要把该分机号维护到对应操作人的用户资料里，否则报文里就不带分机号了（不影响能不能开票，只影响发票归到哪个开票员名下）。
