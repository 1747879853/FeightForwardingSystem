# 1. 背景意图 (Background)

原来收到开票结果回调后，**不读回调里的任何业务字段**，只取流水号/订单号定位，再回查一次【发票详情查询接口】，以查询结果为准落地。

这么做的原因是当初缺两样东西：

1. 回调的 `c_status` 编码**没有文档**，而且与查询接口冲突——沙箱实测一张开票完成的票回传 `c_status=1`，而查询接口里 `2` 才是开票完成、`1` 是"已提交待开票"。**怕把中间态误判成开票完成**，那会把一张还没最终确定的票标成已开票，这是税务记录。
2. **失败场景的报文没见过**，实测的成功报文里没有失败原因字段，直接写会拿不到 `IssueFailCause`。

现在服务商把这两件事都说清楚了：

> `c_status`：发票状态（1：开票完成、2：开票失败、3：开票成功签章失败（电票时））；注：1、企业资质-开票失败是否回调 为"是"时返回该字段；2、（开票失败、开票成功签章失败时）content 中只返回：发票流水号、发票状态、销方税号、失败原因 四个字段。

**三个取值全是终态，没有开票中/签章中这类中间态**，第 1 条顾虑不成立； **失败时失败原因就在推送里**，第 2 条顾虑也不成立。同时确认回调是带 `xmlUrl` 的（**不带 `c_` 前缀**，与 `c_imgUrls`、`c_paper_pdf_url` 同级），版式文件五种推送里都有。

于是改成：**推送本身就能落地，不再无条件回查**。开票完成到界面能看到发票号的延迟少一次 HTTP 往返。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 回调解析产出 content 对象

`ReadCallbackKeys` → `ReadCallback`，返回值从 `(serialNo, orderNo)` 变成 `(serialNo, orderNo, content)`， `content` 是回调 `content` 字段解出来的 `JObject`。表单形态与 JSON 形态两条分支都返回它。

## 2.2 新增 `BuildResultFromCallback`：把回调翻译成开票结果

关键在于**把回调状态换算成查询接口的口径**，之后交给原有的统一落地逻辑 `ApplyResultAsync`，回填、存附件、回填开票申请全都不用改：

| 回调 `c_status` | 含义 | 换算成查询接口 status | 本地枚举 |
| :-- | :-- | :-- | :-- |
| `1` | 开票完成 | `2` | `开票完成` |
| `2` | 开票失败 | `22` | `开票失败` |
| `3` | 开票成功签章失败（电票） | `24` | `签章失败` |

字段映射（注意大部分带 `c_` 前缀，但有两个例外）：

| 回调字段 | 映射到 |
| :-- | :-- |
| `c_fpqqlsh` | `SerialNo` 发票流水号 |
| `c_orderno` | `OrderNo` 订单号 |
| `c_fphm` | `InvoiceNo` 发票号码 |
| `c_fpdm` | `InvoiceCode` 发票代码 |
| `allElectronicInvoiceNumber` | `AllElectronicInvoiceNumber`（**无 `c_` 前缀**） |
| `c_kprq` / `dt_invoicedate` | `InvoiceTime` 开票日期（毫秒时间戳） |
| `c_url` | `PdfUrl` |
| `c_ofd_url` | `OfdUrl` |
| `xmlUrl` | `XmlUrl`（**无 `c_` 前缀**） |
| `c_paper_pdf_url` | `PaperPdfUrl` |
| `c_imgUrls` | `ImgUrls` |

## 2.3 什么时候仍然回查

`BuildResultFromCallback` 返回 `null` 时回查，两种情况：

1. **推送里没有 `c_status`**。该字段只在"企业资质-开票失败是否回调"为**是**时才返回，资质没开就认不出状态 → 回查，行为与改造前完全一致。
2. **失败推送读不到失败原因**。服务商只说了"返回失败原因"，**没给键名**，代码里试了 `c_failCause` / `c_failcause` / `failCause` / `c_errorMessage` / `c_message` / `c_reason` 六种常见写法；都读不到就回查，避免界面上只有一个"开票失败"没法排查。

**红票推送不走这条捷径**：冲红要的是【红字确认单】状态，那不在开票回调里，仍走 `RefreshRedAsync` 查询。

# 3. 避坑指南 (Blockers & Pitfalls)

> [!IMPORTANT] **坑点 1：`c_status` 与查询接口的 `status` 是两套编码，换算只能有一处**
>
> 两套编码不同不是服务商随手定的，是因为两个接口的性质不同：
>
> |  | 字段 | 取值 | 为什么这样设计 |
> | :-- | :-- | :-- | :-- |
> | 查询接口 | `status` | `2` 开票完成 / `20` 开票中 / `21` 签章中 / `22` 开票失败 / `24` 签章失败 / `3` 已作废 / `31` 作废中 | **能随时调用**，票可能正处在任何阶段，所以必须能表达中间态 |
> | 回调 | `c_status` | `1` 开票完成 / `2` 开票失败 / `3` 签章失败 | **只在票走到终态时才推送**，压根不会推中间态，三个值就够 |
>
> 查询接口那套就是 `InvoiceIssueStatus`，原样入库不转换；回调那套必须换算。 **最要命的是 `2` 在两套里含义正好相反**——回调 `2` 是开票失败，查询 `2` 是开票完成。所以没法靠值判断是哪套编码，**只能靠字段名**。换算集中在 `BuildResultFromCallback` 里，**别在别的地方直接拿 `c_status` 当开票状态用**，也别把这两套编码写进同一个枚举。

> [!IMPORTANT] **坑点 2：失败原因的键名是猜的** 服务商只说"返回失败原因"没给键名。真收到第一条失败推送时，去 `App_NuonuoPushLogs.RawJson` 看实际键名，补进 `BuildResultFromCallback` 的候选列表。在补上之前失败推送会走回查，功能不受影响，只是多一次请求。

> [!NOTE] **回查兜底没有被删掉，只是不再无条件执行** 手动点「查询开票结果」仍然是纯回查，逻辑没变；缺的版式文件也仍然靠它补下载。所以即使回调解析出了任何问题，用户手动刷一次永远能拿到正确结果。

> [!NOTE] **前端无改动** 接口出入参、字段、状态枚举一个都没变，只是开票完成到界面能看到发票号的延迟少了一次 HTTP 往返。
