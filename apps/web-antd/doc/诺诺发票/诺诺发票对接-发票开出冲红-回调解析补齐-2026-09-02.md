# 一、背景意图

冲红链路上线后，实测**电票冲红 100% 走不完**：确认单在税局那边已经生效、税局也把红票开出来了，本地却永远停在「确认单已生效」，红票号码和附件一个都拿不到，点「查询冲红结果」也没用。

排查下来是三个独立缺陷叠在一起。三个都修了。完整流程与所有分叉见《诺诺发票对接-发票开出冲红-2026-08-16.md》第一节，本文只写这次相对上一版改了什么。

# 二、缺陷一：确认单回调一条都没接住

**现象**：`App_NuonuoPushLogs` 里每条确认单回调都记着「回调报文里读不到发票流水号(serialNo)与订单号(orderNo)，无法定位发票开出」，`Success=0`。

**原因**：两种回调的键名**完全不是一套**，而解析代码只按开票回调那套写的。

|  | 开票回调 | 确认单回调 |
| :-- | :-- | :-- |
| `operater` | `callback` | `confirmCallback` |
| 顶层参数 | `operater` / `content` / `orderno` | `operater` / `content` / `billId`（**没有 orderno**） |
| content 键名 | `c_` 前缀：`c_fpqqlsh`、`c_orderno`、`c_fphm`、`c_url` | 驼峰：`billId`、`billNo`、`billUuid`、`billStatus`、`orderNo` |

原解析只找三个地方：顶层 `orderno`、content 里的 `c_fpqqlsh` 和 `c_orderno`。确认单回调这三个一个都没有，于是返回全空、直接落日志走人。

讽刺的是 `billId` 和 `orderNo` **都是我们自己生成的号**，本来一查就能定位，纯粹是键名不认。

**改法**：`ReadCallback` / `ReadCallbackFromFormBody` 返回值加一项 `billId`；表单分支补认顶层 `billId`、content 里的 `orderNo` 与 `billId`； `FindByCallbackKeysAsync` 增加第五步「按 `RedBillId` 匹配，命中即按红票处理」； `ProcessCallbackAsync` 的守卫把 `billId` 一并算进去。

# 三、缺陷二：快捷冲红只有纸票才调

**现象**：确认单生效后 `RedStatus` 停在 1/4 不动，红票流水号永远是空的。

**原因**：原代码 `IsRedConfirmEffective(status) && 流水号为空 && IsPaperInvoice(...)` ——只有数电纸票才调 `fastInvoiceRed`，电票被认为"税局自动开、我们只要查"。

**这个前提是错的。** 官方《发票快捷冲红接口》说明：

> 若红票在税局已自动开具，但本地开票状态非开票完成，此接口也支持向税局查询自动开具的数电电子红票。

而 `orderNo` 的说明是：

> 订单号，每个企业唯一；自动开具的数电红票，支持传该值替换掉自动开具红票诺诺生成的订单号，**仅支持替换一次**。

也就是说：**税局自动开红票时用的是服务商自己生成的订单号，不是我们申请确认单时传的那个。** 不调这个接口就没人把订单号换回我们的 `RedOrderNo`，后续拿它去 `queryInvoiceResult` 永远查不到红票，链路到此断掉。

**改法**：去掉 `IsPaperInvoice` 这个条件，确认单生效且本地还没有红票流水号时一律调。 `IsPaperInvoice` 已删除（本系统不开数电纸票）。

# 四、缺陷三：确认单作废状态漏了两个

**现象**：确认单被税局作废后，本地仍显示「冲红中」，这条发票开出**既不能编辑删除、也不能重新申请冲红**，只能改库。

**原因**：`InvoiceRedStatus` 枚举从 `9` 直接跳到 `15`，缺 `10` 作废（异常凭证）与 `11` 作废（纳税人状态异常阻断）。`ParseRedStatus` 靠 `Enum.IsDefined` 判定，认不出来就**保持原状态**，于是税局那边已废、本地还锁着。

**改法**：枚举补 `已作废异常凭证 = 10`、`已作废纳税人状态异常 = 11`，并把这两个纳入 `InvoiceRedStatusHelper.IsFailed`（失败终态才会解锁、才允许重新申请）。全项目 `5~9` 的表述统一改成 `5~11`。

# 五、顺带修的两处防回退

确认单回调**会随确认单每次变更重复推送**，而确认单自己的状态永远停在「已确认/无需确认」那几个值上、不带「红票已开出」这层信息。修完缺陷一之后这些推送真的会进来，于是暴露出两个会把已完成的冲红推回去的问题：

1. `ParseRedStatus` 增加「已经 `99` 冲红完成就不再改状态」——否则一条已冲红的票会被推回「冲红中」。
2. `RefreshRedAsync` 里 `RedStatus == 99` 时不再清 `RedFailCause`——那上面可能记着「红票开具成功但签章失败」，是留给人去服务商侧处理的痕迹，不能被一次重复推送抹成空。

红票号码、代码、开票日期、附件本来就是只增不清的（任何路径都只在取到值时才覆盖，附件按文件名去重），加上这两处，重复推送不会动到已落地的红票。

# 六、避坑指南

> [!IMPORTANT] **一次冲红会收到至少两条推送，不是一条。** 确认单推送（`confirmCallback`）负责把链路推到「调快捷冲红」，开票推送（`callback`）负责落地红票号。两者打的是**同一个回调地址**，靠 `operater` 与字段名区分。开票推送能打进来是因为确认单申请时传了 `callbackUrl`，官方说明「自动开票时，会透传到开票接口」。

> [!IMPORTANT] **`orderNo` 的替换只有一次机会，所以快捷冲红只在红票流水号为空时调。** 别为了"保险"去重复调，也别在已有流水号的情况下再调。

> [!IMPORTANT] **服务商的确认单作废取值必须列全。** 漏任何一个都会让那种作废因 `Enum.IsDefined` 判不出来而保持原状态，结果确认单在税局已废、本地却停在「冲红中」被永久锁死。日后服务商再加取值，枚举与 `IsFailed` 要同步加。

# 八、上线注意

回调解析的修复**必须一起上线**，否则确认单推送依然接不住，冲红全程只能靠人工点「查询冲红结果」。

已经卡在「确认单已生效」的历史票，部署后点一次「查询冲红结果」即可继续走完，不用手工改库。
