# 发票开出冲红（后端逻辑）

在【发票开出】上对已开出的蓝票发起冲红，走诺诺【红字确认单申请】→【红字确认单查询】→【发票快捷冲红】→【发票详情查询】四个接口，红票开出后回填红票号码/发票代码/开票日期，并把红票版式文件存进附件。完整流程与每个分叉见第一节。

**同时新增一条硬约束：一旦发起冲红，这条发票开出就只能查询**——编辑、删除、加挂/移除开票申请、重新开票全部拒绝。

> 前置阅读：`诺诺发票对接-发票开出调用诺诺开票-2026-08-15.md`（蓝票开具）。本文只写冲红新增的部分，凭据/token/签名/回调那一套完全复用，没有任何改动。

---

## 一、为什么冲红这么绕

数电发票**不能作废，只能冲红**。而且冲红不是"调一个接口开一张负数发票"这么简单，税局要求先立一张【红字确认单】，整条链路四个接口、五步，中间每一步都可能停下来等。

```
第0步  点「冲红」+ 选冲红原因            ← 唯一一次人工操作
         │  前置校验不过 → 当场报错，状态不变(见 0-A)
         ▼
第1步  saveInvoiceRedConfirm 提交确认单申请(带 callbackUrl 与我们生成的红票 orderNo)
         │  服务商报错 → 直接抛给操作人，状态留在"未冲红"，可改完重来
         ▼  受理成功 → RedStatus=15 申请中，落 RedBillId / RedOrderNo
         ┊
         ┊  (以下 2~4 步由【确认单回调】【开票回调】或人工点「查询冲红结果」触发，
         ┊   三者走的是同一段 RefreshRedAsync，行为完全一致)
         ┊
第2步  queryInvoiceRedConfirm 查确认单状态 ── 五个分叉(见 2-A)
         │  ├ 01 无需确认 / 04 购销双方已确认  → 生效，往下走
         │  ├ 02 待购方确认 / 03 待销方确认    → 停住，系统推不动
         │  ├ 05~11 作废 / 16 申请失败         → 失败终态，解锁，可重新申请
         │  └ 15 申请中 / 查不到 / 认不出      → 保持原状态，等下次
         ▼  顺带落 RedBillNo / RedBillUuid
第3步  fastInvoiceRed 拿红票流水号 ── 两个分叉(见 3-A)
         │  ├ 税局【已】自动开票 → 触发服务商按我们的 orderNo 修复红票落库，返回流水号
         │  └ 税局【未】自动开票 → 由它执行开票任务，返回流水号
         │  billNo/billUuid 还没回来 → 本次跳过、不报错，等下次
         ▼  已有红票流水号 → 不再调(orderNo 只能替换一次)
第4步  queryInvoiceResult 查红票详情 ── 按红票开票状态分叉(见 4-A)
         │  ├ 2 开票完成 / 24 签章失败 → 落地红票号码/代码/日期 + 存红票附件
         │  ├ 20/21/22 开票中/签章中/开票失败 → 只记原因，保持冲红中，等下次
         │  └ 查不到                   → 到此为止，等下次
         ▼
第5步  RedStatus=99 冲红完成 → 自动解除与开票申请的挂靠、重算费用(见第六节)
```

**为什么必须做成异步可刷新的**：第2步要不要购方点头，由税局按开票时间、购方是否已勾选抵扣/已入账等规则判定，本系统无从预知，只能查。

**但正常情况是"一次点击走完"**：购方还没勾选抵扣、没入账时确认单就是 `01 无需确认`，提交后立即生效、税局随即自动开红票，两条推送在几秒到几分钟内先后到达，全程无需人工介入。「查询冲红结果」是回调漏了或购方迟迟不确认时的兜底，不是每次都要点。

### 分叉明细

**0-A 点「冲红」时的前置校验**（任一不过就当场报错，`RedStatus` 不变）

| 校验 | 不过时的提示 |
| --- | --- |
| 冲红原因是合法枚举值 | 请选择冲红原因 |
| 发票开出存在 | 发票开出不存在 |
| `IssueStatus` 是开票完成或签章失败 | 该发票开出还没有通过接口开出发票，不能冲红 |
| `InvoiceNo` 有值 | 该发票开出没有发票号，不能冲红，请先查询开票结果 |
| `RedStatus` 未被锁定 | 已冲红(红票号 xxx)，不能重复冲红／正在冲红中(当前 xx)，请勿重复申请 |
| 客户开票信息有抬头 | 取不到客户开票信息的抬头，无法作为购方申请冲红 |
| 所属公司维护了税号与 appKey/appSecret | 公司[xxx]未维护统一社会信用代码…／未维护开票应用的 appKey/appSecret |
| 蓝票能取到20位数电票号码 | 取不到蓝票的数电票号码，无法申请冲红 |

**2-A 确认单状态（`billStatus`）的五个分叉**

| billStatus | 本地 RedStatus | 系统怎么做 | 锁定 |
| --- | --- | --- | --- |
| `01` 无需确认 | 1 | 进第3步 | 锁 |
| `04` 购销双方已确认 | 4 | 进第3步 | 锁 |
| `02` 销方录入待购方确认 | 2 | **停住**，等购方去电子税局确认；超72小时自动作废 | 锁 |
| `03` 购方录入待销方确认 | 3 | **停住**，等销方去电子税局确认（本系统只发起销方申请，这个状态只会查到） | 锁 |
| `05`~`11` 各种作废、`16` 申请失败 | 5~11 / 16 | 失败终态，记 `RedFailCause` | **解锁**，可重新申请（换新的 `billId` 与 `orderNo`） |
| `15` 申请中 | 15 | 保持，等下次 | 锁 |
| 查不到确认单 / 认不出的取值 | 保持原值 | 什么都不改，等下次 | 按原值 |

**3-A 快捷冲红的两个分叉**（同一个调用，不用我们判断）

| 情况 | 服务商做什么 | 返回 |
| --- | --- | --- |
| 税局**已**自动开票 | 按我们申请时传的 `orderNo` 修复红票并落库（该替换**仅支持一次**） | 红票流水号 |
| 税局**未**自动开票 | 执行开票任务 | 红票流水号 |
| `billNo` 或 `billUuid` 还没回来 | —（本次不调） | null，等下次查询 |
| 本地已有红票流水号 | —（本次不调） | 不重复调 |

**4-A 红票开票状态的分叉**

| 红票 status | 系统怎么做 |
| --- | --- |
| `2` 开票完成 | 回填红票号码/代码/开票日期，`RedStatus=99`，存红票附件，解除申请挂靠 |
| `24` 开票成功签章失败 | **同样按完成处理**（票已经开出来了），但 `RedFailCause` 记下签章问题让人去服务商侧处理 |
| `20` 开票中 / `21` 签章中 / `22` 开票失败 | 只记 `RedFailCause`，`RedStatus` 保持冲红中，等下次 |
| 查不到（税局还没生成） | 什么都不改，等下次 |

**谁来触发第2~4步**

| 触发源 | 说明 |
| --- | --- |
| 【确认单回调】`operater=confirmCallback` | 确认单状态每次变更都推，是最主要的推进源 |
| 【开票回调】`operater=callback` | 红票开出后推，按红票号命中红票分支 |
| 人工点「查询冲红结果」 | 兜底，走同一段代码 |
| 报文读不出 `serialNo`/`orderNo`/`billId` | 落回调日志，不处理 |
| 本机没有匹配的发票开出 | 落回调日志并返回成功，避免服务商反复重推 |

**幂等**：任何一步重复执行都安全——`RedStatus=99` 后不会被确认单状态推回去、红票号码只增不清、附件按文件名去重、第二次解绑挂靠时查出来是空的什么都不做。

### 只做全额冲红

诺诺的确认单申请支持部分冲红（传 `detail` 明细，序号要和原蓝票严格对齐）。**本实现不传 `detail`，即全额冲红**。理由：本系统的发票开出是"多张开票申请合并成一张票"，部分冲红要精确到票面明细行，业务上还没有对应的操作入口；真要部分冲红，正确做法是全额冲红后重新开一张。

### 只做销方发起

`applySource` 固定 `0`（销方），`identity` 固定 `0`。购方发起的确认单（03 购方录入待销方确认）本系统只会**查到**、不会**发起**，查到时提示销方去税局端确认。

## 四、锁定规则（本次的另一半需求）

### 判定口径只有一份

`InvoiceRedStatusHelper`（`Dto\NuonuoIssueDto.cs`）：

```csharp
IsFailed(s)  => s ∈ {5,6,7,8,9,16}          // 确认单作废 / 申请失败
IsFinal(s)   => s == 99 || IsFailed(s)      // 不必再轮询
IsLocked(s)  => s != 0 && !IsFailed(s)      // 冲红中或已冲红 → 只能查询
```

**为什么失败态要解锁**：确认单被否认/超时作废/申请失败时，这张蓝票在税局那边**还是有效的**，冲红等于没发生过，所以要允许重新发起冲红，自然也不该继续锁着。

**为什么 99 也锁着**：票已经冲红了，红蓝两张都是税局在册的凭证，本地记录必须原样保留下来对账，不能再改、更不能删。

### 加在哪几处

| 入口 | 方法 | 校验 |
| --- | --- | --- |
| 修改发票开出（全量） | `EditAsync` | `InvoiceIssueLockRule.EnsureNotLocked` |
| 仅改主表 | `EditMainAsync` | `InvoiceIssueLockRule.EnsureNotLocked` |
| 加挂开票申请 | `AddApplicationsAsync` | `InvoiceIssueLockRule.EnsureNotLocked` |
| 移除开票申请 | `RemoveApplicationsAsync` | `InvoiceIssueLockRule.EnsureNotLocked` |
| 批量删除 | `DeleteAsync` | `InvoiceIssueLockRule.EnsureNoneLocked`（一次报出所有被挡下的单号与原因） |
| 重新开票 | `NuonuoInvoiceManager.IssueAsync` | `InvoiceRedStatusHelper.EnsureNotLocked`（只拦冲红；开票状态那几种在下面有更贴切的提示） |

查询类接口（`DetailAsync` / `GetPagedListAsync` / `QueryIssueResultAsync` / `QueryRedResultAsync`）**不加校验**，冲红中/已冲红照常可查。

> 校验一律放在"取出实体、判空之后，任何写动作之前"，避免出现"改了一半才被拦下"。

> **2026-08-16 补充**：`InvoiceIssueLockRule` 同时还拦"发票已经开出去了"这一种情况（`IssueStatus` 不是未开票也不是开票失败）。也就是说接口开票**一发出去**这条发票开出就只能查询，不必等到冲红。详见《发票开出-已开票口径与编辑锁定-2026-08-16.md》。

## 五、报文怎么组出来的

### 红字确认单申请 `saveInvoiceRedConfirm`

| `sellerTaxNo` | 所属公司 `UnifiedSocialCreditCode` |
| `sellerName` | 所属公司 `DisplayName`，截 100 字符 |
| `buyerTaxNo` | 客户开票信息 `ClientInvoiceInfo.TaxNum` |
| `buyerName` | 客户开票信息 `ClientInvoiceInfo.Header`，截 100 字符 |
| `redReason` | 操作人选的冲红原因 |
| `extensionNumber` | **当前登录人**的 `User.ExtensionNumber`，没维护则不带该字段（2026-09-01 起，原为全局配置） |

| `autoInvoice` | **不传**。文档写着"目前该字段不生效，电票都自动开，纸票都不自动"，传了也没用 |

### 红字确认单查询 `queryInvoiceRedConfirm`

固定按 `identity=0` + `billId` 查，`pageNo=1` / `pageSize=10`。用申请号查时不需要传时间范围（否则最大只能查 90 天，历史票就查不到了）。

### 发票快捷冲红 `fastInvoiceRed`（确认单生效后一律会走）

> **2026-09-02 修正**：原来写"只有纸票会走"，那是错的，导致电票冲红永久卡在"确认单已生效"。官方文档对本接口的说明是「若红票在税局已自动开具，但本地开票状态非开票完成，此接口也支持向税局查询自动开具的数电电子红票」，而 `orderNo` 是「自动开具的数电红票，支持传该值替换掉自动开具红票诺诺生成的订单号，**仅支持替换一次**」。
>
> 也就是说：**税局自动开红票时用的是诺诺自己生成的订单号，不是我们申请确认单时传的那个**。不调这个接口就没人把订单号改回我们的，后续拿 `RedOrderNo` 去 `queryInvoiceResult` 永远查不到红票，冲红一直停在 `RedStatus=1/4`。所以现在不分票种，只要确认单生效且本地还没有红票流水号就调它；因为订单号只能替换一次，也只在流水号为空时调。

| 诺诺字段 | 取值来源 |
| --- | --- |
| `orderNo` | `RedOrderNo` |
| `taxNum` | 销方税号（须与消息头 `userTax` 一致） |
| `billNo` / `billUuid` | 确认单查询返回的编号与 uuid，**两者都必填**；税局还没回这两项时本次跳过，等下一次查询再开 |
| `elecInvoiceNumber` | 蓝票的20位数电票号码 |
| `invoiceCode` | 蓝票发票代码 |
| `invoiceId` | 蓝票开票流水号 `IssueSerialNum` |
| `invoiceLine` | 红票票种，取蓝票同票种 |
| `callBackUrl` | 同蓝票 |

## 六、几个关键实现决策

### 申请号与订单号怎么生成

|  | 首次申请 | 失败后重新申请 |
| --- | --- | --- |
| `billId`（上限32位，需唯一） | `发票开出Id.ToString("N")`（32位十六进制） | `Guid.NewGuid().ToString("N")` |
| `orderNo`（上限20位，企业内唯一） | `"R" + 发票开出Id.ToString("N").Substring(0,19)` | `"R" + 新Guid` 同样规则 |

**首次为什么用 Id 派生**：和蓝票订单号同一个道理——万一请求已经发到税局、本地事务却回滚了，重试时算出来的还是同一个申请号，会被服务商按重复挡下，**不可能在税局那边留下两张确认单**。

**失败重试为什么必须换号**：确认单被作废/申请失败后重新申请，沿用旧号会被判重复直接拒绝。此时是操作人看到失败后有意重来，回滚风险远小于首次，换随机号是划算的。判断依据是 `RedBillId` 已有值（说明申请过）。

**`R` 前缀不是装饰**：十六进制里不会出现 `R`，所以红票订单号与蓝票订单号**结构上不可能相同**，回调按订单号命中哪一套就能确定推的是红票还是蓝票，不需要额外标记位。

### 纸票的数电票号码从哪来

冲红接口要的是 **20位数电票号码**（`blueElecInvoiceNumber`）：

- 电票：`InvoiceNo` 本身就是 20 位，直接用。
- 纸票：`InvoiceNo` 只有 8 位，20 位那个本地**没有存**（当初刻意没加 `AllElectronicInvoiceNumber` 列，因为电票下它与 `invoiceNo` 完全重复）。

处理办法（`ResolveElecInvoiceNumberAsync`）：**发票号不是 20 位时，按流水号回查一次发票详情**，从 `allElectronicInvoiceNumbe` 取。只有纸票会多这一次调用，换来不加一列冗余字段。

### 整条链路是回调驱动的：一次冲红会收到**两条**推送（2026-09-02 补记）

操作人只点一次「冲红」，后面全靠服务商推送把链路往前推。两种推送**打的是同一个地址** `POST /api/invoice-issue/callback`：

```
① 点「冲红」
   → saveInvoiceRedConfirm 提交确认单申请(带 callbackUrl 与我们生成的红票 orderNo)
   → 同步返回 redStatus=15 申请中，本次请求结束

② 服务商推【确认单回调】 operater=confirmCallback
   → 按 billId / orderNo 认出是哪张票
   → queryInvoiceRedConfirm 查确认单状态
   → 已生效(无需确认/双方已确认)则**就在这次回调处理里调 fastInvoiceRed** 拿红票流水号
   → 顺手 queryInvoiceResult 查一次，红票已开出就直接落地

③ 服务商推【开票回调】 operater=callback
   → 按 RedSerialNum / RedOrderNo 匹配到红票分支
   → 回填红票号码/开票日期 + 下载红票版式文件存附件
   → redStatus=99 冲红完成
```

**开票回调为什么也会打到这个地址**：确认单申请时传的 `callbackUrl`，官方说明是「确认单回传地址；**自动开票时，会透传到开票接口**」。所以税局自动开出的那张红票，开票结果会推到同一个地址，不需要另外配。

**两种推送的字段名完全不是一套**，解析时都要认（见《诺诺发票对接-发票开出冲红-回调解析补齐-2026-09-02.md》）：

|  | 开票回调 | 确认单回调 |
| :-- | :-- | :-- |
| `operater` | `callback` | `confirmCallback` |
| 顶层参数 | `operater` / `content` / `orderno` | `operater` / `content` / `billId`（**没有 orderno**） |
| content 键名 | `c_` 前缀：`c_fpqqlsh` / `c_fphm` / `c_url` | 驼峰：`billId` / `billNo` / `billUuid` / `billStatus` / `orderNo` |

**推送只是触发器，不是落库依据**：收到后仍然去查确认单、查发票详情，以查询结果为准写库，这样即使推送报文结构变了也不会写脏数据。

**任何一条推送丢了都能补**：点「查询冲红结果」走的是完全相同的 `RefreshRedAsync`，幂等。唯一推不动的是确认单停在「待购方确认」——服务商也没什么可推的，得购方去电子税局确认，或者等超 72 小时自动作废。

### 回调怎么区分红票和蓝票

`FindByCallbackKeysAsync` 按五步匹配，命中哪一步就决定走哪条链路：

```
IssueSerialNum == serialNo  → 蓝票
RedSerialNum   == serialNo  → 红票
IssueOrderNo   == orderNo   → 蓝票
RedOrderNo     == orderNo   → 红票
RedBillId      == billId    → 红票   (确认单回调只带 billId 时靠它兜底)
```

流水号一票一号最准，排在订单号前面；确认单申请号只可能是红字确认单的，命中即按红票处理。红票订单号带 `R` 前缀、与蓝票订单号不可能相同，因此不存在红蓝误判。

命中红票时走 `RefreshRedAsync`（红票号码落在红冲字段上），**绝不能走蓝票那条 `ApplyResultAsync`，否则会拿红票号码把蓝票的 `InvoiceNo` 覆盖掉**。

### 冲红完成后解除与开票申请的挂靠

`ApplyRedResultAsync` 回填完红票字段后会调 `DetachApplicationsAsync`：

1. 软删该发票开出的全部 `InvoiceIssueItem`
2. 关联开票申请 `Status = Auditing`、`InvoiceNo = null`
3. 重算这些申请所关联费用的开票状态与已开票金额

**票被冲掉就等于没开过**，那批开票申请必须重新可用，否则关联费用永远卡在"已开票"、再也开不出票。

蓝票的 `InvoiceNo` 与红票的 `RedInvoiceNo` 都**保留在这条发票开出上**，红蓝两张票在本地都查得到；挂靠明细是软删除，历史上挂过哪些申请在库里也查得到。发票开出本身仍被红冲状态锁死，只能查询。

重复回调时这段是幂等的：第二次进来挂靠明细已删完，查出来是空的，什么都不做。

> 费用的"已开票"口径就是"有没有挂在发票开出上"，所以解绑后金额会自动退回来，不需要在这里额外算金额。详见《发票开出-已开票口径与编辑锁定-2026-08-16.md》。

### 红字确认单查询响应的层级做了兼容

《红字确认单查询接口》文档的"响应参数"表把 `total` / `list` 和 `code` / `describe` **并列**写在一起，但同平台其它接口（如发票详情查询）内容都在 `result` 里，无从确定服务商实际给的是哪一层。

因此 `NuonuoResponse<T>` 加了 `[JsonExtensionData] Extra` 收集未声明的顶层字段，`ExtractRedConfirm` 三种形态都认：

1. `result` 本身是数组
2. `result.list` 是数组
3. 顶层 `list` 是数组

这样服务商无论按哪种给都能读到，不会因为层级猜错在生产上读到空值。

### 状态解析的容错

`ParseRedStatus(billStatus, current)`：解析不出来、或解析出 `0`/`99` 这两个本地专用值时，**保持原状态不动**。避免把一条正在走流程的确认单误判成"未冲红"（会被误解锁）或"冲红完成"（会被误认为已完成）。

**已经 `99` 冲红完成的不再改动状态**（2026-09-02 补）：确认单回调会随确认单每次变更重复推送，而确认单自己的状态永远停在"已确认/无需确认"那几个值上、不带"红票已开出"这层信息；照它回写会把一条已冲红的票推回"冲红中"，界面上看着像没冲完。同理，`99` 时也不再清 `RedFailCause`——那上面可能记着"红票开具成功但签章失败"，是留给人去服务商侧处理的痕迹。

> ⚠️ **服务商的作废取值必须列全**，漏一个就会锁死一张票。`billStatus` 的作废值是 `05`~`11` （`10` 异常凭证、`11` 纳税人状态异常阻断这两个是 2026-09-02 才补上的），漏掉的那个会因为 `Enum.IsDefined` 判不出来而保持原状态，结果确认单在税局已经废了、本地还停在"冲红中"，这条发票开出既不能编辑删除、也不能重新申请冲红，只能改库。

`RedBillNo` / `RedBillUuid` 只在返回值非空时覆盖——这两项进了税局就不会再消失，先有后无必然是异常返回，不能让一次空返回把它们抹掉（抹掉后纸票就再也开不出红票了）。

## 七、落地回填做了什么

红票状态为**开票完成**或**签章失败**（票已经开出来了，只是签章没成）时：

1. **发票开出**：`RedInvoiceNo`、`RedInvoiceCode`（仅纸票）、`RedInvoiceTime`、`RedStatus=99`
2. **附件**：下载红票的 `ofdUrl` / `pdfUrl`（都没有则退 `paperPdfUrl`），文件名 `红票OFD-{红票号}.ofd` / `红票PDF-{红票号}.pdf`，与蓝票附件挂在同一个模块下（`ModuleTypeId=160090` / `ItemId=发票开出Id`），按文件名去重
3. 签章失败时 `RedStatus` 仍记 `99`（号码确实开出来了），但 `RedFailCause` 会写上签章失败原因留痕

4. **解除与开票申请的挂靠**：删挂靠明细、申请退回待审核、重算费用开票状态（见上方"冲红完成后解除与开票申请的挂靠"）

红票还在开票中/开票失败时，只写 `RedFailCause`，`RedStatus` 保持确认单的状态（仍是锁定态）。

## 八、防呆一览

| 场景 | 处理 |
| --- | --- |
| 开票方式不是接口开票 | 拒绝冲红 |
| 蓝票还没开出来（`IssueStatus` 不是开票完成/签章失败） | 拒绝，提示先开票 |
| 蓝票没有发票号 | 拒绝，提示先查询开票结果 |
| 已冲红（99） | 拒绝重复冲红，提示红票号 |
| 冲红中（1/2/3/4/15） | 拒绝重复申请，提示去查询冲红结果 |
| 确认单作废/申请失败（5~11/16） | **允许**重新申请冲红，换新的申请号与订单号 |
| 没申请过冲红就查冲红结果 | 拒绝，提示还没申请过 |
| 冲红原因没传/传了非法值 | 拒绝 |
| 确认单刚提交、服务商还没落库（查不到） | 不报错，保持"申请中"，等下次查 |
| 纸票确认单生效但 `billNo`/`billUuid` 还没回来 | 本次跳过开红票，等下一次查询，不报错 |
| 冲红中/已冲红的记录做写操作 | 全部拒绝，见第四节 |
