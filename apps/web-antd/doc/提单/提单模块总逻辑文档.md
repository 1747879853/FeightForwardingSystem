# 1. 业务背景说明 (Background)

**白话解释：**

一票海运出口或件杂货（以及它们下面的每一条分单）都会签发一份提单。提单从我们手里流转到客户手里这一路，业务上要留下痕迹：正本提单什么时候收到的（签入）、审批通过之后什么时候交出去的（签出）、交出去用的什么方式（快递/自提/外派/邮件/电子提单）、中途因为欠款等原因被扣下过没有（扣单）、客户不要正本改成电放了没有（换签）。

所以提单不是一张用户手工新建的单据，而是**跟着主单和分单自动生成的一条流转记录**。提单的来源有四种： **海运出口主单、海出分单、件杂货主单、件杂货分单**。主单建一条、每条分单各建一条，主单或分单被删除时连带删掉。用户在提单模块里做的事只有流转动作（签入、换签、提交签出审核、签出、扣单及它们的取消），不做新增和删除。

**只有海运出口与件杂货（含各自的分单）有提单**，海运进口与空运出口不建提单。件杂货本身的字段与操作见 `文档/件杂货/件杂货模块总逻辑文档.md`。件杂货没有船公司、装运方式、提单类型、集装箱，所以件杂货的提单上这几项一律没有（见第 5 章卡点 10）。

# 2. 功能与操作说明 (Features & Operations)

- **自动建提单：** 下面 10 个入口都会自动建出对应的提单。签单方式为「正本」的初始状态是 `待签入`，其余（电放、SEAWAY 等）建出来就是 `已签入`。
  - 海运出口侧：新增主单、复制主单、业务联系单（业务类型为海运出口）审核通过转正式票、新增海出分单、复制海出分单。
  - 件杂货侧：新增件杂货、复制件杂货、业务联系单（业务类型为件杂货）审核通过转正式票、新增件杂货分单、复制件杂货分单。
  - 联系单上没有签单方式，从联系单转出来的主单提单一律先按非正本建成 `已签入`，操作补录签单方式时再按第 3.2 节纠正。
- **签入：** 只有 `待签入` 的提单可以签入。要填签入日期（必填，用户自己填，不限制未来日期）、签入备注（选填）、提单扫描件（必填，只能一个）。签入后状态变 `已签入`。
- **取消签入：** 只有**正本**且当前签入着的提单可以取消，回到 `待签入`。已换签的要先取消换签。取消不会删掉之前上传的扫描件——扫描件挂在那一次签入的历史记录上，永久留存；再签入时要重新上传一份。
- **换签（改签）：** 把正本改成电放，支持批量。只有**正本**且状态为 `已签入`/`已驳回` 的提单可以换签。要填换签时间（必填）与备注（选填）。换签改的是**主单提单改主单（海运出口或件杂货）、分单提单只改该分单（海出分单或件杂货分单）**的签单方式，不连带改别人。
- **取消换签：** 把签单方式恢复成换签前那个正本。状态不变。
- **提交签出审核：** 一次可提交多张提单，整批放进一个工作流。只有 `已签入`/`已驳回` 的提单可以提交，且**整批提单对应的委托单位必须相同**。比的是提单的结算对象：主单提单取主单的委托单位，分单提单取分单自己的结算对象，海出分单与件杂货分单同一口径（见卡点 3）。一批里可以同时有海运出口和件杂货的提单，只要结算对象相同。
- **撤销提交：** 整批撤销。只要有任何一个审核人已经审过（通过或驳回）就不允许撤销。
- **签出审核：** 通过、驳回、通过后驳回**都走同一个接口**，支持批量、支持部分审核（同一批里可以只驳回其中几张，其余照常通过）。
- **签出：** 只有 `可签出` 的提单可以签出，支持批量，整批共用同一份签出信息：签单方式（必填）、签出方式（必填，枚举）、签出日期（必填）、备注（选填）。签单方式会**回填主单和分单**：主单提单回填主单（海运出口或件杂货），分单提单同时回填该分单（海出分单或件杂货分单）和它所属的主单。
- **取消签出：** 回到 `可签出`。签出时回填给主单/分单的签单方式**不回退**。
- **扣单：** 除 `签出审核中` 与 `已扣单` 外的任何状态都可以扣单，支持批量。要填扣单日期（必填）与备注（选填）。
- **取消扣单：** 回到**扣单之前**的那个状态（由历史记录上的「动作前状态」决定）。
- **操作历史：** 8 种动作（签入/取消签入、签出/取消签出、换签/取消换签、扣单/取消扣单）各记一条，只增不改，按操作时间倒序查看。
- **海运出口列表带提单状态：** `GET /api/services/app/SeaExportAdmin/GetPagedListAsync` 每条海运出口返回 `billOfLadings`，主单和该票全部分单各一条，只含提单 id 与状态。主单在前，分单按创建时间升序。详情不返回这个列表。
- **提单分页列表：** 可见范围 = 当前用户能看到的海运出口 ∪ 能看到的件杂货，两边各按自己模块的业务数据权限与表级权限算。筛选含船公司、签单方式、委托单位。**船公司只有海运出口有**：按船公司筛选时件杂货提单一律不出现，筛「船公司未填写」时件杂货提单全部出现。船名、航次同时匹配海运出口与件杂货；开船日期、委托编号、业务员/操作按业务表取，两种业务都生效。 `IsOverdueUnpaid` 只接受 `true`：已过应结日期且应收未结清，不管承诺付款日期；主单提单比主单应结日期，分单提单比分单自己的应结日期（海出分单或件杂货分单）。 `IsDeducted` 同样只接受 `true`：只返回状态为 `已扣单` 的提单，传 `false` 或不传都不筛选；与 `Status` 同时传时取交集。列表和详情都带最近一次签出审核意见 `AuditRemark`、审核时间 `AuditTime`、审核人昵称 `AuditUserName`（权限仍是查看，不要求审核权限）。已驳回时 `AuditRemark` 就是驳回原因。
- **分组统计：** `GetGroupedListAsync` 查询条件与列表完全一致，按委托单位 / 船公司 / 签单方式分组，返回每组 id、名称、提单条数（按条数倒序，不分页）；按船公司分组时额外返回 logo。件杂货的提单一起参与分组：按船公司分组时全部并进「未填写」组；按签单方式分组时件杂货主单提单按件杂货的、件杂货分单提单按该分单的签单方式计。点某组再带对应筛选条件调列表；点未填写组传 `CarrierIdEmpty` / `CodeIssueTypeIdEmpty`。
- **四个数量：** `GetCountAsync` 一次返回总数量（当前用户能看到的全部提单，含件杂货的）、待签出（状态 `可签出`）、超期未收（口径同 `IsOverdueUnpaid=true`）、已扣单（状态 `已扣单`，口径同 `IsDeducted=true`）。无搜索条件，四个数量都只统计当前用户能看到的提单，点哪个数量就带对应条件查列表和分组，条数对得上。
- **签出审核任务列表：** 审核人看「与我有关的」提单审核任务。**一行就是一次提交**（一个主任务），行下面挂本批的全部提单；审核时在行里勾选其中几张即可，没勾的保持原状。可按「待我审核 / 我已审核」「是否处理完毕」「提单号 / 委托单位 / 提交时间」筛选。
- **签出审核任务详情：** 按主任务 id 取一次提交，在列表行字段之外多给六部分审核依据：本批提单明细（带是否压单）、压单的提单、后续新单的提单、委托单位详情、该委托单位的应收欠费报表、 **结算单位的超期列表**（四类超期合并成一张表，一票一条；海运出口的票挂 `SeaExport`，件杂货的票挂 `BreakBulk`）。压单、后续新单的范围是同委托单位下所有未签出的提单，海运出口与件杂货混在一起按开船日期比。与列表不同的是不限「与我有关」，审核完的、别人审的批次都能按 id 查出来看进度。

# 3. 状态流转说明 (Status Transitions)

提单状态共 **7 个**：`待签入`、`已签入`、`已驳回`、`签出审核中`、`可签出`、`已签出`、`已扣单`。

> `已驳回` 在**行为上与 `已签入` 完全相同**（可提交审核、可换签、可取消签入、可扣单），单独一个状态值只是为了让列表看得出这张被驳回过。驳回原因在列表和详情的 `AuditRemark`。

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| （无） | 系统 / 主单或分单新建 | `待签入` | 签单方式为「正本」 |
| （无） | 系统 / 主单或分单新建 | `已签入` | 签单方式不是「正本」，不需要签入 |
| `待签入` | 操作 / 签入 | `已签入` | 必填签入日期与扫描件 |
| `已签入`、`已驳回` | 操作 / 取消签入 | `待签入` | 仅正本、且当前签入着、且未换签 |
| `已签入`、`已驳回` | 操作 / 换签 | 状态不变 | 只改签单方式（正本→电放），不动状态 |
| `已签入`、`已驳回` | 操作 / 取消换签 | 状态不变 | 恢复成换签前的正本 |
| `已签入`、`已驳回` | 操作 / 提交签出审核 | `签出审核中` | 工作流算不出审核人时直接到 `可签出` |
| `签出审核中` | 操作 / 撤销提交 | `已签入` 或 `已驳回` | 之前被驳回过的回 `已驳回`，否则回 `已签入` |
| `签出审核中` | 审核人 / 审核通过（末级） | `可签出` | 未到末级时状态不变，继续 `签出审核中` |
| `签出审核中` | 审核人 / 审核驳回 | `已驳回` | 可重新提交 |
| `可签出` | 审核人 / 通过后驳回 | `已驳回` | 只有审核通过过的那个人能驳回 |
| `可签出` | 操作 / 签出 | `已签出` | 必填签单方式、签出方式、签出日期 |
| `已签出` | 操作 / 取消签出 | `可签出` | 签单方式不回退 |
| 除 `签出审核中`、`已扣单` 外任意状态 | 操作 / 扣单 | `已扣单` | 扣单前状态记在历史上 |
| `已扣单` | 操作 / 取消扣单 | 扣单前的状态 | 按历史记录回滚 |

## 3.1 几条必须记住的互斥规则

- **`签出审核中` 禁止任何其他操作**：不能签入、取消签入、换签、扣单、签出，只能撤销提交或走审核。
- **`已扣单` 只能取消扣单**，其余动作全禁。
- **`已签出` 只能取消签出与扣单**，不能再签入、换签、重新提交审核。
- **`可签出` 不能重复提交审核**，已经通过了就直接签出。
- **换签之后不能取消签入**（换完签单方式是电放，电放不可取消签入），要先取消换签。

## 3.2 签单方式变了，提单状态怎么跟

主单（海运出口或件杂货）或分单（海出分单或件杂货分单）的签单方式被改动时（单条编辑、批量编辑、分单提单签出回填主单），会自动纠正提单状态：

| 改动方向 | 提单当前状态 | 纠正结果 | 为什么 |
| :-- | :-- | :-- | :-- |
| 改成非正本（电放等） | `待签入` | → `已签入` | 电放没有签入这一步，不纠正的话这张提单永远卡在待签入 |
| 改成正本 | `已签入`/`已驳回` 且**没有人工签入记录** | → `待签入` | 那个「已签入」是建单时自动给的，没有签入依据，必须补签入 |
| 改成正本 | `已签入`/`已驳回` 且**有人工签入记录** | 不动 | 那次签入是真的 |
| 任意 | `签出审核中`/`可签出`/`已签出`/`已扣单` | 一律不动 | 动了会把审核与签出的结果冲掉 |

「有没有人工签入记录」的判定口径：**签入条数 > 取消签入条数**（每次取消都对应它前面那一次签入）。

# 4. 核心字段说明 (Field Definitions)

## 4.1 提单表 `App_BillOfLadings`

提单表**不存签单方式**。正本/电放一律直读主单或分单上的 `CodeIssueTypeId`：海运出口主单提单读 `App_SeaExports`、件杂货主单提单读 `App_BreakBulks`、海出分单提单读 `App_SeaExportSeparates`、件杂货分单提单读 `App_BreakBulkSeparates`，换签与签出回填改的也是这四张表。

**四种来源怎么区分**：`SeaExportSeparateId` 有值是海出分单提单，`BreakBulkSeparateId` 有值是件杂货分单提单， **两列都为空才是主单提单**。主单是海运出口还是件杂货，看业务表 `App_TransportOrders.BizType`（0 海运出口、3 件杂货）。

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🔗 联动规则 | 🛡️ 校验限制 |
| :-- | :-- | :-- | :-- | :-- |
| **Id** | 提单主键 | 系统生成 Guid | — | — |
| **TenantId** | 租户 | 系统 | — | — |
| **SeaExportId** | **业务 id**：海运出口或件杂货的 id，与业务表 `TransportOrder` 同 id。列名沿用历史命名，外键指向业务表 | 建单时写入 | 决定提单的委托单位、船名航次、应结日期，以及查看、操作时按哪个模块判数据权限 | 必填 |
| **SeaExportSeparateId** | 海出分单 id，仅海出分单的提单有值 | 建单时写入 | 有值时签单方式、结算对象、分提单号取该海出分单的 | 可空 |
| **BreakBulkSeparateId** | 件杂货分单 id，仅件杂货分单的提单有值 | 建单时写入 | 有值时签单方式、结算对象、分提单号取该件杂货分单的 | 可空；与 `SeaExportSeparateId` 不会同时有值 |
| **Status** | 提单状态（7 个枚举值） | 流转动作写入 | 见第 3 章 | 必填 |
| **PromisePayDate** | 承诺付款日期 | 提交审核时用户填 | 只有该张提单**超期**时才要求填 | 超期时必填，且**必须晚于主单应结日期** |
| **OverdueRemark** | 超期备注 | 提交审核时用户填 | 同上 | 超期时必填，≤1024 字 |

**超期证明附件**不在表上，走附件表：`ModuleTypeId = 160140`（`BillOfLadingOverdue`），`ItemId = 提单id`，可多个。

## 4.2 提单操作历史表 `App_BillOfLadingHistories`

只增不改。取消类动作按 `BeforeStatus` 回滚提单状态，所以每条都必须把动作前的状态记全。

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🛡️ 说明 |
| :-- | :-- | :-- | :-- |
| **Id** | 历史主键 | 系统生成 Guid | **签入扫描件按它挂附件**，不是按提单 id |
| **BillOfLadingId** | 提单 id | 系统 | 必填 |
| **ActionType** | 动作（签入/取消签入/签出/取消签出/换签/取消换签/扣单/取消扣单） | 系统 | 必填 |
| **BeforeStatus** | 动作前的提单状态 | 系统 | 取消扣单按它回滚 |
| **AfterStatus** | 动作后的提单状态 | 系统 | 换签与取消换签时与 `BeforeStatus` 相同（状态不变） |
| **ActionDate** | 动作日期：签入日期 / 签出日期 / 换签时间 / 扣单日期 | 用户填 | 这 4 个动作必填；取消类动作为空 |
| **Remark** | 备注 | 用户填 | 全部动作都可填，≤1024 字 |
| **CodeIssueTypeId** | 签单方式 id，**不同动作语义不同**（见下） | 系统 | 可空 |
| **SignOutType** | 签出方式（快递/自提/外派/邮件/电子提单） | 用户填 | 仅签出有值，签出时必填 |

> [!IMPORTANT] **`CodeIssueTypeId` 在不同动作下的语义**
>
> - **签出 / 取消签出**：签出时用户填的那个签单方式（已回填主单/分单，这里留一份痕迹）
> - **换签 / 取消换签**：**换签之前**那个签单方式（也就是正本那条）。取消换签就是按它恢复，所以这里绝对不能改成记「换签后的电放」，否则恢复不回去。
> - 签入、取消签入、扣单、取消扣单：不记，为空。

**签入扫描件**走附件表：`ModuleTypeId = 160130`（`BillOfLadingSignIn`），`ItemId = 历史记录id`，只能一个。按历史记录挂而不是按提单挂，是为了让「取消签入后再签入」的两次扫描件各自留存、互不覆盖。

## 4.3 依赖的既有字段

| 字段 | 所在表 | 提单模块怎么用 |
| :-- | :-- | :-- |
| `BizType` | `App_TransportOrders` | 主单是海运出口（0）还是件杂货（3）。查看详情、历史和单张动作按它决定走哪个模块的数据权限 |
| `CodeIssueTypeId` | `App_SeaExports` / `App_BreakBulks` / `App_SeaExportSeparates` / `App_BreakBulkSeparates` | 提单的签单方式；四张表都是新增与单条编辑时必填 |
| `BillType` | `App_CodeIssueTypes` | **精确等于「正本」**判定正本；换签要找 `BillType` 精确等于「电放」的那条 |
| `ClientId` | `App_TransportOrders` | 委托单位。提单列表筛选、任务行展示、压单范围、客户详情与欠费报表都按它取 |
| `CarrierId` | `App_SeaExports` | 船公司，**只有海运出口有**。件杂货没有船公司，列表按船公司筛选、分组时件杂货提单一律算未填写 |
| `Vessel` / `InnerVoyno` / `TerminalVoyno` | `App_SeaExports` / `App_BreakBulks` | 船名、船公司航次、码头航次，列表的船名航次筛选两张表都匹配 |
| `SettlementId` | `App_SeaExportSeparates` / `App_BreakBulkSeparates` | 分单结算对象。**分单提单的「结算对象」取它**，主单提单的结算对象则等于主单的委托单位；提交审核时比的就是这个值 |

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **卡点 1：签单方式已改为必填** 新增、单条编辑海运出口主单、海出分单、件杂货主单、件杂货分单时，签单方式为空一律拦住，提示「签单方式不能为空」。批量编辑不校验（没传就是不改）。 **存量数据影响**：库里签单方式为空的老票，下次单条编辑时必须先补填签单方式才能保存。业务联系单转正式票**不校验**（联系单上没有这个字段），海运出口和件杂货都一样：转出来的主单提单先按非正本建成 `已签入`，等操作在海运出口或件杂货里补录签单方式时由状态纠正逻辑处理。

> [!IMPORTANT] **卡点 2：正本判定靠「签单方式名称精确等于正本」** 签单方式表 `App_CodeIssueTypes` 是用户可维护的基础资料，只有 `BillType` 一个文本列，没有「是否正本」的标志。所以判定口径是 `BillType.Trim() == "正本"`。 **风险**：客户把那一行改名成「正本提单」「ORIGINAL」，或者自己新建一行叫别的名字，正本判定会**静默失效**（不报错，只是新建的提单全部按非正本处理、直接已签入）。同理，**基础资料里必须有一行 `BillType` 精确等于「电放」**，否则换签会报「请先在签单方式基础资料中维护【电放】,否则无法换签」。

> [!IMPORTANT] **卡点 3：提交审核时整批委托单位必须相同** 同一次提交里的提单必须结算给同一家，否则报「同一次提交的提单委托单位必须相同」。取值口径：**主单提单取主单的委托单位 `TransportOrder.ClientId`，分单提单取分单自己的结算对象 `SeaExportSeparate.SettlementId` 或 `BreakBulkSeparate.SettlementId`**——分单有独立的结算对象，不能拿所属主单的委托单位去比。海运出口和件杂货的提单可以放进同一次提交，只要这个值相同。出参上这个值是提单结构里的 `Settlement` 字段（任务行上也有一个，整批相同）。
>
> 注意提单模块里另外几处说「委托单位」的地方（提单列表的委托单位筛选、任务行的 `Client`、任务详情的压单/后续新单范围、客户详情与欠费报表）**仍然一律按主单的委托单位取**，没有跟着换成结算对象；结算对象是作为额外字段返回的，不参与那几处的取数与筛选。

> [!IMPORTANT] **卡点 4：超期就必须填承诺付款日期、超期备注、证明附件** 超期判定 = **当天已过主单应结日期**（只比日期不比时分） **且** **该票应收未全部结清**。结清口径：该 `TransportOrderId` 下所有 `PaySide=收` 的费用（含各更改单）全部 `SettlementStatus=结算完毕` 才算结清；**一条应收都没有时视为已结清**（与销售提成口径一致）。也就是说：钱已经收齐的票，哪怕应结日期早就过了，也**不算超期**，不用填这三样。逐张判定，一批里只有超期的那几张要填。承诺付款日期必须**晚于**主单应结日期。撤回或驳回后重新提交时**重新判定、重新填**，上一轮的值不清空（不再超期时就留着不动）。

> [!IMPORTANT] **卡点 5：主单/分单能不能删，要看提单状态** 提单处于 `签出审核中`、`已签出`、`已扣单` 时，**禁止删除**对应的主单或分单（海运出口、海出分单、件杂货、件杂货分单同一规则），提示「提单处于XX状态,禁止删除」。删主单时会连该主单下**所有分单的提单**一起校验。允许删除时，提单及其历史、签入扫描件、超期证明附件、签出审核任务（`TaskBase`/`TaskItem`）、主子工作流实例（`WorkFlowInstance`/`WorkFlowInstanceItem`）全部连带清理。

> [!IMPORTANT] **卡点 6：签出可以把签单方式改成正本，且会回填** 签出时填的签单方式没有限制，允许从电放改成正本。签出后按 **主单提单→回填主单；分单提单→同时回填该分单和它所属的主单** 写回去。件杂货同理：件杂货主单提单回填件杂货，件杂货分单提单同时回填该件杂货分单和所属件杂货。回填之后会触发签单方式变更的状态纠正（第 3.2 节），所以分单签出有可能把主单提单从 `待签入` 放行到 `已签入`。 **取消签出不回退签单方式**：那个值是对实际签发情况的更正，而且可能已被后续操作改过，盲目写回旧值只会把更新的数据覆盖掉。要改签单方式请直接改主单/分单。

> [!IMPORTANT] **卡点 7：工作流必须先配好才能提交** 提交签出审核前，库里必须有一条 `TaskType = 提单签出`(11) 且 `Enable = true` 的工作流，否则报「未配置或未启用提单签出工作流，无法提交审核」。工作流条件支持三个维度：**委托单位**、**提交人所属组织**、**是否超期**（本批里只要有一张超期就算满足）。「提交人所属组织」配在大组织上时，提交人挂在下属部门也算属于：配「属于青岛分公司」，青岛业务部的人提交会走这条线；反过来配业务部、人挂在分公司则匹配不上。节点审核人支持按用户、按角色配置，**不支持按用户属性**（一批提单可能跨多票业务，没有唯一的业务关联人员可取），配了会报「提单签出工作流不支持用户属性审核」。全部节点都是「直接通过」时，提交后整批直接变 `可签出`，不生成工作流实例。

> [!IMPORTANT] **卡点 8：提单没有新增与删除接口** 提单随主单/分单自动创建、连带删除，所以**不提供手工新增与手工删除接口**，也没有编辑接口。`Admin.BillOfLading.Add` / `.Edit` / `.Delete` 三个权限当前是占位，没有对应接口。 **存量数据不补建**：本次上线前已存在的海运出口与分单不会自动补出提单。

> [!IMPORTANT] **卡点 9：字段级屏蔽未接入** `FrightModule` 新增了 `BillOfLading = 10`，但按需求**没有接字段级屏蔽（PropMask）**：提单相关 DTO 上没有 `[PropMaskModule]`，编辑方法里也没有 `PropMaskInputGuard`。后果是：如果有人在「用户/角色字段级权限」里给提单模块配了屏蔽规则，**规则静默无效**，一个字段都不会被屏蔽。以后要接，输出侧 DTO 特性与输入侧 guard 必须同一次改动里一起加上。本次新增的 `BillOfLadingBreakBulkDto`、`BillOfLadingBreakBulkSeparateDto` 同样没有标 `[PropMaskModule]`。

> [!IMPORTANT] **卡点 10：件杂货的提单没有船公司与集装箱，权限按件杂货模块算**
>
> - **没有船公司**：列表按 `CarrierId` 筛选时件杂货提单一律不出现；`CarrierIdEmpty=true` 时件杂货提单全部出现；按船公司分组时全部并进「未填写」组。
> - **没有装运方式、提单类型、集装箱**：出参挂的是 `BreakBulk` 对象，里面不声明这几个字段；业务表那一层的箱型箱量为空数组、合计为空字符串。件杂货分单也没有箱型子表，所以 `BreakBulkSeparate` 里没有箱型箱量。
> - **权限分派**：查看详情、看历史、单张动作（签入、取消签入、取消换签、取消签出、取消扣单）按业务表 `BizType` 分派——件杂货的票按件杂货模块的业务数据权限与表级权限判，其余按海运出口判；票找不到时分别报「件杂货不存在」「海运出口不存在」。批量动作（换签、扣单、提交审核、撤销提交、签出）一批里可以同时有两种票，两边各自算出能编辑的票再合在一起，缺任何一张都报「所选提单中有您没有权限XX的票」。
> - **列表排序路径**：提单实体的导航由 `SeaExport` 改成了 `TransportOrder`，排序要写 `TransportOrder.ETD DESC` 这类路径；旧的 `SeaExport.TransportOrder.ETD` 找不到属性，会报「排序字段无效」。

## 7.4 数据库变更

**新增两张表**（迁移文件由人工生成）：

- `App_BillOfLadings`：`Id`(Guid,PK)、`TenantId`、`SeaExportId`（业务 id，海运出口或件杂货）、`SeaExportSeparateId`(可空)、 `BreakBulkSeparateId`(uniqueidentifier，可空)、`Status`、`PromisePayDate`(可空)、`OverdueRemark`(可空,1024)、以及 `FullAuditedEntity` 的审计与软删列。索引：`(SeaExportId, SeaExportSeparateId)`、`Status`。外键：`SeaExportId` → `App_TransportOrders`、`SeaExportSeparateId` → `App_SeaExportSeparates`、`BreakBulkSeparateId` → `App_BreakBulkSeparates`，均为 `Restrict`。 **2026-09-27 件杂货上线的变更**（迁移由开发生成）：`SeaExportId` 的外键由指向 `App_SeaExports` 改为指向 `App_TransportOrders`，列名与存量值都不变（海运出口与业务表同 id）；新增列 `BreakBulkSeparateId` 及其外键。
- `App_BillOfLadingHistories`：`Id`(Guid,PK)、`TenantId`、`BillOfLadingId`、`ActionType`、 `BeforeStatus`、`AfterStatus`、`ActionDate`(可空)、`Remark`(可空,1024)、`CodeIssueTypeId`(可空)、 `SignOutType`(可空)、以及 `CreationAuditedEntity` 的创建人与创建时间。索引：`(BillOfLadingId, ActionType)`。外键：→ `App_BillOfLadings`（`Cascade`，但软删下不生效，代码里显式删）。

**已有表字段变更**：`App_SeaExportSeparates` 新增 `SettlementId`(uniqueidentifier，结算对象，带索引与指向 `App_Clients` 的外键) 与 `SettlementDate`(datetime2，应结日期)。**存量分单这两列是默认值**，客户超期统计里已显式排除 `SettlementDate` 为默认值的分单，但正式使用前建议先补数据。

**删表**：`App_ClientOverdueHistories` 整张删除。`App_OrderFees.FinalSettlementTime` **保留**——四项超期统计就是靠它现算的。

另外 `App_SeaExports.CodeIssueTypeId` 与 `App_SeaExportSeparates.CodeIssueTypeId` 在**应用层**变成了必填（数据库列仍可空，存量空值不做数据修补）。件杂货的 `App_BreakBulks.CodeIssueTypeId`、`App_BreakBulkSeparates.CodeIssueTypeId` 同样是应用层必填、数据库列可空（新表，没有存量）。
