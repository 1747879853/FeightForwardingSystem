# 1. 背景意图 (Background)

编号规则的「组织匹配」一直是拿**当前登录用户所在的组织**去比对，而且只取了用户组织路径列表里的第一条（默认组织）。

一个用户可以同时挂在多个组织下，例如同时属于「青岛分公司-业务部」和「天津分公司-销售部」，于是出现两类错号：

- 用户默认组织是青岛，且青岛分公司配了规则 —— 该用户在**天津分公司**建的单子也会套用**青岛分公司**的编号规则；
- 用户默认组织是天津 —— 青岛分公司的规则压根匹配不到，只能掉到全局规则，甚至直接报「未配置生成规则」。

编号属于业务数据的一部分，应该跟着**这条数据自己的所属组织 `OrgId`** 走，而不是跟着录入人走。本次把匹配依据从「用户组织」改成「业务组织」。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 入参新增业务组织

`src/CsprojBuilder.Application/App/GenerateNum/Dto/GenerateNumDto.cs`

`GetGenerateTextDto` 新增 `OrgId`（`long?`）：业务数据自身的所属组织id。

## 2.2 匹配依据改为业务组织链

`src/CsprojBuilder.Application/CsprojBuilderAppServiceBase.cs`

- `GenerateNumAsync` 不再读 `GetUserOrganizationPathsAsync(当前用户).FirstOrDefault()`，改为调用新增的私有方法 `ResolveGenerateNumOrgChainAsync(input.OrgId)` 得到组织链。
- 组织链取 `input.OrgId` 所在节点的 `Parents`（组织树缓存里已是「顶→底且含本组织」），反转成**本组织→顶级**，即「业务部 → 青岛分公司 → 山东 → 中国」，仍然是从近到远、最先命中的规则生效。
- `input.OrgId` 为空时退化为按当前用户的**全部**组织路径匹配（不再只看默认组织那一条）：层级越深的组织越优先，同层级默认组织优先。

# 3. 避坑指南 (Pitfalls)

- **不要再用当前用户的组织匹配编号规则**。除数据权限过滤外，凡是「这条数据归谁管」的判断都应取数据自身的 `OrgId`；用户可以同时属于多个组织，用户组织只能表达「他能建哪些组织的单」，不能表达「这单属于哪个组织」。
- 新增调用点时务必传 `OrgId`。不传不会报错，会静默退回按用户组织匹配，多组织用户又会出现同样的错号。
- 修复后行为会变：原先靠「默认组织恰好匹配上」拿到分公司编号的单子，如果该单的 `OrgId` 落在别的分公司，将改用该分公司的规则；若那个分公司没配规则，就会落到全局规则，都没有则抛「未配置生成规则」。**上线前需确认各分公司规则配置齐全**。
- 组织与适用用户在新增/编辑规则时是互斥校验的（"组织和适用用户不能同时设置"），所以用户级规则不带组织，本次不涉及用户级规则的匹配顺序，用户级仍是第一优先级。
- 组织链取自 `GetAllOrganizationTreesAsync()` 缓存，组织树调整由 `OrganizationCacheInvalidator` 失效，无需额外处理。
- 无需数据库迁移。
