# 1. 背景意图 (Background)

`InvoiceIssueAdminAppService.DetailAsync`（发票开出详情）此前只在 `invoiceIssueItems.invoiceApplication` 中返回开票申请的**简易信息**（`InvoiceApplicationSimpleDto` + 轻量费用明细），字段远少于发票开出新建/编辑页所用的「已提交开票申请列表」。

前端在详情页要展示与新建页一致的开票申请卡片（申请人、抬头/客户开票信息、金额汇总、汇率匹配、费用明细含业务与海运出口信息、商品明细）时，只能自己再拼接数据。

本次在详情出参中**额外返回 `invoiceIssueApplications`**，其字段与结构和 `GetSubmittedApplicationListAsync` 完全一致，前端两处页面可复用同一套渲染逻辑。

`InvoiceIssueApplicationDto` 关键内容（详见接口文档第六节）：主表字段 + `creatorUserName`/`applyUserName`/`companyName`/`settlementName`/`currencyCode`/`clientInvoiceInfo`、`totalAppliedAmount`/`totalGoodsAmount`/`appliedAmountRmb`/`invoiceExchangeRate`/`amountMatched`、扁平费用明细 `invoiceApplicationItems`（每条含 `orderFee`，其 `transportOrder.seaExport` 含港口与船公司对象）、商品明细 `invoiceApplicationGoodsDtls`。

## 2.3 复用方式（重构）

把 `GetSubmittedApplicationListAsync` 中「实体列表 → DTO 列表」的整段组装逻辑抽成私有方法：

```csharp
private async Task<List<InvoiceIssueApplicationDto>> BuildInvoiceIssueApplicationDtosAsync(List<Entites.InvoiceApplication> datas)
```

- `GetSubmittedApplicationListAsync`：条件过滤 + 数据权限 + 排序后拿到实体列表，交由该方法组装。
- `DetailAsync`：按 `invoiceIssueItems.invoiceApplicationId` 去重后重新查询开票申请（`Include InvoiceApplicationItems → OrderFee → TransportOrder`，以及 `InvoiceApplicationGoodsDtls`），按 `ApplyTime` 倒序，交由同一方法组装。

该方法内部保持原有行为：批量查询用户/组织/币别/发票汇率/客户开票信息/费用代码/客户/海运出口（含港口、船公司）避免 N+1，按当前发票汇率计算 `appliedAmountRmb` 与 `amountMatched`，最后对 `InvoiceIssueApplicationDto` 与 `TransportOrderSimpleDto` 调用 `SetDataPermissionPropsAsync` 填充数据权限属性。

# 3. 避坑指南 (Pitfalls)

- **不按状态过滤**：详情里的申请通常已是 `Invoiced`（已开票），因此详情侧的查询**不加** `Status == Auditing` 条件；已提交列表接口的状态过滤仍在其自身查询里，未下沉到公共方法。
- **两处开票申请数据并存**：`invoiceIssueItems[].invoiceApplication` 是轻量结构（老字段，保持不变，兼容既有前端），`invoiceIssueApplications` 是完整结构（新字段）。同一份申请数据会出现两次，前端按需取用即可。
- **`amountMatched` 取的是当前汇率**：详情页展示的匹配结果随发票汇率变动而变化，与开出时点的结论不一定一致，这是既有设计（同已提交列表）。
- **无关联申请时为 `null`**：`invoiceIssueItems` 为空时不查询，`invoiceIssueApplications` 不赋值（`null`），前端需做空值兼容。
