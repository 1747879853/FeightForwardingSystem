# 1. 背景意图 (Background)

**白话解释：** 原先发票开出强制要求「至少一条开票申请」且「至少一条商品明细」，移除申请时还要求「至少保留一条」。实际业务中存在需要把一张发票开出暂时清空、或本来就没有商品明细的情况。本次放开这些硬性条数限制，只保留一条真正的业务约束：**开票申请的商品明细金额合计与发票开出的商品明细金额合计必须相等**。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 校验口径

放开后各接口的约束如下：

| 接口 | invoiceIssueItems | invoiceIssueGoodsDtls | 说明 |
| :-- | :-- | :-- | :-- |
| `AddAsync` | **仍至少一条** | 可为空 | 见 2.2 |
| `EditAsync` | 可为空 | 可为空 | 清空申请时主表四要素保持原值 |
| `AddApplicationsAsync` | 至少一条（本次新增的申请） | 可为空 | 语义上就是「新增申请」，零条无意义 |
| `RemoveApplicationsAsync` | — | 可为空 | 取消「至少保留一条」，可全部移除 |
| `DeleteAsync` | — | — | 本来就已支持空子表，无需改动 |

金额校验保持不变：两边都为空时合计都是 0，天然相等；只有一边为空而另一边合计不为 0 时，仍会被「金额合计不一致」拦下。

## 2.2 为什么新增接口仍要求至少一条开票申请

`InvoiceIssue` 主表的 `SettlementId`、`InvoiceType`、`CurrencyId`、`ClientInvoiceBankId`、`OrgBankAccountId` 全部取自 `applications.First()`。实体上这五个字段均为非空值类型，且 `SettlementId` / `ClientInvoiceBankId` / `OrgBankAccountId` 都配了 `[ForeignKey]` 导航属性、数据库存在外键约束，填 `Guid.Empty` 会直接写不进去。没有开票申请就没有这些值的来源，因此新增接口保留「请至少选择一个开票申请」。

若将来确实需要「先建空壳再挂申请」，需要在 `InvoiceIssueAddDto` 上补这五个字段由前端传入，或把实体字段改为可空并调整外键，属于另一次改动。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT] **1. 清空开票申请不会清空主表的结算对象等字段。** `EditAsync` / `RemoveApplicationsAsync` 把申请清空后，主表的 `SettlementId`、`InvoiceType`、`CurrencyId`、`ClientInvoiceBankId`、`OrgBankAccountId` 保持删除前的原值。这是刻意的——这些字段非空且带外键，没有申请可供取值。所以「清空后的发票开出」看上去仍然挂着原来的结算对象和银行，不是 bug。

> [!IMPORTANT] **2. 清空申请照样会触发反开票。** 被移除的申请一律回退为「待审核」并清空 `InvoiceNo`，回退前仍会执行 `EnsureNotSettledByInvoiceAsync`：只要有一条申请已被收费结算引用，整个清空操作就会失败。这一条没有因为放开条数限制而放松。

> [!IMPORTANT] **3. 只有一边为空是走不通的。** 「申请非空 + 商品明细为空」只有在这些申请的商品明细金额合计恰好为 0 时才能通过；「申请为空 + 商品明细非空」同理只有合计为 0 才行。前端不要理解成两个列表可以随意独立留空。

> [!IMPORTANT] **4. 金额校验只看 `Amount`。** `NoTaxAmount`（不含税金额）与 `TaxAmount`（税额）不参与校验，代码里一直如此。旧版接口文档写的「三项分别校验」是错的，本次已一并订正。
