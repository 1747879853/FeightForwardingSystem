# 1. 背景意图 (Background)

**白话解释：** 开票申请创建时，按「当时」的发票汇率把费用原币金额折算成人民币写进商品明细。发票汇率会随时间变动，等到真正开票（发票开出）时，开票申请商品明细里的人民币金额往往已经跟「费用原币金额 × 当前汇率」对不上了。

原先 `AddAsync` / `AddApplicationsAsync` 只有一个硬校验：开票申请商品明细金额合计必须等于发票开出商品明细金额合计。汇率变动这件事完全不管，于是开出来的发票用的是过期汇率；前端也只能靠已提交列表的 `amountMatched` 自己判断，没有服务端权威结论。

本次改动分三块，职责切得很干净：

1. **两个新增接口只负责"校验 + 报告"**：按当前汇率把账算一遍，只要有对不上的就什么都不做，直接把结论和涉及的开票申请ID吐给前端。
2. **修正数据单独一个接口**：`SyncApplicationGoodsDtlByExchangeRateAsync`，专门按当前汇率改开票申请商品明细的金额。
3. **修正必须留痕**：改完在商品明细的 `remark` 追加一行「什么时候、谁、以什么方式、把哪些字段从多少改成了多少」。

对不上的开票申请分两种命运：只有一条商品明细的可以自动按汇率改（金额没有分配歧义）；有多条的怎么在多条之间重新分配金额是业务决策，服务端不能替用户猜，只能驳回后让用户自己改。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 汇率校验口径（两个接口完全一致）

逐条开票申请计算，与开票申请 `SubmitAsync` 及已提交列表 `amountMatched` 的口径一致：

```
费用申请金额折算人民币 = ToFinancialRound(sum(InvoiceApplicationItems.AppliedAmount) × 当前发票汇率)
对得上 = (sum(InvoiceApplicationGoodsDtls.Amount) == 费用申请金额折算人民币)
```

对不上的按 `InvoiceApplicationGoodsDtls.Count` 分组：等于 1 进 `SingleGoodsDtlApplicationIds`，否则进 `MultiGoodsDtlApplicationIds`。`Code` 由分组结果推出——有 multi 就是 `2`，只有 single 就是 `1`，两组都空就是 `0`。

**统一行为：`Code` 不为 `0` 时一律不做任何操作**，直接返回校验结果。不新增、不改数据，后续校验（申请状态、四要素一致、金额合计、组织归属）全都不执行。

## 2.2 `AddAsync`：出参 `Guid` → `InvoiceIssueAddResultDto`

| 字段 | 类型 | 说明 |
| :-- | :-- | :-- |
| `Code` | `int` | `0`=正常（已新增）；`1`=汇率已变动但对不上的申请都只有一条商品明细；`2`=存在对不上且商品明细不止一条的申请 |
| `Id` | `Guid?` | 新建的发票开出ID；`Code` 不为 `0` 时为 `null` |
| `SingleGoodsDtlApplicationIds` | `List<Guid>` | 对不上且只有一条商品明细的开票申请ID |
| `MultiGoodsDtlApplicationIds` | `List<Guid>` | 对不上且商品明细不止一条的开票申请ID |

两个ID列表任何情况下都会返回（不会是 `null`），便于前端无条件取值。

## 2.3 `AddApplicationsAsync`：出参 `bool` → `InvoiceIssueExchangeRateCheckDto`

直接返回基类，就是 `Code` + 两组ID，没有额外字段。**`Code=0` 本身就等价于"加挂成功"**，它替代了原来的 `bool` 返回值——校验没过会提前 return、出错会抛异常，能返回 `Code=0` 就说明加挂已经执行完了。这里刻意不加 `Success` 之类的标志位：它恒等于 `Code == 0`，不带任何新信息，只会制造第二个真相来源。

`AddAsync` 之所以要多一个 `Id`，是因为那是前端真正需要的数据（新建的发票开出主键），不是状态位。

与 `AddAsync` 的唯一区别：**只校验本次新增的开票申请**（`input.InvoiceIssueItems` 里的），已关联的申请不参与。它们早已是"已开票"、开票当时已经校验过；若把它们也算进来，任何一次历史汇率变动都会永久堵死「往这张发票开出加挂新申请」这个动作。

## 2.4 新接口 `SyncApplicationGoodsDtlByExchangeRateAsync`

`PUT`，权限 `Admin.InvoiceIssue.Add` 或 `Admin.InvoiceIssue.Edit`（`RequireAllPermissions=false`，因为新增与加挂两条流程都会调它）。

入参只有一个 `InvoiceApplicationIds`（直接把 `SingleGoodsDtlApplicationIds` 传进来）；出参 `UpdatedApplicationIds`（实际改了的）与 `UnchangedApplicationIds`（金额本来就对得上、跳过的）。

修正规则（只动那**唯一一条**商品明细）：

```
Amount      = 费用申请金额折算人民币
NoTaxAmount = ToNoTaxFinancialRound(Amount, TaxRate)   // Amount / (1 + TaxRate/100) 四舍五入2位
TaxAmount   = Amount - NoTaxAmount
```

`Quantity`、`UnitPrice`、`TaxRate`、`CodeInvoiceId` 等其余字段不动。

前置校验：申请必须存在、必须是**待审核（`Auditing`）**状态、商品明细必须**恰好一条**、币别必须有当前有效发票汇率。任一不满足直接报错，不做部分成功。

## 2.5 备注留痕

每次实际修正都会在该条商品明细的 `Remark` **末尾追加一行**（不覆盖原备注）：

```
更新时间：2026-08-04 15:36:12；更新方式：汇率变动（张三提交的更新）；更新字段：金额（更新前 1000.00，更新后 1050.00）、不含税金额（更新前 917.43，更新后 963.30）、税额（更新前 82.57，更新后 86.70）
```

提交人昵称取自用户信息缓存 `GetCachedUserInfoAsync` 的 `NickName`（不额外查库，取不到写 `系统`）。

**`更新字段` 只列本次真正变了的字段**：由 `AppendFieldChange` 逐字段比对 `before == after` 决定是否入列。零税率（`TaxRate=0`）时 `NoTaxAmount` 恒等于 `Amount`、`TaxAmount` 恒为 0，这两项值不变就不会出现在记录里——否则会写出「税额（更新前 0.00，更新后 0.00）」这种把没动过的字段谎报成本次更新的记录。

`Remark` 字段上限 1024 字符，追加后超长时按行丢弃最早的记录，保留最近的。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT] **1. 汇率校验必须排在 `ValidateApplicationsAsync` 之前。** `ValidateApplicationsAsync` 里有「开票申请商品明细金额合计 == 发票开出商品明细金额合计」的硬校验。如果前端按新汇率算了 `invoiceIssueGoodsDtls`，就会先被这条校验抛异常，前端永远拿不到 `code=2` 和需要驳回的申请ID。所以校验、早返回全部放在它前面。

> [!IMPORTANT] **2. 校验查询用 `AsNoTracking()`，修正接口不能用。** `CheckApplicationsExchangeRateAsync` 只读不写，按项目规范加 `AsNoTracking()`；这样也避免它与后面 `ValidateApplicationsAsync` 的跟踪查询互相干扰。反过来 `SyncApplicationGoodsDtlByExchangeRateAsync` 必须走跟踪查询——它靠 EF 变更跟踪只赋值不调 `UpdateAsync`，生成只含 `Amount`/`NoTaxAmount`/`TaxAmount`/`Remark` 四列的 UPDATE。

> [!IMPORTANT] **3. 修正接口只允许改待审核状态的开票申请。** 已开票（`Invoiced`）的申请如果被改了金额，就会与已经开出去的发票脱节，产生对不上账的脏数据。所以状态不是 `Auditing` 一律报错。这也意味着这个接口只服务于「还没开出去」的场景。

> [!IMPORTANT] **4. 不要把 `multiGoodsDtlApplicationIds` 传给修正接口。** 接口会校验商品明细恰好一条，多条直接报错「请驳回后手工调整」。多条明细怎么重新分配金额属于业务决策，服务端不猜。

> [!IMPORTANT] **5. 商品明细为 0 条的开票申请被归入 `multiGoodsDtlApplicationIds`。** 分组用的是「等于 1 / 不等于 1」。0 条且费用折算金额不为 0 时同样无法自动修正（没有行可以改），所以归入只能驳回那组。实际上开票申请 `SubmitAsync` 要求商品明细至少一条，能进入发票开出的都是已提交状态，正常流程下 0 条不会出现。

> [!IMPORTANT] **6. 币别没维护发票汇率会直接报错。** 校验必须要有当前汇率，取不到就抛「未维护xx币种的发票汇率…」。这与开票申请 `SubmitAsync` 的行为一致——能提交的申请当时必然有有效汇率，所以正常流程不会踩到。

> [!IMPORTANT] **7. 修正接口不会动发票开出，也不会自动重试新增。** 它只改开票申请的商品明细。修正完前端必须重新拉取开票申请拿到新金额、重算发票开出商品明细，再调一次 `AddAsync` / `AddApplicationsAsync`。判断成功的依据是 `code=0`（`AddAsync` 另可看 `id` 是否有值），不是 HTTP 200。

> [!IMPORTANT] **8. `UnitPrice` 不参与修正。** 只按汇率改 `Amount`、`NoTaxAmount`、`TaxAmount`。修正后若 `Quantity × UnitPrice ≠ Amount`，属于预期行为（这份不一致原本就存在于开票申请里），不是 bug。
