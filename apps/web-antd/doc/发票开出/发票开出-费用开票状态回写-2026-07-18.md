# 1. 背景意图 (Background)

`OrderFee.InvoiceStatus`（费用开票状态：未开票 / 部分开票 / 已开票）此前只在费用创建时被赋值为 `NotIssued`，**没有任何地方把它推进到 `PartiallyIssued` / `Issued`**，导致该字段长期停留在"未开票"，而它又被业务费用、付费申请、客户对账等多个列表页当作筛选条件（`WhereIf(m => m.InvoiceStatus == ...)`），造成按"已开票 / 部分开票"筛选查不到数据。

经评估：`InvoiceStatus` 是**可筛选、可分页、可建索引的状态列**，应采用**冗余字段回写**而非每次查询实时计算（金额类字段 `InvoicedAmount` 等仍保持实时计算，因其只用于逐行展示、不做筛选主键）。

**回写时机**：当 `InvoiceApplication.Status` 在"已开票(`Invoiced`)"与其它状态之间切换时触发。该状态切换的唯一入口是"发票开出"模块（`InvoiceIssueAdminAppService`）。

| 位置 | 变更 |

| `DeleteAsync` | 删除发票开出、申请回退 `Auditing` 后（反开票），对关联费用回写降级 |

## 回写规则（仅统计 `Status == Invoiced` 的开票申请明细求和）

```
已开票金额 invoiced = Sum(InvoiceApplicationItem.AppliedAmount) WHERE InvoiceApplication.Status == Invoiced，按 OrderFeeId 分组

invoiced == 0               → NotIssued(未开票)
fee.Amount - invoiced == 0  → Issued(已开票，剩余额度为 0)
其它                         → PartiallyIssued(部分开票)
```

> 采用 `fee.Amount - invoiced == 0` 判定"已开票"而非 `invoiced >= fee.Amount`，是为了兼容负数金额（冲红）费用：正负号一致时"剩余为 0"即完全开票，方向无关。

# 3. 避坑指南 (Blockers & Pitfalls)

> [!IMPORTANT] **坑点 1：聚合前必须先落库状态变更** 上游先用 `_invoiceApplicationRepository.UpdateAsync(app)` 把申请状态改成 `Invoiced`/`Auditing`，但此时仍在 EF 变更跟踪的内存中。回写方法内按 `Status == Invoiced` 做 SQL 聚合会读到数据库里的**旧状态**，导致回写错误。因此 `RecalcInvoiceStatusByApplicationsAsync` 内**第一步显式 `await CurrentUnitOfWork.SaveChangesAsync();`**，确保聚合读到最新状态。

> [!IMPORTANT] **坑点 2：回写费用只改单列，禁止 `UpdateAsync`** 费用实体从 `_orderFeeRepository.GetAll()` 查出即被 EF 跟踪。回写只赋值 `fee.InvoiceStatus`，**不调用 `UpdateAsync`**（ABP 的 `Update` 会把整行标记 Modified，生成全列 UPDATE，重写所有金额列）。依赖 UoW 结束时自动 `SaveChanges`，变更跟踪只生成"含改动列"的 UPDATE。

> [!IMPORTANT] **坑点 3：修改/删除的反向降级不可遗漏** 反开票（`EditAsync` 移除申请、`DeleteAsync` 删除发票开出）会把申请退回 `Auditing`，关联费用可能从 `Issued/PartiallyIssued` 降级。`EditAsync` 必须对**新旧申请并集**回写，否则被移除的费用状态会残留。
