# 发票开出 支持空开票申请与空商品明细 — 前端说明

**日期：** 2026-07-31 **接口变更：** 无新增/删除接口，无字段增减，仅放开必填与条数限制。

## 一句话

`invoiceIssueItems`（开票申请明细）和 `invoiceIssueGoodsDtls`（商品明细）都可以传空数组了，唯一还卡着的是**两边金额合计必须相等**。只有新增接口例外，仍要求至少一条开票申请。

## 各接口的新约束

| 接口 | invoiceIssueItems | invoiceIssueGoodsDtls |
| :-- | :-- | :-- |
| `POST AddAsync` | **至少一条**（未放开） | 可传 `[]` |
| `PUT EditAsync` | 可传 `[]` | 可传 `[]` |
| `POST AddApplicationsAsync` | 至少一条（本次新增的申请） | 可传 `[]` |
| `PUT RemoveApplicationsAsync` | — | 可传 `[]`，且**可以把申请全部移除**，不再要求至少保留一条 |
| `DELETE DeleteAsync` | — | — |

## 对接注意

1. **两个列表不能随意独立留空。** 校验的是「开票申请的商品明细金额合计」与「发票开出商品明细金额合计」相等。两者都传空 → 都是 0，通过；只有一边为空 → 除非另一边合计恰好为 0，否则会返回「金额合计不一致：开票申请合计 X，商品明细合计 Y」。

2. **新增接口为什么不能没有开票申请。** 发票开出主表的结算对象、发票类型、币别、客户银行、我司银行都是从第一条开票申请上带过来的，后端没有其他取值来源。所以新增时至少要选一条申请，报错文案是「请至少选择一个开票申请」。

3. **清空申请后，页面上的结算对象/银行等信息不会跟着清空。** 这些字段会保持清空前的原值，属于预期行为，不要当成脏数据处理。

4. **清空申请仍可能被拒。** 被移出的开票申请会回退为「待审核」，若其中任意一条已被收费结算引用，整个请求会失败并提示「开票申请[xxx]已被收费结算引用,不能反开票,请先删除对应的收费结算明细」。

5. **金额校验只看 `amount`。** `noTaxAmount`（不含税金额）和 `taxAmount`（税额）不参与校验，两边合计不等也不会报错。之前接口文档里写的「三项分别校验」是错的，已订正。
