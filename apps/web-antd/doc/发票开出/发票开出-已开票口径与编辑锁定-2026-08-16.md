# 1. 背景意图 (Background)

本次三件事，都是围绕"**费用到底开没开票，以什么为准**"这一个问题：

1. **冲红完成后要解除与开票申请的挂靠**。票被冲掉就等于没开过，那批开票申请必须重新可用，否则关联费用永远卡在"已开票"、再也开不出票。
2. **接口开票的报文发出去之后，发票开出禁止编辑与删除**。注意是"发出去"，不是"开完"——已提交待开票、开票中、签章中一样锁，因为报文已经在税局那边了，本地再改数据就和那张票对不上。
3. **费用的开票状态 `OrderFee.InvoiceStatus` 与已开票金额 `InvoicedAmount`，改为从【发票开出】这条线算**： `InvoiceIssue → InvoiceIssueItem → InvoiceApplication → InvoiceApplicationItem → OrderFee`，而不是看 `InvoiceApplication.Status == Invoiced`。

第 3 条是前两条的地基。原来的口径看的是**状态字段**，而状态是冗余标记、要靠人记得同步；挂靠关系（`InvoiceIssueItem`）才是事实。两者一旦不同步（漏改、并发、异常中断、冲红解绑），按状态算出来的金额就和发票开出对不上。改看挂靠后，发票开出那边加挂 / 移除 / 删除 / 冲红解绑，费用金额天然跟着变，不依赖任何人记得同步状态。

> 本文取代 `发票开出-费用开票状态回写-2026-07-18.md` 里"仅统计 `Status == Invoiced` 的开票申请明细求和"这一条口径，其余（冗余字段回写的定性、单列更新、聚合前先落库）继续有效。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 统一出口：`IOrderFeeInvoicedProvider`

新增 `src\CsprojBuilder.Application\App\InvoiceIssue\OrderFeeInvoicedProvider.cs`。全项目算已开票金额、回写开票状态，只能走它。

| 成员 | 用途 |
| :-- | :-- |
| `GetInvoicedAmountMapAsync(orderFeeIds)` | 取这些费用的已开票金额（费用id → 金额） |
| `GetInvoiceMapAsync(orderFeeIds)` | 取这些费用各自开在了哪些发票上（费用id → 发票列表） |
| `RecalcByApplicationsAsync(applicationIds)` | 按开票申请重算其关联费用的开票状态 |
| `RecalcByOrderFeesAsync(orderFeeIds)` | 按费用重算开票状态（**费用金额变了也要调**） |

核心查询不依赖任何新加的导航属性，用 `IN` 子查询表达"挂在发票开出上"：

```csharp
var linkedApplicationIds = _invoiceIssueItemRepository.GetAll().Select(x => x.InvoiceApplicationId);

await _invoiceApplicationItemRepository.GetAll().AsNoTracking()
    .Where(x => ids.Contains(x.OrderFeeId) && linkedApplicationIds.Contains(x.InvoiceApplicationId))
    .GroupBy(x => x.OrderFeeId)
    .Select(g => new { OrderFeeId = g.Key, Total = g.Sum(x => x.AppliedAmount) })
    .ToDictionaryAsync(x => x.OrderFeeId, x => x.Total);
```

> 用 `IN` 子查询而不是 join：万一同一张开票申请被多条挂靠明细命中，join 会让金额翻倍。

开票状态由 `InvoicedAmountRule.ResolveInvoiceStatus(费用金额, 已开票金额)` 推出：

```
invoiced == 0               → NotIssued(未开票)
fee.Amount - invoiced == 0  → Issued(已开票)
其它                         → PartiallyIssued(部分开票)
```

> 判"已开票"仍用 `fee.Amount - invoiced == 0` 而不是 `invoiced >= fee.Amount`，理由同 2026-07-18 那份：兼容负数金额费用。

## 2.2 为什么放在根命名空间、用属性注入

`IOrderFeeInvoicedProvider` 与 `InvoicedAmountRule` 都放在**根命名空间 `CsprojBuilder`**（与 `CsprojBuilderEnum` 一致），并在 `CsprojBuilderAppServiceBase` 上加了一个属性：

```csharp
public IOrderFeeInvoicedProvider OrderFeeInvoicedProvider { get; set; }
```

十来个模块的列表/详情都要返回费用的已开票金额。放基类上按属性注入（与已有的 `AttachmentAppService` 同一种做法），省掉每个 AppService 改构造函数；更要紧的是让"顺手自己写一段聚合"变成没必要的事，口径不会再散掉。

## 2.3 已开票金额不落冗余列（明确决定）

`InvoicedAmount` **保持实时计算**，不加 `OrderFee` 列。理由：

- 它在全项目**没有任何筛选或排序用途**，23 处全是往 DTO 上赋值做展示；加列买不到任何做不到的能力。
- 实时算的值结构上不可能过期；加列等于把唯一一个"永远对"的数变成"要靠人记得回写才对"。
- 新列对所有历史行都是 0，必须配一次性全量回填才能上线，代价与收益不匹配。

而 `InvoiceStatus` 必须是冗余列：它要进 WHERE（`OrderFeeAdminAppService` 的费用列表筛选、 `StatementAdminAppService` 的对账单按下属费用汇总与筛选），计算值没法分页筛选。

> 什么时候才该给 `InvoicedAmount` 加列：出现"费用列表按已开票金额筛选或排序"这类需求时。那时必须让两个值由 `IOrderFeeInvoicedProvider` 一次写完，绝不能分两处写。

## 2.3.1 费用已开票时返回发票号列表

费用返回已开票金额的同时，一并返回**这条费用开在了哪些发票上**（新出参 `invoices`）。与已开票金额同源、同口径，两者永远对得上；未开票时为空。

```csharp
public class OrderFeeInvoiceSimpleDto
{
    public Guid Id { get; set; }                    // 发票开出id
    public string ApplicationNo { get; set; }       // 发票开出申请单号 恒有值
    public string InvoiceNo { get; set; }           // 发票号 票还没真开出来时为空
    public DateTime InvoiceIssueTime { get; set; }  // 开票时间
    public decimal AppliedAmount { get; set; }      // 本张发票上属于这条费用的金额
}
```

查询走 `费用明细 ⨝ 挂靠明细 ⨝ 发票开出` 的内连接，按开票时间排序：

- 一条费用可以拆到多张发票上，所以是列表；
- **带 `ApplicationNo` 是因为 `InvoiceNo` 可能为空**——费用在挂上发票开出的那一刻就算已开票，但此时接口开票可能还在开票中、手动记录可能还没填号。只给一个空发票号在界面上没法解释，申请单号恒有值，可以用来展示与跳转；
- 冲红完成会解除挂靠，所以**冲掉的票不会出现在这个列表里**，不需要额外过滤。

带这个字段的三个 DTO：`OrderFeeDto`、`InvoiceApplicationFeeDto`、`InvoiceAppSettleItemDto`，即所有原本就返回 `InvoicedAmount` 的地方，23 处赋值一处不落。

## 2.4 冲红完成后解绑（`NuonuoInvoiceManager.DetachApplicationsAsync`）

红票落地、`RedStatus=99` 时：

1. 软删该发票开出的全部 `InvoiceIssueItem`
2. 关联开票申请 `Status = Auditing`、`InvoiceNo = null`
3. 调 `RecalcByApplicationsAsync` 重算费用开票状态

发票开出这条记录本身**保留**（红蓝票号都挂在上面），只是不再挂着申请，且已被红冲状态锁死、不能再改。挂靠明细是软删除，历史上挂过哪些申请在库里查得到。重复回调时这段是幂等的。

## 2.5 编辑锁定：`InvoiceIssueLockRule`

| 锁定原因       | 判定                                                 |
| :------------- | :--------------------------------------------------- |
| 开票报文已发出 | `IssueStatus` 不是 `未开票(0)` 也不是 `开票失败(22)` |
| 冲红中或已冲红 | `InvoiceRedStatusHelper.IsLocked(RedStatus)`         |

命中任一条 → 这条发票开出**只能查询**。加在六个写入口： `EditAsync`、`EditMainAsync`、`AddApplicationsAsync`、`RemoveApplicationsAsync`、`DeleteAsync`、以及重新开票。

判定方法叫 `IsSubmitted` 而不是 `IsIssued`——**已提交待开票(1)、开票中(20)、签章中(21) 也算锁**，名字必须说清楚这一点，否则下一个人会以为只锁"开完的"。

只有"未开票"与"开票失败"可以改：前者还没提交，后者税局那边没有票。 **开票失败故意留开**：订单号按发票开出 Id 派生、固定不变，失败后重开会被服务商按 `E9106 订单号重复` 挡死，唯一的恢复路径就是删掉重建（新 Guid → 新订单号），锁上就没法恢复了。

**手动记录方式下 `IssueStatus` 恒为 `0`，这条规则对手工录票的发票开出没有任何影响。**

`DeleteAsync` 原来那段"开票完成/签章失败/作废中禁止删除"已被这条统一规则取代，覆盖范围更大（多挡住了开票中与已作废）。

## 2.7 补上的回填点

`OrderFeeAdminAppService.ApplyOrderFeeTaskResultAsync` 里，**费用申请修改审核通过时会写 `orderFee.Amount`**，而开票状态是拿费用金额与已开票金额比出来的，金额一变就得重算。原来这里没有回填，现在加了 `RecalcByOrderFeesAsync`。

> 提交申请修改时有"已关联开票申请的费用不可申请修改"拦着，正常走不到"金额变了但已开过票"这一步，但那道拦截在开票申请那个模块里，这里不能指望它。

## 2.8 删掉的废弃接口

`OrderFeeAdminAppService.AddAsync` / `EditAsync`（两个方法头上都写着"不用了"）已连同 `IOrderFeeAdminAppService` 里的声明一起删除。`EditAsync` 会直接改 `Amount` 且**没有任何"已关联开票申请"的校验**，是这条链路上唯一一个能造出状态漂移的口子。同 region 下的 `BatchAddAsync` 保留未动。

`OrderFeeAddDto` / `OrderFeeEditDto` 两个 DTO 类仍被别处使用（批量 DTO 的元素类型、序列化"修改前信息"），保留。

# 3. 避坑指南 (Blockers & Pitfalls)

> [!IMPORTANT] **坑点 1：删除发票开出时必须同步软删 `InvoiceIssueItem`** 口径改成看挂靠关系之后，残留的"孤儿"挂靠明细（`IsDeleted=0` 但主表已删）会让费用**一直**被算成已开票。 `DeleteAsync` 里已经显式软删了子表，别改掉。这是 ABP 软删除不级联那个老坑的延伸。

> [!IMPORTANT] **坑点 2：聚合前必须先落库** 上游对 `InvoiceIssueItem` 的增删、对 `OrderFee.Amount` 的修改此时仍在 EF 变更跟踪的内存里，不落库的话聚合会读到库里的旧数据。`OrderFeeInvoicedProvider` 的两个 Recalc 方法内第一步就是 `SaveChangesAsync`。这条与 2026-07-18 那份的坑点 1 是同一回事，只是从"状态没落库"变成了"挂靠关系/金额没落库"。

> [!IMPORTANT] **坑点 3：回写费用只改单列，禁止 `UpdateAsync`** 同 2026-07-18 那份的坑点 2，未变。

> [!IMPORTANT] **坑点 4：不要为了这个口径给 `InvoiceApplication` 加反向导航** 中途试过在 `InvoiceApplication` 上加 `List<InvoiceIssueItem> InvoiceIssueItems` 让判断写成一句 `x.InvoiceApplication.InvoiceIssueItems.Any()`，后来去掉了：实体模型不该为了一个查询口径多长一个导航，而且内存版会因此被迫多 Include 一层、一旦漏 Include 就**静默算成 0**（不报错、只是数字不对）。现在统一走 `IOrderFeeInvoicedProvider` 的 `IN` 子查询，不碰实体模型。

> [!NOTE] **没有一起改的地方（有意为之）**
>
> - `ReceiveSettlementAdminAppService` 里"按开票申请收费结算"的候选列表仍按 `Status == Invoiced` 过滤。那是开票申请自身的生命周期状态，不是费用金额；且冲红解绑时申请已被退回 `Auditing`，两者结论一致。
> - `InvoiceApplicationAdminAppService.DeleteAsync` 的"已开票的申请不能删除"同理，仍看状态。

> [!WARNING] **存量数据**：`OrderFee.InvoiceStatus` 是缓存列，口径改了之后历史行不会自动刷新（会出现 `invoicedAmount` 已经准了、`invoiceStatus` 还是旧值）。本次**未做**一次性回填，按需要再补一个全量重算入口（调 `RecalcByOrderFeesAsync` 即可）。

# 4. 状态流转说明 (Status Transitions)

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 费用 未开票 | 新建发票开出并挂上该申请 | 部分开票 / 已开票 | 按挂靠后的已开票金额与费用金额比较得出 |
| 费用 已开票 | 从发票开出移除该申请 / 删除发票开出 | 部分开票 / 未开票 | 挂靠没了，金额自然退回 |
| 费用 已开票 | 该发票开出**冲红完成** | 部分开票 / 未开票 | 解绑挂靠 + 申请退回待审核，这批费用可以重新开票 |
| 费用 任意状态 | 费用申请修改审核通过、金额变了 | 重算 | 2.7 新补的回填点 |
| 发票开出 未开票 | 点"开发票" | 已提交待开票 | 此后**只能查询**，编辑/删除/加挂/移除全部拒绝 |
| 发票开出 开票失败 | — | — | 税局没有票，仍可编辑删除 |
