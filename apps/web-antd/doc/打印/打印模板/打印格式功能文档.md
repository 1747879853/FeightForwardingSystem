# 1. 业务背景说明 (Background)

**白话解释：**

打印格式（`PrintFormat`）是系统中管理 FastReport 报表模板的核心数据。每条打印格式记录保存一份 `.frx` 模板内容（`PrintFormatStr`），并关联到一条打印数据源（`PrintJson`）。

与已弃用的旧版 `PrintTemplate` 不同，新架构将**模板**与**数据源**拆分为两张表：

- `PrintJson`：定义某业务模块的 JSON 数据结构（按 `PrintJsonType` 区分，如海运出口详情、空运出口详情等）。
- `PrintFormat`：在同一数据源下可配置多个打印格式（如不同样式的提单、装箱单等）。

业务打印时，前端或桌面设计器选定打印格式 id，传入业务 JSON 数据及导出格式，后端通过 `PrintAsync` 加载模板、注册数据源并生成 PDF / Excel / Word 文件。

# 2. 功能与操作说明 (Features & Operations)

- **打印格式列表：** 管理端按关键字、数据源类型、数据源 id 筛选打印格式，支持分页；列表不展示模板内容，仅展示名称、关联数据源类型等摘要信息。
- **新增/编辑打印格式：** 填写格式名称、选择关联数据源、粘贴或上传 FastReport 模板字符串（`.frx` XML 内容），可设置排序和备注，并可限定签单方式、船公司、组织、业务类型（`BizType`）与打印文件名。**编辑是全字段覆盖，漏传的可空字段会被清空。**
- **按业务类型区分打印格式：** 同一数据源下的格式可用 `BizType` 打业务标签（海运出口/海运进口/空运出口/件杂货），留空表示不限业务类型（各业务通用）；两个列表按 `bizType` 筛选时会同时返回「该业务专用」与「不限业务类型」的格式。
- **查看详情：** 获取完整模板内容 `PrintFormatStr`，供打印设计器加载编辑。
- **删除打印格式：** 支持批量删除；当前未校验是否被业务模块引用。
- **执行打印：** 传入打印格式 id、业务 JSON 及导出格式（`PrintExportFormat`），后端生成 PDF / Excel / Word 文件并返回文件名；文件临时保存在 `wwwroot/PrintTempFile/`。不传 `format` 时默认导出 PDF。
- **按类型自动取数打印（前端不传 json）：** `GetPrintAsync` 传入打印格式 id、数据源类型 `PrintJsonType` 及对应业务接口的真实入参（详情类用 `DetailInput`，费用列表类用 `OrderFeeListInput`），后端按类型先校验对应业务查询权限（如海运出口详情校验 `Admin.SeaExport.Get`），再调用对应业务接口取数生成 JSON 并打印；当前支持海运出口详情及其分单、海运进口详情、空运出口详情、件杂货详情及其分单、应收/应付费用列表、客户对账详情、付费申请详情，空运进口暂未支持。
- **多库同步打印数据源样本 Json：** `PrintFormat/SyncPrintJsonToMultiDbAsync`（无 Body）遍历 `PrintJsonType`，在服务内 `TryBuildPrintJsonAsync` 各分支自行 `new` 业务入参取数生成 Json，再用 ADO.NET 写入多库 `App_PrintJsons`；调用前请先在代码中填好各类型 id/查询条件；需 `Admin.PrintJson.Edit` 权限。件杂货详情、件杂货分单详情两个分支的示例 id 在代码里留空，未填写时直接跳过，结果里分别返回「跳过：未填写件杂货示例业务 id」「跳过：未填写件杂货分单示例 id」。
- **桌面设计器集成：** `CsprojBuilder.PrintDesign` / `CsprojBuilder.AuPrintDesign` 通过 `IPrintFormatAdminAppService` 读写打印格式，按 `PrintJsonType` 分组展示。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：数据源必须先存在]** 新增或编辑打印格式时，`PrintJsonId` 必须指向已存在的 `PrintJson` 记录。若数据源未初始化，接口返回「关联的打印数据源不存在」。

> [!IMPORTANT] **[卡点 2：旧版 PrintTemplate 已弃用]** 历史对接 `PrintTemplateAdminAppService` 的前端/集成代码需迁移至 `PrintFormatAdminAppService`。主键类型、删除入参、数据结构均有变化。

> [!IMPORTANT] **[卡点 3：列表不返回模板内容]** `GetPagedListAsync` 返回的 `PrintFormatDto` 不含 `PrintFormatStr`，编辑模板需先调 `DetailAsync` 获取完整内容。

> [!IMPORTANT] **[卡点 4：导出格式仅支持 PDF / Excel / Word]** `PrintAsync` 的 `format` 仅接受 `PrintExportFormat` 枚举值 `0`、`1`、`2`，分别对应 PDF、Excel、Word。传入其他值将返回「不支持的导出格式」。

> [!IMPORTANT] **[卡点 5：GetPrintAsync 需具备对应业务查询权限]** `GetPrintAsync` 按 `printJsonType` 调用不同业务接口取数前会校验对应查询权限：海运出口详情/分单详情→`Admin.SeaExport.Get`、海运进口详情→`Admin.SeaImport.Get`、空运出口详情→`Admin.AirExport.Get`、件杂货详情/件杂货分单详情→`Admin.BreakBulk.Get`（件杂货分单没有独立权限点，查看权限挂在件杂货上）、应收/应付费用列表→`Admin.OrderFee.Get`、客户对账详情→`Admin.Statement.Get`、付费申请详情→`Admin.PaymentApplication.Get`。缺少权限将返回「没有 XX 查询权限」（件杂货两种类型都报「没有件杂货查询权限」）。

> [!IMPORTANT] **[卡点 6：GetPrintAsync 按类型使用对应入参]** 详情类（海运出口详情 / 分单详情 / 海运进口详情 / 空运出口详情 / 件杂货详情 / 件杂货分单详情 / 客户对账详情 / 付费申请详情）填 `DetailInput`(`GuidIdDto`)，费用列表类（应收 / 应付）填 `OrderFeeListInput`(`OrderFeeQueryDto`)；未传对应入参返回「请传入 XX 入参」。费用列表的 `PaySide` 由类型决定并被服务端覆盖；分页默认 1/10，需打印全部费用应显式传较大的 `PageSize`。空运进口暂未支持，返回「该数据源类型暂未支持打印」。

> [!IMPORTANT] **[卡点 7：费用打印区分普通/更改单]** 费用打印（应收 / 应付）默认查业务(TransportOrder)下的费用；当 `IsChangeOrderPrint=true` 时改为「更改单打印」：改用 `DetailInput`(`GuidIdDto`) 传更改单id，服务端调用 `ChangeOrderAdmin/DetailAsync` 取该更改单费用并按收/付过滤，需同时具备 `Admin.ChangeOrder.Get` 与 `Admin.OrderFee.Get` 权限。

> [!IMPORTANT] **[卡点 12：费用打印顺序固定 sortId 升序]** `GetOrderFeesForPrintAsync` 普通打印把 `OrderFeeListInput.Sorting` 覆盖成 `SortId ASC, CreationTime ASC` 再调 `GetPagedListAsync`；更改单打印在按收/付过滤后再 `OrderBy(SortId).ThenBy(CreationTime)`。前端给费用打印传 `sorting` 无效。业务费用分页列表本身仍走入参 `sorting`（基类默认 `CreationTime DESC`），不要把两套口径混在一起。

> [!IMPORTANT] **[卡点 8：多库同步前需配置连接串并改好代码内入参]** `SyncPrintJsonToMultiDbAsync` 无 Body；依赖 `PrintJsonDbManager.ConnectionStrings`，业务 id/查询条件在 `TryBuildPrintJsonAsync` 各分支内自行填写。某库无对应 `PrintJsonType` 时会新建，已存在则局部更新 `Json`。件杂货详情、件杂货分单详情两个分支的示例 id（`breakBulkId` / `breakBulkSeparateId`）在代码里是 `null`，不填就跳过这两个类型；需要生成样本 Json 时在对应分支填真实 id。填了不存在的 id 会让详情接口抛错，整次同步中断。

> [!IMPORTANT] **[卡点 9：EditAsync 是全字段覆盖，漏传即清空]** `EditAsync` 会把 `codeIssueTypeId`、`carrierId`、`orgId`、`bizType`、`fileName` 全部按入参赋值，漏传的一律写成 `null`。只改模板内容时也必须先取 `DetailAsync` 的全量字段再整体提交。两个桌面设计器此前就因为漏传而在保存模板/重命名时清空这些列，已于 2026-08-22 修复；新接入方同样要传全。`PrintFormatFieldsEditDto`（桌面设计器部分字段保存）也是覆盖式。

> [!IMPORTANT] **[卡点 10：bizType 的 0 是海运出口，不是「未选择」]** `BizType.SeaExport = 0`，判空必须比 `null`。WPF 设计器的下拉因此不能复用 `OptionModel`（其「未选择」占位 `Id = 0` 会与海运出口撞车），已另建 `BizTypeOptionModel` 并按 `SelectedItem` 取值。前端同理，不要用假值判断。

> [!IMPORTANT] **[卡点 11：管理端列表的 bizType 也是「相等或为空」]** 同一个 `PrintFormatQueryDto` 里两种口径并存：`codeIssueTypeId`/`carrierId`/`orgId` 在管理端是精确相等、业务端才是相等或为空；而 `bizType` **两端都是相等或为空**。原因是打印选格式时通用模板必须一起出现，否则只配了通用模板的业务一个格式都选不到。因此管理界面无法「只看某业务专用的格式」。
