# 背景意图

付费申请需要打印付款申请单（给财务/领导签字、给供应商发付款通知），但打印模块的数据源类型 `PrintJsonType` 里没有付费申请，设计器的模块列表看不到它，`GetPrintAsync` 传进来也只会报「不支持的数据源类型」。

本次按已有的「客户对账详情」（`StatementDetail`）这条线，把付费申请完整接进打印模块。模块当前形态见《打印格式功能文档.md》与《打印模板接口文档.md》，本文只记这次相对上一版改了什么。

# 核心逻辑变更

## 1. 两个枚举各加一个值

`CsprojBuilder.Core/CsprojBuilderEnum.cs`：

| 枚举 | 新增值 | 说明 |
| :-- | :-- | :-- |
| `PrintJsonType` | `PaymentApplicationDetail = 12000`，`[Description("付费申请详情")]` | 沿用「一个模块占一个千位段」的编号习惯，客户对账是 11000-12000，付费申请接 12000-13000 |
| `PrintJsonFileNameType` | `申请单号 = 6`，`[Description("[申请单号]")]` | 打印文件名占位符。`结算对象全称`（=3）直接复用，只把它的注释从「支持：应收、应付」改成「支持：应收、应付、付费申请」 |

枚举值一加，两个桌面设计器的模块列表就会自动多出「付费申请详情」卡片—— `ServiceImplementations.GetModuleGroupsAsync` 是 `Enum.GetValues(typeof(PrintJsonType))` 动态遍历 + `GetDescription()` 取名，不存在手写的模块清单，**这两个文件一行都不用改**。

## 2. 接线点清单（共 8 处）

| # | 文件 | 改了什么 |
| :-- | :-- | :-- |
| 1 | `Core/Print/PrintFileNameHelper.cs` | 加 `case PaymentApplicationDetail` → 返回 `申请单号` + `结算对象全称`；类注释补一行 |
| 2 | `Application/App/Print/PrintDataSourceHelper.cs` | 加 `case`：反序列化 `PaymentApplicationDto` → `RegisterData(list, "付费申请", 4)` → `Enabled = true` → `ApplyChineseAliases` |
| 3 | `CsprojBuilder.PrintDesign/Windows/FastReportEditorWindow.xaml.cs` | 同上，WPF 设计器自己的那份 switch |
| 4 | `CsprojBuilder.AuPrintDesign/Views/FastReportEditorWindow.axaml.cs` | 同上，Avalonia 设计器自己的那份 switch |
| 5 | `Application/App/Print/PrintFormatAdminAppService.cs` | 注入 `IPaymentApplicationAdminAppService`；`BuildPrintJsonAsync` 加 `case`：校验 `DetailInput` → 校验 `Admin.PaymentApplication.Get` → 置 `IsPrint = true` → 调 `DetailAsync` → 装配两个文件名占位符 → `PropMaskJsonSerializer.Serialize` |
| 6 | `Application/App/Print/PrintFormatAppService.cs` | 注入同一个服务；`TryBuildPrintJsonAsync` 加 `case`，用于多库同步样本 json（付费申请 id 写死在分支里，同其它类型） |
| 7 | `Application/App/Print/Dto/PrintFormatDto.cs` | `GetPrintDto.DetailInput` 的注释补 `PaymentApplicationDetail` 与 `PaymentApplicationAdmin/DetailAsync` |
| 8 | `PaymentApplication/Dto/PaymentApplicationDto.cs` + `Currency/Dto/CurrencyDto.cs` | 补 `[Description]`，见下一节 |

FastReport 数据源名统一为 **`付费申请`**，三处 `RegisterData` 必须写成同一个字符串，否则模板在设计器里能取到值、服务端打印时取不到。

## 3. 给 `PaymentApplicationDto` 补 `[Description]`

设计器和服务端打印的中文字段名，全部来自 DTO 属性上的 `[Description]`—— `ApplyChineseAliases` 会先 `CollectDescriptions` 扫一遍类型树，**`descMap.Count == 0` 就直接 return**。 `PaymentApplicationDto` 原来一个 `[Description]` 都没有，不补的话数据源虽然注册成功，但字段列表全是 `ApplicationNo`、`TotalPayPrice` 这种英文属性名。

本次补了这几个类（都是付费申请自己的 DTO，或只被付费申请/付费结算用的 DTO）：

| 类 | 位置 |
| :-- | :-- |
| `PaymentApplicationDto` | 主体字段 + 额外字段 + 任务字段 |
| `PayAppFeeAndTransportOrder` | 费用按业务分组 |
| `PaymentApplicationItemDto` | 申请明细 |
| `PaymentApplicationBankDto` | 申请银行 |
| `PaymentSettlementForApplicationSimpleDto` | 关联的付费结算 |
| `CurrencyGroupDto`（`Currency/Dto/CurrencyDto.cs`） | 币别分组合计 |

**id 类字段一律不标**（`SettlementId`、`CurrencyId`、`TenantId`、`AuditUserId`、`OrderFeeId` 等）。这不是偷懒：`CollectDescriptions` 里有一句「无 Description 的属性不进入子树」，标不标同时决定了「这个字段要不要出现在设计器字段列表」和「要不要往下递归它的子对象」，id 出现在打印模板上没有意义。

已经标好的共用 DTO 不动：`ClientSimpleDtoForOrder`、`CurrencySimpleDto`、`OrderFeeDto`、`TransportOrderSimpleDto` 本来就带 `[Description]`（费用打印、对账打印在用）。 `AttachmentItemDto` / `ClientInvoiceBankDto` 这类共用叶子 DTO 也不动——对账单打印同样只在父属性上标，叶子内部不铺开，保持一致。

# 避坑指南

> [!IMPORTANT] **[坑 1：`RegisterDataSource` 有三份，不是一份]** 服务端 `PrintDataSourceHelper.RegisterDataSource`、WPF `FastReportEditorWindow.RegisterDataSource`、Avalonia `FastReportEditorWindow.RegisterDataSource` 是三段**各自维护、内容几乎一样**的 switch，没有抽公共方法。只改服务端的表现是：设计器里能正常拖字段、存下来的模板一打印就 CS0103；只改设计器的表现正好相反。以后再加数据源类型，先把这三处都找出来再动手。

> [!IMPORTANT] **[坑 2：不补 `[Description]` 不会报错，只会全英文]** `ApplyChineseAliases` 在 `descMap.Count == 0` 时静默 return，不抛异常也不打日志。新接一个数据源如果发现设计器里字段全是英文属性名，第一反应应该是去看那个 DTO 有没有 `[Description]`，而不是怀疑数据源没注册。

> [!IMPORTANT] **[坑 3：`RegisterData` 的嵌套层数是 4]** 三处都是 `RegisterData(list, "付费申请", 4)`。付费申请的结构比对账单深（`PayAppFeeBySeaExportGroup` → `PaymentApplicationItems` → `OrderFee` → 各种 SimpleDto 已经吃满 4 层），再深的字段 FastReport 不会注册出来。真需要更深的字段，要么调大这个数字（三处一起调），要么在取数时把值提到浅层。

> [!IMPORTANT] **[坑 4：`TryBuildPrintJsonAsync` 里的 id 是写死的，异常会中断整个多库同步]** `SyncPrintJsonToMultiDbAsync` 的 `foreach` 没有逐类型 try/catch，任何一个分支抛异常（比如写死的 id 在当前库不存在， `DetailAsync` 抛「付费申请不存在」）都会让**所有类型**的同步一起失败。跑同步之前先确认各分支的 id 在目标库里真实存在。

> [!IMPORTANT] **[坑 5：付费申请详情目前不认 `IsPrint`]** `PrintFormatAdminAppService` 里照客户对账的写法置了 `input.DetailInput.IsPrint = true`，但 `PaymentApplicationAdminAppService.DetailAsync` 当前**没有读这个字段**，所以它现在只是个占位。对照客户对账：`StatementAdmin/DetailAsync` 的 `IsPrint` 会额外生成「按币别+费用代码分组的平铺行」和「所属公司打印信息」。将来付费申请也需要打印专用的平铺结构或公司抬头信息时，在 `DetailAsync` 里按 `IsPrint == true` 补即可，打印侧不用再改。
