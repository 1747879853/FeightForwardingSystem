> [!IMPORTANT] **本文是待实施的改造方案，代码尚未落地。** **费用审核（`OrderFee`）已经是目标形态，不在改造范围内**，本文把它当作参照样板，见第 3 章。需要改造的是**提成单、付费申请、业务联系单**三个模块。

# 1. 背景与目标

## 1.1 平台现在有两种任务模型

通用工作流由 `TaskItem`（审核任务）+ `WorkFlowInstance`（工作流实例）+ `WorkFlowInstanceItem`（逐级审核明细）三张表承载。各模块接入时分成了两派，`TaskItem` 实体上的注释把这个分歧写死了：

> 费用的任务需要每次都新建一条 因为修改历史要每次保存 可能1-2-3 其余的直接共用一条即可 上一轮的审核流程不保留 260828定的

| 模型 | 采用模块 | 行为 |
| :-- | :-- | :-- |
| **每轮新建**（目标形态） | 费用审核 | 每次提交插一条新 `TaskItem`，旧任务与已审完的实例永久保留 |
| **复用一条** | 提成单、付费申请、业务联系单 | 驳回后重新提交复用原 `TaskItem`，**删除旧实例与明细**后重建路径 |

`WorkFlowInstance` 实体上的注释描述的是后一种：「一条的审核只保留一个 驳回再提交就删了新建」。

## 1.2 复用模型带来的问题

一旦驳回后重新提交，**上一轮的审批过程完全查不到**：

- 上一轮谁驳的、什么意见；
- 多级审批中前面几级由谁通过的、什么时候通过的；
- 更早几轮的任何信息。

`WorkFlowInstance` 与 `WorkFlowInstanceItem` 都是 `FullAuditedEntity`，数据物理上还留在库里，但被 ABP 的软删除全局过滤器挡住，应用层查不到，等于没有。

## 1.3 目标

把三个模块统一到**每轮新建**模型：每次提交都新建一条 `TaskItem`，旧任务与旧工作流实例原样保留，并通过接口把多轮审批痕迹展示出来。

# 2. 各模块现状对照

| 模块 | 任务模型 | 取当前任务的方式 | 是否需要改造 |
| :-- | :-- | :-- | :-: |
| 费用审核 `OrderFee` | 每轮新建 | `GroupBy(EntityId)` + 按 `CreationTime` 倒序取第一条 | **否** |
| 提成单 `CommissionOrder` | 复用一条 | 按 `EntityId` 直接 `FirstOrDefault`，不排序 | 是 |
| 付费申请 `PaymentApplication` | 复用一条 | 按 `EntityId` 直接 `FirstOrDefault`，不排序 | 是 |
| 业务联系单 `PreOrder` | 复用一条 | 按 `EntityId` 直接 `FirstOrDefault`，不排序 | 是 |

「不排序」在复用模型下是对的（本来就只有一条），改造后会变成**随机取到历史轮次的任务**，这是本次改造最危险的地方。

# 3. 费用审核：已经支持，不需要改

费用侧早就是目标形态，改造时对着它抄即可。

**任务每轮新建。** `SubmitOrderFeeAsync` 里 `TaskBase` 按「业务 + 更改单 + 任务类型」只建一次，之后一直复用；但每次提交都按本次提交的费用逐条 `new TaskItem`（`Id = Guid.NewGuid()`），旧任务不删。申请修改、申请删除同理，各自建自己的 `TaskItem`。

**已审完的工作流实例永久保留。** `RebuildOrderFeeWorkFlowAsync` 的方法注释原文：

> 有任何差异时 主工作流与所有在审子工作流一并删除重建并退回第1级 **已审核完毕(通过/驳回)的子工作流永远保留** 只把 `ParentInstanceId` 改挂到当前主工作流上

**取当前任务的地方全部做了去重。** 四处 live 查询（费用列表展示、费用审核、费用撤回、费用审核后驳回）都是 `GroupBy(EntityId).OrderByDescending(CreationTime).First()`，注释里反复强调「Id 是 Guid 不能当创建顺序用」。

**待我审核列表天然支持历史。** `BuildMyOrderFeeTaskBaseIdQuery` 从 `WorkFlowInstanceItem` 反查，返回的是 `TaskBaseId`（主任务id），列表按「业务 + 更改单」一行，多轮命中会被分组吃掉；而且它本来就提供「待我审核 / 我已审核」筛选，看得到历史是设计意图。

费用之所以一开始就这么做，是因为申请修改任务上要存 `Info`（本次要改成什么）和 `OriginalInfo`（改之前是什么），驳回时靠 `OriginalInfo` 逐字段回滚。复用一条记录会把上一次的快照覆盖掉，回滚就没依据了——**它是被业务需求逼出来的，不是刻意设计成留痕**，但结果正好就是我们现在要的形态。

# 4. 提成单 `CommissionOrder` 改造点

## 4.1 `SubmitToWorkFlowAsync`：复用改为每轮新建

当前的「复用分支」整段去掉，只保留状态校验。

**现在**：按 `EntityId` 查旧任务 → 查到就校验是驳回态 → 删旧实例明细 → 删旧实例 → 重置任务的状态/审核人/审核时间/意见 → 建新实例 → `return`；查不到才 `new TaskItem`。

**改后**：按 `EntityId` 查**最新**旧任务 → 查到就**只校验是驳回态**（防止审核中重复提交），什么都不删不改 → 统一往下走 `new TaskItem` + 建实例 + `InsertAsync`。

旧实例不需要手动置终态：基类 `AuditWorkFlowInstanceAsync` 驳回时会把 `WorkFlowInstance.Status` 置为 `Reject`，全部层级走完通过时置为 `Pass`。历史实例天然不是 `Active`，这是 4.3 防重的基础，别破坏它。

## 4.2 四处「取任务」改为取最新

| 位置 | 当前写法 |
| :-- | :-- |
| `UnSubmitAsync` 撤销提交 | `FirstOrDefaultAsync(TaskType == 提成单 && EntityId == 单id)` |
| `AuditAsync` 审核 | 同上 |
| `RejectAsync` 审核后驳回 | 同上 |
| `LoadTaskItemsAsync` 批量审核与批量驳回共用 | `GroupBy(EntityId).ToDictionary(g => g.Key, g => g.First())` |

统一改成按 `CreationTime` 倒序取第一条。`UnSubmitAsync` 额外注意：它现在删任务和实例，**改后只能删最新那一条**，早先几轮必须留着。

## 4.3 待我审核列表会出现重复行

`CommissionOrderTaskListAsync` 从 `WorkFlowInstanceItem` 按 `UserId = 当前登录人` 反查。历史保留后同一个审核人在多轮实例里都存在，同一张提成单会列出多行。反查处加：

```csharp
.Where(x => x.WorkFlowInstance.Status == WorkFlowInstanceStatus.Active)
```

主表查询再补 `TaskStatus == TaskStatus.Auditing` 做双保险。

## 4.4 不需要改的

`DeleteAsync` 已经是按 `EntityId` 查**全部**任务 id、删全部实例明细、实例、任务，天然支持多条。`SubmitAsync` 里清空单据上 `AuditUserId` / `AuditTime` / `AuditRemark` 的逻辑仍然成立——那三个字段代表「当前轮结论」，历史去任务表看，职责不冲突。

提成单模块内所有对 `WorkFlowInstance` 的查询都走 `TaskItemId`，**没有**按 `EntityId` 查实例的地方，这点已全文核实，是三个模块里最干净的。

## 4.5 配套收益：详情返回审批历史

新增 `CommissionOrderAuditHistoryDto`（轮次序号、提交人、提交时间、本轮结论、终审人、终审时间、意见，以及该轮实例的逐级明细），`GetSalesDetailAsync` 与 `GetOperationDetailAsync` 各加一个字段，按 `TaskItem.CreationTime` 升序返回全部轮次。

# 5. 付费申请 `PaymentApplication` 改造点

## 5.1 重新提交改为每轮新建

`SubmitAsync` 的创建任务段：现在查到旧任务就把 `TaskStatus` 改回待审核、删旧实例后重建；改成只校验驳回态，然后新建 `TaskItem`。查旧任务那次也要取最新。

## 5.2 撤回只能撤最新那条

撤回逻辑按 `EntityId` 取任务后直接 `DeleteAsync(task)`。改成取最新，且只删最新那一条及其实例。

## 5.3 三处列表与详情的取数口径必须改（本模块特有的坑）

列表、另一个列表、详情三处都是这么取任务的：

```csharp
var taskItem = taskItems.Where(t => t.EntityId == item.Id).OrderByDescending(t => t.AuditTime).FirstOrDefault();
```

排序键是 **`AuditTime`**。当前轮刚提交时 `AuditTime` 为 `null`，降序排列会把它排到**最后**，于是取到的是历史上最近一次**审完**的任务——显示出来的审核人和审核时间全是上一轮的。

**必须改成按 `CreationTime` 倒序。** 这三处在复用模型下只有一条数据，怎么排都对，所以现在看不出问题；一旦保留历史立刻暴露。

## 5.4 按 `EntityId` 查工作流实例的地方会中招

审核列表里有一处：

```csharp
var workFlowInstance = workFlowInstances.FirstOrDefault(x => x.EntityId == item.EntityId);
```

一张付费申请对应多条实例之后，这里会随机取到历史轮次的实例，`MyStatus` 和逐级明细都会错。**改成按 `TaskItemId == item.Id` 匹配。**

## 5.5 审核列表反查要加 Active 过滤

`PayAppTaskListAsync` 与提成单同理，反查处加 `WorkFlowInstance.Status == Active`，否则出重复行。

## 5.6 不需要改的

审核与审核后驳回两个接口是按 **`input.Ids` 直接取任务id**（`Where(x => input.Ids.Contains(x.Id))`）的，前端从审核列表拿到的就是任务id，不经过 `EntityId` 反查，改造后天然安全。这一点比提成单和业务联系单都好。

## 5.7 需要确认的遗留问题

删除付费申请时执行的是：

```csharp
await _taskItemRepository.DeleteAsync(x => input.Ids.Contains(x.EntityId) && x.TaskStatus == TaskStatus.Rejected && x.TaskType == TaskType.PaymentApplication);
```

只删**驳回态**的任务。复用模型下一张单最多一条任务，删掉就干净了；保留历史后会残留已通过轮次的任务与实例，成为指向已删单据的孤儿数据。建议改成删除该 `EntityId` 下的全部任务及其实例，口径对齐提成单的 `DeleteAsync`。

# 6. 业务联系单 `PreOrder` 改造点

## 6.1 重新提交改为每轮新建

`SubmitAsync` 的创建任务段与付费申请同构：现在复用旧任务、删旧实例重建，改成只校验驳回态后新建。

## 6.2 四处「取任务」改为取最新

提交、撤销提交、审核、审核后驳回四个入口都是 `FirstOrDefaultAsync(x => x.EntityId == input.Id && x.TaskType == TaskType.PreOrder)`，全部改成按 `CreationTime` 倒序取第一条。撤销提交同样只能删最新那一条。

**本模块比付费申请多两处**：审核和审核后驳回也是按 `EntityId` 反查的，付费申请那边走的是任务id。

## 6.3 按 `EntityId` 查工作流实例的地方会中招

`PreOrderTaskListAsync` 里同样有一处 `workFlowInstances.FirstOrDefault(x => x.EntityId == item.EntityId)`，改成按 `TaskItemId == item.Id` 匹配。

## 6.4 审核列表反查要加 Active 过滤，并注意筛选条件

`PreOrderTaskListAsync` 的反查处加 `WorkFlowInstance.Status == Active`。

**本模块特有的额外风险**：这个列表支持按 `AuditUserId`、`AuditTimeStart/End`、`Remark` 筛选，直接打在 `TaskItem` 上。保留历史后这些条件会同时命中历史轮次的任务，「按某人审过筛选」会把早已重新提交过的单子也捞出来。需要决定是限定在当前轮，还是明确对外说明这是跨轮次检索。

## 6.5 不需要改的

`DeleteAsync` 已经是按 `EntityId` 查全部任务 id、删全部实例明细、实例、任务，天然支持多条。

# 7. 三个模块共同的坑

## 7.1 排序键只能用 `CreationTime`，绝不能用 `Id`

`TaskItem.Id` 是 `Guid.NewGuid()` 生成的随机值，没有任何时间含义，`OrderByDescending(x => x.Id)` 等于随机取。费用侧踩过这个坑，四处去重查询的注释都专门写了「Id 是 Guid 不能当创建顺序用」，改造时把同样的注释带上。

付费申请那三处用 `AuditTime` 排序同样不行，理由见 5.3。

## 7.2 `WorkFlowInstance.EntityId` 是冗余字段，不能拿来定位实例

`WorkFlowInstance` 上同时有 `TaskItemId` 和冗余的 `EntityId`。改造后一张单据会有多条实例指向同一个 `EntityId`，**任何按 `EntityId` 查实例并期望唯一的代码都会随机取错**。付费申请和业务联系单各有一处（5.4、6.3），提成单没有。后续开发一律按 `TaskItemId` 查。

## 7.3 `TaskItem` 上没有唯一索引

索引是 `(EntityId, TaskType, TaskStatus)`，普通索引，不挡多条插入，**不需要改表结构**。严格来说可以补一个 `(EntityId, TaskType, CreationTime)` 支撑「取最新」，但这三个模块的数据量级下收益很小，可以不做。

## 7.4 两处实体注释会变成假的

改完之后 1.1 引用的两条注释不再成立，必须同步改掉，否则下一个人照着注释改别的模块会踩坑：

- `TaskItem`：「其余的直接共用一条即可 上一轮的审核流程不保留 260828定的」
- `WorkFlowInstance`：「一条的审核只保留一个 驳回再提交就删了新建」

## 7.5 存量数据不需要迁移

三个模块现有单据每张都只有一条任务，改造后「取最新」作用在只有一条的数据上，结果就是那一条，新旧混用没有问题。

# 8. 实施顺序与风险

## 8.1 顺序

**每个模块内部，「改成每轮新建」与「取任务改成取最新」必须在同一次提交里完成。** 只改前者不改后者，会让审核、撤销、驳回随机操作到历史轮次的任务上——这类问题测试很难覆盖，但线上一定会错。

审核列表的 Active 过滤建议同批加，否则待办列表立刻出现重复行，是用户第一眼就能看到的回归。

详情返回审批历史（4.5）可以拆到后一批，不影响正确性。

## 8.2 模块之间可以分批

三个模块互不依赖，可以一个一个来。建议顺序：**提成单 → 业务联系单 → 付费申请**。

- 提成单最干净（没有按 `EntityId` 查实例的地方），适合先做验证方案；
- 业务联系单次之，多两处按 `EntityId` 反查任务的入口和一个筛选条件要定口径；
- 付费申请放最后，它有三处列表与详情的取数口径要改（5.3），还有一个删除残留的遗留问题要一并决定（5.7）。

## 8.3 回归重点

| 场景               | 验证点                                                 |
| :----------------- | :----------------------------------------------------- |
| 驳回后重新提交     | 生成新任务，旧任务与旧实例仍在；单据状态、审批路径正确 |
| 重新提交后再撤销   | 只删掉最新那一轮，历史轮次不受影响                     |
| 重新提交后审核通过 | 结论落在最新那一轮，不是历史轮次                       |
| 待我审核列表       | 同一张单据只出现一行；已审完的历史轮次不出现           |
| 列表与详情的审核人 | 显示当前轮结论；审核中的单据不显示上一轮的审核人       |
| 删除单据           | 全部轮次的任务、实例、明细都清干净，不留孤儿           |
