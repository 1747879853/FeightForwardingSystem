# 1. 背景意图 (Background)

编辑工作流并保存时，节点审批人（`auditors`）未按本次提交结果做全量替换。前端删除旧审批人、仅提交新审批人后，`GetAsync` 详情仍返回「旧审批人 + 新审批人」叠加的结果（如提交 1 条却返回 3 条）。

根因：`WorkFlowAdminAppService.EditAsync` 在修改已有工作流时采用「先删父表、再整批插入」策略，仅按 `WorkFlowId` 删除了节点（`WorkFlowNode`）和流转线（`WorkFlowTransition`）两张父表，**未显式清理**其子表审批人（`WorkFlowNodeAuditor`）与流转线条件（`WorkFlowTransitionCondition`）。虽然模型层配置了级联删除，但删除与插入在同一次 `SaveChanges` 中执行，且前端会**复用原节点 Id**，导致残留的旧审批人被重新关联到同 Id 节点上，与新插入数据并存。

# 2. 核心逻辑变更 (Core Changes)

`src/CsprojBuilder.Application/App/Workflow/WorkFlowAdminAppService.cs`：

- 新增注入两个子表仓储：`IRepository<WorkFlowNodeAuditor, Guid>`、`IRepository<WorkFlowTransitionCondition, Guid>`。
- `EditAsync` 修改分支中，删除父表前**先查出旧节点/旧流转线 Id 集合，显式全量删除其下的审批人与条件子表**。
- 删除完成后调用 `CurrentUnitOfWork.SaveChangesAsync()` **先提交删除再插入新数据**，避免复用的节点/线 Id 与待删除旧行在同一次 `SaveChanges` 中发生主键冲突或执行顺序问题。

# 3. 避坑指南 (Pitfalls)

- 该「删父留子、再插入」模式只要前端复用主键 Id，就会出现子表残留。`WorkFlowNodeAuditor`、`WorkFlowTransitionCondition` 均需在删父表前显式清理，**不能仅依赖 EF/数据库级联删除**。
- 删除与插入务必用 `SaveChangesAsync()` 分两次提交：复用 Id 时若不先 flush 删除，EF 可能因主键已存在而冲突或顺序错乱。
- 后续若新增工作流相关子表（如新增更深一层子表），需同步在 `EditAsync` 删除阶段补齐清理逻辑。
