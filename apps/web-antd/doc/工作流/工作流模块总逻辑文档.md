# 1. 业务背景说明

工作流模块只管两件事：

1. **定义审批图**（`WorkFlowAdmin`）：给某个任务类型画节点、连线、条件、审核人，并启用。同一任务类型同一时间只能启用一条。
2. **查出某条业务当前挂着的审批实例、以及把待审名额转给别人**（`WorkFlowInstanceAdmin`）：按任务类型 + 业务主键把层级、审核人、意见吐出来；转交改当前这条明细的审核人，并往该条 `Transfers` JSON 追加履历。

真正「提交 / 撤回 / 审核 / 改业务状态」都在各业务模块自己的 AppService 里。客户走 `ClientAdmin`，费用走 `OrderFeeAdmin`，提单走 `BillOfLadingAdmin`，不要在工作流模块里找这些按钮。

工作流从**线**进、从**节点**出。必须有一条源节点为空的开始线；节点可以是「直接通过」（不产生人工层级）。非默认线上的条件决定这单走哪条分支，都匹配不上才走默认线。

# 2. 功能与操作说明

- **列表 / 详情 / 保存 / 删除：** 租户管理员配审批流。保存是整图覆盖：修改时先显式删光旧审批人、旧条件、旧节点、旧连线并 `SaveChanges`，再按本次提交插入。前端会复用节点 id，不先清子表就会把旧审核人重新挂回去。
- **启用：** 启用时检查同 `TaskType` 没有另一条已启用的。未启用的定义可以存多条，提交业务时只认已启用的那条。
- **客户接入（2026-09-21）：** 客户提交审核走 `TaskType = SubmitClient(90)`，申请修改走 `ModifyClient(91)`。两条都要配并启用。连线条件新增客户所属人 / 归属公司 / 客户性质 / 共享类型，提交与申请修改共用。`DeleteClient(92)` 枚举占位，客户模块没有删除审核，配了也不会被调用。
- **转交（2026-09-22）：** `WorkFlowInstanceAdmin/TransferAsync`。只能把**本人待审核**的那条 `WorkFlowInstanceItem` 的 `UserId` 改成对方，同时往本条 `Transfers` 追加 `{ fromUserId, toUserId, creationTime }`。会签本级已经有这个人则拒绝。被转交人必须已有该任务对应的审核权限（用户直接授予或角色授予都算），否则报「被转交人无xxx审核权限 无法转交」。不换层级、不新增明细行。

# 3. 状态流转说明

工作流**定义**本身没有审批状态，只有启用/停用。

工作流**实例**状态：

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| — | 业务侧提交审核，图上存在需要人工审的节点 | 活动(0) | 生成 `WorkFlowInstance` + 按层级展开的 `WorkFlowInstanceItem` |
| — | 业务侧提交审核，所有节点都是「直接通过」 | 不生成实例 | 业务侧当场落终态（客户提交→已通过；客户申请修改→当场把快照落到客户上） |
| 活动(0) | 本级或签任一人通过，或会签全部通过，还有下一级 | 活动(0) | 只推进层级，不改业务单状态 |
| 活动(0) | 最后一级通过 | 通过(1) | 业务侧再把单据改成已通过 |
| 活动(0) | 任意一级驳回 | 拒绝(2) | 业务侧再把单据改成已驳回 |
| 活动(0) | 业务侧撤回 | 实例被删 | 客户是删掉这一轮的任务和实例；历史轮次不动 |
| 活动(0) | 当前待审人转交 | 活动(0) | 该条明细 `UserId` 换成被转交人，状态仍是待审核；本条 `Transfers` 追加一跳；原审核人从待办消失 |

# 4. 核心字段说明

## 4.1 工作流定义 `WorkFlow`

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🔗 联动规则 | 🛡️ 校验限制 |
| :-- | :-- | :-- | :-- | :-- |
| **Name** | 流程名称 | 配置页 | — | 必填，不能空白 |
| **TaskType** | 这条定义给哪种业务用 | 配置页下拉 | 决定能配哪些连线条件、提交时哪条业务来匹配 | 启用时同类型只能有一条启用中；`DeleteOrderFee(2)` 直接禁止保存 |
| **Enable** | 是否启用 | 配置页 | 提交审核只找已启用的 | 同类型不可同时启用多条 |

## 4.2 节点 / 审核人 / 连线 / 条件

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🔗 联动规则 | 🛡️ 校验限制 |
| :-- | :-- | :-- | :-- | :-- |
| **Node.Id** | 节点主键 | 前端生成 | 修改时必须带回原 id | 同一张图里不能重复 |
| **PassMethod** | 直接通过 / 或签 / 会签 | 配置页 | 直接通过不产生实例层级 | 或签/会签必须有审核人 |
| **Auditor** | 用户 / 角色 / 用户属性 三选一 | 配置页 | 用户属性由各业务在**生成实例时**解析成具体用户 | 付费申请配置时就禁用户属性；客户配置时不拦，提交时才报 `客户工作流不支持用户属性审核` |
| **Transition.SrcNodeId** | 线的起点，空=开始线 | 配置页 | 图必须至少有一条开始线 | 指向的节点必须在本次提交的节点集合里 |
| **Transition.IsDefault** | 默认分支 | 配置页 | 匹配条件都失败时走它 | 同一源节点多条出线时必须恰好一条默认；默认线的条件会被清空 |
| **Transition.Priority** | 匹配顺序 | 配置页 | **越大越先匹配** | — |
| **Condition.IsOr** | 或 / 且 | 配置页 | `(所有或 任一成立) 并且 (所有且 全部成立)` | — |
| **Condition.TaskTypeCondition** | 比哪个字段 | 配置页，随 TaskType 变 | 必须属于当前任务类型那一组 | 客户条件配到非客户任务报 `非客户任务不可输入客户条件` |
| **Condition.ShouldBe / Value** | 比较符与被比较值 | 配置页 | 比较符、值类型按条件固定 | 解析失败报 `被比较值输入错误` |

## 4.3 客户连线条件（提交与申请修改共用）

| 枚举 | 取值来源 | 比较符 | 运行时口径 |
| :-- | :-- | :-- | :-- |
| `ClientUserId`(90001) | `Client.UserId` | 等于 / 不等于 | 建档时写入的所属人，不是点提交的人（驳回后可能换人再交） |
| `ClientOrgID`(90002) | `Client.OrgId` 及其**上级**组织 | 属于 / 不属于 | 配大组织覆盖下属部门。必须向上展开，向下展开会让「属于青岛分公司」匹配不到青岛业务部 |
| `ClientClientType`(90003) | `Client.ClientType` | 等于 / 不等于 | **为空时该条件一律不满足** |
| `ClientIsShared`(90004) | `Client.IsShared` | 等于 / 不等于 | `0` 不共享 / `1` 共享本公司 / `2` 共享所有人 |

客户审核人只解析用户 id 和角色 id。客户上的销售/客服/操作是干系人，不是审批语义，没有「本单销售」可取，所以不支持用户属性。

## 4.4 工作流实例明细 `WorkFlowInstanceItem`

| 字段名 | 📖 字段含义说明 | 🔌 数据来源 | 🔗 联动规则 | 🛡️ 校验限制 |
| :-- | :-- | :-- | :-- | :-- |
| **UserId** | **现在**该审的人 | 生成实例时写入；转交时改成对方 | 待我审核、或签/会签、通过后驳回都看这个字段，不看履历 | 转交后原审核人没投过通过票就不能再驳 |
| **TaskStatus** | 还没轮到 / 审核中 / 驳回 / 通过 | 审核推进时改 | 转交不改状态，仍是审核中 | 只有审核中才能转交 |
| **Transfers** | 本条名额的转交履历 JSON 数组 | 转交时追加，只追加不覆盖 | 一级、二级各记在各自明细上，不会混；同一名额 A→B→C 就是多段 | 库里只存 `fromUserId`/`toUserId`/`creationTime`，nickname 查询时再补。从未转过是 `null`，接口吐空数组 |

# 5. 核心业务卡点

> [!IMPORTANT] **[卡点 1：客户要配两条工作流]** `SubmitClient` 和 `ModifyClient` 是两个任务类型，启用互不替代。只配了提交、没配申请修改时，客户点「申请修改」会报「未配置或未启用申请修改客户工作流，无法提交审核」。

> [!IMPORTANT] **[卡点 2：客户条件只能配在客户工作流上]** 四个 `90001~90004` 配到费用/提单等其它类型上，保存时报 `非客户任务不可输入客户条件`。反过来，客户工作流上配费用条件报 `非费用任务不可输入费用条件`。

> [!IMPORTANT] **[卡点 3：用户属性审核人在客户图上能存下来]** `WorkFlowAdmin.EditAsync` 只拦付费申请的用户属性，不拦客户。生成客户工作流实例时才抛 `客户工作流不支持用户属性审核`。配置页应直接不让选，不要把报错留到业务员点提交。

> [!IMPORTANT] **[卡点 4：同类型只能启用一条]** 客户提交、客户申请修改各自算一种类型。同一类型启用第二条会被拦。停用旧的才能启用新的。

> [!IMPORTANT] **[卡点 5：不要用实例通用查询拼客户审批历史]** 客户每轮新建 `TaskItem` + `WorkFlowInstance`。`WorkFlowInstanceAdmin.GetAsync` 按 `TaskType + EntityId` 取第一条且不按时间排序，多轮之后结果不确定。客户历史走 `ClientAdmin.GetAuditDetailAsync`。

> [!IMPORTANT] **[卡点 6：编辑必须先清子表再插入]** 前端复用节点 id。只删节点/连线、不删审批人和条件，旧审核人会挂回同 id 节点，详情出现「删掉的人还在」。删除工作流同样要显式清子表，软删主表不会级联。

> [!IMPORTANT] **[卡点 7：转交只能转自己待审核的名额，且对方要有审核权限]** `WorkFlowInstanceItem.UserId` 必须是当前登录人，且 `TaskStatus` 必须是审核中。还没轮到、已经审过、别人的、流程已结束，一律报「只能转交自己待审核的任务」或「工作流已结束,不可转交」。被转交人按实例上的 `TaskType` 校验审核权限：费用提交/修改/删除看业务费用审核，新建/修改/删除客户看客户审核，付费申请、业务联系单、提成单、提单签出各看自己的审核权限。没有则报「被转交人无xxx审核权限 无法转交」，xxx 是费用、付费申请、业务联系单、客户、提成单、提单之一。履历挂在该条 `Transfers` 上，详情从 `itemList[].transfers` 取；或签/会签判定仍只看当前 `UserId`。
