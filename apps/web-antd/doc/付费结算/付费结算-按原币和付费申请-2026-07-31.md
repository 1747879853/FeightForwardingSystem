# 1. 背景意图 (Background)

付费结算原本的粒度是「一条付费申请」：选择列表一条申请一行，币别塞在行内的 `currencyGroup[]` 数组里；写接口的入参是 `paymentApplicationGroups[].currencyItems[]` 两层结构；详情回显也是按申请分组、内嵌币别数组。

但业务上用户是**按币别**勾选、按币别填结算金额的。旧结构导致：前端要自己把币别数组拍平做展示，提交时再聚合回两层，回显时又要拆开，来回转换容易出错；分页也对不上（一页10条申请可能展开出30行）；追加明细时同一个付费申请只要加过就不能再加它的其他币别。

本次把整条链路的粒度下沉到「**付费申请 + 原币币别**」，选择列表、新建、加明细、删明细、详情五个环节各新增一个同粒度接口。**原有五个接口一行未改，两套并存**，前端按页面需要选用。

新粒度天然对齐底层：`PaymentSettlementItem.OriginalCurrencyId` 本来就是按原币存的，旧的两层结构其实是接口层多包了一层。

## 2.3 与原接口的行为差异

| 差异点 | 原接口 | 新接口 |
| :-- | :-- | :-- |
| 选择列表一行 | 一个付费申请 | 一个「付费申请+原币币别」组合 |
| 选择列表 `totalCount` | 付费申请条数 | 展开后的组合行数 |
| 选择列表 `currencyId>0` | 申请层过滤，返回整条申请 | **行级过滤**，只返回该原币币别的行 |
| 写接口结算行 | 两层 `groups[].currencyItems[]` | 一层 `paymentApplicationCurrencyItems[]` |
| 按总额自动分摊 | 固定币别申请可只传 `settledPrice`，后端调 `DistributeSettledPriceAcrossCurrencies` | **不支持**，每行必须直接给 `settledAmount` |
| 追加/删除判重粒度 | 按付费申请 | 按「付费申请+原币币别」组合 |

`currencyId` 传 `0`（只搜原币申请）的语义两边一致，未变。

## 2.4 实现方式

**选择列表的分组分页**：复用本文件内 `GetPayAppFeeGroupPagedListAsync`「按业务+结算对象分组并分页」的既有套路——先按与原接口完全一致的条件构建 `baseQuery`（状态、有未结算余额、排除已关联结算单、关键字、单号、结算对象、时间区间、申请人、组织 + `DataPermissionFilterAsync`）；用 `ApplySorting(...).Select(m => m.Id)` 取出排序后的付费申请 id 定住分组键顺序；再用**未排序**的 `baseQuery` 做 `SelectMany` 投影出 `(付费申请id, 原币币别id)` 后 `Distinct()`（避免 DISTINCT 与 ORDER BY 冲突）；拼成一维 `groupKeys` 后 `Skip/Take` 切片，最后只物化当页涉及的付费申请与费用。`currencyId > 0` 的行级过滤放在 `Distinct()` 之前下推到 SQL，不会先展开再内存过滤。

**写接口**：四个新方法的校验与事务骨架都是从对应原方法平移的（悲观锁 `LockOrderFeeRowsAsync`、`UpdateRelatedDataAfterAddWithLockedFees`、汇率全量替换、删除时的 `UnSettledAmount` 回加与 `OrderFee.SettledAmount`/`SettlementStatus` 重算、`UpdatePaymentApplicationStatus` 等一字未改），只有结算行的解析部分不同。新增私有方法 `BuildSettlementItemsByCurrencyRows(rows, payApps, rateDict, paymentSettlementId)` 逐行找付费申请、按 `OrderFee.CurrencyId` 过滤该原币的申请明细，再调既有的 `BuildSettlementItemsForCurrency` 做顺序分配；新增和加明细共用它。

**详情的拉平**：`GroupBy(item => new { item.PaymentApplicationId, item.OriginalCurrencyId })`，每组求 `SettledAmount` 之和并乘该结算单汇率得 `SettledPrice`，结果按 `applicationNo` + `originalCurrencyId` 升序。

**行 key**：选择列表行和详情行都补了 `RowKey`（`付费申请id_原币币别id`），因为同一申请多币别时 `id` 是重复的。

# 3. 避坑指南 (Pitfalls)

## 3.1 行标识与分页

- **`id` 会重复**：同一付费申请有几种原币币别就出现几行，选择列表和详情的 `id` 都是那个付费申请的 id。表格行 key 必须用 `rowKey`，否则会丢行或选中串行。
- **同一申请可能被分页切断**：选择列表的 `totalCount` 是展开后的行数，`pageSize=10` 时第10、11行可能属于同一个付费申请却落在两页。要做「按申请合并单元格」的展示必须处理跨页。
- **排序只作用在申请层**：`sorting` 传币别相关字段无效，同一申请内的币别固定按币别id升序。

## 3.2 币别字段别混

- **`currencyId` 有三种含义**：结算单头上的是**结算币别**；付费申请行上的是**申请币别**（原币申请为 null）；`originalCurrencyId` 才是**原币币别**，也是汇率表、结算明细、所有写接口入参用的键。
- **选择列表 `currencyId` 语义与原接口不同**：`>0` 时原接口是申请层过滤（整条申请都返回），新接口是行级过滤（只返回那一个币别的行）。切换接口时前端的筛选逻辑要一起改。
- **原币申请没有 Price 系列字段**：选择列表行的 `rate`、`payPrice`、`receivePrice`、`settleablePriceUpperLimit`、`settleablePriceLowerLimit` 在原币申请（`currencyId` 为 null）下全是 null，只有 Amount / Limit 系列有值。

## 3.3 写接口

- **不支持 `settledPrice` 总额分摊**：固定币别的付费申请也必须逐行给 `settledAmount`。要用自动分摊只能走原来的 `AddAsync` / `AddItemsAsync`。
- **`AddItemsByCurrencyAsync` 的判重放宽了**：同一付费申请的不同原币币别可以分多次加进同一张结算单。前端别再按「这个申请已经加过了」去灰掉整条申请，要按币别行去灰。
- **汇率仍是全量替换**：三个写接口都要求 `paymentSettlementRates` 的币别集合与操作后结算单中所有明细的原币币别集合**完全相等**，多一个少一个都会报「汇率的币别种类必须跟结算明细的币别完全一致」。删到一条明细都不剩时不校验，可以传空数组。
- **两套接口混用要当心**：用原 `AddItemsAsync` 加过整条申请后，再用 `DeleteItemsByCurrencyAsync` 只删其中一个币别是允许的，剩余币别仍在单里；此时若再用原 `DeleteItemsAsync` 传该申请id，会把剩余币别一起删掉。

## 3.4 详情

- **选择列表没有 `paymentSettlements`**：前端如果从原接口切过来，用到这个字段的地方要改走付费申请详情。
- **`rate` 未命中时是 0**：详情行的汇率取自该结算单汇率表，理论上不会缺，但汇率表被改坏时会返回 0，导致 `settledPrice` 为 0，排查金额对不上时先看这里。
