# 背景意图

付费结算的列表与详情此前只返回创建人昵称 `creatorUserName`（取 `CreatorUserId`），前端展示「申请人」一列时无名称可用。本次在列表与详情中补一列 `userName`，取数据所属人 `UserId` 对应用户的 `nickName`。

`UserId` 是 `DataPermissionFullAuditedEntity` 的数据所属人字段，付费结算在 `AddAsync` / `AddByCurrencyAsync` 中写入 `AbpSession.GetUserId()`，即建单人，业务语义上就是「申请人」。

# 核心逻辑变更

## 1. DTO 新增字段

文件：`src/CsprojBuilder.Application/App/PaymentSettlement/Dto/PaymentSettlementDto.cs`

| DTO | 新增字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `PaymentSettlementListDto` | `UserName` | `string` | 结算单申请人昵称（结算单 `UserId` 对应的 `NickName`） |
| `PaymentSettlementDetailDto` | `UserName` | `string` | 同上 |
| `PaymentSettlementDetailByCurrencyDto` | `UserName` | `string` | 同上 |
| `PaymentSettlementPayAppCurrencyDto` | `UserName` | `string` | **该结算行所属付费申请**的申请人昵称（付费申请 `UserId` 对应的 `NickName`） |

四个 DTO 均继承 `DataPermissionFullAuditedEntityDto<Guid>`，`userId` 本身已随基类返回，本次只补名称列。

> 注意两级 `userName` 的取数对象不同：主表上的是**结算单**的申请人，`paymentApplicationCurrencies[]` 行上的是**该行付费申请**的申请人，两者可以不是同一个人。

## 2. 接口填充逻辑

文件：`src/CsprojBuilder.Application/App/PaymentSettlement/PaymentSettlementAdminAppService.cs`

| 接口 | 填充方式 |
| :-- | :-- |
| `GetPagedListAsync` | 复用已加载的 `GetUserInfoMapAsync()` 整表用户字典，`users.TryGetValue(item.UserId, out var ownerUser)` 后取 `NickName` |
| `DetailAsync` | `result.UserName = (await GetCachedUserInfoAsync(settlement.UserId))?.NickName;` |
| `DetailByCurrencyAsync` | 主表同 `DetailAsync`；结算行在「结算行关联数据」区一次性取 `GetUserInfoMapAsync()`，行内 `users.TryGetValue(payApp.UserId, ...)` 取 `NickName` 填 `PaymentApplicationCurrencies[].UserName` |

全部走 `CsprojBuilderAppServiceBase` 的用户整表内存缓存（缓存名 `UserInfoCacheName`，按租户分 key，缓存 `Id / NickName / UserAttribute`），**不新增任何用户表查询**。

# 避坑指南

- 取的是实体的 `UserId`（数据所属人 / 申请人），**不是** `CreatorUserId`。两者在正常建单流程下相同，但数据迁移或后台改所属人后会不一致，不要混用。
- 主表 `userName` 与结算行 `paymentApplicationCurrencies[].userName` 是两个不同来源（结算单所属人 vs 付费申请所属人），前端不要互相顶替。
- 列表接口里已有 `var users = await GetUserInfoMapAsync();`，禁止再单独查一次用户表；详情接口用 `GetCachedUserInfoAsync` 即可，其内部同样命中同一份缓存。结算行在 `Select` 同步 lambda 内无法 `await`，必须在 LINQ 之前把字典取好。
- 历史数据 `UserId` 可能为 0（早期未赋值），此时缓存查不到，`userName` 返回 `null`，前端需容错。
- 用户昵称改名后依赖缓存失效（`UserInfoCacheInvalidator`）刷新，不是实时读库。
