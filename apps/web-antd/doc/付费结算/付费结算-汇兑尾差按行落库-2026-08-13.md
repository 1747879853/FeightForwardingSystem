# 1. 背景意图 (Background)

用户在 ByCurrency 结算行里填的是**结算币别金额**，后端按本行汇率倒算成原币量落库（`PaymentSettlementItem.SettledAmount`，`decimal(18,2)`），详情再用「原币量 × 汇率」把金额算回来。汇率不为 1 时这条往返路径**不是无损的**：

- 汇率 7、录人民币 `100` → 原币 `round(100 / 7) = 14.29` → 折回 `14.29 × 7 = 100.03`
- 该汇率下人民币金额只能落在 `0.07` 的格点上（`14.28 × 7 = 99.96`、`14.29 × 7 = 100.03`），**100 本身不可表示**

用户填 100 保存，再打开详情看到 100.03，会当成算错。根因是「金额是派生值 + 原币量只有两位小数」，只要这个结构不变，差额就必然存在。

本次不改明细口径，把差额单独记一列。**关键决定是记在哪一级**：录入是按「付费申请 + 原币币别」一行一个金额的，所以尾差天然就是**每行一个**，记在明细（`PaymentSettlementItem`）上，随行增删自然跟着走，不需要在主表上做任何增量维护。

> 为什么不能删行时反推尾差：落库丢了信息。满足 `takePrice / 7 ∈ [14.285, 14.295)` 的录入金额（100.00 ~ 100.06 共 7 个值）落库结果都是 `14.29`，删的时候只剩 `14.29` 和 `7`，倒不回当初填的是哪一个 —— 能反推出来就不会有尾差了。所以必须在落库时就把它存下来。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 明细表新增 `PriceDiff`

`src/CsprojBuilder.Core/Entites/PaymentSettlement.cs`

```
[Column(TypeName = "decimal(18,2)")]
public decimal PriceDiff { get; set; }
```

含义：**本行录入的金额 − 该行明细折算取整后的合计**，可正可负。差额记在「付费申请 + 原币币别」这一行的**首条明细**上，同行其余明细恒为 0。非空列，存量行为 0。**本次未生成迁移**，由开发自行生成。

主表不加任何字段。

## 2.2 分配方法逐行结算尾差

`BuildSettlementItemsByCurrencyRows` 原来是直接往总列表 `AddRange`，且全额结算分支用 `continue` 提前跳出。改为每行先收进局部的 `rowItems`，行处理完后统一算尾差再并入总列表：

```
if (rowItems.Count > 0)
    rowItems[0].PriceDiff = ToFinancialRound(row.SettledPrice - ToFinancialRound(rowItems.Sum(i => i.SettledAmount * i.Rate)));
```

分配逻辑本身一行没动，只是把 `continue` 换成 `else` 分支。行内一条可结算明细都没有时（此时上下限均为 0，录入金额只能是 0）不记尾差。

## 2.3 返回的金额全部补回尾差

光存不够，**读的时候必须加回去**，否则前端看到的还是 100.03。

| 接口 | 字段 | 新口径 |
| :-- | :-- | :-- |
| `DetailByCurrencyAsync` | 行 `settledPrice` | 该行折算取整合计 **+ 该行 `PriceDiff`** = 录入该行时填的金额 |
| `DetailByCurrencyAsync` | `totalSettledPrice` | 各行 `settledPrice` 之和（自动含尾差）= 录入合计 |
| `GetPagedListAsync` | `totalSettledPrice` | 按「付费申请+原币币别」逐行 `ToFinancialRound(Σ 原币量 × 汇率)` 再加该行尾差后累加 |
| `GetPagedListAsync` | `currencySumList[].totalSettledPrice` | 该原币下按付费申请逐行取整再加尾差 |
| `PaymentApplicationAdminAppService.GetPagedListAsync` | 固定币别申请的 `settledPrice` / `totalSettledPrice` | 按「结算单+原币币别」逐行取整再加尾差，即各结算单当初录入的金额之和 |

列表原来是一把梭的 `Sum(SettledAmount × Rate)`（不分组、不取整），与详情的逐行取整口径本来就可能差几分，本次一并对齐，两个接口现在返回同一个数。

尾差按「付费申请 + 原币币别」产生，归属唯一的原币、唯一的付费申请、唯一的结算单，所以**各原币汇总相加仍等于整单合计**，付费申请侧的已结算金额也和结算单侧对得上。原币申请汇率恒为 1，折算无损，尾差恒为 0。

## 2.4 不含尾差的地方

费用行的 `thisSettledPrice` / `settledPrice` 是**纯折算值**，不摊尾差。所以行内各费用 `thisSettledPrice` 相加**不等于**行级 `settledPrice`，差额就是本行尾差（最多几分钱）。对账请用行级 `settledPrice`。

# 3. 避坑指南 (Pitfalls)

- **行级 `settledPrice` ≠ 行内各费用 `thisSettledPrice` 之和**，差的是本行尾差，这是设计如此，不是 bug。
- **单条明细仍然自洽**：`settledAmount × rate` 就是那条明细的折算值，尾差不摊到明细，别拿单条明细去对录入金额。
- **尾差记在行的首条明细上**，靠的是「明细永远按行整删」这个前提。两个删除接口都是按付费申请或按付费申请+币别整行删，如果以后加了「删单条明细」的功能，必须同时把尾差迁移到同行剩下的明细上，否则行金额会跳变。
- **存量单据 `PriceDiff` 为 0**，历史单据的行金额仍是纯折算值（还是 100.03），不回填。
- **全额结算的行也可能有 1 分尾差**：上下限 `priceUpper`、`priceLower` 是各自取整后再相加的，与整体一次取整不一定相等。每行尾差上界约 `汇率 × 0.005`（汇率 7 时约 4 分）。
- **原币申请不会有尾差**，汇率恒为 1；出现非 0 尾差说明数据有问题。
