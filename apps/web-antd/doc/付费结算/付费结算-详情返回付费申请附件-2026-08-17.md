# 背景意图

付费结算详情页需要同时查看结算单自身的附件和**来源付费申请**上传的附件（如付款水单、对方账单等），此前要逐个跳付费申请详情才能看到。本次在 `DetailByCurrencyAsync` 上直接返回一份关联付费申请的附件列表。

# 核心逻辑变更

## 1. DTO 新增字段

文件：`src/CsprojBuilder.Application/App/PaymentSettlement/Dto/PaymentSettlementDto.cs`

| DTO | 新增字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `PaymentSettlementDetailByCurrencyDto` | `PaymentApplicationAttachments` | `List<AttachmentItemDto>` | 本结算单关联的所有付费申请的附件，结构与 `Attachments` 完全一致 |

## 2. 接口填充逻辑

文件：`src/CsprojBuilder.Application/App/PaymentSettlement/PaymentSettlementAdminAppService.cs` → `DetailByCurrencyAsync` 的「附件」区

| 数据 | 取数方式 |
| :-- | :-- |
| `Attachments` | `ModuleTypeId = 160011`(PaymentSettlement) + `ItemId = 结算单id`，逻辑不变 |
| `PaymentApplicationAttachments` | `ModuleTypeId = 160005`(PaymentApplication) + `ItemIds = payAppIds`（结算明细里去重后的全部付费申请id），一次批量查出 |

`payAppIds` 复用「结算行关联数据」区已算好的集合，为空时直接返回空列表、不发查询。两份附件的 `CreatorUserName` 合并成一次 `GetCachedUserInfosByIdsAsync` 填充，走用户整表内存缓存。

# 避坑指南

- 返回的是**扁平列表**，不按付费申请分组。每条 `AttachmentItemDto` 自带 `itemId`（= 付费申请ID）和 `moduleTypeId`（= `160005`），前端要分组按 `itemId` 分。
- 排序沿用 `GetAttachmentItemsAsync` 的口径（`IsFirstShow` 降序、`DisplayOrder` 降序），多张付费申请的附件会交叉出现，**不要假设同一申请的附件相邻**。
- 该列表是**只读展示**用。结算单的附件增删仍只针对 `Attachments`（`160011`），编辑接口不会碰付费申请的附件；删除付费结算时也只清理 `160011` 的关联，付费申请附件不受影响。
- 只有 `DetailByCurrencyAsync` 返回该字段。已停用的 `DetailAsync` 未同步改动。
