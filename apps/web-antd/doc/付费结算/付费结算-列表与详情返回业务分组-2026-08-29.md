# 1. 背景意图 (Background)

付费结算的列表和详情原来只能看到结算单号、结算对象、金额、关联的付费申请单号，以及一串扁平的费用（只带主提单号）。看不出这张结算单到底覆盖了哪几票业务，要核对得先点进付费申请再点业务，层层下钻。

本次与付费申请侧对齐（付费申请列表 / 审批任务列表 / 付费申请详情已先后返回该结构），把「按业务分组」直接挂到结算单上。

只给**业务简要**，不给费用明细与金额分组：结算单的金额口径已经由 `totalSettledPrice` / `currencySumList` / `paymentApplications` 表达清楚了，业务分组这里只解决「涉及哪几票业务」这一个问题。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 影响接口

| 接口 | 地址 |
| :-- | :-- |
| 付费结算分页列表 | `GET /api/services/app/PaymentSettlementAdmin/GetPagedListAsync` |
| 付费结算详情 | `GET /api/services/app/PaymentSettlementAdmin/DetailAsync` |

## 2.2 出参新增

| DTO | 字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `PaymentSettlementListDto` | `PayAppFeeBySeaExportGroup` | `List<PayAppFeeAndSeaExportDto>` | 本结算单涉及的业务票，按业务去重 |
| `PaymentSettlementDetailDto` | `PayAppFeeBySeaExportGroup` | `List<PayAppFeeAndSeaExportDto>` | 同上 |

**挂在结算单这一层，不是挂在付费申请下。** 复用付费申请侧已有的 `PayAppFeeAndSeaExportDto`，组内只填 `TransportOrder`：

| 字段                                  | 本次两个接口 |
| :------------------------------------ | :----------- |
| `TransportOrder`                      | 有值         |
| `PaymentApplicationItems`             | `null`       |
| `CurrencyGroup`                       | `null`       |
| `TotalPayPrice` / `TotalReceivePrice` | `null`       |

> 详情的 `PaymentApplications` 是 `PaymentApplicationDto`，该类型自带一个同名的 `PayAppFeeBySeaExportGroup`。**本接口不给它赋值，恒为 `null`**，请只读结算单根上的那个。DTO 注释里已写明这条区分。

## 2.3 业务来源口径

结算明细 `App_PaymentSettlementItems` 上**没有业务 id**，只有 `OrderFeeId`，所以业务是由费用反查出来的：

```
结算明细.OrderFeeId → App_OrderFees.TransportOrderId → App_TransportOrders
```

一张结算单的多条明细常常落在同一票业务上（同一票的多条费用），所以要按业务 id 去重后再返回。

## 2.4 两个接口的取数方式不同

| 接口 | 取业务的方式 | 原因 |
| :-- | :-- | :-- |
| 列表 | 复用已有的 `orderFeeInfos` 查询，投影里补一个 `TransportOrderId`，再按整页去重批量查业务 | 列表本来就要按费用查主提单号，顺路带出业务 id，不额外增加查询 |
| 详情 | 直接从已加载的 `orderFees` 的 `TransportOrder` 导航去重取用，**不查库** | 详情原来查 `orderFees` 时已经 `.Include(x => x.TransportOrder)` |

两个接口都额外查了一次「业务关联人员」以填销售/操作/客服昵称，按业务 id 批量查，一次搞定。

# 3. 避坑指南 (Pitfalls)

- **业务必须去重**。一张结算单的多条明细通常指向同一票业务的不同费用，不去重会出现重复的业务行。列表侧是先对费用 id 去重、映射到业务 id 后再 `Distinct()`；详情侧是对 `TransportOrder` 按 `Id` 分组取首条。
- **不要去 `paymentApplications[].payAppFeeBySeaExportGroup` 取值**。详情的付费申请对象自带这个字段但本接口不填，恒为 `null`；能取到值的只有结算单根上的那个。两处同名，很容易取错层级。
- **列表的业务对象是跨结算单共享的同一个实例**。同一票业务被多张结算单引用时共用一个对象，序列化输出没问题；但以后若要在某张结算单上给 `transportOrder` 挂只属于该单的数据，必须先克隆，否则会串到其它行。
- **没有调用 `SetDataPermissionPropsAsync`**，所以 `transportOrder.companys` / `organizationUnits` 为空。这与付费申请侧的同名字段行为一致。若要展示业务所属公司，需参照 `GetOrderFeeGroupAsync`：先给 DTO 赋 `UserId` 再批量填充。
- 详情侧用的是 `ObjectMapper.Map<List<TransportOrderSimpleDto>>(实体集合)` 而不是 `ProjectTo`，因为本服务没有注入 `IConfigurationProvider`；实体在上一步已经加载好了，这里只是内存映射，不涉及额外查询。列表侧同理，避免为了 `ProjectTo` 去改构造函数。
