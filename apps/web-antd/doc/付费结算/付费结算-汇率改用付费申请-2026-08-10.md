# 1. 背景意图 (Background)

改造前，付费结算需要用户在结算单上逐个原币录一遍汇率，存在 `App_PaymentSettlementRates`（结算单 + 原币，一条一汇率），再快照到 `PaymentSettlementItem.Rate`。这套设计有两个问题：

1. **重复录入且容易和付费申请对不上**。固定币别的付费申请在申请阶段就已经逐条录过「原币 ÷ 申请币别」的汇率（`PaymentApplicationItem.Rate`），结算时再录一遍等于让用户对着同一笔业务填两次汇率，填岔了金额就对不上。
2. **结算单级别的单一汇率表达不了多申请场景**。一张结算单可以挂多张付费申请，同一个原币在不同申请上的汇率完全可能不同，但 `App_PaymentSettlementRates` 每个原币只能存一行。

本次改为：结算单不再录汇率，汇率一律从付费申请取。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 汇率规则

结算币别 `PaymentSettlement.CurrencyId` 仍由用户选择，作为整张结算单的唯一口径，然后按付费申请类型分流：

| 付费申请类型 | 判定 | 结算币别约束 | 汇率来源 |
| :--- | :--- | :--- | :--- |
| 固定币别申请 | `PaymentApplication.CurrencyId` 有值 | 申请币别必须**等于**结算单 `CurrencyId`，否则拒绝 | 逐条取 `PaymentApplicationItem.Rate` |
| 原币申请 | `PaymentApplication.CurrencyId` 为空 | 只能结算 `OrderFee.CurrencyId` **等于**结算单 `CurrencyId` 的费用 | 恒为 `1` |

原币申请的明细本来就没有汇率（`PaymentApplicationItem.Rate` 为 null），所以只能原币对原币结算：结算币别选美元，那这张原币申请里只有美元费用能被选进来，人民币费用不能进。

两类申请可以挂在同一张结算单上，金额口径仍是 `SUM(SettledAmount × Rate)`。

## 2.5 ByCurrency 结算行改收结算币别金额

客户在界面上只会填折算后的金额，不会去算原币量，所以 `PaymentSettlementItemByCurrencyInputDto` 新增 `SettledPrice`（结算币别），原有的 `SettledAmount` **保留但后端不再读取**，仅为兼容旧调用方。`AddByCurrencyAsync` 与 `AddItemsByCurrencyAsync` 都改为按 `SettledPrice` 计算。

关键点是**不能用一个代表汇率去除**。同一原币下每条申请明细的汇率可能不一样，必须逐条用各自的 `PaymentApplicationItem.Rate` 折算。新增私有方法 `ResolveSettledAmountFromPrice`，分配顺序与 `BuildSettlementItemsForCurrency` 完全对齐：

1. 明细按 `OrderFee.CreationTime` 排序，逐条算出有效金额（付取 `UnSettledAmount`、收取相反数）和各自的汇率。
2. 结算币别口径的上下限 = 正/负有效金额分别 `Σ(Effective × Rate)`。先在客户填写的币别上校验 `SettledPrice` 落在区间内——否则超范围的值会被下面的逐条分配悄悄夹到边界值，用户察觉不到。
3. `diffPrice = SettledPrice - (priceUpper + priceLower)`。为 0 时全量结算；大于 0 时正数项全量、差额从负数项按序回吃；小于 0 时负数项全量、差额从正数项按序补足。每吃一条都用**该条自己的汇率**换算：`takeAmount = ToFinancialRound(takePrice / ie.Rate)`。
4. 累加得到原币额（有效金额口径），交给既有的 `BuildSettlementItemsForCurrency` 做原币上下限校验与逐条落库。

## 2.6 付费申请选择列表按结算币别过滤

`src/CsprojBuilder.Application/App/PaymentApplication/`

- `GetPagedListForSettlementAsync`：SQL 层加「固定币别申请要求申请币别相同、原币申请要求存在该原币的费用」的过滤；原币申请的 `CurrencyGroup` 内存层只保留匹配币别那一组。
- `GetPagedListByCurrencyForSettlementAsync`：同口径的申请层过滤下推到 `baseQuery`；`pairQuery` 的投影补 `PayAppCurrencyId`，再按「原币申请只留原币等于结算币别的行」过滤，保证分组键与分页总数正确。
- `PaymentApplicationCurrencyForSettlementDto.Rate` **删除**。该字段取的是「付费申请 + 原币」组内第一条明细的汇率，而付费申请侧并未强制同一原币只能用一个汇率，实际结算时每条明细各用各的，把一个代表值当成整行汇率展示会让用户按它心算的金额对不上。折算金额看 `PayPrice` / `ReceivePrice`（逐条乘各自汇率求和）与 `SettleablePrice*`（沿用组内首条汇率，与结算侧分摊口径一致）即可。

# 3. 避坑指南 (Pitfalls)

- **汇率不可再在结算单上修改**。`EditAsync` 原本是唯一能改汇率的入口，现在汇率完全跟随付费申请。付费申请汇率填错了只能删结算明细、改申请、重新结算，不能在结算单上直接改。
- **`AddItemsAsync` 不再刷新已有明细的汇率快照**。改造前汇率全量替换会把结算单内所有明细的 `Rate` 一起刷一遍，现在每条明细各自保留落库时从付费申请取到的值。这是有意为之：不同付费申请对同一原币可以有不同汇率，统一刷会把别的申请的汇率冲掉。
- **前端选申请必须带 `settlementCurrencyId`**。用户先选结算币别，再调选择列表。不传这个参数接口会返回全量，用户勾了不合规的申请要到保存时才报错。
- **同一申请同一原币的多汇率**。付费申请侧只校验了 `Rate > 0`，并没有强制「同一原币只能有一个汇率」。明细快照按每条 `PaymentApplicationItem.Rate` 各自存（最忠实），而分摊与可结算上下限这类组级计算沿用既有的 `g.First().Rate` 口径，极端情况下两者会有微小差额，属已知可接受偏差。
- **存量数据不受影响**。老结算单的 `PaymentSettlementItem.Rate` 快照仍在，列表和详情金额照常算。但历史上如果存在「固定币别申请的申请币别 ≠ 结算币别」的单据，再往里追加明细会被新校验拦下。
- **`PaymentSettlementCurrencySumDto.Rate`、详情的 `paymentSettlementRates`、选择列表的 `PaymentApplicationCurrencyForSettlementDto.Rate` 都没了**，前端如果在读这些字段需要一起改，直接读折算后的金额字段即可。
- **ByCurrency 写接口的行金额换字段了**。`settledAmount` 虽然还在 DTO 上但后端完全不读，前端必须改成填 `settledPrice`，否则会按 0 结算且不报错。这是本次唯一一个「传旧字段不报错但结果不对」的坑，联调时优先验。
