# 1. 背景意图 (Background)

现场反馈：付费结算选择付费申请列表里，`PYR26080079` 显示「部分结算」，但「未结算费用」是 0.00，选中也只能结 0。

查库确认数据本身没错，是列表过滤口径的问题：

| 单号 | 申请类型 | 原币 | 申请金额 | 未结算 |
| :-- | :-- | :-- | :-- | :-- |
| PYR26080079 | 原币申请（`CurrencyId` 为空） | RMB | 1490.00 | 0.00（4 条费用全部结完） |
| PYR26080079 | 原币申请 | USD | 1280.00 | 1280.00（2 条一分没结） |

两件事叠在一起才看着矛盾：

1. **`status` 是申请级的**。`UpdatePaymentApplicationStatus` 按「全部明细都结完 → 结算完毕(5)，有结过 → 部分结算(4)」算，USD 那两条没结，所以整张申请是 4。这个值在 `ObjectMapper.Map` 时原样落到展开后的每一行上，行级看着就和该行余额对不上。
2. **「还有未结算」只在申请层判过**。`.Where(m => m.PaymentApplicationItems.Any(x => x.UnSettledAmount > 0))` 被 USD 明细满足，而后面按原币展开成行时完全没有再判余额。结算币别是 RMB 时，原币申请只允许原币=结算币别的行，USD 行被正确挡掉，剩下的偏偏是那个已经结完的 RMB 行。

更隐蔽的是申请层的结算币别过滤：`Any(x => x.OrderFee.CurrencyId == settlementCurrencyId)` 里没带余额条件，于是「有未结算」和「有该币别的费用」被**两条不同的费用**分别满足，这张申请就被放进了列表。

# 2. 核心逻辑变更 (Core Changes)

`src/CsprojBuilder.Application/App/PaymentApplication/PaymentApplicationAdminAppService.cs`

## 2.1 GetPagedListByCurrencyForSettlementAsync：展开成行时按行判余额

- `pairQuery` 展开「付费申请 + 原币」组合前先过滤明细：`.Where(i => i.UnSettledAmount > 0)`。该原币已经结完的组合不再成行，`totalCount` 与行数同步收缩。
- 申请层结算币别过滤补上余额条件，原币申请分支改为 `Any(x => x.OrderFee.CurrencyId == settlementCurrencyId && x.UnSettledAmount > 0)`。余额条件必须和币别条件写在**同一个 `Any`** 内，分开写等于两条独立的存在性判断，会被不同费用分别满足。

行内金额口径不变：`groupItems` 仍取该原币下的**全部**明细，`payAmount` / `receiveAmount` 是申请额（不随结算变），`orderFees` 仍带上已结完的费用，前端展开还能看到全貌。

## 2.2 GetPagedListForSettlementAsync：币别分组同口径收紧

- 固定币别申请与原币申请两个分支的 `CurrencyGroup` 都加 `.Where(g => g.Any(i => i.UnSettledAmount > 0))`，整组已结完的币别不再返回。过滤的是**组**而不是组内明细，所以组内金额算法没动。
- `currencyId > 0` 与 `settlementCurrencyId` 两处的原币存在性判断同样补上 `&& x.UnSettledAmount > 0`。这一步是为了让「申请层能不能进来」和「进来后还剩几个组」保持一致——否则申请进了列表但所有组都被过滤掉，会返回一条 `currencyGroup` 为空的幽灵行，而 `totalCount` 是数据库 `CountAsync` 出来的，改不了。

# 3. 避坑指南 (Pitfalls)

- **别用行上的 `status` 判断这一行还剩多少**。`status` 永远是整张付费申请的状态，一张申请展开的多行共用一个值。行余额看 `totalUnSettledAmount`（原币）/ `totalUnSettledPrice`（结算币别），分组口径看 `currencyGroup[].totalUnSettledAmount`。原币 A 结完、原币 B 没结时，B 行显示「部分结算」是正常的。
- **申请层写存在性条件时，余额和币别必须绑在同一个 `Any` 里**。`Any(币别) && Any(有余额)` 与 `Any(币别 && 有余额)` 在多币别申请上结果完全不同，本次 bug 就是踩在这里。以后再加类似过滤（费用类型、业务归属等）同理。
- **列表现在会少行，不是漏数据**。已结完的币别行不再出现；要查历史，走付费申请详情或付费结算详情，那里仍返回全部明细。
- **`payAmount` / `receiveAmount` 没有跟着变小**。它们是申请额，一直包含已结完的费用；「还能结多少」只看未结算与可结算上下限。
- **`GetPagedListForSettlementAsync` 的 `totalCount` 来自数据库计数，组过滤是内存里做的**。所以申请层条件必须和组级条件同口径，不然会出现「有行、组为空」。要改这两处过滤时务必成对改。
