# 租户配置（自定义键值对）新增 — 2026-08-18

## 一、背景意图

前端需要一块「整个租户共用的小设置」存储区：列表默认列、页面开关、提示文案之类。这类配置数量不定、随时新增，如果每加一项都要后端建字段或在 `SettingProvider` 里补定义再发版，成本完全不成比例。

因此本次的诉求很明确：

- 键（配置名）由**前端自定义**，后端**不预先定义**；
- **不设默认值**，没配过就是没有；
- 读写范围固定为 **`TenantId` = 当前登录租户 且 `UserId` 为空**；
- **不挂权限点**，登录即可用。

落库直接复用 ABP 的设置表 `Sys_Settings`（框架原名 `AbpSettings`，本项目在 `CsprojBuilderDbContext` 里统一加了 `Sys_` 前缀），**没有新建表，也没有任何 Migration**。

### 2.3 为什么不用 SettingManager

`SettingManager` 是 ABP 读写设置的正规入口，但它**要求设置名事先定义**：

```
GetSettingValueAsync(name) → _settingDefinitionManager.GetSettingDefinition(name)
                           → 未定义时 throw new AbpException("There is no setting defined with name: " + name)
```

本需求要的恰恰是「配置名不预定义」，所以走不通。最终改为注入 `IRepository<Setting, long>` 直接操作实体，`Setting` 就是 `Abp.Configuration.Setting`（`AuditedEntity<long>` + `IMayHaveTenant`）。

顺带的两个后果：

- 本模块写入的行**不参与** `SettingManager` 的缓存，也不会被它读到（读它会抛未定义异常），两套体系互不干扰；
- 因此必须**主动隔离**系统预定义设置名，见 2.5。

### 2.4 TenantId 必须显式赋值

`Setting` 实现了 `IMayHaveTenant`，但**不能指望框架自动填 `TenantId`**：

```
AbpDbContext.CheckAndSetMayHaveTenantIdProperty()
    //Only works for single tenant applications
    if (MultiTenancyConfig?.IsEnabled ?? false) { return; }
```

多租户开启时这个方法直接 return。所以新增时显式写了 `TenantId = AbpSession.TenantId.Value`、`UserId = null`。宿主账号（`AbpSession.TenantId` 为空）会被前置拦掉，否则会写出一行 `TenantId` 为 NULL 的**应用级**设置，污染 Host 全局配置。

### 2.5 系统预定义设置名的读写双向隔离

`Sys_Settings` 的租户级那一层里本来就躺着设置页和框架写的行（`App.Site.SiteName`、`Abp.Zero.UserManagement.*`、`Abp.Timing.TimeZone` 等）。这些行由 `SettingManager` 带缓存管理，本模块绕过缓存直接改库，会造成「库里是新值、页面行为是旧值」。

处理方式是以 `ISettingDefinitionManager.GetAllSettingDefinitions()` 为准，两个方向都隔离：

- **写**：`NormalizeName` 里撞上预定义名直接报「配置名 xxx 是系统预定义设置,请换一个名称」，新增、编辑、删除都过这道校验；
- **读**：`BuildQuery` 在查询条件里排除全部预定义名，列表和详情都看不到它们。

### 2.6 其他实现细节

- 新增用 `InsertAndGetIdAsync`：`Sys_Settings.Id` 是数据库自增，`InsertAsync` 在 SaveChanges 之前拿不到 Id。
- 新增前先查一次重名，只为把数据库唯一索引 `(TenantId, Name, UserId)` 的冲突转成可读提示。
- 编辑按项目约定走**局部更新**：查出被 EF 跟踪的实体后只给 `Value` 赋值，不调用 `UpdateAsync`（那会把整行标记为 Modified 变成全列 UPDATE）。
- 所有查询接口 `AsNoTracking()`；分页参数用 `PageIndex` / `PageSize`，返回 `PagedList<T>`。
- 列表和详情按约定回填 `CreatorUserName` / `LastModifierUserName`（NickName），取自基类的 `GetUserInfoMapAsync()` 用户缓存。
- 详情查不到时返回 `null` 而非报错——「还没配过」是这类接口的正常状态，前端据此决定调新增还是编辑。
- 删除是物理删除（`Sys_Settings` 无软删除字段），批量为全有或全无；无子表、无外键引用，因此不需要级联清理和引用校验，真正需要拦的只有预定义设置名。

## 三、避坑指南

1. **不要拿这个模块去改系统设置**。系统设置一律走 `TenantSettingsAppService` / `HostSettingsAppService`，那边会正确失效 `SettingManager` 缓存。反过来，也不要用直接改库的方式修本模块数据以外的任何设置行。
2. **配置名统一加前缀**，建议 `Web.<页面>.<配置项>`。后端将来若新增一个设置定义并与前端已用的名字撞车，那个配置项会立刻从列表里消失且改不了（被 2.5 的隔离规则挡住）。
3. **配置名不能改**，一旦前端用起来就是契约；要改名只能删旧增新。
4. **配置名大小写不敏感**（SQL Server 默认排序规则），`Web.A` 与 `web.a` 视为同一个，会报重复；前端自己统一写法。
5. **「值为空」不等于「不存在」**。编辑传空只是把 `Value` 清空，记录还在，详情仍返回对象。前端拿「值为空」判断没配过，下次保存就会调错接口。
6. **新增不覆盖、编辑不新增**，两侧都是严格模式。标准姿势是先 `DetailAsync` 判空，再决定调哪个。需要 upsert 单接口的话另提。
7. **租户内共用，不是每人一份**。A 改了 B 立刻受影响，验收时不要按「快捷文本」那种完全私有的思路测。
8. **不要存敏感信息**。本模块无权限点，租户内任何登录用户都能读写全部配置项。真需要管控就得加 `Admin.TenantConfig.*` 权限点，并把读写拆成两个服务。
9. **并发是后写覆盖**，没有版本号或乐观锁。多人可能同时编辑的配置项，要在产品层面规避。
