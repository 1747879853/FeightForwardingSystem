# 海运出口业务关联用户变更同步服务项任务处理人 修改记录 2026-07-02

**修改时间：** 2026-07-02

**修改人：** 后端

**关联需求：** 修改海运出口 `TransportOrder` 的业务关联用户（OrderUser）后，需同步更新服务项任务（SeServiceTask）的处理人（SeServiceTaskUser）

---

## 一、需求背景

服务项任务的处理人（`SeServiceTaskUser`）是在任务生成时，依据海运出口业务关联用户（`OrderUser`）的用户属性（`UserAttribute`）与服务项配置（`SeServiceConfigItem.UserAttribute`）按位匹配得出的，`SeServiceTaskUser` 并不是 `OrderUser` 的实时外键，只是生成时刻的拷贝。

此前编辑海运出口时，只有在「起运港变更」或「服务项变更」的情况下才会删除并重新生成全部任务；若仅修改了业务关联用户（新增/删除/换人/改属性），已生成的待处理任务处理人不会同步，导致处理人与最新的 OrderUser 不一致。

本次改动在编辑海运出口时补齐该同步逻辑。

---

## 二、改动范围

| 文件 | 路径 | 修改类型 |

|------|------|----------|

| 服务 | `Application/App/SeaExport/SeaExportAdminAppService.cs` | `EditAsync` 增加 `else` 分支调用同步；新增私有方法 `SyncPendingTaskUsersAsync` |

---

## 三、核心逻辑

编辑保存海运出口时：

1. 若「起运港」或「服务项」发生变更，走原有逻辑：删除全部服务项与任务并重新生成（首个任务处理人按最新 `OrderUser` 生成）。

2. 否则进入新增的 `else` 分支，调用 `SyncPendingTaskUsersAsync(input.Id, finalOrderUsers)`，对待处理任务重新计算处理人。

`SyncPendingTaskUsersAsync` 处理逻辑：

```csharp

// 仅取待处理(Pending)任务

var pendingTasks = await _seServiceTaskRepository.GetAll()

    .Include(x => x.SeServiceTaskUsers)

    .Where(x => x.SeaExportId == seaExportId && x.ServiceTaskStatus == ServiceTaskStatus.Pending)

    .ToListAsync();

// 已转交(AssigneeUserId 有值)的任务跳过，其处理人由转交指定，不随 OrderUser 变更

// 按 (configItem.UserAttribute & ou.UserAttribute) != 0 匹配 UserId

// 处理人无变化则跳过；有变化则删除旧的 SeServiceTaskUser 后重新插入

```

匹配规则与任务生成时（`GenerateFirstServiceTaskAsync`、`SeServiceTaskAdminAppService.CompleteAsync`）保持完全一致。

---

## 四、同步范围与边界

| 场景 | 是否同步 | 说明 |

|------|----------|------|

| 待处理（Pending）且未转交的任务 | ✅ 是 | 按最新 OrderUser 重新计算处理人 |

| 已处理（Processed）任务 | ❌ 否 | 保留历史处理人，作为完成记录 |

| 已转交（AssigneeUserId 有值）任务 | ❌ 否 | 处理人由转交动作指定，不受 OrderUser 影响 |

| 起运港/服务项变更 | 走重建逻辑 | 删除并重新生成全部任务 |

| 传入的 OrderUser 属性无法匹配到任务处理人 | 抛出异常 | 提示「未找到对应用户属性的处理人，无法同步任务处理人」 |

---

## 五、避坑指南

1. **数据源为内存中的 `finalOrderUsers`**：同步使用编辑过程中收集的最终 OrderUser 列表，而非重新查库，避免 EF 尚未落库导致读到旧值。

2. **只同步待处理任务**：已处理任务不会被改写，避免破坏历史完成记录；已转交任务同样不受影响。

3. **匹配为空即报错**：若修改后的用户属性无法匹配出任何处理人（`matchedUserIds.Count == 0`），会抛出友好异常阻止保存，防止出现无人处理的待办任务，行为与新建任务保持一致。

4. **无变化不写库**：处理人集合未变化时直接跳过，避免无意义的删除重建。
