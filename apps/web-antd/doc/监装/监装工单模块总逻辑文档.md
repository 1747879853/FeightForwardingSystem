# 1. 业务背景说明 (Background)

**白话解释：** 海运出口的货装集装箱时，公司要派师傅到堆场现场盯着装，确认箱子干净、货码放到位、封条贴好，并且逐箱拍照留证。监装工单就是这件事的载体：**操作在内部系统给一票海运出口开一张监装工单**，填上明细包装、件数、预计到货时间、监装堆场，勾上要检查的监装要求，可以直接指派师傅，也可以不指派、提交后丢进**公共池**让师傅自己抢。

师傅在**小程序**里干活：看公共池抢单、看自己已认领的单、进详情逐个箱子填箱号封号、按类型传照片、勾"是否完成"。**所有箱子都标完成，工单自动变已完成**。

一票海运出口只能有一张监装工单（数据库上是一对多，留了后期改多单的余地）。

**监装视频**：客户光看照片不够，还想在装箱当时亲眼盯着。所以堆场里装了几个可以云台转动的摄像头，每个机身上贴了一个编号。师傅到现场后在小程序里填上自己正在用的那个编号，客户就能拿「主提单号 + 监装工单号」打开公开监装页看实时画面、还能自己转动摄像头。 **监装一完成视频立刻断掉**，摄像头释放给下一张工单。摄像头本身不做成基础资料，编号写死在代码里。

**画面一律由业务后端转发**，视频平台只监听本机回环、外网连不上。这不是为了性能，而是因为平台的播放地址是稳定的（流 id 就是设备编号\_通道编号，永远不变），而一个摄像头要被一张张工单轮流使用——不转发的话，存下地址的人等这个摄像头轮到别家客户的工单时照样能打开。

# 2. 功能与操作说明 (Features & Operations)

## 2.1 内部管理端（带 admin，要权限）

- **新建：** 选海运出口开单，工单号自动生成。可填明细包装+件数、预计到货时间、监装堆场、是否包含水印（默认含水印），可指派最多两个师傅（顺序有意义），可勾监装要求明细。新建后是**未提交**。
- **编辑 / 删除：** **只有未提交状态**能编辑和删除工单主表。编辑不带箱型；师傅列表和监装要求都是全量提交。
- **编辑箱型附件分组：** 输入一只箱子的 `OrderCtn.Id`，只改该箱的监装附件分组。**不改箱型/箱号/封号/是否完成，不改工单状态。任意状态都可以调**，没有别的业务校验。附件按该箱全量替换，传空数组即清空。
- **提交：** 有师傅 → 直接**已认领**；没师傅 → **待认领**（进公共池）。该海运出口**没有箱子不允许提交**。
- **撤回：** 只有**待认领**能撤回，撤回后回到未提交。
- **按海运出口id查详情：** 一次返回工单全部信息 + 海运出口简要 + 该海运出口的箱型列表（箱型/箱号/封号/是否完成/分组附件）+ **全部监装要求主子表（每条明细带 `isChecked`）**，勾选界面直接拿它回填。没有工单时返回 `null`。
- **列表：** 分页查监装工单，每条带**完整的海运出口列表对象**（与海运出口列表返回的是同一个 `SeaExportDto`，但**不含运踪**）。筛选条件见第 6.1 节。**可见范围跟随海运出口数据权限**：工单本身不参与数据权限，只返回当前用户在海运出口列表里能看到的那些票对应的工单。
- **按到货日+船公司查已排师傅的堆场：** 给新建时做「这天这个船公司的某个堆场已经有师傅」的默认提示，返回**按堆场id+师傅id去重**后的组合，每条同时给 id 和名称，前端点中即可回填堆场与监装师傅。

## 2.2 监装师傅端（不带 admin；除公开详情外需登录 + 用户属性含监装）

- **分页查询（一个接口三种用法）：** 状态必填，只能传待认领/已认领/已完成。**待认领只查公共池**（无师傅的单，所有师傅都能看到）；**已认领、已完成只查自己的**（自己在师傅列表里）。可按堆场id、堆场关键字（名称/地址/备注模糊）、主提单号、品名、船公司、起运港、预计到货日、工单号筛。
- **认领：** 只能认领公共池的单，认领后自己进师傅列表，状态变已认领。已有人的单报「该工单已被【xx】认领」。
- **拒接：** 只能拒接已认领且自己在师傅列表里的单，带拒接原因。**把自己从列表移出**，剩下的人重排序；**列表空了就退回待认领重进公共池**，还有人则状态不变。
- **详情：** 出参结构与管理端详情完全一样，但监装要求**只返回勾选了的明细**，一条明细都没勾的要求整条不返回——师傅只看要做的事。师傅只读，不能改勾选。
- **编辑箱型：** 只能改箱型、箱号、封号、是否完成、分组附件；**不能加箱也不能删箱**。只有已认领能编辑。保存后所有箱子都完成 → 工单自动**已完成**。
- **取消完成：** 只有已完成能取消，取消后退回已认领，才能继续编辑。
- **选摄像头：** 两个接口——`GetCameraListAsync` 拉可选列表（带占用情况），`EditCameraNoAsync` 把编号存回工单。师傅对着现场摄像头机身上的号牌挑自己在用的那台，选完客户那边就能看视频了。清空即解绑。 **只有已认领能选，且只能改自己的单**；一个编号同时只能被一张工单占用。
- **公开详情：** 输入主提单号 + 监装工单号（都精确匹配），返回与师傅端详情相同的结构和数据。**免登录、不校验监装属性、不校验工单状态。** 出参 `companyLogo` 是该票所属公司 Logo，没上传时为 `null`。

## 2.3 公开端监装视频（免登录，`/api/services/app/LoadingOrderVideo`）

口令与公开详情相同：**主提单号 + 监装工单号**。三个接口：开始点播、云台控制、查询观看人数。另有一个不带 `Async` 的转发路由 `/api/loading-order-video/stream/{监装工单id}.flv`，播放器直接拉它。

- **看画面：** 开始点播返回的是**业务后端自己的 HTTP-FLV 转发地址**（按工单 id 寻址，**没有有效期**），视频平台的原始地址一个字都不下发。**只有 FLV，没有 HLS**——HLS 延迟十几秒，云台转一下要等二十多秒才看得见，监装场景用不了，不值得为它多做一套分片重写与逐片鉴权。
- **转摄像头：** 云台控制支持八个方向加变倍。**接口只有「开始转」和「停」，没有「转几秒」**，所以前端必须按下发方向、松开发停止。云台是所有人共用的，没有抢占机制。
- **观看人数：** 写死上限 3 个**连接**（同一人多开页面算多个）。转发之后计数由业务后端自己统计，是**准确值**，也是**真的拦得住的硬上限**：第 4 路连接直接 429。
- **什么时候看不了：** 师傅还没填编号、师傅解绑了、**监装已完成**。都是立即生效的——转发时每次都回查工单。**地址本身不带有效期**：工单没完成就一直能看，完成了立刻看不了。 **师傅换摄像头不算失效**，转发时认工单当前绑的那台，客户手里的地址自动切过去。
- **没有「停止播放」接口，是刻意不给的。** 平台的停播是通道级的，一调所有人一起黑屏，放在免登录端等于给任何人一个「让别人看不了」的按钮。观众关页面连接自然断，最后一个人走了平台按无人观看自动回收；真要停流的三处（完成、换绑、解绑）都由后端自己调。

# 3. 状态流转说明 (Status Transitions)

状态枚举 `LoadingOrderStatus`：`未提交=0`、`待认领=1`、`已认领=2`、`已完成=3`。

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| （无） | 操作 新建 | 未提交 | 初始状态 |
| 未提交 | 操作 提交（师傅列表非空） | 已认领 | 认领时间记为提交时间 |
| 未提交 | 操作 提交（师傅列表为空） | 待认领 | 进公共池 |
| 未提交 | 操作 编辑 / 删除 | 未提交 / 已删除 | **只有这个状态能改工单主表** |
| 任意状态 | 操作 编辑箱型附件分组 | 不变 | 只替换该箱监装附件，不走状态机 |
| 待认领 | 操作 撤回 | 未提交 | 清空提交人与提交时间 |
| 待认领 | 师傅 认领 | 已认领 | 自己进师傅列表 SortId=1 |
| 已认领 | 师傅 拒接（列表还剩人） | 已认领（状态不变） | 只把自己移出，剩下的重排序 |
| 已认领 | 师傅 拒接（列表空了） | 待认领 | 重进公共池，清空认领时间 |
| 已认领 | 师傅 修改摄像头编号 | 不变 | 只改 `CameraNo`，不走状态机；换号/解绑时停掉原来那路流 |
| 已认领 | 师傅 编辑箱型（所有箱完成） | 已完成 | 自动流转，记完成时间；**同时把 `CameraNo` 置空并停流** |
| 已完成 | 师傅 取消完成 | 已认领 | 清空完成时间，之后才能编辑。**摄像头不会自动绑回来**，要重新填编号 |

**已认领之后管理端不能再改工单主表**（编辑/删除只允许未提交，撤回只允许待认领）。要换人只能等师傅拒接，或者线下联系师傅。 **例外：** 箱子上的监装附件分组可以由管理端在任意状态下单独改，见第 2.1 节。

所有查询接口都带这个对象，外键一律返回对象不平铺：

| 字段 | 取自 |
| :-- | :-- |

## 4.6 摄像头台账与平台配置（**全部写死在代码里，没有表也不进 appsettings**）

视频这块**一个配置项都不放 `appsettings.json`**，两处常量就是全部来源：

| 代码文件 | 内容 |
| :-- | :-- |
| `App/ExternalApi/Wvp/WvpConfig.cs` | 视频平台地址 `BaseUrl`、控制接口凭证 `ApiKey`、各接口路径与转发路由 |
| `App/LoadingOrder/LoadingOrderCamera.cs` | 摄像头台账：编号 → 设备/通道国标编号 |

观看人数上限不在上面这两处，它在 `LoadingOrderVideoViewerCounter.MaxViewerCount`——那是业务规则不是部署参数。

**为什么不做成配置**：视频平台只有这一台、摄像头是堆场里的固定设施，装完就不动了。而且这两处是**联动**的——平台换了地址，台账里的设备与通道国标编号必然也要跟着核一遍，拆成「一半在配置、一半在代码」只会多一处要同步的地方，换平台时反而更容易漏。所以一起写死，换平台就改常量重新发版。

> `ApiKey` 的初始值是**空串**：平台的 Key 不适合提交到代码库，留空占位，部署的人填上再发版。空着调用会被 `WvpConfig.EnsureConfigured()` 提前拦下，报 `未配置视频服务凭证,请联系管理员`。 **不拦的话**请求会带一个空 `api-key` 头发出去，换回平台的鉴权失败，对外文案变成「点播失败,请稍后重试」——让人以为是摄像头坏了，真实原因只能翻日志。
>
> 填的时候**只填 Key 本身，不要带 `WVP_API_KEY=` 前缀**：平台控制台是按环境变量的形式给出来的，整行粘进来会把前缀一起塞进请求头，换回来同样是鉴权失败。
>
> `BaseUrl` 没有对应校验，它是写死的非空常量，不存在没填的情况。但它有另一条硬要求： **必须是外网访问不到的地址**（当前是 `http://127.0.0.1:8080`）。一旦换成公网可达的地址，「存下地址跨工单复用」这条路就重新打开了，整套转发白做（卡点 12）。
>
> 转发地址**没有密钥也没有有效期**，所以这里不需要任何与访问控制相关的配置：地址的生死完全由工单状态决定，每次拉流回查一遍即可（卡点 13）。

### 摄像头台账 `LoadingOrderCamera`

`src/CsprojBuilder.Application/App/LoadingOrder/LoadingOrderCamera.cs`，一行一个摄像头：

| 字段 | 说明 |
| :-- | :-- |
| `CameraNo` | 摄像头编号，**工单表 `CameraNo` 存的就是它**，也是堆场里贴在机身上的号牌。一经启用不可更改 |
| `Name` | 名称，如「摄像头1」，出参里返回给前端 |
| `DeviceId` | 视频平台的**设备**国标编号。只在后端调平台时用，**不返回给前端** |
| `ChannelId` | 视频平台的**通道**国标编号。同上 |
| `IsEnabled` | 停用后不再允许绑定，但历史工单仍能靠它解析出名称 |

两个查询口：`Find(编号)` 按编号取一台，**已停用的也取得到**（历史工单要靠它解析名称）； `GetEnabled()` 取启用中的全部、按编号升序，**只给师傅端的可选列表用**——停用的列出来只会让师傅选了才被拦。

**为什么不建表**：摄像头是堆场里数量很少、几乎不变的固定设施，做成基础资料要配一整套增删改查加权限，而真正会变的只有「哪张工单用哪个摄像头」——这一项已经落在 `App_LoadingOrders.CameraNo` 上了。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：一票海运出口只能开一张工单]** `AddAsync` 会查该海运出口是否已有工单，有则报 `该海运出口已存在监装工单,不可重复新建`。 **已软删除的不算**（走 `GetAll()` 带软删除过滤），所以删掉之后可以重新开。数据库结构是一对多，只有新增这一处卡，这是为了后期改多工单时改动最小。

> [!IMPORTANT] **[卡点 2：拒接不会把单子退回未提交，而是退回公共池]** 这是与最初需求描述**不同**的一点，改动的理由是：原方案「拒接后师傅id不变、状态变未提交」会死循环——操作重新提交时因为师傅列表非空又直接变已认领派给同一个人，拒接等于无效。现在的规则：拒接**只删自己那一行**，剩下还有人 → 状态不变；**一个人都不剩 → 状态变待认领**，重回公共池等人抢。这样单子既不会卡在"已认领但没人"的幽灵态，也不会弹回给刚拒接的人。

> [!IMPORTANT] **[卡点 3：没有箱子不能提交]** 「所有箱子都完成 → 自动完成」在零箱时集合上恒为真，会让工单一提交就完成。所以 `SubmitAsync` 先卡一道：该海运出口没有 `OrderCtn` 直接报 `该海运出口没有箱型,不能提交监装工单`。

> [!IMPORTANT] **[卡点 4：取消完成不重置箱子的完成标记]** 取消完成只把工单状态从已完成退回已认领，**各箱的 `IsLoadingCompleted` 原样保留**。所以师傅如果只是进去改个封号就保存，所有箱子仍是完成态，保存后会**立刻再次自动完成**。这是刻意的：真要改完成状态就去把某个箱子的勾去掉。前端要提示清楚，别让师傅以为没保存上。

> [!IMPORTANT] **[卡点 5：师傅改的是业务委托单的真实箱数据]** 箱号大部分本来就是师傅现场回填的，所以师傅端编辑写的是 `OrderCtn` 本表，海运出口那边看到的就是改后的值。**没有留改动痕迹**，谁改的只能从附件创建人间接推断。

> [!IMPORTANT] **[卡点 6：管理端在已认领之后不能再改工单主表，但能改箱型附件]** 工单主表的编辑/删除只允许未提交，撤回只允许待认领。一旦提交且有师傅（直接变已认领），管理端改不了师傅、要求、堆场这些主表字段，也删不了、撤不回，换人只能等师傅拒接。 **箱型上的监装附件分组除外**：`EditOrderCtnAttachmentGroupsAsync` 不看工单状态，未提交到已完成都可以按箱全量替换附件，也不改工单状态、不改箱号封号。

> [!IMPORTANT] **[卡点 7：监装要求是拍快照式的 id 引用，不是内容副本]** 工单只存 `LoadingRequirementItemId`。基础资料里把这条明细改名或删掉，工单上的勾选会跟着变名字、或者变成一个查不到的 id（两端详情都是拿现存的要求去比对勾选集合，已删除的明细不会出现在 `loadingRequirements` 里，但仍留在 `loadingRequirementItemIds` 中）。监装要求那边**没有做被引用禁止删除的校验**（《监装要求模块总逻辑文档》卡点 4 已标注），现在有引用方了，需要的话要去那边补。

> [!IMPORTANT] **[卡点 8：编号规则必须先配]** `LoadingOrder.LoadingOrderNum` 这条规则要在编号生成模块里配好，否则 `AddAsync` 直接报 `未配置生成规则`，一条工单都建不出来。

> [!IMPORTANT] **[卡点 9：公开详情靠「主提单号 + 监装工单号」当口令]** `DetailByMblAndLoadingOrderNumAsync` 免登录。两个号码都必须精确匹配到同一张工单才给数据，对不上统一报 `主提单号或监装工单号错误`，避免被人拿一个号码去试另一个。定位时关闭 `MustHaveTenant` / `MayHaveTenant`，找到后再 `SetTenantId` 切到该工单租户做详情映射（否则监装要求、附件、用户昵称会按空租户过滤，映射出来是空的或串租户）。不校验工单状态，未提交的单只要号码对也能看到。出参 `companyLogo` 与业务详情所属公司打印信息的 Logo 同一口径（组织管理里该公司上传的 Logo，相对路径已拼基址）。公司没上传时字段为 `null`，分享页用品牌图兜底，**不要**因此把整次详情请求打成失败。

> [!IMPORTANT] **[卡点 10：摄像头由师傅维护，管理端一个接口都没有]** 摄像头是**现场信息**——师傅到了堆场才知道自己站在哪台摄像头下面，操作在办公室填不了也填不准。所以整套摄像头功能**只有师傅端两个接口**：`LoadingOrder/GetCameraListAsync` 拉可选列表、 `LoadingOrder/EditCameraNoAsync` 存回编号。两个的权限口径与编辑箱型完全一致： **只有已认领状态、且自己在师傅列表里**。
>
> 连带结论：
>
> - 管理端 `AddAsync` / `EditAsync` **不带** `cameraNo` 字段，管理端详情里 `cameraNo` / `camera` 是**只读**的；
> - 可选列表**必须传工单id**且限定在自己的单上——占用情况是跨租户查出来的，不限定就成了「枚举全系统摄像头正被谁占着」的接口。列表里已停用的不返回，别家占着的只说被占用、不给单号；
> - 列表上的 `isOccupied` 只是**提前告知**，真正的拦截在 `EditCameraNoAsync` 那一步（拉完列表到点保存之间别人可能刚好占了同一台）。师傅也可以不看列表直接照着号牌填，编号合法性完全由后端判（报 `摄像头编号错误,请核对摄像头上的编号`）——这也是为什么台账里的编号必须和现场号牌一致；
> - 已完成状态改不了。要继续用得先「取消完成」退回已认领，再重新选一次（会重新走一遍占用校验，此时那个摄像头可能已经被别的工单拿走了）。

> [!IMPORTANT] **[卡点 11：一个摄像头同时只能被一张工单占用，且占用校验必须跨租户]** 摄像头是堆场里的**物理设备**，视频服务是全系统一套配置、不分租户。只按本租户查重的话，两个租户会各自以为某个编号空着、双双填上去，最后两家客户看到的是同一路画面——**等于把别人的货给外人看了**。所以 `ValidateCameraNoAsync` 里 `DisableFilter(MustHaveTenant, MayHaveTenant)` 之后再查占用。
>
> 报错分两种，**刻意不一致**：占用方同租户时把工单号说出来（师傅好去那张单解绑），跨租户时只说「已被其它监装工单占用」，不透露别家的单号。

> [!IMPORTANT] **[卡点 12：平台地址是稳定的，所以画面必须经业务后端转发]** 视频平台的流 id 就是「设备国标编号\_通道国标编号」，**同一个摄像头永远是同一串**，播放地址跟着永远不变。而摄像头要被一张张工单轮流使用。把平台地址下发给浏览器，就等于发了一把**永久钥匙**：存下来的人等这个摄像头轮到下一张工单（很可能是别家客户的货）时照样能打开。
>
> 平台侧补救不了（见 `文档/监装/视频/对接.md` 第 8 节）：没有带过期时间的播放令牌，自己在地址后面拼 `token`/`expires` 不起作用；国标流的播放鉴权回调对 `rtp` 应用直接放行；停播是**通道级**的，踢不掉单个人。
>
> 所以：**平台只监听 `127.0.0.1:8080`，外网封死**，画面一律走 `LoadingOrderVideoController` 转发，给前端的是我们自己的地址。这条是整套访问控制的地基——**哪天把平台端口对外开放了，下面这些全部失效**。
>
> 两个实现上必须注意的点：
>
> - 平台返回的 flv 地址里的主机是**平台自己配置的对外地址**（很可能是公网 IP），与我们从哪儿调它无关。拉流前必须只取路径重新拼到回环地址（`WvpApiClient.ToInternalPath`），照着它去连要么绕出内网、要么直接被防火墙挡掉。
> - 转发是**几小时级的长连接**，所以转发那个 action 必须 `[UnitOfWork(IsDisabled = true)]`，鉴权交给 AppService 用它自己的短工作单元做完。不然一个观众就长期占着一条数据库连接，三五个人能把连接池吃干净。拉流用的 HttpClient 也必须是**单独一个、超时设无限**的命名客户端，挂在控制接口那个 60 秒超时的客户端上，画面看一分钟就黑。

> [!IMPORTANT] **[卡点 13：转发地址不签名、不设有效期，「链接失效」全靠每次拉流回查工单]** 地址里直接放工单 id，`/api/loading-order-video/stream/{工单id}.flv`。**没有令牌，没有过期时间。**
>
> 曾经做过一版带 HMAC 签名和 180 分钟有效期的令牌，拆掉了。理由是它挡不住任何东西：
>
> - 签名想防的是「改地址里的参数」，但**改也没用**——摄像头编号本来就要跟工单当前的 `CameraNo` 比对，工单 id 是 128 位随机 Guid 猜不出来。签名唯一的作用就是让那个有效期生效。
> - 而有效期本身没有业务含义：**工单没完成就该一直能看，完成了就该立刻看不了**，中间插一个 180 分钟只会制造「装箱装了半天、客户页面自己断掉」的问题。
> - 点播接口是免登录的，知道那两个号码的人随时能换一个新地址，签名也拦不住他，本来也不该拦。
>
> 所以**每一次拉流**（首播、断线重连、刷新页面）都完整走一遍这几道，这是唯一的关卡：id 是合法 Guid 吗 → 工单还在吗 → 是不是已完成 → 还绑着摄像头吗 → 占得到观看位吗。
>
> **师傅换摄像头不会让地址失效**：转发时认的是工单**当前**绑的那台，所以原来那台坏了换一台，客户手里的地址自动切到新的一路。地址绑的是工单不是设备，切过去看到的仍然是自己这票货。
>
> 工单 id 因此会暴露给客户，这是可以的：**没有任何免登录接口拿工单 id 当入参** （公开详情认的是主提单号 + 监装工单号）。以后加免登录接口时别把工单 id 当口令用。
>
> 解绑、换号、任务完成三处**仍要额外调一次停流**（`StopCameraStreamAsync`）：上面那几道只让人连不进来，**掐不断已经在推的那一路**。
>
> 停流是外部调用，**失败只记日志不抛错**：这三处都已经改过业务数据了（工单完成、箱号封号、附件、新编号），这里一抛就会连坐——AppService 默认带事务，前面的改动会一起回滚，师傅那一次保存等于白做。停不掉也不算破窗：转发那一层已经拦住了，客户根本拿不到画面。

> [!IMPORTANT] **[卡点 14：观看人数只能由我们自己数，平台的 readerCount 转发后恒为 1]** 上限写死 3（`LoadingOrderVideoViewerCounter.MaxViewerCount`，不放 `appsettings`——这是业务规则不是部署参数）。
>
> **不要再去查平台的 `readerCount`**：转发之后平台那边的拉流方只有业务后端一个，那个数恒为 1，跟真实观众数没有关系。真实连接数只有我们自己知道，所以 `IWvpApiClient` 里干脆没有查流信息的方法。
>
> 计数**放进程内存**，不落库也不进分布式缓存：计数必须与「这个进程正在转发的连接」严格对应，落库反而会因为进程崩溃留下永远减不回去的脏数据，把摄像头卡死在「满 3 人」；进程内的计数进程一死就跟着连接一起消失，天然自愈。代价是**业务服务不能多实例** （每个实例各算 3 个）——当前平台就装在业务服务器本机，本身就是单机部署。
>
> 两处必须注意：
>
> - `TryAcquire` 的「查当前数 + 加一」必须在同一个锁里，否则三个人同时进来会一起读到 2 再一起加成 5。用 `Dictionary` 加锁而不是 `ConcurrentDictionary`：后者的 `AddOrUpdate` 没法表达「超了就别加」。
> - `Release` **必须放 `finally`**。少释放一次这个摄像头就永久少一个观看位，漏满 3 个谁都看不了，而且只有重启服务才能恢复。
>
> 点播接口里也判了一次人数，但那只是**提前告知**，让客户立刻看到原因；手上已经有地址的人可以跳过点播直接连，**真正拦得住的是转发时占位那一步**。

列表接口的筛选条件分两类：工单自身的（监装状态单选 `status` / 多选 `statuses`、工单号、堆场、预计到货日、监装师傅、工单创建时间区间）直接落在工单表上；海运出口维度的（主提单号、委托编号、品名、船公司、起运港、船名、航次、所属组织）先解析成海运出口id集合再过滤工单，口径与师傅端一致。默认排序是工单创建时间倒序，可由 `sorting` 覆盖。 `sorting` 除工单表字段外，还支持：

- `CarrierYard.Name`：堆场名称，未选视为空
- `CodePackageItem.Name`：明细包装名称，未选视为空
- `LoadingOrderUsers.UserId`：师傅子表 `SortId` 最小那条的 UserId（先输入的师傅）；没有师傅视为空。一对多不能按属性路径反射，走 `ApplySorting` 的 `customPaths`

多字段逗号分隔，例如 `CreationTime DESC, CarrierYard.Name ASC`、`LoadingOrderUsers.UserId ASC`。管理端 `GetPagedListAsync` 与师傅端 `GetMyPagedListAsync` 同一套。

**数据权限**：工单主表不继承数据权限基类（没有自己的所属人/所属组织），列表可见性**跟随海运出口**，用的也是海运出口模块的数据权限配置（`DataPermissionModule.SeaExport`），监装工单没有自己的数据权限模块。 `GetPagedListAsync` 先 `GetDataPermissionUserIdsAsync(DataPermissionModule.SeaExport)` 判断：「全部」且没有排除人员时**不挂任何海运出口 id 条件**；其余情况用 `SeaExportListDataPermissionFilterAsync` 圈出可见海运出口 id，再按 `LoadingOrder.SeaExportId` 过滤。口径与海运出口列表完全一致：所属人、创建人、所属组织、业务关联人员（销售/商务/操作/客服/单证/海外客服/航线）任一命中即可见；这几类人里任一是当前用户排除人员名单里的人，这票对应的工单就不可见（全部权限也挡）。详情、新建、编辑、删除、提交、撤回**不接**这层行级过滤（仍只校验后台权限位）。师傅端列表按师傅身份过滤，也不走这套。

师傅端除公开详情外都不校验后台权限，但每个都会先查当前登录人的 `UserAttribute` 是否含监装，不含直接报 `当前登录人的用户属性不包含监装,无权使用监装功能`。 `[AbpAuthorize]` 标在方法上，不标在 `LoadingOrderAppService` 类上，这样公开详情才能免登录。

## 6.3 公开端监装视频 `/api/services/app/LoadingOrderVideo`（全部免登录）

| 接口方法 | HTTP | 说明 |
| :-- | :-- | :-- |
| `StartPlayAsync` | `POST` | 开始点播，返回摄像头对象、**本系统的 FLV 转发地址**与当前观看连接数 |
| `PtzAsync` | `POST` | 云台控制，八方向 + 变倍 + 停止，带三个速度 |
| `GetViewerCountAsync` | `GET` | 查当前有几路连接在看，只要两个号码，**不需要流标识** |
| `AuthorizeStreamAsync` | — | **标了 `[RemoteService(false)]`，不对外暴露**，只给转发控制器调：回查工单 + 点播 |

`LoadingOrderVideoAppService` **类上不标 `[AbpAuthorize]`**，所以每个方法默认匿名——和 `LoadingOrderAppService` 的做法相反（那边类上不标是为了让公开详情匿名、其余方法各自标上）。 **这个类里新增方法时要特别注意**：不标就是对外公开的。

**没有「停止播放」接口是刻意的**，别看着 `IWvpApiClient` 里有 `StopPlayAsync` 就顺手补一个：平台的停播是通道级的，暴露给免登录端等于给任何人一个「让别人看不了」的按钮。停流只在监装完成、师傅换绑、师傅解绑这三处由 `LoadingOrderAppService.StopCameraStreamAsync` 调。

## 6.4 画面转发 `/api/loading-order-video`（免登录，普通控制器**不带 `Async`**）

# 9. 避坑指南 (Pitfalls)

- **两个「场站」不是一回事**：海运出口本身有个 `YardId`（指向往来单位的场站），监装堆场是船公司下的 `CarrierYard`。新建工单时**不会**自动带出海运出口的场站，必须从船公司堆场里选。
- **师傅端堆场关键字搜的是堆场表**：`carrierYardKeyword` 对 `CarrierYard.Name` / `Address` / `Remark` 做模糊匹配，工单自己的 `Remark` 不在范围内；没选堆场的工单也匹配不上。与 `carrierYardId` 同时传是 AND。
- **海运出口改了船公司/包装之后不管**：工单上的堆场、明细包装可能变成不属于新船公司/新包装的脏数据，这次明确不做联动校验。
- **软删除不级联**：`DeleteAsync` 里两张子表都是显式批量删除。新增第三张子表时记得补。
- **子表全量替换走仓储增删，不要换导航集合**：`EditAsync` 里先 `DeleteAsync(predicate)` 再逐条 `InsertAsync`，**不去动 `loadingOrder.LoadingOrderUsers`**。两张子表是硬删除实体，把导航集合整体替换会和已标记删除的实体互相干扰；而从集合里移除元素只会把外键置空（列非空 → 报错）。
- **子表 Id 显式 `Guid.NewGuid()`**：不依赖 EF 的 Guid 值生成器，和 `StatementFee` 的写法一致。
- **局部更新不调 `UpdateAsync`**：主表、箱型都是局部赋值 + `CurrentUnitOfWork.SaveChangesAsync()`。
- **待认领的口径是「无师傅」而不是「师傅不是我」**：公共池查询用 `!x.LoadingOrderUsers.Any()`。因为提交时有师傅就直接进已认领，所以待认领的单必然没有师傅，两种写法结果相同，但前者语义更准。
- **师傅端的「自己的」按子表判定**：`x.LoadingOrderUsers.Any(u => u.UserId == 当前用户)`，不是主表上的某个字段。
- **附件按箱替换**：师傅端编辑箱型时对**提交上来的每个箱**先删该箱全部监装附件再重建，没出现在数组里的箱附件不动。管理端 `EditOrderCtnAttachmentGroupsAsync` 一次只替换一只箱子，口径相同。
- **附件分组维度是「附件明细类型」**：复用系统现成的 `AttachmentGroupDto`。空箱照/装货中/封箱照这类分组要去附件类型基础资料里配，不是代码里写死的。
- **`OrderCtn` 老接口没动**：业务委托单、海运出口、分单的箱型接口都不返回也不写 `IsLoadingCompleted`。需要在海运出口界面展示监装进度的话要另外加。
- **公开详情是精确匹配、两个号码一起当口令**：不要做成模糊搜。对不上时不要拆开报「主提单号不存在」或「工单号不存在」。
- **公开详情定位必须关租户过滤**：免登录没有 `AbpSession.TenantId`，不过滤会按空租户查，永远找不到。找到工单后要立刻 `SetTenantId` 再映射，不能全程关着过滤——`BuildRequirementsAsync` 会把所有租户的监装要求混在一起。
- **匿名是靠「不标 `[AbpAuthorize]`」实现的，不是靠 `[AbpAllowAnonymous]`**： `LoadingOrderAppService` 类上不标，公开详情那个方法也不标（**所以它是匿名的**），其余方法各自标 `[AbpAuthorize]`。 `LoadingOrderVideoAppService` 整个类都不标，所有方法全匿名；其中 `AuthorizeStreamAsync` 靠 `[RemoteService(false)]` 不生成对外路由，**它只是不可见，不是有鉴权**，别把它当受保护方法用。 **这两个类里新增方法时，不标就是对外公开的**，别漏。
- **摄像头编号用 `int?`，不要用 0 当"未绑定"**：`CameraNo == null` 才是没绑，`0` 不是合法编号（台账从 1 开始）。判断一律写 `!= null`，别写 `> 0`。
- **平台的播放地址一个字都不许下发给前端**：它是稳定地址（流 id = 设备编号\_通道编号，永远不变），下发了就等于发了把永久钥匙，能跨工单看到别家客户的货。出参里只给我们自己的转发地址，连 `app` / `stream` / `mediaServerId` 这些流标识都不给——前端没有任何场景需要它们。见卡点 12。
- **平台端口必须对外网封死**：`WvpConfig.BaseUrl` 是 `http://127.0.0.1:8080`。一旦对外开放，上面那条就绕过去了，整套转发白做。
- **拉流要把平台返回地址的主机丢掉**：平台返回的 flv 地址里的主机是**它自己配置的对外地址**，与我们从哪儿调它无关。必须只取 `PathAndQuery` 重新拼到回环（`WvpApiClient.ToInternalPath`）。
- **转发的 action 必须禁工作单元**：`[UnitOfWork(IsDisabled = true)]`。一路画面能挂几个钟头，工作单元跟着开那么久等于一个观众长期占一条数据库连接。鉴权交给 AppService 用它自己的短工作单元做。
- **拉流的 HttpClient 必须单独一个且超时设无限**：挂在控制接口那个 60 秒超时的客户端上，画面看一分钟就黑，日志里只有一句超时。取消靠 `HttpContext.RequestAborted`。
- **观看位 `Release` 必须放 `finally`**：少释放一次这个摄像头就永久少一个名额，漏满 3 个谁都看不了，只有重启服务能恢复。见卡点 14。
- **别再去查平台的 `readerCount`**：转发后平台那边的拉流方只有业务后端一个，那个数恒为 1。观看人数只认 `LoadingOrderVideoViewerCounter`。
- **业务服务不能多实例**：观看计数是进程内的，多开一个实例上限就翻倍。
- **别给转发地址加签名或有效期**：加过又拆了，见卡点 13。签名唯一的作用是让有效期生效，而有效期本身没有业务含义——工单没完成就该一直能看，完成了就该立刻看不了，中间插一个过期时间只会制造「装箱装了半天、客户页面自己断掉」。地址的生死只由工单状态决定。
- **转发地址里有工单 id，这不是口令**：不要新增「拿工单 id 就能查/改」的免登录接口。公开端认的一直是主提单号 + 监装工单号。
- **停流不许做成对外接口**：平台的停播是**通道级**的，一调整路画面掐断、所有人一起黑屏。公开端是免登录的，暴露出去等于给任何人一个「让别人看不了」的按钮。 `IWvpApiClient.StopPlayAsync` 只给后端那三处（完成、换绑、解绑）用，别顺手包一个接口出去。
- **换摄像头必须停旧流**：转发那几道校验只让人连不进来，**掐不断已经在推的那一路**。所以 `EditCameraNoAsync` 里编号真的变了才调 `StopCameraStreamAsync(旧编号)`，见卡点 13。三个调用点（换号、解绑、任务完成）漏一个，那一路流就会在平台上空转到自动回收。
- **停流失败不能抛**：`StopCameraStreamAsync` 内部 `try-catch` 只记 `Logger.Warn`。它的调用点前面都已经改过业务数据，抛异常会让整个工作单元回滚。
- **被禁了工作单元的 action 调用的 AppService 方法，不能直接用 `CurrentUnitOfWork`**：转发 action 标了 `[UnitOfWork(IsDisabled = true)]`，所以 `AuthorizeStreamAsync` 里是自己 `UnitOfWorkManager.Begin()` 的，那段不是多余的，删了就是拉流时报 `NullReferenceException`。以后再加这类手写控制器同理。
- **对外报错不许出现视频平台的名字和字段名**：统一说「视频服务」「外部接口」。平台名与原始报文只写进 `Logger`，排查问题全靠它们。
- **摄像头台账的编号和现场号牌是同一个东西**：师傅照着机身上的号牌填，台账里改错编号等于把师傅指到别的摄像头上。加摄像头时先贴号牌、再改代码。
- **视频这块改配置要发版**：平台地址、ApiKey、摄像头台账、观看人数上限 **全都是代码里的常量**，`appsettings.json` 里一个都没有。别去配置文件里找，也别指望改完重启就生效。
- **海运出口被删时摄像头会自动释放，但流不会停**：工单跟着软删除后就查不到占用了（走 `GetAll()` 软删除过滤），编号自然可以给别人用；但没有任何地方去停那路流。客户那边**看不到**（转发时查不到工单，直接 403），只是平台上那一路流会空转到自动回收。这个场景很少（删海运出口通常意味着单子作废），暂不处理。
