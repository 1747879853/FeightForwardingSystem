# 1. 业务背景说明 (Background)

**白话解释：** 海运出口一票货装集装箱时，客户或公司内部会提出一堆具体要求——比如「装箱前拍空箱照」「货物码放需加护角」「装完贴封条并拍照」。这些要求是**可复用的模板**，不需要每票货重新手打一遍。

监装要求模块就是维护这批模板：**主表是一条「监装要求」（有个要求名）**， **子表是这条要求下面的若干条具体明细**。后续监装单可以直接挂某条监装要求，把它下面的明细一次性带过去。

本模块是监装模块的前置基础资料，本次只做这张主子表的维护（增删改查），监装单本身不在本次范围内。

# 2. 功能与操作说明 (Features & Operations)

- **新建监装要求：** 填要求名、排序、备注，下面的明细表格里录入明细名称、备注，随主表一次提交。
- **编辑监装要求：** 子表按**全量提交 + 差异比对**处理——传了 `id` 的更新、`id` 为 null 的新增、原有但本次未提交的删除。
- **删除监装要求：** 显式删除明细子表，再软删除主表。
- **列表 / 详情：** 都返回该条监装要求下的全部明细，**按明细 `SortId` 升序**（与录入顺序一致）。
- **列表默认排序：** 按主表 `SortId` **升序**（主表排序是前端自己维护的），前端也可以传 `sorting` 覆盖。

## 2.1 两个 SortId 的区别（本模块最需要说清的一点）

|  | 主表 `SortId` | 子表 `SortId` |
| :-- | :-- | :-- |
| 谁决定 | **前端输入**，入参里有这个字段 | **后端生成**，入参里**没有**这个字段 |
| 取值 | 前端随便填，不填就是 `0` | 按提交数组下标自增，从 **1** 开始 |
| 编辑时 | 前端传什么就存什么 | 按本次提交的数组顺序**整体重排** |
| 返回顺序 | 列表默认按其升序（可被 `sorting` 覆盖） | 恒按其升序，不可改 |

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：主表排序前端传，子表排序前端不能传]** 这是本模块唯一容易搞混的地方。主表 Add/Edit 入参**有** `sortId`；子表 Add/Edit 入参**没有** `sortId`，传了会被 JSON 反序列化直接忽略，后端一律按数组下标自增赋值（`i + 1`）。子表想调顺序就调数组元素顺序。

> [!IMPORTANT] **[卡点 2：子表是全量提交，漏传等于删除]** 编辑时以本次提交数组中出现的 `id` 集合为准，原有明细中不在该集合里的**一律删除**。传 `null` 或 `[]` 表示清空该条要求下的全部明细。前端编辑页必须把保留行的 `id` 原样回传，只提交增量会导致其余明细被删掉。

> [!IMPORTANT] **[卡点 3：ABP 软删除不级联，子表必须显式删]** `AbpDbContext` 在 `SaveChanges` 前会把 `ISoftDelete` 主表的 `EntityState` 从 `Deleted` 改回 `Modified`，等 EF 执行级联时主表已不是删除态，**子表一条都不会被删**（即使外键配了 `Cascade`）。因此 `DeleteAsync` 在软删主表之前用带谓词的批量删除显式清理明细。

> [!IMPORTANT] **[卡点 4：监装单上线后必须补删除引用校验]** 现阶段没有任何业务表引用 `LoadingRequirement.Id` 或 `LoadingRequirementItem.Id`，所以 `DeleteAsync` 没有引用校验、`EditAsync` 删明细也没有引用校验。 **监装单一旦开始存监装要求 id，必须同时补两处**： `DeleteAsync` 里加「已被【监装单】引用,禁止删除」， `EditAsync` 的删除段加待删明细的引用校验。否则监装单上的 id 会指向已软删数据，界面表现为「要求凭空消失」。

> [!IMPORTANT] **[卡点 5：两层重名校验的口径不同]** **主表要求名**：同租户下唯一。`AddAsync` / `EditAsync` 都会查库（`ValidateDuplicateNameAsync`），去首尾空格、大小写不敏感（两边 `ToUpper()` 比较）、**已软删除的记录不参与**、编辑时按 id 排除自身。重名报 `监装要求名【xxx】已存在`。
>
> **子表明细名称**：同一条监装要求下唯一，但校验是**在提交的数组内做的，不查库** （`ValidateItemInputs`，去空格 + 大小写不敏感）。这不是偷懒——子表是全量提交，编辑完成后该主表下的明细**就等于本次提交的数组**，所以「数组内不重复」与「同主表下不重复」是等价的，再查一次库纯属多余。重名报 `监装要求明细名称【xxx】重复`。
>
> 跨主表不查重：两条不同的监装要求下面可以有同名明细（比如都有「装完贴封条并拍照」），这是预期行为。
>
> **后续若新增「单独增删一条明细」的接口，上面这个等价关系就不成立了**，那种接口必须自己查库校验同主表下重名。

# 9. 避坑指南 (Pitfalls)

- **两个 SortId 语义不同**：主表前端传，子表后端生成。见第 2.1 节表格。
- **子表全量提交**：前端必须回传保留行的 `id`，只提交增量会导致其余明细被删除。
- **列表默认排序不是创建时间倒序**：`LoadingRequirementQueryDto` 在构造函数里把基类的 `Sorting` 默认值从 `CreationTime DESC` 改成了 `SortId ASC`，因为主表排序就是给前端排的。前端显式传 `sorting` 仍然生效。
- **软删除不级联**：新增任何 `LoadingRequirement` 子表都要在 `DeleteAsync` 里补显式批量删除。
- **局部更新不要调 `UpdateAsync`**：`EditAsync` 用的是局部赋值 + `CurrentUnitOfWork.SaveChangesAsync()`，本项目 ABP 的 `Update` 会把整行标记 `Modified` 产生全列 UPDATE，后续维护不要加回来。
- **明细 id 不能重复提交**：同一数组里出现两条相同 `id`，后一条会静默覆盖前一条，已加 `监装要求明细id重复` 拦截。
- **明细 id 必须属于当前主表**：传了不属于本条要求的 `id` 报 `输入监装要求明细id错误`，整个编辑回滚。
- **删除引用校验待补**：见第 5 节卡点 4，这是监装单开发时最容易漏的一步。
- **重名校验一个查库一个不查库**：主表要求名查库（同租户唯一），子表明细名只在提交数组内查。原因和边界见第 5 节卡点 5，**新增单条明细的接口时必须自己补查库校验**。
- **重名校验绕不过软删除**：`GetAll()` 走的是 ABP 软删除过滤，已删掉的同名要求不算重复，也就是说删掉一条「标准整箱监装要求」之后可以再建一条同名的，库里会同时存在两行（一行 `IsDeleted=1`）。
- **`LoadingRequirementSimpleDto` 目前没人用**：它是为监装单预留的外键出参对象（按项目约定外键要返回对象不平铺）。监装单开发时直接用它，不要再新建一个平铺的 `loadingRequirementId + loadingRequirementName`。
- **命名可改**：主子表和路由都用了 `LoadingRequirement` 前缀（与用户属性 `UserAttribute.LoadingSupervision` 同族，所有监装相关表都会是 `App_Loading*`）。**前端一旦按 `/LoadingRequirementAdmin/...` 接完就不好改了**，要换名字（比如 `SupervisionRequirement`）请在联调前提。
