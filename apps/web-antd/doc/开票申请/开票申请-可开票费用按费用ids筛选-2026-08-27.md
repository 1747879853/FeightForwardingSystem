# 1. 背景意图 (Background)

新建开票申请的流程是「先拉可开票费用列表 → 勾选费用 → 生成申请」。前端在别处（业务费用列表、客户对账详情等）已经拿到一批费用 id 后，没办法只用这些 id 把对应的可开票费用明细捞回来，只能带着其它业务条件重新翻页去找。

本次给拉取接口加一个费用 id 集合筛选条件，前端拿着已选中的费用 id 直接回捞明细即可，**不新增任何生成申请的接口**。

# 2. 核心逻辑变更 (Core Logic)

## 2.1 影响接口

| 接口 | 地址 |
| :-- | :-- |
| 拉取剩余未开票金额>0的费用（按业务分组） | `GET /api/services/app/InvoiceApplicationAdmin/GetOrderFeeGroupAsync` |

## 2.2 入参新增

| DTO | 字段 | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| `InvoiceApplicationFeeQueryDto` | `OrderFeeIds` | `List<Guid>` | 费用 id 集合，可空；只返回这些费用。不传时行为完全不变 |

GET 传数组须**重复键名**：`?orderFeeIds=guid1&orderFeeIds=guid2`。

## 2.3 过滤实现

条件挂在与其它业务字段同一条 `WhereIf` 链的最前面，与既有条件是**与**关系：

```csharp
.WhereIf(input.OrderFeeIds != null && input.OrderFeeIds.Count > 0, x => input.OrderFeeIds.Contains(x.Id))
```

判空沿用本仓库 `FeeCodeIds` 的 `!= null && Count > 0` 写法，空集合等价于不筛选。

分组明细与分页键都取自同一个 `feeQuery`（分页取 `feeQuery` 里的 `TransportOrderId` 去重，明细再从 `feeQuery` 捞回），所以 id 筛选会**同时**收窄「返回哪些业务分组」和「每个分组里返回哪些费用」，不会出现「分组被筛了、组内费用还是全量」的错位。

# 3. 避坑指南 (Pitfalls)

- **返回条数不一定等于传入条数，前端必须以返回结果为准。** 本接口的固定条件照旧全部生效：费用必须 `FeeStatus=Passed`、`InvoiceBlocked=false`、无审核中的申请修改/申请删除任务、剩余可开票额度（`Amount - 已申请额度`）大于 0，另外还要过数据权限。任何一条不满足，传了 id 也不会返回。典型场景是这条费用刚被别人开票申请占掉了额度。
- **默认只回一页，跨业务多选时极易踩坑。** 分页单位是**业务（TransportOrder）**，`PageSize` 默认 **10**。选中的费用若分布在 10 票以上的业务上，默认参数下只会返回前 10 票的费用。回捞时请把 `pageSize` 放大（上限 100000）或按 `totalCount` 翻页，**不要**沿用列表页的默认分页参数。
- **同时传 `invoiceApplicationId` 会再挖掉一批。** 编辑场景下该参数会排除「已经挂在这张开票申请上的费用」，与 id 筛选叠加后可能一条都不剩，这是预期行为。
- **id 筛选与其它筛选是「与」关系。** 又传 `settlementId`/`currencyId`/`paySide` 时，两边都要命中才返回，别指望 id 能绕过它们。
- 软删除的费用由 ABP 全局查询筛选器自动排除，不需要也不应手写 `IsDeleted` 判断。
- 本接口的费用**收付都返回**（支持收付互抵，总额=收−付），所以传混了应付费用的 id 也会照样返回应付费用；要只看应收请自行再传 `paySide=0`。
