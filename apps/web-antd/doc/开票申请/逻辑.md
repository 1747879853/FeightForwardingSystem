# 开票申请模块 - 逻辑说明与坑点分析

> 本文档面向前端、后端、测试人员及AI辅助开发，详细说明开票申请模块的核心业务逻辑、数据流转、并发控制、以及各端需要注意的坑点。

---

## 一、核心数据模型

### 表关系

```
InvoiceApplication (主表, CurrencyId=主币别)
├── InvoiceApplicationItem (费用明细, 1:N, AppliedAmount 为费用原币)
│   └── OrderFee (费用, N:1, 币别可与主币别不同)
│       └── TransportOrder (业务, N:1)
│           └── SeaExport (海运出口, 1:1, 共享PK；接口返回在 transportOrder.seaExport)
├── InvoiceApplicationExchangeRate (汇率, 1:N, 明细里出现的每个费用币别一行, 主币别=1)
├── InvoiceApplicationMailRecipient (邮件收件人/抄送人, 1:N, 名字+邮箱, 2026-10-03)
└── InvoiceApplicationGoodsDtl (商品明细, 1:N)
    └── CodeInvoice (发票商品编码, N:1)
```

### InvoiceApplication 邮件收件人（2026-10-03）

开票申请可以带多个收件人、多个抄送人，每个是「名字 + 邮箱」。用途：新建发票开出时，前端把所选开票申请的收件人合并、去重后带到发票开出上，用户可以再改；按邮件模板给发票开出生成邮件时，发票开出上有收件人就直接用（见 `文档/邮件模板/邮件模板模块总逻辑文档.md`）。

| 字段 | 含义 | 校验 |
| --- | --- | --- |
| `RecipientType` | 0 收件人 / 1 抄送人 | 必须是已定义的值 |
| `Name` | 名字 | 可空，去首尾空格，最长 64 |
| `Email` | 邮箱 | 必填，去首尾空格，只收纯地址，最长 256；同一类型里不能重复（不区分大小写） |
| `SortId` | 排序 | 按提交顺序生成 |

- 新增：根层一份，按币别生成的每张申请各存一份。按对账单新建不带。
- 编辑（`EditAsync` / `EditMainAsync`）：不传不改，传了整份替换（删了重建），空数组清空；和其它字段一样只有录入、驳回状态能改。
- 删除：随开票申请一起删。
- 详情返回，列表不返回；发票开出选开票申请的列表（`GetSubmittedApplicationListAsync`）也返回。

> **接口约定**：`GetOrderFeeGroupAsync` / `DetailAsync.feeGroups` 的海运出口均在 `transportOrder.seaExport`，分组 DTO 根上无独立 `seaExport`。

### InvoiceApplication 银行字段

| 字段 | 类型 | 含义 | 校验时机 |
| --- | --- | --- | --- |
| `OrgBankAccountId` | `Guid?` | 我司银行ID | 新增/编辑可空，未传不校验；**提交审核必填** |
| `ClientInvoiceBankId` | `Guid?` | 客户银行ID | 新增/编辑可空，未传不校验；**提交审核必填** |

> 新增时不再自动取默认银行；传值时才校验我司银行归属公司、客户银行归属结算对象。

### InvoiceApplication 审核追踪字段

| 字段           | 类型        | 含义     | 设置时机       |
| -------------- | ----------- | -------- | -------------- |
| `RejectUserId` | `long?`     | 驳回人ID | 审核驳回时设置 |
| `RejectTime`   | `DateTime?` | 驳回时间 | 审核驳回时设置 |
| `RejectReason` | `string`    | 驳回原因 | 审核驳回时设置 |

> 审核**只支持驳回**，故已移除「通过人(`ApproveUserId`)」「通过时间(`ApproveTime`)」字段。详情/列表接口会额外返回 `RejectUserNickName`（来自 `User.NickName`）

### InvoiceApplication 发票类型字段

| 字段 | 类型 | 含义 | 取值 |
| --- | --- | --- | --- |
| `InvoiceType` | `string` | 发票类型 | p=普通发票(电票)(默认)，c=普通发票(纸票)，s=专用发票 |

> 新增时由每个币别分组（CurrencyGroup）各自传入；修改接口（单条）由 InvoiceApplicationEditDto.InvoiceType 传入；详情/列表接口返回 InvoiceType 字段。

### 列表结算状态汇总（不落库）

`GetPagedListAsync` 每条返回 `SettlementStatus`，按该申请 `InvoiceApplicationItems` 关联费用的 `OrderFee.SettlementStatus` 聚合（与客户对账列表同一套 `CombinedFeeStatusHelper.ComputeSettlementStatusForFees`）：

| 值  | 含义                                                 |
| --- | ---------------------------------------------------- |
| 0   | 关联费用全部未结算（无关联费用时也返回 0）           |
| 1   | 部分结算（有的结完有的没结，或费用自身就是部分结算） |
| 2   | 关联费用全部结算完毕                                 |

详情 `DetailAsync` 不返回该字段。

### 关键字段（OrderFee表）

| 字段 | 含义 | 说明 |
| --- | --- | --- |
| ~~`InvoicedAmount`~~ | ~~已开票金额~~ | **已删除**，通过关联 InvoiceApplicationItem 动态计算 |
| ~~`OrderInvoiceAmount`~~ | ~~开票申请中的金额~~ | **已删除**，同上 |
| `InvoiceStatus` | 开票状态(NotIssued/PartiallyIssued/Issued) | 保留，采用冗余字段回写；由"发票开出"在申请状态切换到/离开 `Invoiced` 时重算回写（详见 `文档/发票开出/发票开出-费用开票状态回写-2026-07-18.md`） |
| `InvoiceBlocked` | 是否禁开发票 | 手动控制 |

### 核心公式

```
已开票金额(InvoicedAmount) = Sum(InvoiceApplicationItem.AppliedAmount) WHERE InvoiceApplication.Status = Invoiced(3)
发票申请金额(OrderInvoiceAmount) = Sum(InvoiceApplicationItem.AppliedAmount)  -- 包含所有状态，不区分是否审核通过
未开票金额(UnInvoicedAmount) = Amount - InvoicedAmount
剩余可开票金额(RemainingInvoiceAmount) = Amount - OrderInvoiceAmount

其中:
- Amount: 费用总金额（不变）
- InvoicedAmount: 仅统计审核通过(Status=Invoiced)的开票申请明细之和
- OrderInvoiceAmount: 所有状态的开票申请明细之和（录入、待审核、驳回、已开票全部计入）
```

> **重要变更说明**：
>
> - `InvoicedAmount` 和 `OrderInvoiceAmount` 已从 OrderFee 实体中移除（数据库字段保留但代码不再使用）
> - 两个金额均通过 JOIN `InvoiceApplicationItem` 表计算：
>   - `InvoicedAmount`：仅统计 `InvoiceApplication.Status = Invoiced` 的记录
>   - `OrderInvoiceAmount`：统计所有状态的记录（就算没审核通过也统计）
> - 新建/修改/删除/审核开票申请时，不再需要更新 OrderFee 表的任何金额字段
> - **费用删除校验**：删除 OrderFee 时，如果该费用已关联了 InvoiceApplicationItem，则禁止删除

### 冲红下限（2026-10-02 补一条）

单条明细 `AppliedAmount` 可以为负（冲红），但该费用的开票申请合计（全部状态）有两条下限：

```
其他开票申请合计 + 本次金额 ≥ 0                      -- 原规则：不能冲红超过已占用额度
其他开票申请合计 + 本次金额 ≥ 已按发票收费结算        -- 2026-10-02 新增
```

- **为什么加第二条**：按费用收费结算、付费申请扣的是开票申请合计，不扣按发票收费结算。开票申请合计被冲到按发票已结以下，差出来的额度就会被它们再放出来，同一笔钱结两次。详见 `文档/收费结算/收费结算模块总逻辑文档.md` 卡点 15。
- 已按发票结算额只认 `ReceiveSettlementInvoiceItem`，按费用收费结算不算在内。所以**只按费用结算过的费用不受影响**：这时第二条就是 0，和原规则一样；上限也从来不扣收费结算，先按费用结算、再开票申请照常能开。
- 新增、编辑、追加明细都校验这两条，报错分别是「费用冲红额度不足,最小可用额度:xxx」和「费用已按发票收费结算xxx,开票申请合计不能少于该金额,最小可用额度:xxx,请先删除对应的收费结算明细」。
- 编辑时去掉的费用、移除明细、删除申请会让合计变小，也要守第二条（只查已按发票结算过的费用），报「费用已按发票收费结算xxx,移除后开票申请合计xxx少于该金额,请先删除对应的收费结算明细」。原规则「合计 ≥ 0」在移除时仍不查，与以前一致。
- 已按发票结算额统一取 `IOrderFeeInvoicedProvider.GetInvoiceSettledAmountMapAsync`。

### 负数费用（2026-10-02）

客户会录金额为负的费用（折扣、返利等），这类费用可以和正数费用开进同一张申请抵减：**费用明细允许为负，整张申请折成开票申请币别后的合计必须大于 0，商品明细每行金额必须大于 0**。

| 环节 | 规则 |
| :-- | :-- |
| 选费用 `GetOrderFeeGroupAsync` | 剩余可开票金额与费用同号且不为 0 才返回：正数费用 > 0，负数费用 < 0（如 −100 的折扣返回剩余 −100） |
| 申请金额上下限（新增 / 编辑 / 追加明细） | 按费用方向取反后套用正数费用的规则：负数费用可申请到剩余为止（−100 的费用最多填 −100），开票申请合计不能冲成正数，也不能少于已按发票收费结算（比绝对值）。提示里的「最小可用额度」对负数费用显示为「最大可用额度」 |
| 按对账单新建 `AddByStatementAsync` | 负数费用按剩余全额申请（填负数），与正数费用放进同一张申请 |
| 提交 `SubmitAsync` | 新增两条：商品明细每行金额 > 0，否则报「商品明细金额必须大于0」；费用明细折成开票申请币别后的合计 > 0，否则报「费用明细申请金额合计(折成开票申请币别xxx)必须大于0」。商品合计 = 申请合计 × 发票汇率的原校验不变 |

- 方向统一取 `OrderFeeSettlementHelper.FeeSign`（费用金额 < 0 为 −1，否则为 1），收费结算那边同一个口径，见《收费结算模块总逻辑文档》卡点 16。
- 正数费用的规则完全没变；正数费用填负数仍是冲红，受上面「冲红下限」约束。
- 开出的发票上商品合计仍须 > 0（发票开出推诺诺时校验），负数费用只是在费用明细里抵减，不会单独开成负数发票。

## 二、状态流转

```
Entering(录入) ──SubmitAsync──→ Auditing(待审核/已提交即可开票) ──后续开票操作──→ Invoiced(已开票) [终态]
    ↑    ↑                          │
    │    └──────WithdrawAsync───────┤ (撤回到录入)
    │                               │
    └──────AuditAsync(仅驳回)────────┘ Rejected(驳回) → 可修改后重新提交
```

> **审核只驳回**：AuditAsync 只支持驳回有问题的申请，没问题的不处理；已提交（Auditing）即视为可开票。Invoiced 状态由后续的开票操作设置，不再由审核设置。

### 各状态下的操作限制

| 操作       | Entering | Auditing | Rejected | Invoiced |
| ---------- | -------- | -------- | -------- | -------- |
| 修改       | ✅       | ❌       | ✅       | ❌       |
| 删除       | ✅       | ✅       | ✅       | ❌       |
| 审核(驳回) | ❌       | ✅       | ❌       | ❌       |
| 提交审核   | ✅       | ❌       | ✅       | ❌       |
| 撤回       | ❌       | ✅       | ❌       | ❌       |

> **接口说明**：
>
> - `SubmitAsync`：将录入/驳回状态的申请提交到待审核（Entering/Rejected → Auditing）；提交前校验我司银行、客户银行均不可为空
> - `WithdrawAsync`：将待审核状态的申请撤回到录入状态（Auditing → Entering），仅在尚未审核时可撤回
> - 两个接口均使用 `Admin.InvoiceApplication.Edit` 权限

## 三、并发控制机制

### 行级悲观锁（核心防护）

新增和修改开票申请时，为防止并发超额申请，使用 SQL Server 行锁序列化验证：

```sql
SELECT * FROM App_OrderFees WITH (UPDLOCK, ROWLOCK) WHERE Id IN (...)
```

**触发场景**：

1. 新增开票申请 → 锁定所有关联费用行（用于验证剩余额度）
2. 修改开票申请 → 锁定新旧费用的并集（用于验证剩余额度）
3. 删除开票申请、移除明细 → **2026-10-02 起重新加锁**：锁住被移除明细涉及的费用行，再校验移除后合计不低于已按发票收费结算（见「冲红下限」），与收费结算的写入串行
4. ~~审核驳回~~ → **不再需要锁**（无 OrderFee 金额字段需要更新）

**锁内操作顺序**（以新增为例）：

1. 锁定 OrderFee 行
2. 查询当前所有 InvoiceApplicationItem 的 AppliedAmount 总和
3. 验证剩余额度（`Amount - Sum(AppliedAmount) >= 本次申请金额`）
4. 插入新数据
5. 提交事务

> **变更说明**：不再更新 OrderFee 的 `OrderInvoiceAmount` 和 `InvoicedAmount`，行锁仅用于序列化并发验证。

### 为什么需要行锁

同一条费用可能同时被多个用户创建开票申请。如果不加锁，两个请求可能同时读到相同的剩余额度，导致超额开票。

## 四、新建接口的特殊逻辑

### 多币别分组

前端可能一次传入多个币别的费用。后端处理流程：

1. 根据每条费用的 CurrencyId（从 OrderFee 表获取，不是前端传的），按币别分组
2. 每个币别生成一个独立的 InvoiceApplication
3. 每个 InvoiceApplication 有独立的 ApplicationNo、OrgBankAccountId、ClientInvoiceBankId、InvoiceType（发票类型，每个币别各自独立）

### 银行字段（可空，提交审核必填）

- **我司银行 / 客户银行**：新增、编辑均可不传，存 `null`，不自动匹配默认银行
- **传值校验**：我司银行须属于 `orgId` 解析出的所属公司；客户银行须属于结算对象
- **提交审核**：`SubmitAsync` 强制两字段均有值，否则禁止进入待审核

### 多币别费用与汇率（2026-09-26）

分组币别就是开票申请的**主币别**（发票开出按主币别合并申请），分组里的费用可以是别的币别：

- 费用明细 `AppliedAmount` 永远是**费用自己的原币**，额度校验（剩余可开票额度、冲红下界）也全按原币，与改版前一致；负数费用按方向取反后比较（见一节「负数费用」）
- 明细里与主币别不同的**每个费用币别**都要一条汇率（1 单位费用币别折合多少主币别，大于 0，六位小数）；主币别恒为 1
- 汇率在新增、编辑、编辑主表、追加费用明细时就校验，缺了报「币别[xxx]与开票申请币别不同,汇率必填且必须大于0」；解析顺序为「入参 → 单上已有 → 报错」，入参里明细没有的币别忽略
- 汇率行按「明细里出现的币别」对齐：新币别新增、已有币别改值、不再出现的币别删除（删费用明细时也会顺带删）

**折算公式**（唯一实现 `InvoiceApplicationAmountRule.ToApplicationCurrency`，开票申请与发票开出共用）：

```
申请总额(主币别) = Σ_币别 round(Σ 该币别 AppliedAmount × 该币别汇率, 2, AwayFromZero)
                  其中主币别不乘汇率(即使没有汇率行也按 1)；任一非主币别缺汇率 → 结果为 null
```

先按币别合计再乘汇率，而不是逐条乘，这样同一个币别只舍入一次，前端「原币合计 × 汇率」能与后端对上。

### 商品明细与费用明细的金额校验

- 新增/编辑/追加/删明细都**不校验**，提交审核时统一校验
- 提交时：`Σ GoodsDtl.Amount` 必须等于 `round(申请总额(主币别) × 发票汇率, 2)`，发票汇率取主币别在 `ExchangeRate` 表的 `InvoiceValue`（对人民币）

## 五、修改接口的特殊逻辑

### 全量替换

修改时，费用明细和商品明细采用**全量替换**策略：

1. 先删除旧的 InvoiceApplicationItem 和 InvoiceApplicationGoodsDtl
2. 再插入新的（InvoiceApplicationItem 的变化会自动反映到"已开票金额"的计算中）

### 不可修改字段

- `ApplicationNo`（申请单号，自动生成）
- `InvoiceNo`（发票号，后续开票操作生成）
- `CurrencyId`（主币别，新建时由分组币别决定；改了会让已挂的发票开出和汇率全部失真）

### 驳回后修改

驳回状态的申请修改后，状态自动回到 Entering（录入），需要重新提交审核。

## 六、审核（仅驳回）的记录

### 审核只支持驳回

- `AuditAsync` 只支持驳回，不支持审核通过
- 设计理念：只要是已提交（Auditing）的申请即可开票；审核时只驳回有错误的，没问题的不处理
- `Invoiced` 状态由后续的开票操作设置，不再由审核设置

### 审核驳回

驳回后的数据变更：

1. `InvoiceApplication.Status` → `Rejected`
2. `InvoiceApplication.RejectUserId` = 当前操作人
3. `InvoiceApplication.RejectTime` = 当前时间
4. `InvoiceApplication.RejectReason` = 驳回原因（必填）

> 驳回后用户可以修改后重新提交。

### 详情/列表返回审核人信息

- 详情接口和列表接口返回 `RejectUserNickName`（驳回人昵称）
- 昵称取自 `User.NickName` 字段

## 七、前端注意事项

### 7.1 新建页面

1. **币别分组**：每个分组生成一张开票申请，分组币别就是主币别；分组里可以放别的币别的费用，但每个非主币别都要让用户填汇率（`invoiceApplicationExchangeRates`）
2. **银行选择**：
   - 先选归属组织 → 加载组织下的银行列表 → 默认选该币别的默认银行
   - 先选结算对象 → 加载客户开票信息 → 默认选该币别的默认银行
3. **金额校验**：每条费用的申请金额（原币）不能超过 `remainingInvoiceAmount`（从 GetOrderFeeGroupAsync 返回）
4. **商品明细金额校验**：商品明细的 Amount 合计须等于 `round(折成主币别的申请总额 × 发票汇率, 2)`，后端提交时校验
5. **重复费用检查**：同一条费用不能在一次申请中出现两次

### 7.2 编辑页面

1. 调用详情接口获取数据时，`remainingInvoiceAmount` 已排除本条申请的占用额度
2. 调用拉取费用接口时，传入 `invoiceApplicationId` 可以排除本条申请已关联的费用
3. 不要修改 ApplicationNo / InvoiceNo / CurrencyId
4. 只有 Entering / Rejected 状态的申请才能编辑

### 7.3 列表页面

1. 分页参数是 `pageIndex`（从1开始）和 `pageSize`，不是 skipCount
2. 费用拉取接口的分页也是按 TransportOrder 分页，不是按费用条数分页
3. `totalAppliedAmount` 和 `itemCount` 是后端计算好的，不需要前端二次计算；`totalAppliedAmount` 已折成主币别，缺汇率（历史数据）时为 `null`
4. `settlementStatus` 是本申请关联费用结算状态的汇总，不是开票申请自己的列：全部未结算=`0`，全部结算完毕=`2`，其余（含费用自身为部分结算）=`1`；无关联费用时为 `0`。详情接口不返回该字段

### 7.4 审核

1. 通过后不可撤销
2. 驳回必须填写驳回原因

## 八、后端注意事项

### 8.1 行锁范围

新增和修改操作时，需要锁定相关 OrderFee 行来序列化并发验证。修改操作时，必须锁定新旧费用的**并集**（`newOrderFeeIds.Union(oldOrderFeeIds)`），确保验证的原子性。

> **变更说明**：行锁不再用于更新 OrderFee 金额字段，仅用于防止并发验证通过后超额申请。删除和审核操作不再需要行锁。

### 8.2 已开票金额 vs 发票申请金额

两个金额均不再存储在 OrderFee 表中，通过关联 InvoiceApplicationItem 动态计算：

```csharp
// 已开票金额 = 仅统计已开票状态的申请
var invoicedAmount = InvoiceApplicationItems
    .Where(x => x.OrderFeeId == fee.Id && x.InvoiceApplication.Status == InvoiceApplicationStatus.Invoiced)
    .Sum(x => x.AppliedAmount);

// 发票申请金额 = 统计所有状态的申请（录入、待审核、驳回、已开票）
var orderInvoiceAmount = InvoiceApplicationItems
    .Where(x => x.OrderFeeId == fee.Id)
    .Sum(x => x.AppliedAmount);

// 未开票金额 = 费用总额 - 已开票金额
var unInvoicedAmount = fee.Amount - invoicedAmount;

// 剩余可开票金额 = 费用总额 - 发票申请金额（用于新建/修改验证，防止超额）
var remainingInvoiceAmount = fee.Amount - orderInvoiceAmount;
```

各 AppService 中的实现方式：

- **InvoiceApplicationAdminAppService**：通过 `.Include(x => x.InvoiceApplicationItems).ThenInclude(x => x.InvoiceApplication)` 加载导航属性
- **OrderFeeAdminAppService**：通过 `.Include(x => x.InvoiceApplicationItems).ThenInclude(x => x.InvoiceApplication)` 加载导航属性
- **其他 AppService**（SeaExport、ChangeOrder 等）：通过批量查询 `_invoiceApplicationItemRepository` + `x.InvoiceApplication.Status` 构建两个字典

### 8.3 数据一致性

- 新增/修改/删除/审核开票申请时，**不再更新** OrderFee 的任何金额字段
- InvoiceApplicationItem 的增删即为"金额"变更的唯一来源
- 并发控制通过行锁 + InvoiceApplicationItem 求和验证实现

### 8.4 费用删除校验

删除 OrderFee 时，如果该费用已关联了 InvoiceApplicationItem，则禁止删除，提示"已关联开票申请的费用不可删除"。

### 8.5 费用查询的过滤条件

拉取可开票费用时的过滤条件：

- 不限制收付类型（收付均可，支持互抵，总额=收-付）
- `InvoiceBlocked == false`
- `FeeStatus == Passed`（审核通过）
- `Amount - Sum(InvoiceApplicationItems.AppliedAmount) > 0`（剩余可开票金额大于0，此处用所有状态的发票申请金额）

### 8.5 GenerateNum 配置

需要确保 GenerateNum 表中存在 `TableName = "InvoiceApplication.ApplicationNo"` 的编号规则，否则新建时会报错。

### 8.6 发票汇率

发票汇率从 `ExchangeRate` 表的 `InvoiceValue` 字段获取，查询条件：

- `CurrencyId` 与开票申请的币别一致
- `LocalCurrency = 'RMB'`（系统开的发票都是人民币发票，本位币固定为 RMB）
- `Enable = true`
- `StartDate <= 当前时间 <= EndDate`
- `InvoiceValue IS NOT NULL`

**新建/修改时验证**：如果对应币别在当前时间没有有效的发票汇率，抛出错误"未维护xxx币种的发票汇率，请先维护"。

**详情/列表接口**：返回 `invoiceExchangeRate` 字段，取当前时间有效的发票汇率值。如果不存在则返回 `null`。

## 九、测试注意事项

### 9.1 并发测试

1. **同一费用并发申请**：两个用户同时对同一条费用创建开票申请，验证只有一个成功或两个都成功但总额不超限
2. **申请和修改并发**：用户A修改申请，用户B对同一费用创建新申请
3. **申请和审核并发**：用户A修改申请，用户B审核另一条包含相同费用的申请
4. **申请和删除并发**：同上

### 9.2 金额边界测试

1. 申请金额 = 剩余可开票金额（刚好用完）
2. 申请金额 > 剩余可开票金额（应该报错）
3. 负数申请金额（冲红场景，且绝对值不得超过当前已占用额度）3.1 费用已按发票收费结算 100：开负数申请、改小金额、移除明细、删除申请，使开票申请合计低于 100 → 应报错；先删掉收费结算明细后再操作 → 应成功 3.2 费用只按费用收费结算过（没有按发票结算）：开票、开负数申请、删除申请的行为与改版前一致 3.3 负数费用 −100：选费用列表能看到（剩余 −100）；填 −100 成功，填 −150 报额度不足，填 +10 报冲红额度不足；与一条 +500 的费用放进同一张申请，商品明细 400（×汇率）可提交 3.4 申请里只有负数费用、或负数抵减后合计 ≤ 0：提交报「费用明细申请金额合计…必须大于0」；商品明细有一行 ≤ 0：提交报「商品明细金额必须大于0」
4. 多条申请累计刚好等于费用总金额
5. 已开票金额 + 申请金额 = 总金额（完全开票）

### 9.3 多币别测试

1. 一次提交包含2个币别的费用 → 应生成2个InvoiceApplication
2. 验证每个申请的银行匹配是否正确
3. 验证商品明细按币别正确分配

### 9.4 状态流转测试

1. 录入 → 修改 → 提交 → 验证已提交(Auditing)状态不可修改/删除
2. 录入 → 提交 → 驳回 → 修改 → 重新提交
3. 驳回后修改，状态是否自动回到 Entering
4. 已开票申请删除应报错

### 9.5 外键验证测试

1. 传入不存在的 SettlementId → 应报错
2. 传入非数据所属人本人直属组织的 OrgId → 应报错
3. 传入不属于所选归属组织的银行 → 应报错
4. 传入不属于所选客户的开票银行 → 应报错

### 9.6 数据一致性测试

1. 删除申请后，该费用的已开票金额（通过 InvoiceApplicationItem 计算）是否正确减少
2. 修改申请后，旧费用和新费用的已开票金额是否正确反映变更
3. 开票操作后状态变为 Invoiced，已开票金额（InvoicedAmount）应包含该申请的明细
4. 查询费用时，OrderInvoiceAmount 是否包含所有状态的开票申请（包括未开票的）
