# 1. 背景意图 (Background)

**白话解释：** 云当的「推送运单动态接口」需要我们提供**一个固定的回调地址**接收推送；但本系统**部署在多台服务器**上，无法用同一个地址接收。同时同一个云当账号在多台服务器各自换取 token 存在**相互顶号**风险。

为此新增一个独立可发布的 **中转站(Relay)** 项目，职责：

1. **统一换取并缓存云当 token**：各业务服务器不再保存云当密钥，改为向中转站获取 token（含 companyCode/orgCode）。
2. **统一接收云当推送**：云当只需推送到中转站的一个固定地址；中转站按每条推送里的 `customer` **精准路由**到对应业务服务器。
3. **全局通用密钥**：所有业务服务器共用同一个 `X-Relay-Token`（= 中转站 `Relay:AccessToken`），取 token 与接收推送均用它校验来源；**不区分服务器、不区分IP**。`customer` 在业务端 `appsettings` 配置。
4. **预留扩展**：平台无关设计，`{provider}` 作为渠道标识，将来对接其它平台只需在中转站配置中新增节点。

对接文档：

- 获取Token：<https://trackingeyes-cn.apifox.cn/api-221743604>
- 推送运单动态：<https://trackingeyes-cn.apifox.cn/api-221743609>

# 2. 架构与数据流

```
业务服务器 ──取token(头 X-Relay-Token=全局通用密钥)──▶ 中转站 /relay/yundang/token ──▶ {token, params:{companyCode,orgCode}}
业务服务器 ──订阅(companyCode+token+orgCode, body带Relay:Customer)──▶ 云当 api.trackingeyes.com
云当 ──推送(单一地址, 回传customer)──▶ 中转站 /relay/yundang/push ──按customer路由(带本下游密钥)──▶ 对应业务服务器 /api/yundang/push
```

# 3. 中转站项目 (src/Freight.Relay，.NET 8，独立发布)

| 文件 | 说明 |
| :-- | :-- |
| `Program.cs` | 最小宿主：注册控制器、HttpClient、`RelayOptions`、`ITokenService`、`IPushForwarder` |
| `Options/RelayOptions.cs` | 配置模型：`AccessToken`(全局通用密钥)、`Providers`(各平台)、`Downstreams`(下游业务服务器，含 `Customer`/`BaseUrl`) |
| `Services/TokenService.cs` | 通用 token 换取+进程内缓存(按 TTL)；按配置 URL/请求体调用，按点分路径提取 token |
| `Services/TokenRefreshHostedService.cs` | 后台托管服务：**启动即刷新**各平台 token，之后**每个平台按各自** `RefreshIntervalMinutes`/`RetryIntervalMinutes` 独立调度强制刷新，保证缓存始终新鲜 |
| `Services/PushForwarder.cs` | 按推送中 `customer` 拆分并路由到对应下游(单个失败不影响其它，不抛异常) |
| `Controllers/RelayController.cs` | `GET /relay/{provider}/token`(通用，按密钥识别)、`POST /relay/yundang/push`(**云当专用**，推送非通用)、`GET /health` |
| `appsettings.json` | 云当密钥与下游地址/密钥配置(**云当密钥只存在这里**) |

**中转站配置要点(`Relay` 节点)：**

- `AccessToken`：全局通用密钥，所有业务服务器共用；业务端 `Relay:Token` 须与之一致。取 token 与转发推送均用它校验，**不区分服务器/不区分IP**。
- **每平台的 token 三项时间(均在各平台节点内配置，中转站启动即刷新，之后各平台独立调度)：**
  - `TokenTtlMinutes`：token 有效期(分钟)。用于计算过期时间(`ExpireTime = 刷新时间 + 本值`)，应略小于平台实际有效期(云当2小时)。
  - `RefreshIntervalMinutes`：**成功后**刷新间隔(分钟，默认30)。上次刷新成功后间隔本值再刷；应小于 `TokenTtlMinutes` 以保证始终新鲜；≤0 则该平台不再定时刷新。
  - `RetryIntervalMinutes`：**失败后**刷新间隔(分钟，默认1)。刷新失败后间隔本值尽快重试。
- `Providers.yundang.TokenRequestBody`：`companyCode`/`secret`(云当密钥)；`Extra.orgCode`、`CustomerField`(默认 `customer`)。
- `Providers.yundang.LogFolder`：该平台在 `Logs` 下的子文件夹名，云当=`云当`、飞驼=`飞驼`；token→`Logs/{LogFolder}/token`，云当海运推送→`Logs/{LogFolder}/海运推送`。
- `Providers.yundang.ForwardPath`：`/api/yundang/push`(下游业务服务器接收路径)。
- `Providers.yundang.PushAllowedIps`：**该平台自己的**来源IP白名单(放在各平台节点内，不放在 `Relay` 顶层)，推送入口 `/relay/yundang/push` **仅接受这些IP**(云当为 `47.76.250.177`)。非白名单来源视为恶意推送，记录IP+内容到日志后返回 403。为空表示不校验(不建议)。若中转站部署在反向代理(Nginx等)之后，需确保代理透传 `X-Forwarded-For`。
- **云当推送地址须为纯 URL，不能带 Query 参数**（如云当不接受 `?key=`）。
- `Downstreams[]`：每台业务服务器一项 — `Customer`(客户标识,须与业务端 `Relay:Customer` 一致,用于推送路由)、`BaseUrl`(转发目标)、`Enabled`。

**推送应答**：中转站按云当要求返回 `{code:200,type:"S",message:null,time}`，即使下游全部失败也返回成功，避免云当反复重推(下游转发失败有日志)。

**本地日志(Serilog，按天滚动，均在程序运行目录 `AppContext.BaseDirectory` 下，发布后自动创建)——按类别分目录：**

| 日志类别 | 文件路径 | 说明 |
| :-- | :-- | :-- |
| 系统运行日志 | `Logs/relay-yyyyMMdd.log` | 中转站框架/系统级日志(保留31天) |
| 云当 token 刷新 | `Logs/云当/token/token-yyyyMMdd.log` | 后台刷新记录(刷新时间/本次token/有效期/下次刷新，保留90天) |
| **云当海运推送** | `Logs/云当/海运推送/push-yyyyMMdd.log` | 本节下述推送全过程(保留90天；后期空运用 `Logs/云当/空运推送/`) |
| 飞驼 token 刷新 | `Logs/飞驼/token/token-yyyyMMdd.log` | 飞驼后台刷新记录 |

其中**云当海运推送日志** `Logs/云当/海运推送/push-yyyyMMdd.log` 完整记录一次推送：

- `[恶意推送-已拒绝]`：非白名单IP的推送，记录来源IP与完整报文，随后返回 403；
- `[收到推送]`：平台/来源IP/长度/原始报文；
- `[转发请求]`：每个下游的 URL 与发出的报文；
- `[转发返回]`：每个下游的 HTTP 状态码与返回内容；
- `[转发完成]`/`[应答平台]`：转发成功数与返回给云当的应答。

> 平台子文件夹由各平台配置项 `Relay:Providers:{平台}:LogFolder` 决定(云当=`云当`、飞驼=`飞驼`)，统一位于 `Logs/` 下；token 固定归到 `Logs/{LogFolder}/token`，云当海运推送归到 `Logs/{LogFolder}/海运推送`。

**推送接收关键点：**

- 控制器匿名(`[AllowAnonymous]`)，仅凭 `X-Relay-Token` 与 `Relay:Token` 比对校验来源。
- **原始数据必存**：无论是否匹配订阅、解析是否成功，都先把完整原始报文写入 `App_YundangPushLogs`，便于回溯排查。
- **成功即全量解析**：一条运单有 `id`(云当订阅Id)或 `referenceNo` 即视为有效，解析全部字段写入运单动态主表及各子表。
- **二次推送策略(全量更新)**：主表按 `YundangId` 定位同一条，**标量整表覆盖**；子表(集装箱/箱轨迹/航段/海运节点)**删旧建新**，完全以最新推送为准。适用于云当每次推送均为完整快照的场景。原始报文每次推送都新增一行(`App_YundangPushLogs`)完整保留历史，用于回溯。
- 处理时**关闭租户过滤**(`DisableFilter(MayHaveTenant, MustHaveTenant)`)，以便跨租户按云当订阅Id/本地键定位记录；解析表本身不做租户隔离(全局)，命中订阅时冗余 `TenantId`/`SeaExportId`。
- 单条运单处理异常不影响其它条(计入 `FailedCount` 并记录到日志 `Remark`)。

# 5. 避坑指南 (Blockers)

> [!IMPORTANT]
>
> 1. **云当密钥只配置在中转站** `Relay:Providers:yundang`；每台业务服务器配 `Relay:BaseUrl`、`Relay:Token`(= 中转站 `Relay:AccessToken`，**所有服务器同一个**)、`Relay:Customer`(= 中转站该服务器 `Downstreams[].Customer`)。
> 2. **customer 在业务端配置**(`Relay:Customer`)，订阅时上传云当；须与中转站 `Downstreams[].Customer` 一致，推送才能路由到本机。
> 3. **提供给云当的推送地址**是中转站的纯 URL：`POST {中转站}/relay/yundang/push`（**不能带任何 Query 参数**）。
> 4. **下游地址/密钥/customer** 在中转站 `Downstreams` 配置并 `Enabled=true`；转发路径固定 `/api/yundang/push`。
> 5. 业务端接收控制器**匿名**，务必设置并保密 `Relay:Token`(建议再叠加网络层白名单)。
> 6. **可靠性**：当前转发为尽力而为(best-effort)，下游宕机期间的推送会丢失；如需不丢，可后续在中转站增加持久化队列+重试。
> 7. **迁移**：`YundangOceanSubscription` 新增字段(`LatestPushJson`/`LastPushTime`)及新增表(`App_YundangPushLogs`、`App_YundangShipmentDynamics`、`App_YundangShipmentContainers`、`App_YundangShipmentContainerStatuses`、`App_YundangShipmentContainerCharges`、`App_YundangShipmentCarriages`、`App_YundangShipmentOceanNodes`)需自行生成 EF Core 迁移。
> 8. 中转站已加入 `Freight.sln`，但**无任何 ProjectReference**，可单独 `dotnet publish src/Freight.Relay` 独立部署。
> 9. **原始报文的落库必须走独立工作单元，不要退回 `CurrentUnitOfWork.SaveChangesAsync()`**：`ProcessOceanPushAsync` / `ProcessAirPushAsync` 里写 `App_YundangPushLogs` 用的是 `InsertPushLogIndependentlyAsync`（`Scope = RequiresNew` + `IsTransactional = false`），统计回写用 `UpdatePushLogStatsIndependentlyAsync`，两者各自独立提交。早先的写法是先 `InsertAndGetIdAsync` 再 `CurrentUnitOfWork.SaveChangesAsync()`，注释写着「保证即使后续解析异常也不丢原始数据」，但**事务里 `SaveChanges` 只是 flush、不是提交**：后面任何未捕获异常都会让外层事务回滚，原始报文一起没了，等于排查时连报文都看不到。
