# 1. 背景意图 (Background)

**白话解释：** 继海运之后对接云当空运跟踪。操作人员在系统中勾选多票 **空运出口**，把主运单号(AWB)批量提交云当发起货物跟踪订阅；订阅成功后云当会通过**中转站**把运单动态(航班/状态轨迹/空运节点)推送回本系统，解析入库并回写到对应空运出口。

对接接口文档：

- 空运批量运单订阅：`POST https://api.trackingeyes.com/api/airLinesBill/bookAirLines` （<https://trackingeyes-cn.apifox.cn/api-262798596>）
- 空运推送运单动态：<https://trackingeyes-cn.apifox.cn/api-223351055>
- 鉴权(Token)与中转站架构：与海运共用，见《云当对接-中转站与推送接收.md》

# 3. 核心逻辑 (Core Logic)

## 3.1 批量订阅 `BatchSubscribeAirBillAsync`

- 入参：`AirExportIds`(空运出口Id集合)，单次≤30条，超出自动分批。
- 逐票组装订阅明细：
  - `referenceNo` = 主运单号 `TransportOrder.MblNum`(空则该票失败)。
  - `carrierCd` = **留空**，交云当自动识别航司。
  - `extendNo` = 起降机场三字码均有时上传 `{"org": POL.IataCode, "dest": POD.IataCode}`。**厦门航空(MF)订阅必需 org/dest**；因 carrierCd 留空无法预知是否 MF，故只要两个机场三字码都有就一律上传(对其它航司为附加信息)。
  - `customer` = 本机 `Relay:Customer`(推送回程路由用)。
  - `localKey` = 空运出口Id无连字符 + 递增序号。
- 本地校验失败(无主运单号)直接作为失败结果返回，不提交云当；有效明细每30条一批提交。
- 云当返回按上传顺序与请求一一对应；`itemCode=200` 视为订阅成功。
- **云当识别出的航司会回写库中** `CarrierCd`(我方上传空串，返回值即识别结果，如 MF)；我方上传的空串不会覆盖已保存的识别结果。
- 因 `carrierCd` 库中存的是云当识别结果、上传恒为空，**重复订阅校验只比对订阅单号**(比 carrierCd 会永远判定"已变"导致校验失效)。

## 3.2 重新订阅 `ResubscribeAirBillAsync`

- 单条；须已有订阅记录；复用同一 `BuildItem`。
- 单号(referenceNo)与航司(carrierCd)均未变：已成功→禁止；失败且未勾选强制→拦截；失败且强制→允许。
- YundangId 变化时清除原 YundangId 关联的运单动态推送数据。

## 3.3 推送接收 `YundangAirPushController` → `YundangAdminAppService`

- 中转站 `POST /relay/yundang/air/push` → 业务端 `POST /api/yundang/air/push`(匿名，`X-Relay-Token` 校验)。
- **始终记录原始报文**到 `App_YundangPushLogs`(与海运共用，`Remark` 前缀 `[空运]` 区分)。
- 成功运单**全量解析落库**：主表 `YundangAirShipmentDynamic` + 子表 航段/状态轨迹/空运节点，**删旧建新**以最新推送为准。
- 按 `YundangId` 匹配订阅记录，命中则回写：
  - `flightNo` → `AirExport.FlightNo`
  - `etd`/`eta`/`atd` → `TransportOrder.ETD/ETA/ATD`(`ata` 业务表无对应字段，未回写)
  - 回写采用**局部更新**(仅改动列进 UPDATE)。

## 3.4 落库表

| 表 | 说明 |
| :-- | :-- |
| `App_YundangAirSubscriptions` | 空运订阅记录(按 AirExportId 一条)，含请求/返回留痕 `SubscribeRequestJson`/`SubscribeResponseJson` |
| `App_YundangAirShipmentDynamics` | 运单动态解析主表(按 YundangId 唯一) |
| `App_YundangAirShipmentFlights` | 航段(航班) `airFlightInfo` |
| `App_YundangAirShipmentStatuses` | 状态轨迹 `airStatusInfo` |
| `App_YundangAirShipmentNodes` | 空运节点 `airLinesNodes` |

> `deleteStatusInfo` 为云当增量删除标记，本系统全量删旧建新，不入库。

## 3.5 空运出口列表/详情运踪展示

与海运出口同口径，`AirExportAdminAppService` 的 `GetPagedListAsync`/`DetailAsync` 直接返回：

- `IsYundangSubscribed`/`IsYundangSubscribeSuccess`：按 `App_YundangAirSubscriptions` 是否存在记录及其 `IsSuccess` 判定。
- `YundangAirShipmentNode`：按订阅 `YundangId` 关联运单动态，取**最后一个有 `ActualityTime` 的空运节点**(排序：实际时间最晚 → `Sno` → 时间字符串 → Id 倒序)。
- 列表为**批量查询**(一次性取订阅+节点后在内存归组)，避免逐行查库。

## 3.6 字段覆盖核对(对照云当官方示例逐项)

| 报文 | 字段数 | 落库情况 |
| :-- | :-- | :-- |
| 推送主体 | 42 | 全部入 `App_YundangAirShipmentDynamics` |
| 推送 `airFlightInfo[]` | 14 | 全部入 `App_YundangAirShipmentFlights` |
| 推送 `airStatusInfo[]` | 17 | 全部入 `App_YundangAirShipmentStatuses` |
| 推送 `airLinesNodes[]` | 11 | 全部入 `App_YundangAirShipmentNodes` |
| 推送 `deleteStatusInfo[]` | — | **有意不入库**(增量删除标记，本系统全量删旧建新) |
| 订阅返回 `result[]` | 14 | `id`/`itemCode`/`itemCodeDesc`/`itemMessage`/`billCreateTime`/`carrierCd`/`referenceNo`/`localKey` 落列；`deliveryNo`/`orderNo`/`customer`/`customerService`/`remark` 我方从不上传(返回恒为空回显)，不单独建列，完整报文存 `SubscribeResponseJson` |
| 订阅返回批次级 `code`/`codeDesc`/`message` | 3 | 批次级非单票信息，不落单票列；失败原因已写入 `ItemMessage` |

# 4. 避坑指南 (Blockers)

> [!IMPORTANT]
>
> 1. **航司留空自动识别**：`carrierCd` 上传空串。若云当识别失败可能订阅不成功，需人工核对主运单号。
> 2. **厦门航空(MF)必传 org/dest**：本系统在起降机场三字码齐全时一律上传 `extendNo={org,dest}` 以满足 MF；机场未维护三字码则不上传，MF 可能订阅失败。
> 3. **主运单号来源**：`TransportOrder.MblNum`，为空则该票判为失败。
> 4. **推送走中转站空运专用入口** `/relay/yundang/air/push`，与海运 `/relay/yundang/push` 分开；中转站需配 `Providers:yundang:AirForwardPath=/api/yundang/air/push`。
> 5. **迁移**：新增表(`App_YundangAirSubscriptions`、`App_YundangAirShipmentDynamics`、`App_YundangAirShipmentFlights`、`App_YundangAirShipmentStatuses`、`App_YundangAirShipmentNodes`)需自行生成 EF Core 迁移。
> 6. **Token 复用海运**：空运服务自持一份进程内 token 静态缓存，来源同一中转站，值一致。
