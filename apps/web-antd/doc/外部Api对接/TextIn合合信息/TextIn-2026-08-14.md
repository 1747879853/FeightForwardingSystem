# 1. 背景意图 (Background)

**白话解释：** 业务联系单（PreOrder）是销售接单的第一张单子，字段和海运出口/进口高度重合，但一直只能手工录入。本次给它加上和海运出口、海运进口同款的 AI 识别：上传客户发来的委托书/提单，识别出文本后按名称匹配成系统 id，直接返回「新建业务联系单」表单可用的 `PreOrderAddDto`。

前端接口说明见同目录 `TextIn业务联系单智能抽取接口文档.md`。

# 2. 核心逻辑变更 (Changes)

| 项 | 说明 |
| :-- | :-- |
| 新增接口 | `TextInAdmin/ExtractPreOrderToAddDtoAsync`，出参 `PreOrderExtractAddDto`（`preOrder` + `extract`） |
| 抽取字段 | 25 个平铺字段 + 1 个数组字段 `集装箱信息`，抽取类型 `PreOrder`、schema 版本 `1`，缓存与海运出口/进口独立 |
| 剔除字段 | 业务联系单没有船名、航次、船代、订舱编号、签单方式/地点/日期、唛头、货物描述，这些字段不抽取 |
| 新增字段 | **付费方式**（海运出口没有），匹配 `CodeFrt` 的 `EnName`/`CnName`/`EdiCode` |
| 港口字段 | 比海运出口多回填**收货地**与**交货地**（含备注），共四个港口字段 |
| 空运港口 | `bizType=2`（空运出口）时四个港口字段全部改走 `AirPort` 表，海运走 `PortCode`，见第 3 节 |
| 箱型箱量 | 复用逐箱解析后**按箱型汇总**为「箱型 + 箱量」；`PreOrderCtn` 没有箱号/封号，指导价、卖价、货重留空 |
| 业务类型 | 由前端传入，AI 不判断；参数类型是 `int?` 而不是枚举，原因见第 4 节 |

## 2.1 名称→id 匹配规则

| 抽取字段 | 目标字段 | 匹配的引用表/字段 |
| :-- | :-- | :-- |
| 委托单位 | `clientId` | `Client.EnName`，匹配不到为 `Guid.Empty` |
| 船公司简称 | `carrierId` | `Carrier.CnShortName` |
| 收货地/起运港/目的港/交货地 | `receivePortId` / `polId` / `podId` / `deliverPortId` | 海运 `PortCode`、空运 `AirPort`，同步回填对应 `*Remark` |
| 付费方式 | `codeFrtId` | `CodeFrt.EnName` → `CnName` → `EdiCode` → 包含匹配 |
| 运输条款 | `codeServiceId` | `CodeService.EnName` |
| 包装 | `codePackageId` | `CodePackage.Name` |
| 贸易条款 | `tradeTermsType` | 按枚举名匹配，忽略大小写，支持包含匹配 |
| 品名 | `preOrderCodeGoodss` | 按 逗号/顿号/分号/斜杠/换行 拆分，逐个匹配 `CodeGoods.EnName` |
| 集装箱信息 | `preOrderCtns` | `CtnCode.CtnName`/`EdiCode`，归一化后比对（去符号、`DC`=`GP`、`HC`=`HQ`），按箱型汇总箱量 |

匹配策略统一为：去空白 → 精确匹配 → 包含匹配 → 仍未命中则 id 留空，**不报错**。

# 3. 空运港口与海运港口不能混用

`PortCode`（海运港口）和 `AirPort`（空运港口/机场）是两张独立的表，id 各自编号。空运业务如果回填海运港口 id，会指向完全不相干的一条基础资料，且前端机场下拉里根本找不到这个 id。

新增 `ResolveAirPortAsync`，匹配顺序：

1. 三字码 `IataCode` 精确匹配（有「起运港代码」等代码字段时优先走这条）；
2. `EnName` / `CnName` / `City` / `IataCode` 精确匹配；
3. 命中多条且名称里带国家（`SHANGHAI, CHINA` 这种格式，按最后一个逗号拆分）时，用国家英文名去空格后收窄；
4. 仍未命中则 `EnName` / `City` 包含匹配。

备注回填格式与海运一致：`机场英文名, 国家英文名`。入口收敛在 `ResolvePortByBizTypeAsync(bizType, name, code)`，四个港口字段都走它，避免以后漏改某一个。

抽取提示词里四个港口字段的描述也补了「空运时为机场名/机场三字码」，让模型在空运单据上取三字码而不是港口代码。

# 4. 避坑指南 (Pitfalls)

> [!IMPORTANT] **[坑 1：枚举参数会被 ABP 加上 `[FromBody]`，与文件上传冲突报 415]** `AbpAppServiceConvention` 用 `TypeHelper.IsPrimitiveExtendedIncludingNullable` 判断参数是不是简单类型，该方法的 `includeEnums` **默认为 false**，所以枚举参数被当成复杂对象自动加 `[FromBody]`。而 `multipart/form-data` 请求没有 JSON body，MVC 找不到 body formatter，直接返回 **415 Unsupported Media Type**。因此 `bizType` 用 `int?` 接收（和 `GeminiAdmin/ExtractSeFreiPriceByPromptAsync` 的 `string text` 同理），在 `ParseBizType` 里转成 `BizType`。**以后不要顺手把它改回枚举类型。**

> [!IMPORTANT] **[坑 2：空运的港口必须走 AirPort]** 见第 3 节。`PreOrder` 实体上 `POLId` 等外键在模型里指向 `PortCode`，空运场景存的是 `AirPort` 的 id，属于按 `bizType` 复用同一列的既有设计；如果后续给这些列加了数据库外键约束，空运数据会保存失败，需要先确认约束情况。

> [!IMPORTANT] **[坑 3：箱型是汇总不是明细]** 业务联系单的 `preOrderCtns` 是「箱型 + 箱量」，识别出 6 个箱号只会返回 1 行 `count=6`。需要箱号封号明细的是海运进口，不要拿这个接口的结果去填箱号。

> [!IMPORTANT] **[坑 4：改了抽取字段或提示词要提 schema 版本]** 不提版本号的话，老文件会一直命中旧缓存，改动看不出效果。业务联系单当前为 `PreOrder` / `1`。
