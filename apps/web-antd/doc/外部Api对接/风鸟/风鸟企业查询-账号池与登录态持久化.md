# 1. 背景意图 (Background)

此前 `RiskbirdAdminAppService` 把单一账号密码硬编码在代码中，登录态（token + Cookie）仅保存在进程内的 `static` 字段。该方案存在三个问题：

1. 只能配置一个账号，无法多账号轮换使用。
2. 登录态随进程重启丢失，且多实例部署时无法共享。
3. 并发首登时多个请求会同时判定“未登录”，对同一账号重复登录。

本次改造：将账号放入数据库（支持多账号），查询时由调用方选择某个账号；当该账号未登录或 token 失效时，对该账号数据行加悲观锁串行重新登录，并把 token 与 Cookie 回写数据库，避免并发重复登录。

## 2.3 服务逻辑

`src/CsprojBuilder.Application/App/Riskbird/RiskbirdAdminAppService.cs`

- 删除所有 `static` 登录态字段与硬编码账号；改为注入 `IRepository<RiskbirdAccount, long>`。
- `EnsureAccountReadyAsync(accountId)`：
  - 快路径：`AsNoTracking` 读取账号，token 有效（存在且未过期）直接复用，**不加锁**。
  - 慢路径：开启 `ReadCommitted` 事务，`FromSqlRaw("... WITH (UPDLOCK, ROWLOCK) WHERE Id = {0}")` 对该行加悲观锁；拿锁后**二次检查**（其他线程可能已重登则直接复用），仍失效才真正登录并回写 `Token/CookieJson/TokenExpireTime/LastLoginTime`。
- `SendWithReloginAsync`：统一发请求；当返回 HTTP 401 或业务体判定登录态失效时，先 `InvalidateTokenIfMatchAsync` 作废 token，再 `EnsureAccountReadyAsync` 重登并重试一次。
- `InvalidateTokenIfMatchAsync`：同样加行锁，且**仅当库中 token 与本次失败 token 相同时**才清空，避免误清其他线程刚刷新的有效 token。
- Cookie 与登录改为按账号传递 `Dictionary<string,string>`（`CreateConfiguredClient`/`LoginAsync`/`CaptureCookies`/`BuildCookieHeader` 均带参），`BuildDeviceCookies` 复用历史 `app-uuid` 保持设备标识稳定。
- 新增账号管理接口：`GetAccountListAsync`、`SaveAccountAsync`、`DeleteAccountAsync`。

# 3. 避坑指南 (Pitfalls)

- **并发重复登录**：核心在于“锁内二次检查 + token 比对作废”。只要复用现有 `UPDLOCK, ROWLOCK` 行锁模式（与 `App_GenerateNumRuleNums`、`App_OrderFees` 一致），同一账号并发只会重登一次。
- **不要无条件清 token**：401 重试时若直接清空 token，会把其他线程刚登好的有效 token 误删，因此用 `Token == failedToken` 守卫。
- **token 与 Cookie 必须同源保存**：风鸟鉴权同时依赖 Cookie 中的 `token`，所以整份 Cookie 以 `CookieJson` 持久化，重登时基于 `BuildDeviceCookies` 重新发起以丢弃过期鉴权 Cookie。
- **详情页失效判定**：详情接口返回 HTML 而非 JSON，无法用 `code=401` 判断，改用“解析不出 `jbxxInfo` 即视为可能失效”触发一次重登重试。
- **迁移**：`App_RiskbirdAccounts` 表需执行迁移后才存在；账号需先通过 `SaveAccountAsync` 录入后才能在查询中选择。
- **token 的读写事务必须是 `RequiresNew`，别改回去**：`EnsureAccountReadyAsync` 重登后回写 token、`InvalidateTokenIfMatchAsync` 作废坏 token，两处的 `UnitOfWorkManager.Begin` 都带 `Scope = RequiresNew`。原因是 ABP 里嵌套 `Begin` 不带 `RequiresNew` 会**并入外层工作单元**，内层 `CompleteAsync()` 并不真提交，要等外层公开方法正常结束才落库；而这两处后面还会抛错（业务码校验失败、「登录态失效，重新登录后仍请求失败」），一抛就把「刚登录拿到的 token」和「坏 token 已作废」一起回滚，下一个请求又拿着同一个坏 token 重来，每次失败白烧一次登录。`IsTransactional` 保持 `true`：`UPDLOCK, ROWLOCK` 行锁要靠事务撑住，改成 `false` 会让串行化失效。

# 6. 查询接口取消 AccountId 入参，改为随机使用账号（2026-06-29）

- 背景：此前 `SearchCompanyAsync`/`GetCompanyDetailAsync` 要求前端传入 `AccountId` 指定账号，交互繁琐且固定账号易触发风控。本次改为服务端在每次查询时从“启用”的账号池中**随机择一**账号使用。
- DTO 变更（`RiskbirdDto.cs`）：`RiskbirdCompanySearchDto`、`RiskbirdCompanyDetailInputDto` 移除 `long AccountId` 字段。
- 服务逻辑（`RiskbirdAdminAppService.cs`）：
  - 两接口移除 `input.AccountId <= 0` 的“请选择查询账号”校验。
  - 新增私有方法 `PickRandomEnabledAccountIdAsync()`：查出 `IsEnabled = true` 的全部账号 Id，随机取其一返回；账号池为空时报错「没有可用的风鸟账号，请先在账号池中添加并启用账号」。
  - 两接口发起请求前调用该方法取随机账号 Id，再传入 `SendWithReloginAsync`。
- 避坑：随机选号仅在启用账号范围内进行，需保证至少一个启用账号；选中账号登录态失效仍由 `EnsureAccountReadyAsync` 加行锁串行重登，并发安全不受影响；前端调用方需同步移除请求体中的 `AccountId`。
