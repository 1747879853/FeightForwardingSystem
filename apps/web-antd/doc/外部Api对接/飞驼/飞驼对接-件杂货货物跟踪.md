# 1. 业务背景说明 (Background)

**白话解释：** 件杂货走飞驼的「散货/RORO货物跟踪」：支持 RORO 船公司、件杂货船公司、散杂货船公司，按**提单号**跟踪，跟踪颗粒度细化到货物维度。业务员在件杂货上点订阅，系统拿主提单号去飞驼订阅；订阅与查询是同一个接口，订阅成功当场带回全量数据落库；之后飞驼在数据变化时推送增量，系统按 `dbtype` 合并落库，前端随时可查最新轨迹。

| 飞驼接口 | 文档 | 说明 |
| :-- | :-- | :-- |
| 散货/RORO货物跟踪(订阅+查询) | <https://doc.freightower.com/508089566e0> | `POST http://openapi.freightower.com/application/RORO/v1/query`，Bearer 鉴权(token 走中转站，与其它飞驼接口共用缓存) |
| 散货/RORO货物跟踪(增量) | <https://doc.freightower.com/513261689e0> | 推送，回调地址由飞驼客服配置 |

> [!IMPORTANT] **件杂货业务表本身没有集装箱，这一点不变。** 飞驼这个接口返回的 `result.containers[]` 按飞驼原样存进跟踪快照的集装箱子表：散货/RORO 文档里 `containerNo` 标为「货物编码」(示例 `RORO000001`)，箱型、箱尺寸、标准箱型、铅封号、整拼箱标为「该字段无数据」。

# 2. 功能与操作说明 (Features & Operations)

- **订阅：** `FeituoAdminAppService.SubscribeBreakBulkAsync`，入参件杂货Id集合，可批量，单条失败不影响其它票。返回的全量数据当场落库，订阅成功后把「提单号 → 本机客户标识」登记到中转站。
- **查询已落库数据：** `FeituoAdminAppService.GetBreakBulkTrackingAsync`，读本地最新快照，不请求飞驼；接货地/交货地/头程大船缺失时用计划地点兜底。
- **推送接收：** 飞驼 → 中转站 `POST /relay/feituo/breakbulk-push` → 按 `param.billNo` 查登记表路由(查不到广播) → 业务端 `POST /api/feituo/breakbulk-push` → `ProcessBreakBulkPushAsync` 按提单号认领订阅 → 按 `dbtype` 合并落库；本地无快照时把本次推送当全量落库，**不回查**飞驼。
- **业务单直接带运踪：** 件杂货的列表与详情返回运踪摘要(`FeituoTracking`)，详情额外返回完整快照(`FeituoTrackingDetail`)；业务联系单列表的 `TransportOrder.BreakBulk` 带运踪摘要。都走只读查询器 `FeituoBreakBulkTrackingQueryManager`。
- **删除件杂货时一并清理：** 订阅记录软删(之后的推送就认领不到这票)，快照主表与全部子表硬删。

# 3. 订阅规则 (核心业务规则)

| 飞驼参数 | 取值 | 说明 |
| :-- | :-- | :-- |
| `billNo` | 主提单号 `TransportOrder.MblNum`(去首尾空格) | 必填；件杂货只按提单号订阅 |
| `carrierCode` | 固定 `AUTO` | 件杂货没有船公司；飞驼文档允许「不明确时传 AUTO」 |
| `polCode` | 起运港 `POL.EdiCode` | 取不到时不传 |
| `podCode` | 目的港 `POD.EdiCode` | 取不到时不传 |

散货/RORO 接口只收这 4 个字段，**没有** `businessNo`、`portCode`、`isExport`、`billCategory`。

| 情况 | 结果 |
| :-- | :-- |
| 没传件杂货Id | 整批抛错：`请至少选择一条件杂货` |
| 件杂货不存在 | 该条失败：`未找到指定的件杂货` |
| 未填主提单号 | 该条失败：`该件杂货未填写主提单号，无法订阅` |
| 请求飞驼 HTTP 失败 | 该条失败：`货物跟踪订阅失败(HTTP 状态码)`，日志记飞驼原始返回 |
| 请求飞驼异常 | 该条失败：`请求外部接口异常，请稍后重试` |
| 飞驼返回为空 | 该条失败：`外部接口返回为空` |
| 飞驼返回失败状态码 | 该条失败，`errorMessage` 为飞驼的 `message` |
| 飞驼返回 `20000` / `20001` | 订阅成功(`20001` 表示暂无数据) |

**一票件杂货只保留一条订阅记录**：再订阅时复用原记录并刷新订阅参数与应答，但**每调一次都会消耗一次飞驼调用次数**。

# 4. 架构与数据流

```
业务端 ──取token(头 X-Relay-Token)──▶ 中转站 /relay/feituo/token ──▶ access_token
业务端 ──订阅(Bearer token, billNo/carrierCode=AUTO/polCode/podCode)──▶ 飞驼 /application/RORO/v1/query ──▶ 全量数据(当场落库)
业务端 ──订阅成功后登记 billNo→Relay:Customer(头 X-Relay-Token)──▶ 中转站 /relay/feituo/breakbulk-register(存 SQLite 表 FeituoBreakBulkRoutes)

[增量推送]
飞驼 ──增量──▶ 中转站 /relay/feituo/breakbulk-push ──按 param.billNo 查登记表(查不到/下游不可用/解析失败都广播)──▶ 业务端 /api/feituo/breakbulk-push
业务端 ──按 billNo 认领件杂货订阅──▶ 有 RawJson 则按 dbtype 合并；无则当全量 → 整体落库；原始报文记件杂货推送日志
```

**为什么要登记路由**：集装箱推送靠订阅时编进 `businessNo` 的客户前缀路由，而散货/RORO 接口不收 `businessNo`，推送的 `param` 只回显 `billNo/carrierCode/polCode/podCode`，中转站光看报文分不出是哪家客户。所以沿用空运的做法：业务端订阅成功后把「提单号 → 客户标识」登记到中转站，推送到达时按 `param.billNo` 查表精确转发。登记失败只记日志不影响订阅；查不到登记时广播给全部下游，由各下游按提单号自行认领，不丢推送。

# 5. 推送认领与增量合并

**认领**：推送不带租户上下文，关闭租户过滤后按 `param.billNo` = 订阅记录 `BillNo` 查件杂货订阅，同一提单号被重新订阅过时取 `SubscribeTime` 最近的一条。认领不上(别家客户的广播推送)只记原始报文后忽略。

**合并**(`FeituoBreakBulkTrackingManager.ApplyPushAsync`)：不直接改数据库行，在内存快照上合并后整体落库。

| 步骤 | 做法 |
| :-- | :-- |
| 取基准 | 快照主表的 `RawJson`(上一次的完整 data)；没有或原文损坏时，用推送的 `param` 搭一个空快照，合并后即为全量(`UsedAsFullSnapshot=true`) |
| 整票字段 | 推送 `result` 只是查询 `result` 的子集，`billCategory/statusCategory/statusDescription/endTime/updateTime` **给了值才覆盖**；`carrier` 推送只带 `code` |
| 发生地 | 推送的 `places` 没有 `dbtype`，按「地点CODE + 地点类型」定位**逐字段覆盖**，找不到则追加 |
| 集装箱 | 按 `dbtype`(1新增 2修改 3删除)处理，`containerNo` 为定位键，为空按有则改无则增；`offLoadOfCarrier` 只判空不判值(解除甩柜也要落下去) |
| 物流节点 | 按 `dbtype` 处理，「状态代码 + 地点CODE」为定位键；**不含发生时间**(预计转实际时飞驼以 `dbtype=2` 推同一个状态代码)；合并后按发生时间排序 |
| 集装箱当前状态 | 取合并后时间最新的**实际**节点(没有实际节点退回最新的预计节点)回写 `currentStatusCode/描述/发生地/地点CODE` |
| 整票当前状态 | 推送不带 `currentStatus`，按全部节点里最新的实际节点回算；经纬度从同 CODE 的发生地取 |
| 接货地/交货地 | 推送不带 `receipt/delivery`，按地点CODE匹配推送里的发生地刷新时间(接货地取 `type` 最小、交货地取最大)，匹配不上不动 |
| 落库 | 合并后的完整 data 交给 `PersistDataAsync`：主表整表覆盖、子表删旧建新、`RawJson` 存最新快照 |

> [!NOTE] 推送示例里物流节点带 `statusId`，但查询返回的节点没有这个字段、推送的字段定义里也没列，所以不拿它做定位键，也不落库。

# 6. 落库结构

| 表 | 实体 | 说明 |
| :-- | :-- | :-- |
| `App_FeituoBreakBulkSubscriptions` | `FeituoBreakBulkSubscription` | 订阅记录，**一票件杂货一条**，按租户隔离，外键 `BreakBulkId` → `App_BreakBulks`。存 `BillNo`/`CarrierCode`(=AUTO)/`PolCode`/`PodCode`、飞驼状态码与提示、失败原因、请求/响应原文、最近推送报文与时间 |
| `App_FeituoBreakBulkTrackings` | `FeituoBreakBulkTracking` | 快照主表，按 `SubscriptionId` 唯一；冗余 `TenantId`/`BreakBulkId`；`query`/`actualParam`、船公司、订舱、接货地、交货地、头程大船、当前状态全部平铺 + `RawJson` |
| `App_FeituoBreakBulkTrackingPlaces` | `FeituoBreakBulkTrackingPlace` | 发生地 `places[]` |
| `App_FeituoBreakBulkTrackingRoutes` | `FeituoBreakBulkTrackingRoute` | 路径 `routes[]`，`modeDetails` 平铺为 `Mode` 前缀的列 |
| `App_FeituoBreakBulkTrackingContainers` | `FeituoBreakBulkTrackingContainer` | 集装箱物流信息 `containers[]`，按飞驼原样落库 |
| `App_FeituoBreakBulkTrackingContainerStatuses` | `FeituoBreakBulkTrackingContainerStatus` | 物流节点 `containers[].status[]`，`Sort` 按数组下标从 0 起 |
| `App_FeituoBreakBulkTrackingVessels` | `FeituoBreakBulkTrackingVessel` | 船舶 `vessel[]` |
| `App_FeituoBreakBulkPushLogs` | `FeituoBreakBulkPushLog` | 每次推送的原始报文(全局，不按租户)，无论是否匹配都记录；`BillNo`、`ContainerCount`、`StatusCount`、`MatchedCount`、`AppliedCount`、`Success`、`Remark` |

- **更新策略**：主表整表覆盖、子表删旧建新，完全以最新快照为准。散货/RORO 没有预警，所以没有「按票累积、不参与删旧建新」的例外表。
- **经纬度**：`decimal(18,6)`(集装箱那套表是默认精度)。
- **时间字段一律存字符串**：飞驼返回 `2026/07/25 19:00:00` 这种格式，原样保存。
- **字段类型按散货/RORO 文档**：`places[].atdSource`、`routes[].modeDetails.polAtdSource/podAtaSource`、`carrier.status` 是整数。
- **不接字段级屏蔽**(PropMaskModule)。

# 8. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **1. 要另找飞驼客服配一个回调地址。** 散货/RORO 的增量推送和集装箱增量推送是两个产品，回调地址各配各的，地址为中转站的纯 URL：
>
> ```
> POST {中转站}/relay/feituo/breakbulk-push
> ```
>
> 没配之前件杂货只有订阅时带回的那一份快照，要看最新数据只能再订阅一次(每次都消耗调用次数)。中转站需随本次改动重新发布并配置 `BreakBulkForwardPath`。

> [!IMPORTANT] **2. 按提单号路由与认领，改了主提单号要重新订阅。** 推送只回显订阅时的 `billNo`，件杂货改了主提单号而没重新订阅，推送会认领不到。

> [!NOTE] **3. 订阅后飞驼立刻推的那一条可能认领不到，属正常。** 飞驼订阅成功时会马上推一次当前状态，而订阅记录要等订阅接口所在事务结束才提交、路由登记也在订阅返回之后，这一条推送可能先到。它的内容就是订阅接口已带回并落库的那份快照，丢掉不影响数据。

> [!NOTE] **4. 船公司代码固定传 `AUTO`。** 件杂货没有船公司字段，按飞驼文档「不明确时传 AUTO」处理。飞驼文档的散货船示例传的是 `BULK`、RORO 示例传的是船司代码 `UGR`；真实订阅若发现 `AUTO` 识别不出船司，需要和飞驼确认后再调整。飞驼识别出的船司可在快照的 `query.actualParam.carrierCode` 与 `result.carrier` 里看到。

> [!NOTE] **5. 不回填件杂货的任何字段。** 跟踪数据只落跟踪表，不写回件杂货业务单。

> [!IMPORTANT] **6. 需自行生成 EF Core 迁移。** 新增第 6 节的 8 张表；上一版曾给集装箱推送日志 `App_FeituoPushLogs` 加过 `BizType` 列，已撤回，迁移里应删除该列。迁移文件由开发人员自行生成。
