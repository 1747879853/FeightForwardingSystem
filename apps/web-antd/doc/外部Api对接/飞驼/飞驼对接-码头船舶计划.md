# 1. 业务背景说明 (Background)

**白话解释：** 飞驼「码头船舶计划」提供某条船在某个**港区**的作业计划：预计/实际抵达(抵锚)、预计/实际靠泊、预计/实际离港，以及开港、截港、截单、截关时间。

本系统的用法是**按业务单一键查询**：操作在海运出口/海运进口单据上点一下，后端拿这条单子的**船名**、**码头航次**和**起运港 EDI 代码**去查飞驼，把结果原样返回给前端。前端只需要传业务单Id。

> [!IMPORTANT] **航次有两套编号，这里用的是「码头航次」。** 海运出口/进口上有两个航次字段：`InnerVoyno`「航次」是**船公司航次**，`TerminalVoyno`「码头航次」是**港区航次**。码头船舶计划认的是码头航次。业务单只填了船公司航次时，后端会先调飞驼「船司航次转码头航次」换算一次再查；返回条目里的 `evoyage`/`ivoyage` 同样是码头航次。

> [!IMPORTANT] **纯查询接口：不建表、不落库、不回填业务单。** 结果只透传给前端展示，由用户从列表里挑一条、自行填到表单上，再走海运出口/海运进口各自的编辑保存接口。后端不做任何覆盖。

# 2. 功能与操作说明 (Features & Operations)

- **码头船舶计划查询：** `FeituoAdminAppService.QueryTerminalScheduleAsync`，入参只有业务单Id。
  - 返回 **1 条或多条** → 全部放在 `items` 里返回，后端**不做取舍**，由前端展示给用户选。
  - 返回 **0 条** → `items` 为空数组，`message` 带上"未查到"的提示。

**内部查两趟（前端只调一次）：**

| 情况 | 行为 | `FilteredByTerminalVoyno` |
| :-- | :-- | :-- |
| 有码头航次且按它查到 | 只查一趟 | `true` |
| 有码头航次但按它查不到 | **去掉航次与进出口标识重查一次，无论结果如何都以重查为准** | `false` |
| 本来就没有码头航次 | 直接不带航次查 | `false` |

# 3. 架构与数据流

```
业务端 ──取token(头 X-Relay-Token)──▶ 中转站 /relay/feituo/token ──▶ access_token
业务端 ──(仅码头航次为空且船公司航次有值时)──▶ 飞驼 GET /vessel2/voyage/location ──▶ 码头航次
业务端 ──第一趟(带码头航次+isExport)──▶ 飞驼 POST /terminal/selectScheduleInfo ──▶ 有数据则直接返回
业务端 ──第二趟(0条时去掉航次与isExport重查)──▶ 飞驼 POST /terminal/selectScheduleInfo ──▶ 以这趟为准
```

**Token 与其它飞驼功能共用**：`FeituoTokenProvider` 是同一份进程内缓存，船期、港口拥堵、集装箱跟踪、航空货运跟踪、码头船舶计划共用，不会重复取号。

**请求参数的来源(全部由后端从业务单推导，前端只传业务单Id)：**

| 飞驼参数 | 必填 | 取值来源 |
| :-- | :-- | :-- |
| `vesselNameEn` | 是 | 海运出口 `SeaExport.Vessel` / 海运进口 `SeaImport.Vessel` |
| `portCode` | 是 | **起运港** `POL` → `PortCode.EdiCode`，自动 Trim 并转大写 |
| `voyage` | 否 | **码头航次**：优先取 `TerminalVoyno`；为空且 `InnerVoyno`(船公司航次)有值时取换算结果；两者都没有则**不带该参数**，按船名+港口查全部 |
| `isExport` | 否 | 海运出口 `E`、海运进口 `I`，但**与 `voyage` 同进同退**：只有传了航次才带它，没航次时两个都不传 |

**航次换算接口 `GET /vessel2/voyage/location` 的参数：**

| 参数     | 必填 | 取值来源                                          |
| :------- | :--- | :------------------------------------------------ |
| `vessel` | 是   | 业务单船名 `Vessel`（与查计划用的是同一个）       |
| `voyage` | 是   | 业务单**船公司航次** `InnerVoyno`                 |
| `pol`    | 是   | 起运港 `PortCode.EdiCode`（与查计划用的是同一个） |

返回 `data` 就是换算出来的码头航次字符串。

> [!IMPORTANT] **`isExport` 必须跟着 `voyage` 一起传或一起不传。** 没有航次时若单独带上 `isExport`，飞驼会把本该返回的挂靠计划过滤掉，结果查不到数据。代码里的写法是 `IsExport = 航次为空 ? null : (出口 ? "E" : "I")`，再靠 `NullValueHandling.Ignore` 让空值字段整个不出现在请求体里——注意**不能发成 `null` 或空串**，那样飞驼仍会当成有值来过滤。

> [!NOTE] **出口和进口都按起运港查。** 这是产品确认的口径。需要注意进口的起运港通常是国外港，而飞驼码头船舶计划的覆盖范围以国内港区为主，因此**进口方向经常查不到数据**属正常现象。

# 5. 返回字段口径

飞驼返回的 23 个字段**全部原样透传**，一个都不落库。时间类字段都是飞驼返回的原始字符串（`yyyy-MM-dd HH:mm:ss`），没数据时为 `null`。

| 分组 | 字段 | 说明 |
| :-- | :-- | :-- |
| 船期状态 | `status` | **仅上海港提供**：预报 / 确报 / 在港 / 离港 / 取消，其它港为 `null` |
| 船舶 | `vesselNameEn` / `vesselNameCn` | 船舶英文名 / 中文名 |
| 船公司 | `shipCode` / `shipName` | 船公司代码 / 中文名 |
| 船代 | `agentCode` / `agentName` | 船代代码 / 名称 |
| 航线 | `lineCode` | 航线代码 |
| 码头 | `terminal` | 码头 |
| 挂靠港 | `portsEn` / `portsCn` | 以 `+` 分隔的长字符串 |
| 抵达(抵锚) | `eta` / `ata` | 计划 / 实际抵达**本次查询的港区** |
| 靠泊 | `etb` / `atb` | 计划 / 实际靠泊 |
| 离港 | `etd` / `atd` | 计划 / 实际离港 |
| 港区节点 | `cyOpen` / `cyClosing` / `portCloseDate` / `customsCloseDate` | 开港 / 截港 / 截单 / 截关 |
| 航次 | `evoyage` / `ivoyage` | 出口航次 / 进口航次，都是**码头航次** |
| 更新时间 | `updateTime` | 飞驼侧最后更新时间 |

**业务字段对应关系**（供前端填表参考，后端不做写入）：

| 飞驼字段 | 对应业务单字段 | 适用 |
| :-- | :-- | :-- |
| `atd` 实际离港 | `TransportOrder.ATD` 实际开船日期 | 出口 + 进口 |
| `evoyage` / `ivoyage` | `TerminalVoyno` **码头航次**（不是船公司航次 `InnerVoyno`） | 出口 / 进口 |
| `cyClosing` 截港时间 | `SeaExport.ClosingTime` 截港日期 | 仅出口 |
| `portCloseDate` 截单时间 | `SeaExport.CloseDocTime` 截单日期 | 仅出口 |
| `customsCloseDate` 截关时间 | `SeaExport.CloseManifestTime` 截关日期 | 仅出口 |

> [!IMPORTANT] **`CloseManifestTime` 就是截关日期。** 这一列的实体注释、`SeaExportPropEnum` 和海运出口的各 DTO 里写的都是"截舱单日期"，但本系统的业务口径上它承载的是**截关**。看这块代码时别按字面的"截舱单"去理解。

海运进口没有截港/截单/截关字段，能对上的只有实际开船日期与航次。

# 6. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **1. `eta`/`ata` 不是"预抵目的港"。** 飞驼这两个值是「抵达**本次查询的那个港区**(抵锚)」，本系统按**起运港**查询，所以它表示的是"船到起运港"——比开船还早。而业务单的 `TransportOrder.ETA` 是"预抵目的港"。这两个概念不能混：前端展示时文案要写清"抵达起运港"，更不能拿它去算箱使、转站等派生日期。若将来把海运进口改成按**目的港**查询，进口方向的 `eta`/`ata` 才等价于预抵目的港。

> [!IMPORTANT] **2. 后端不做任何取舍与写入。** 同一船名+港口可能有多个航次、多次挂靠，飞驼会返回多条。后端**不猜哪条对**、也**不回填业务单**，全部返回给前端由用户选。用户选完之后是前端把值填到表单、再走海运出口/海运进口自己的编辑保存接口落库。

> [!IMPORTANT] **3. 起运港必须维护 EDI 代码。** `portCode` 取的是 `PortCode.EdiCode`（与集装箱跟踪订阅取船公司 `EdiCode` 同一套基础资料口径）。没维护 EDI 代码会直接报错并带上港口名，提示去补基础资料。

> [!IMPORTANT] **4. 按码头航次查不到时会自动去掉航次重查，且以重查结果为准。** 码头航次填错、或换算结果与港区口径不一致都很常见，直接回"未查到"对操作没用。所以第一趟带航次查到 0 条时，会**去掉 `voyage` 与 `isExport` 再查一次**，把该船在该港的全部挂靠计划返回，由 `FilteredByTerminalVoyno=false` 标明这批数据没按航次过滤。 **因此 `items` 为空时不是航次的问题**——航次那一层已经被兜底掉了，空只可能是船名或港口对不上。代价是这种情况会打两次飞驼接口。可以接受：它是操作手动触发的低频动作，而且第一趟命中时只打一次。前端必须把 `FilteredByTerminalVoyno=false` 显著提示出来，否则用户会以为列表里那条就是自己那票的。

> [!IMPORTANT] **5. 航次换算失败不阻断查询，且无法分辨"换算成功"。** 飞驼「船司航次转码头航次」在**找不到对应港区航次时，会把传入的船公司航次原样返回**，因此从返回值分辨不出到底换没换。本系统不做分辨：拿到什么就用什么去查计划，查不到就按"未查到"提示。换算请求本身失败（HTTP 异常、报文异常、状态码非成功）时**只记 Warn 日志、返回 null，不抛异常**，退回"不带航次按船名+港口查全部"——换算只是为了提高命中率，为它让整个查询报错不值得。结果里的 `terminalVoynoConverted` 标识这次的航次是不是换算来的，前端可以据此提示用户把它补录到业务单的码头航次上。

> [!IMPORTANT] **对外报错不许出现"飞驼"，返回字段名要和系统字段一致。** 抛给前端的报错与 `message` / `errorMessage` 一律用「外部接口」这类中性说法，供应商名与对方的字段名只写进 `Logger` 日志和落库的原始报文。返回结构里的航次字段直接叫 `innerVoyno` / `terminalVoyno`，与业务单字段名完全一致——用户挑一条之后前端要把值填回业务单，名字对上了就不需要额外的对应表。**不要**再起 `voyage` / `carrierVoyage` 这种自造名。已写入规则 `.cursor/rules/dotnet-api-dto.mdc`。

> [!NOTE] **6. 状态码 20001 不是失败。** 飞驼的 `20001` 表示"请求成功但无数据"，判成功统一走 `FeituoStatusCode.IsSuccess`，**不要**写 `statusCode == 20000`，否则查不到数据的单子会报"查询失败"而不是"未查到"。两个飞驼接口（查计划、换航次）都按这个口径判。

> [!NOTE] **7. `PortCode` 类型必须写全限定名。** `CsprojBuilder.App.PortCode` 是个同名命名空间，在 AppService 里直接写 `PortCode` 会编译报 CS0118，需写 `Entites.PortCode`。
