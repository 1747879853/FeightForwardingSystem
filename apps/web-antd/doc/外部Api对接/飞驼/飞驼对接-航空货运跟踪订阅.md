# 1. 业务背景说明 (Background)

**白话解释：** 飞驼「航空货运跟踪」覆盖 180+ 家航司，可跟踪一票空运货从收运、装机、起飞、中转、落地到提货的全程节点。本次把该能力接到**空运出口**模块：业务员在空运出口单上点订阅，系统取主运单号去飞驼订阅拿回**订阅ID**，紧接着用订阅ID回查一次把轨迹落库；此后飞驼有变化会主动推送全量数据，系统自动更新。

## 1.1 空运与海运的对接方式完全不同(务必分清)

|  | 海运集装箱跟踪 | 空运航空货运跟踪 |
| :-- | :-- | :-- |
| 订阅接口 | `POST /application/v1/query` | `POST /air/subscribe` |
| 订阅与查询 | **同一个接口**，订阅成功当场带回全量数据 | **两个接口**，订阅只回订阅ID |
| 查询接口 | 同上 | `GET /air/observer/{订阅ID}`，`data` 是**数组** |
| 推送内容 | 增量+预警，按 `dbtype` 合并 | **全量快照**，直接整体覆盖 |
| 推送匹配依据 | `param.businessNo` | 根节点 `id`(订阅ID)，退回 `data.businessNumber` |
| 客户标识 | 订阅时传 `businessNo`，推送原样回传，中转站按前缀**精确路由** | 订阅入参**无处编入客户标识**，改由业务端订阅后向中转站**登记映射**再精确路由 |
| 预警数据 | 查询接口不返回，只能单独累积 | 查询接口**也返回**，跟着删旧建新即可 |

## 1.2 空运推送怎么路由回本机(与海运的做法不同)

飞驼空运订阅只收一个 `businessNumber`（11位航司单号），**没有任何自定义字段可以承载客户标识**。海运是把客户标识编在 `businessNo = {Customer}_{业务单Id}` 前缀里、飞驼推送时原样回传，空运做不到这一点。

解决办法是**让中转站记住映射**：

1. 业务端订阅成功拿到飞驼订阅ID后，调用中转站 `POST /relay/feituo/air-register` 登记「订阅ID → 客户标识」
2. 中转站把映射存进本地 SQLite（`App_Data/relay.db`，嵌入式单文件，无需部署数据库服务）
3. 推送到达时，中转站读报文根节点的 `id` 查表 → 精确转发给对应下游
4. 订阅ID查不到时用 `data.businessNumber` 再查一次；**仍查不到才广播**，由各下游按订阅ID/航司单号自行认领

> [!NOTE] **广播是兜底而不是主路径。** 登记失败、中转站换机器、历史订阅没登记过——这些情况都会退回广播，推送依然送得到，只是转发得不那么精确。因此业务端登记失败**只记日志、不报错**，不影响订阅结果。

# 2. 功能与操作说明 (Features & Operations)

- **航空货运跟踪订阅：** `FeituoAdminAppService.SubscribeAirWaybillAsync`，仅支持**空运出口**，可批量。取主运单号 → 剥离非数字字符 → 校验11位 → 调飞驼订阅 → 保存订阅ID → **向中转站登记推送路由** → **立即回查一次**把轨迹落库。
- **航空货运跟踪重新订阅：** `FeituoAdminAppService.ResubscribeAirWaybillAsync`，单条。无视已有订阅强制再订一次、拿新订阅ID，用于运单号改过或订阅数据异常需要重来的场景（**会消耗一次订阅配额**）。
- **推送接收：** 飞驼 → 中转站 `POST /relay/feituo/air-push` → 查登记表**精确路由**(查不到才广播) → 业务服务器 `POST /api/feituo/air-push` → 按订阅ID/航司单号匹配订阅 → 全量快照整体落库，**不回查**飞驼。
- **业务单直接带运踪：** 空运出口的**列表**返回运踪摘要（`FeituoTracking`：当前节点、整票状态、航司、货物、起降机场、预警条数与最近一条），**详情**额外返回完整跟踪数据（`FeituoTrackingDetail`）与全部预警（`FeituoTrackingWarnings`），前端跟单不用再调飞驼专用接口。

> [!NOTE] **订阅成功不代表马上有轨迹。** 刚订阅时飞驼往往还没抓到数据，回查会返回空，此时订阅结果里 `trackingLoaded=false`、`trackingMessage` 说明原因。这不影响订阅本身成功，等飞驼推送来了会自动落库。

> [!NOTE] 系统里**没有 `AirImport` 实体**（`BizType.AirImport` 枚举虽已预留但无对应业务表），因此空运跟踪只做出口。

# 3. 取号规则 (核心业务规则)

| 项 | 规则 |
| :-- | :-- |
| **单号来源** | `TransportOrder.MblNum`（主运单号，空运出口与业务表共用主键） |
| **格式处理** | **剥离所有非数字字符**后作为 `businessNumber` 上传 |
| **校验** | 剥离后必须**恰好11位**，否则拒绝订阅并报错 |
| **报错文案** | 未填单号 → `该空运出口未填写主运单号，无法订阅`<br/>位数不对 → `主运单号[999-1234567]提取出的数字为10位，飞驼要求11位数字，无法订阅` |

**为什么要剥离：** 主运单号业务上常写成 `999-12345678`（3位航司前缀 + 8位流水），带连字符直接上传飞驼会被拒。剥离后 `99912345678` 正好11位。

> [!NOTE] 云当空运订阅取的是同一个 `MblNum`，但**原样上传、不做任何校验**（云当自己容错）。飞驼这边明确要求11位数字，所以本对接**在本地就拦截**，避免白白消耗订阅配额。

# 4. 架构与数据流

```
业务端 ──取token(头 X-Relay-Token)──▶ 中转站 /relay/feituo/token ──▶ access_token
业务端 ──订阅(Bearer token, body={businessNumber})──▶ 飞驼 /air/subscribe ──▶ 订阅ID(落库)
业务端 ──登记路由(头 X-Relay-Token)──▶ 中转站 /relay/feituo/air-register ──▶ SQLite 存「订阅ID→customer」
业务端 ──紧接着回查(Bearer token)──▶ 飞驼 /air/observer/{订阅ID} ──▶ 全量快照(整表覆盖落库)

[自动更新]
飞驼 ──全量推送──▶ 中转站 /relay/feituo/air-push ──查登记表按订阅ID精确路由(查不到才广播)──▶ 业务端 /api/feituo/air-push
业务端 ──按根节点id(订阅ID)或data.businessNumber定位订阅──▶ 全量快照整体落库
```

**Token 与海运共用**：`FeituoTokenProvider` 是同一份进程内缓存，船期、集装箱跟踪、航空货运跟踪三处共用，不会重复取号。

**查询与推送共用同一条落库路径**：两者的 `data` 结构完全一致且都是**全量快照**，因此都走 `FeituoAirTrackingManager.PersistDataAsync`——主表整表覆盖、子表删旧建新，不必维护两套映射。

# 6. 落库结构

| 表 | 实体 | 说明 |
| :-- | :-- | :-- |
| `App_FeituoAirSubscriptions` | `FeituoAirSubscription` | 空运订阅记录，**一条空运出口一条**，按租户隔离 |
| `App_FeituoAirTrackings` | `FeituoAirTracking` | 跟踪解析主表，按 `SubscriptionId` 唯一。航司/货物/整票状态/**当前节点**/**起降汇总**平铺 + `RawJson` |
| `App_FeituoAirTrackingLocations` | `FeituoAirTrackingLocation` | 地点 `shipmentLocations[]`（含 sta/eta/ata） |
| `App_FeituoAirTrackingTransports` | `FeituoAirTrackingTransport` | 运输路径 `shipmentTransports[]`（装/卸货地平铺） |
| `App_FeituoAirTrackingEvents` | `FeituoAirTrackingEvent` | **四类事件合并一张表**，用 `EventSource` 区分 |
| `App_FeituoAirTrackingWarnings` | `FeituoAirTrackingWarning` | 异常预警 `warnings[]` |
| `App_FeituoAirPushLogs` | `FeituoAirPushLog` | 空运推送原始报文（全局，不按租户），无论是否匹配都记录 |

**中转站侧还有一张表**（不在业务库里，在中转站的 SQLite 文件中）：

| 表 | 位置 | 说明 |
| :-- | :-- | :-- |
| `FeituoAirRoutes` | `{中转站程序目录}/App_Data/relay.db` | 推送路由映射：`SubscriptionId`(主键) / `Customer` / `BusinessNumber` / `UpdatedTime` |

**订阅记录关键字段：**

| 字段 | 说明 |
| :-- | :-- |
| `AirExportId` | 关联的空运出口Id（= `AirExport.Id` = `TransportOrder.Id`） |
| `BusinessNumber` | 上传给飞驼的11位航司单号 |
| `SourceMblNum` | 订阅时业务单上的主运单号**原文**，保留原始写法便于核对取号是否正确 |
| `FeituoSubscriptionId` | **飞驼返回的订阅ID**，后续查询轨迹与匹配推送全靠它 |
| `SubscribeTime` / `IsSuccess` / `StatusCode` / `Message` / `ErrorMessage` | 订阅状态 |
| `SubscribeRequestJson` / `SubscribeResponseJson` | 请求与响应原文，便于排查 |

**事件表的 `EventSource` 取值：**

| 值  | 含义       | 来源                                                      |
| :-- | :--------- | :-------------------------------------------------------- |
| 1   | 单证事件   | `data.shipmentEvents`                                     |
| 2   | 运输事件   | `data.transportEvents`                                    |
| 3   | 货物动态   | `data.equipmentEvents`                                    |
| 4   | 装货地事件 | `data.shipmentTransports[].loadTransportCall.events`      |
| 5   | 卸货地事件 | `data.shipmentTransports[].dischargeTransportCall.events` |

> [!NOTE] **为什么四类事件合并成一张表：** 这 5 处的结构**完全一致**，只有末尾的分类字段（`shipmentEventCategory` / `transportEventCategory` / `equipmentEventCategory`）按来源取其一。建 5 张一模一样的表没有意义。装/卸货地事件另带 `TransportId` 指回所属运输路径。

**二次更新策略：** 主表按 `SubscriptionId` 定位、标量整表覆盖；子表**全部删旧建新**（含预警表），完全以最新快照为准。查询与推送返回的都是全量，这么做不会丢数据。

## 6.1 当前节点与起降汇总是本地算的

飞驼空运**不返回 `currentStatus`**（海运有），但列表要显示"这票现在到哪了"，因此落库时就算好存进主表，列表一次查询即可读到：

| 汇总项 | 算法 |
| :-- | :-- |
| 当前节点 | 取单证/运输/货物动态三类事件里**时间最新的实际事件**（`eventClassifier=ACT`）；一条实际的都没有才退回最新的预计事件 |
| 起飞机场 | 运输路径 `shipmentTransports` **第一段**的 `loadTransportCall.location` |
| 目的机场 | 运输路径 **最后一段**的 `dischargeTransportCall.location` |
| 目的地 ETA/ATA | 按目的机场CODE去 `shipmentLocations` 匹配，取 `detail.eta` / `detail.ata` |

> [!NOTE] **事件时间用字符串排序，不做 `DateTime.Parse`。** 飞驼返回的是定长的 `yyyy-MM-dd HH:mm:ss`，这种格式字符串排序等价于时间排序；用解析反而会因个别脏数据解析失败而把节点排错。

> [!NOTE] **起降不按 `locationCategory` 判断。** 飞驼没有公开 `shipmentLocations[].locationCategory` 的枚举（只在示例里见过 `PTR`），硬编码判断迟早写错值。运输路径本身有序，取首尾最可靠。

# 7. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **1. 主运单号必须能提取出11位数字。** 带连字符、空格都可以（会自动剥离），但数字位数不对就直接拒绝订阅，不会发请求给飞驼。

> [!IMPORTANT] **2. 默认不重复订阅，避免浪费配额。** 同一条空运出口若**已订阅成功且航司单号未变**，再次调用订阅接口会**直接复用已有订阅ID、不请求飞驼**，返回结果里 `alreadySubscribed = true`。确实需要重订时传 `forceResubscribe: true`。

> [!IMPORTANT] **3. 订阅成功不等于马上有轨迹。** 订阅接口只回订阅ID，系统紧接着会回查一次。但刚订阅时飞驼往往还没抓到数据，此时 `trackingLoaded=false`，**不算订阅失败**，等推送来了会自动落库。

> [!IMPORTANT] **4. 必须把空运回调地址提供给飞驼客服配置。** 地址为中转站的纯 URL：
>
> ```
> POST {中转站}/relay/feituo/air-push
> ```
>
> 它与海运的 `/relay/feituo/increment-push` 是**两个独立回调**，都要配。

> [!IMPORTANT] **5. 中转站的 SQLite 文件需要写权限，且不能被发布覆盖。** 中转站跑在 IIS 里，应用池账户（通常是 `IIS AppPool\{池名}`）必须对 `App_Data` 目录有**写权限**，否则登记会失败（推送退回广播，不会丢，但转发不精确）。该文件也**不要**放在每次发布都会被清空的目录，否则部署一次就把映射清光了。可用 `Relay:DatabasePath` 指到程序目录之外的固定位置。

> [!NOTE] **6. 推送路由查不到时会广播，属正常兜底。** 见第 1.2 节。中转站换机器、`App_Data` 被清、老订阅没登记过，都会走广播。此时下游按订阅ID/航司单号认领，认不上的就是别家客户的推送、直接忽略。日志里出现 `[路由未登记]` 与业务端的"未匹配到订阅记录"**不是 bug**。想恢复精确路由，重新订阅一次即可（会重新登记）。

> [!IMPORTANT] **7. 需自行生成 EF Core 迁移。** 新增 7 张表：`App_FeituoAirSubscriptions`、`App_FeituoAirTrackings`、`App_FeituoAirTrackingLocations`、`App_FeituoAirTrackingTransports`、`App_FeituoAirTrackingEvents`、`App_FeituoAirTrackingWarnings`、`App_FeituoAirPushLogs`。迁移文件由开发人员自行生成。中转站的 `FeituoAirRoutes` 表由程序启动时**自动创建**，不需要手工建。

> [!NOTE] **8. 重量字段实际会返回小数。** 飞驼文档把 `cargo.weight` 标注为整数，但实际返回如 `5273.7`，因此 DTO 与数据库都用 `decimal`，不要按整数建列。
