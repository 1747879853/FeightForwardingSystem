# 1. 业务背景说明 (Background)

**白话解释：** 飞驼「集装箱综合跟踪」可以跟踪一票货从提空箱、进场、装船、离港、中转、抵港、卸船到还空箱的**全程物流节点**，覆盖近百家船公司与中国港区/海关数据。

本次对接把该能力接到**海运出口**与**海运进口**两个模块：业务员在业务单上点订阅，系统按规则取单号或箱号去飞驼订阅；订阅成功后飞驼在数据变化时推送「增量+预警」，系统按 `dbtype` 合并落库(飞驼确认**首次推送即为全量**)，前端随时可查最新轨迹与异常预警。

> [!IMPORTANT] 飞驼的「订阅」和「查询」是**同一个接口**(`POST /application/v1/query`)：第一次调用即订阅，之后手动刷新也可再调取最新数据。 **自动更新只对接「增量+预警推送」**，不再对接「更新通知推送」(那种只回传参数再回查的方式已删除)。

# 2. 功能与操作说明 (Features & Operations)

- **集装箱跟踪订阅：** `FeituoAdminAppService.SubscribeContainerAsync`，支持**海运出口/海运进口**，可批量。按规则取订阅单号后调用飞驼接口，返回的全量跟踪数据当场解析落库。
- **跟踪数据查询：** `FeituoAdminAppService.GetContainerTrackingAsync`，读本地最新快照，不请求飞驼。
- **推送接收(增量+预警，唯一回调)：** 飞驼 → 中转站 `POST /relay/feituo/increment-push` → 按 `param.businessNo` 前缀路由 → 业务服务器 `POST /api/feituo/increment-push` → 按 `dbtype` 增量合并落库并累积异常预警；本地无快照时把本次推送当全量落库，**不回查**飞驼。
- **业务单直接带运踪：** 海运出口/海运进口的**列表**返回运踪摘要(`FeituoTracking`，含预警条数与最近一条)，**详情**额外返回完整跟踪数据(`FeituoTrackingDetail`)与全部预警(`FeituoTrackingWarnings`)，前端做列表跟单与详情轨迹都不用再调飞驼专用接口。
- **自动回填业务单的两个航次(当前已停用)：** 设计为订阅成功与每次收到增量推送后，把跟踪数据里的航次写回业务单——头程大船航次(`firstVessel.voyage`) → **航次** `InnerVoyno`，港区船舶计划航次(`terminalPlan.voyage`) → **码头航次** `TerminalVoyno`。 **现行代码里两处调用都已注释掉**，业务单航次不会被回填，详见 2.2。

## 2.2 自动回填业务单的两个航次

飞驼这个接口返回**四个** `voyage`，含义各不相同，其中两个会回填业务单：

| 飞驼字段 | 是什么航次 | 落库列 | 回填到业务单 |
| :-- | :-- | :-- | :-- |
| `result.firstVessel.voyage` | 头程大船航次(**船公司口径**) | `App_FeituoTrackingDynamics.FirstVesselVoyage` | ✅ **航次** `InnerVoyno` |
| `result.terminalPlan.voyage` | 港区船舶计划航次(**码头口径**) | `App_FeituoTrackingDynamics.TerminalPlanVoyage` | ✅ **码头航次** `TerminalVoyno` |
| `result.routes[].modeDetails.voyage` | 各航段航次 | `App_FeituoTrackingRoutes.ModeVoyage` | ❌ 只落库 |
| `result.places[].voyage` | 发生地航次 | `App_FeituoTrackingPlaces.Voyage` | ❌ 只落库 |

> [!WARNING] **现行代码里回填已停用。** `SubscribeContainerAsync` 与 `ProcessIncrementPushAsync` 里调用 `BackfillVoynosToOrderAsync` 的那一行都被注释掉了，方法本身还在。以下是恢复调用后的设计口径。

**触发时机**：订阅成功后、以及**每次收到增量推送**后各回填一次，两条路径都走同一个私有方法 `FeituoAdminAppService.BackfillVoynosToOrderAsync`。推送里的港区计划航次会变，所以两处都得填，业务单的航次才能一直跟着最新。

**覆盖策略**：飞驼返回非空即覆盖，以飞驼为准；返回空则跳过，不会把业务单上已有的航次清掉。

> [!IMPORTANT] **回填统一读跟踪主表，不从报文取值。** 订阅是全量 `result`、推送是按 `dbtype` 的增量，两种报文结构不同；但落库后都汇聚到 `App_FeituoTrackingDynamics` 的 `FirstVesselVoyage` / `TerminalPlanVoyage` 两列。从主表读能少写一套解析，也不会出现「订阅那条路径填了、推送那条口径不一样」的问题。前提是调用点必须在跟踪数据**已落库之后**——`QueryAndPersistAsync` 与 `ApplyAsync` 内部都有 `SaveChanges`，满足这个前提。

> [!NOTE] **这给码头航次提供了第二个来源。** 「码头船舶计划」需要码头航次，原本只能靠用户手填或调「船司航次转码头航次」换算；订过集装箱跟踪的单子现在会自动带上，等于省掉那次换算请求。但**只有订过跟踪的单子才有**，所以码头船舶计划里的换算兜底不能去掉。

# 3. 订阅单号规则 (核心业务规则)

| 模块 | 判断依据 | 取值规则 | 报错条件 |
| :-- | :-- | :-- | :-- |
| **海运出口** | `SeaExport.BLType`(装运方式) | `BLType=0(整箱)` → 用**主提单号** `TransportOrder.MblNum`<br/>其余(拼箱主票/拼箱分票) → 用**第一个箱号** `OrderCtn.CtnNo` | 整箱无主提单号 → "该海运出口未填写主提单号，无法订阅"<br/>非整箱无箱号 → "该海运出口无箱号信息，无法订阅" |
| **海运进口** | 无 `BLType` 字段(实体上不存在) | **优先主提单号**，无主提单号则用**第一个箱号** | 两者都没有 → "该海运进口既未填写主提单号也无箱号信息，无法订阅" |

**其它订阅参数：**

| 飞驼参数 | 取值 | 说明 |
| :-- | :-- | :-- |
| `carrierCode` | **船公司 `Carrier.EdiCode`** | 未维护 EdiCode 直接报错(与云当取 `Code` 不同，飞驼明确用 EDI 代码) |
| `businessNo` | `{Relay:Customer}_{业务单Id无连字符}` | 双重职责：中转站按前缀路由、本机按此定位订阅记录。增量推送会原样回传它 |
| `polCode` / `podCode` | `POL.EdiCode` / `POD.EdiCode` | polCode 参与飞驼数据判断，podCode 仅显示 |
| `portCode` / `isExport` | **成对传** | `portCode` 取这一票**在国内靠的那个港**的 EDI 代码：出口取起运港 `PolCode`、进口取目的港 `PodCode`；`isExport` 出口 `E`、进口 `I`。取不到港口代码时两个都不传，退回只订船公司数据。**传了就产生港区数据计费** |
| `billCategory` | 不传 | 由飞驼首次订阅后按有数据的类型自动确定 |

> [!IMPORTANT] **"第一个箱号"已做稳定排序**：按 `OrderCtn.Id` 升序取第一条非空 `CtnNo`，避免每次订阅取到不同的箱号。

# 4. 架构与数据流

```
业务端 ──取token(头 X-Relay-Token)──▶ 中转站 /relay/feituo/token ──▶ access_token
业务端 ──订阅/查询(Bearer token, body带businessNo)──▶ 飞驼 /application/v1/query ──▶ 全量跟踪数据(当场落库)

[增量+预警 · 唯一自动更新回调]
飞驼 ──增量+预警──▶ 中转站 /relay/feituo/increment-push ──按param.businessNo前缀路由──▶ 业务端 /api/feituo/increment-push
业务端 ──按businessNo定位订阅──▶ 有RawJson则按dbtype合并；无则当全量落库 → 整体落库 + 预警累积
```

**为什么推送要走中转站：** 飞驼只接受**一个固定回调地址**，而本系统部署在多台服务器上。云当推送靠报文里的 `customer` 字段路由，**飞驼推送报文没有 customer 字段**，因此改用订阅时上传的 `businessNo`：把客户标识编成前缀 `{Customer}_{业务单Id}`，飞驼在 `param.businessNo` 原样回传，中转站按前缀匹配下游(配置项 `IncrementBusinessNoField`)。

**读不到 businessNo 时兜底广播**：若飞驼改了报文结构导致读不到，中转站不会丢弃，而是把报文发给全部下游，由各业务服务器按 `billNo`/`containerNo` + `carrierCode` 自行认领，认领不上直接忽略。触发时中转站日志会记 `[路由未命中]`。

**增量合并怎么做的(关键设计)：** 不直接改数据库行，而是

1. 取出跟踪主表的 `RawJson`(上一次的完整快照，结构 = 飞驼 `data`)；没有则用本次推送搭基线(首次推送即为全量)；
2. 在**内存对象**上按 `dbtype` 应用增量(1新增 / 2修改 / 3删除)；
3. 把合并后的完整快照交给 `FeituoContainerTrackingManager.PersistDataAsync` 整体落库。

这样主表、子表、`RawJson` 三者一次对齐，且**复用订阅落库那套映射**，不必为增量再维护一遍 200+ 字段的写库代码。

# 6. 落库结构

| 表 | 实体 | 说明 |
| :-- | :-- | :-- |
| `App_FeituoContainerSubscriptions` | `FeituoContainerSubscription` | 订阅记录，**一条业务单一条**，按租户隔离。存订阅参数、飞驼应答、最近推送报文 |
| `App_FeituoPushLogs` | `FeituoPushLog` | 每次增量+预警推送的原始报文(全局，不按租户)，无论是否匹配都记录；`AppliedCount`/`WarningCount` 记处理结果 |
| `App_FeituoTrackingDynamics` | `FeituoTrackingDynamic` | 跟踪解析主表，按 `SubscriptionId` 唯一。含 query/actualParam、船公司、订舱、接货地、交货地、头程大船、当前状态、港区船舶计划(全部平铺) + `RawJson` |
| `App_FeituoTrackingPlaces` | `FeituoTrackingPlace` | 发生地 `places[]` |
| `App_FeituoTrackingRoutes` | `FeituoTrackingRoute` | 路径 `routes[]`(含 `modeDetails` 平铺) |
| `App_FeituoTrackingContainers` | `FeituoTrackingContainer` | 集装箱 `containers[]` |
| `App_FeituoTrackingContainerStatuses` | `FeituoTrackingContainerStatus` | 箱物流节点 `containers[].status[]`。`Sort` 按飞驼返回的数组下标自增(从 0 开始)，**不是**飞驼报文里的 `sort` 字段 |
| `App_FeituoTrackingWarnings` | `FeituoTrackingWarning` | 异常预警 `containers[].warnings[]`，**只来自增量推送**，按票**累积**保留 |
| `App_FeituoTrackingVessels` | `FeituoTrackingVessel` | 船舶 `vessel[]` |
| `App_FeituoTrackingPackingLists` | `FeituoTrackingPackingList` | 装箱单 `document.packinglist[]` |
| `App_FeituoTrackingVgms` | `FeituoTrackingVgm` | VGM `document.vgm[]` |

**二次更新策略(全量覆盖)：** 主表按 `SubscriptionId` 定位，**标量整表覆盖**；子表**删旧建新**，完全以最新快照为准(飞驼每次返回都是完整快照)。原始报文 `App_FeituoPushLogs` 每次新增一行完整保留历史。

> [!IMPORTANT] **预警表是删旧建新的唯一例外。** `App_FeituoTrackingWarnings` 的数据只来自增量推送，飞驼「订阅+查询」接口**从不返回** `warnings`。如果把它一起删旧建新，任意一次手动订阅刷新都会把历史预警清空。因此 `DeleteChildrenAsync` 里**没有**预警表，预警按"同箱号+同事件代码+同发生时间"去重累积，重复推送只刷新描述与接收时间。

**时间字段一律存字符串**：飞驼返回的时间格式为 `2025/09/01 00:00:00`，原样保存避免解析歧义与时区问题。

# 7. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **1. 船公司必须维护 EDI 代码。** `carrierCode` 取 `Carrier.EdiCode`，未维护直接报错"该业务单未关联船公司或船公司未维护EDI代码，无法订阅"。这与云当(优先取 `Code`)不同，不要混淆。

> [!IMPORTANT] **2. 只把「增量+预警」地址提供给飞驼客服配置。** 地址为中转站的纯 URL，**不允许带验证、不能带 Query 参数**：
>
> ```
> POST {中转站}/relay/feituo/increment-push
> ```
>
> 更新通知路径(`/relay/feituo/push` 与业务端回查逻辑)已删除；飞驼确认首次增量推送即为全量，本地无基线时直接落库。

> [!IMPORTANT] **3. `Relay:Customer` 必须配置且与中转站 `Downstreams[].Customer` 一致。** 它是 `businessNo` 的前缀，配错会导致推送路由不到本机(中转站日志会打 `[路由未命中]`)。

> [!IMPORTANT] **4. 飞驼推送IP白名单待补。** `Relay:Providers:feituo:PushAllowedIps` 当前为空(=不校验)。拿到飞驼推送来源IP后务必填上，否则任何来源都能往推送入口发数据。

> [!IMPORTANT] **5. 港区数据已启用，且单独计费。** 订阅时会成对传 `portCode` + `isExport`，因此除船公司数据外还能拿到港区/海关节点(进场、放行、装船等)。 **这部分与飞驼单独结算**，订阅量上去时留意账单。
>
> **`portCode` 取的是这一票在国内靠的那个港**：海运出口装货在起运港(`PolCode`)、海运进口卸货在目的港(`PodCode`)。拿另一头去传等于给了个国外港，港区侧什么都查不到——这是最容易写反的地方。
>
> `portCode` 与 `isExport` 飞驼要求**成对使用**，所以港口代码取不到(没选港、或港口没维护 EDI 代码)时**两个都不传**，退回「只订船公司数据」，订阅本身照常成功。不因为基础资料缺一个 EDI 代码就让整票订不上。
>
> 判断集中在 `FeituoContainerTrackingManager.ResolvePortCodeAndIsExport`，订阅与推送回查共用，不会两边口径不一致。

> [!NOTE] **6. 推送签名校验未启用。** 飞驼支持 HmacSHA1 签名(`x-ft-timestamp`/`x-ft-nonce`/`x-ft-client`/`x-ft-signature`)，但官方说明**默认可不做验证**。本系统沿用既有方案：中转站做 IP 白名单，业务端校验 `X-Relay-Token`。

> [!IMPORTANT] **7. 需自行生成 EF Core 迁移。** 跟踪相关表见第 6 节；`App_FeituoPushLogs` 需有 `WarningCount`、`AppliedCount`(原 `RequeriedCount` 已更名)，**不要**再加 `PushType`。迁移文件由开发人员自行生成。

> [!NOTE] **8. 增量推送的 `businessNo` 文档里没写，但飞驼确认会回传。** 飞驼文档(327653391e0)的 `param` 结构没有列出 `businessNo`，**已与飞驼确认实际会原样回传**，路由与订阅匹配都依赖它。上线后建议拿一票实际推送确认一次：中转站日志出现 `[路由命中]` 即正常；若出现 `[路由未命中]` 说明没回传，此时不会丢数据(会兜底广播、下游按单号/箱号认领)，但要找飞驼确认。

> [!NOTE] **9. 增量合并的节点定位键是"状态代码 + 地点CODE"。** 飞驼的轨迹节点**没有主键**，`dbtype=2(修改)` 时只能靠字段组合定位。这里刻意**不把发生时间纳入键**——预计转实际(`isEsti` 由 `Y` 变 `N`)时发生时间必然会变，纳入键就会重复插入一条而不是更新原节点。副作用：同一箱在同一地点出现两次相同状态代码时会被合并成一条。实际业务里几乎不出现；业务员手动重新订阅会以飞驼完整快照纠正。

> [!NOTE] **10. 增量推送不带 `currentStatus` / `receipt` / `delivery`，这三处由本地回算。** 而列表摘要的"当前节点"和 ETD/ETA 恰好读的就是这三处，不回算就会一直停在上一次订阅/合并的旧值。
>
> - 当前节点：取合并后所有箱里**时间最新的实际节点**(没有实际节点则取最新的预计节点)，经纬度从同 CODE 的发生地补。
> - 接货地/交货地：按**地点CODE**(不是 `type`，飞驼的地点类型枚举未公开)匹配推送里的发生地，同 CODE 多条时接货地取 `type` 最小的、交货地取最大的；匹配不上就不动，宁可保旧值也不写错值。业务员手动重新订阅会用飞驼查询接口的完整值覆盖。

> [!NOTE] **11. 飞驼 `status[].sort` 故意不对接，不要当成漏接去补。** 订阅+查询文档(<https://doc.freightower.com/318680523e0>)物流节点有 `sort`(标题「排序」，说明「按业务节点排序」)。实测飞驼**已经按该顺序返回数组**，`sort` 的 1、2、3 与数组位置一一对应，再接到表里只是多存一个从 1 起算的序号。增量+预警文档甚至没列这个字段。
>
> 因此：
>
> - `FeituoContainerStatusDto` / `FeituoIncrementStatusDto` **不要加** `sort` 属性；
> - 表 `App_FeituoTrackingContainerStatuses.Sort` 在 `InsertChildrenAsync` 里按数组下标 `sort++` 写入，从 0 开始；
> - 前端画轨迹用 `status[]` 数组顺序即可，详情反序列化 `RawJson` 后也不会带回 `sort`。
