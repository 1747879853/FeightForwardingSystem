# 1. 说明

前端集装箱跟踪只需对接 **两个接口**：订阅、查询。token 获取、飞驼增量推送接收与自动落库等均由后端处理，前端无需关心。

另外**海运出口/海运进口的列表与详情已直接带上运踪字段**(见「6. 海运出口/海运进口 列表与详情中的运踪字段」)，做列表跟单不用额外调接口。

**海运出口与海运进口都支持**，用 `bizType` 区分。

> 完整的架构/订阅规则/推送说明见：`飞驼对接-集装箱跟踪订阅与推送.md`
>
> 件杂货(散货/RORO)货物跟踪是另一套接口与数据结构，见 `飞驼对接-件杂货货物跟踪-前端对接.md`。

# 2. 接口清单

| 接口 | 方法 | 地址 | 权限 |
| :-- | :-- | :-- | :-- |
| 集装箱跟踪订阅 | `POST` | `/api/services/app/FeituoAdmin/SubscribeContainerAsync` | `Admin.ExternalApi.Use` |
| 查询跟踪数据 | `POST` | `/api/services/app/FeituoAdmin/GetContainerTrackingAsync` | `Admin.ExternalApi.Get` |

> [!WARNING] **2026-08-09 接口地址已变更。** 飞驼的所有接口合并到了同一个服务 `FeituoAdmin`，地址前缀由 `FeituoContainerAdmin` 改为 `FeituoAdmin`。方法名与入参出参**完全没变**。

> 返回体 ABP 统一包一层 `result`。

# 3. 集装箱跟踪订阅 SubscribeContainerAsync

## 3.1 请求参数 (FeituoContainerSubscribeInputDto)

| 字段名 | 类型 | 含义 | 必填 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| **bizType** | int | 业务类型 | 是 | 0=海运出口 1=海运进口 |
| **orderIds** | Guid[] | 业务单Id集合 | 是 | 海运出口Id / 海运进口Id，可批量；内部自动去重 |

**请求示例：**

```json
{
  "bizType": 0,
  "orderIds": ["3f2504e0-4f89-11d3-9a0c-0305e82c3301"]
}
```

## 3.2 返回结构 (FeituoContainerSubscribeResultDto)

| 字段名       | 类型  | 含义                            |
| :----------- | :---- | :------------------------------ |
| total        | int   | 提交订阅的总条数                |
| successCount | int   | 订阅成功条数                    |
| failedCount  | int   | 订阅失败条数                    |
| items        | array | 各业务单订阅结果，元素见「3.3」 |

## 3.3 单条订阅结果 (items[] - FeituoContainerSubscribeItemResultDto)

| 字段名         | 类型   | 含义                                          |
| :------------- | :----- | :-------------------------------------------- |
| orderId        | Guid   | 业务单Id                                      |
| bizType        | int    | 业务类型：0=海运出口 1=海运进口               |
| subscriptionId | Guid?  | 本地订阅记录Id(订阅记录创建成功才有)          |
| isSuccess      | bool   | 是否订阅成功                                  |
| billNo         | string | 上传给飞驼的单号(按箱号订阅时为空)            |
| containerNo    | string | 上传给飞驼的箱号(按单号订阅时为空)            |
| carrierCode    | string | 上传给飞驼的船公司代码(取船公司 EdiCode)      |
| businessNo     | string | 上传给飞驼的客户自定义业务编号                |
| statusCode     | int    | 飞驼返回的状态码(20000有数据)                 |
| message        | string | 飞驼返回的提示信息                            |
| alertMessage   | string | 飞驼返回的异常提示信息                        |
| errorMessage   | string | 失败原因(本地校验失败或请求异常时有值)        |
| data           | object | 本次返回的跟踪数据，结构见「5. 跟踪数据结构」 |

## 3.4 订阅单号规则(前端需知)

| 模块 | 规则 | 报错提示 |
| :-- | :-- | :-- |
| 海运出口 | 装运方式=整箱 → 用**主提单号**；拼箱主票/拼箱分票 → 用**第一个箱号** | 整箱无主提单号：`该海运出口未填写主提单号，无法订阅`<br/>非整箱无箱号：`该海运出口无箱号信息，无法订阅` |
| 海运进口 | 优先**主提单号**，无主提单号则用**第一个箱号** | 都没有：`该海运进口既未填写主提单号也无箱号信息，无法订阅` |
| 两者 | 船公司代码取 `EdiCode` | 未维护：`该业务单未关联船公司或船公司未维护EDI代码，无法订阅` |

> 单条失败不影响其它条：失败信息在该条的 `errorMessage` 上，不会整批抛错。

# 4. 查询跟踪数据 GetContainerTrackingAsync

## 4.1 请求参数 (FeituoContainerTrackingInputDto)

| 字段名      | 类型 | 含义     | 必填 | 说明                  |
| :---------- | :--- | :------- | :--- | :-------------------- |
| **bizType** | int  | 业务类型 | 是   | 0=海运出口 1=海运进口 |
| **orderId** | Guid | 业务单Id | 是   |                       |

## 4.2 返回结构 (FeituoContainerTrackingDto)

| 字段名 | 类型 | 含义 |
| :-- | :-- | :-- |
| orderId | Guid | 业务单Id |
| bizType | int | 业务类型：0=海运出口 1=海运进口 |
| hasSubscription | bool | 是否已订阅(false 表示该单从未订阅过) |
| subscriptionId | Guid? | 本地订阅记录Id |
| isSuccess | bool | 订阅是否成功 |
| billNo | string | 订阅用的单号 |
| containerNo | string | 订阅用的箱号 |
| carrierCode | string | 订阅用的船公司代码(EdiCode) |
| businessNo | string | 上传给飞驼的客户自定义业务编号 |
| subscribeTime | DateTime? | 最近一次订阅/回查时间 |
| lastPushTime | DateTime? | 最近一次收到飞驼推送的时间 |
| lastQueryTime | DateTime? | 最近一次回查落库时间 |
| message | string | 飞驼返回的提示信息 |
| alertMessage | string | 飞驼返回的异常提示信息 |
| errorMessage | string | 失败原因 |
| data | object | 跟踪数据，结构见「5」；未取到数据时为 null |
| placeFallbackApplied | bool | 是否用**计划地点**兜底补过 `data.result` 里的 `receipt`/`delivery`/`firstVessel`，见下方说明 |

> [!IMPORTANT] **`placeFallbackApplied=true` 时，船期来自计划而非实际跟踪。** 订阅刚受理、飞驼还在采集时（`statusCategory=PROCESS`、`statusDescription="Shipment updating"`），报文里往往**只有 `places`（计划地点）和一个空的 `containers`**，没有 `receipt`/`delivery`/`firstVessel`——界面上「起运预计开航」「目的预计到港」「头程船名航次」就会全是空的，而其实 `places` 里已经带了这些信息。
>
> 本接口在这三个节点**整个为 null** 时，会用计划地点补齐：起运侧取 `type=2`（缺失退 `type=1`）、目的侧取 `type=4`（缺失退 `type=5`），船名航次取起运侧那条。飞驼给了就一个字段都不动。
>
> 前端拿到 `true` 时建议加一句「以下为计划船期」的说明，让用户知道这还不是实际跟踪数据。 **`currentStatus`（当前节点）不兜底**：计划地点没有事件代码与描述，硬凑出来的当前节点会误导，所以那一格仍为空。

## 6.3 异常预警明细 (feituoTrackingWarnings[] - FeituoTrackingWarningDto)

**仅详情返回**，按本地收到时间**倒序**(最新的在最前)。

| 字段名        | 类型     | 含义                                       |
| :------------ | :------- | :----------------------------------------- |
| eventCategory | string   | 事件类型(如 `DELAY` 延误)                  |
| eventCode     | string   | 事件状态代码(如 `WGITM`)                   |
| eventTime     | string   | 事件发生时间(飞驼原样字符串)               |
| portCode      | string   | 事件发生地点CODE                           |
| portPlace     | string   | 事件发生地点名                             |
| equipmentCode | string   | 箱号                                       |
| description   | string   | **预警描述(中文)，主展示字段**，可能含换行 |
| descriptionEn | string   | 预警描述(英文)                             |
| receivedTime  | DateTime | 本地收到该预警的时间                       |

**示例：**

```json
{
  "eventCategory": "DELAY",
  "eventCode": "WGITM",
  "eventTime": "2025-05-13 16:00:00",
  "portCode": "CNTXG",
  "portPlace": "TIANJIN(XINGANG)",
  "equipmentCode": "OOCU0863070",
  "description": "起运港船舶离港前48小时还未进港;\n ETD:2025/05/15 16:00:00",
  "descriptionEn": "Container Not Yet Gated-In 48 Hours Before Vessel Departure;  ETD:2025/05/15 16:00:00",
  "receivedTime": "2026-08-08T19:20:31"
}
```

> [!IMPORTANT] 异常预警**只来自飞驼的「增量+预警推送」**，订阅/查询接口从不返回它。所以：
>
> - 刚订阅完还不会有预警，要等飞驼推；
> - 预警是**累积**的，不会因为后端回查而被清掉；
> - 同一条预警(同箱号+同事件代码+同发生时间)重复推送不会产生重复记录。

# 7. 注意事项

- **订阅即查询**：飞驼订阅和查询是同一个接口，订阅成功时 `data` 里就带回了当前全量数据，前端可直接展示，无需再调查询接口。
- **数据会自动更新**：订阅成功后飞驼有变化会推送增量+预警，后端直接合并落库(首次推送即为全量)。前端**不需要轮询飞驼**，调 `GetContainerTrackingAsync` 或看列表/详情里的运踪字段即可。
- **异常预警只从增量推送来**：`hasWarning`/`warningCount`/`feituoTrackingWarnings` 依赖飞驼「增量+预警推送」已由客服配置回调地址；若尚未配置，这几个字段会一直是 false/0/空数组。
- **首次订阅可能无数据**：`statusCode=20001` 或 `data` 为空表示订阅成功但飞驼尚未抓到数据，属正常情况，等推送更新即可。
- **"数据获取中"阶段也可能已有船期**：此时报文只有计划地点，会用它兜底补出预计开船/预计到港/船名航次并置 `placeFallbackApplied=true`。**三处都做了这个兜底**：`GetContainerTrackingAsync` 的 `data.result` 里的 `receipt`/`delivery`/`firstVessel`，以及海运出口/进口**列表与详情**里 `feituoTracking` 摘要的 `polEtd`/`polAtd`/`podSta`/`podEta`/`podAta`/`firstVesselName`/`firstVesselVoyage`。字段名不变，前端不用改取值路径。
- **重复订阅是安全的**：一条业务单只保留一条订阅记录，重复调用等同于刷新最新数据。
- **未订阅过的单**：`GetContainerTrackingAsync` 返回 `hasSubscription=false`，`data` 为 null。
- **进出口无需前端指定**：`bizType` 只用于本系统区分从哪个模块取业务单，发给飞驼的进出口标识由后端按它自动带。
- **港区/海关节点已启用**：订阅时后端会带上港区代码(出口取起运港、进口取目的港的 EDI 代码)，因此除船公司节点外还能拿到进场、放行、装船等港区/海关节点。**业务单没选港、或港口没维护 EDI 代码时拿不到这部分**，此时订阅照常成功、只是没有港区节点。
- **不要对接飞驼 `status[].sort`**：飞驼已按业务节点顺序返回物流节点数组，`sort` 与数组位置重复。后端不接、详情不回这个字段，前端按 `status[]` 数组顺序画轨迹即可。
