# 1. 背景意图 (Background)

飞驼「集装箱综合跟踪」提供一票货从提空箱到还空箱的全程物流节点(覆盖近百家船公司及中国港区/海关数据)。本次把该能力接入**海运出口**与**海运进口**两个模块，并同时对接飞驼的**更新通知推送**：订阅成功后飞驼在数据变化时主动通知，系统自动回查取最新全量数据并落库，实现轨迹自动更新。

对接文档：

- 订阅+查询：<https://doc.freightower.com/318680523e0>
- 更新通知推送：<https://doc.freightower.com/327637324e0>

# 2. 核心逻辑变更 (Changes)

## 2.1 订阅单号规则(业务核心)

| 模块 | 规则 |
| :-- | :-- |
| 海运出口 | `BLType=0(整箱)` → 用主提单号 `TransportOrder.MblNum`；其余(拼箱主票/拼箱分票) → 用**第一个箱号** `OrderCtn.CtnNo`；取不到对应值直接报错 |
| 海运进口 | 实体上**没有 `BLType` 字段**，改为：优先主提单号，无主提单号则用第一个箱号，两者都没有才报错 |
| 两者 | `carrierCode` 取**船公司 `Carrier.EdiCode`**(未维护直接报错)；箱号按 `OrderCtn.Id` 升序取首条，保证"第一个箱号"稳定 |

## 2.4 推送路由方案(与云当的关键差异)

云当推送靠报文里的 `customer` 字段路由，**飞驼推送报文没有该字段**。方案：订阅时把客户标识编进 `businessNo`，格式 `{Relay:Customer}_{业务单Id无连字符}`，飞驼推送时原样回传 `BUSINESSNO`，中转站按前缀匹配下游(多个 Customer 互为前缀时取**最长匹配**避免串台)。该 `businessNo` 同时用于业务端定位订阅记录。

## 2.5 海运出口/海运进口 列表与详情返回运踪

参照云当在海运出口列表/详情的做法(3 个字段：是否订阅/是否订阅成功/最后一个有实际时间的海运节点)，为飞驼做等价接入，并**同时覆盖海运进口**(云当此前只有海运出口)。

- **列表**(`SeaExportAdmin.GetPagedListAsync` / `SeaImportAdmin.GetPagedListAsync`)：返回 `IsFeituoSubscribed`、`IsFeituoSubscribeSuccess`、`FeituoTracking`(摘要)
- **详情**(`SeaExportAdmin.DetailAsync` / `SeaImportAdmin.DetailAsync`)：以上三项 + `FeituoTrackingDetail`(完整跟踪数据，前端不用再调 `GetContainerTrackingAsync`)
- 摘要 DTO `FeituoTrackingSimpleDto` 分五组：订阅状态、整票数据状态、当前节点、关键时间(起运ETD/ATD、目的STA/ETA/ATA)、船期订舱，外加甩柜标记与飞驼可视化轨迹页链接
- 新增只读查询器 `FeituoTrackingQueryManager`(`GetTrackingSummariesAsync` 批量 / `GetTrackingDetailAsync` 单票)，**与调飞驼落库的 `FeituoContainerTrackingManager` 职责分开**，海运模块不会拿到能打外部接口的依赖

**为什么比云当简单**：云当要 订阅→`YundangId`→`ShipmentDynamic`→`OceanNodes` 再筛出最后一个有 `ActualityTime` 的节点；飞驼的 `currentStatus` 本身就是"当前节点"，落库时已平铺进跟踪主表，列表一次查询即可。

**性能**：列表共 3 次批量查询(订阅表、跟踪主表、甩柜箱号)，均按 `OrderId`/`SubscriptionId`/`TrackingId` 走索引，沿用既有 `transportOrderIds` 批量字典写法，无 N+1；跟踪主表投影时**排除 `RawJson`**(体积大，列表用不上)。

## 2.6 落库策略

主表按 `SubscriptionId` 定位并**标量整表覆盖**，子表**删旧建新**，完全以最新快照为准(飞驼每次返回都是完整快照)；`RawJson` 保存飞驼 `data` 原文。查询接口直接反序列化 `RawJson` 返回，与订阅接口返回结构完全一致，避免维护两套 200+ 字段的映射代码。

# 3. 避坑指南 (Blockers & Notes)

> [!IMPORTANT] **1. 需自行生成 EF Core 迁移。** 新增 9 张表：`App_FeituoContainerSubscriptions`、`App_FeituoPushLogs`、`App_FeituoTrackingDynamics`、`App_FeituoTrackingPlaces`、`App_FeituoTrackingRoutes`、`App_FeituoTrackingContainers`、`App_FeituoTrackingContainerStatuses`、`App_FeituoTrackingVessels`、`App_FeituoTrackingPackingLists`、`App_FeituoTrackingVgms`。

> [!IMPORTANT] **2. 推送地址须提供给飞驼客服配置**：`POST {中转站}/relay/feituo/push`(纯 URL，不允许带验证与 Query 参数)。

> [!IMPORTANT] **3. 飞驼推送IP白名单待补**：`Relay:Providers:feituo:PushAllowedIps` 当前为空(=不校验)，拿到飞驼推送来源IP后务必填上。

> [!IMPORTANT] **4. `Relay:Customer` 必须配置且与中转站 `Downstreams[].Customer` 一致**，否则推送路由不到本机(中转站日志会打 `[路由未命中]`)。

> [!NOTE] **5. `portCode`/`isExport` 都不传**：已与飞驼确认**可自动区分进出口**，无需传 `isExport`；`portCode` 涉及港区数据单独计费，默认不启用，因此只取船公司数据。如需港区+海关细节点(进场/放行/装船等)，需补传 `portCode` 与 `isExport`(飞驼要求两者绑定使用)并确认计费。

> [!NOTE] **6. 船公司代码用 EdiCode，与云当不同**：云当是优先 `Code` 再 `EdiCode`，飞驼明确用 `EdiCode`，不要照搬云当的 `ResolveCarrierCode`。

> [!NOTE] **7. 推送签名校验未启用**：飞驼支持 HmacSHA1 签名(`x-ft-*` 头)但官方说明默认可不验证；本系统沿用中转站IP白名单 + 业务端 `X-Relay-Token` 的既有方案。

# 4. 追加对接：集装箱综合跟踪(增量+预警推送)

对接文档：<https://doc.freightower.com/327653391e0>

## 4.1 背景意图

上面对接的「更新通知推送」只回传订阅参数，收到后必须**回查**一次「订阅+查询」才拿得到数据——多一次外部调用、也多一段延迟。飞驼另有一个「增量+预警推送」，报文里**直接带着变化的节点**，还带着**异常预警(warnings)**——而预警是「订阅+查询」接口**从来不返回**的数据，只能从这个推送拿。因此本次追加对接它，并顺手优化前一版的落库与展示。

## 4.2 两种推送的差异(为什么必须分开写)

|  | 更新通知(327637324e0) | 增量+预警(327653391e0) |
| :-- | :-- | :-- |
| 报文 | `{ referenceno, params[] }` | `{ param, result }` |
| 内容 | 只有订阅参数 | 变化的 places/terminalPlan/containers/status/warnings |
| 收到后 | **必须回查**飞驼 | 按 `dbtype` 增量合并，**不回查** |
| 中转站路由 | 按 `params[].BUSINESSNO` 前缀精确路由 | 按 `param.businessNo` 前缀精确路由(大小写与层级不同) |
| 异常预警 | 无 | **有(唯一来源)** |

## 4.3 新增文件

**业务端**

- `App/ExternalApi/Feituo/Dto/FeituoIncrementPushDto.cs`：增量推送报文全量 DTO(param/result/places/terminalPlan/containers/status/warnings + `dbtype` 常量) + 预警展示 DTO
- `App/ExternalApi/Feituo/FeituoIncrementTrackingManager.cs`：按 `dbtype` 增量合并 + 预警累积落库
- `App/ExternalApi/Feituo/FeituoIncrementPushAdminAppService.cs` + `IFeituoIncrementPushAdminAppService.cs`：推送处理(记原始报文 → 匹配订阅 → 合并 → 落预警)

**实体**

- `FeituoTracking.cs` 内新增 `FeituoTrackingWarning`(表 `App_FeituoTrackingWarnings`)

## 4.4 修改文件

- `FeituoPushLog.cs`：新增 `PushType`(0=更新通知 1=增量+预警)、`WarningCount`；`ItemCount`/`RequeriedCount` 的含义按推送类型分别说明
- `FeituoContainerTrackingManager.cs`：新增公开方法 `PersistDataAsync`(把一份完整快照落库，不请求飞驼)，供增量合并后复用同一套映射

- `SeaExportAdminAppService.cs` / `SeaImportAdminAppService.cs`：详情补取预警明细

- 中转站 `RelayOptions.cs`：新增 `IncrementForwardPath`、`IncrementBusinessNoField`

- 中转站 `appsettings.json`：`feituo` 节点补 `IncrementForwardPath`、`IncrementBusinessNoField`

## 4.5 核心设计：合并走"快照 → 内存合并 → 整体落库"

不直接改数据库行，而是：

1. 取跟踪主表的 `RawJson`(上次的完整快照，结构 = 飞驼 `data`)；
2. 在**内存对象**上按 `dbtype`(1新增/2修改/3删除)合并；
3. 交给 `PersistDataAsync` 整体落库。

好处：复用回查那套 200+ 字段映射，主表/子表/`RawJson` 一次对齐，增量逻辑只需关心"怎么合"，不必关心"怎么写库"。

**只覆盖有值的字段**：推送的 `result` 是查询 `result` 的**子集**(没有 booking/receipt/delivery/firstVessel/currentStatus/routes/vessel/document/iframeUrl)，整段替换会把回查才有的富字段清空。

**本地无快照时退回回查**：订阅后飞驼一直没数据的票没有基线可合并，此时调一次 `QueryAndPersistAsync` 补齐全量，再单独落预警。

## 4.6 路由方案：沿用 `businessNo`

增量推送的 `param` 是**订阅参数的原样回显**。飞驼文档(327653391e0)的 `param` 结构里没有列出 `businessNo`，**但已与飞驼确认实际会原样回传**，因此两种推送的路由规则完全一致，只是字段名的大小写与所在层级不同：

|           | 报文里的位置          | 中转站配置项               |
| :-------- | :-------------------- | :------------------------- |
| 更新通知  | `params[].BUSINESSNO` | `BusinessNoField`          |
| 增量+预警 | `param.businessNo`    | `IncrementBusinessNoField` |

两者共用同一个最长前缀匹配函数(多个 Customer 互为前缀时不会串台)。业务端定位订阅记录也优先用 `businessNo`，读不到才退回按 `billNo`/`containerNo` + `carrierCode` 匹配。

**兜底不丢数据**：中转站读不到 `businessNo` 时不丢弃，而是广播给全部下游由其自行认领，日志记 `[路由未命中]`。正常不会触发。

## 4.7 优化前一版的地方

| 优化点 | 说明 |
| :-- | :-- |
| 推送日志能区分类型 | `FeituoPushLog` 加 `PushType`，两种推送同表存放但可分别排查；同时加 `WarningCount` |
| 列表当前节点不再滞后 | 增量推送不带 `currentStatus`，改由合并结果**回算**(所有箱里时间最新的实际节点)，经纬度从同 CODE 的发生地补 |
| 列表 ETD/ETA 不再滞后 | 增量推送不带 `receipt`/`delivery`，改按**地点CODE**从推送的 `places` 回填(不按 `type` 硬编码，飞驼地点类型枚举未公开) |
| 少一次外部调用 | 增量推送直接合并，不再像更新通知那样每次都回查飞驼 |
| 预警可用于跟单 | 列表给红点(条数+最近一条)、详情给全量明细 |

# 5. 避坑指南(增量+预警部分)

> [!IMPORTANT] **1. 需自行生成 EF Core 迁移。** 新增表 `App_FeituoTrackingWarnings`；`App_FeituoPushLogs` 新增列 `PushType`、`WarningCount`。

> [!IMPORTANT] **2. 只配增量推送这一个回调**：`POST {中转站}/relay/feituo/increment-push`(纯 URL)。**不要再配更新通知** —— 两个都配会对同一次变化重复触发(多花一次查询配额)，还会让"全量回查覆盖"和"增量合并写回"两条写入路径出现并发窗口(增量读完 `RawJson` 到写回之间若全量先提交，会被旧快照+增量盖掉；下次推送能自愈，但只开一个就不会发生)。更新通知的代码路径保留，供手动订阅刷新与"无基线兜底回查"使用。补充：两者数据结构上**不冲突**，都走同一个 `PersistTrackingAsync` 写同一份快照，后写的赢且输的那份是赢的那份的子集；预警表不在删旧建新范围内，全量回查冲不掉它。

> [!NOTE] **3. 增量推送的 `businessNo` 文档里没写，但飞驼确认会回传。** 路由与订阅匹配都依赖它(见 4.6)。上线后拿一票实际推送确认一次：中转站日志出现 `[路由命中]` 即正常；若是 `[路由未命中]`，说明没回传 —— 此时不丢数据(兜底广播、下游按单号/箱号认领)，但要找飞驼确认。

> [!IMPORTANT] **4. 预警表绝不能参与"删旧建新"。** 查询接口不返回 `warnings`，一旦把预警表加进 `DeleteChildrenAsync`，任何一次回查都会清空全部历史预警。

> [!NOTE] **5. 节点定位键是"状态代码 + 地点CODE"，刻意不含发生时间。** 预计转实际时 `eventTime` 必变，纳入键会重复插入而非更新原节点。副作用是同箱同地点的相同状态码会被合并成一条，实际业务几乎不出现，且下次回查会以飞驼完整快照纠正。

> [!NOTE] **6. 签名仍不校验。** 飞驼 HmacSHA1 签名头(`x-ft-timestamp`/`x-ft-nonce`/`x-ft-client`/`x-ft-signature`)按官方"默认可不验证"处理，中转站只把它们记进日志，便于日后需要时比对。
