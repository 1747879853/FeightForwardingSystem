# 1. 背景意图 (Background)

**白话解释：** 调外部 AI 识别是**按次收费**的，同一份单证被反复上传识别纯属浪费。TextIn 之前已经做了结果缓存（表 `App_TextInExtractRecords`），但只有它自己在用；Gemini 的海运报价识别 `ExtractSeFreiPriceByPromptAsync` 每次调用都会真实请求一次 Gemini。

本次把这套缓存**从 TextIn 专用改成全局通用**：表名和列名改成与服务商无关的命名，抽出共用的 `AiExtractCacheManager`，TextIn 与 Gemini 统一走同一张表。以后接入通义千问等其它识别服务，直接换个 `Provider` 值即可复用。

# 2. 表结构变更（需自行生成 Migration）

| 项 | 变更前 | 变更后 |
| :-- | :-- | :-- |
| 实体 | `TextInExtractRecord` | `AiExtractRecord` |
| 表名 | `App_TextInExtractRecords` | `App_AiExtractRecords` |
| 服务商 | 无（隐含 TextIn） | **新增** `Provider` nvarchar(32)：`TextIn` / `Gemini` |
| 模型 | 无 | **新增** `ModelName` nvarchar(64)：如 `gemini-3.6-flash`；TextIn 无模型概念，记接口版本 `v3` |
| 场景 | `ExtractType` nvarchar(32) | `SceneCode` nvarchar(64) |
| 输入MD5 | `FileMd5` nvarchar(32) | `SourceMd5` nvarchar(32) |
| 输入大小 | `FileSize` bigint | `SourceSize` bigint |
| 版本 | `SchemaVersion` | 不变 |
| 结果 | `ResultJson` | 不变 |
| 唯一索引 | `(FileMd5, ExtractType, SchemaVersion)` | `(SourceMd5, Provider, SceneCode, ModelName, SchemaVersion)` |

`ModelName` **参与去重**：换模型（例如从 `gemini-3.1-flash-lite` 换到 `gemini-3.6-flash`）后旧缓存不再命中，会用新模型重新识别一次，便于对比不同模型的识别效果，也避免拿着老模型的结果当成新模型的表现。

`SourceMd5` / `SourceSize` 改名的原因：输入不一定是文件。Gemini 的报价识别支持直接粘贴文字，文字按 UTF8 字节算 MD5，用「文件」命名已经不准确。

> [!IMPORTANT] **生成 Migration 时请确认是 Rename 而不是 Drop + Create。** EF 有可能把表/列改名识别成「删旧建新」，那样历史缓存会全部丢失，所有老文件下次上传都要重新花钱识别一遍。若生成的迁移是 Drop/Create，请手工改成 `RenameTable` / `RenameColumn`，并给两个新增列补数据：`Provider` 刷成 `TextIn`、`ModelName` 刷成 `v3`（旧数据都是 TextIn v3 写的）。两列都是 NOT NULL 且进了唯一索引，留空会导致老缓存永远命不中。

## 3.1 各识别场景的缓存标识

| Provider | SceneCode | ModelName | SchemaVersion | 读缓存 | 说明 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| TextIn | SeaExport | v3 | 5 | **否** | 海运出口，当前只写不读，每次重新识别 |
| TextIn | SeaImport | v3 | 3 | 是 | 海运进口 |
| TextIn | PreOrder | v3 | 1 | 是 | 业务联系单 |
| Gemini | SeFreiPrice | gemini-3.1-flash-lite | 1 | 是 | 海运报价，本次新增；模型取代码里实际调用的那个 |

## 3.2 Gemini 报价识别的缓存口径

- **去重键**：传文字时取 `text.Trim()` 的 UTF8 MD5；传文件时取文件内容 MD5。文字和文件是两条独立缓存。
- **缓存内容**：存**模型原始输出 JSON**，不存回填 Id 之后的结果。
- **命中后**：反序列化原始输出，再**重新跑一遍** `FillMatchedIdsAsync`。这样港口、币别、箱型等基础资料后来补录了，老文件再识别一次也能匹配上新 Id，不会返回过期的 `-1`。
- **失败不落缓存**：识别失败或结果无法解析时不会写入，下次仍会真实调用。

# 4. 避坑指南 (Pitfalls)

> [!IMPORTANT] **[坑 1：改提示词必须提 SchemaVersion]** 不提版本号，老文件会一直命中旧缓存，改动看不出效果，还容易误判成「AI 没听懂提示词」。每个场景的版本号见 3.1。

> [!IMPORTANT] **[坑 2：缓存存的是识别结果，不是最终出参]** 名称→Id 的匹配逻辑每次都会重跑，所以改了匹配规则或补了基础资料，不用清缓存也能立刻生效；但改了**出参 DTO 结构**就得提版本号，否则老 JSON 反序列化出来会缺字段。

> [!IMPORTANT] **[坑 3：Gemini 文字识别的去重键是整段文字]** 文字里多一个空格就是另一条缓存。前端如果每次都拼接不同的前后缀（比如带时间戳），缓存永远命不中，等于没开。

> [!IMPORTANT] **[坑 4：ModelName 记的是「请求的模型」，不是外网服务器最终用的模型]** 外网服务器遇 Gemini 503 会按 `FallbackModels` 链自动降级换模型重试，这个降级发生在业务端之外，业务端只知道自己请求的是哪个模型。所以缓存里记的是请求模型；如果一次识别其实是被降级模型完成的，缓存仍挂在请求模型名下。排查识别质量差异时，以外网服务器日志里的实际模型为准。
