# 1. 说明

新增发票识别接口 `ExtractInvoiceAsync`：上传发票文件、或直接给一个**已上传附件的 Id**，后端调用 AI 识别出**发票号码**、**开票日期**、**销售方纳税人识别号**、**销售方抬头**、**价税合计**五个字段返回。

> 2026-09-06 起在原有发票号码、开票日期之外**新增 `sellerTaxNo`、`sellerHeader`、`totalAmount` 三个字段**，见「4」。老字段与接口地址、入参都没变，前端按需取用即可。

支持各种版式的发票（增值税专用发票、增值税普通发票、电子发票、机打发票、收据，以及商业发票 Commercial Invoice、形式发票 Proforma Invoice、货代账单 Debit Note）。

本接口为**新增**，不影响任何已有接口。

> **2026-09-07 补充：** 另新增了 `UploadAndExtractInvoiceAsync`，上传一个发票文件即**同时落成附件并识别**（识别失败不报错，只是 `invoice` 为 null）。「用户当场选发票文件、既要存档又要预填」的场景请优先用它；本接口保持不变，适用于「附件已存在只想重新识别」或「只识别不留档」。两者共享识别缓存与识别字段，详见《Gemini对接-前端对接》第 8 节（含两者差异对照表）。

# 2. 接口

| 项目 | 内容 |
| :-- | :-- |
| 方法 | `POST` |
| 地址 | `/api/services/app/GeminiAdmin/ExtractInvoiceAsync` |
| 请求体 | `multipart/form-data`，**单个文件** 或 **字段 `attachmentId`**（二选一，见「3」） |
| 权限 | 需登录（类级 `[AbpAuthorize]`，无额外权限点） |
| 返回 | `GeminiInvoiceDto`，见「4」 |
| 返回包装 | ABP 统一包一层 `result` |
| 失败 | 统一抛 `UserFriendlyException`，前端按常规错误提示展示即可，错误文案见「6」 |
| 耗时 | 通常 3~20 秒，前端务必给 loading 且**不要设过短的超时**（后端超时 180 秒） |

---

# 3. 请求参数

**文件与附件Id二选一，传了 `attachmentId` 就按附件记录读服务器本地文件、不再读上传的文件；两者都不传报「请上传发票文件或传入附件Id」。**

| 字段名 | 类型 | 含义 | 必填 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| **attachmentId** | long | 已上传附件的Id | 否 | 即附件表主键（附件列表接口返回的 `attachmentId`）。**有值时优先使用，此时上传的文件被忽略**。后端凭此查出附件的存储相对路径，**直接读服务器磁盘文件，不发任何 HTTP 请求**。文件大小上限 **20MB**，超过直接报错 |
| **（文件）** | File | 待识别的**发票文件** | 否 | 未传 `attachmentId` 时必传，**取第一个文件**（文件字段名不限）。支持 pdf / png / jpg / jpeg / webp / heic / heif / gif / bmp / txt / xlsx / xls |

> **为什么用 attachmentId 而不是 Url：** 附件已经存在本服务器 `wwwroot` 下，凭 Id 查库拿到相对路径后直接读磁盘即可，既不用绕一圈 HTTP 自请求，也避免了把可访问地址暴露成入参。前端**不需要**再拼 Url。

## 3.1 attachmentId 的传参方式（重要）

| 方式 | 是否支持 | 示例 |
| :-- | :-- | :-- |
| `multipart/form-data` 表单字段（推荐） | ✅ | `formData.append('attachmentId', 12345)` |
| `application/x-www-form-urlencoded` 表单字段 | ✅ | `attachmentId=12345` |
| URL query 参数 | ✅ | `...ExtractInvoiceAsync?attachmentId=12345` |
| JSON 请求体 `{"attachmentId":123}` | ❌ **不支持** | 后端绑不到值，会当作没传并报错 |

## 3.2 调用示例

**方式一：上传文件（用户当场选文件识别）**

```javascript
const formData = new FormData();
formData.append('file', selectedFile);
const res = await axios.post(
  '/api/services/app/GeminiAdmin/ExtractInvoiceAsync',
  formData,
);
```

**方式二：传附件Id（文件已在附件列表里，直接识别已有附件）**

```javascript
const res = await axios.post(
  '/api/services/app/GeminiAdmin/ExtractInvoiceAsync?attachmentId=' +
    attachment.attachmentId,
);
```

# 4. 返回结构 (GeminiInvoiceDto)

| 字段名 | 类型 | 含义 | 说明 |
| :-- | :-- | :-- | :-- |
| **invoiceNo** | string | 发票号码 | 按发票原文返回，保留其中的字母与数字，不额外加空格或分隔符。**识别不到为 `null`** |
| **invoiceDate** | DateTime? | 开票日期 | 已统一转成标准日期（JSON 形如 `2026-08-15T00:00:00`）。**识别不到为 `null`** |
| **sellerTaxNo** | string | 销售方纳税人识别号（销方税号） | 只取**销售方/销方**那一栏，购买方税号不会取；只保留字母数字并转大写。发票上只有一个税号且分不清归属时返回 `null`。**识别不到为 `null`** |
| **sellerHeader** | string | 销售方抬头（销方名称） | 只取**销售方/销方**那一栏，购买方名称不会取；与 `sellerTaxNo` 取自同一栏、必然是同一个主体。按原文返回**公司全称**，不简称不翻译，已去掉「名称:」这类标签前缀。只有一个单位名称且分不清归属时返回 `null`。**识别不到为 `null`** |
| **totalAmount** | decimal? | 价税合计（含税总金额） | 纯数字，不带货币符号与千分位逗号；取的是含税总额，不是不含税金额栏、税额栏或某一行明细。大写金额栏不作为取值来源。**识别不到为 `null`** |

## 4.2 字段名与两张发票表的对应

字段名对齐系统里的业务字段名，两个使用场景基本都能直填：

| 识别结果 | 付费申请发票（`paymentApplicationInvoices[]`） | 进项发票（`inputInvoice`） |
| :-- | :-- | :-- |
| `invoiceNo` | 同名 | 同名 |
| `invoiceDate` | 同名 | 同名 |
| `sellerHeader` | 同名 | 同名 |
| `totalAmount` | **映射到 `amount`** | 同名 |
| `sellerTaxNo` | 该表**没有**税号字段，用不上 | 同名 |

> 进项发票的销方名称字段已于 2026-09-06 由 `sellerTaxName` 改名为 `sellerHeader`，与付费申请发票统一。唯一还需要映射的是付费申请发票的金额：那张表上叫 `amount`。

## 4.1 返回示例

```json
{
  "result": {
    "invoiceNo": "24327000000012345678",
    "invoiceDate": "2026-08-15T00:00:00",
    "sellerTaxNo": "91310000MA1K35Q12X",
    "sellerHeader": "上海某某国际物流有限公司",
    "totalAmount": 1234.56
  },
  "targetUrl": null,
  "success": true,
  "error": null,
  "unAuthorizedRequest": false
}
```

**识别不到时（不会报错，字段为 null）：**

```json
{
  "result": {
    "invoiceNo": null,
    "invoiceDate": null,
    "sellerTaxNo": null,
    "sellerHeader": null,
    "totalAmount": null
  },
  "targetUrl": null,
  "success": true,
  "error": null,
  "unAuthorizedRequest": false
}
```

# 5. 前端处理要点

- **五个字段都可能为 `null`**，表示 AI 在文件里没找到该信息（后端要求模型宁可返回 null 也不编造）。前端应把识别结果作为**预填**，允许用户校对修改后再提交，不要直接当成准确值使用。
- **`totalAmount`、`sellerTaxNo`、`sellerHeader` 尤其要让用户核对**：价税合计容易与不含税金额、税额混淆；销方税号与销方抬头在只印了一个主体的单据上有可能归属不明（分不清销方/购方时后端宁可返回 `null`），而国际单据上的 Seller 栏格式五花八门，识别出来的全称可能带多余的地址或分支机构信息。
- **识别结果有缓存**：按**文件内容**去重，同一份发票第二次调用直接返回上次的识别结果，响应会明显变快。传 `attachmentId` 与直接上传文件两种来源共用同一份缓存（内容相同即命中，与文件名、附件Id无关）。2026-09-06 两次加字段已把提示词版本提到 **3**，**此前识别过的老文件缓存全部失效**，第一次重新上传会真实调一次 AI（慢一些），之后恢复命中。
- **20MB 上限只作用于 `attachmentId`** 这条路径；走上传文件不受此限制。
- 发票号码容易与**发票代码、税号、订单号、合同号、校验码**混淆，后端提示词已做排除，但仍建议前端在界面上让用户能一眼核对。

# 6. 错误提示汇总

以下文案会通过 `UserFriendlyException` 返回，前端直接展示即可。

| 场景 | 提示文案 |
| :-- | :-- |
| 文件和附件Id都没传 | 请上传发票文件或传入附件Id |
| 附件Id查不到记录（或已删除、不属于当前租户） | 附件不存在或已被删除 |
| 附件记录没有存储路径 | 附件没有记录存储路径，无法读取文件 |
| 附件记录在但磁盘文件已丢失 | 附件文件在服务器上不存在，请重新上传 |
| 附件文件大小为 0 | 附件文件是空的 |
| 附件文件超过上限 | 发票文件大小 {实际大小}MB，超过 20MB 上限，无法识别 |
| AI 返回内容无法解析（已自动重试 3 次） | AI识别发票结果无法解析 |
| 其他识别异常 | AI识别失败：{原因} |
