# 1. 背景意图 (Background)

**白话解释：** Gemini 属于境外接口，业务服务器不一定能直连，且 Gemini 密钥散落在业务代码里（原先硬编码在 `GeminiAdminAppService` 的 `_apiKey` 字段），多台业务服务器各自持有，既不安全也不好换。

为此新增一个独立可发布的 **外网服务器(`Freight.GlobalServer`)** 项目，专门部署在能直连境外接口的机器上，职责只有一件事：

> **把业务服务器组装好的请求发给 Gemini，再把 Gemini 的响应原文原样送回来。**

**拆分边界（本次改造的核心约定）：**

| 环节 | 拆分后所在位置 |
| :-- | :-- |
| 上传文件接收、文件转 Base64 | **业务服务器**（不变） |
| 提示词(prompt)、`generationConfig` 组装 | **业务服务器**（不变） |
| 请求发出 / 响应取回（含密钥、境外网络） | **外网服务器** |
| 响应报文解析、`candidates` 取正文 | 业务服务器（由客户端类统一封装） |
| 反序列化为 DTO、港口/币别/箱型模糊匹配回填 | **业务服务器**（不变） |

> 一句话：**只拆"请求和返回"，返回后的数据处理仍然全部在本项目内。** 外网服务器不理解任何业务语义，不解析报文，换提示词/换字段不需要动它。

**注意**：外网服务器与已有的中转站(`Freight.Relay`)是**两个独立项目**，不要混放。中转站负责云当/飞驼等平台的 token 下发与推送路由；外网服务器只负责境外接口的出站访问。

# 2. 架构与数据流

```
浏览器 ──上传文件──▶ 业务服务器 GeminiAdminAppService
                        │ 1) 文件转Base64 + 组装提示词/请求体
                        │ 2) 序列化 + GZip 压缩
                        ▼
                   GeminiGlobalServerClient
                        │ POST /global/gemini/generate?model=xxx
                        │ 头：X-Global-Token、Content-Encoding: gzip
                        ▼
        外网服务器 Freight.GlobalServer (可直连境外)
                        │ 校验密钥 → 拼接 key(仅存本机)
                        │ 压缩体不解压，原样转发
                        ▼
              https://generativelanguage.googleapis.com
                        │ 响应原文 + 状态码
                        ▼
        外网服务器（原样透传，不加工）──▶ 业务服务器
                        │ 3) 取 candidates[0].content.parts[0].text
                        │ 4) 反序列化 DTO + 回填港口/币别/箱型Id
                        ▼
                     返回前端
```

# 3. 核心逻辑变更

## 3.1 新增项目 `src/Freight.GlobalServer`（.NET 8，独立发布）

| 文件 | 说明 |
| :-- | :-- |
| `Program.cs` | 最小宿主：Serilog 日志、放开请求体大小限制、注册 `GlobalServerOptions`/具名 HttpClient/`IGeminiForwarder` |
| `Options/GlobalServerOptions.cs` | 配置模型：`AccessToken`(全局通用密钥)、`Gemini`(密钥/地址/版本/超时/日志) |
| `Services/GeminiForwarder.cs` | 转发实现：拼接 `{BaseUrl}/{ApiVersion}/models/{model}:generateContent?key=***`、返回状态码+报文+耗时 |
| `Services/GlobalServerFileLoggerProvider.cs` | 按"文件夹+前缀"归档的按天滚动日志器工厂 |
| `Controllers/GeminiController.cs` | `POST /global/gemini/generate`(Gemini 专用)、`GET /health` |
| `appsettings.json` | **Gemini 密钥只存在这里**，业务服务器不再持有 |

**对外接口：** `POST /global/gemini/generate?model=gemini-3.5-flash`

| 项目 | 内容 |
| :-- | :-- |
| 请求头 | `X-Global-Token`：全局通用密钥；`Content-Type: application/json`；`Content-Encoding: gzip`(可选) |
| 请求体 | 业务端组装好的 Gemini 请求体原文（可 GZip 压缩） |
| 返回 | `{ success, text, message }`：成功 `success=true` + `text` 模型正文；失败 `success=false` + `message`。**不再透传 Gemini 原始 candidates 报文** |
| 401 | `X-Global-Token` 与配置的 `AccessToken` 不一致 |
| 400 | 缺少 `model` / 请求体为空 |
| 502 / 504 | 调用 Gemini 异常 / 超时（本服务自身生成，非 Gemini 返回） |

**日志（Serilog，按天滚动，位于程序运行目录）：**

| 日志类别 | 文件路径 | 说明 |
| :-- | :-- | :-- |
| 系统运行日志 | `Logs/global-yyyyMMdd.log` | 框架/系统级日志（保留31天），鉴权被拒也记在这里 |
| Gemini 各接口转发明细 | `Logs/Gemini/{接口名}/{接口名}-yyyyMMdd.log`（例：`Logs/Gemini/generate/generate-yyyyMMdd.log`） | 每条含来源IP、请求时间、**当日第N次**(该接口独立内存计数，不与其它接口共享)；`[收到请求]`/`[转发完成]`/`[转发失败]`/`[请求被拒-*]`；成功与失败均可附 Gemini 完整报文（`LogSuccessBody`/`LogFailureBody`，默认开启；保留90天） |

> 密钥只在拼接 URL 时使用，**任何日志都不会记录 URL 或密钥**。

## 3.2 业务端新增 `GeminiGlobalServerClient`

位置：`src/CsprojBuilder.Application/App/AI/GeminiGlobalServerClient.cs`（`ITransientDependency`，构造注入即可用）。

| 成员 | 说明 |

```json
"GlobalServer": {

  "Token": "<与外网服务器 GlobalServer:AccessToken 完全一致的密钥>"
```

# 4. 避坑指南

> [!IMPORTANT] **1. 外网服务器不限制模型，`X-Global-Token` 是唯一防线。** 传什么 `model` 就转发什么，换模型只需在业务端 `GeminiGlobalServerClient` 加个常量、无需动外网服务器。密钥泄露后对方可借道消耗配额，异常时看对应接口目录下日志（如 `Logs/Gemini/generate/`）里的模型名与「当日第N次」。进程重启后当日次数从 1 重新计(只放内存、不落盘)。

> [!IMPORTANT] **2. 压缩体是"透传"，不要在外网服务器加请求解压中间件。** 业务端 GZip 压缩后发出，外网服务器**不解压**，只是把字节连同 `Content-Encoding: gzip` 原样丢给 Gemini（ASP.NET Core 默认不会自动解压请求体，正是我们要的行为）。若日后加了 `RequestDecompression` 中间件，会变成"解压后仍带着 gzip 头转发"，Gemini 直接报错。

> [!IMPORTANT] **3. IIS 部署要额外放开请求体大小。** 代码里已把 Kestrel 与 ANCM 的 `MaxRequestBodySize` 置为 null、接口打了 `[DisableRequestSizeLimit]`，但 **IIS 请求筛选的 `maxAllowedContentLength` 默认约 30MB 仍会先拦截**。发布到 IIS 后若上传大 PDF 报 404.13，需在站点 `web.config` 增加：
>
> ```xml
> <security><requestFiltering><requestLimits maxAllowedContentLength="209715200" /></requestFiltering></security>
> ```

> [!IMPORTANT] **4. 两端超时不要设反。** 业务端 `GlobalServer` 客户端 180 秒 > 外网服务器 `Gemini:TimeoutSeconds` 120 秒。反过来会导致业务端先断开，日志里查不到 Gemini 究竟返回了什么。

> [!IMPORTANT] **5. 密钥有三个，不要搞混。** `X-Global-Token`(业务端 `GlobalServer:Token` = 外网服务器 `GlobalServer:AccessToken`) 是**业务端访问外网服务器**的密钥，两端不一致返回 401「无效的 X-Global-Token」；`Gemini:ApiKey` 是**外网服务器访问 Gemini** 的密钥，只存在外网服务器上，业务端不应再出现；中转站的 `Relay:Token` 是**另一套独立密钥**，与本模块无关，**两者刻意不共用**，一个泄露不影响另一个，轮换时也互不牵连。

> [!IMPORTANT] **6. 别把解析挪到外网服务器。** 外网服务器刻意不认识 `GeminiSeFreiPriceDto`、不认识港口/币别/箱型匹配。提示词改字段、DTO 加字段、匹配规则调整，都只改业务项目、无需重新发布外网服务器——这是本次拆分想保住的收益。

> [!IMPORTANT] **7. 参照中转站的写法，不同平台分开写接口。** 外网服务器没有做通用 `{provider}` 转发：各家地址拼法、鉴权位置（query 还是 header）、压缩与报错格式都不一样。后续接入其它境外平台，请新增独立 Controller，不要为了"复用"合并。

# 5. 部署与联调步骤

1. 发布 `src/Freight.GlobalServer` 到**能直连 Google 的服务器**（IIS 进程内托管，与中转站一致）。
2. 改外网服务器 `appsettings.json`：`GlobalServer:AccessToken`（自定义强随机串）、`Gemini:ApiKey`（真实密钥）。
3. 访问 `http://<外网服务器地址>/` 出现"服务已正常启动并可访问"（与中转站一致），或 `GET /health` 返回 `{"status":"ok"}` 即部署成功。
4. 改业务端 `appsettings.json` 的 `GlobalServer:BaseUrl` 为实际地址，`GlobalServer:Token` 与第 2 步的 `AccessToken` 保持一致。
5. 前端调用原有三个接口验证，同时看 `Logs/Gemini/generate/generate-yyyyMMdd.log` 是否有 `[转发完成]` 且带「当日第N次」。

**本地自测（已验证通过）：**

```powershell
dotnet run --project src/Freight.GlobalServer/Freight.GlobalServer.csproj --urls http://localhost:5081
# 无/错误 token → 401；缺 model 参数或空请求体 → 400
# 携带正确 token + gzip 请求体 → 200，返回 Gemini 原始报文，日志记录 [转发完成]
```
