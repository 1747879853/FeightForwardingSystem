# 1. 背景意图 (Background)

业务员拿到的报价不一定是文件，很多时候是**微信/邮件里直接复制的一段文字**。改动前 `ExtractSeFreiPriceByPromptAsync` 只从 `Request.Form.Files` 取文件，用户必须先把文字另存成文件（截图/存 txt）才能识别，操作很绕。

本次给该接口增加一个**可选的文字入参 `text`（string）**：

- **传了文字** → 直接把文字拼在内置提示词后面交给 Gemini 识别，不再读上传文件；
- **没传文字** → 完全走原来的"读上传文件"分支（PDF/图片 base64 内联、Excel 转 HTML 表格），行为与改动前一致。

出参结构、提示词、模型、Id 模糊匹配逻辑**全部没有变化**，前端已有的文件上传调用**无需改动**。

# 2. 核心逻辑变更

| 项 | 说明 |
| :-- | :-- |
| 接口签名 | `ExtractSeFreiPriceByPromptAsync(string text = null)`；`IGeminiAdminAppService` 同步修改 |
| 取数优先级 | `text` 非空白 → **文字分支**；`text` 为 null/空/纯空白 → **文件分支** |
| 文字分支 | 请求 `parts` 只有一段 text：`内置提示词` + `"以下是报价文字内容，请据此识别：\n"` + 用户文字，**不带 `inline_data`**，也**完全不读 `Request.Form`** |
| 文件分支 | 原文件处理逻辑原样抽成私有方法 `BuildPartsFromUploadedFileAsync(prompt)`：Excel(xlsx/xls) 走 `ExcelToHtmlTableHelper` 转 HTML 表格随提示词发送，其余按 `GetMimeType` + base64 走 `inline_data` |
| 表单读取保护 | 文件分支先判 `Request.HasFormContentType` 再取 `Request.Form.Files`，非表单请求不再抛框架异常 `Incorrect Content-Type` |
| 报错文案 | 两者都没传时：「请上传文件」→ **「请上传文件或输入需要解析的文字」** |
| 未变部分 | 提示词常量 `SeFreiPriceExtractPrompt`（含"当前年"替换）、`generationConfig`、JSON 解析失败最多重试 10 次、`FillMatchedIdsAsync` 回填港口/币别/箱型Id（匹配不到 -1）、返回 `List<GeminiSeFreiPriceDto>` |

# 3. 避坑指南

> [!IMPORTANT] **`text` 不能放在 JSON body 里。** 它是简单类型参数，ABP 动态 WebApi 不会给它加 `[FromBody]`，只能从 **form 字段**（`multipart/form-data` 或 `x-www-form-urlencoded`）或 **query 参数**绑定。前端发 `{"text":"..."}` 的 JSON body 会绑不上值，后端当作没传文字，转去找文件并报「请上传文件或输入需要解析的文字」。

- **文字和文件同时传**：以**文字**为准，文件被静默忽略（不报错），这是刻意设计，避免两份来源冲突。
- 只传空白字符（空格、换行、制表符）等同于没传，仍会去找文件。
- 纯文字没有版面信息，**表格型报价建议仍旧传文件或 Excel**；若一定要用文字，各列之间用空格/制表符对齐、每个目的港一行，识别准确率明显更高。
- 文字很长时同样受外网服务器 120 秒、业务端 180 秒超时约束，前端不要设过短超时。
- 当前代码实际调用的模型是 `GeminiGlobalServerClient.ModelFlash31Lite`（`gemini-3.1-flash-lite`），`ModelFlash36` 那行是被注释掉的；早期文档里写的 `gemini-3.5-flash` 已与代码不符，**排查识别效果以代码为准**。
