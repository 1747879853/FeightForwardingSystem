# 1. 背景意图 (Background)

**业务需求：** 完成服务项时除了校验字段和费用，还需要校验附件。例如"完成订舱服务项前必须上传托书（附件类型 id=1）"。

**方案选型：** 未新建独立子表，而是复用现有 `SeServiceRequire`（完成时必填项）表：`SeaExportPropEnum` 新增扩展类型枚举，配合新字段 `RequireValues` 承载具体值（`|` 分隔，可多个）。这样后续再出现"必填某类联系人""必填某类单据"等需求，只需新增枚举值，无需继续横向建表。

# 2. 核心逻辑变更 (Core Logic Changes)

## 2.1 枚举 (CsprojBuilderEnum.cs)

`SeaExportPropEnum` 新增扩展类型段位：

| 枚举              | 值    | 说明                                         |
| ----------------- | ----- | -------------------------------------------- |
| AttachmentDtlType | 10001 | 附件类型，具体附件类型id存于 `RequireValues` |

**段位约定：** 1000 以内为海运出口字段、1001-2000 为其 Name 派生字段，各业务类型按千位划分自有段位（如 2000-3000 为空运出口），因此非字段类的扩展类型统一从 **10001** 起，避免占用业务字段段位。

## 2.2 实体 (Core/Entites/SeServiceConfig.cs)

`SeServiceRequire` 新增：

- `RequireValues`（`string`，`[StringLength(512)]`，可空）：扩展类型的具体值，多个用 `|` 分隔，如 `"1|2|3"`。普通字段类型为空。

> 注：按规范未生成 migration，由维护人自行生成。

## 2.3 值解析辅助类（新增）

`Application/App/SeServiceConfig/SeServiceRequireValueHelper.cs`：

- `ParseIds(string)`：解析为 id 集合，去重、升序、忽略非法项。
- `ToStorageValue(IEnumerable<long>)` / `Normalize(string)`：拼装/规范化存储值，空集合返回 `null`。

## 2.4 配置接口 (SeServiceConfigAdminAppService)

- `AddAsync` / `EditAsync`：新增共用校验 `ValidateConfigItemPropsAsync`
  - `seServiceShows`、`seServiceLocks` 传入扩展类型枚举（≥10001）直接报错——附件不是展示字段也谈不上锁定。
  - 必填项为附件类型时 `RequireValues` 必须至少含一个 id。
  - 校验附件类型是否存在（查 `AttachmentDtlType`）。
- `RequireValues` 存储前统一走 `Normalize` 规范化（去重、升序）。
- `DiffSubTableRequires`：差异更新时同步 `RequireValues`。
- `DetailAsync`：返回 `requireValues`。

## 2.5 完成任务校验 (SeServiceTaskAdminAppService)

`CompleteAsync` 复用**同一套累积逻辑**（当前任务 + 该票所有已完成任务）：

- 新增 `CollectRequiredProps`：遍历 `SeServiceRequires`，普通字段进 `HashSet<SeaExportPropEnum>`，附件类型从 `RequireValues` 解析后进 `HashSet<long>`。
- 新增 `ValidateRequiredAttachmentsAsync`：按 `ModuleTypeId`=海运出口、`ItemId`=海运出口id 取已上传附件，比对缺失的附件类型，报错：

```
完成任务需要上传以下附件: 托书、提单
```

缺失类型名按 `AttachmentDtlType.SortId` 排序；若类型已被删除取不到名称，用 id 兜底提示。

## 2.6 配置带出接口 (SeaExportAdminAppService.GetServiceTypesByPOLAsync)

**破坏性变更：** `seServiceShows`、`seServiceLocks`、`seServiceRequires` 由 `int[]`（纯枚举值数组）改为对象数组 `SeServicePropItemDto`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| seaExportPropEnum | int | 字段枚举，`10001`=附件类型（仅 `seServiceRequires` 会出现） |
| requireValues | string | 扩展类型具体值，`\|` 分隔；附件类型时为附件类型id，普通字段为 `null` |

三个列表共用同一对象结构，前端处理方式统一；`seServiceShows`/`seServiceLocks` 的 `requireValues` 恒为 `null`（配置时已禁止扩展类型）。

# 3. 避坑指南 (Pitfalls)

- **扩展枚举仅限必填项**：`10001` 只能出现在 `seServiceRequires`，传给 `seServiceShows`/`seServiceLocks` 会被拒绝。
- **附件类型无外键**：`RequireValues` 以字符串存 id，无数据库外键约束。附件类型被删除后，配置中的 id 会失效，完成任务时报错以 id 兜底显示。若需引用校验，应在附件类型删除接口中增加对 `SeServiceRequires.RequireValues` 的 LIKE 检查。
- **模糊查询需注意分隔符**：存储格式不带首尾分隔符（如 `1|2`），按 id 精确检索时不能直接 `LIKE '%1%'`，会误匹配 `11`。
- **附件不区分服务项**：校验只看该海运出口是否上传了对应类型的附件，不区分是哪个服务项上传的。
