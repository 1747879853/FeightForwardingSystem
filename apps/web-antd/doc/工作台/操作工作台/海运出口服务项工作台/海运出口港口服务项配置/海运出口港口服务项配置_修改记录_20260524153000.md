# 海运出口港口服务项配置 修改记录

**修改时间：** 2026-05-24 15:30:00

**修改人：** 后端

**关联接口：** `GET /api/services/app/SeServiceConfigAdmin/GetPagedListAsync`

**问题示例：** `?pageIndex=1&pageSize=20&serviceType=4`

---

## 一、问题描述

### 1.1 serviceType 筛选不生效 / 表现异常

调用列表接口并传入 `serviceType` 参数时，筛选结果不符合预期，常见表现为：

| 现象 | 说明 |
| --- | --- |
| 筛选无效 | 传入 `serviceType=4` 后，仍返回未配置该服务项的主配置，或应命中的主配置未返回 |
| 前端感知「没筛到」 | 主配置虽被命中，但 `seServiceConfigItems` 仍返回该港口下**全部**服务项，列表 UI 仍展示其他类型，用户认为筛选未生效 |
| 与软删除数据干扰 | 主配置下存在已软删除的同类型服务项时，筛选行为不稳定 |

### 1.2 复现方式

```http
GET /api/services/app/SeServiceConfigAdmin/GetPagedListAsync?pageIndex=1&pageSize=20&serviceType=4
```

对比以下两次请求的主配置集合与 `totalCount`：

- 不带 `serviceType`
- 带 `serviceType=4`（仅保留配置了服务项类型 4 且未删除的港口主配置）

## 二、根因分析

### 2.1 查询链路中 Include 前置，干扰 ServiceType 条件翻译

**当前代码：**

```csharp
var query = _seServiceConfigRepository.GetAll()
    .Include(x => x.POL)
    .Include(x => x.SeServiceConfigItems)   // ← 在筛选前 eager load 子表
    .WhereIf(input.POLId.HasValue, x => x.POLId == input.POLId.Value)
    .WhereIf(input.ServiceType.HasValue, x => x.SeServiceConfigItems.Any(
        item => !item.IsDeleted && item.ServiceType == input.ServiceType.Value));
```

问题点：

1. **Include 写在 Where 之前**，EF Core 在生成 SQL 时容易将导航集合与筛选条件耦合，部分场景下 `Any` 子查询未正确下推到数据库，或产生多余 JOIN，导致筛选结果异常。
2. 分页前已 Include 全量子项，**先加载再过滤**的内存压力更大，异常时表现为筛选「时灵时不灵」。

对比项目中已验证可用的写法（如 `SeaExportAdminAppService` 的 `ServiceType` 筛选）：**先 Where / Any 筛选主表，分页完成后再 Include 关联数据**。

### 2.2 子表筛选未走独立仓储，且重复判断 IsDeleted

1. `SeServiceConfigAdminAppService` 已注入 `_seServiceConfigItemRepository`，但 `GetPagedListAsync` 未使用，而是通过主表导航属性 `SeServiceConfigItems.Any(...)` 筛选。
2. 子项实体 `SeServiceConfigItem` 继承 `FullAuditedEntity`，ABP **全局软删除过滤器**已自动排除 `IsDeleted = true` 的记录。
3. 筛选条件中又显式写了 `!item.IsDeleted`，与全局过滤器叠加，在导航属性 `Any` 表达式中可能引发 EF 翻译差异，导致筛选 SQL 与预期不一致。

### 2.3 返回结构与筛选语义不一致（前端体验问题）

接口文档说明：

> 当传入 `serviceType` 筛选条件时，返回**包含**该服务项类型的主配置记录。

当前实现仅过滤**主配置行**，映射 DTO 时仍输出该主配置下**全部未删除子项**：

```csharp
var activeItems = (config.SeServiceConfigItems ?? ...)
    .Where(item => !item.IsDeleted)
    .OrderBy(item => item.SortId)
    .ToList();   // ← 未按 input.ServiceType 二次过滤
```

因此前端若直接渲染 `seServiceConfigItems` / `serviceTypes`，会看到 `[1, 2, 4, 5]` 等全部类型，**视觉上像筛选未生效**。这是产品语义与实现不一致导致的体验问题，需在本次一并明确并修正。

## 三、修改方案

### 3.1 修改文件清单

| 文件 | 路径 | 修改类型 |
| --- | --- | --- |
| 应用服务实现 | `App/SeServiceConfig/SeServiceConfigAdminAppService.cs` | 重写 `GetPagedListAsync` 查询链路 |
| 对接文档 | `文档/.../海运出口港口服务项配置.md` | 补充 serviceType 筛选行为说明 |

> DTO、接口签名**不变**。

### 3.2 查询链路重构（核心修复）

**原则：** 主表筛选 → 数据库端 Count / 排序 / 分页 → 再加载关联数据。

**修改后伪代码：**

```csharp
// 1. 构建主表查询（不含 Include）
var query = _seServiceConfigRepository.GetAll()
    .WhereIf(input.POLId.HasValue, x => x.POLId == input.POLId.Value);

// 2. ServiceType 筛选：通过子项仓储子查询，避免导航 Any + Include 耦合
if (input.ServiceType.HasValue)
{
    var serviceType = input.ServiceType.Value;
    var matchedConfigIds = _seServiceConfigItemRepository.GetAll()
        .Where(item => item.ServiceType == serviceType)
        .Select(item => item.SeServiceConfigId);

    query = query.Where(x => matchedConfigIds.Contains(x.Id));
}

// 3. 数据库端分页
var totalCount = await query.CountAsync();
var configs = await query
    .OrderBy(input.Sorting)
    .Skip(input.GetSkipCount())
    .Take(input.GetTakeCount())
  // 4. 分页完成后再 Include
    .Include(x => x.POL)
    .Include(x => x.SeServiceConfigItems)
    .ToListAsync();
```

**要点：**

| 项 | 说明 |
| --- | --- |
| 移除筛选条件中的 `!item.IsDeleted` | 依赖 ABP 全局软删除过滤器 |
| 子项仓储子查询 | 与 `SeServiceTaskAdminAppService` 等现有用法一致，SQL 更稳定 |
| Include 后置 | 仅对当前页主配置加载 POL 与子项 |

### 3.3 返回数据与筛选条件对齐（体验修复）

当 `input.ServiceType.HasValue` 时，映射 DTO 时对子项集合**同步过滤**，仅保留匹配类型的明细：

```csharp
var activeItems = (config.SeServiceConfigItems ?? ...)
    .Where(item => !item.IsDeleted)
    .WhereIf(input.ServiceType.HasValue, item => item.ServiceType == input.ServiceType.Value)
    .OrderBy(item => item.SortId)
    .ToList();
```

同步更新汇总字段：

| 字段                   | 调整                            |
| ---------------------- | ------------------------------- |
| `serviceItemCount`     | 按过滤后的 `activeItems` 计数   |
| `serviceTypes`         | 按过滤后的 `activeItems` 生成   |
| `seServiceConfigItems` | 仅包含匹配 `serviceType` 的子项 |

未传 `serviceType` 时，行为与现网一致（返回全部未删除子项）。

### 3.4 对接文档补充说明

在 `海运出口港口服务项配置.md` 列表接口章节补充：

```markdown
**serviceType 筛选说明：**

- 主配置维度：仅返回至少包含 1 条「未删除且 serviceType 匹配」子项的主配置；
- 子项维度：传入 serviceType 时，返回的 seServiceConfigItems / serviceTypes / serviceItemCount 仅包含匹配项；
- 未传 serviceType 时，返回主配置下全部未删除子项。
```

## 四、影响范围

| 影响项 | 说明 |
| --- | --- |
| 列表筛选 | `serviceType` 条件在数据库端稳定生效 |
| 列表返回（传 serviceType 时） | 嵌套子项由「全量」变为「仅匹配项」，前端列表展示与筛选一致 |
| 列表返回（未传 serviceType） | 无行为变化 |
| totalCount | 仍按**主配置**计数，含义不变 |
| polId / 分页 / 排序 | 无变更 |
| 详情 / 新增 / 编辑 / 删除接口 | 无变更 |

---

## 五、验收标准

| 序号 | 验收项 | 期望结果 |
| --- | --- | --- |
| 1 | 基础筛选 | 仅配置 serviceType=4 的港口主配置，请求 `serviceType=4` 能命中；未配置 4 的主配置不出现 |
| 2 | totalCount | 带 `serviceType` 时的 totalCount = 满足条件的主配置数，不是子项数 |
| 3 | 嵌套子项 | 传 `serviceType=4` 时，每条主配置的 `seServiceConfigItems` 仅含 type=4；`serviceTypes` 仅为 `[4]` |
| 4 | 未传 serviceType | 与不传时现网行为一致，返回全部未删除子项 |
| 5 | 软删除 | 某主配置仅存在已删除的 serviceType=4 子项时，不应被 `serviceType=4` 命中 |
| 6 | 组合筛选 | `polId` + `serviceType` 同时传入，结果取交集 |
| 7 | 分页 | `pageIndex=1&pageSize=20&serviceType=4` 分页稳定，翻页无重复/遗漏 |

## 六、建议 SQL 验证（可选）

```sql
-- 应被 serviceType=4 命中的主配置 Id
SELECT DISTINCT SeServiceConfigId
FROM App_SeServiceConfigItems
WHERE IsDeleted = 0 AND ServiceType = 4;

-- 与接口 totalCount 对比
SELECT COUNT(DISTINCT c.Id)
FROM App_SeServiceConfigs c
WHERE c.IsDeleted = 0
  AND EXISTS (
    SELECT 1 FROM App_SeServiceConfigItems i
    WHERE i.SeServiceConfigId = c.Id
      AND i.IsDeleted = 0
      AND i.ServiceType = 4
  );
```

## 七、回滚说明

若前端已依赖「传 serviceType 仍返回全量子项」的旧行为，回滚仅需还原 `GetPagedListAsync` 映射段对 `activeItems` 的二次过滤；主表子查询筛选建议保留，因其修复的是筛选准确性问题。
