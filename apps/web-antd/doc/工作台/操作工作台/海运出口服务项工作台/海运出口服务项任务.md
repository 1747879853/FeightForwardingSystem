# 海运出口服务项任务 (SeServiceTaskAdmin) 前端对接文档

## 校验规则

| 校验规则 | 错误信息 |
| --- | --- |
| 任务不存在 | "任务不存在" / "部分任务不存在" |
| 任务不是待处理状态(转交) | "任务{id}不是待处理状态，无法转交" |
| 任务不是待处理状态(完成) | "任务不是待处理状态，无法完成" |
| 任务不是已完成状态(取消完成) | "任务不是已完成状态，无法取消完成" |
| 转交时当前用户不是被转交人也不在处理人列表 | "任务{id}的被转交人不是当前用户，无法转交" / "当前用户不在任务{id}的处理人列表中，无法转交" |
| 完成时当前用户不是被转交人也不在处理人列表 | "任务的被转交人不是当前用户，无法完成" / "当前用户不在任务的处理人列表中，无法完成" |
| 被转交人已在处理人列表 | "被转交人已在任务{id}的处理人列表中，不能转交给处理人" |
| 被转交人不存在（2026-10-02 新增） | "被转交人不存在" |
| 完成时必填字段为空 | "必填字段[字段名]不能为空" |
| 完成时必填的附件类型未上传 | "完成任务需要上传以下附件: 托书、提单" |
| 完成时必填费用不存在 | "完成任务需要以下费用: [收/付]费用名称、..." |
| 完成时未找到海运出口 | "未找到对应的海运出口数据" |
| 完成时海运出口无起运港 | "海运出口的起运港(POLId)为空" |
| 完成时下一任务未匹配到处理人 | "未找到对应用户属性的处理人" |
| 工作台分页未找到起运港配置且无默认配置 | "未找到该起运港对应的服务项配置,请配置该港口或配置默认港口服务项" |

### 业务逻辑

1. 根据输入条件筛选 `SeServiceTask`，包括：任务状态、开船日期范围、委托单位、船公司、主提单号、目的港
2. 根据 `isAssigned` 参数决定筛选方式：
   - `true`：搜索 `AssigneeUserId == 当前用户` 的任务
   - `false`：搜索 `AssigneeUserId == null` 且 `SeServiceTaskUsers` 中包含当前用户的任务
3. **不分页**，返回所有符合条件的任务
4. 每个 `SeServiceConfig` 额外返回该配置下满足查询条件的任务总数 `taskCount`
5. 每个任务的 `seaExport` 字段包含完整的海运出口信息(与 `SeaExportAdminAppService.GetPagedListAsync` 返回的 `SeaExportDto` 结构一致)。往来单位为 `ClientSimpleDtoForOrder` 对象，船公司为 `CarrierSimpleDto` 对象，港口为 `PortCodeSimpleDtoForOrder` 对象（详见《海运出口-往来单位与船公司对象化-前端对接文档-2026-07-24》《海运出口-港口对象化-前端对接文档-2026-08-06》）
6. **默认港口配置展开**：当 `SeServiceConfig.POLId` 为空（默认配置）时，将其下的任务按实际海运出口的起运港(`SeaExport.POLId`)分组，每个实际港口生成一个独立的 `SeServiceTaskConfigGroupDto`。`polId` 始终为实际港口id，不会为空

### 业务逻辑

1. 查询与当前用户相关的**所有**任务，无需传入 `isAssigned`：
   - `AssigneeUserId == 当前用户` 的任务（指派给我的）
   - `AssigneeUserId == null` 且 `SeServiceTaskUsers` 包含当前用户的任务（我的非指派任务）
2. **不分页**，返回所有符合条件的任务
3. 组装多层结构时，每个 `SeServiceConfig` 的 `seServiceConfigItems` 中：
   - **正常元素**（按服务项分开）：包含 `AssigneeUserId` 为空的非指派任务，按 `SeServiceConfigItem` 分组
   - **最后一个额外元素**（`serviceType = null`）：包含该配置下 `AssigneeUserId` 不为空的所有指派任务，不区分服务项类型
4. 指派任务汇总元素的 `id`、`serviceType`、`userAttribute`、`autoComplete`、`manualAllowed`、`reminder`、`sortId` 均为 `null`，`seServiceShows` 为空数组
5. 其余逻辑（SeaExport映射、taskCount等）与接口1一致
6. **默认港口配置展开**：与接口1一致，默认配置(POLId为空)的任务按实际海运出口起运港分组展开，`polId` 始终为实际港口id

## 3. 批量转交任务

**POST** `/api/services/app/SeServiceTaskAdmin/TransferAsync`

### Request Body

```json
{
  "ids": [
    "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "3fa85f64-5717-4562-b3fc-2c963f66afa7"
  ],
  "assigneeUserId": 2,
  "assigneeRemark": "请帮忙处理一下"
}
```

### 字段说明

| 字段           | 类型   | 必填 | 说明               |
| -------------- | ------ | ---- | ------------------ |
| ids            | Guid[] | 是   | 要转交的任务id列表 |
| assigneeUserId | long   | 是   | 被转交人id         |
| assigneeRemark | string | 否   | 转交备注           |

### Response

```json
true
```

### 业务逻辑

1. 校验被转交人存在，不存在报"被转交人不存在"（2026-10-02 起；之前转给不存在的用户后任务对谁都不可见）
1. 校验所有任务存在且状态为**待处理**(Pending)，有一个不是就报错
1. 校验当前用户是否有权操作每个任务：
   - 如果任务有 `AssigneeUserId`：必须等于当前用户
   - 如果任务没有 `AssigneeUserId`：当前用户必须在 `SeServiceTaskUsers` 列表中
1. 校验被转交人(`assigneeUserId`)不能在任何任务的 `SeServiceTaskUsers` 列表中
1. 更新每个任务的 `AssigneeUserId`、`AssigneeTime` 和 `AssigneeRemark`（如有传入）
1. **允许多次转交**：已被转交的任务可以再次被转交(当前被转交人转交给下一个人)

### 业务逻辑

1. 校验任务存在且状态为**待处理**(Pending)
2. 校验当前用户是否有权完成任务：
   - 如果任务有 `AssigneeUserId`：必须等于当前用户
   - 如果任务没有 `AssigneeUserId`：当前用户必须在 `SeServiceTaskUsers` 列表中
3. **必填字段校验**：收集当前任务及该海运出口所有已完成任务的 `SeServiceConfigItem.SeServiceRequires`，对 SeaExport 和 TransportOrder 上对应的字段进行非空校验。若任一必填字段为空，报错"必填字段[字段名]不能为空"
4. **必填附件校验**：与必填字段**同一套累积逻辑**。`SeServiceRequires` 中 `SeaExportPropEnum = 10001`(附件类型) 的记录，其 `RequireValues`（`|` 分隔的附件类型id）即为要求上传的附件类型。校验该海运出口下已上传附件（`ModuleTypeId`=海运出口、`ItemId`=海运出口id）是否覆盖全部要求的附件类型，缺少时报错"完成任务需要上传以下附件: 托书、提单"
5. **必填费用校验**：如果当前任务对应的 `SeServiceConfigItem.RequireFee = true`，检查配置的 `SeServiceRequireFees` 中每条记录对应的 `PaySide` + `FeeCodeId`，必须在当前海运出口的 `OrderFee` 中存在相同 `PaySide` 和 `FeeCodeId` 的记录。若缺少，报错"完成任务需要以下费用: [收/付]费用名称、..."
6. 更新任务主表字段：
   - `ServiceTaskStatus` → `Processed`(已处理)
   - `CompletionUserId` → 当前用户id
   - `CompletionTime` → 当前时间
7. **如果是正常任务**（`AssigneeUserId` 为空）：还需要同时更新 `SeServiceTaskUser` 表中当前用户的 `CompletionTime`（一个人完成就算完成）
8. **如果是转交任务**（`AssigneeUserId` 有值）：只更新主表，不更新 `SeServiceTaskUser`（因为 `SeServiceTaskUser` 中没有被转交人的记录）

### 完成后自动生成下一个任务

完成任务后，系统会自动检查是否需要生成下一优先级的服务项任务：

1. 根据当前任务的 `SeServiceConfigItem`，找到同一 `SeServiceConfig` 下所有配置项
2. 判断当前优先级（`SortId`）下，该票所有已启用服务项对应的任务是否**全部已完成**
3. 若同优先级仍有未完成任务，**不生成**下一优先级任务
4. 若同优先级全部完成，取大于当前 `SortId` 的最小值作为下一优先级
5. 为下一优先级下所有已启用且未排除的配置项**批量生成** `SeServiceTask`（同 `SortId` 可有多条并行任务）
6. 新任务的 `SeServiceTaskUsers` 通过 `UserAttribute` 与 `OrderUsers` 匹配确定处理人
7. 若无下一优先级或对应配置项已有任务，则跳过生成

**示例：** 配置项 A(SortId=0)、B(SortId=0)、C(SortId=1)。新建票勾选 A、B、C 时同时生成 A、B 两个任务；完成 A 后 B 未完成则不生成 C；A、B 均完成后才生成 C。

## 5. 取消完成单个任务

**POST** `/api/services/app/SeServiceTaskAdmin/CancelCompleteAsync`

### Request Body

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
}
```

### 字段说明

| 字段 | 类型 | 必填 | 说明               |
| ---- | ---- | ---- | ------------------ |
| id   | Guid | 是   | 要取消完成的任务id |

### Response

```json
true
```

### 业务逻辑

1. 校验任务存在且状态为**已完成**(Processed)，否则报错"任务不是已完成状态，无法取消完成"
2. 获取当前任务的 SortId（通过 SeServiceConfigItem.SortId）
3. 查询同一海运出口（SeaExportId）下所有 SortId 大于当前任务的后续任务
4. **删除所有后续任务**（包括关联的 SeServiceTaskUsers）
5. 将当前任务状态改为 **Pending（待处理）**，清空 `CompletionUserId` 和 `CompletionTime`，并清空处理人 `SeServiceTaskUsers[].CompletionTime`（2026-10-02 起；之前回到待处理的任务里还挂着处理人的完成时间）

### 示例场景

假设某海运出口有任务序列 1→2→3→4（按 SortId 排序），当前任务4状态为 Pending，任务1、2、3为 Processed：

| 操作          | 效果                                   |
| ------------- | -------------------------------------- |
| 取消完成任务3 | 删除任务4，任务3状态变为 Pending       |
| 取消完成任务2 | 删除任务3和4，任务2状态变为 Pending    |
| 取消完成任务1 | 删除任务2、3、4，任务1状态变为 Pending |
