# 一、变更概述

| # | 变更 | 影响 |
| :-- | :-- | :-- |
| 1 | 选可对账费用的 `settlementId` 由**必填改为非必填**，不传则不按结算对象过滤 | 入参放宽，不传即可跨结算对象浏览 |
| 2 | 新建对账单 / 加费用时，若所选费用的结算对象不一致或与对账单客户不符，**报错更明确** | **报错文案变化** |

受影响接口：

| # | 接口 | 方法 | 路径 |
| :-- | :-- | :-- | :-- |
| 1 | GetOrderFeeGroupAsync | GET | `/api/services/app/StatementAdmin/GetOrderFeeGroupAsync` |
| 2 | AddAsync | POST | `/api/services/app/StatementAdmin/AddAsync` |
| 3 | AddFeesAsync | PUT | `/api/services/app/StatementAdmin/AddFeesAsync` |

出参结构**没有任何变化**。

# 二、接口 1 — GetOrderFeeGroupAsync

## 2.1 入参变化

| 字段名 | JSON Key | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- | :-- |
| SettlementId | `settlementId` | Guid? | **否**（原为是） | 结算对象（客户）id。不传则不按结算对象过滤，列表里会同时出现多个结算对象的费用 |

其余入参不变。

## 2.2 每条费用上怎么看它属于谁

费用行的 `settlement`（`ClientSimpleDto`，含 `id`/`name`/`code`）就是该费用自己的结算对象，跨结算对象浏览时按它区分即可。录入状态的费用允许没有结算对象，此时 `settlement` 为 `null`。

# 三、接口 2、3 — 新建与加费用的报错

一张对账单**只能对一个结算对象**（就是对账单头的 `clientId`），这一点没有放开。跨结算对象混选的费用会在提交时被拦下：

| 报错文案 | 触发条件 |
| :-- | :-- |
| `存在未设置结算对象的费用 不可对账` | 选中的费用里有 `settlement` 为空的（通常是录入状态费用） |
| `所选费用的结算对象不一致 不可对账` | 选中的费用分属两个及以上结算对象 |
| `费用的结算对象与对账单客户不一致` | 费用结算对象统一，但不等于对账单的 `clientId` |
| `关联费用输入错误` | **含义收窄**：现在只表示费用 id 不存在或已被删除 |

> [!IMPORTANT] 以前上述前三种情况统统报 `关联费用输入错误`。若页面对这句文案做过特殊处理，请改按新文案区分。

# 四、前端改动建议

1. **选费用弹窗的结算对象筛选项可以改成非必填**，允许用户先按单号/会计期间等条件把费用捞出来。
2. **选择阶段就限制单一结算对象**：用户勾第一条费用后，把其它结算对象的费用置灰或提示，避免提交时才报错。`settlement` 为 `null` 的费用同样不可选。
3. **想享受「对账人免数据权限」就必须传 `settlementId`。** 当前登录人是某客户的对账人时，传了 `settlementId` 能看到该客户下的全部费用；不传则退回普通数据权限，看到的费用会变少。这是刻意为之——不传结算对象时后端无从判断是谁的对账人。
4. **不要在不带任何筛选条件的情况下拉这个接口。** 该接口的费用查询不分页，不传结算对象又不带其它条件时会把全租户符合条件的费用一次性捞出来，很慢。界面上建议至少保留一个默认条件。
