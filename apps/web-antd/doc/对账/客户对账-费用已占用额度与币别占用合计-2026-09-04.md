# 背景意图

费用上有**两套互不相同的额度**，各自由一个 provider 做唯一出口（口径见 `文档/发票/完整发票逻辑.md` 第 5 章）：

| 费用行字段 | 口径 | 唯一出口 |
| :-- | :-- | :-- |
| `orderInvoiceAmount`（发票申请量，本次起前端可叫「发票已占用额度」） | 开票申请已申请 **+** 付费申请已申请（三种发票流程一律计入）。**不含收费结算** | `IOrderFeeInvoicedProvider.GetOrderInvoiceAmountMapAsync` |
| `settlementOccupiedAmount`（结算已占用额度） | 付费申请已申请 **+** 收费结算已结算 **+** 开票申请已申请 | `IOrderFeeOccupiedProvider.GetOccupiedAmountMapAsync` |

客户对账的场景就是「把一个结算对象的费用摆给客户确认」，对账时最需要看的恰恰是「这条费用还剩多少可用」。但改动前这两个额度在本模块里是缺的：

| 接口 | 改动前 |
| :-- | :-- |
| 选可对账费用 `GetOrderFeeGroupAsync` | `orderInvoiceAmount` 有值；`settlementOccupiedAmount` 恒 0；另有 `settledAmount` / `unSettledAmount` / `rqstPaymentAmount` / `unRqstPaymentAmount` 四个字段**本接口从来没赋过值**，恒 0 |
| 详情 `DetailAsync` | `orderInvoiceAmount` 有值；`settlementOccupiedAmount` 恒 0 |
| 币别分组 `statementCurrencyGroup` | 只有应收/应付**金额**合计，没有任何占用合计 |

本次把两个额度补齐到费用行，并在币别分组上加 4 列占用合计（两套额度 × 收/付各一列）。

上游的 `SettlementOccupiedAmount` 字段与 `IOrderFeeOccupiedProvider` 本身是上一次提交（`结算已占用额度`）加的，属于**业务费用**模块，本文档不重复其实现。

# 核心逻辑变更

## 1. `StatementCurrencyDto` 新增 4 列占用合计

文件：`src/CsprojBuilder.Application/App/Statement/Dto/StatementDto.cs`

| 新增字段 | JSON Key | 含义 |
| :-- | :-- | :-- |
| `ReceiveInvoiceOccupiedAmount` | `receiveInvoiceOccupiedAmount` | 应收费用的发票已占用额度合计 |
| `PayInvoiceOccupiedAmount` | `payInvoiceOccupiedAmount` | 应付费用的发票已占用额度合计 |
| `ReceiveSettlementOccupiedAmount` | `receiveSettlementOccupiedAmount` | 应收费用的结算已占用额度合计 |
| `PaySettlementOccupiedAmount` | `paySettlementOccupiedAmount` | 应付费用的结算已占用额度合计 |

沿用该 DTO 上既有 `ReceiveAmount` / `PayAmount` 的 `Receive`/`Pay` 前缀命名。**没有**为这 4 列加「应收−应付」差额字段——既有的 `balanceAmount` 只对 `ReceiveAmount - PayAmount`，额度相减没有业务含义。

## 2. 三个赋值点，两种取数方式

`StatementCurrencyDto` 是共享类型，三处都填，否则某个接口上这 4 列恒为 0，是误导性的数字。

| 位置 | 挂在哪 | 取数方式 | 额外查询 |
| :-- | :-- | :-- | :-- |
| 详情 `DetailAsync` | `orderFeeGroups[].statementCurrencyGroup` | 直接 `Sum` 费用 DTO 上已算好的 `OrderInvoiceAmount` / `SettlementOccupiedAmount` | 0 |
| 详情汇总 | `orderFeeGroups[].statementCurrencyGroupSummary` | 对上一行的结果按 `CurrencyId` 再 `Sum` | 0 |
| 对账单列表 `GetPagedListAsync` | `statementCurrencyGroup` | 本页费用 id 整批取两张占用字典，再按费用 id 查 | +2 |

详情侧零查询是因为费用 DTO 已经算好了，**行与合计天然对得上**，不存在两套聚合漂移的可能。

列表侧的费用是匿名投影（只取了 `Id`/`PaySide`/`CurrencyId`/`Amount` 等几列），拿不到费用 DTO，所以在费用查完之后紧跟着整页取一次：

```csharp
var listFeeIds = orderFees.Select(x => x.Id).Distinct().ToList();
var listInvoiceOccupied = await OrderFeeInvoicedProvider.GetOrderInvoiceAmountMapAsync(listFeeIds);
var listSettlementOccupied = await OrderFeeOccupiedProvider.GetOccupiedAmountMapAsync(listFeeIds);
```

代价是对账单列表每页多两次分组查询（按费用 id `IN`），范围是本页对账单收录的全部费用。

## 3. 选费用接口补齐 4 个恒 0 的费用字段

文件：`src/CsprojBuilder.Application/App/Statement/StatementAdminAppService.cs`，`GetOrderFeeGroupAsync`

这 4 个字段 `OrderFeeDto` 上早就有，本接口一直没赋值。因为要参与按币别汇总，本次一并补上，口径与其余模块对齐：

| 字段 | 取值 |
| :-- | :-- |
| `settledAmount` | `OrderFee.SettledAmount`（结算回写维护的冗余列，直接取） |
| `unSettledAmount` | `OrderFee.Amount - OrderFee.SettledAmount` |
| `rqstPaymentAmount` | `IOrderFeeInvoicedProvider.GetPayableInvoiceAppliedMapAsync`（**只**付费申请已申请，应付侧单独口径） |
| `unRqstPaymentAmount` | `OrderFee.Amount - settlementOccupiedAmount` |

`rqstPaymentAmount` 刻意走 provider 的应付侧单独方法，不自己再写一遍 `PaymentApplicationItem` 聚合。

`unRqstPaymentAmount` 的减数是**结算已占用额度**（付费申请+收费结算+开票申请）而不是 `rqstPaymentAmount`，这样才和付费申请侧「这条费用还能申请多少」同口径。

## 4. 详情费用行补 `settlementOccupiedAmount`

`DetailAsync` 里在已有的 `totalAppliedByFee` 旁边加一次 `GetOccupiedAmountMapAsync`，按费用 id 赋值。详情本来就是整单费用一次性查出来的，多一次分组查询。

# 避坑指南

- **两套额度不是一回事，禁止互相加减或比大小。** 发票额度不含收费结算，结算额度含。同一条费用上 `settlementOccupiedAmount ≥ orderInvoiceAmount` 只在「没有收费结算」时成立，有收费结算时两者的差就是结算掉的那部分。哪一列该显示在哪个页面，按业务含义选，不要图省事只取一个。
- **`settlementOccupiedAmount` ≠ `settledAmount`。** 后者只是「实际结算掉多少钱」，前者还包含尚未结算、仅被申请占住的部分（付费申请、开票申请）。两者含义不同、数值也不同，别拿来互相校验。
- **收/付 是按费用自己的 `paySide` 拆的，不是按占用来源拆的。** 这一点最容易想歪：**付费申请和结算单都允许收付混选**（应收费用进付费申请是做冲抵用的，付费申请详情里本来就有 `receiveAmount`/`payAmount` 两栏），所以一条**应收**费用的占用额度里完全可能有付费申请的份额。唯一被强制的是开票申请——它只能选应收费用，应付费用提交时报「存在应付费用 不可提交开票申请」。因此不要把 `payInvoiceOccupiedAmount` 理解成「付费申请占用」、把 `receiveInvoiceOccupiedAmount` 理解成「开票申请占用」，它们只是「应付费用上的发票占用」和「应收费用上的发票占用」。
- **列表侧的 4 列合计无从与费用行对照。** 对账单列表根本不返回费用行（费用行只在详情和选费用接口里有），前端要核对只能进详情。详情侧的合计是从行直接 `Sum` 出来的，一定对得上。
- **`statementCurrencyGroupSummary` 目前与 `statementCurrencyGroup` 完全等价。** 它是对 `statementCurrencyGroup` 按 `CurrencyId` 再分组求和，而后者本来就已经按 `CurrencyId` 分过组了，等于一次空转，逐元素相同。这是本次之前就存在的状况，本次只是把 4 个新字段照原样一并填上，**没有**改变这个行为。两者都是**业务组内**的汇总（挂在 `orderFeeGroups[]` 下），都不是整单合计——整单没有币别合计，别把 Summary 当整单用。
- **未对账的费用也可能已被占用。** 选费用列表里 `settlementOccupiedAmount > 0` 是正常的：占用来自付费申请/开票申请/收费结算，跟对账没有先后关系。看到「没对过账却已占用」不是脏数据。
