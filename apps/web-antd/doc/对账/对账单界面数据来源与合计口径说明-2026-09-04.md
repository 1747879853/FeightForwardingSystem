# 一、怎么用这份文档

界面上某个数字不对时，按顺序走：

1. **先看第二节**确认字段口径 —— 三个「额度」类字段口径互不相同，混用是最常见的误判来源。
2. **再看第四节**找到该界面该数字的数据来源（接口字段 or 前端计算式）。
3. **再看第五节**确认币别汇总卡的口径 —— 2026-09-05 起只有「前端自算」一条路，展示项只剩 4 个。
4. 最后用 F12 抓接口原值比对：`GetPagedListAsync` / `DetailAsync` / `GetOrderFeeGroupAsync`。

> [!IMPORTANT] 带「筛选」的界面区域统计的都是**筛选后的子集**，不是全量。对账单编辑页的一级行币别合计、底部合计条、币别汇总卡都受筛选影响。列表页当页合计只统计**当前页**。

# 二、费用行字段口径（最容易搞错的一节）

费用行类型为 `OrderFeeAdminApi.OrderFeeDto`（`api/sea-export/order-fee-admin.ts`），详情与选费用两个接口共用。

| 界面列名 | 字段 | 等于什么 | 备注 |
| :-- | :-- | :-- | :-- |
| 金额 | `amount` | 费用原币金额 | — |
| **已申请** | `rqstPaymentAmount` | **只**含付费申请已申请 | 不含开票申请、不含收费结算 |
| 发票占用 | `orderInvoiceAmount` | 开票申请已申请 **+** 付费申请已申请 | **不含**收费结算 |
| 结算占用 | `settlementOccupiedAmount` | 付费申请已申请 **+** 收费结算已结算 **+** 开票申请已申请 | 含「被申请占住但还没结算」的钱 |
| 已结算 | `settledAmount` | 结算回写，**仅**真结算掉的钱 | ≠ `settlementOccupiedAmount` |
| 未结算 | `unSettledAmount` | `amount - settledAmount` | 只扣已结算，不扣被占用的 |
| 可用额度 | `unRqstPaymentAmount` | `amount - settlementOccupiedAmount` | 付费申请侧真实可用额度 |

## 2.1 四条禁止事项

> [!WARNING]
>
> 1. **`orderInvoiceAmount` 与 `settlementOccupiedAmount` 不能互相加减、也不能比大小。** 参与项不同（前者不看收费结算，后者看）。同一条费用两列不相等是正常的，差额就是收费结算掉的部分。
> 2. **`rqstPaymentAmount + unRqstPaymentAmount ≠ amount`。** 因为 `unRqstPaymentAmount` 的减数是 `settlementOccupiedAmount` 而不是 `rqstPaymentAmount`。**别用这个等式校验数据。**
> 3. **`settlementOccupiedAmount ≠ settledAmount`。** 前者含被申请占住的部分，后者只含真结算掉的钱。
> 4. **`balanceAmount` 与占用额度无关。** 它恒等于 `receiveAmount - payAmount`，后端**没有**提供占用额度的「收−付」差额字段，不要用 `balanceAmount` 推算占用差额。

## 2.2 收 / 付是按什么拆的

按**费用自己的 `paySide`** 拆（0=应收，1=应付），**不是**按占用来源拆。

> [!WARNING] 不要把 `payInvoiceOccupiedAmount` 读成「付费申请占用的额度」。付费申请和结算单都允许收付混选（应收费用进付费申请是做冲抵），所以一条**应收**费用的占用里也可能有付费申请的份额。
>
> 正确读法：`receive*` = 应收费用上的占用，`pay*` = 应付费用上的占用。

## 2.3 未对账的费用出现占用是正常的

占用来自付费申请 / 开票申请 / 收费结算，与是否对过账**没有先后关系**，不要当脏数据提 bug。

# 四、各界面数值来源明细

## 4.1 列表页当页合计（index.vue）

数据源：`items[].statementCurrencyGroup[]`（接口，**整张对账单**按币别汇总）。

| 展示项     | 来源 | 计算                                      |
| :--------- | :--- | :---------------------------------------- |
| 应收       | 接口 | Σ `group.receiveAmount`                   |
| 应付       | 接口 | Σ `group.payAmount`                       |
| 发票占用收 | 接口 | Σ `group.receiveInvoiceOccupiedAmount`    |
| 发票占用付 | 接口 | Σ `group.payInvoiceOccupiedAmount`        |
| 结算占用收 | 接口 | Σ `group.receiveSettlementOccupiedAmount` |
| 结算占用付 | 接口 | Σ `group.paySettlementOccupiedAmount`     |

前端只做**跨对账单按币别 code 累加**，不重算任何口径。

> [!IMPORTANT] 这是**当页**合计，翻页会变，不是全库合计。列表接口不返回费用行，要逐条核对请进详情页（对接文档 note#4）。

## 4.2 编辑页一级行（订单分组行）

数据源：**前端从费用行计算**（`groupFeesByOrder`），统计范围是 `filteredFeeDetailRows`（受筛选影响）。

每币别 6 列，`paySide=0` 为收、`paySide=1` 为付：

| 列名             | 计算式                | 实现函数                  |
| :--------------- | :-------------------- | :------------------------ |
| `{币别}应收`     | Σ `amount`            | `calcCurrencySummary`     |
| `{币别}应付`     | Σ `amount`            | `calcCurrencySummary`     |
| `{币别}未收`     | Σ `unSettledAmount`   | `calcCurrencyUnSummary`   |
| `{币别}未付`     | Σ `unSettledAmount`   | `calcCurrencyUnSummary`   |
| `{币别}已申请收` | Σ `rqstPaymentAmount` | `calcCurrencyRqstSummary` |
| `{币别}已申请付` | Σ `rqstPaymentAmount` | `calcCurrencyRqstSummary` |

字段名规则：`currency_{currencyId}_receive` / `_pay` / `_un_receive` / `_un_pay` / `_rqst_receive` / `_rqst_pay`。

> [!IMPORTANT] **列的排列顺序是「跨币别分组」，不是「每币别 6 列连续」。** `buildDynamicCurrencyColumns` 用两轮循环：第一轮排完**所有**币别的应收/应付/未收/未付，第二轮再排**所有**币别的已申请收/已申请付。
>
> 例（CNY + USD）：`CNY应收 CNY应付 CNY未收 CNY未付 USD应收 USD应付 USD未收 USD未付` → `CNY已申请收 CNY已申请付 USD已申请收 USD已申请付`
>
> 这是 2026-09-05 的业务要求，函数注释里已写明，**不要把两轮循环合并回单轮**。

一级行的固定列中，「**应收结算状态**」列取 `transportOrder.recSettlementStatus`（运输订单的应收结算状态），2026-09-05 由「结算状态」改名而来。

> [!WARNING] 不要与对账单**列表页**（`statement/data.ts`）的「结算状态」列/筛选项混淆 —— 后者取对账单自身的 `settlementStatus`，语义不同，名称也刻意保持不同，本次未改。

> [!WARNING] **样式判定必须用 `endsWith` 精确匹配，且长后缀优先。** 因为 `currency_1_un_receive` 和 `currency_1_rqst_receive` 都包含子串 `_receive`。早期用 `includes('_receive')` 判断，导致「未收」「已申请收」被「应收」分支抢先命中、套错颜色。现已改为 `editor.vue` 的 `getCurrencyAmountClass()` 统一判定。
>
> **新增币别列时，务必同步在该函数里补后缀分支，并注意判断顺序。**

## 4.3 编辑页二级行（费用行）

数据源：**全部接口字段直读**，前端不重算。

| 列名       | 来源                    | 说明             |
| :--------- | :---------------------- | :--------------- |
| 金额       | `fee.amount`            | —                |
| **已申请** | `fee.rqstPaymentAmount` | 仅付费申请已申请 |
| 已结算     | `fee.settledAmount`     | —                |
| 未结算     | `fee.unSettledAmount`   | 见下方兜底说明   |
| 汇率       | `fee.exchangeRate`      | —                |

**未结算的兜底**：`mapDetailToFeeRows` 里做了单点兜底 —— `unSettledAmount = fee.unSettledAmount ?? (fee.amount - fee.settledAmount)`。兜底后下游（二级行展示、一级行币别合计、底部合计条、汇总卡）**直接用该字段即可，不要再各自重算**。

## 4.4 编辑页底部合计条（totalAmount）

数据源：`orderGroups`（已筛选）→ 遍历费用行，按 `currencyId` 分组。

| 展示项        | 计算式                                |
| :------------ | :------------------------------------ |
| `应收{币别}:` | Σ `amount` where `paySide=0`          |
| `应付{币别}:` | Σ `amount` where `paySide=1`          |
| `未收{币别}:` | Σ `unSettledAmount` where `paySide=0` |
| `未付{币别}:` | Σ `unSettledAmount` where `paySide=1` |

> [!NOTE] 该 computed 内部还会往 `recAmountMap` / `payAmountMap` / `unRecAmountMap` / `unPayAmountMap` 这几个模块级 ref 写值（computed 带副作用，属历史遗留写法）。这些 ref 目前只被本 computed 自己消费，排查时注意别被绕进去。

## 4.5 选费用弹窗

**一级行**：`buildOrderRow`（`add-fee-statement-modal/data.ts`），6 列口径与 4.2 完全一致，同样由 `buildDynamicCurrencyColumns` 生成列（**共用函数，所以列顺序的跨币别分组规则两处同步生效**）。一级行同样有「应收结算状态」列（`field: 'recSettlementStatus'`）。渲染走 `column.field.startsWith('currency_')` 统一格式化，新增币别列**自动生效**，无需改模板。

**二级行**：接口字段直读 —— 金额 `amount`、**已申请** `rqstPaymentAmount`、**可用额度** `unRqstPaymentAmount`。

**底部合计**（`selectedFeeSummary`）：按**可用额度**口径累加，即 `Σ unRqstPaymentAmount`（按币别分组）。勾选时的默认金额同样取 `unRqstPaymentAmount`。

> [!NOTE] 这里刻意**不用** `unSettledAmount`：后者只扣已结算、不扣被申请占住的部分，会让用户以为可用额度比实际多（对接文档建议 #2）。

# 五、币别汇总卡（FeeSummaryCard）

**只有一条数据路：全部前端从费用行自算。** 2026-09-05 起卡片只展示 4 项（应收/应付/未收/未付），不再有「接口汇总 / 前端自算」双路，也不再展示发票占用、结算占用两组。

## 5.1 各币别卡片

数据源：`props.feeDetails`（编辑页传的是 `filteredFeeDetailRows`，**受筛选影响**），按 `currencyId` 分组累加。

| 展示项 | 计算式                                |
| :----- | :------------------------------------ |
| 应收   | Σ `amount` where `paySide=0`          |
| 应付   | Σ `amount` where `paySide=1`          |
| 未收   | Σ `unSettledAmount` where `paySide=0` |
| 未付   | Σ `unSettledAmount` where `paySide=1` |

`currencyId` 或 `currencyName` 为空的费用行直接跳过（不进任何币别卡）。币别名与符号分别取 `getCurrencyLabel` / `getCurrencySymbol`（枚举缺失时符号回退 `¥`）。

> [!WARNING] `currencySummaries` computed 里还算了 `totalAmount`（应收−应付）和 `unsettledTotal`（未收−未付），但**模板没有渲染这两个字段**。排查「界面上找不到某个数」时先看模板，别只翻 script。

## 5.2 原币折算合计卡片

展示项与 5.1 相同，计算式为 `Σ (字段值 × exchangeRate)`，`exchangeRate` 缺失或为 0 时回退 1（`fee.exchangeRate || 1`）。币别符号固定取 `getCurrencySymbol(1)`（人民币）。

> [!NOTE] 折算卡与底部合计条（4.4）口径不同：折算卡乘汇率合成单一币种，底部合计条按币别分行展示原币值。两者数字对不上是正常的。

## 5.3 与接口汇总的关系

后端 `StatementCurrencyDto` 提供的发票占用 / 结算占用汇总字段，**当前编辑页已无任何消费方**（列表页仍在用，见 4.1）。移除原因：

1. 详情接口只返回「业务组内」汇总，**不返回整单合计**，前端必须自己跨组累加才能用；
2. `StatementCurrencyDto` **不带汇率字段**，折算卡无论如何都得逐条费用乘 `exchangeRate`，用了接口值也会与折算卡产生分位差异；
3. 有筛选 / 本地增删费用时接口汇总不再匹配费用行，混用会出现「应收 100 但占用 500」的矛盾，需额外维护一套退回逻辑。

综合业务取舍后整体移除，卡片回到纯自算。若将来要重新接入，`editor.vue` 的 `buildStatementCurrencyTotals()` 实现可从 git 历史（2026-09-04 版本）取回参考，注意其中 `balanceAmount` **不直接相加**而是按累加后的 `receiveAmount - payAmount` 重算。
