# 个人设置：只能操作自己的 + 同人下名称唯一 — 2026-08-18

## 一、背景意图

`UserSettingAdminAppService`（个人设置）有两个缺陷：

1. **越权**：增删改查全都没有按归属人过滤，任何登录用户都能看到、修改、删除同租户内**别人**的个人设置；
2. **重名**：同一个人名下可以建任意多条同名设置，前端按名称取配置时拿到哪一条不确定。

「个人设置」这个模块的语义就是每人一份私有配置，因此归属判定统一收敛到 `CreatorUserId = 当前登录用户`，名称唯一性也按 `CreatorUserId + Name` 这个维度约束。

表 `App_UserSettings` 上**已有** `(CreatorUserId, Name)` 联合索引（非唯一），校验查询正好走它，**本次不改表、不产生 Migration**。

## 二、核心逻辑变更

改动文件：

| 文件 | 改动 |
| :-- | :-- |
| `src/CsprojBuilder.Application/App/UserSetting/UserSettingAdminAppService.cs` | 五个接口全部按归属人收口；新增名称校验；编辑改为局部更新 |
| `src/CsprojBuilder.Application/App/UserSetting/Dto/UserSettingDto.cs` | 新建入参去掉审计基类；列表入参去掉 `CreatorUserId`；补齐 summary |

### 2.1 归属人收口

新增私有方法 `GetOwnedAsync(long id)`：按主键取**当前登录用户自己**的记录（返回被 EF 跟踪的实体，供编辑与删除复用），取不到就报「输入个人设置错误」。**越权与不存在返回同一个提示**，不区分，避免通过提示文案探测他人数据是否存在。

| 接口 | 收口方式 |
| :-- | :-- |
| `AddAsync` | 不再整体映射入参，显式构造实体，`CreatorUserId` 交给 ABP 从登录态写入 |
| `EditAsync` | **不接受前端传主键**，按 `CreatorUserId + Name` 定位，见 2.3 |
| `DeleteAsync` | 走 `GetOwnedAsync`，再删实体（原来是 `DeleteAsync(input.Id)` 直接按 id 删）。**仍是软删除，本次未改** |
| `DetailAsync` | 查询条件加 `CreatorUserId == 当前用户` |
| `GetPagedListAsync` | 强制 `Where(m => m.CreatorUserId == userId)`；入参 `CreatorUserId` 删除；新增 `Name` **完全匹配**，原 `Keyword` 模糊匹配保留，两者可叠加 |

### 2.2 新增接口为什么不能用 ObjectMapper 整体映射

原来是：

```
var data = ObjectMapper.Map<Entites.UserSetting>(input);
```

而 `UserSettingAddDto` 当时继承 `AuditedEntityDto`，也就是入参上带着 `Id`、`CreationTime`、**`CreatorUserId`**、`LastModificationTime`、`LastModifierUserId`。两者叠加的后果是前端可以自己指定归属人，因为 ABP 的审计填充遇到已有值就不再覆盖：

```
EntityAuditingHelper.SetCreationAuditProperties()
    var entity = entityAsObj as ICreationAudited;
    if (entity.CreatorUserId != null)
    {
        //CreatorUserId is already set
        return;
    }
```

所以本次把新建入参的审计基类去掉，并改为显式 `new Entites.UserSetting { Name, Setting }`，只接收业务字段。

> `[AutoMap(typeof(Entites.UserSetting))]` 特性保留（映射配置留着不影响，仅是不再使用）。**但不要再把入参整体映射到实体上**，否则这个洞会重新打开。

### 2.3 名称校验与编辑时的自动去重

- `NormalizeName(string)`：Trim → 判空 → 判长度（64，与 `App_UserSettings.Name` 列一致）。原来只判了空白，超长会被数据库截断或报错。
- `EnsureNameNotExistsAsync(userId, name)`：**仅新增用**，自己名下已有同名就报「个人设置名称{name}已存在」。表是软删除的，`GetAll()` 已自动过滤掉 `IsDeleted = true` 的行，所以**删掉的名称可以再用**。
- **编辑按名称定位 + 自动去重**：入参不再含 `Id`，按 `CreatorUserId + Name` 取出全部记录；一条都没有报「个人设置名称{name}不存在」（不自动新建）；保留 `CreationTime` 最新的一条（相同则取 id 大的），把本次提交的 `Setting` 写到它上面，其余全部软删除。

为什么编辑不能沿用「报重名」这条路：本模块上线时没有唯一性约束，库里已经存在同一个人名下多条同名的脏数据。如果编辑也报重名，这些用户改哪一条都会被拦，等于**功能被自己的校验锁死**。改成去重之后，保存一次数据就收敛成一条，不需要人工洗数据。

按名称定位带来的两个变化：

- **编辑不再能改名**。名称是定位条件而非可改字段，改名等价于删旧增新。
- **结果幂等**。前端不需要知道库里有几条、留下的是哪条 id；副作用是承载数据的记录 `id` 与 `CreationTime` 可能与界面上原先显示的那条不同，保存后建议刷新。

`GetOwnedAsync(long id)` 现在只剩删除接口在用（详情接口自己带了 `AsNoTracking` 的查询）。

### 2.4 顺带修的

- `EditAsync` 原来调 `UpdateAsync`，会把整行标记为已修改生成**全列 UPDATE**；改为走 EF 变更跟踪只赋值改动列，符合项目「局部更新」约定。
- 全部接口补 `input == null` 判空，`DeleteAsync` 不再在 id 不存在时抛框架的 `EntityNotFoundException`。
- 查询类接口补 `AsNoTracking()`。

## 三、避坑指南

1. **重名判定是「同一个人」维度，不是租户维度**。两个人各有一条同名设置是正常数据，不要按全租户唯一去验收。
2. **新增报错、编辑去重，两个接口行为不一致是刻意的**，原因见 2.3。不要为了「统一」把编辑也改成报错，那会把有脏数据的用户锁死。
3. **编辑会删数据**，虽然是软删除可恢复。测试要专门构造「同一个人名下三条同名」的数据，验证保存一次后只剩创建时间最新的一条，且值是本次提交的值。
4. **列表的 `Name` 是完全匹配、`Keyword` 是模糊匹配**，两个入参各管一件事，不要把 `Name` 也改成 `Contains`。
5. **编辑不接受 `id`**，前端传了也会被忽略（入参 DTO 里已没有这个字段）。要改名只能删旧增新。
6. **没有数据库唯一索引兜底**。软删除表加唯一索引会导致「删了同名的再建」直接违反约束，所以这里只做应用层处理；代价是并发双提交理论上仍可能插入两条同名，但之后任意一次编辑保存都会收敛。真要严格唯一，得配合改表（去掉软删除或加过滤索引），需要单独评估。
7. **别再给新建入参加审计基类**，也别把入参整体 `Map` 到实体上，见 2.2。
8. **越权和不存在共用同一句提示**，测试不要期望能区分出「无权限」。
9. **必须多账号交叉验证**：A 建的设置，B 在列表里看不到，且 B 拿 A 的 id 调详情/编辑/删除都要失败。单账号测不出这次修的问题。
10. 宿主(host)账号本模块本来就不可用（`App_UserSettings` 是 `IMustHaveTenant`，无租户时 ABP 会直接抛异常），本次未改动这一行为。
