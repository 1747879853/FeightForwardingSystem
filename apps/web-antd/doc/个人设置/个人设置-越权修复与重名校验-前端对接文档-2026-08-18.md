# 个人设置 越权修复与重名校验 — 前端对接说明

**日期：** 2026-08-18 **服务：** `UserSettingAdminAppService`，路径前缀 `/api/services/app/UserSettingAdmin/` **权限：** 仅需登录，无权限点 **接口变更：** 没有新增或删除接口；**列表和编辑的入参都有字段调整，新增两类校验提示**。

## 一句话

个人设置以前能看到、能改、能删**别人的**，现在一律只能操作自己的；编辑**不再接受主键 `id`，改为按设置名称定位**；列表的名称查询由模糊改为**完全匹配**；同一个名称下有多条时（历史脏数据）编辑会自动去重，**只保留创建时间最新的那条，其余删掉**。

---

## 1. 入参变化

### 1.1 列表接口：删掉 `creatorUserId`，新增完全匹配的 `name`

| 项目         | 值                                                     |
| :----------- | :----------------------------------------------------- |
| **接口地址** | `/api/services/app/UserSettingAdmin/GetPagedListAsync` |
| **请求方式** | `GET`                                                  |

| 字段 | 变化 | 说明 |
| :-- | :-- | :-- |
| `creatorUserId` | **已删除** | 以前可以传任意用户 id 查他人的设置。现在归属人由后端从登录态取，传了也会被忽略（多余的 query 参数不会报错） |
| `name` | **新增** | 设置名称，**完全匹配**。用于「按名称取某一条配置」的场景 |
| `keyword` | 无变化 | 关键字，**模糊匹配**设置名称。管理页搜索用 |
| `pageIndex` | 无变化 | 页码，默认 1 |
| `pageSize` | 无变化 | 每页条数，默认 10 |
| `sorting` | 无变化 | 排序，默认 `CreationTime DESC` |

前端如果原来在传自己的 `creatorUserId`，**不用改代码也能正常工作**，返回结果一致；原来的 `keyword` 模糊搜索**也照旧可用**。

> `name` 和 `keyword` 是两个独立条件：`name` 精确、`keyword` 模糊，**同时传则两个条件都生效（AND）**，都不传则返回自己的全部设置。

### 1.2 新增接口的 `creatorUserId` 等审计字段不再接收

| 项目         | 值                                            |
| :----------- | :-------------------------------------------- |
| **接口地址** | `/api/services/app/UserSettingAdmin/AddAsync` |
| **请求方式** | `POST`                                        |

入参只剩两个字段：

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `name` | string | **是** | 设置名称，Trim 后不能为空，最长 **64 字符**，同一个人下不能重复 |
| `setting` | string | 否 | 设置值，原样存储不解析。结构化数据请自行序列化成 json 字符串 |

以前入参上还挂着 `id`、`creationTime`、`creatorUserId`、`lastModificationTime`、`lastModifierUserId`（继承自审计 DTO），其中 `creatorUserId` 传了是**真会生效**的，等于可以替别人建设置。现在这些字段已从入参移除，传了也只会被忽略。

### 1.3 编辑接口：删掉 `id`，按设置名称定位

| 项目         | 值                                             |
| :----------- | :--------------------------------------------- |
| **接口地址** | `/api/services/app/UserSettingAdmin/EditAsync` |
| **请求方式** | `PUT`                                          |

入参只剩两个字段，和新增接口完全一样：

| 字段 | 类型 | 必填 | 说明 |
| :-- | :-- | :-- | :-- |
| `id` | — | **已删除** | 不再接受前端传主键 |
| `name` | string | **是** | 设置名称，用来定位自己名下那条设置。该名称不存在时报错，**不会自动新建** |
| `setting` | string | 否 | 新的设置值，整体覆盖 |

> **编辑接口不能改名了**。名称现在是定位条件而不是可改字段：提交的 `name` 用来找记录，找到后只更新 `setting`。要改名请删掉旧的重新新增。

## 2. 行为变化

| 接口 | 以前 | 现在 |
| :-- | :-- | :-- |
| `GetPagedListAsync` | 不传 `creatorUserId` 时返回**整个租户所有人**的设置 | 只返回自己的 |
| `GetPagedListAsync` | 只有 `keyword` 模糊匹配 | `keyword` 模糊匹配保留，另加 `name` **完全匹配** |
| `DetailAsync` | 用别人的 id 能查到 | 报「输入个人设置错误」 |
| `EditAsync` | 传 id 定位，能改别人的，也能改名 | 传 `name` 定位自己的，**不能改名** |
| `DeleteAsync` | 用别人的 id 能删；id 不存在时抛框架异常 | 报「输入个人设置错误」（仍按 id 删，仍是软删除） |
| `AddAsync` | 同名可以无限建 | 自己名下已有同名时报错 |
| `EditAsync` | 同名可以无限存在 | **自动去重**，见下节 |

> **越权与不存在返回同一个提示**（「输入个人设置错误」），前端不需要区分这两种情况。

---

## 2.1 编辑接口的自动去重（重点）

调用 `EditAsync` 保存后，**该名称在你名下一定只剩一条**：

1. 按 `name` 取出你名下所有叫这个名称的记录；
2. 一条都没有 → 报「个人设置名称{name}不存在」；
3. 保留 **创建时间最新** 的一条（创建时间相同则取 id 大的），把本次提交的 `setting` 写到它上面；
4. 其余同名记录全部删除（软删除，库里还能捞回来）。

因此：

- **历史脏数据会被顺手清理掉**。以前没有唯一性校验，同一个人名下可能存在多条同名设置；保存一次就会收敛成一条。
- **结果是幂等的**。因为定位靠名称而不是主键，前端不需要关心库里到底有几条、留下的是哪条 id，保存完拿到的就是「这个名称唯一的一条，值是你刚提交的」。
- **保存成功后建议刷新列表/详情**，因为承载数据的那条记录的 `id`、`creationTime` 可能和你界面上原来显示的不是同一条。

## 3. 新增的失败提示

| 提示文案 | 触发接口 | 触发条件 |
| :-- | :-- | :-- |
| 输入不能为空 | 全部 | Body / 参数为空 |
| 个人设置名称不能为空 | 新增、编辑 | `name` 为空、纯空格 |
| **个人设置名称长度不能超过64** | 新增、编辑 | `name` 超过 64 字符（以前不校验，会被数据库截断或报错） |
| **个人设置名称{name}已存在** | **仅新增** | 自己名下已有同名设置 |
| **个人设置名称{name}不存在** | **仅编辑** | 自己名下没有这个名称的设置，编辑不会自动新建 |
| 输入个人设置错误 | 删除、详情 | id 不存在，**或该数据不属于当前登录用户** |

---

## 4. 对接注意事项

1. **保存流程**：新增走 `AddAsync`（重名报错），改值走 `EditAsync`（名称不存在报错）。两个接口入参一模一样，前端按「这个名称有没有」决定调哪个，可以先用 `GetPagedListAsync?name=xxx` 判断。
2. **名称是这个模块事实上的业务主键**。编辑、去重都按它走，`id` 只在删除和详情接口用。
3. **列表查名称有两个入参**：要精准取某一条用 `name`（完全匹配），管理页做搜索用 `keyword`（模糊匹配）。别拿 `name` 传半截字符串，那样查不到数据。
4. **名称重复的判定范围是「同一个人」**，不是整个租户。两个人各建一个叫「常用列表」的设置是允许的。
5. **删除是软删除，删掉的名称可以再用**。删除后再建同名设置不会报重名。
6. **名称长度按字符数算**，一个汉字算 1 个，上限 64。
7. **`setting` 没有长度限制**，是整体覆盖而不是合并，编辑时要回传完整内容。
8. **没有唯一索引兜底**，重名靠应用层处理。同一个人在两个标签页同时**新增**同名设置，理论上仍可能各插一条；不过之后任意一次编辑保存就会把它们收敛成一条。前端保存按钮仍建议做防重复提交。
9. 个人设置是**按人隔离**的，和「租户配置」不同：这里 A 看不到 B 的，改的也只是自己的。
