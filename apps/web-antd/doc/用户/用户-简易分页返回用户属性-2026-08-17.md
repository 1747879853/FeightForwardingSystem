# 1. 背景意图 (Background)

**白话解释：** `User/GetUserSimplePagedListAsync` 是业务页面"下拉搜索选人"用的接口。它的入参早就支持按 `userAttribute`（用户属性：操作/客服/单证/商务/销售/财务…）筛选，但**出参里没有这个字段**。

于是前端只能这样凑：要么按属性一个个发请求再拼列表，要么在下拉里把人列出来却标不出岗位，用户看到一堆名字分不清谁是操作谁是单证。

本次把 `userAttribute` 一并返回，前端一次请求就能拿到人和他的岗位属性，自行分组、打标签、前端二次过滤都行。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 受影响接口

| 接口 | 地址 | 变更 |
| :-- | :-- | :-- |
| 获取用户简易分页列表 | `GET /api/services/app/User/GetUserSimplePagedListAsync` | 出参**新增** `userAttribute` |

> 纯新增字段，不动原有字段，前端不改也不会坏。

## 2.2 返回字段变更（`UserSimpleDto`）

- 新增：`userAttribute`（`long`，用户属性位掩码，无属性为 `0`）

变更后返回示例：

```json
{
  "totalCount": 2,
  "currentPage": 1,
  "totalPages": 1,
  "items": [
    {
      "id": 1,
      "nickName": "张三",
      "enName": "Zhang San",
      "employeeID": "EMP001",
      "avatar": "/images/avatar.png",
      "userAttribute": 5,
      "companyIds": [1, 8]
    }
  ]
}
```

### `userAttribute` 位掩码取值（`UserAttribute` 枚举，底层类型 `long`，带 `[Flags]`）

| 值  | 名称                    | 说明     |
| :-- | :---------------------- | :------- |
| 0   | None                    | 无       |
| 1   | Operation               | 操作     |
| 2   | CustomerService         | 客服     |
| 4   | Documentation           | 单证     |
| 8   | Business                | 商务     |
| 16  | Sale                    | 销售     |
| 32  | Finance                 | 财务     |
| 64  | OverseasCustomerService | 海外客服 |
| 128 | HR                      | 人事     |
| 256 | Laner                   | 航线     |

示例中的 `5 = 1 | 4`，表示该用户同时是「操作」和「单证」。

## 2.3 实现要点

1. 在 `UserSimpleDto` 上加 `public UserAttribute UserAttribute { get; set; }`，与 `User` 实体上的字段**同名同类型**，`ProjectTo<UserSimpleDto>` 自动按名投影，SQL 只是多带一列。
2. **服务层不需要任何改动**：不像 `companyIds` 要查组织链后在内存里填，本字段就在用户表上，没有额外查询、没有 N+1。
3. 枚举值原样返回**数字**（`UserAttribute` 底层类型是 `long`），不返回中文名，展示文案由前端按上表映射。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **必须按位与判断，不能等值比较**：一个人可以同时是操作和单证（`userAttribute = 5`）。判断"是不是单证"要写 `(userAttribute & 4) === 4`，写成 `userAttribute === 4` 会把多属性的人全漏掉。这是本字段最容易踩的坑。
> 2. **JS 位运算是 32 位的**：枚举底层是 `long`，目前最大值 `256`（航线），用 `&` 完全没问题；但后续若继续翻倍扩到超过 2^31，前端再用 `&` 会溢出出错，届时要改用 `BigInt`。加新属性时记得同步这条。
> 3. **`0` 是"没配属性"不是"某种属性"**：新建但没勾岗位的用户返回 `0`，前端筛选时不要把 `0` 当成默认岗位显示。
> 4. **入参与出参含义一致但用途不同**：入参 `userAttribute` 是"只要包含该属性就命中"的服务端过滤（`(user.UserAttribute & input) == input`）；出参是这个人**全部**属性的组合值。想让用户在前端切换岗位标签而不重新请求，就别传入参，拿全量后在前端按位过滤。
> 5. **`PreOrder` 等复用 `UserSimpleDto` 的地方恒为 `0`**：业务联系单里的 `creatorUser`、`user` 是手动 `new UserSimpleDto { ... }` 投影出来的，只填了姓名/工号/头像，没填 `userAttribute`（同理 `companyIds` 恒为 `[]`）。那些位置不要依赖这两个字段，需要的话得去 `PreOrderAdminAppService` 的投影里补上。
