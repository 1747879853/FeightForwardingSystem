# 1. 背景意图 (Background)

**白话解释：** 一个用户可以同时挂在**多个组织机构**下（例如同时属于 A 公司报关部和 B 公司操作部）。

`User/GetUserSimplePagedListAsync` 是业务页面"下拉搜索选人"用的轻量接口，此前它返回一个单值字符串字段 `organization`（部门名）。该字段有两个问题：

1. **表达不了多组织**：它底层调用 `UserManager.GetOrganizationNames`，规则是"用户**恰好**属于一个组织才返回组织名，否则返回 null"。也就是说，正好命中多组织用户时反而是空的，越是需要区分公司的人，越拿不到值。
2. **拿到的是名字不是 id**：前端要按公司过滤可选人员（例如开单时只能选本公司的操作），需要的是**公司 id**，拿名字无法比对。

本次把 `organization` 下线，改为返回 `companyIds`（所属公司 id 集合），与"用户可属多个组织"的现行逻辑对齐。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 受影响接口

| 接口 | 地址 | 变更 |
| :-- | :-- | :-- |
| 获取用户简易分页列表 | `GET /api/services/app/User/GetUserSimplePagedListAsync` | 移除返回 `organization`；**新增**返回 `companyIds` |

> `UserSimpleDto` 还被 `PreOrder`（业务联系单）的 `creatorUser`、`user` 等字段复用。这些地方是直接 `new UserSimpleDto { ... }` 构造的，不填组织，因此 `companyIds` 恒为 `[]`（此前 `organization` 恒为 `null`），行为等价，前端不要在这些位置依赖 `companyIds`。

## 2.2 返回字段变更（`UserSimpleDto`）

- 移除：`organization`（`string`，单值"部门名"）
- 新增：`companyIds`（`long[]`，所属公司 id 集合，无组织时为 `[]`）

变更后返回示例：

```json
{
  "totalCount": 2,
  "currentPage": 1,
  "totalPages": 1,
  "items": [
    {
      "id": 1,
      "nickName": "张三",
      "enName": "Zhang San",
      "employeeID": "EMP001",
      "avatar": "/images/avatar.png",
      "companyIds": [1, 8]
    }
  ]
}
```

| 字段 | JSON Key | 类型 | 说明 |
| :-- | :-- | :-- | :-- |
| CompanyIds | `companyIds` | `long[]` | 所属公司id集合，已去重；无组织或组织链上无公司节点时为 `[]` |

## 2.3 实现要点

1. **公司 id 的取法**：调用 `GetAllUserOrganizationPathsAsync()`（租户级缓存，`userId -> 组织路径列表`），一个用户可能有多条组织链，每条链是"根→叶（公司→部门）"顺序，取 `OneOrganizationPath.LastOrDefault(x => x.IsCompany)`，即**最靠近本部门的那一级公司**（本身就是公司则取自身），最后 `Distinct()` 去重。
   - 该取法与 `OrganizationUnitAppService.GetUserCompanyIdsAsync`、`CsprojBuilderAppServiceBase.GetCompanyOrgIdAsync` 完全一致，多级公司（公司下挂子公司）场景下取到的是**最近的**那一级公司，而不是最顶层集团。
2. **批量取数，不做 N+1**：走的是缓存字典，一次拿到全租户用户的组织链，循环内只做内存查找；缓存由 `OrganizationCacheInvalidator` 在组织/用户-组织/用户变更时失效。
3. **移除** 对 `UserManager.GetOrganizationNames(userIds)` 的调用（该方法本身保留在 `UserManager` 中，目前已无调用方）。
4. 顺带给查询补上 `AsNoTracking()`（本接口为纯查询）。

## 2.4 文档偏差更正 (Doc Fix)

`用户通用api.md` 原先写"仅返回**审核已通过**且已激活的用户（`Status == 已通过 && IsActive`）"，与代码不符：当前实现**只过滤 `IsActive`**。审核状态过滤是在后续 commit「用户搜不到」中去掉的（否则待审核用户在业务页面选不到人），属于有意为之。本次已把文档中相关的三处描述（接口 Summary、业务规则、与 `UserAdmin` 分页接口对比表）更正为"仅已激活、不按审核状态过滤"。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **`organization` 是破坏性移除**：前端凡是读 `items[].organization` 的地方都会变成 `undefined`，必须改。若页面确实要展示"组织/部门名称"而不只是 id，本接口不提供，请改调 `User/GetUserListByIdsAsync`（返回完整多组织路径 `organizations`，含每级组织的 `id`、`name`、`isCompany`）。
> 2. **`companyIds` 是数组不是单值**：多组织用户会有多个公司 id，不要写成 `companyIds[0]` 就当成"他的公司"。按公司过滤请用"包含"语义：`user.companyIds.includes(当前公司id)`。
> 3. **空数组是正常业务态**：用户没挂任何组织、或所在组织链上一个 `isCompany = true` 的节点都没有（组织树没配公司层），都会返回 `[]`，前端要做空态处理，不要当成接口异常。
> 4. **别拿 `companyIds` 当权限用**：它只表示"这个人挂在哪些公司下"，不代表当前登录人有权看这些公司的数据。数据权限请走 `UserDataPermission` 那套（`GetMyPermissionCompaniesAsync` 等）。
> 5. **`PreOrder` 等复用 `UserSimpleDto` 的地方 `companyIds` 恒为空**：那些字段是手动 `new` 出来的投影，没有填组织，见 2.1 的说明。
