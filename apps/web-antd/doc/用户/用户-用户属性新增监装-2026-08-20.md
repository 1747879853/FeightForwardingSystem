# 用户-用户属性新增监装-2026-08-20

# 1. 背景意图 (Background)

即将开发的**监装模块**里，海运出口的一票货可以对应多条监装单，需要派人到堆场现场监督集装箱装货。这个人在系统里要能被识别出来——按船公司和预计到货日判断「这天这个船公司的某个堆场有没有师傅」，从而做默认提示与派单。

因此在用户属性 `UserAttribute` 上加一个「监装」岗位，作为监装模块的前置改动。本次**只加枚举值**，监装模块本身的表和接口不在本次范围内。

# 2. 核心逻辑变更 (Core Changes)

`src/CsprojBuilder.Core/CsprojBuilderEnum.cs`

| 枚举 | 变更内容 |
| :-- | :-- |
| `UserAttribute`（`[Flags]`，底层 `long`） | 末尾新增 `LoadingSupervision = 512`，`[Display(Name = "监装")]` |
| `UserAttributeEnum`（幂序号，仅界面展示用） | 新增 `LoadingSupervision = 9`；**顺带补上此前漏掉的 `Laner = 8`** |

**没有任何服务层代码需要改**，原因是所有按用户属性走的逻辑都是反射/位运算通用实现：

| 位置 | 为什么自动生效 |
| :-- | :-- |
| `UserAdminAppService.BuildUserAttributeDisplayNameMap()` | 反射遍历 `Enum.GetValues(typeof(UserAttribute))` 取 `Display(Name)` 建映射，Excel 导入里写「监装」即可解析成 512 |
| `UserAdminAppService.ParseUserAttributes()` | 按「操作.客服.财务」这种点分文本查上面的映射表，无需硬编码 |
| `SeaExportAdminAppService` / `SeServiceTaskAdminAppService` / `PreOrderAdminAppService` 的服务项人员提示 | 同样是 `Enum.GetValues` + 按位与过滤后拼中文名 |
| `UserAppService.GetUserSimplePagedListAsync` 的 `userAttribute` 入参过滤与出参 | 纯位掩码运算 `(user.UserAttribute & input) == input`，与具体有哪些位无关 |
| `SeServiceConfig.UserAttribute`（港口服务项配置的负责岗位） | 同一枚举，配置界面多一个可勾选项即可 |

# 3. 数据库变更

**无表结构变更**。`User.UserAttribute` 已经是 `bigint`（枚举底层类型 `long`），512 远未超出范围，存量数据不受影响，**不需要生成 Migration**。

# 4. 避坑指南 (Pitfalls)

- **新增的位必须是 2 的幂且不能复用旧值**：`UserAttribute` 带 `[Flags]`，现有最大位是 `Laner = 256`，所以监装取 `512`。往后继续加要接着 `1024`、`2048`……， **绝对不要**插在中间或改动已有值，否则存量用户的岗位会集体错位。
- **判断要用按位与**：`(userAttribute & 512) === 512` 才是「这个人是监装」，写成 `userAttribute === 512` 会漏掉「既是操作又是监装」的人（值为 `513`）。
- **JS 位运算 32 位上限还没到**：前端用 `&` 判断，目前最大值 `512`，安全。但这条约束仍然成立——后续继续翻倍到超过 2^31（即第 32 位）时，前端必须改用 `BigInt`。每次加新属性都回来看一眼这条。
- **`UserAttributeEnum` 是展示用的幂序号，和 `UserAttribute` 一一对应但值不同**：一个是 `512`，一个是 `9`。它此前漏了 `Laner`，本次一并补齐。这个枚举当前**代码里没有任何引用**，加新属性时别忘了同步，否则两个枚举会继续漂移。
- **`0` 是「没配属性」不是某种属性**：新建但没勾岗位的用户是 `0`，筛监装时不要把 `0` 当默认值。
- **Excel 导入用的是中文 Display 名**：导入模板里用户属性列写「监装」即可，多个岗位用点号分隔（如 `操作.监装`）；写错字会进 `unmatched` 提示，不会静默忽略。
