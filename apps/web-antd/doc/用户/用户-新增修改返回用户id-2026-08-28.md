# 1. 背景意图 (Background)

**白话解释：** 后台「新增或更新用户」接口以前成功只回 HTTP 200，前端拿不到用户 id。新增完如果还要立刻绑附件、跳详情、设角色，只能再靠用户名去查一遍。本次让接口直接把用户 id 吐回来。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 受影响接口

| 接口 | 地址 | 变更 |
| :-- | :-- | :-- |
| 新增或更新用户(含数据权限) | `POST /api/services/app/UserAdmin/CreateOrUpdateUserInAdminAsync` | 由无返回值改为返回用户 id（`long`） |

同模块的 `CreateOrUpdateUserAsync` **未改**，仍无返回值。

## 2.2 出参

ABP 标准包装，`result` 即为用户 id：

```json
{
  "result": 1,
  "success": true,
  "error": null
}
```

| 字段   | 类型 | 说明                                      |
| :----- | :--- | :---------------------------------------- |
| result | long | 用户 id。新增为新生成的 id，更新为入参 id |

完整字段与入参见 `文档/用户/用户api.md` 第 4 节。

## 2.3 实现要点

内部 `CreateUserInAdminAsync` / `UpdateUserInAdminAsync` 本来就返回 `UserDto`，公开方法之前把返回值丢掉了。现在取出 `user.Id` 作为接口结果，业务写入逻辑不变。

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **用户主键是 `long`，不是 `Guid`**：这是 ABP 自带 `AbpUsers` 表，和业务表「新增必须用 Guid」不是同一套。前端按数字接，不要当 Guid 字符串解析。
> 2. **前端原先按「无 result」写的话要改**：以前 `result` 是 `null`，现在是数字。如果前端用 `if (result)` 判断成功，`id === 0` 不会出现（ABP 用户 id 从 1 起），一般没问题；但不要再把「有 result 就算失败」写进判断。
> 3. **只改了 `CreateOrUpdateUserInAdminAsync`**：若页面走的是 `CreateOrUpdateUserAsync`，这次拿不到 id，别调错接口。
