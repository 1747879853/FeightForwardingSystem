# 1. 背景意图 (Background)

**白话解释：** 业务单据上到处都存着"人"的 id——业务员、操作员、申请人、审批人、被转交人。页面要把这些 id 显示成人名（以及判断这个人还在不在职、属于哪个公司/部门、是什么角色）时，此前前端只有两条路：

- 逐个调用 `User/GetUserAsync`：一个单据上有 5 个人就是 5 次请求，且每次都会附带查 `UserProfile`、角色等，返回体里还包含身份证号、邮箱密码、收发件服务器等**与展示无关的敏感字段**。
- 调用 `User/GetUserSimplePagedListAsync`：它是"搜索选人"用的分页接口，**只返回审核已通过且已激活的用户**。历史单据上那些已停用的人会查不到，导致页面显示空白；而且它不返回角色和多组织路径。

因此新增一个**按 id 批量取用户**的接口：一次请求拿回这批用户，不分页，只返回展示所需的字段，并且**不按状态过滤**，保证历史数据里已停用的人也能正常显示姓名。同时兼容"不传 `ids` 返回全部用户"，供前端一次性加载全量用户做本地缓存/自行筛选。

## 接口地址

- 按 id 批量获取：`GET /api/services/app/User/GetUserListByIdsAsync?ids=2&ids=5&ids=9`
- 获取全部用户：`GET /api/services/app/User/GetUserListByIdsAsync`

## 取数与组装逻辑

```
1. ids = input.Ids.Distinct()
2. UserManager.Users.AsNoTracking().WhereIf(ids.Count > 0, ids.Contains(Id))
                                                              → ids 为空则不加过滤，返回全部用户；不按状态过滤
3. _userStore.GetRolesByUserIds(命中的userIds)                → 一次查出全部角色，userId -> List<Role>
4. GetAllUserOrganizationPathsAsync()                         → 读租户级缓存字典，userId -> 组织路径列表
5. 逐条映射为 UserInfoDto，回填 Roles / Organizations
6. OrderBy(ids.Count > 0 ? ids.IndexOf(dto.Id) : dto.Id)      → 传了 ids 按 ids 顺序，否则按用户 id 升序
```

## 为什么单独建 `UserInfoDto` 而不复用 `UserDto` / `UserListDto`

`UserListDto`（`UserDto` 继承自它）包含 `IdNumber`（身份证号）、`EmailPwd`（邮箱密码）、`ReceiveAddrPort` / `SendAddrPort`（收发件服务器）等敏感字段。本接口权限只要求"登录即可"，一旦复用这些 DTO，任何登录用户都能按 id 批量拉取全员的敏感信息。因此单独定义只含展示字段的 `UserInfoDto`。

# 3. 避坑指南 (Blockers & Pitfalls)

> [!IMPORTANT] **坑点 1：本接口不按审核/激活状态过滤，这是刻意设计** `GetUserSimplePagedListAsync` 会过滤 `Status == 已通过 && IsActive`，那是"选人"场景的正确行为。但本接口是"按 id 回显"场景，历史单据上的人可能早已停用，若同样过滤会导致人名显示为空。所以本接口返回全部命中的用户，并把 `enable` 一并返回，由前端决定是否给停用用户加灰显/删除线等样式。**不要**为了"统一"给本接口加上状态过滤。

> [!IMPORTANT] **坑点 2：不存在的 id 被静默忽略，返回条数可能少于传入数量** 用户被真删或传错 id 时不抛异常（批量回显场景抛异常会导致整个页面数据加载失败）。前端必须按 `id` 做匹配而不是按下标硬对应缺失项，找不到时给出兜底展示。

> [!IMPORTANT] **坑点 3：角色与组织必须批量取，禁止在循环里查** 角色走 `_userStore.GetRolesByUserIds(userIds)` 一次 join 查回；组织走 `GetAllUserOrganizationPathsAsync()` 的租户级缓存字典（缓存由 `OrganizationCacheInvalidator` 在组织/用户-组织/用户变更时失效）。若改成在 `Select` 里逐个调 `GetUserOrganizationPathsAsync(userId)`，虽然同样命中缓存，但传入上百 id 时代码语义会退化成 N 次查找，后续维护者容易误改为直查数据库。

> [!IMPORTANT] **坑点 4：数组参数传错会退化成"查全部"** 入参是 `List<long>`，走 `[FromQuery]` 绑定，必须用 `ids=1&ids=2&ids=3` 重复传参。若误传 `ids=[1,2,3]` 或 JSON 字符串，绑定结果为空，而空 `ids` 的语义是**返回全部用户**——接口不会报错，前端会拿到一份全量数据而不易察觉。前端务必确认数组参数的序列化方式。

> [!IMPORTANT] **坑点 5：不传 ids 返回全部用户，没有数量上限** 该行为是刻意保留的（便于前端一次性加载全量用户做本地缓存），但意味着用户表规模增长后返回体会线性变大。若将来用户量级到几千以上，应改为要求前端显式传 `ids`，或另加分页/关键字接口，而不是继续在此接口上拉全量。
