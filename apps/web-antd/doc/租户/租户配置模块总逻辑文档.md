# 1. 业务背景说明 (Background)

**白话解释：**

前端经常需要往后端存一点「整个公司共用的小设置」——列表默认显示哪几列、某个开关要不要打开、某段提示文案是什么。这类东西数量不定、随时会加，如果每加一个就让后端建字段、建表、发版，成本完全不成比例。

「租户配置」就是给前端开一块**自由的键值对存储区**：配置名(`Name`)由前端自己起，值(`Value`)是一个字符串，存什么、怎么解释全由前端决定。后端只负责按当前登录租户隔离地存取，不参与业务含义。

物理落库就是 ABP 设置表 **`Sys_Settings`**（实体 `Abp.Configuration.Setting`）。本模块只碰其中「当前租户 + UserId 为空 + 不是系统预定义名」的那一层。

三个关键定位：

1. **租户级共用**。同一租户下所有用户读到的是同一份数据，A 改了 B 立刻能看到。**不是每人一份的个人偏好**。
2. **无需预定义、无默认值**。配置名不需要事先在后端 `SettingProvider` 里声明；没配过就是没有，接口返回 `null`，后端不会兜一个默认值给你。
3. **后端不解释值**。`Value` 原样存、原样取，要存结构化数据请前端自己序列化成 json 字符串。

## 1.1 表与接口速查

| 要找的东西 | 答案 |
| :-- | :-- |
| 物理表 | **`Sys_Settings`**（实体特性写的是 `AbpSettings`，本项目 `CsprojBuilderDbContext` 把 ABP 表统一加了 `Sys_` 前缀） |
| 自定义键值对（前端自己起名） | **`TenantConfig`**：`/api/services/app/TenantConfig/GetPagedListAsync`、`DetailAsync` |
| 系统预定义设置（站点名、密码策略、时区等） | **`TenantSettings/GetAllSettings`**（**方法名没有 `Async`**），权限 `Admin.Setting.Tenant`，走 `SettingManager` |
| Host 全局设置 | **`HostSettings/GetAllSettings`**，走 `SettingManager` |

两套接口共用同一张表，但读写路径完全隔离：自定义名走仓储直写，预定义名走 `SettingManager`（带缓存）。不要用 `TenantConfig` 去拉设置页上的那些字段。

# 2. 名词与范围约定 (Glossary & Scope)

| 名词 | 含义 |
| :-- | :-- |
| **Sys_Settings** | 本项目设置表的物理名。框架实体 `[Table("AbpSettings")]`，`OnModelCreating` 统一前缀后落到 `Sys_Settings` |
| **租户配置** | 本模块管理的一条自定义键值对，落在 `Sys_Settings` 的租户级那一层 |
| **配置名 (Name)** | 键。前端自定义，同一租户下唯一，是本模块的业务主键 |
| **配置值 (Value)** | 值。字符串，`nvarchar(max)`，可为空 |
| **系统预定义设置** | 后端 `SettingProvider`（`AppSettingProvider` / `AbpZeroSettingProvider` / 邮件、时区等框架 Provider）里声明过的设置名，例如 `App.Site.SiteName`、`Abp.Zero.UserManagement.TwoFactorLogin.IsEnabled` |
| **应用级 / 租户级 / 用户级** | `Sys_Settings` 的三个层级，靠 `TenantId` + `UserId` 的组合区分，详见 3.3 |
| **SettingManager** | ABP 读写系统预定义设置的入口，带内存缓存。**本模块完全不走它** |

**范围边界（明确不做的事）：**

| 不做 | 原因 |
| :-- | :-- |
| 不支持应用级（Host 全局）配置 | 本模块定位是租户自己的配置，Host 全局设置走现有的 `HostSettingsAppService` |
| 不支持用户级（每人一份）配置 | 需求是租户共用；按人存的偏好要另开模块或另开一层 `UserId` |
| 不支持改配置名 | 改名等价于删旧增新，没必要多一条更新路径 |
| 不支持存在即改的 upsert 单接口 | 本期按标准增删改查交付，前端先查详情再决定调新增还是编辑 |
| 不读写系统预定义设置 | 那些名字由 `SettingManager` 带缓存管理，混写会产生缓存不一致 |

## 3.3 三个层级怎么区分（理解本表的关键）

`Sys_Settings` 一张表同时装着三个层级的设置，靠两个字段的组合区分：

| 层级 | TenantId | UserId | 谁在用 |
| :-- | :-- | :-- | :-- |
| 应用级（Host 全局） | NULL | NULL | 现有 `HostSettingsAppService` / `SettingManager` |
| **租户级** | 租户 Id | NULL | **本模块 + 现有租户设置页 `TenantSettingsAppService`** |
| 用户级 | 租户 Id（Host 用户为 NULL） | 用户 Id | 通知订阅等按人存的设置 |

本模块的所有增删改查都硬编码 `TenantId = 当前租户 AND UserId IS NULL`，既不会读到别的租户，也不会碰到应用级和用户级的行。同一层里系统预定义名再由 `ISettingDefinitionManager` 名单排除。

## 3.4 索引

| 索引 | 字段 | 是否唯一 | 用途 |
| :-- | :-- | :-- | :-- |
| `IX_Sys_Settings_TenantId_Name_UserId` | `TenantId`, `Name`, `UserId` | **是** | 保证同一层级下配置名不重复；本模块的按名查询也走它 |
| `IX_Sys_Settings_UserId` | `UserId` | 否 | 框架自带 |

> 唯一索引是数据库层的最后兜底。应用层在新增前会先查一次是否重名，目的是给出「配置名 xxx 已存在,请直接修改」这种可读提示，而不是把数据库异常抛给前端。

# 4. 功能与操作说明 (Features & Operations)

| 操作 | 接口 | 说明 |
| :-- | :-- | :-- |
| **新增** | `AddAsync` | 传配置名 + 配置值。重名报错，不会静默覆盖。返回自增 id（前端一般不用存） |
| **编辑** | `EditAsync` | 按配置名定位，**只更新 `Value` 一列**。配置名不存在时报错，不会自动新增 |
| **删除** | `DeleteAsync` | 按配置名删，支持单条和批量。物理删除，全有或全无 |
| **分页列表** | `GetPagedListAsync` | 分页 + 关键字模糊匹配配置名和配置值，按配置名升序 |
| **详情** | `DetailAsync` | 按配置名查单条，**没配过返回 null 而不是报错**；若 `name` 是系统预定义名则直接抛错，不会返回 null |

- 五个接口都在 `TenantConfigAppService`，类级 `[AbpAuthorize]`，**登录即可访问，不需要任何权限点**。
- 列表和详情都返回创建人、最后修改人的 **NickName**（`CreatorUserName` / `LastModifierUserName`），取自 `CsprojBuilderAppServiceBase.GetUserInfoMapAsync()` 的租户级用户缓存。
- 查询类接口全部 `AsNoTracking()`；编辑走 EF 变更跟踪只改 `Value`，不调用 `UpdateAsync`，生成的 UPDATE 只含 `Value` 与审计列。
- 本模块**没有字段级屏蔽**（`PropMaskModule`），出入参都不走 `PropMaskInputGuard`。

# 5. 状态流转说明 (Status Transitions)

本模块没有审批流、没有业务状态机，只有一条记录的存在与否：

| 当前状态 | 触发人 / 动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 该配置名不存在 | 调 `DetailAsync` | 仍不存在 | 返回 `null`，`success = true`，**不报错** |
| 该配置名不存在 | 调 `AddAsync` | 存在，值为传入值 | 正常新增 |
| 该配置名不存在 | 调 `EditAsync` | 仍不存在 | 报「配置名 xxx 不存在」，**不会自动新增** |
| 已存在 | 调 `AddAsync` | 保持原值不变 | 报「配置名 xxx 已存在,请直接修改」，**不会覆盖** |
| 已存在 | 调 `EditAsync` | 值被整体替换 | 后提交的赢，无版本校验 |
| 已存在 | 调 `EditAsync` 且值传空 | 存在，值为空 | **记录还在，只是值为空**，与「不存在」是两种不同状态 |
| 已存在 | 调 `DeleteAsync` | 不存在 | 物理删除，不可恢复 |
| `name` 是系统预定义名 | 调新增 / 编辑 / 删除 / 详情 | 不变 | 一律报「配置名{name}是系统预定义设置,请换一个名称」。详情**不会**返回 null |

> 「值为空的记录」和「记录不存在」在接口上表现不同：前者 `DetailAsync` 返回对象且 `value` 为 `null`，后者返回 `null`。前端如果只判断 `value` 是否有值，会把两种情况混在一起，进而在保存时调错接口。

# 7. 核心业务规则 (Core Rules)

## 7.1 数据范围与隔离

- `TenantId` 由后端从登录态取，`UserId` 恒定写 `null`，**前端两个都传不了**。
- 所有查询、编辑、删除都强制带 `TenantId = 当前租户 AND UserId IS NULL`。
- 除此之外，实体 `Setting` 实现了 `IMayHaveTenant`，ABP 的租户过滤器还会再加一层 `TenantId = 当前租户`，两层条件同向，结果一致。
- **宿主(host)账号不可用**：`AbpSession.TenantId` 为空时直接报「宿主用户不能使用租户配置」。原因是宿主没有租户，落库会变成应用级设置，污染 Host 全局配置。
- **租户内不做人和角色的区分**：没有权限点，租户内任何登录用户都能读写全部配置项。

## 7.2 系统预定义设置名的拦截（本模块最重要的一条规则）

`Sys_Settings` 的租户级那一层里，除了本模块写入的自定义配置，还躺着框架和现有设置页写入的行，比如 `Abp.Zero.UserManagement.UserLockOut.IsEnabled`、`App.Site.SiteName`、`Abp.Timing.TimeZone`。

那些名字由 `SettingManager` 读写，而 `SettingManager` **对应用级、租户级、用户级的值都做了内存缓存**，只有通过它的 `ChangeSettingFor*Async` 才会失效缓存。本模块是直接用仓储操作数据库的，绕过了缓存。

因此本模块对「已在 `SettingProvider` 里声明过的设置名」采取**读写双向隔离**：

- **写**：新增、编辑、删除时校验配置名，撞上预定义名直接报「配置名 xxx 是系统预定义设置,请换一个名称」。
- **读**：列表查询条件里排除全部预定义名，所以即使库里有这些行，本模块也看不到它们。
- **详情**：先走 `NormalizeName`，预定义名在查库之前就被拦下，**不会返回 null**。

判定依据是运行时的 `ISettingDefinitionManager.GetAllSettingDefinitions()`，也就是说**后端将来新增一个设置定义，如果和前端已经在用的自定义配置名撞了，那个配置项会立刻从本模块的列表里消失并且改不了**。所以约定：前端自定义配置名统一加 `Web.` 之类的前缀，与后端 `App.` / `Abp.` 前缀分开。

## 7.3 配置名规则

- 必填，Trim 后不能为空（纯空格会被拦）。
- 最长 256 字符，与 `Sys_Settings.Name` 列长度一致。
- 同一租户下唯一，应用层先查再插，数据库唯一索引兜底。
- **大小写不敏感**：SQL Server 默认排序规则不区分大小写，`web.a` 与 `Web.A` 会被判定为重复。
- **创建后不可修改**。要改名只能删旧增新，因此配置名一旦被前端用起来就相当于契约。

## 7.4 配置值规则

- 非必填，`nvarchar(max)`，**不做长度校验**。
- 后端不解析、不校验、不转换，存进去什么样取出来就什么样。
- 会被全局入参 Trim 影响：首尾空格会被去掉（这是全站行为，不是本模块特有）。
- 编辑是**整体覆盖**，不是字段合并。前端存 json 时必须回传完整对象。
- 没有乐观锁，多人同时改同一个配置名，后提交的覆盖前面的。

## 7.5 删除规则

- 物理删除，`Sys_Settings` 没有软删除字段，删了就没了。
- **不需要做引用校验**：本表存的是自由键值对，没有任何其他业务模块通过外键引用这里的行，也没有子表需要级联清理。真正需要拦的是「不许删系统预定义设置」，已由 7.2 的配置名校验统一拦下。
- 批量删除**全有或全无**：先按配置名集合数一遍命中条数，与去重后的入参条数不相等就整批报错，一条都不删。
- 集合内部自动去重、自动剔除空字符串；`names` 非空时忽略 `name`。

## 7.6 校验规则汇总

| 字段 | 校验规则 | 违反时的提示 |
| :-- | :-- | :-- |
| 入参对象 | 不能为 null | 输入不能为空 |
| 登录态 | 必须归属某个租户 | 宿主用户不能使用租户配置 |
| `Name` | 必填，Trim 后非空 | 配置名不能为空 |
| `Name` | 最长 256 字符 | 配置名长度不能超过256 |
| `Name` | 不能是系统预定义设置名 | 配置名{name}是系统预定义设置,请换一个名称 |
| `Name` | 新增时同租户内不能重复 | 配置名{name}已存在,请直接修改 |
| `Name` | 编辑时必须已存在 | 配置名{name}不存在 |
| `Name` | 删除时每条都必须已存在 | 输入配置名错误 |
| `Value` | 无校验 | — |

# 8. 前端交互说明 (Frontend Interaction)

- **保存流程**：先 `DetailAsync`，`result` 为 `null` 走 `AddAsync`，否则走 `EditAsync`。本期没有 upsert 单接口。
- **配置名加前缀**：建议 `Web.<页面或模块>.<配置项>`，一是便于用 `keyword` 按模块筛，二是避开后端 `App.` / `Abp.` 命名空间（见 7.2）。
- **值只有字符串**：数字、布尔、对象都要自己序列化与反序列化，读出来永远是 string 或 null。
- **别当个人偏好用**：租户级共用，A 改了 B 立刻受影响。列宽、主题这类应该按人存的东西不要放这里。
- **别存敏感信息**：无权限点，租户内任何登录用户都能读写全部配置项。
- 列表按配置名升序，前端不要自己重排；分页参数是 `pageIndex` / `pageSize`。
- 系统设置页（站点名、安全策略）走 `TenantSettings/GetAllSettings`，**不要**用本模块列表去筛 `App.` / `Abp.`。

# 9. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **卡点 1：这张表是框架表，混着系统设置和自定义配置**
>
> 直接查库看 `Sys_Settings` 会看到一堆 `Abp.*` / `App.*` 的行，那些**不属于本模块**，是设置页和框架写的。本模块的接口既不返回也不允许改它们。测试时验证「列表只返回自定义配置」这一条，需要对照库里同租户的全部行：库里有 N 行，接口返回的只应是其中 `Name` 不在系统设置定义清单里的那部分。

> [!IMPORTANT] **卡点 2：绝不能用直接改库来测试或修数据**
>
> 本模块的行不走 `SettingManager` 缓存，直接改库是「能生效」的；但如果误改了系统预定义设置的行，`SettingManager` 的缓存不会失效，站点要重启才认，会出现「库里值是新的、页面行为还是旧的」这种极难定位的现象。结论：系统设置一律走设置页，自定义配置一律走本模块接口。

> [!IMPORTANT] **卡点 3：「值为空」和「不存在」是两种状态**
>
> `EditAsync` 传空值只会把 `Value` 清空，记录还在，`DetailAsync` 依然返回对象。前端若用「值为空」来判断没配过，下次保存就会调错接口（该调编辑却调了新增，撞重名报错）。测试需覆盖：清空值后再调 `DetailAsync`，预期 `result` 非 null 且 `value` 为 null。

> [!IMPORTANT] **卡点 4：新增不覆盖、编辑不新增**
>
> 两个接口都是「严格模式」：重名新增报错，缺名编辑报错。任何一方都不做静默兜底。前端如果不先查详情就盲调，必然在某一侧撞到错误提示。

> [!IMPORTANT] **卡点 5：批量删除全有或全无**
>
> 集合里混进一个不存在的配置名，整批都不删，直接报「输入配置名错误」。测试要专门构造混合集合，预期是库里一条都没少，而不是有效的那几条被删掉了。

> [!IMPORTANT] **卡点 6：配置名大小写不敏感，但存进去保留原样**
>
> 用 `Web.A` 建了记录后再用 `web.a` 新增会报重复；但列表里显示的仍是最初存入的 `Web.A`，按 `web.a` 查详情也能查到。前端必须自己统一大小写，否则界面上会出现「明明没有这个配置，却说已存在」的困惑。

> [!IMPORTANT] **卡点 7：宿主账号不可用**
>
> 未切换到具体租户的宿主管理员调本模块任何接口都会报「宿主用户不能使用租户配置」，这是预期行为。宿主要配全局设置请走 Host 设置页。

> [!IMPORTANT] **卡点 8：租户级是共用的，不是每人一份**
>
> 多账号测试时，A 账号新增的配置，同租户的 B 账号在列表里**必须能看到**——这与「快捷文本」那种完全私有的模块正好相反，不要照搬那套验收思路。跨租户才应该互不可见。

> [!IMPORTANT] **卡点 9：详情查预定义名是报错，不是返回 null**
>
> `DetailAsync` 对没配过的自定义名返回 `null`；但对 `App.Site.SiteName` 这类预定义名会先 `NormalizeName` 再查库，直接抛「是系统预定义设置」。前端不要用详情接口去探测系统设置是否存在。

# 10. 权限说明 (Permissions)

| 权限点 | 说明                                                         |
| :----- | :----------------------------------------------------------- |
| 无     | 本模块**不定义任何权限点**，类级 `[AbpAuthorize]` 只要求登录 |

- 设计意图：这块存储服务于前端各业务页面的自身配置，如果挂权限点，没配该权限的操作员打开业务页面就会读不到配置。这与 `QuickTextAppService` 的取舍一致。
- 代价：租户内任何登录用户都能读写、删除全部配置项，**因此不能存敏感信息，也不适合放需要管控的业务参数**。若将来需要管控，应加 `Admin.TenantConfig.*` 权限点并把读接口和写接口拆成两个服务。
- 对比：租户设置页 `TenantSettings/GetAllSettings` 需要 `Admin.Setting.Tenant`。
