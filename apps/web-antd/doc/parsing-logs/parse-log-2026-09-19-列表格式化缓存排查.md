# 解析目标

由海运出口港口列的旧值显示问题，扫描 web-antd 列配置的 field 与 formatter 数据依赖。此次仅排查，没有扩展修改业务代码。

# 核心逻辑梳理

使用 TypeScript 语法树抽取实际 formatter，再调用当前安装 VXE 的 getCellLabel 源码，在同一行标识的缓存保留场景下更新数据。以下 9 个样例均复现“实际 formatter 已输出新值，表格仍返回旧文本”：

| 模块 | 列或场景 | 根因 |
| --- | --- | --- |
| 海运出口、海运进口、空运出口（3 个样例） | 操作人员；销售、客服、单证等列也有相同配置 | field 为 operationUserName 等展示键，实际读取 transportOrder.orderUsers |
| 预录单 | 起运港；目的港同构 | polName / podName 与 polRemark / podRemark 不一致 |
| 海运出口 | 手填发货人文本；收货人、通知人及海进、空运同构 | 绑定对象 name，回退文本变化时 name 可保持空值 |
| 监装列表 | 船名不变、航次由 001 改成 002 | 绑定 seaExport.vessel，显示同时依赖 innerVoyno |
| 客户对账列表 | USD 应收由 100 变成 200 | 虚拟币别列键不变，实际依赖 statementCurrencyGroup；应付及占用金额同构 |
| 运价列表 | 订舱代理 | 绑定 bookingAgent.name，实际读取 bookingAgentName |
| 往来单位 | 从客户改成客户兼供应商 | 绑定 clientType，实际读取 isClient / isSupplier |

另发现空运计费重量/体积重量、运价日期/有效期、审核审批港口等配置具有同类依赖偏差，尚未逐项验证。不把依赖同一字段的日期格式化、枚举显示，以及正常替换引用的数组格式化列算作已确认缺陷。运价箱型报价使用插槽渲染，不能仅因 formatter 使用虚拟字段就认定可见单元格受影响。

# 架构洞察

VXE 的格式化缓存只比较 column.field 对应的 cellValue。sortable: false 不会关闭此缓存。单字段列应绑定真实字段；多字段或集合派生列可在查询结果中生成真实显示字段，或采用不依赖此 formatter 缓存的渲染方式，同时维护列持久化与排序映射。

验证范围为真实 formatter 与真实缓存方法的单元级复现；尚未逐页面在浏览器执行保存、搜索流程，不能据此断言所有刷新入口都必现。

# 2026-09-20 处理结果与更正

已修复跨字段派生文本显示缓存，详见[变更记录](../changelogs/change-log-2026-09-20-列表派生文本刷新.md)。运价订舱代理的旧 formatter 虽可单独复现缓存，但实际页面使用 bookingAgentId 插槽，属于上次排查误报，本次保留原交互。其余已确认场景采用实时函数插槽，仍保留列键、排序和权限。
