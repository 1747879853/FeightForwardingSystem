# 0. 这份文档什么时候看

报表现在（数据量小）是快的。这份文档是**等它慢下来之后**再打开的，按顺序往下试，不要跳着做。

核心判断：**货代业务的数据量通常远没到需要换数据库的程度。** 粗算一下，一家中大型货代一年 5~20 万票、每票 10~20 条费用，就是每年 100~400 万条 `App_OrderFees`；五年累计 500 万~2000 万行。这个量级 SQL Server 加对索引是轻松的。真正需要独立 OLAP 库的信号是**费用表过亿行**，撑到那个量级通常已经是行业头部了。

所以下面的顺序是：先榨干现有库 → 再考虑隔离 → 最后才是换库。

# 1. 动手之前先量

不要凭感觉优化。先拿到三样东西。

## 1.1 数据量

```sql
SELECT COUNT(*) FROM App_OrderFees WHERE IsDeleted = 0;
SELECT COUNT(*) FROM App_TransportOrders WHERE IsDeleted = 0;
SELECT MIN(ETD), MAX(ETD) FROM App_TransportOrders;
-- 单次报表大概会命中多少费用（按典型查询条件估）
```

## 1.2 执行计划

抓一次报表实际生成的 SQL（EF Core 日志或 SQL Server Profiler），看执行计划里是哪一步在扫表、哪一步的估计行数与实际行数差得离谱。

## 1.3 分清是哪种慢

这两种慢的解法完全不同，别搞混：

| 症状 | 本质 | 对应方案 |
| :-- | :-- | :-- |
| 点一次报表要等很久，但不影响别人 | **查询本身慢** | 第 2~5 章 |
| 一跑报表，整个系统的下单、查列表都跟着卡 | **报表挤占了业务库资源** | 第 6 章只读副本 |

# 2. 代码层（本次已完成）

以下两项在 2026-08-19 已经做掉了，记在这里是为了说明「代码层已经榨过一轮，不用再回头找」。

## 2.1 聚合下推到数据库

原先是把命中的费用行**整行拉回内存**再用 LINQ 分组，一次几十万行费用全部进内存。

现在改成在数据库端先聚合：

- 利润报表按 `(业务id, 更改单id, 币别id, 收付类型)` 分组
- 欠费报表按 `(业务id, 更改单id, 结算对象id, 币别id)` 分组

返回行数大约是原始费用行的 **1/10 ~ 1/20**。本位币折算（`SUM(Amount × ExchangeRate)`）也在同一次聚合里做完——每条费用汇率不同，聚合之后就没法折算了，这一步必须留在 SQL 里。

代码见 `ReportAdminAppService.ProjectProfitAggAsync` / `ProjectArrearsAggAsync`。

## 2.2 减少子查询嵌套

原先费用查询套了三层：`allowedOrderIds` → `orderIdsQuery` → `orderIdsL2Query`。其中最外层的 `orderIdsQuery.Contains(f.TransportOrderId)` 是冗余的——`orderIdsL2Query` 和 `changeOrderIdsL2Query` 都是从 `orderQuery` 派生的，本身就含 L1 条件。已去掉一层。

## 2.3 发票号查询下推

原先是把命中的费用 id 全部取到内存，再用 `Contains(ids)` 去查发票号。几十万个 `Guid` 拼进 `IN` 会把 SQL 打爆（参数上限 / 巨型 IN 列表）。

现在改成直接 join 费用查询本身，在数据库端投影到分组粒度。应收方向为此给 `IOrderFeeInvoicedProvider` 加了不落地的子查询出口 `GetIssuedInvoiceNoQuery()`，**没有复制那条开票链路的口径逻辑**（该口径必须只有一个出口，见该接口的注释）。

# 3. 最便宜的一刀：强制时间范围

**不带时间条件的报表，按定义就是全表扫。**

> [!IMPORTANT] 2026-08-25 之后这一条对**利润报表**更要紧了：它改成了业务驱动，没有费用的业务也返回一行，所以不带时间条件时返回的行数从「有费用的业务数」变成「全部业务数」。以前「反正没费用的票不返回」这个天然的收窄没有了。

现在业务日期和会计期间都是选填，用户什么都不填就是全量。最省事的优化是加个兜底：业务日期与会计期间**至少填一个**，或者默认给「近一年」让用户自己放宽。

这一条不需要任何基础设施改动，效果通常比后面所有技术手段加起来都明显。当初评审时确认过「就是不分页、不加兜底」，所以没做——真到性能瓶颈时，这是第一个该重新讨论的决定。

# 4. 索引

## 4.1 覆盖索引

报表的访问模式是：按 `TransportOrderId` 关联费用 → 按 `ETD` / `AccountDate` / `ClientId` / `OrgId` / `BizType` 过滤主单 → 按干系人子查询过滤。

对应的覆盖索引方向：

```sql
-- 费用：让聚合走 index-only scan，不回表
CREATE NONCLUSTERED INDEX IX_OrderFees_Report
ON App_OrderFees (TenantId, IsDeleted, TransportOrderId)
INCLUDE (ChangeOrderId, SettlementId, CurrencyId, PaySide, FeeStatus,
         SettlementStatus, InvoiceStatus, IsConfidential,
         Amount, SettledAmount, ExchangeRate);

-- 主单：按业务日期筛的主路径
CREATE NONCLUSTERED INDEX IX_TransportOrders_Report
ON App_TransportOrders (TenantId, IsDeleted, ETD)
INCLUDE (BizType, ClientId, OrgId, AccountDate, SettlementType, SettlementDate,
         MblNum, CommissionNum, CargoId, FeeLocked);

-- 干系人子查询：六类人员筛选都走这条
CREATE NONCLUSTERED INDEX IX_OrderUsers_Report
ON App_OrderUsers (UserAttribute, UserId)
INCLUDE (TransportOrderId);
```

> 注意 ABP 的软删除：所有查询都带 `IsDeleted = 0`，索引前导列要把 `TenantId` / `IsDeleted` 放进去，否则筛选性会打折。

## 4.2 非聚集列存索引（本章重点）

**这是我认为性价比最高的一招，很多人不知道 SQL Server 有。**

SQL Server 支持在 OLTP 表上直接建**非聚集列存索引**，微软管这个叫 HTAP / real-time operational analytics，就是为「在业务库上直接跑分析查询」设计的。

```sql
CREATE NONCLUSTERED COLUMNSTORE INDEX IX_OrderFees_Analytics
ON App_OrderFees (TenantId, IsDeleted, TransportOrderId, ChangeOrderId, SettlementId,
                  CurrencyId, PaySide, FeeStatus, Amount, SettledAmount, ExchangeRate)
WITH (COMPRESSION_DELAY = 60 MINUTES);
```

| 项 | 说明 |
| :-- | :-- |
| 收益 | 聚合类查询通常提速 **10~100 倍**，跟自建同步到 ClickHouse 拿到的收益在同一数量级 |
| 成本 | 不用换库、不用同步、**没有延迟、事务一致**、代码零改动 |
| 代价 | 写入有额外开销。`App_OrderFees` 的写入频率（录费用、结算回写）对列存来说不算高 |
| 调优 | `COMPRESSION_DELAY` 让热行先待在 delta store 里再压缩，进一步降低对写入的影响 |

**判断：列存索引 + 第 2 章的聚合下推，八成能解决问题，而且一天之内就能验证。真做到这一步还不够再往下看。**

# 5. 同库物化

## 5.1 索引视图预聚合

报表最热的那部分——按 `(业务id, 更改单id, 结算对象id, 币别id, 收付类型)` 对 `Amount` / `SettledAmount` 求和——正好符合 SQL Server 索引视图的限制（单表、有 GROUP BY、有 SUM 和 COUNT_BIG、无外连接、无子查询）。

```sql
CREATE VIEW dbo.vw_OrderFeeAgg WITH SCHEMABINDING AS
SELECT TenantId, TransportOrderId, ChangeOrderId, SettlementId, CurrencyId, PaySide,
       SUM(Amount) AS Amount, SUM(SettledAmount) AS SettledAmount,
       SUM(Amount * ExchangeRate) AS AmountBase,
       COUNT_BIG(*) AS RowCnt
FROM dbo.App_OrderFees
WHERE IsDeleted = 0
GROUP BY TenantId, TransportOrderId, ChangeOrderId, SettlementId, CurrencyId, PaySide;

CREATE UNIQUE CLUSTERED INDEX IX_vw_OrderFeeAgg
ON dbo.vw_OrderFeeAgg (TenantId, TransportOrderId, ChangeOrderId, SettlementId, CurrencyId, PaySide);
```

数据库自动维护，写入时增量更新，查询直接读聚合结果，再 join 业务表取展示字段。比自己建汇总表加触发器强，因为**不会漂**。

**注意事项：**

- `ChangeOrderId` / `SettlementId` 可空，索引视图的唯一聚集索引不允许键列为 NULL，需要用 `ISNULL(..., '00000000-0000-0000-0000-000000000000')` 包一层
- 必须 `SCHEMABINDING`，之后改 `App_OrderFees` 的列要先删视图
- 建索引视图的会话和写入会话都要求特定的 `SET` 选项（`ANSI_NULLS`、`QUOTED_IDENTIFIER` 等），EF Core 默认是对的，但要确认

## 5.2 自建汇总表（不推荐）

用触发器或应用层维护一张 `App_OrderFeeReportFacts` 宽表。**能不用就不用**——维护成本高，且一定会出现「汇总表和明细对不上」的事故。索引视图能覆盖的场景就用索引视图。

# 6. 只读副本（解决的是另一个问题）

如果痛点是「跑报表把业务库拖慢了，别人下单卡住」，那 **Always On 可读辅助副本**是最省事的解法：

- 技术栈不变
- 代码只改连接串（报表走只读连接）
- 报表流量和业务流量物理隔离

**它不会让单次查询变快**，只是防止报表影响业务。第 1.3 节区分的两种慢，这一章只解决第二种。

# 7. 独立 OLAP 库 + 实时同步

只有第 2~6 章全做完还不够，才走到这一步。这不是技术选型问题，是**要不要背一套长期运维负担**的问题。

## 7.1 两个致命的坑

### 坑一：数据权限搬不过去

这是最大的问题。报表能看到哪些费用，取决于：

- `OrderUser` 干系人行（销售/商务/操作/客服/单证/海外客服/航线）
- 组织树与「本组织及所有下属组织」的展开
- 每个用户/角色的 `UserDataPermission` 配置
- 表级动态权限 `UserTablePermission`
- 机密费用权限 `Admin.OrderFee.Confidential.Get`

这一整套现在都在 C# 里。搬到新库之后只有两条路：

1. 在新库里重新实现一遍 → 两边口径**必然漂移**，而这是**安全问题**不是性能问题（漂了就是越权看到不该看的钱）
2. 先在业务库算出可见业务 id 集合，再带到新库去查 → 那你并没有绕开业务库，收益大打折扣

**这类项目多数死在这一步。**

### 坑二：费用行是可变的，不是 append-only

`OrderFee.SettledAmount` 每次收付结算都会回写，费用本身还能改、能软删。这直接影响选型：

| 候选 | 评价 |
| :-- | :-- |
| **ClickHouse** | 聚合极快，但更新删除是异步 mutation，处理可变行很难受。**不推荐** |
| **StarRocks / Doris** | 主键模型天然支持行级更新，join 能力也比 ClickHouse 强。**要选就选这个** |
| **另一个 SQL Server + 列存** | 引入的新技术最少，但既然同库列存已经能做（第 4.2 章），单独再开一个库的意义有限 |

## 7.2 先挑战一下「实时」这个要求

财务报表一般容忍分钟级延迟。

- 如果 **T+1 或 5 分钟延迟可接受** → 定时批量同步即可，方案简单便宜非常多
- 如果**坚持严格实时** → 得上 CDC（SQL Server 原生 Change Data Capture，Standard 版从 2016 SP1 起支持）或 Debezium + 消息队列

后者你要长期背的东西：同步延迟监控、schema 变更同步、历史数据回填、断点续传、两边对账。**这套运维负担是永久的，不是一次性的。**

# 8. 决策路线

| 顺序 | 做什么 | 成本 | 预期收益 |
| :-- | :-- | :-- | :-- |
| 1 | 量行数 + 抓执行计划 + 分清哪种慢 | 半天 | 决定后面做什么 |
| 2 | 聚合下推、减少嵌套、发票号下推 | — | **已完成** |
| 3 | 强制时间范围兜底 | 半天 | 通常最明显 |
| 4 | 覆盖索引 + 非聚集列存索引 | 1 天 | 聚合快 10~100 倍 |
| 5 | 索引视图预聚合 | 2~3 天 | 再上一个台阶 |
| 6 | 只读副本 | 看运维 | 隔离影响，不提速 |
| 7 | 独立 OLAP 库 + CDC | 数周起 + 长期运维 | 只有 1~6 做完还不够才值得 |

**走到第 7 步的判断标准**：`App_OrderFees` 过亿行、并发报表几十个以上、且第 3~5 步做完单次查询仍在十几秒以上。三个条件同时满足才动。
