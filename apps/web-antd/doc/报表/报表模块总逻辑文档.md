# 1. 业务背景说明 (Background)

**白话解释：**

公司接一票货（一条业务），围绕这票货会产生一堆收付费用：向委托单位收运费（应收），向船公司/场站/代理付费（应付）。业务开始后如果发生变更（改港、改船期、加费用等），会开「更改单」，更改单上也能挂自己的费用。

- **利润报表**：老板视角。一票（或一票的某个更改单）赚了多少钱 = 应收 − 应付，以及利润率，不分收付。算钱时只认**已经提交出去的费用**（提交审核中 + 审核通过），录入中和被驳回的不算。**业务本身必定出现在报表里**，哪怕它一条费用都没录——这样才能看出哪些票漏录了费用。
- **欠费报表**：财务视角。哪些钱该收还没收到（或该付还没付出去），欠了多久。按**结算对象**（欠谁的钱 / 谁欠我们的钱）拆开看。

两个报表都是**查询 `OrderFee`（业务费用表）后按维度聚合**，不是查业务表。

# 2. 数据模型基础 (测试必读)

## 2.1 表关系

```
TransportOrder (业务主表 App_TransportOrders)
  ├─ SeaExport (海运出口 App_SeaExports)     BizType = 0，与主表共用同一个 Id
  ├─ SeaImport (海运进口 App_SeaImports)     BizType = 1，与主表共用同一个 Id
  ├─ AirExport (空运出口 App_AirExports)     BizType = 2，与主表共用同一个 Id
  ├─ BreakBulk (件杂货 App_BreakBulks)       BizType = 3，与主表共用同一个 Id
  ├─ ChangeOrder[]   (更改单 App_ChangeOrders)
  ├─ OrderFee[]      (费用 App_OrderFees)      ← 报表的数据源
  ├─ OrderCtn[]      (箱型箱量 App_OrderCtns)
  ├─ OrderUser[]     (业务干系人 App_OrderUsers)
  └─ OrderCodeGoods[](品名 App_OrderCodeGoodss)
```

**关键点：**

1. 费用只有 `TransportOrderId`（必填）和 `ChangeOrderId`（可空），**没有业务类型字段**。业务类型要 join 主表的 `BizType` 才知道。
2. `ChangeOrderId` 为空 = **原票费用**；不为空 = 该**更改单的费用**。系统里没有「是否原票」这一列，全靠 `ChangeOrderId` 是否为空判断。
3. 费用自身**不参与数据权限**（没有 `UserId`/`OrgId`），所属组织统一取主表 `TransportOrder.OrgId`。

## 2.2 四种业务类型的字段差异（重要，直接影响筛选结果）

下表中标 ✗ 的表示该业务类型**根本没有这个字段**。

| 字段 | 存放位置 | 海运出口 | 海运进口 | 空运出口 | 件杂货 |
| :-- | :-- | :-: | :-: | :-: | :-: |
| 委托单位 | `TransportOrder.ClientId` | ✓ | ✓ | ✓ | ✓ |
| 委托编号 | `TransportOrder.CommissionNum` | ✓ | ✓ | ✓ | ✓ |
| 主提单号 | `TransportOrder.MblNum` | ✓ | ✓ | ✓ | ✓ |
| 业务日期 | `TransportOrder.ETD` | ✓ 开船日期 | ✓ **到港日期** | ✓ 起飞日期 | ✓ 开船日期 |
| 会计期间 | `TransportOrder.AccountDate` / `ChangeOrder.AccountDate` | ✓ | ✓ | ✓ | ✓ |
| 货物类型 | `TransportOrder.CargoId` | ✓ | ✓ | ✓ | ✓ 恒为普通货 |
| 件数/重量/尺码 | `TransportOrder.PKGS/Kgs/Cbm` | ✓ | ✓ | ✓ | ✓ |
| 所属组织 | `TransportOrder.OrgId` | ✓ | ✓ | ✓ | ✓ |
| 干系人 | `OrderUser` | ✓ | ✓ | ✓ | ✓ |
| 品名 | `OrderCodeGoods` | ✓ | ✓ | ✓ | ✓ |
| 订舱代理 | `SeaExport/AirExport/BreakBulk.BookingAgentId` | ✓ | **✗** | ✓ | ✓ |
| 地面代理 | `BreakBulk.GroundAgentId` | **✗** | **✗** | **✗** | ✓ 只返回，不是查询条件 |
| 船公司 | `SeaExport/SeaImport.CarrierId` | ✓ | ✓ | **✗** | **✗** |
| 场站 | `SeaExport.YardId` | ✓ | **✗** | **✗** | **✗** |
| 船名 | `SeaExport/SeaImport/BreakBulk.Vessel` | ✓ | ✓ | **✗** | ✓ |
| 航次 | `SeaExport/SeaImport/BreakBulk.InnerVoyno` | ✓ | ✓ | **✗** | ✓ |
| 装运方式 | `SeaExport.BLType` | ✓ | **✗** | **✗** | **✗** |
| 起运港/目的港 | `POLId`/`PODId` | 海运港 `PortCode` | 海运港 `PortCode` | **空运港 `AirPort`** | 海运港 `PortCode` |
| 箱型箱量 | `OrderCtn` | ✓ | ✓ | **✗ 空运无集装箱** | **✗ 件杂货无集装箱** |

> [!IMPORTANT] **规则：查询条件中的字段在某业务类型上不存在时，该业务类型的数据直接排除。**
>
> 例：填了「船公司」→ 空运出口和件杂货的所有数据都不会出现在结果里；填了「装运方式」或「场站」→ 只剩海运出口的数据；起运港/目的港传海运港 → 空运出口被排除，传空运港 → 海运出口、海运进口、件杂货都被排除。
>
> 返回字段同理：业务类型专属对象里不声明该类型没有的字段（`ReportSeaImportDto` 没有订舱代理/场站/装运方式，`ReportAirExportDto` 没有船公司/场站/装运方式/船名/航次，`ReportBreakBulkDto` 没有船公司/场站/装运方式），空运出口和件杂货的箱型箱量恒为空列表。

## 2.3 港口的两套 Id 空间

海运港（`App_PortCodes`）和空运港（`App_AirPorts`）是两张独立的表，主键都是 `long`，**id 会重复且互不相干**。

因此起运港/目的港的查询条件**必须成对传**：`港口Id` + `是否海运港`。只传 id 会匹配到错误的港口。

为此新增「海空港口合并分页列表」接口（见第 7 章），前端从该接口选港口，拿到的每一项都自带 `IsSeaPort` 标记，原样回传即可。

# 3. 通用规则 (两个报表共用)

## 3.1 过滤层级 (核心，决定金额算得对不对)

所有查询条件按作用对象分三层，**过滤时机不同**：

| 层级 | 作用对象 | 包含的条件 | 不满足时的效果 |
| :-- | :-- | :-- | :-- |
| **L1 业务级** | `TransportOrder` + 对应扩展表 | 关键词、业务类型、委托单位、订舱代理、船公司、场站、业务日期起/止、主提单号、委托编号、起运港、目的港、船名、航次、货物类型、装运方式、结算方式、所属组织、销售/操作/客服/单证/航线/海外客服 | 该业务下**所有**费用都不参与 |
| **L2 单据级** | `TransportOrder` 或 `ChangeOrder`（看费用挂在哪） | 会计期间起/止、是否费用锁定 | 挂在该单据下的费用不参与 |
| **L3 费用级** | `OrderFee` | 审核状态、收付类型、结算状态、付费申请状态、开票状态、是否对账 | 该条费用不参与 |

> [!IMPORTANT] **「过滤后一条费用都不剩就整组不返回」这一条只适用于欠费报表。** 利润报表是主单驱动的：业务通过 L1/L2 就必定返回一行，费用被 L3 筛光了也照样返回，只是金额全为 0。见 4.2。

**L2 的判定方式，按是否合并更改单分两种：**

- **合并 = 否**：原票费用（`ChangeOrderId` 为空）取 `TransportOrder` 上的值；更改单费用取**它自己所属的那张 `ChangeOrder`** 上的值。
- **合并 = 是**：**只按 `TransportOrder` 判定**。主单命中则该业务的全部费用（含所有更改单的）都参与；主单不命中则整个业务排除。

合并模式之所以不逐单据判定，是为了让「筛出来的」和「显示的」是同一个值（显示口径见 3.3）。代价是合并时更改单自己的会计期间和锁定状态筛不到，只有不合并时才筛得到。

**执行顺序：** L1 → L2 → L3 逐层过滤费用行 → 剩下的费用行按第 3.2 节分组。

**分组后空组怎么处理，两个报表不一样：**

| 报表 | 空组处理 | 原因 |
| :-- | :-- | :-- |
| 欠费报表 | **过滤后一条费用都不剩的组，整组不返回** | 报表本身就是「欠了多少钱」，没费用就没有欠款可言 |
| 利润报表 | **业务通过 L1/L2 就必定返回一行**，费用被 L3 筛光也照样返回，只是金额全为 0、币别明细为空列表、利润率为 null | 要能看出哪些票漏录了费用。行集不由费用决定，见 4.2 |

> [!IMPORTANT] **测试要点：** 组内的金额只统计**过滤后保留下来的费用行**。
>
> 例：某业务对客户 A 有 3 条应收，2 条未结算、1 条已结算完毕。筛「结算状态 = 未结算」时，这一行的「应收」只有那 2 条之和，**不是这票对 A 的全部应收**。这是设计如此，不是 bug。

## 3.2 分组规则

| 报表 | 是否合并更改单 = 否 | 是否合并更改单 = 是 |
| :-- | :-- | :-- |
| 利润报表 | 按 `主单Id + 更改单Id` 分组 | 按 `主单Id` 分组 |
| 欠费报表 | 按 `主单Id + 更改单Id + 结算对象Id` 分组 | 按 `主单Id + 结算对象Id` 分组 |

**说明：**

- 「否」时更改单Id 为空的费用自成一组（即原票组），每个更改单各自一组。
- 「是」时原票和所有更改单的费用合并进同一组。
- 欠费报表的**结算对象为空**（费用处于录入状态时允许为空）的费用，**单独归为一个「空结算对象」组**，不排除。

## 3.3 合并模式下组内不唯一字段的取值

合并（是否合并更改单 = 是）时，一个组里同时有原票和更改单的费用。以下字段固定取**原票（主单）**的值，与 3.1 中 L2 条件的判定口径保持一致：

| 字段                   | 合并 = 是 时取值             |
| :--------------------- | :--------------------------- |
| 是否原票 / 更改单-原票 | 固定返回「原票」             |
| 会计期间               | `TransportOrder.AccountDate` |
| 是否费用锁定           | `TransportOrder.FeeLocked`   |

不合并时无歧义：原票组取 `TransportOrder` 的值，更改单组取该 `ChangeOrder` 自己的值。

> [!NOTE] 「是否原票」在合并模式下**没有区分意义**（组里本来就混着原票和更改单的费用），恒返回「原票」。极端情况下该业务的费用可能全部挂在更改单上、组内一条原票费用都没有，此时仍然显示「原票」，属于预期行为。

## 3.4 数据权限（三层，全部要过）

能不能看到一条费用，取决于能不能看到它对应的**业务数据**。三层全部通过才返回：

1. **行级数据权限**：按业务类型分别走 `SeaExportListDataPermissionFilterAsync` / `SeaImportListDataPermissionFilterAsync` / `AirExportListDataPermissionFilterAsync` / `BreakBulkListDataPermissionFilterAsync`。判定口径为：数据所属人、创建人、所属组织（含下属组织）、业务干系人（销售/商务/操作/客服/单证/海外客服/航线）任一命中即可见。

   > 四个具名方法都在 `CsprojBuilderAppServiceBase`，是泛型实现 `BizOrderListDataPermissionFilterAsync<T>` 的薄包装（约束 `T : DataPermissionFullAuditedEntity<Guid>`，四张扩展表与主单共用同一个 Id，所以干系人子查询可以直接拿主单id和扩展表Id比），与各业务模块自己的列表共用同一套口径。**业务 AppService 里不能再写同名的私有实现**，否则会隐藏基类方法。以后再加业务类型，照件杂货的做法加一个具名包装，或直接调泛型方法即可。

2. **表级权限**：`TablePermissionsAsync(query, FrightModule.SeaExport / SeaImport / AirExport / BreakBulk)`。
3. **机密费用权限**：没有 `Admin.OrderFee.Confidential.Get` 权限的用户，`IsConfidential = true` 的费用**不参与统计**（连带影响该组的金额与合计）。

## 3.5 所属组织

- **作为查询条件**：传一个组织 id，实际搜索「该组织 + 其所有下属组织」。
- **作为返回字段**：返回**从最高级组织到本组织的一串** `List<OrganizationUnitSimpleDto>`。取值来源是 `TransportOrder.OrgId`；`OrgId` 为空时返回空列表。

## 3.6 汇率与合计

- 折算汇率一律取 **`OrderFee.ExchangeRate`（该费用自己的汇率）**，不重新按期间取汇率表。
- 折算方向：**本位币(人民币)金额 = 原币金额 × ExchangeRate**。
- 应收和应付在汇率表里取的是不同的值（应收 `DRValue`、应付 `CRValue`），但报表不关心，直接用费用行上已存好的 `ExchangeRate`。
- **汇率为 0 时按 0 计算**（该费用折算后计入 0，不报错、不跳过）。因此合计金额可能小于原币明细之和。
- 分母为 0 导致算不出来的比率类字段，一律**返回 null**（不返回 0，前端显示为空）。

## 3.7 分页与排序

**两个报表都不分页**，一次性返回全部结果 `List<T>`。

查询条件**不做必填兜底**：业务日期、会计期间均为选填，允许不带任何条件做全量查询。

> [!NOTE] 金额聚合是在数据库端按「业务 + 更改单 + (结算对象) + 币别 + 收付」分组求和后才取回的，不会把命中的费用行整行拉进内存。发票号也是直接 join 费用查询、在数据库端投影到分组粒度。数据量涨上来之后的进一步优化路线（强制时间范围、覆盖索引、列存索引、索引视图、只读副本、独立 OLAP 库）见同目录《性能达到瓶颈后的优化方案.md》。

默认排序：

| 报表     | 默认排序                   |
| :------- | :------------------------- |
| 利润报表 | 业务日期倒序，委托编号倒序 |
| 欠费报表 | 超期天数倒序，业务日期倒序 |

# 4. 利润报表

## 4.1 接口

| 项       | 值                                                            |
| :------- | :------------------------------------------------------------ |
| 接口地址 | `POST /api/services/app/ReportAdmin/GetProfitReportListAsync` |
| 方法名   | `GetProfitReportListAsync`                                    |
| 入参     | `ProfitReportQueryDto`                                        |
| 出参     | `List<ProfitReportDto>`                                       |
| 权限     | `Admin.Report.Profit.Get`                                     |

## 4.2 行集与费用状态（本报表与欠费报表最大的差别）

### 业务必定返回一行

**只要业务通过了 L1/L2 条件与数据权限，就必定返回一行**——哪怕它一条费用都没有，或者费用全是「录入」「驳回」状态。这种行的表现是：币别明细为空列表，`合计应收/未收/应付/未付/利润` 全为 0，`合计利润率` 为空。

所以本报表的行集是**主单驱动**的，不是费用驱动：

| 是否合并更改单 | 行集 |
| :-- | :-- |
| 是 | 每个业务一行 |
| 否 | 每个业务的**原票行必定有**；更改单行只在该更改单**有合格费用**时才出现 |

> [!NOTE] 一票没有任何费用时，不合并模式下也只返回 1 行（原票行）。没有合格费用的更改单不会凭空占一行。
>
> 另外「必定返回」仍然受 L2 约束：主单的会计期间不在筛选范围内时，原票行不会出现——但它的某张更改单若在范围内且有合格费用，那一行照样会出现。

### 参与算钱的费用状态

**只统计「非录入、非驳回」的费用**，也就是 `FeeStatus` 为 `Submitted(1) 提交审核` 或 `Passed(2) 审核通过` 的费用。`Entering(0) 录入` 与 `Rejected(3) 驳回` 的费用不计入任何金额。

这个筛选只决定**哪些费用参与算钱**，不影响上面「业务必定返回一行」——费用被筛光了，行还在，只是金额都是 0。

## 4.3 输入参数 `ProfitReportQueryDto`

> 未标「必填」的均为选填；未标「多选」的均为单选。

| 字段名 | 类型 | 含义 | 层级 | 说明 |
| :-- | :-- | :-- | :-: | :-- |
| `IsMergeChangeOrder` | `bool` | 是否合并更改单 | — | **必填**，见 3.2 |
| `BizType` | `BizType?` | 业务类型 | L1 | 0海运出口 1海运进口 2空运出口 3件杂货；不传=全部业务类型都查 |
| `ClientId` | `Guid?` | 委托单位 | L1 | `TransportOrder.ClientId` |
| `BookingAgentId` | `Guid?` | 订舱代理 | L1 | 海运进口无此字段，会被排除 |
| `CarrierId` | `long?` | 船公司 | L1 | 空运出口、件杂货无此字段，会被排除 |
| `YardId` | `Guid?` | 场站 | L1 | 仅海运出口有 |
| `BizDateStart` | `DateTime?` | 业务日期起 | L1 | 以天为单位，含当天 |
| `BizDateEnd` | `DateTime?` | 业务日期止 | L1 | 以天为单位，含当天 |
| `AccountDateStart` | `DateTime?` | 会计期间起 | L2 | 以月为单位，含当月 |
| `AccountDateEnd` | `DateTime?` | 会计期间止 | L2 | 以月为单位，含当月 |
| `Keyword` | `string` | 关键词 | L1 | 模糊匹配主提单号**或**委托编号，命中任一即可。与下面两个单独条件是且的关系 |
| `MblNum` | `string` | 主提单号 | L1 | 模糊匹配 |
| `CommissionNum` | `string` | 委托编号 | L1 | 模糊匹配 |
| `POLId` | `long?` | 起运港Id | L1 | 必须与 `POLIsSeaPort` 同时传 |
| `POLIsSeaPort` | `bool?` | 起运港是否海运港 | L1 | true 查 `PortCode`（排除空运出口），false 查 `AirPort`（排除海运出口、海运进口、件杂货） |
| `PODId` | `long?` | 目的港Id | L1 | 必须与 `PODIsSeaPort` 同时传 |
| `PODIsSeaPort` | `bool?` | 目的港是否海运港 | L1 | 同上 |
| `Vessel` | `string` | 船名 | L1 | 模糊匹配，空运出口无此字段 |
| `InnerVoyno` | `string` | 航次 | L1 | 模糊匹配，空运出口无此字段 |
| `CargoId` | `CargoType?` | 货物类型 | L1 | 0普通货 1冻柜 2危险品 3超限箱 |

| 字段名            | 类型                      | 含义                 |

| `TotalReceivable` | `decimal`                 | 合计应收（本位币）   |
| `TotalUnReceived` | `decimal`                 | 合计未收（本位币）   |
| `TotalPayable`    | `decimal`                 | 合计应付（本位币）   |
| `TotalUnPaid`     | `decimal`                 | 合计未付（本位币）   |
| `TotalProfit`     | `decimal`                 | 合计利润（本位币）   |
| `TotalProfitRate` | `decimal?`                | 合计利润率           |

**`ProfitCurrencyDto`（币别明细，原币，不折算）：**

| 字段名 | 类型 | 含义 | 计算公式 |
| :-- | :-- | :-- | :-- |
| `Currency` | `CurrencySimpleDto` | 币别 | — |
| `Receivable` | `decimal` | 应收 | `Σ Amount (PaySide=收)` |
| `UnReceived` | `decimal` | 未收 | `Σ (Amount − SettledAmount) (PaySide=收)` |
| `Payable` | `decimal` | 应付 | `Σ Amount (PaySide=付)` |
| `UnPaid` | `decimal` | 未付 | `Σ (Amount − SettledAmount) (PaySide=付)` |
| `Profit` | `decimal` | 利润 | `Receivable − Payable` |

**合计的计算公式（全部折算到本位币人民币）：**

```
TotalReceivable = Σ (Amount × ExchangeRate)                    其中 PaySide = 收
TotalUnReceived = Σ ((Amount − SettledAmount) × ExchangeRate)  其中 PaySide = 收
TotalPayable    = Σ (Amount × ExchangeRate)                    其中 PaySide = 付
TotalUnPaid     = Σ ((Amount − SettledAmount) × ExchangeRate)  其中 PaySide = 付
TotalProfit     = TotalReceivable − TotalPayable
TotalProfitRate = TotalPayable == 0 ? null : TotalProfit / TotalPayable
```

> [!IMPORTANT] **利润率的分母是「应付」，不是「应收」**，这是本项目确认的口径。应付为 0 时返回 null。

## 5.5 发票号的取数逻辑

收付两个方向走**完全不同**的链路：

**应收（`PaySide = 收`）：**

```
OrderFee → InvoiceApplicationItem → InvoiceApplication → InvoiceIssueItem → InvoiceIssue.InvoiceNo
```

- 直接复用已有的 `IOrderFeeInvoicedProvider.GetInvoiceMapAsync(orderFeeIds)`，取其中的 `InvoiceNo`。
- 权威来源是 `InvoiceIssue.InvoiceNo`（真正开出的票），**不取** `InvoiceApplication.InvoiceNo`（那是冗余副本）。
- **发票冲红完成后挂靠会被自动解除**，该票不会再出现在结果里，无需额外处理红冲状态。
- 一条费用可以拆到多张发票上，所以是列表。

**应付（`PaySide = 付`）：**

```
OrderFee → PaymentApplicationItem → PaymentApplication.InvoiceNo
```

- 系统中没有现成的批量解析器，需自行 join。
- 与 5.3 节「付费申请状态只看是否提交」的口径保持一致，**不按付费申请单状态过滤**，取所有 `InvoiceNo` 非空的记录。
- 同一费用可能出现在多张付费申请上，所以是列表。

组内多条费用的发票号**去重合并**后返回。

| 字段名           | 类型              | 含义                            |
| :--------------- | :---------------- | :------------------------------ |
| `SettlementType` | `SettlementType?` | 结算方式。0票结 1月结 2约定天数 |

## 8.2 为什么要加

结算方式原先只存在于客户账期表 `ClientBillingPeriod` 上，是按「委托单位 + 业务类型 + 销售 + 组织 + 业务来源 + 生效时间」一整套规则匹配出来的，匹配结果只用来算应结日期，算完即丢。既无法作为 SQL 查询条件，报表也返回不了。

## 8.3 赋值时机

在 `CsprojBuilderAppServiceBase.GetSettlementDateAsync` 中，**计算应结日期的同时**把命中的结算方式一并写入：

| 场景 | `SettlementDate` | `SettlementType` |
| :-- | :-- | :-- |
| 该客户没有任何生效账期 | 业务日期当天 | 票结 |
| 匹配不到符合条件的账期规则 | 业务日期当天 | 票结 |
| 命中规则且为票结 | 业务日期当天；填了 `AddDays` 再加天数，不填不加 | 票结 |
| 命中规则且为月结 | 按间隔月份 + 结算日计算 | 月结 |
| 命中规则且为约定天数 | 业务日期 + 约定天数 | 约定天数 |

## 8.4 语义说明（测试注意）

- 该字段是**下单当时的快照**。之后客户账期规则被修改，历史业务单上的结算方式**不会自动刷新**，与应结日期的行为一致。
- 应结日期（以及由它算出的超期天数）是按**委托单位**的账期算的。收付类型 = 付 时，应结日期同样取这个值，不按供应商账期另算。
- **存量数据不回刷**。新增列之前已存在的业务单该字段为空，按结算方式筛选时这些历史单据查不出来，属于预期行为。

## 8.5 对业务模块的暴露：可查不可改

该字段对海运出口 / 海运进口 / 空运出口三个业务模块开放，但**只读**：

| 场景 | 是否开放 | 说明 |
| :-- | :-: | :-- |
| 详情接口返回 | ✓ | `SeaExportDto` / `SeaImportDto` / `AirExportDto` 增加 `SettlementType` |
| 列表接口返回 | ✓ | 同上 |
| 作为列表查询条件 | ✓ | `SeaExportQueryDto` / `SeaImportQueryDto` / `AirExportQueryDto` 增加 `SettlementType?` 筛选 |
| 新增时录入 | **✗** | `*AddDto` **不含**该字段 |
| 修改时录入 | **✗** | `*EditDto` **不含**该字段 |

**唯一写入口**是 `GetSettlementDateAsync`（见 8.3），跟着应结日期一起自动算出来，前端无法直接改。

# 9. 权限点

需在 `FreightPermissions.cs` 与 `FreightAuthorizationProvider.cs` 中新增（现有的 `Admin_Reportinganalysis` 系列是注释状态，不复用）：

权限树按「报表 → 各张报表 → 具体查询」三层组织。欠费报表按收付拆成两个查询权限，所以它自己需要一个父节点；利润报表只有一个查询权限，直接挂在报表下即可。

```
Admin.Report                        报表（父节点）
├── Admin.Report.Profit.Get         利润报表（只有一个权限，不再往下分层）
└── Admin.Report.Arrears            欠费报表（父节点）
    ├── Admin.Report.Arrears.Receive.Get   应收查询
    └── Admin.Report.Arrears.Pay.Get       应付查询
```

| 权限常量 | 权限字符串 | 汉化 | 说明 |
| :-- | :-- | :-- | :-- |
| `Admin_Report` | `Admin.Report` | 报表 | 父节点 |
| `Admin_Report_Profit_Get` | `Admin.Report.Profit.Get` | 利润报表 | 利润报表查询 |
| `Admin_Report_Arrears` | `Admin.Report.Arrears` | 欠费报表 | **父节点**，接口不校验它 |
| `Admin_Report_Arrears_Receive_Get` | `Admin.Report.Arrears.Receive.Get` | 应收查询 | 收付类型=收 时校验 |
| `Admin_Report_Arrears_Pay_Get` | `Admin.Report.Arrears.Pay.Get` | 应付查询 | 收付类型=付 时校验 |

> [!NOTE] `Admin.Report.Arrears` 这个父节点**必须建**。少了它，应收查询和应付查询会跟利润报表平级挂在「报表」下面，配置界面上看不出这两项属于同一张报表。
>
> 父节点只用于组织权限树，**接口只校验叶子权限**，不校验父节点——这与项目里其它模块的做法一致（例如费用锁定是 `Admin.OrderFee.Lock` 父节点 + `.Get` / `.Edit` 两个叶子）。

欠费报表接口在方法内部按入参 `PaySide` 判定该用哪个叶子权限，无权限时抛出无权访问异常。

**利润报表不区分应收应付**，只用 `Admin.Report.Profit.Get` 一个权限点控制。有这个权限就能同时看到应收、应付和利润，不受欠费报表那两个权限的影响。
