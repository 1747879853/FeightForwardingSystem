# 背景意图

2026-08-10 的「TransportOrderSimpleDto 外键对象化」把 `SeaExport` / `SeaImport` / `AirExport` 三个简要对象加到了 `TransportOrderDto` 与 `TransportOrderSimpleDto` 上。这三个字段 **不参与 AutoMapper 自动映射，必须由代码手动赋值**，于是各模块自行复制了一份填充逻辑。复制过程中出现了系统性退化：

**6 个接口只填了 `SeaExport`，`SeaImport` 与 `AirExport` 从未被赋值。** 这些接口本身并没有把查询限制在海运出口（例如开票申请的费用分组过滤条件是 `.WhereIf(input.BizType.HasValue, x => x.TransportOrder.BizType == input.BizType.Value)`，可以传入海运进口或空运出口；发票开出的助手与业务费用的打印分支则完全没有 `BizType` 判断），所以当业务是海运进口或空运出口时，前端拿到的三个字段全是 `null`，船名／航次／起运港／目的港／船公司／航班全部丢失。

还有一个更隐蔽的连带问题：**这几处手工 new 出来的 `TransportOrderSimpleDto` 都没有给 `BizType` 赋值。** `BizType` 枚举的 `SeaExport = 0` 恰好是默认值，所以「只填 SeaExport」的旧代码看起来是对的，但接口返回的 `bizType` 字段对海运进口和空运出口业务一律错报成 `0`（海运出口）。前端若按 `bizType` 分支渲染，会直接走错分支。

受影响接口：

| 模块 | 接口 | 旧行为 |
| :-- | :-- | :-- |
| 开票申请 | `InvoiceApplicationAdmin/GetOrderFeeGroupAsync` | 只填 `seaExport`，`bizType` 恒为 0 |
| 开票申请 | `InvoiceApplicationAdmin/DetailAsync` | 只填 `seaExport`，`bizType` 恒为 0 |
| 发票开出 | `InvoiceIssueAdmin/DetailAsync` | 只填 `seaExport`，`bizType` 恒为 0 |
| 发票开出 | `InvoiceIssueAdmin/GetSubmittedApplicationListAsync` | 同上（与详情共用助手） |
| 业务费用 | `OrderFeeAdmin/GetPagedListAsync`（`isPrint=true`） | 只填 `seaExport` |
| 业务联系单 | `PreOrderAdmin/TransportOrderDetailAsync` | 只填 `seaExport`，代码内留有 TODO |

# 核心逻辑变更

## 1. 新增业务输出契约 `ITransportOrderBizSimple`

`TransportOrderDto` 与 `TransportOrderSimpleDto` 是两个独立的类（分别继承 `AuditedEntityDto<Guid>` 与 `DataPermissionFullAuditedEntityDto<Guid>`），没有公共基类承载这三个字段，导致填充逻辑无法用一套代码同时服务两种输出——这正是逻辑被复制多份的根本原因。

在 `TransportOrderDto.cs` 中新增契约接口，两个 Dto 同时实现（三个属性与 `Id`、`BizType` 本来就存在，只补接口声明，无需改动任何属性）：

```csharp
public interface ITransportOrderBizSimple
{
    Guid Id { get; }
    BizType BizType { get; }
    SeaExportSimpleDto SeaExport { get; set; }
    SeaImportSimpleDto SeaImport { get; set; }
    AirExportSimpleDto AirExport { get; set; }
}
```

`TransportOrderSimplePrintDto`（继承 `TransportOrderSimpleDto`）与 `TransportOrderFeeLockDto`（继承 `TransportOrderDto`）通过继承自动获得契约，无需单独处理。

## 2. 新增共享填充器 `ITransportOrderBizSimpleFiller`

新文件 `App/TransportOrder/TransportOrderBizSimpleFiller.cs`，按项目既有的 `ITransientDependency` 约定注册（与 `IFeituoTokenProvider` 同一写法），对外只暴露两个方法：

- `FillAsync(IEnumerable<ITransportOrderBizSimple> orders)`：批量填充
- `FillOneAsync(ITransportOrderBizSimple order)`：单条填充

实现要点：

- **三张扩展表与业务表共用同一个 Id**，按 Id 集合一次性批量捞 `SeaExport` / `SeaImport` / `AirExport`，再一次性批量补港口（`PortCode`）、船公司（`Carrier`）、空运港口（`AirPort`）等外键对象，全程无逐条查库。
- 海运出口与海运进口共用港口代码表，港口 id 合并成一次查询；空运出口单独查空运港口表。
- 填充前先把三个字段一律置 `null`，再按 `BizType` 只赋值命中的那一个，三者恒互斥。
- 入参允许为 `null` 或含 `null` 元素，内部先过滤；同一个业务 id 在集合里重复出现多次也能正确填充（发票开出的费用明细就是多条费用指向同一业务）。
- 全部查询走 `AsNoTracking()`，仓储一律走注入的 `IRepository<,>`，**不使用 `GetDbContext()`**。

## 3. 六处调用点改为走填充器

各处删掉自建的 `seaExports` / `ports` / `carriers` 预加载与 `new SeaExportSimpleDto{...}` 代码块，改为在数据组装完成后统一调用一次填充器：

| 文件 | 调用方式 |
| :-- | :-- |
| `InvoiceApplicationAdminAppService.GetOrderFeeGroupAsync` | `FillAsync(result.Select(x => x.TransportOrder))` |
| `InvoiceApplicationAdminAppService.DetailAsync` | `FillAsync(result.FeeGroups.Select(x => x.TransportOrder))` |
| `InvoiceIssueAdminAppService.BuildInvoiceIssueApplicationDtosAsync` | `FillAsync(allTransportOrderDtos)`（详情与已提交列表共用，一次覆盖两个接口） |
| `OrderFeeAdminAppService.GetPagedListAsync` | 复用已有私有助手 `SetTransportOrderBizSimpleAsync(new List<TransportOrderSimpleDto> { printDto })` |
| `PreOrderAdminAppService.TransportOrderDetailAsync` | `FillOneAsync(result)` |

**同时补上 `BizType = to.BizType`。** 三处手工构造 `TransportOrderSimpleDto` / `TransportOrderSimplePrintDto` 的地方（开票申请两处、发票开出一处）原先漏了这个字段，不补的话填充器无法判断业务类型，接口返回的 `bizType` 也会继续错报。

## 4. 去掉 `OrderFeeAdminAppService` 内的重复实现

`SetTransportOrderBizSimpleAsync`（2026-08-11 为费用任务分组新增）原本是一份约 100 行的完整实现，与新填充器逐字重复。现改为一行委托：

```csharp
private Task SetTransportOrderBizSimpleAsync(List<TransportOrderSimpleDto> transportOrders)
{
    return _transportOrderBizSimpleFiller.FillAsync(transportOrders);
}
```

保留这个私有方法名是为了不动 `OrderFeeTaskListAsync` / `OrderFeeTaskDetailAsync` / 打印分支三处调用点（其中列表那处对调用顺序有要求，必须在 `CloneTransportOrderSimple` 之前）。此改动顺带移除了原实现里的 `_transportOrderRepository.GetDbContext()`。

## 5. 清理失效的注入依赖

预加载代码删除后，部分注入仓储变成了死依赖，已连同构造函数参数一并移除：

- `InvoiceIssueAdminAppService`：`_seaExportRepository`、`_portCodeRepository`、`_carrierRepository`
- `InvoiceApplicationAdminAppService`：`_portCodeRepository`、`_carrierRepository`（`_seaExportRepository` 仍用于费用分组的筛选查询，保留）

# 避坑指南

- **手工 new 业务 Dto 时必须显式赋 `BizType`。** `BizType.SeaExport = 0` 是枚举默认值，漏赋值时「只认海运出口」的代码不会报错、也不会返回空，而是静默地把海运进口和空运出口当成海运出口处理。这类 bug 在本次之前一直存在且不易被发现。
- **`SeaExport` / `SeaImport` / `AirExport` 不参与 AutoMapper 映射。** `ObjectMapper.Map<TransportOrderDto>(entity)` 与 `ProjectTo<TransportOrderSimpleDto>()` 都不会填这三个字段，必须显式调用填充器，否则恒为 `null`。
- **新增返回 `TransportOrderDto` / `TransportOrderSimpleDto`（含其子类）的接口，一律调用 `ITransportOrderBizSimpleFiller`，不要再复制填充代码。** 本次 6 个残缺实现就是复制粘贴退化的结果；契约接口 + 单一实现是为了从结构上杜绝这件事再次发生。
- **填充器要在数据权限方法之前调用。** `SetDataPermissionPropsAsync` 之后再填充没有问题，但放在前面可以保证权限脱敏作用于完整对象，本次统一放在 `SetDataPermissionPropsAsync` 之前。
- **同一业务重复出现是常态。** 发票开出的费用明细是扁平结构，多条费用指向同一业务，填充器按 Id 建字典后逐个对象赋值，不能改成「按 Id 去重后只填第一个」。
- **不要用 `GetDbContext()` 绕过仓储。** 需要 `SeaImport` / `AirExport` / `AirPort` / `Carrier` 时，注入对应的 `IRepository<,>`。

# 尚未纳入本次改动

以下接口的返回类型里也含 `TransportOrder`，但三个简要字段**一个都没赋值**（不属于本次「只填海运出口」的范围），如需统一口径可后续接入同一个填充器：

- 付费申请：`GetPagedListForSettlementAsync`、`GetPagedListByCurrencyForSettlementAsync`、`DetailAsync`
- 付费结算：`DetailByCurrencyAsync`
- 收费结算：`GetOrderFeeGroupAsync`、`GetInvoiceApplicationGroupForSettlementAsync`、`DetailAsync`
- 海运出口／海运进口／空运出口／服务项任务各自的列表与详情（`XxxDto.TransportOrder` 走 `ObjectMapper.Map` 后三字段为 `null`）

已正确按业务类型填充、本次未改动的接口：`TransportOrderAdmin/DetailAsync`、`StatementAdmin/GetOrderFeeGroupAsync`、`StatementAdmin/DetailAsync`、`OrderFeeAdmin/OrderFeeTaskListAsync`、`OrderFeeAdmin/OrderFeeTaskDetailAsync`。其中前三处仍是内联实现，后续可一并收敛到填充器。
