# 1. 背景意图 (Background)

**白话解释：** 同日早些时候的 `文档/业务/净重精度四位与DTO校验位数对齐-2026-08-31.md` 把主单和主单箱表的重量体积统一到了 4 位小数，但当时把三张「旁支箱表」列为已知遗留没有一起动。

这三张表的问题是**不会报错、只会悄悄丢精度**：主单箱录了 `1.2345`，拆到分单、派到派车单、或者从业务联系单那边录，再存一遍就变成 `1.23`。用户看到两个界面上同一个箱子的毛重对不上，但没有任何提示告诉他是被截断了。

本次把这三张表连同它们的输入 DTO 一起改到 4 位，至此**全项目的重量体积列精度全部对齐**。

## 2.2 改的 DTO 校验位数

`[DecimalPrecision(scale)]` 会在 **JSON 反序列化时**就把入参 `Math.Round` 到 `scale` 位，所以库列改了 DTO 必须一起改，否则等于没改。机制细节见 `文档/业务/净重精度四位与DTO校验位数对齐-2026-08-31.md` 第 2.2 节。

| 文件 | DTO / 字段 | 原 | 新 |
| :-- | :-- | :-- | :-- |
| `SeaExportSeparateDto.cs` | 分单箱型新增/编辑 · `GrossWeight`、`TareWeight`、`Volume` | 2 | **4** |
| `SeaExportDispatchDto.cs` | 派车箱型新增/编辑 · `GrossWeight`、`TareWeight`、`Volume` | 2 | **4** |

`PreOrderCtnAddDto.Weight`（业务联系单箱型的货重）**本来就没挂** `[DecimalPrecision]`，不挂就不做四舍五入，4 位小数原样透传到 SQL Server，改完库列即可生效，**不需要补这个特性**。

## 2.3 刻意没改的

| 对象 | 字段 | 原因 |
| :-- | :-- | :-- |
| 三张箱表 | `OverLength`、`OverWidth`、`OverHeight` | 超长超宽超高不是重量体积，仍 `decimal(18,2)`，DTO 仍标 2，两边自洽 |
| `App_PreOrderCtns` | `SugPrice`（指导价）、`Price`（卖价） | 金额，不在本次范围，仍 `decimal(18,2)` |
| `App_CtnCodes` | `CtnWeight`（箱皮重）、`LimitWeight`（默认限重） | 箱型基础资料上的标称值，是配置不是录入，2 位够用 |
| `App_YundangShipmentContainers` | `Gwgt`（毛重）、`Vgm` | 云当推送落下来的对方数据，精度跟对方报文走 |
| `App_FeituoAirTrackings` / `...Transports` / `...Events` | `CargoWeight` | 飞驼跟踪数据，当时按对方文档显式定的 `decimal(18,3)` |

至此全项目重量体积列的精度分布是：

- **`decimal(20,4)`**：所有自有业务表的毛重、皮重、净重、体积、货重、KGS、CBM
- **`decimal(18,6)`**：空运货物明细的长、宽、高、体积重、计费重，以及空运出口的泡比
- **`decimal(18,2)`**：超长、超宽、超高，箱型基础资料的箱皮重与限重
- **`decimal(18,3)`**：飞驼空运跟踪的重量（外部数据）

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **存量数据不会因为改精度而变准。** `ALTER COLUMN` 只是把列放宽，历史行里已经被截成 2 位的值仍然是 2 位，不会凭空恢复出后两位。如果业务上需要，得让用户重新录入相关箱子。
> 2. **前端三个界面的输入框小数位要一起放开**：海运出口分单、海运出口派车、业务联系单，毛重 / 皮重 / 体积 / 货重都要允许 4 位小数。只改后端，用户在前端仍然填不进第 3、4 位。
> 3. **超长超宽超高保持 2 位不是遗漏。** 这三个是尺寸超限值，和重量体积不是一类，库列和 DTO 都是 2 位，两边自洽。看到同一张表里 4 位 2 位混着别顺手"统一"掉。
> 4. **业务联系单箱型的货重不要补 `[DecimalPrecision]`。** 它本来就没有，没有反而是对的（不四舍五入，直接透传给 SQL Server 按列精度处理）。补一个 `[DecimalPrecision(4)]` 结果等价但属于多余改动。
