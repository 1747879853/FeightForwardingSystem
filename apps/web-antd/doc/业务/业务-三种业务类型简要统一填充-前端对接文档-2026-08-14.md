# 业务-三种业务类型简要统一填充-前端对接文档-2026-08-14

## 1. 背景意图

以下 6 个接口返回的业务对象（`TransportOrderDto` / `TransportOrderSimpleDto` 及其子类）此前**只填充了 `seaExport`**，海运进口与空运出口业务拿到的 `seaImport`、`airExport` 恒为 `null`；同时这些接口对海运进口、空运出口业务**错误地返回 `bizType = 0`（海运出口）**。

本次统一改为按 `bizType` 填充对应简要对象，并修正 `bizType` 取值。**入参与返回结构均无变化，只是原本为 `null` 的字段现在会有值、`bizType` 的值变正确。**

## 3. 出参变更

业务对象上三个字段的填充规则改为：

| JSON 字段 | 类型 | 填充条件 | 变更 |
| :-- | :-- | :-- | :-- |
| `bizType` | int 枚举 | 始终返回 | **修正**：0=海运出口 / 1=海运进口 / 2=空运出口，此前恒为 0 |
| `seaExport` | `SeaExportSimpleDto` | 仅 `bizType=0` | 不变 |
| `seaImport` | `SeaImportSimpleDto` | 仅 `bizType=1` | **新增填充**，此前恒为 `null` |
| `airExport` | `AirExportSimpleDto` | 仅 `bizType=2` | **新增填充**，此前恒为 `null` |

三个字段恒互斥：当前业务类型对应的那一个有值，另外两个为 `null`。若业务的扩展表记录缺失，对应字段同样为 `null`。

## 4. 前端适配清单

- [ ] 上述 6 个接口改为按 `bizType` 分支读取 `seaExport` / `seaImport` / `airExport`，不要再无条件只读 `seaExport`
- [ ] 检查是否有代码依赖了「这些接口的 `bizType` 恒为 0」这一错误行为（例如硬编码走海运出口分支），需改为按实际 `bizType` 判断
- [ ] 船名／航次取值：海运出口与海运进口都在 `vessel` / `innerVoyno`；空运出口没有航次，只有 `flightNo`（航班），语义与航次无关，不要混用
- [ ] 港口取值：海运走 `pol` / `pod`（港口代码表），空运走 `pol` / `pot` / `pod`（空运港口表），三者 id 分属不同基础资料表，不可互相比对
- [ ] 港口／船公司／空港一律读对象字段（如 `seaImport.pol.cnName`），不要读扁平的 `*Id` / `*Name`
- [ ] 需要完整业务详情时，仍调各自模块的 `DetailAsync`，本接口只给简要

## 5. 兼容性说明

- **无破坏性变更。** 没有删除或重命名任何字段，没有改变任何字段类型，入参不变。
- 原先取 `seaExport` 的海运出口业务，行为与数据完全不变。
- 变化只发生在海运进口与空运出口业务上：`seaImport` / `airExport` 从 `null` 变为有值，`bizType` 从错误的 `0` 变为正确值。
