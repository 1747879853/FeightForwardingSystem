# 1. 背景意图 (Background)

**白话解释：** 费用的数量不是随便填的，单位选「毛重」时它直接等于业务主表的毛重 `Kgs`，选「尺码」时等于体积 `Cbm`。这两列同日已经改成 4 位小数，但费用数量列还是 `decimal(10,2)`（2 位小数）——**取过来的那一刻就被截掉了后两位**。

毛重 `1234.5678` 生成的费用，数量落库变成 `1234.57`，再乘单价算出来的金额跟按真实毛重算的对不上。金额是要收钱的，这个偏差不能留。

本次把费用数量改到 4 位小数，与毛重体积对齐。

# 2. 核心逻辑变更 (Core Changes)

## 2.1 实体列精度

| 表 | 实体 | 字段 | 原精度 | 新精度 |
| :-- | :-- | :-- | :-- | :-- |
| `App_OrderFees` | `OrderFee` | `Quantity` 数量 | `decimal(10,2)` | `decimal(20,4)` |

`decimal(20,4)` = 整数 16 位 + 小数 4 位，最大值 `9999999999999999.9999`，与同日全项目重量体积列的写法一致。

> 落地过程中先按「整数位不变」写成过 `decimal(12,4)`（沿用原来的 8 位整数），同日改为与重量体积统一的 `decimal(20,4)`。**最终以 `decimal(20,4)` 为准**，详见 `文档/业务/重量体积整数位放宽到16位-2026-08-31.md`。

## 2.2 DTO 校验位数

`[DecimalPrecision(scale)]` 会在 **JSON 反序列化时**就把入参 `Math.Round` 到 `scale` 位，库列改了 DTO 不改等于没改。机制细节见 `文档/业务/净重精度四位与DTO校验位数对齐-2026-08-31.md` 第 2.2 节。

| 文件             | DTO / 字段                 | 原  | 新    |
| :--------------- | :------------------------- | :-- | :---- |
| `OrderFeeDto.cs` | `OrderFeeAddDto.Quantity`  | 2   | **4** |
| `OrderFeeDto.cs` | `OrderFeeEditDto.Quantity` | 2   | **4** |

## 2.3 数量是怎么生成的

公共方法 `CsprojBuilderAppServiceBase.ResolveQuantityByUnit(unit, transportOrder, totalTeu, ctnNameCountMap)`：

| 单位 | 数量取值 | 小数位 |
| :-- | :-- | :-- |
| `票` | `1` | 整数 |
| `毛重` | `transportOrder.Kgs ?? 0` | **4 位**（`decimal(20,4)`） |
| `尺码` | `transportOrder.Cbm ?? 0` | **4 位**（`decimal(20,4)`） |
| `件数` | `transportOrder.PKGS ?? 0` | 整数（`int`） |
| `TEU` | `totalTeu` | 整数 |
| 其它（箱型名） | 按 `CtnName` 匹配到的箱子数 | 整数；匹配不到返回 `null`，调用方跳过该条费用 |

只有「毛重」「尺码」两个单位会产生小数，也正是它们撑着这次改动的必要性。

调用这个方法生成费用的入口有三处，本次都受益：

- `PreOrderAdminAppService.GenerateBizFromPreOrderAsync` — 业务联系单审核通过生成费用
- `SeServiceTaskAdminAppService` — 自动费用模板按服务项生成费用
- `OrderFeeAdminAppService.ImportOrderFeesToTransportOrderAsync` — 跨业务批量引入费用（数量在目标业务上重算）

## 2.4 金额不受影响

`Amount` 与 `NoTaxAmount` 仍是 `decimal(18,2)`，仍由 `ToFinancialRound(单价 × 数量)` 算出，保留 2 位。数量精度提高之后，这个乘积只会更准，不需要改金额列。

## 2.5 刻意没改的

| 对象 | 字段 | 原因 |
| :-- | :-- | :-- |
| `App_PreOrderFees` | `Quantity`（业务联系单费用数量） | 仍 `decimal(10,2)`。它是**用户在业务联系单上手填的报价数量**，审核通过生成正式费用时走 `ResolveQuantityByUnit` **重新算**，并不会把这个值抄过去，所以不构成截断链路 |
| `App_InvoiceApplicationGoodsDtls` / `App_InvoiceIssueGoodsDtls` | `Quantity` | 仍 `decimal(18,2)`。这是**发票货物明细行的数量**，用户按发票内容填，与费用数量不是同一条数据，开票申请挂费用走的是 `OrderFeeId` + `AppliedAmount` 而不是数量 |
| `App_OrderFees` | `Amount`、`NoTaxAmount` | 金额，见 2.4 |
| `App_OrderFees` | `UnitPrice`、`NoTaxUnitPrice`（`decimal(18,4)`）、`TaxRate`（`decimal(10,4)`）、`ExchangeRate` | 本来就已经是 4 位或更高，DTO 标注也已对齐 |

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **数量的精度跟着重量体积走。** 数量在单位为毛重 / 尺码时就等于 `Kgs` / `Cbm`，两边写法必须一致，否则又会出现这次要修的截断问题。重量体积列改成什么，数量列就跟着改成什么，当前统一是 `decimal(20,4)`。
> 2. **存量费用的数量不会变准。** `ALTER COLUMN` 只放宽列，历史行里已经被截成 2 位的数量仍是 2 位，连带那些行的金额也仍是按截断后的数量算的。需要修正的话只能重新生成或人工改。
> 3. **前端数量输入框要放到 4 位小数**，否则用户手改数量时仍然填不进第 3、4 位；列表和详情的数量展示也要按 4 位对齐，不然界面显示 `1234.57`、导出却是 `1234.5678`。
> 4. **金额仍是 2 位，不要跟着改。** `Amount = ToFinancialRound(单价 × 数量)` 是财务口径，数量变 4 位只是让乘积更准，金额本身的 2 位不能动。
