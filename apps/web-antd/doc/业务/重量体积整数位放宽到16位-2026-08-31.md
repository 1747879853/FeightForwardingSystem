# 1. 背景意图 (Background)

**白话解释：** 8-28 起，项目里的重量体积列陆续统一成了 `decimal(16,4)`。这个写法的小数位是对的（4 位），但**整数位只有 12 位**——`16` 是总位数，减掉 4 位小数才是整数位。能存的最大值是 `999999999999.9999`。

本次按需求把整数位提到 **16 位**，写法相应变成 `decimal(20,4)`（总位数 = 16 + 4），最大值 `9999999999999999.9999`。

**小数位一位没动，仍然是 4 位。** 所以输入 DTO 上的 `[DecimalPrecision(4)]` 一个都不用改——该特性只控制小数位的四舍五入，与列的总精度无关。这次是纯库列改动。

## 2.3 费用数量一并对齐

| 表 | 实体 | 字段 | 原 | 现 |
| :-- | :-- | :-- | :-- | :-- |
| `App_OrderFees` | `OrderFee` | `Quantity` 数量 | `decimal(10,2)` → 同日曾写作 `decimal(12,4)` | `decimal(20,4)` |

## 2.4 DTO 一律不动

`[DecimalPrecision(scale)]` 只在 JSON 反序列化时按 `scale` 做 `Math.Round`， **看的是小数位，不是总精度**。本次小数位没变，所以：

| DTO 文件 | 相关字段 | 本次是否改动 |
| :-- | :-- | :-- |
| `TransportOrderDto.cs` | `Kgs`、`Cbm`、`GrossWeight`、`TareWeight`、`NetWeight`、`Volume` | 否，仍 `[DecimalPrecision(4)]` |
| `SeaImportDto.cs` | `TotalNetWeight` | 否，仍 `(4)` |
| `SeaExportSeparateDto.cs` | `Kgs`、`Cbm`、箱型三项 | 否，仍 `(4)` |
| `SeaExportDispatchDto.cs` | 箱型三项 | 否，仍 `(4)` |
| `AirExportDto.cs` | `KGS`、`CBM` | 否，仍 `(4)` |
| `OrderFeeDto.cs` | `Quantity` | 否，仍 `(4)` |
| `PreOrderDto.cs` | `Kgs`、`Cbm`、箱型 `Weight` | 否，本来就没挂这个特性 |

# 3. 避坑指南 (Pitfalls)

> [!IMPORTANT]
>
> 1. **`decimal(a,b)` 里的 `a` 是总位数，不是整数位。** 整数位 = `a - b`。要「整数 16 位 + 小数 4 位」就得写 `decimal(20,4)`，写成 `decimal(16,4)` 只有 12 位整数。项目里此前一直写 `decimal(16,4)`，就是踩了这个。
> 2. **本次不需要动任何 DTO。** `[DecimalPrecision]` 管小数位，小数位没变就不用改。看到库列数字变了就顺手去改 DTO，只会把 `(4)` 改错。
> 3. **放宽精度不会丢数据**，`ALTER COLUMN` 从 `decimal(16,4)` 到 `decimal(20,4)` 是纯扩容，存量行原样保留，不需要数据订正脚本。但**反向回滚会截断**，真要回滚得先确认没有超过 `999999999999.9999` 的行。
> 4. **同日三份变更记录里写的 `decimal(16,4)` / `decimal(12,4)` 都已按本次结论订正**，以 `decimal(20,4)` 为准。2026-08-28 及更早的历史记录保留当时的写法不动，读到那些文档时以本文为准。
