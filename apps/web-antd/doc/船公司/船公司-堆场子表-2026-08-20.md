# 船公司-堆场子表-2026-08-20

# 1. 背景意图 (Background)

船公司（`Carrier`）原来是一张单层基础资料表，只有名称、简称、代码、Logo 这些自身属性。业务上一家船公司在不同港口往往有多个**堆场**（还箱/提箱点），操作需要知道具体堆场叫什么、在哪里。本次给船公司挂上一张**堆场子表**（`CarrierYard`），在船公司基础资料里跟主表一起维护。

堆场有四个字段：**名称、地址、排序id、备注**。其中**排序id 不由前端输入**，后端按提交数组的顺序自动自增生成，返回时按其升序排列，保证「录入什么顺序、看到什么顺序」。

实现方式与《包装类型-明细包装子表-2026-08-20》**完全一致**，两处逻辑可互相参照。

# 4. 避坑指南 (Pitfalls)

- **`sortId` 前端不要传**：Add/Edit 的子表 DTO 里没有这个字段，排序完全由数组顺序决定，从 1 开始自增。
- **返回是升序**：`SortId` 升序 = 提交时的数组顺序，前端直接按返回顺序渲染，不要再排一遍。
- **子表全量提交**：前端必须回传保留行的 `id`，只提交增量会导致其余堆场被删除。
- **软删除不级联**：`AbpDbContext` 在 `SaveChanges` 前会把 `ISoftDelete` 主表状态从 `Deleted` 改回 `Modified`，等 EF 执行级联时主表已不是删除态，子表一条都不会被删。因此 `DeleteAsync` 必须显式批量删堆场。
- **局部更新不要调 `UpdateAsync`**：本次已把 `EditAsync` 的 `UpdateAsync` 去掉，后续维护不要加回来。
- **堆场 id 不能重复提交**：同一数组里出现两条相同 `id`，后一条会静默覆盖前一条，已加 `堆场id重复` 拦截。
- **堆场 id 必须属于当前船公司**：传了不属于本船公司的 `id` 报 `输入堆场id错误`，整个编辑回滚。
- **堆场目前没有引用校验**：现阶段没有任何业务表引用 `CarrierYard.Id`，所以编辑时删堆场不做引用校验。 **后续一旦有业务表开始存堆场 id，必须在 `EditAsync` 的删除段补上引用校验**，否则业务单上的 id 会指向已软删堆场。
- **其它模块内嵌的船公司对象不带堆场**：`CarrierDto` 同时被海运运价（`SeFreiPriceDto.Carrier`，见 `SeFreiPriceAdminAppService` 的 DTO 组装）复用，那里只 `Include` 了 `Carrier` 本身，因此 `carrier.carrierYards` 为 **`null`**（不是 `[]`）。需要堆场请单独调船公司详情接口。同理那里的 `creatorUserName` / `lastModifierUserName` 也不会被填充。
- **删除引用校验的模块清单**：船公司被 `SeaExport`、`SeaImport`、`SeFreiPrice` 直接持有 `CarrierId`，这部分逻辑本次未改动，新增直接持有 `CarrierId` 的实体时仍需在 `DeleteAsync` 里补判断。
