# 1. 背景意图 (Background)

运输条款、商品信息、包装类型、签单方式、业务来源、付费方式、币别、货代费用、航线、港口、集装箱、国家等基础资料被大量业务/单据模块通过外键引用。此前这些模块的 `DeleteAsync` 直接物理删除（部分集装箱/国家的删除甚至被注释为空操作），未做引用校验，可能造成已被业务引用的基础资料被误删，导致历史单据外键悬空、显示异常。

本次为这些模块的删除增加引用校验：若该基础资料已被其他模块引用，则禁止删除，并提示具体被哪些模块引用。实现方式统一为：**注入对应引用实体的仓储，使用 `repository.GetAll().AnyAsync(...)` 判断是否存在引用**（不使用 `DbContext.Set`）。

# 2. 核心逻辑变更 (Core Changes)

各 AppService 的 `DeleteAsync`：删除前先校验主记录存在，再逐一检查引用实体，命中则收集中文模块名，最终若存在引用抛出 `UserFriendlyException`，提示 `该XX已被【模块1、模块2】模块引用,禁止删除`。

# 3. 避坑指南 (Pitfalls)

- **引用源以"实体的标量外键列"为准**：排查发现部分中文名相同的实体并非业务引用方，例如：
  - 「商品信息」对应两个实体 CodeGoods(海运业务用) 与 GoodsInfo(仓储用)，二者均做了校验；
  - 「货代费用」对应 FeeCode(海运用) 与 FeeName(仓储/合同用)，二者均做了校验。
- **多类同文件**：`CbpCodeSource`(业务来源被客户账期引用)、`ClientInvoiceBank`(币别被客户开票银行引用)、`PaymentSettlementItem`(原币币别)、`ClientLane`/`ClientExceptService` 等是分单/子表，外键列在子类上，需用子类实体的仓储查询，不能用其父实体。
- **AgreementStorageFee 无标量 FeeNameId**：该实体仅有 `[ForeignKey("FeeNameId")]` 的导航属性 `FeeName`(影子外键)，故用 `x.FeeName.Id == id` 判断。
- **多租户范围**：基础资料多为"通用 不分租户"，而引用实体多为分租户；删除在当前租户上下文执行，校验仅覆盖当前租户的数据(与既有 Carrier 删除一致)。
- **实现约束**：统一使用注入仓储 `GetAll().AnyAsync()`，不使用 `DbContext.Set`。后续若新增直接持有这些外键的实体，需要在对应 `DeleteAsync` 追加仓储与判断。
