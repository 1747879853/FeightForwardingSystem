# 商品信息-规格型号子表-2026-08-13

# 1. 业务背景说明 (Background)

**白话解释：** 海运进口的箱表里要录「规格」和「型号」。原来这两个字段是箱子上的自由文本，每个操作员各写各的，同一个品名的同一种规格能写出七八种写法，没法统计、没法做下拉、也没法复用。本次把规格和型号上移成**品名（`CodeGoods`）的两张子表**，在基础资料里统一维护，箱表改为从该箱所选品名下的规格/型号里**选**，存 id 而不是文本。

> **注意区分**：本模块是海运业务用的商品信息 `CodeGoods`（表 `App_CodeGoodses`，路由 `CodeGoodsAdmin`）。仓库的品名是 `GoodsInfo`（表 `App_GoodsInfos`，路由 `GoodsInfoAdmin`），**没有**规格/型号子表。两者中文名都叫「商品信息」，`OrderCtn.CodeGoodsId` 指向的是前者。

# 2. 功能与操作说明 (Features & Operations)

- **品名维护规格/型号：** 在品名新建/编辑页的「规格」「型号」两个明细表格里录入名称、排序、备注，随品名一次提交。
- **品名编辑子表：** 两张子表按**全量提交 + 差异比对**处理——传了 id 的更新、id 为 null 的新增、原有但本次未提交的删除。
- **品名删除：** 先做引用校验，再显式删除两张子表，最后软删除主表。
- **品名列表/详情：** 返回两张子表全部明细，**按 `SortId` 升序**（与录入顺序一致）。
- **海运进口箱表选规格/型号：** 箱行先选品名，再从该品名下的规格/型号里选，后端强校验归属关系。

# 3. 状态流转说明 (Status Transitions)

本模块为基础资料，无状态机。存在两处删除卡点：

| 当前状态 | 触发人/动作 | 目标状态 | 状态说明 |
| :-- | :-- | :-- | :-- |
| 规格/型号未被箱表选中 | 操作员 编辑品名时移除该明细 | 删除成功 | 明细被软删除 |

| 品名被业务单/分单/派车引用 | 操作员 删除品名 | 删除被拒绝 | 抛 `该商品信息(品名)已被【xx】模块引用,禁止删除` |

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：规格/型号必须属于该箱所选的品名]** `ValidateSeaImportOrderCtnsAsync` 先批量查出所有传入规格/型号 id 的归属品名，再逐箱比对：本行未选 `CodeGoodsId` 却传了规格 id -> `选择规格前必须先选择箱内商品信息(品名)`；规格 id 查不到 -> `规格ID:xxx不存在`；归属品名与本行 `CodeGoodsId` 不一致 -> `规格不属于该箱所选的商品信息(品名)`。型号同理。 **前端切换品名时不清空规格/型号，提交必然报错**，这是最容易踩的联调坑。

> [!IMPORTANT] **[卡点 2：被箱表引用的规格/型号不允许删除]** 品名编辑时若把某条规格/型号从数组里移除，而它已被任何 `OrderCtn` 选中，抛 `待删除的规格已被【业务委托单】的箱型引用,禁止删除`，整个编辑事务回滚。不做这层校验的话，箱子上的 `CodeGoodsSpecId` 会指向一条已软删除的明细，详情接口取不到对象只能返回 null，界面上表现为「规格莫名消失」。

> [!IMPORTANT] **[卡点 3：子表是全量提交，漏传等于删除]** 品名编辑对两张子表做全量比对：以本次提交数组中出现的 `id` 集合为准，原有明细中不在该集合里的**一律删除**。传 `null` 或 `[]` 表示清空该品名下对应子表的全部明细。

> [!IMPORTANT] **[卡点 4：ABP 软删除不级联，子表必须显式删]** `AbpDbContext` 在 `SaveChanges` 前会把 `ISoftDelete` 主表的 `EntityState` 从 `Deleted` 改回 `Modified`，等 EF 执行级联时主表已不是删除态，**子表一条都不会被删**（即使外键配了 `Cascade`）。因此 `DeleteAsync` 在软删主表之前用带谓词的批量删除显式清理两张子表。

> [!IMPORTANT] **[卡点 5：历史自由文本数据丢失]** `Model`、`Specification` 两列被物理删除，原有单据上手写的规格/型号文本**无法自动迁移**成 id（文本没有对应的子表明细，也无法可靠反查）。上线后历史单据这两列为空，需要业务侧按需重新选。

# 8. 避坑指南 (Pitfalls)

- **`CodeGoods` ≠ `GoodsInfo`**：两者中文名都叫「商品信息」。`OrderCtn.CodeGoodsId` 指向 `CodeGoods`（`App_CodeGoodses`），规格/型号子表也挂在它上面；`GoodsInfo`（`App_GoodsInfos`）是仓库/库存模块的品名，没有这两张子表。改代码和文档时别串台。
- **切换品名不清空规格/型号 = 必报错**：这是前端最容易漏的联动。
- **子表全量提交**：前端必须回传保留行的 `id`，只提交增量会导致其余明细被删除。
- **软删除不级联**：新增任何 `CodeGoods` 子表都要在 `DeleteAsync` 里补一条显式批量删除。
- **删除明细前必须查引用**：否则箱子上的 id 会指向已软删明细，界面表现为规格/型号凭空消失。
- **AutoMapper 元素映射**：主表 DTO 加了集合成员、箱表 DTO 加了导航对象后，元素类型必须有 TypeMap，否则运行时 `Missing type map configuration`；本项目未启用 `AssertConfigurationIsValid`，启动阶段发现不了，只在真实请求时报错。
- **局部更新不要调 `UpdateAsync`**：本项目 ABP 的 `Update` 会把整行标记为 `Modified` 产生全列 UPDATE，依赖 UoW 的 `SaveChangesAsync` 即可只更新改动列。
- **返回是升序**：`SortId` 升序，与新建/编辑时提交的数组顺序一致，前端直接按返回顺序渲染即可。
- **规格/型号没进 `BasicDataCache`**：它是品名的子表而非小字典表，走按 id 批量查询；不要图省事塞进整表缓存。
