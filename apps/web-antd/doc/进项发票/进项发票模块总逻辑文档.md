# 1. 业务背景说明 (Background)

**白话解释：**

销项是本系统把票开出去；进项是税局/开票接口发票池里**已经开给我们（购方）**的票。系统每 5 分钟按公司把发票池里的票拉下来，落到本地进项发票表；也可以按公司手动拉一次（可带号码、开票时间等条件）。财务在列表和详情里查看。

票不会在本系统里「开出来」，也不能在本系统里改票面。本地只是发票池的副本：这家公司从没拉成功过时，按发票池**更新时间**取最近 5 天；之后只拉更新时间落在上一轮游标附近的增量。更早的票用手动拉取。

购方税号、开票凭据与销项开票是同一套，取自**公司资料**（统一社会信用代码、appKey、appSecret、令牌）。没配齐的公司本轮直接跳过。

对外文案只说「进项发票 / 开票接口」，不出现外部供应商名称。

# 2. 功能与操作说明 (Features & Operations)

控制器 `InputInvoiceAdmin`。数据由后台 `BackgroundWorker` 或手动拉取写入。前端查看 + 手动拉取，不能改票面。

| 功能 | 接口 / 任务 | 操作路径与结果 |
| :-- | :-- | :-- |
| **定时拉取** | `InputInvoicePullWorker`（进程启动立刻跑一轮，之后每 5 分钟） | 遍历启用租户 → 已配开票凭据的公司 → 查发票池列表 → 每 100 张查明细 → 按「公司+发票号码+发票代码」写入或更新。**有发票号且版式地址已返回**才下载 OFD/PDF/XML/电子凭证存附件 |
| **手动拉取** | `POST /api/services/app/InputInvoiceAdmin/PullAsync` | 指定公司（必填），可选号码/开票时间等条件，现查发票池并落库。落库与存附件规则同定时任务。**不推进**定时游标 |
| **分页列表** | `GET /api/services/app/InputInvoiceAdmin/GetPagedListAsync` | 按数据权限看本公司进项票。默认按开票时间倒序。含附件、是否已使用、关联付费申请。**筛选条件覆盖列表返回的全部业务字段**：号码/流水号/销方抬头/购方名称/开票人/备注模糊，票种/状态/蓝红/精确等级/特定业务/查验/报销/签收/入账枚举精确，开票/归集/池更新/落库/更新五组时间范围，含税/不含税/税额三组金额范围，创建人与修改人，以及是否含冲红、是否已使用、是否已拉明细；发票类型/购方名称/销方名称还可按「未填写」筛 |
| **分组统计** | `GET /api/services/app/InputInvoiceAdmin/GetGroupedListAsync` | 与列表**同一套筛选条件和数据权限**，按发票类型/购方名称/销方名称分组返回每组条数（按条数倒序，不分页）。供列表页的分组导航用，点某组再带对应筛选条件调列表 |
| **详情** | `GET /api/services/app/InputInvoiceAdmin/DetailAsync` | 票头 + 商品明细 + 特定业务 + 附件 + 是否已使用 + 关联付费申请 |

权限：`Admin.InputInvoice` 下增删改查（`Add` / `Get` / `Edit` / `Delete`）。列表、详情用查看；手动拉取用**新增**。没有票面新增/编辑/删除接口。

申请把税局票灌进发票池（`applyDownload`）**不在定时任务和手动拉取里**。那是按月限额的异步申请，乱调会把额度打满。池里还没有的票，拉不来。

# 3. 状态流转说明 (Status Transitions)

本系统不改发票状态。发票池里已定码的字段**落到本地一律是枚举（库列 int）**。对方 JSON 有时是字符串、有时是数字，拉取时转成本地枚举；未收录的码落空，不挡整张票入库。

票种 `InputInvoiceLine` 对方用字母（`p`/`pc`/`bs` 等），本地按枚举存 int，调发票池时再转回字母。数字码（状态、蓝红、入账等）本地枚举值与对方数字一致，入账状态对方补零成 `01` 只在请求对方时补。

| 字段 | 本地枚举 | 说明 |
| :-- | :-- | :-- |
| `invoiceStatus` | `InputInvoiceStatus` | 1正常 … 9已全部冲红。不是费用开票状态 `InvoiceStatus`，也不是销项 `InvoiceIssueStatus` |
| `invoiceType` | `InputInvoiceType` | 1蓝票 2红票。不是销项票种 `p/c/s` |
| `invoiceLine` | `InputInvoiceLine` | 票种。接口 JSON 为数字 |
| `hasDetail` | `bool` | 是否已拉到明细（含商品行为空的票） |
| 拉取游标 `LastError` | 空=最近一轮成功 | 只写在 `App_InputInvoicePullStates`，不对外接口返回 |

列表筛选条件的口径是**「列表出参里的业务字段都要能筛」**：出参有的字段就有对应筛选（字符串模糊、枚举精确、时间与金额成对的起止），只有版式文件地址 `PdfUrl` 和发票图片地址 `PictureUrl` 例外，它们是外链、按内容筛没有意义。 **仅详情返回的字段一律不提供列表筛选**（风险等级、计算抵扣种类、查验状态(新)与查验时间、报销/签收/入账的时间与人、入账失败原因、机动车与航空票头）——列表页没有这些列，筛出来用户看不到命中的是什么值。以后要按它们筛，必须先把字段加进 `InputInvoiceListDto`，两件事一起做。

# 5. 核心业务卡点 (Business Blockers)

> [!IMPORTANT] **[卡点 1：没配开票资料的公司不会出现进项票]** 公司必须同时有统一社会信用代码、appKey、appSecret。缺任何一项本轮跳过。令牌与销项相同：沙箱可不填，正式环境没填会在开票接口报错并记到该公司拉取游标的 `LastError`。

> [!IMPORTANT] **[卡点 2：定时任务不会申请下载]** 申请下载有月份额度，税局还要审核，通过后票才进池。定时任务只拉**已经在池里的票**。池是空的，列表就是空的，不是接口坏了。

> [!IMPORTANT] **[卡点 3：首拉只覆盖最近 5 天]** 从未拉过的公司按发票池**更新时间**取「现在往前 5 天」，不是开票日期，也不是池里全部历史。5 天以前进池、之后再也没更新过的票，定时任务不会补，要用手动拉取。上一轮没结束，下一轮直接跳过。

> [!IMPORTANT] **[卡点 4：单公司失败不影响其它公司]** 某家公司凭据错、接口超时，只记该行 `LastError`，其它公司和租户继续拉。游标 `LastPullTime` 不推进，下一轮会按原窗口重拉（upsert 幂等）。

> [!IMPORTANT] **[卡点 5：附件只在开票完成后才存]** 没有发票号、或版式文件地址还没返回，本轮不下载。等下一轮该票带着号码和地址再被拉到时补存。下载失败只记日志，不回滚票头；已有同名附件跳过。`pictureUrl` 不当文件存。

> [!IMPORTANT] **[卡点 6：手动拉取不推进定时游标]** 手动拉是「现在把符合条件的票同步进来」。带筛选时更不能把 `LastPullTime` 改成现在，否则定时任务会跳过窗口外的票。公司未配开票资料时直接报错，不会像定时任务那样默默跳过。

> [!IMPORTANT] **[卡点 7：已使用只认发票号]** 进项票和付费申请发票没有外键。列表/详情的 `isUsed`、筛选 `isUsed`、嵌套 `paymentApplication` 都按发票号精确相等判断。不比对发票代码。付费申请侧发票号租户内不可重复，所以一条进项最多挂一条付费申请。

> [!IMPORTANT] **[卡点 8：名称分组的「未填写」是 null 和空串合起来的一组]** 发票池给的购方名称/销方名称有时是 `null`、有时是空串，同一批数据里两种都有。分组统计把两者**合并成同一组**返回（`id`、`name` 都是 `null`），列表的 `payerNameEmpty` / `sellerHeaderEmpty` 也按「`null` 或空串」筛，两边条数才对得上。名称分组的 `id` 回填到列表走的是**模糊匹配**（`payerName` / `sellerHeader` 本身是模糊筛选），所以某个名称是另一个名称的子串时，点进去的列表条数会比分组的 `count` 多，这不是统计错了。

# 6. 定时拉取逻辑

```
进程启动 / 每 5 分钟
  若上一轮还在跑 → 跳过
  查出所有启用租户
  每个租户：查出已配开票凭据的公司
    读该公司 LastPullTime
      空 → updateTimeStart = 现在 - 5 天，updateTimeEnd = 本轮开始时刻
      有 → updateTimeStart = LastPullTime - 2 分钟，updateTimeEnd = 本轮开始时刻
    分页查列表（pageSize=50, level=1）
    每页先捞本地已有票的同步时间，挑出真的需要同步的票（见下面「跳过没更新的票」）
    只对需要同步的票按最多 100 张批量查明细；一批失败则这些票只用列表字段落库
    按 公司+发票号码+发票代码 upsert 票头
    命中已有票时无条件盖 LastModificationTime（这一轮票面值没变也盖）
    明细成功则硬删商品行再插入，并刷新特定业务 JSON
    本页落库提交后：有发票号且有版式地址的票，下载 OFD/PDF/XML/电子凭证存附件（同名跳过）
  该公司全部页成功后才写 LastPullTime / LastSuccessTime，清空 LastError
  整轮结束后 Worker 记一条 Info 日志：本次写入或更新张数、本轮开始时间、耗时
```

### 6.0 跳过没更新的票（定时与手动同一套）

每页票落库前先按「公司+发票号码」把本地已有的票捞出来，逐张比时间：

```
对方时间 = max(归集时间 collectionTime, 更新时间 updateTime)
本地时间 = max(CreationTime, LastModificationTime)
对方时间 < 本地时间 - 重叠分钟数  →  跳过这张票
```

跳过的票**不查明细、不写票头、不计入返回张数**，所以重复拉同一批票 `count` 会是 0，日志里的「本次写入或更新 n 张」也只算真的同步过的。省掉的明细查询是这里最大的收益——明细是按 100 张一批的外部调用，一轮里绝大多数票其实都没变。

几个要点：

- **附件不受跳过影响**，仍会尝试补齐。附件缺失是我们当时没下成功、跟对方有没有更新无关，跳过它就等于「某张票的 PDF 下载失败过一次，之后永远补不上」。同名判重照旧，不会重复下载。
- **比较时把本地时间往前放宽一个重叠分钟数**（`InputInvoicePullOverlapMinutes`，与游标用的是同一个值）。两边时钟不齐时宁可多同步一次，也不能漏掉更新——本地时钟快几分钟的话，严格比较会把对方之后的真实更新judge成「更早」而跳掉。
- **对方两个时间都没给**时无从判断，一律同步。
- 这套判断依赖 `LastModificationTime` 每轮同步都被盖新（见第 4 节该字段），否则本地时间不前进，同一张票会每轮重复同步。
- **手动拉取指定发票号码也照样跳过**。想强制重新同步某张票时，时间戳判断不认「人工意图」，只能等对方那边更新，或先把本地这条记录的附件/记录处理掉。

**本轮汇总日志**：`InputInvoicePullWorker` 每轮结束写一条 `Info`，格式为 `进项发票拉取完成 本次写入或更新 {n} 张 开始时间 {yyyy-MM-dd HH:mm:ss} 耗时 {s} 秒`。

日志落在 **`App_Data/Logs/Logs.txt`**（相对进程工作目录：VS 调试是 `src\CsprojBuilder.Web.Host\`，部署后是站点根目录），满 10MB 滚动、保留 10 个备份。配置在 `src\CsprojBuilder.Web.Host\log4net.config`。该文件的 `root` 级别是 `WARN`，所以这条汇总**必须**靠单独给 `CsprojBuilder.App.InputInvoice.InputInvoicePullWorker` 和 `...InputInvoicePuller` 两个 logger 配 `INFO` 才写得进去（已配，见该文件末尾）。改动这两个类的命名空间或类名时要同步改 logger 名，否则汇总日志会静默消失。张数是所有租户所有公司的合计（`PullAllAsync` 的返回值），**中途失败的公司不计入**——它那份已经单独记了 `拉取进项发票失败 tenant=… org=… 公司=…` 的 `Warn` 并落到该公司游标行的 `LastError`。一张票在本轮被写入和被更新都算 1 张，**因为对方没更新而跳过的不算**，所以「0 张」是常态：表示这个窗口内没有新票、也没有票被对方改过，不代表任务没跑。排查「票没进来」时先看这条日志有没有出现，再看是不是被「上一轮进项发票拉取尚未结束，跳过本轮」挡掉了。

不调用申请下载。协议字段、票种码、状态码见 `文档/诺诺发票/诺诺开票模块总逻辑文档.md` 的 2.4。

### 6.1 版式文件附件

与销项发票开出同一套附件模块。`ModuleTypeId = 160120`，`ItemId` 为进项发票主键。

**何时存：** 发票号码已有，且 `pdfUrl` / `backupUrl` / `xmlUrl` / `voucherUrl` 至少一个可下载。号码或地址未出 = 开票还没完成，本轮不存。

**附件名是「发票号 + 扩展名」**，不带来源后缀；只有电子凭证例外，保留 `-电子凭证` 用来和数电 xml 区分。扩展名按地址判：识别不出时 pdf 类按 `.pdf`、xml 类按 `.xml`，地址里带 ofd 则存 `.ofd`。

**存哪些：**

| 来源字段 | 附件名 | 说明 |
| :-- | :-- | :-- |
| `pdfUrl` | `{发票号}.pdf` 或 `{发票号}.ofd` | 版式正本 |
| `backupUrl` | 同上 | 备份源文件。**与正本同名，正本已存在或本轮已下成功就不存它** |
| `xmlUrl` | `{发票号}.xml` | 数电 xml |
| `voucherUrl` | `{发票号}-电子凭证.xml` | 电子凭证。它不是发票版式本身，名字带「电子凭证」区分，**不会被数电 xml 挤掉，两个并存** |
| `pictureUrl` | **不存** | 在线查看页短链，存下来打不开 |

所以一张票最多留三个附件：一个 pdf/ofd、一个 xml、一个电子凭证 xml。正本与备份撞名，取的优先级是上表顺序（正本 → 备份），**正本下载失败时备份会顶上** （`existing` 是下载成功后才记名字的），下轮再拉到这张票还会继续尝试补齐。

列表、详情都返回 `attachments`。`clientVisible` 为 false（进项给内部看，不给客户）。

**存储路径**沿用全仓库约定的 `{媒体类型}/{yyyyMMdd}/{时间戳+随机数}{扩展名}`（与 `UploadController`、发票开出、付费申请打包一致），物理文件名里不含发票号。要按票找文件走附件表：`AttachmentItem.ItemId` = 进项发票 id，`Attachment.FriendlyFileName` 才是「发票号+扩展名」。物理路径与显示名是两套，判重只看显示名。

> [!IMPORTANT] **判重看的是文件名，不是内容。** 同名就跳过、不更新，所以票被红冲重开后对方换了版式文件内容、但地址扩展名没变时，本系统仍挂着旧的那一份，这种「内容过期」不会自愈（「附件缺失」会：下次该票再被拉到时补下）。要改成以对方为准，得把判重键换成能反映版本的东西（如存 `pdfUrl` 原文比对），并在替换时删掉旧的 `AttachmentItem` 与 `Attachment` 行。
>
> **2026-09-08 改名前的存量附件不会被清理**：老名字 `{发票号}-备份.pdf`、`{发票号}-凭证.xml` 匹配不上新名字，会原样留在票上。这些票下次再被拉到时，会按新名字各自补一份（备份只在没有正本时补），于是同一张票上新旧名字并存——不影响业务，前端按 `attachments` 数组展示即可；要清干净只能人工处理存量。

### 6.2 手动拉取

```
POST PullAsync
  companyId 必填（部门则向上找到公司）
  校验数据权限、开票资料
  有发票号码/代码/数电号码 → 只查这些票，不分页
  否则按筛选条件分页扫池（pageSize=50）
  跳过没更新的票、查明细、upsert、存附件：与定时任务同一套
  不写 LastPullTime / LastSuccessTime / LastError
  返回本次写入或更新的张数（跳过的不算，所以重复拉同一批票返回 0）
```

## 7.4 本模块数据被谁读走

进项发票除了自己的列表与详情，还被**付费申请**读走：

| 消费方 | 读什么 | 口径 |
| :-- | :-- | :-- |
| `PaymentApplicationAdmin.GetInputInvoiceListAsync` | 按公司+结算对象挑可用的进项发票，返回 `InputInvoiceSimpleDto` | 公司按 `OrgId` **直接相等**比对（不向上解析组织串，调用方必须传公司 id）；结算对象靠「客户开票信息 `TaxNum` = 进项 `SellerTaxNo`」搭桥（可再传 `ClientInvoiceInfoId` 收窄到某一条开票信息的税号）；只取近一个月、发票号未被付费申请占用的；附件只给首个 pdf |

反向关系（进项发票列表/详情上的 `isUsed` 与 `paymentApplication`）看的是同一张付费申请发票子表，两边判「已被占用」的口径一致：都按**发票号**精确比对，都不算指向已删付费申请的孤儿行。改其中一边的口径时另一边必须同步，否则会出现「进项列表显示未使用、付费申请里却挑不到」。
