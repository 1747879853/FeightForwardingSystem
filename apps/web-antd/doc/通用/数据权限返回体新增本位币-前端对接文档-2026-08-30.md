# 一、一句话说明

所有**带数据权限的业务单据**（继承 `DataPermissionFullAuditedEntityDto` 的返回体）统一新增两个字段： `localCurrencyId` 和 `localCurrencyCode`，值取自**该单据所属公司**配置的本位币。 **两个报表接口**虽然不继承这个基类，也按同样口径加了这两个字段（见 4.16）。

同时 `orgs`（组织串）数组的元素新增 `isCompany`，用来标识组织串里哪一级是公司。

# 二、新增字段

## 2.1 单据层（`localCurrencyId` / `localCurrencyCode`）

| 字段名              | 类型             | 说明                            |
| :------------------ | :--------------- | :------------------------------ |
| `localCurrencyId`   | `long \| null`   | 本位币id（指向币别表）          |
| `localCurrencyCode` | `string \| null` | 本位币代码，如 `"RMB"`、`"USD"` |

**取值口径**：由单据的 `orgId` 沿组织串向上找到**所属公司**（`isCompany = true` 且最接近本单据组织的那一级），取该公司配置的本位币。

> [!IMPORTANT] **不是「组织串上第一个有本位币的节点」。**
>
> `orgs` 是从**最高级组织到本组织**排列的。本位币按规定只配在公司节点上，但集团等上级节点历史上也可能配过。如果前端自己写 `orgs.find(o => o.localCurrencyId)` 去取，会取到**集团**的而不是公司的。
>
> **请直接用单据上的 `localCurrencyId` / `localCurrencyCode`，不要自己从 `orgs` 里找。**

**以下三种情况为 `null`**：

1. 单据的 `orgId` 为空；
2. `orgId` 对应的组织未归属任何公司；
3. 所属公司没有配置本位币。

## 2.2 组织串元素新增 `isCompany`

`orgs` 数组的元素类型 `OrganizationUnitSimpleDto` 新增一个字段：

| 字段名      | 类型   | 说明                         |
| :---------- | :----- | :--------------------------- |
| `isCompany` | `bool` | 是否公司节点，`false` 为部门 |

完整结构：

```json
"orgs": [
  { "id": 1, "name": "XX集团", "isCompany": true,  "localCurrencyId": null, "localCurrencyCode": null },
  { "id": 2, "name": "上海XX", "isCompany": true,  "localCurrencyId": 1,    "localCurrencyCode": "RMB" },
  { "id": 3, "name": "海运部", "isCompany": false, "localCurrencyId": null, "localCurrencyCode": null }
]
```

上例中单据的 `localCurrencyId` = `1`、`localCurrencyCode` = `"RMB"`（取「上海XX」这一级，因为它是最接近本组织的公司）。

# 三、破坏性变更（客户对账）

> [!WARNING] **只有客户对账有破坏性变更，其余模块都是纯新增字段。**

`StatementDto`（客户对账列表与详情）删掉了两个重复字段：

| 原字段 | 现在 | 前端要怎么改 |
| :-- | :-- | :-- |
| `localCurrency`（对象，含 `code`） | **已删除** | 读 `localCurrency.code` 的地方改成读 `localCurrencyCode` |
| `localCurrencyId`（`long?`） | 字段名保留，但**取值口径变了** | 以前是「组织串上第一个有本位币的节点」，现在是「所属公司」。集团配过本位币的租户，这个值会变 |

`localCurrencyReceiveAmount`（本位币应收汇总）与 `localCurrencyPayAmount`（本位币应付汇总）**没有变**，照旧。

# 四、接口清单

以下接口的返回体已带上 `localCurrencyId` / `localCurrencyCode`。「返回结构位置」列写的是这两个字段在 JSON 里的路径，`items[]` 指分页返回的 `items` 数组。

## 4.1 付费申请

服务名 `PaymentApplicationAdmin`。

| 接口地址 | 方法 | 说明 | 返回结构位置 |

>

## 4.16 报表（不继承基类，但同样返回这两个字段）

服务名 `ReportAdmin`。报表的返回体是独立实现的，**不继承 `DataPermissionFullAuditedEntityDto`**，但为了标注合计金额的币种，行级同样加了这两个字段，取值口径完全一致（主单 `orgId` → 所属公司 → 本位币）。

| 接口地址 | 方法 | 说明 | 返回结构位置 |
| :-- | :-: | :-- | :-- |
| `/api/services/app/ReportAdmin/GetProfitReportListAsync` | POST | 利润报表 | 数组元素（行级，与 `accountDate` 同层） |
| `/api/services/app/ReportAdmin/GetArrearsReportListAsync` | POST | 欠费报表 | 数组元素（行级） |

> [!IMPORTANT] **报表的合计字段就是本位币金额**（`totalReceivable` / `totalProfit` / `totalUnReceived` 等）， `localCurrencyCode` 是它们的计量单位，展示时要配着一起显示，不要写死「元」或「RMB」。
>
> 一次查询会跨多个公司，**不同行的本位币可能不一样**，所以不要把某一行的币种当成整张报表的单位，也不要跨行直接加总合计列。

# 五、有这两个字段但恒为 null 的地方

这些返回体在结构上带这两个字段（因为继承了同一个基类），但后端没有填充，**前端不要指望从这里取值**。

| 位置 | 原因 |
| :-- | :-- |
| 提成配置 `CommissionConfigDto` 的全部接口 | 提成配置的数据权限**暂时停用**，`orgId` 不写库，`orgs` 也是空的，所以本位币无从解析 |
| `/api/services/app/BankStatement/GetPagedListAsync`（非管理端银行流水列表） | 该接口未做数据权限字段填充，`orgs` 同样为空 |
| `/api/services/app/BankStatementAdmin/GetReceiveSettlementPagedListAsync` | 同上 |
| `/api/services/app/PaymentApplicationAdmin/PayAppTaskListAsync` | 返回体是平铺结构，压根没有这两个字段（不是 null，是不存在），见 4.1 |

> 上面这几条都是既有情况，本次没有改动。如果这些列表页需要展示本位币，请提出来，后端补一行填充即可。

# 六、费用行上的本位币（`orderFee`）不在本次范围内

费用对象 `OrderFeeDto` 上另有一对 `localCurrencyId` / `localCurrency`（**注意后者是对象，不是字符串**），它们不属于本次基类改动，字段与类型都**没有变化**。

本次只是把后端的填充逻辑收敛了一下，取值口径同样改成了「所属公司」（以前是「组织串第一个有本位币的节点」），所以**集团配过本位币的租户，这个值可能会变**。

目前会填充费用本位币的接口：业务费用分页列表、费用任务列表与详情、客户对账的费用分组与详情、付费申请的费用分组与详情、更改单详情。

> [!NOTE] **业务费用详情 `/api/services/app/OrderFeeAdmin/DetailAsync` 不返回费用本位币**（`localCurrencyId` / `localCurrency` 恒为 null），这是既有情况，本次未改。需要的话请提。
